질문 하나가 답이 되기까지 — 온톨로지(그래프)로 범위를 잡고, RAG(문서 검색)로 정확한 글을 찾고, 그 글만 근거로 답합니다.

  1. ① 질문 읽기어느 사업·연도·문서(계획서·실적·평가)를 묻는지, 계획 대비 실적·앞 단계 사업 같은 관계를 묻는지 알아봅니다. 지금: {{ '27B 가 질문을 온톨로지 말로 읽음(실패하면 이름 맞추기)' if flow.model_read_on else '이름 맞추기(사업 이름·「N차년도」·갈래 낱말) — 27B 읽기는 측정 뒤 켭니다' }}

온톨로지설계도 — 「사업에는 연차가, 연차에는 계획서·실적보고서가 있고 계획과 실적은 짝」 같은 종류와 관계의 규칙
지식그래프설계도대로 채운 실제 내용 — 「LINC 3.0 → 2023 → ○○ 계획서 → 3절」
RAG문서 조각에서 질문에 맞는 글을 찾아 답의 근거로 붙이는 방식

왜 기성 도구 대신 직접 만들었나

LangChain·LlamaIndex 의 RAG, Microsoft GraphRAG, Neo4j 같은 그래프 DB 를 그대로 쓰지 않고 지식그래프·온톨로지·검색을 우리 코드로 만들었습니다. 부품(PostgreSQL·Kiwi·임베딩 모델 등)은 오픈소스를 씁니다 — 「핵심 기술」 탭.

문서가 행정 문서다
한글(hwp)·스캔 PDF·병합 칸이 많은 표가 대부분이라 범용 도구의 문서 자르기로는 표와 절이 깨집니다. 절·표·조문 단위로 자르는 규칙과 판독을 우리 문서에 맞춰 만들었습니다.
사업 구조가 정해져 있다
사업 → 연차 → 계획서·실적보고서, 계획↔실적 짝, 앞·뒤 단계 사업처럼 관계가 분명합니다. 범용 GraphRAG 는 글에서 관계를 LLM 으로 뽑아 비용이 크고 틀릴 수 있어, 파일 이름·폴더·외부 확인 장부 같은 근거로 관계를 짓고 근거를 함께 적습니다.
권한과 보안
부서·열람 등급·학생 공개를 검색 단계에서 걸러야 하고(절대 규칙 4), 원문이 학교 밖으로 나가면 안 됩니다. 폐쇄망·자체 서버에서 돌고, 권한 필터가 검색 SQL 안에 들어가도록 직접 짰습니다.
수치를 지어내지 않게
답의 수치는 근거에 있는 것만 쓰도록 근거 조각·출처를 끝까지 들고 다닙니다. 단계마다 무엇을 왜 골랐는지 기록(리즈닝 단계)이 남아 검수와 학습 데이터로 이어집니다.
운영 규모와 비용
그래프(규모는 위 「현재 규모」의 그래프 노드)를 이미 쓰는 PostgreSQL 한 곳에 두어 따로 그래프 DB 를 운영하지 않습니다. 측정 도구(scripts/173·184)로 바꿀 때마다 수치를 견줍니다.
