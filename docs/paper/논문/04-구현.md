# 4. 구현

이 장은 AURA 의 기능을 하나씩 설명한다. 절마다 사용 설명서처럼 먼저 그 기능으로 무엇을 하는지(목적), 화면에서 어떻게 쓰는지
(사용 방법), 실제 업무에서는 어떻게 쓰이는지(업무 시나리오)를 보이고, 이어서 왜 그렇게 만들었는지(설계 선택과 이유), 어떻게

둔다. 시나리오에 나오는 부서·사업·값은 설명을 위한 예이며 실제 문서 내용이 아니다.

## 4.1 문서 반입·OCR·복원

### 4.1.1 목적

학교 원본 문서를 형식에 상관없이 읽어 검색할 수 있는 처리본으로 바꾸고, 서류 종류·사업·연도로 정리한다. 원본은 PDF(디지털·스캔),
한글(hwp·hwpx), 워드·엑셀·파워포인트, 옛 오피스 형식, 사진이 섞여 있다. 담당자는 원본이 어느 폴더에 어떤 이름으로 있든 라이브러리에서
본문 제목으로 찾고, 원본 모양 그대로 열어 보며, 그 글이 검색과 초안의 근거로 쓰이기를 기대한다.

### 4.1.2 사용 방법

문서가 들어오는 길은 넷이다. 학교 원본 동기화는 자동이고, 나머지 셋은 담당자가 한다.

1. 라이브러리에 올리기. 사이드바 「라이브러리」 → 「문서」 탭 → 「문서 올리기」를 누른다. 올리기 창에서 「파일(여러 개 가능)」을 고르고,
   폴더(「폴더 없이」도 됨), 사업(「사업 없음」 또는 「＋ 새 사업 등록…」), 「사업 연도(선택)」, 「업무 갈래」(기본 「자동으로 정하기」)를
   정한 뒤 「올리기」를 누른다. [그림 4-1]
2. 채팅에 첨부하기. 채팅 입력창의 클립 단추(「파일 또는 사진 첨부」)를 누르거나 파일을 창에 끌어 놓는다(「파일을 놓으면 첨부됩니다」).
3. 프로젝트에 넣기. 프로젝트 화면의 「프로젝트 문서」 › 「문서 추가」에서 「내 컴퓨터에서 올리기」나 「문서함·구글 드라이브에서 가져오기」를
   고른다.
4. 학교 원본은 따로 할 일이 없다. 학습 장비의 사업별 폴더에 들어온 원본은 주기 동기화로 원본 장부에 잡히고 처리된다. 원본 장부는
   라이브러리의 「원본 보관소」 탭(/archive)에서 「목록」·「카드」·「사업별로 보기」로 본다. [그림 4-2]

### 4.1.3 업무 시나리오

기획처 담당자가 지난 3 년치 결과보고서 묶음(스캔 PDF 일부, hwp 다수, 엑셀 현황표)을 받았다. 담당자는 라이브러리에서 「문서 올리기」로
파일을 한꺼번에 올리고 사업과 연도만 고른다. 몇 분 뒤 라이브러리 목록에 「최종_수정본(2).hwp」 같은 파일 이름 대신 본문 제목인
「2024년 ○○사업 결과보고서」가 보인다. 서류 종류는 「결과보고서」로, 엑셀은 「현황표」로 붙었다. 스캔 PDF 를 열어 「원문」 탭에서 표
부분을 드래그하자 글자가 그대로 골라진다. 담당자는 같은 날 채팅에서 「2023년 결과보고서의 취업률 목표와 실적」을 묻고, 답의 출처를 눌러
방금 올린 스캔본의 표가 열리는 것을 확인한다.

### 4.1.4 설계 선택과 이유

하나의 처리기. 들어오는 길이 넷이지만 모두 같은 처리기(app/pipeline.py 의 DocumentProcessor)를 거친다(ADR-0049). 길마다 처리가 다르면
같은 문서가 길에 따라 다르게 검색된다.

형식별로 다른 읽기 길. 한 OCR 엔진으로 전부 읽으면 글자층이 멀쩡한 디지털 PDF 까지 오인식한다. 실제로 MinerU[19][20] 가 글자층 있는 문서를
스캔으로 다뤄 「기초과학」을 「기추과하」로 읽은 일이 있었다. 반대로 스캔본을 글자층으로 읽으면 깨진 한자만 남는다. 그래서 문서마다
글자층을 먼저 재고 길을 나눈다.

복원 보기는 배경 그림 + 투명 글자층. 블록 좌표를 다시 배치하는 방식, 글자 좌표만 직접 그리는 방식, 원본 그림 위에 투명 글자층을 얹는
방식을 실물 렌더로 비교했다. 첫째는 잘림·중복·왜곡이 생겼고, 둘째는 표 괘선과 서식을 나타내지 못했다. 셋째가 원본 모양과 글자 고르기를
둘 다 지켜 채택했다(실험 로그 3 절).

판정은 모델, 후보와 형식은 코드. 서류 종류를 제목 낱말 규칙으로 정하자 「주간업무보고」를 결과보고서로, 견적서를 계획서로 보는 오판이
많았고 규칙을 덧대면 사례 짜맞추기가 됐다. 그래서 종류와 사업 판정은 Writer 27B 가 하고, 코드는 후보 목록·출력 형식·재확인 관문을
맡는다.

### 4.1.5 구현

[그림 4-4] 는 한 문서가 처리되는 순서다.

```
 원본 파일 ── 실제 형식 확인(확장자 없거나 틀리면 파일 머리로)
    │
    ├─ 디지털 PDF ─ 표본 6쪽 글자 충분 · 깨진 글자 비율 < 0.15 ─▶ pdfium 글자 좌표 직독
    │                                                          + MinerU 구조(표·2단·읽기 순서) 위에 원본 글자 덮어쓰기
    ├─ 스캔 PDF ─── 쪽당 200자 미만 또는 깨진 글자 ≥ 0.15 ─▶ 짧으면 27B 이미지 판독(최대 30쪽), 기본 MinerU
    ├─ 사진 ─────────────────────────────────▶ 27B 이미지 판독 → MinerU OCR → tesseract
    ├─ hwp ── kordoc(판 고정) → 실패 시 pyhwp      hwpx ── 자체 OWPML 파서(표·글상자·머리말)
    ├─ docx·xlsx·pptx ── kordoc → python-docx·openpyxl·python-pptx (쪽당 60자 미만이면 MinerU 로 다시)
    └─ 옛 형식(xls·doc·ppt·hwp3) ── LibreOffice 로 새 형식 변환 뒤 위의 길
    │
    ▼
 표 정리 → 개인정보(4.2) → 조각 나누기 → 서류 종류(27B) → 사업 분류 → 판본 묶기 → 문서 이름 → 색인(4.3)·그래프(4.4)
```

[그림 4-4] 문서 한 건의 처리 순서

원본 장부와 동기화. 원본 장부(archive_files 표, app/archive.py)는 원본 파일 하나가 한 줄이고 경로·크기·수정 시각·사업·처리 상태·
서류 종류·연도·차수·중복 대상·등록 문서 번호를 담는다. 운영 서버는 10 분 주기로 학습 장비 원본 목록을 훑어 새로·바뀜·옮김·없어짐의
차이로 장부를 갱신하고(scripts/170, 잠금으로 겹쳐 돌지 않음), 학습 장비 쪽 목록이 바뀌면 그 표시를 1 분 안에 받아 바로 동기화한다.
같은 파일 찾기는 이름·크기가 같은 묶음 안에서만 sha256 을 내어 비교해 지문 계산 비용을 줄인다.

이미지 판독. 27B 이미지 판독은 표를 병합 칸(rowspan·colspan)이 살아 있는 HTML 표로, 제목을 머리말로 쓰도록 지시한다. 흘린 손글씨는
「(판독 불가)」로 적게 해 지어내지 않게 한다. 대량 스캔 판독은 처리량 때문에 학습 장비에서 MinerU 로 했다(ADR-0007). 글자층 직독은 pdfium[22], 사진의 마지막 물러남은 tesseract[23], 옛 형식 변환은 LibreOffice[27] 다.

표 처리. 표 조각은 칸마다 [행, 열, 행 병합, 열 병합, 머리칸 여부, 글] 로 저장하고, 화면은 이것을 병합 표로 그린다. 검색·인용용 평문은
행마다 칸을 「 | 」로 잇되, 가로 병합은 첫 칸에만 한 번 쓰고 세로 병합 때문에 되풀이만 하는 행은 내지 않는다(app/render.py, ADR-0027).
처음 방식은 병합 칸을 칸마다 채워 「예비군대대 | 예비군대대 | 예비군대대 …」 같은 줄이 검색 잡음이 됐다. 디지털 PDF 의 표는 괘선 좌표와
글자층을 직접 읽어 칸 비율까지 복원한다.

조각 나누기. 사업 문서는 파서가 낸 블록(제목·문단·표·그림 글)을 하나씩 조각으로 만들고(본문 최대 2,000 자, 문서당 최대 2,000 조각),
조각마다 쪽 번호와 소속 절의 제목 경로를 붙인다(app/chunk_path.py). 규정은 「제N조」가 셋 이상이면 조문 단위로 자른다(app/regulations.py).
40 자 미만 조각은 다음 조각과 합치고 1,400 자를 넘으면 줄·문장 단위로 나누며, 실질 20 자 미만 잡음 조각은 뺀다(ADR-0048).

서류 종류 판정. 27B 에게 종류 19 가지와 한 줄 설명, 제목, 폴더, 본문 앞 1,500 자를 주고 {kind, why} JSON 하나를 받는다(app/kind_read.py).
목록 밖 답이나 형식 오류는 버리고 규칙 판정을 남긴다. 검색에서 빠지는 종류(증빙)가 나오면 본문 2,500 자로 한 번 더 확인한다. 본문이 200 자
미만이면 규칙과 엇갈리는 증빙 판정을 받지 않는다. 지시를 고치면 지시 판 번호를 올려 옛 판정을 다시 보고, 판정 줄마다 판정한 모델 정보를 남긴다.

사업 분류. 기준은 사업 장부(kg_external.json)다. 사업마다 정식 이름·다른 이름·기간·주관 부처·전담기관·앞뒤 단계와 그 출처를 담고, 사업의
동일성과 이름 변경은 외부 검색으로 출처를 확인해 적는다. 분류는 규칙(폴더 경로·제목·본문의 장부 이름) → 폴더 단위 판정 → 파일 단위 판정의
세 층이고 뒤의 것이 앞선다(graph/programs.py). 파일 단위 판정은 27B 가 장부 목록 가운데 하나, 「사업 아님」, 「모름」 중에서 근거 한 문장과 함께
고른다(scripts/196). 장부에 없는 이름과 「모름」은 적지 않는다.

판본 묶기와 이름. 제목에서 붙임 번호·괄호·공백을 뗀 열쇠로 후보를 찾고 본문을 8 자 조각 집합으로 비교해, 겹침 0.95 이상은 같은 내용으로
받지 않고 그 아래는 판본으로 잇는다(app/doc_family.py). 가장 가까운 실제 판본 쌍이 0.90 이라 문턱을 0.95 로 두었다. 문서 이름은 공문의
「제목:」 줄 → 본문 제목 줄 → 모델이 짚은 본문 제목 줄 → 군더더기를 걷은 파일 이름 → 「종류 · 사업 연도」 순으로 정한다(app/doc_naming.py).
본문 제목이 파일 이름의 연도·차수·기관 같은 구별 정보를 잃으면 쓰지 않고, 사람 이름은 제목에서 뺀다.

정리. 지출·계약 증빙, 같은 본문 중복, 빈 문서, 도면, 개인 제출물은 라이브러리에서 정리한다(scripts/187). 지우기 전에 문서 행과 딸린
조각·그림·색인·연결을 백업하고, 원본은 원본 보관소의 정리함으로 옮긴다. 관리자는 원본 보관소의 「정리」 칸에서 「목록 보기」·「정리함으로」·
「되돌리기」를 쓴다.

## 4.2 개인정보 가림

### 4.2.1 목적

문서 속 주민등록번호·전화·이메일·계좌·사업자번호·학번·생년월일·성명을 찾아 가린다. 같은 원문이라도 쓰는 곳에 따라 위험이 다르다.
교내 담당자가 업무로 보는 원문을 모두 가리면 일을 할 수 없고, 학습 데이터나 밖으로 나가는 글은 반드시 가려야 한다. 그래서 내부 열람과
학습 반출을 서로 다른 관문으로 나눈다(ADR-0044).

### 4.2.2 사용 방법

관리자가 개발자 화면의 「개인정보·반출 점검」(/dev/pii)에서 설정하고 점검한다. [그림 4-5]

[그림 4-5] 개인정보·반출 점검 — 「내부 마스킹 설정」과 「마스커 자가 점검」 결과 표 (그림 docs/images/figures-1025/f4-05-pii-masking.jpg)

1. 「내부 마스킹 설정」에서 「내부 문서의 개인정보 가리기」 스위치를 켜고 끈다. 켜면 「가릴 항목」에서 항목을 고르고 「설정 저장」을 누른다.
   기본은 꺼짐이다.
2. 「마스커 자가 점검」에서 「자가 점검 실행」을 누른다. 정답을 아는 표본으로 항목별 판정과 가린 결과가 표(항목 · 판정 · 가린 결과 · 비고)로
   나온다. 「전체 항목별 결과 보기」로 펼친다.
3. 「저장 본문 잔여 검사」에서 「잔여 검사 실행」을 누르면 색인에 들어간 본문에서 가렸어야 할 꼴이 남았는지 찾는다. 결과 표는 문서 유형 ·
   잔여 위치 · 문맥 표본이며 표본 속 값은 가려서 보인다.
4. 「과거 유형별 처리 정책」 표에서 문서 유형마다 언제 어떤 까닭으로 처리했는지 기록을 본다.

| 밖으로 나가는 글·수집 자료 | 고위험 꼴을 언제나 한 번 더, 실패하면 내보내지 않음 | 고정 |

### 4.2.3 업무 시나리오

입학처 담당자가 채팅에서 「○○○ 학생의 연락처 알려 줘」라고 묻는다. 권한 점검이 특정인의 개인정보 요청으로 보고 모델을 부르지 않은 채
막으며, 이 시도는 감사 기록에 질문 앞부분만 남는다. 같은 담당자가 「신입생 장학 신청서 양식에서 개인정보 동의 문구가 어디 있지?」라고 물으면
정상 질문으로 답한다. 한편 관리자는 학기 말에 수집 자료를 학습 재료로 내보내기 전에 「개인정보·반출 점검」에서 자가 점검과 잔여 검사를
돌려 결과를 확인한다.

### 4.2.4 설계 선택과 이유와 구현

탐지는 Presidio[47] 위에 한국형 패턴 인식기 8 종을 얹었다(ingest/pii.py). 주민등록번호와 사업자번호는 체크섬으로 검증해 숫자가 우연히 같은 꼴인
경우를 거른다. 계좌·학번·생년월일·성명은 「계좌번호:」·「성명」 같은 이름표 문맥이 있을 때만 잡는다. 이름표 없는 이름까지 잡으면 사업 이름·
기관 이름이 대량으로 가려져 문서를 쓸 수 없게 되기 때문이다. 표에서는 옆 칸의 직위 문맥으로 성명을 한 번 더 가린다.

가림 설정과 정책은 한 모듈(app/privacy_policy.py)에 두고, 밖으로 나가는 글에는 설정과 상관없이 고위험 꼴(주민번호·이메일·휴대전화·카드번호
정규식)을 한 번 더 쓴다. 가림에 실패하면 보내지 않는다(fail-closed). 학습 사본은 가림을 다시 해도 바뀌지 않는 파일만 반출한다.

### 4.2.5 결과

배포 점검의 전체 잔여 검사(10-09)에서 문서 41,764 건·조각 1,973,998 개 가운데 가렸어야 할 잔여는 0 건이었다. 이 검사는 정규식 기반이라
이름표 없는 이름·주소를 놓칠 수 있으므로 완전 제거의 증명은 아니다. 그래서 학습 반출에는 사람 검수를 함께 요구한다.

## 4.3 검색 — 하이브리드와 리랭커

### 4.3.1 목적

질문에 맞는 근거 조각을 열람 권한 안에서 찾는다. 행정 질문에는 사업 약칭·규정 이름·숫자처럼 글자 그대로 맞아야 하는 말과, 「학생이
휴학하려면」처럼 뜻으로 찾아야 하는 말이 함께 있다. 한 방식만으로는 어느 한쪽을 놓친다.

### 4.3.2 사용 방법

담당자는 검색을 따로 다루지 않는다. 채팅에서 질문하면 검색이 돌고, 답 아래 출처와 오른쪽 작업 패널의 「연관 자료」에 근거가 보인다.
제목과 본문을 바로 찾고 싶으면 사이드바 「검색」(Ctrl+K)을 쓴다.

1. 사이드바 「검색」을 누르거나 Ctrl+K 를 누른다.
2. 「문서 제목·본문, 프로젝트, 대화에서 찾기」 칸에 낱말을 넣고 「검색」을 누른다.
3. 결과는 「문서」, 「본문 대목」, 「프로젝트」, 「대화」 네 묶음으로 나온다. 본문 대목을 누르면 문서 화면의 그 자리가 열린다. [그림 4-6]

### 4.3.3 업무 시나리오

학사지원팀 담당자가 「현장실습 학점 인정 기준이 바뀌었나?」라고 묻는다. 어휘 축은 「현장실습」·「학점」이 그대로 든 조문을, 의미 축은
「실습 이수 시간에 따른 학점 부여」처럼 말이 다른 조문을 함께 올린다. 리랭커가 후보 20 개를 질문과 한 쌍씩 다시 읽어 순서를 고치고, 같은
규정의 옛 판 조문이 걸리면 최신 판의 같은 조문으로 바뀐다. 답에는 최신 판 조문이 출처로 달린다. 담당자가 「2022년 기준으로는?」이라고
되묻자 연도를 지정한 질문이라 옛 판이 근거로 쓰인다.

같은 시각 학생 계정으로 「휴학은 최대 몇 학기까지 할 수 있나요?」를 묻는 학생에게는 학생 공개로 지정된 학사 규정만 후보가 된다.

### 4.3.4 설계 선택과 이유

두 색인. 규정 색인(교내 규정·지침·공고를 조문 단위로)과 사업 문서 색인(계획서·보고서·서식·공문 조각)을 따로 둔다. 하나로 합치면 규정
질문에 사업 문서 조각이, 사업 질문에 규정이 섞인다. 두 검색은 서로 기대지 않으므로 동시에 돌린다.

| | 규정 색인 | 사업 문서 색인 |
|---|---|---|
| 조각 | 조문·표제 단위(regulation_chunks) | 블록 단위(doc_chunks) |
| 의미 | Embed v2 | Embed v2, pgvector(grant_vec) |
| 어휘 | Kiwi 명사·IDF | 미리 뽑은 낱말(grant_lex, GIN) |
| 리랭커 | 씀 | 끔 |
| 범위 | 열람 등급·부서·학생 공개 | 열람 등급·RAG 공간 부서, 증빙 종류 제외 |

[표 4-6] 두 색인의 차이

학습한 임베딩. 공개 한국어 임베딩 KURE-v1[29] 은 일반 문장에는 좋지만 「교원업적평가」·「차년도 사업비 이월」 같은 교내 용어와 규정 문체에
약했다. 채택 기준은 단독 지표가 아니라 운영 하이브리드 위에서 후보 진입률이 오르는지로 두었다. v1 은 단독 지표만 오르고 운영 경로에서 이득이
없어 버렸고 v2 를 채택했다(ADR-0021). 다중 벡터 모델 KURE-v2 는 학습 전에도 근접했지만 운영 경로에서 이득이 없어 채택하지 않았다(ADR-0025).

리랭커는 규정에만. 사업 문서 검색에서는 그래프 절 축·문서당 2 개 규칙과 겹쳐 오히려 손해라 꺼 두었다. 생성 모델로 후보를 다시 매기는 방식은
덜 정확하고 53 배 느려 쓰지 않는다.

pgvector. 사업 문서 벡터를 운영 서버 메모리의 배열에서 PostgreSQL 의 pgvector[36] HNSW[37] 색인으로 옮겼다(ADR-0057). 권한·부서·종류 조건을 같은 SQL 에서
걸 수 있고, 메모리에서 5GB 넘는 배열이 빠졌다.

```

[그림 4-8] 검색의 흐름

어휘 축은 색인과 질의가 같은 낱말 함수(app/grant_lex.py 의 lex_terms)를 쓴다. Kiwi[33] 명사와 두 글자 이상 영문 약칭을 소문자로 모으고, 띄어
쓴 복합 명사를 붙이며, 드문 낱말에 무게를 주는 IDF[34] 로 점수를 내고, 두 축은 순위 융합(RRF)[35]으로 섞는다. 의미 축의 임베딩은 규정 조각마다 27B 로 만든 합성 질의 세 꼴(실무형·공고
요구사항형·키워드형)과, 운영 하이브리드가 실제로 올린 후보 상위 20 가운데 정답이 아닌 조각(어려운 오답, 최대 6 개)으로 대조학습(InfoNCE[31],
온도 0.05)을 2 에폭 했다. 서빙 장비 GPU 에서 약 20 분 걸렸다(scripts/108). 문서 단위로 20 %를 홀드아웃으로 뗐다. 리랭커(bge-reranker-v2-m3[32] 바탕)는 운영 하이브리드가
올린 후보 목록 전체에 대해 정답 쪽 확률을 높이는 목록 단위 학습을 했다(scripts/104).

섞는 비율. 어휘 가중 0.2~0.5 가 고원이었고, 임베딩 학습 문서를 뺀 질의 22,084 건으로 다시 재도 후보 진입률이 가중 0~0.6 에서 같아 0.4 를
유지했다(실험 로그 10 절).

서빙과 물러남. 색인과 질의의 모델이 다르면 벡터 공간이 어긋나므로 색인에 모델 이름을 적고 대조한다. 교내망 보안 장비가 긴 숫자열 요청을 끊어
9 자리 이상 숫자열은 가린 뒤 보낸다. 서비스가 응답하지 않으면 규정 검색은 운영 서버 CPU 모델로, 사업 문서 검색은 어휘 축만으로 물러난다.

판본과 규정 등록. 검색 때 같은 판본 묶음에서 개정일(없으면 원본 수정 시각)이 가장 늦은 판만 남기고, 옛 판 조각이 걸리면 최신 판의 같은 글로
바꾼다(app/grant_search.py). 학교 원본으로 들어온 규정은 처음에 사업 문서로 반입되며, 관리자가 판본 묶음마다 최신 판 하나를 「새 판·미등록
규정」에서 골라 「검색에 추가」하면 조문 단위로 다시 조각낸다(ADR-0064, 되돌리기 있음).

## 4.4 지식 그래프와 온톨로지

### 4.4.1 목적

문서가 수만 건이면 「LINC 3.0 2차년도 실적보고서의 취업 성과」 같은 질문을 조각 유사도만으로 풀기 어렵다. 사업·연차·종류를 먼저 좁히고
그 안에서 찾아야 한다. 또 「계획 대비 실적」·「앞 단계 사업」처럼 문서 사이 관계를 묻는 질문은 관계가 데이터로 있어야 답할 수 있다
(ADR-0047). 지식 그래프는 사업 > 연차 > 문서 > 절 구조와 문서 사이 관계를 근거와 함께 담아, 검색이 무엇을 어디서 찾을지 알게 한다.

### 4.4.2 사용 방법

그래프는 라이브러리의 「지식그래프」 탭이나 개발자 화면의 「그래프 탐색」(/graph/explore)에서 본다. [그림 4-9]

[그림 4-9] 그래프 탐색 — 사업 하나를 고르고 「이웃 펼치기」 한 모습 (그림 docs/images/figures-1025/f4-09-graph-explore-expand.jpg)

1. 「사업 찾기 · 문서·단위과제·지표도」 칸에 사업 이름을 넣는다. 「전체 보기」는 사업 중심 전체 그림을 보인다.
2. 노드를 누르면 옆 칸에 정보가 뜬다. 「이것만 보기」, 「선택에 더하기」/「선택에서 빼기」, 「이웃 펼치기」로 그림을 좁히고 넓힌다.
3. 문서 노드에서 「문서 열기 ↗」나 「원본 파일 ↗」로 원문을 연다.
4. 「다시 배치」, 「화면 맞춤」으로 그림을 정리하고, 「사업별 표」를 누르면 사업 그래프(/graph/program)로 간다.
5. 사업 그래프에서는 「연차별 문서」, 「성과지표」, 「계획 ↔ 실적 대응」(계획서 절 · 실적보고서 절 · 근거), 「연차 사이 같은 절 · 평가」를
   표로 본다. 「다른 사업 선택」으로 사업을 바꾼다. [그림 4-10]
6. 관리자는 보기 전환 「지식그래프」/「온톨로지」에서 「온톨로지」를 골라 노드 종류·관계(기준별)·속성의 전체 스키마를 보고,
   「온톨로지 파일 내려받기」로 설계도를 받는다. 구조 검사 결과는 「구조 검사 {시각} · 세 쌍 N · 규칙 N개 · 위반 N건」 한 줄로 보인다.

### 4.4.3 업무 시나리오

산학협력단 담당자가 「LINC 3.0 2차년도 계획 대비 실적을 비교해 줘」라고 묻는다. 27B 가 질문을 읽어 사업(LINC 3.0), 차수(2), 따라갈 관계
(계획↔실적)를 낸다. 코드는 그래프에서 그 사업의 2 차년도 계획서와 실적보고서를 찾고, 계획↔실적 짝으로 이어진 절 쌍(예: 「취업 지원」 절
↔ 「취업 지원 실적」 절)에서 한 조각씩 근거에 담는다. 답에는 계획서 쪽 목표와 실적보고서 쪽 실적이 각자의 출처와 함께 나온다. 담당자가
「그 전 단계 사업에서는?」이라고 이어 묻자 그래프의 앞 단계 관계(succeeded_by)를 따라 LINC+ 문서로 범위가 넓어진다.

### 4.4.4 설계 선택과 이유

질문 읽기는 모델, 그래프 탐색은 코드. 처음에는 사업 이름 맞추기와 「N차년도」·종류 낱말 정규식으로 질문을 읽었다. 이 방식은 「계획 대비
실적」을 계획 종류로만 보고, 앞 단계 사업을 물어도 질문에 적힌 사업만 봤다. 질문 꼴마다 정규식을 덧대는 대신 질문의 뜻은 모델이 읽고,
그래프 탐색은 코드가 결정적으로 하게 했다(ADR-0063).

근거 없는 관계는 만들지 않는다. 관계마다 기준(구조·분류·식별자 일치·추출·유사도 다섯 가운데 하나)과 근거(문서·절 위치나 외부 출처 URL)를
단다. 사업 사이 관계와 기관은 외부 확인 장부에서만 가져온다. 사업은 각각 독립적으로 분석하고, 관계 근거가 있을 때만 사업 사이를 잇는다.

표준 층. 온톨로지를 우리 코드 안의 규칙으로만 두면 검증할 수 없다. 그래서 설계도를 OWL[40]·RDF[41] 로 내보내고 SHACL[42] 규칙으로 검사한다(ADR-0056).

### 4.4.5 구현

온톨로지. 노드 종류는 여덟이다 — 사업 묶음, 사업, 기관, 연차, 문서, 절, 단위과제, 성과지표. 문서는 서류 종류를 하위 분류로 갖고, 어느
사업에도 속하지 않는 기관 업무 문서는 따로 둔다(ADR-0048·0055). [그림 4-12] 는 주요 관계다.

SHACL 규칙은 「연차는 사업 하나에만 속하고 연도는 1990~2035」, 「문서의 종류는 하나까지이고 사업·연차에 속하거나 기관 업무 문서」, 「관계는
기준 다섯 중 하나에 근거 하나 이상」 등이다(graph/shapes.ttl). 그래프를 다시 지을 때마다 검사가 돈다.

그래프 구축(scripts/157, graph/programs.py·sections.py·units.py). 그래프는 PostgreSQL 의 노드 표(kg_nodes)와 관계 표(kg_edges)에 둔다.
사업 → 연차 → 문서는 사업 분류와 문서 연도·차수로 잇고, 연차를 모르는 문서는 연차에 넣지 않는다. 문서 → 절은 처리본의 제목 경로로 만든다.
계획↔실적은 같은 사업·연차의 계획서와 실적보고서를 잇고, 절끼리는 제목 맥락과 본문 유사도로 짝짓는다. 「차년도 계획」 절은 빼고 연차가 맞지
않으면 잇지 않는다. 성과지표는 표 칸 격자에서 「성과지표」 칸을 찾고 칸 이름으로 기준·목표·실적·달성률을 읽어 값을 그대로 꺼낸다
(graph/indicators.py). 모델이 값을 만들지 않는다.

GraphRAG[39](graph/question_read.py, graph/retrieve.py). [그림 4-13] 과 같다.

```

```

## 4.5 채팅과 답변 방식

### 4.5.1 목적

질문하면 열람 권한 안의 근거 문서를 찾아 출처와 함께 답한다. 근거에 없는 숫자는 표시한다. 긴 대화에서도 담당자가 알려 준 값과 정한 방향을
잃지 않는다.

### 4.5.2 사용 방법

사이드바 「새 채팅」을 누르면 채팅 화면(/chat)이 열린다. 첫 화면 제목은 「근거를 찾고, 문서를 다듬으세요」다. [그림 4-14]

[그림 4-14] 채팅 첫 화면 — 「답변 방식」 선택과 입력창 (그림 docs/images/figures-1025/f4-14-chat-start-answer-mode.jpg)

1. 입력창 옆 「답변 방식」에서 답을 만드는 방식을 고른다. 「문서 작업」은 등록 문서를 근거로 답하고 작업 문서를 고친다. 「기본 대화」는 문서 없이 모델이 답한다.
   「웹 검색」은 질문만 밖으로 보내 웹에서 찾는다.
2. 「질문이나 수정할 내용을 입력하세요」 칸에 질문을 쓰고 「보내기」를 누른다. 답을 기다리는 동안 「요청 처리 중」과 「작업 내역」 단추가 보인다.
3. 답이 오면 답 아래에 출처가 달린다. 출처를 누르면 오른쪽 패널에 그 대목이 열린다. 오른쪽 작업 패널의 「연관 자료」에는 이번 답의 근거 목록이,
   「적용 기준」에는 이 대화에 적용한 기준 문서가 보인다.
4. 답 위의 「생각 과정 펼치기」를 누르면 [1단계: 질문 파악] → [2단계: 근거 확인] → [3단계: 답 구성] 의 단계 추론이 보인다. [그림 4-15]
5. 답 아래 「답변 복사」, 「도움됨」, 「아쉬움」을 쓴다. 「아쉬움」은 「근거 문서가 틀림」, 「숫자·사실이 틀림」, 「질문과 다른 답」, 「너무 길거나
   짧음」, 「느림」, 「기타」 가운데 여럿을 고르고 한 줄 의견을 남긴다.
6. 「답변 다시 생성」은 그 질문부터 다시 답하게 하고 이후 대화는 이력에 보관한다. 내 질문에는 「이 질문 수정」과 「이 질문부터 다시 생성」이 있다.
7. 입력창 오른쪽 아래 「문맥 N% 사용」을 누르면 「문맥 관리」 창이 열려 「지금 목표」와 모델 호출 횟수를 보여 준다.

### 4.5.3 업무 시나리오

기획처 담당자가 새 채팅에서 「AI 교육 쪽으로 뭔가 사업을 해 보고 싶은데」라고 쓴다. AURA 는 비슷한 지난 사업과 관련 규정을 출처와 함께
보이고 대상·예산·기간을 묻는다. 담당자가 「2027년 1학년 대상, 예산 5천만원, 기간은 3월부터 12월」이라고 답한다. 세 턴 뒤 「문맥 관리」 창의
「지금 목표」는 「2027년 1학년 대상 AI 교육 사업계획서 작성 및 목차 구성」으로 바뀌어 있고, 확정된 것에 대상·예산·기간이 원문 그대로 남아
있다(실제 27B 세 턴 시험의 결과, 임시 DB). 담당자가 「작년 비슷한 사업의 참여 인원은?」이라고 묻자 답에 「300명(근거 확인 필요)」이 나온다.
근거에서 찾지 못한 숫자이므로 담당자는 출처 패널을 열어 실제 값을 확인한다.

### 4.5.4 설계 선택과 이유

권한은 검색 단계에서. 답을 만든 뒤에 거르면 모델이 이미 남의 부서 자료를 읽은 뒤다. 그래서 권한은 검색 SQL 조건으로 건다(3.5 절).

출처는 건넨 근거에서만. 화면의 출처는 모델에 실제로 건넨 근거 목록에서만 만든다. 모델이 답에 쓴 출처 표시를 그대로 믿지 않는다.

수치 검증은 코드가. 모델이 쓴 숫자가 근거에 있는지는 모델에게 판단을 맡기지 않고 기계적으로 대조한다(verify/numbers.py). 수치는 인출하고
생성하지 않는다는 규칙의 실행 자리다.

대화 기억은 비율로. 요청마다 최근 대화 몇 개만 넣으면 그 밖의 대화가 사라지고, 모델마다 문맥 한도가 달라 개수로 자르는 방식은 맞지 않는다.
그래서 작업 메모와 문맥 한도 비율을 쓴다(ADR-0065).

### 4.5.5 구현

답 흐름(app/main.py → app/responder.py)은 다음 열 단계다.

1. 입력 정리: 전각 문자를 반각으로 바꾼다.
2. 권한 점검(app/access_guard.py): 특정인의 개인정보를 묻는 질문은 모델을 부르지 않고 막는다. 지시를 바꾸려는 꼴의 질문과 범위 밖 부서 질문은
   감사 기록에 남긴다. 계정의 RAG 공간으로 검색 범위를 정한다.
3. 문서 작업 에이전트가 먼저 받아 도구를 고른다(4.6). 모델에 닿지 못했을 때만 낱말 규칙 경로로 물러난다.
4. 검색: 규정 검색과 사업 문서 검색을 동시에 돌린다. 프로젝트 대화면 그 프로젝트에 올린 문서가 먼저 온다.
5. 근거 묶기: 규정 묶음과 사업 문서 묶음을 따로 표시해 건넨다. 근거가 없거나 약하면 그렇다고 알린다.
6. 문맥 맞추기(app/llm_budget.py): 첨부 → 오래된 대화 → 출력 상한 → 검색 근거 순으로 줄인다. 다 줄여도 넘으면 보내지 않는다.
7. 생성: 「첫머리 1~3 문장 답, 근거 요점 5 개 이내, 표·문단 옮겨 적지 않기, 600 자 안팎」. 화면에 흘려 보이고, 출력 한도에서 끊기면 한 번 이어 쓴다.
8. 근거 밖 숫자 표시: 근거에 없는 숫자에 「(근거 확인 필요)」를 붙이고 끝에 안내한다.
9. 출처: 모델에 건넨 근거 목록에서만 만든다.
10. 기록: 답마다 실행 기록(answer_runs)과 담당자 평가를 남긴다.

화면은 답 생성 같은 긴 일을 뒤에서 돌리고 진행 상태(/chat/{번호}/status)를 1~4 초 간격으로 물어 단계 이름과 근거 개수만 받는다. 모델의 내부
추론·프롬프트·원문은 진행 상태에 싣지 않는다.

수치 대조. 답과 근거에서 숫자를 뽑아 표면형(쉼표 제거)과 정준값(조·억·만·천 환산, 「3억 5천만」 합산, 「1만 1799명」 → 11,799)으로 비교한다.
목록 번호·연도·전화·날짜·코드 꼴과 단위 없는 10 이하 숫자는 대조에서 뺀다. 같은 금액을 단위만 바꿔 쓴 값(5억 = 500,000,000 원 = 500 백만원 =
「(단위: 백만원)」 표의 500)은 같은 값으로 본다(ADR-0068). 우회를 막으려고 환산은 금액끼리만, 같은 덩이에서 가장 가까운 단위 선언 하나만 쓴다.

작업 메모와 단계 추론(app/chat_memory.py). 답이 끝나면 배경에서 「앞 메모 + 그 뒤 대화 → 새 메모」를 만든다. 메모는 지금 목표 / 확정된 것 /
진행 상황 / 남은 일·물어볼 것이고, 맨 앞의 「최종 결과물」 한 줄은 담당자가 바꾸자고 하지 않으면 지킨다. 요청에는 메모(문맥 한도의 6 %까지)와
최근 대화 원문(30 % 몫)이 들어간다. 단계 추론의 꼴은 학습 데이터의 구조 단계 문답과 같다.

「웹 검색」 방식(app/web_search.py)은 구글[70]·네이버[71] 검색 키가 있으면 그것을, 없으면 DuckDuckGo[72] 를 쓰고 가져온 쪽 글을 근거로 27B 가 출처 번호를
달아 답한다.

## 4.6 문서 작업 에이전트

### 4.6.1 목적

대화의 요청(「작년 실적보고서 참고해서 추진 배경 절 써 줘」, 「이 표 채워 줘」, 「한글 파일로 내보내 줘」)을 처리한다. 요청 글을 낱말 규칙으로
해석하면 꼴이 조금만 달라도 틀린 일을 한다. 무엇을 할지는 모델이 판단하고, 코드는 그 판단을 안전하게 실행한다. 목표는 로컬 27B 가 맥락을
파악하고, 문서함에서 재료를 찾고, 양식대로 초안까지 쓰는 것이다.

### 4.6.2 사용 방법

문서 작업은 프로젝트에서 시작하는 것이 기본이다.

1. 사이드바 「내 프로젝트」 옆 「프로젝트 추가」를 누른다. 「프로젝트 추가」 창에서 「업무」를 고르고, 「자료(선택)」에 공고나 지난 계획서를 고르면
   이름이 자동으로 정해진다. 「사업단(선택)」, 「마감일(선택)」을 넣고 「만들기」를 누른다. [그림 4-16]
2. 프로젝트 화면(/project/{번호})의 「대화·문서」 탭에서 「프로젝트 문서」 › 「문서 추가」로 자료를 넣는다. 공고·지침은 「기준으로 쓰기」로 기준
   문서가 된다. 「작성 원칙」에 「원칙 추가 — 예: 근거 조항 함께 적기」 처럼 이 업무의 규칙을 적는다. 「관련 지난 사업」에서 「지난 사업 연결」로
   지난 사업 묶음을 참조로 잇는다. [그림 4-17]
3. 「대화 시작」을 누르면 이 프로젝트의 채팅이 열린다. 머리줄의 「문서 패널 열기」로 「문서 패널」을 연다. 패널에는 「작업 문서」, 「첨부 문서」,
   「참고 문서」, 「기준 문서」가 있고, 편집기를 「한글」/「구글」로 고른다. [그림 4-18]
4. 「사업계획서 초안 써 줘」처럼 요청한다. 에이전트가 양식을 고르거나 만들고 작업본을 연 뒤 절을 차례로 쓴다. 쓰는 동안 편집 화면에 AURA 의
   커서와 「AURA가 … 하는 중」 상태가 보인다.
5. 자료에 없는 값이 있으면 답 아래 「필요한 값 입력」 칸이 생긴다. 칸마다 「값 입력」에 넣고 「저장」을 누르거나 「모두 다음에 받기」를 고른다.
   자료에서 찾은 값은 「자료에서 찾음 · 확인 전」으로 미리 채워지고 담당자가 「확인」해야 담당자 값이 된다. [그림 4-19]
6. 「2번 절 더 구체적으로」, 「일정은 표로 정리해 줘」, 「가로로 바꾸고 여백 좁게」처럼 고쳐 달라고 한다.
7. 프로젝트를 동료와 나누려면 머리줄의 공유 단추(「공유 안 함」/「공유 중 · N」)를 누른다. 「나만 보기」 또는 「함께 쓰기」를 고르고, 「이름·아이디·
   부서로 찾기」로 사람이나 부서를 더한 뒤 권한을 「참조」(읽기 전용)나 「함께 작업」(읽기·쓰기)으로 정한다. [그림 4-20]

### 4.6.3 업무 시나리오

기획처 담당자가 「2027 AI 교육 지원사업」 프로젝트를 만들고 공고와 지난해 비슷한 사업의 결과보고서를 올린다. 채팅에서 「공고 기준으로
사업계획서 초안 써 줘」라고 하자, 에이전트는 먼저 문서함의 한글 양식을 찾는다(hwp_forms). 목적에 맞는 양식이 없자 같은 모델이 깨끗한 문맥에서
양식을 설계한다(hwp_form_create) — 표지, 사업 개요 요약표, 「1. 추진 배경 → 가. 필요성」 꼴의 절, 절마다 【작성방법】 상자. 코드가 이를 학교
서식 표 모양으로 빌드해 작업본을 연다. 이어 에이전트는 빈 절이 많아 절 여럿을 서브에 동시에 맡긴다(delegate_section). 서브는 공고의 평가 항목과
지난 결과보고서에서 근거를 찾아 [개요] → [본문]을 쓰고, 근거 문서에서 온 문장 끝에 「(출처: 문서 이름 N쪽)」을 단다. 지난 사업의 참여 인원처럼
공고에 없는 숫자는 「○○명」으로 가려진다. 담당자가 「추진 일정은 표로, 2번 절은 더 구체적으로」라고 하자 고쳐 쓰기 도구가 지시를 점검표로
바꿔 절을 다시 쓰고, 코드가 길이가 늘었는지와 표가 생겼는지를 센다.

### 4.6.4 설계 선택과 이유

에이전트가 판단, 코드는 도구. 27B 가 매 단계 상태를 보고 {생각, 도구, 인자} 를 고르고(ReAct[48] 꼴), 코드는 고른 인자로 함수를 바로 부른다. 요청 글을
코드가 다시 해석하지 않는다. 낱말 규칙 경로로 물러나는 것은 모델에 닿지 못했거나 형식 오류가 두 번 났을 때뿐이다.

양식 모양은 코드, 내용은 모델. 양식의 모양·구조·채우기 규칙은 코드가 지키고 27B 는 내용만 쓴다. 공통 양식의 처음 판은 「병합 없는 8 열 이하
표」였으나 실제 서식 모양(2 단 머리행·병합 칸·서식 격자·합계 행)으로 바꿨다(ADR-0058·0059). 어떤 양식으로 쓸지는 27B 가 후보(프로젝트 작성
서식, 대화에서 정한 목차, 공통 양식) 안에서 고른다(ADR-0060).

필요할 때만 맡기기. 한 문맥에서 대화·검색·단계 기록·긴 본문을 다 다루면 절 41 개 서식이 한 요청에 17 절에서 멈췄다. 그래서 같은 27B 를 다른
역할·깨끗한 문맥으로 한 번 더 부르는 서브 에이전트(절 맡기기)를 두되, 기본은 메인이 직접 쓰고 빈 절이 많거나 남은 문맥이 모자랄 때만 맡긴다.
맡길지는 에이전트가 판단한다(ADR-0065).

[표 4-13] 문서 작업 에이전트의 도구 묶음

절 작성. 절을 쓰기 전에 27B 가 필요한 정보와 찾을 곳·검색어를 정하고 코드가 그대로 찾는다(app/context_plan.py). 재료는 그 절의 작성방법,
문서 전체 규칙, 기준 문서, 프로젝트 문서, 문서함의 사업 문서 RAG(보는 사람의 열람 범위 안, 실적보고서면 같은 연차 계획서도)다. 답과 글에 쓰는
사실은 그 요청에서 찾은 결과에 있는 것만 쓴다. 앞 대화는 맥락일 뿐 근거가 아니어서, 앞에서 본 사실을 쓰려면 다시 찾는다.

받지 못한 값. 값은 사실(자료에 있을 수 있는 값)과 결정(담당자가 정할 목표·계획)으로 나눈다. 사실 값만 찾고, 이 프로젝트 문서의 검색 결과에 글자
그대로(두 글자 이상) 있을 때만 출처와 함께 확인 전 제안으로 남긴다. 한 값을 세 번 찾아도 없으면 「자료에서 못 찾음」으로 둔다.

양식 설계(app/webhwp_form_create, ADR-0067). 문서함에 맞는 양식이 없을 때만, 그리고 이 대화에서 양식 찾기를 먼저 돌렸을 때만 돈다. 깨끗한 문맥의
같은 모델이 JSON 으로 제목·표지·요약 표 칸·절 단계와 제목·작성방법·분량·표 열 머리·도식 자리를 낸다. 재료는 작업 메모의 목표·확정 값, 공고의
작성·평가 항목, 목적이 비슷한 실물 양식 2~3 개의 구조(값은 넣지 않음), 실물 양식에서 종류별로 센 흔한 절이다. 코드는 관문(빈 제목·절 0 개·30 개
초과·중복 절·단계 건너뛰기·긴 안내·안내 글 꼴 제목·칸 라벨 꼴)을 두고, 번호를 학교 서식 꼴(1. → 가. → 1))로 매기며, 공통 양식과 같은 빌더로
작업본을 만든다.

서브 맡기기와 고쳐 쓰기(app/delegate.py, ADR-0068). 메인은 절 이름·요지·형식·분량만 정하고, 지시서의 필수 항목(작업 메모의 목표·확정 값,
문서 개요, 앞 절 요지, 담당자 원문 인용)은 코드가 채운다. 서브는 검색어 2~3 개를 먼저 내고, 코드가 찾아 번호·쪽을 붙인 근거를 문장 단위로
Rerank v1 로 압축한다(숫자·날짜·고유명사 문장 우선). 서브는 [개요] → [본문]을 쓰고 기준표(구체성·근거·작성방법·개요 반영)로 한 번 자기
점검한다. 여러 절은 연결의 동시 상한(없으면 2) 안에서 모델 호출만 동시에 하고 찾기와 파일 쓰기는 차례로 한다. 고쳐 쓰기는 서브 호출 둘이다 —
첫째가 지시를 점검표 JSON(의도·길이 늘림/줄임·표·도식·더할 항목·뺄 항목·문체·검색어)으로 바꾸고, 둘째가 절 전체를 다시 쓴다. 코드는 셀 수 있는
것(바뀌었나, 길이 방향 1.15 배·0.9 배, 표·도식 유무, 더할 항목 낱말)만 보고 어기면 까닭을 붙여 한 번 다시 청한다.

### 4.6.6 결과

## 4.7 한글 문서

### 4.7.1 목적

행정 서식은 대부분 한글이고, 제출본은 공고가 준 한글 서식 그대로여야 한다. AURA 는 한글 문서를 세 방향으로 다룬다. 읽기(반입), 열람·작업용
변환(독스), 그리고 쓰기(원본 서식 보존 채우기와 웹 기안기 편집)다. 웹 기안기에서는 여러 사람과 AURA 가 같은 문서를 칸 단위로 함께 고친다.

3. 목록은 이름 · 수정일 · 수정한 사람이다. 누군가 편집 중이면 「{이름} 편집 중」이 보인다.

   「사본 만들기」를 누르면 사본이 기안기로 열린다. [그림 4-23]
5. 지우기는 부서 휴지통으로 옮기며 관리자가 되살릴 수 있다. 여러 개는 「모두 선택」 뒤 「N개 선택」 줄의 「지우기」로 한다.
6. 구글 드라이브 보기에서는 파일마다 「가져오기」로 부서 폴더에 받아 기안기로 연다.

### 4.7.4 업무 시나리오

교무처 행정 담당자 셋이 학과 평가 보고서의 요약표를 나눠 쓴다. 한 사람이 「사본 만들기」로 공통 양식에서 부서 폴더에 사본을 만들고 채팅에서
AURA 에게 「현황 칸은 지난해 결과보고서 값으로 채워 줘」라고 한다. 세 사람이 같은 문서를 열자 머리줄에 아바타 셋과 「A」가 보인다. 두 사람이 서로
다른 칸에 동시에 쓰는 동안 글이 0.2 초 안팎으로 서로의 화면에 나타난다. AURA 는 사람이 쥔 칸은 건너뛰고 빈 칸만 채우며, 그 칸에는 「AURA · 시킨
사람」 깃발이 잠시 남는다. 마지막으로 한 사람이 「문서 틀 고치기」로 표 행 하나를 더해 저장하자, 다른 두 화면은 입력이 멈춘 뒤 새 판을 받고 각자의
칸 글은 그대로 남는다. 완성본은 「⋯」 → 「내려받기」 → 「한글(hwpx)」로 받는다.

### 4.7.5 설계 선택과 이유

읽기는 대조 수치로 고른다. 옛 hwp 읽기는 kordoc[25] 이 1 순위다(ADR-0033). 실물 비교에서 30MB 옛 hwp 읽기가 우리 pyhwp[26] 경로 3 분에서 1 초로 줄었고,
글자 양은 같았으며 표의 중첩·병합이 보존됐다. kordoc 의 판을 고정하고, 판을 올릴 때는 대조 스크립트(scripts/147)를 다시 돌려 통과해야 한다. 포크를
보관해 지원 종료에 대비하고, 내장 OCR 은 쓰지 않으며 자원 내려받기를 막는다. hwpx 는 자체 OWPML[24] 파서를 유지한다 — 독스 변환에 같은 XML 을 쓰고
이미 빠르다.

완성본은 원본 서식에 채운다. 행정 서식은 표 테두리·칸 폭·글꼴이 정해져 있어 변환기로 새로 만든 한글 파일은 제출용으로 쓸 수 없다. 한글 프로그램을
원격 조작하던 윈도우 COM 에이전트 방식은 담당자 PC 에 설치가 필요하고 불안정해 폐기했다(ADR-0034). kordoc 의 patch 는 새 문단·표 블록 추가가
안 되고, generate 는 서식을 새로 만드는 것이라 원본 보존이 아니었다. 그래서 「원본 서식을 보존하며 내용을 채우는」 원리를 흡수해 우리 채우기를
만들었다(ADR-0035).

공동 편집은 칸 단위 임대. 한컴 웹 기안기(WebHwpCtrl 13.82)[51]의 공개 API 에는 문서가 바뀌었다는 사건이 없고 문서 내부 모델에 닿을 수 없어, 글자 단위
병합 기법(OT[52]·CRDT[53])을 쓸 수 없다. 쓸 수 있는 것은 필드 API(칸 목록·칸 글 읽기·쓰기·커서 칸·칸으로 옮기기), 칸 속성(양식 모드에서 편집 가능),
양식 보호 모드, 커서 저장·되돌리기, 칸 서식 꺼내기·넣기다. 네 안을 비교했다(ADR-0070).

| 안 | 장점 | 단점 |
|---|---|---|
| 문서 전체 잠금만 | 단순 | 한 사람만 쓴다 |
| 기안기 내부 모델에 OT·CRDT | 글자 단위 병합 | 공개 API 밖이라 제품 판이 바뀌면 깨진다 |
| 별도 실시간 협업 페이지(Socket.IO[66]·React[67]) | 성숙한 도구 | 새 의존성과 빌드 단계, 앱은 빌드 없는 정적 JS |
| 칸 단위 비관적 임대 + 칸 글 전체 전송 + 서버 정답(채택) | 공개 API 만으로 된다, 같은 칸을 둘이 쓰지 않아 병합 불필요 | 칸 밖 고침은 따로(구조 잠금), 칸 안 서식은 기본으로 글만 |

### 4.7.6 구현

독스 변환. 한글은 구글 드라이브가 가져오기 형식으로 받지 않는다(원본 hwpx 를 어떤 MIME 으로 올려도 400). 그래서 한글만 우리가 docx 로 풀고 마지막
변환은 구글이 한다. hwpx 는 글자·문단·표·글상자·그림·쪽 설정을 docx 로 옮기고(ingest/hwpx_docx.py), 옛 hwp 는 pyhwp 의 구조 XML 을 같은 변환기에
넣는다(ingest/hwp5_docx.py). 실측 사업계획서 95 쪽에서 표 124(중첩 41)·그림 27·글상자 19 가 모두 옮겨졌다. 변환 품질은 묶음으로 잰다 — 문서함의
한글 문서 전부를 변환해 원본과 글자·표·그림 수를 대조하고 워드 구조 오류를 실패로 낸다(scripts/145). 작성서식 62 쪽 기준 빈 쪽이 6 에서 1 로 줄었다.

서식 보존 채우기(ingest/hwpx_fill.py). hwpx 는 XML 을 담은 ZIP 이다. [그림 4-26] 과 같이 채운다.

```

   │ 구역 XML 을 다시 직렬화하지 않음         │ 글 · 표 · 그림(안내 상자 제외)
   ▼                                          ▼
 절 제목 문단(또는 그 뒤 【작성방법】 상자) 찾기 ── 번호·제목 글자로 맞춤
   │
   ├─ 서식에 이미 있는 문단·표 → 다시 넣지 않고 그 자리를 지나 이어 씀
   ├─ 서식 표를 채웠으면 → 작업본 열 너비로 값 칸 x 위치를 재어 원래 칸에 써 넣음
   ├─ 새 표 → id 는 문서 최댓값 다음부터, 테두리는 그 구역 본문 표의 가장 흔한 실선 승계
   └─ 글자열 위치에 문단·표·그림 XML 끼워 넣기(손대지 않은 문단은 한 글자도 안 바뀜)
   │
   ▼
 바뀐 구역만 줄 배치 캐시 지움 → ZIP 항목 순서·압축 방식 유지, 바뀐 항목만 다시 씀
   │
   ▼
 자가 점검(ZIP 규약 · XML 형식 · 참조 id · 항목 수 · 표 격자) ── 통과할 때만 저장
```

[그림 4-26] 원본 서식 보존 채우기

원본이 옛 .hwp 면 채우지 않고 hwpx 로 저장한 서식의 반입을 안내한다. 이 층은 내용을 만들지 않는다. 내용은 에이전트와 담당자가 작업본에 쓴 것이고,
이 층은 그것을 서식에 옮길 뿐이다.

한글 문서함과 양식 정리. 문서함은 부서 디렉터리 꼴이다. 부서마다 저장 전 판(.판)과 휴지통(.휴지통)을 두고, 사람마다 「내 폴더」가 처음 열 때 생긴다.
폴더 이름을 바꾸면 안의 문서 장부 경로와 즐겨찾기·최근 폴더를 함께 고친다. 지난 문서에서 모은 양식은 한 판정 모듈(app/past_forms.py)이 공통 양식·지난
사업 문서·휴지통(개인 서류·채워진 제출본·한 번 쓴 기록·깨짐·빈 파일·중복)으로 가른다(scripts/208). 규칙은 특정 파일·사업을 적지 않고 장부의 사업 이름,
제목 낱말, 본문에서 기계로 잰 값(빈 칸 비율·개인 정보 꼴·양식 예시 글자 수)만 보며, 적용은 계획의 지문이 지금과 같을 때만 돌고 먼저 백업한다.

기안기 편집 도구. 에이전트의 편집 도구는 서버가 hwpx 파일을 직접 고친다. 기안기가 열려 있지 않아도 되고, 고치기 전 판을 남기며, 자가 점검을 통과할
때만 저장한다. 표 서식의 기본값은 학교 서식 문서 1,459 건의 표 20,441 개에서 캔 값이다(머리줄 회색 음영·굵게, 바깥 0.4mm·안쪽 0.12mm 실선, 10pt).
열린 기안기에서 바로 해야 하는 동작은 기안기의 기본 기능을 동작 이름 그대로 부른다(hwp_action). 동작 이름 1,143 개 가운데 웹에 등록된 467 개를 확인하고,
쓸모 있는 73 개를 허용 목록(app/webhwp_native)에 두었다. 기안기에 있는 기능은 우리 창을 새로 만들지 않고 기안기 것을 쓴다는 원칙이다.

칸 단위 공동 편집(ADR-0070). 세 겹 구조다. 어댑터(static/webhwp-wrapper.js)는 기안기 API 를 부르는 유일한 곳이고, 공동 편집 층(static/webhwp-collab.js)이
임대·보낼 줄·받을 줄·판 번호·지문 대조·충돌 사본과 화면 표시를 맡으며, 서버(app/webhwp_coedit.py)의 표 일곱(칸 임대·칸 글·받은 변경·고친 기록·충돌 사본·
알림 줄·같이 보는 사람)이 정답이다. 밀어 주기는 SSE[54], 변경은 fetch[69] POST 다. 세 겹의 관계와 AURA 참여자, 한글 파일 써 넣기는 [그림 2-26] 의 구성도(docs/images/diagrams/03-hwp-coedit.png)와 같고, [그림 4-27] 은 글자 하나가 다른 화면에 닿기까지다.

```
[창 A] 키·한글 조합 사건 → 어댑터가 칸 글 읽기(조합 중엔 읽지 않음)
   → 첫 고침에 POST /lease, 300ms 마다 POST /ops {창 번호, 차례 번호, 기준 판, 칸 글 전체}
     (보낼 줄은 IndexedDB[68] 에도 — 끊기면 「오프라인 — 연결되면 저장」, 다시 이어지면 보냄)
                                       │
[서버] 문서별 쓰기 줄 세우기(PostgreSQL advisory lock) 안에서:
       같은 (창, 차례) → 같은 답(두 번 반영 안 함) · 기준 판 어긋남·남의 임대 → 충돌 사본(버리지 않음)
       → 칸 판 번호 올림 → 알림 줄 → 3초 뒤(이어지면 최대 20초) hwpx 필드에 써 넣기(앞 판은 .판/)
                                       │ SSE /events (끊기면 Last-Event-ID 로 이어 받음)
[창 B] 판 번호가 앞선 글만, 입력이 300ms 멈추고 조합 중이 아닐 때 칸에 넣고 커서·스크롤 되돌림
       30초마다 칸 글 지문(CRC32) 대조로 놓친 알림 메움 · 0.25초마다 칸 자리 다시 셈 → 바탕·커서·깃발
```

[그림 4-27] 칸 단위 공동 편집의 흐름

이 흐름에는 실브라우저에서 찾은 함정 두 가지를 막는 장치가 들어 있다. 하나는 한글 조합이다. 조합 중에 기안기에 무엇이든 물으면 조합이 끊겨 자모가
따로 박혔다(「ㄱ기김」). 그래서 조합 중에는 칸 글을 읽지 않고 칸 속성을 바꾸지 않으며 칸 자리도 재지 않는다. 다른 하나는 남이 쓰는 칸의 표시 자리다.
기안기 화면 커서로 재면 그리기 차례가 늦어 이름표가 다른 칸에 그려졌다. 그래서 기안기 내부의 커서 모델(쪽 번호와 쪽 안 좌표)을 읽고, 커서를 칸 처음·
끝으로 옮겨 재고 되돌리는 일을 한 작업 단위 안에서 끝내 화면에 변화가 없게 했다. 이 내부 모델은 공개 API 밖이라, 제품 판이 바뀌어 없어지면 칸 표시만
빠지고 편집은 그대로 돈다.

AURA 도 참여자다. 에이전트가 칸 값을 쓸 때도 같은 길(임대 확인·판 번호·알림)로 쓰고 바로 놓으며, 사람이 쥔 칸은 쓰지 않는다. 보안 점검에서는 화면이
지어 보내는 창 번호를 로그인한 사람과 묶어 남의 변경을 막지 못하게 하고, 요청 본문 4MB, 문서마다 새 칸 줄 2,000 개 같은 상한을 두었다. 시간 값은 모두
설정이다(기본 임대 300 초, 기다리는 사람이 있을 때 120 초, 보내기 간격 300ms 등).

공동 편집 시연(ADR-0071). 운영은 주소가 하나라 한 브라우저에서 세 사람의 세션을 동시에 가질 수 없다. 그래서 관리자 화면 「공동 편집 시연」(/dev/coedit-demo)에
같은 문서를 세 칸으로 열고, 칸 표시를 단 편집 요청만 로그인할 수 없는 시연 계정으로 판정한다. 표시는 권한을 좁히기만 한다 — 관리자만 쓸 수 있고 결과는
시연 폴더만 여는 교직원이다. 「새 시연 문서」와 「문서 비우기」로 시연 문서를 다시 만든다. [그림 4-28]

## 4.8 구글 드라이브·독스 연동

### 4.8.1 목적

담당자 문서의 일부는 구글 드라이브에 있고, 여러 사람이 실시간으로 함께 쓰는 데는 구글 독스가 익숙하다. AURA 는 드라이브를 문서 원천으로 붙이고,
대화에 이은 독스 작업본을 에이전트가 직접 고치게 한다. 교내 내용이 구글로 나가는 일이므로 학교 계정 안에서만, 가리고 기록한다.

### 4.8.2 사용 방법

1. 내 학교 계정 잇기. 사용자 메뉴 「설정」(/settings)의 「구글 계정」 칸에서 「구글 계정 연결」을 누른다. 잇기 전에는 「연결 전 — 문서를 만들려면 학교
   계정을 연결하세요.」가 보인다. 끊을 때는 「연결 해제」를 누른다(이미 만든 문서는 드라이브에 남는다). [그림 4-29]
2. 문서 편집기 고르기. 같은 「설정」의 「문서 편집기」에서 「구글 문서」 또는 「웹 한글 기안기」를 기본으로 고른다. 채팅의 문서 패널에서도 「한글」/「구글」로
   바꿀 수 있다.
3. 드라이브 문서 가져오기. 문서 패널의 「파일 가져오기」 창이나 「드라이브에서 문서 가져오기」 창에서 문서를 골라 「선택한 문서 가져오기」를 누른다.
   가져온 문서는 업로드와 같은 처리 경로를 탄다.
4. 독스 작업본으로 쓰기. 문서 패널에서 문서를 열고 「이 문서로 작업」을 누르면 사본을 만들어 이 대화에 잇는다(「복제본 만드는 중…」 → 「작업 문서 열기」).
   이후 대화의 명령은 그 문서의 편집이 된다. 「새 창에서 열기」로 독스를 따로 연다.
5. 한글로 마무리. 채팅에 「한글 파일로 내보내 줘」라고 쓰면 작업본의 절 본문이 원본 hwpx 서식에 채워져(4.7) 프로젝트 드라이브의 작성 폴더에 올라간다.
   「안내 상자 없이」나 「제출본」이라고 하면 【작성방법】 상자를 뺀다. 문서 패널의 「구글 작업본을 한글로」 단추도 같은 일을 한다.
6. 부서 드라이브. 조직·구성원(/team) 화면의 「부서 드라이브」 칸에서 그 부서 총괄 책임자가 「구글 드라이브 연결」을 누르고 부서가 함께 쓸 학교 계정으로
   잇는다. 「위치 바꾸기」, 「권한 맞추기」, 「연결 끊기」도 여기서 한다. 개인 계정으로 이어져 있으면 「공용 계정으로 바꾸기」를 권하는 안내가 뜬다. [그림 4-30]

### 4.8.3 업무 시나리오

산학협력단 담당자가 협력 기관과 함께 쓰던 계획서 초안을 자기 드라이브에 두고 있다. 문서 패널의 「파일 가져오기」로 그 문서를 프로젝트에 가져오고
「이 문서로 작업」을 누른다. 채팅에서 「3장 추진 체계 아래에 협력 기관 역할 표 넣어 줘」라고 하자, 에이전트가 편집 계획(넣기·표)을 JSON 으로 내고
플랫폼이 독스 API 로 바로 적용해 담당자 화면에 표가 나타난다. 같은 부서 동료는 그 작업본을 「참조」 권한으로 받는다. 제출 전날 담당자는 「한글 파일로
내보내 줘, 제출본으로」라고 해 원본 서식의 한글 완성본을 받는다.

### 4.8.4 설계 선택과 이유와 구현

읽기와 쓰기를 나눴다. 1 단계는 드라이브를 읽기 전용 원천으로 붙였다(ADR-0028). 인증은 담당자 본인의 OAuth[57] 허용이고, 클라이언트 비밀과 갱신 토큰은 서버
파일에만 두고 화면에 되돌려 보이지 않는다. 구글 클라이언트 라이브러리를 들이지 않고 드라이브[56]·독스[55] REST API 를 직접 불러 의존성을 늘리지 않았다. 2 단계 쓰기는 외부 전송이므로
규칙을 먼저 정했다(ADR-0029). 대화에 이은 문서의 명령은 에이전트가 편집 계획(넣기·바꾸기·표·칸 채우기·도식 등)을 JSON 스키마로 강제해[50] 내고 플랫폼이
documents.batchUpdate 로 적용한다. 보내는 글은 개인정보 검사기를 한 번 더 거치고, 검색 근거 조각의 원문은 넣지 않고 에이전트가 쓴 글만 넣으며, 모든 쓰기는
시각·계정·문서·절·글자 수로 감사 기록(gdocs_audit)에 남는다.

공통 양식. 작성 서식이 없는 사업이나 새 문서는 독스 공통 양식 5 종(사업계획서·실적보고서·단위 프로그램 실시계획서·결과보고서·회의록)을 바탕으로 쓴다
(ADR-0058). 한글 서식을 독스로 옮기면 쪽이 밀리고 표가 깨지므로 독스 API 로 직접 짠 사양을 쓰고, 절·표·분량·근거 위치는 실문서 집계(계획서 5,732·보고서
2,273·단위 프로그램 1,151 건)에서 골랐다. 사업 이름은 양식에 넣지 않는다.

계정 체계. 구글 앱은 관리자가 한 번 등록하고(사용자·계정 화면의 「학교 계정 연결 현황」), 사용자마다 자기 학교 계정을 잇는다. 부서 계정 토큰은 그 부서
폴더 안 문서를 만들고 다룰 때만 쓰고, 드라이브 찾기·가져오기·쓸 계정 목록은 본인 계정만 받는다. 연결을 거절해도 허용 state 를 써 버리고, 실패한 토큰은 지운다.

### 4.8.5 결과

운영 실측에서 독스 편집 명령 한 건이 65 초(27B 계획 생성 포함)에 세 항목 254 자를 지정한 절 아래에 넣었다(ADR-0029). 공통 양식과 절 작성 에이전트의 시험
7 회(실물 세트, 임시 DB)에서 한 글자도 안 쓰던 흐름이 절을 순서대로 쓰게 됐고 한글 완성본의 서식 표가 제자리에 채워졌다(새 표 2 → 0). 문서함 RAG 재료로
쓴 「추진 배경」 절은 355~560 자에서 1,567 자(실문서 중앙값 1,800 자)가 됐다. 묶음 접수 5 건은 977 초에서 343 초로 줄었다(ADR-0058).

## 4.9 업무 도우미

### 4.9.1 목적

플랫폼 사용법을 안내하고, 화면에서 하는 일을 대신 제안한다. 채팅 화면의 에이전트 대화와 따로 돈다. 사업 문서 내용 질문은 에이전트 대화로 넘긴다.

### 4.9.2 사용 방법

1. 채팅·프로젝트 첫 화면을 뺀 모든 화면의 오른쪽 아래 「업무 도우미」 단추를 누른다. 학생에게는 보이지 않는다. [그림 4-31]
2. 「어떤 업무를 도와드릴까요?」 아래 「메시지를 입력하세요」 칸에 묻는다(예: 「학생에게 장학 규정을 보이게 하려면?」).
3. 답에 「이렇게 하겠습니다 — …」 제안이 붙으면 「실행」을 누르거나, 「화면에서 직접」을 눌러 화면 위 커서가 같은 일을 하는 단추를 가리키게 한다.
4. 화면의 글을 골라 「쉽게 설명」, 「간추리기」, 「관련 규정 찾기」, 「직접 묻기」를 고를 수도 있다. 이 질문들은 문서 내용이라 답변 경로로 간다.
5. 머리줄의 「지난 대화」, 「새 대화」, 「넓히기」, 「닫기」로 창을 다룬다.

### 4.9.3 업무 시나리오

새로 온 관리자가 RAG 공간 화면을 보다가 도우미에 「학칙을 학생이 볼 수 있게 하고 싶어」라고 쓴다. 도우미는 지금 보는 화면이 RAG 공간임을 알고, 화면 안내
자료에서 해당 항목을 찾은 뒤 「학칙」 규정을 고른 학생 공개 제안을 내민다. 관리자가 「화면에서 직접」을 누르자 화면 위 커서가 「규정·지침」의 해당 줄과 「학생
공개」 단추를 차례로 가리킨다. 관리자가 「실행」을 누르면 화면 단추와 같은 함수로 실행되고, 결과가 대화와 실행 기록에 남는다.

### 4.9.4 설계와 구현

도우미(app/platform_helper.py)는 문서 작업 에이전트와 같은 단계 구조(단계 8 번까지)에 도구만 다르다 — 화면 안내 찾기(platform_help), 내 대상 목록 보기
(platform_lookup), 동작 제안(propose_action), 화면 열기(open_page), 마무리(finish). 요청이 사용법인지, 할 일인지, 문서 내용인지는 모델이 도구를 고르며
정하고 낱말 규칙은 두지 않는다. 동작은 바로 실행하지 않고 제안하며, 실행은 언제나 「실행」 뒤 서버에서 한다(app/platform_ops.py). 화면 안내 자료
(app/platform_guide.py)는 화면마다 한 항목이고, 적어 둔 단추 이름·자리가 템플릿에 실제로 있는지 자동 테스트가 확인한다. 모델 용도는 helper 이고 지정이 없으면
answer 연결을 쓴다. 단계 기록은 따로 남는다.

## 4.11 모델 학습(SFT) 파이프라인

### 4.11.1 목적

Writer 27B 를 교내 업무에 맞게 적응시킨다. 다만 사실과 수치는 외우게 하지 않는다. 사업 자료는 해마다 바뀌는데 외운 값은 바뀌지 않고, 내부 원문을 학습에 넣으면
개인정보가 모델에 남는다. 그래서 파인튜닝은 「질문을 보고 무엇을 어디서 찾아 어떤 근거로 답을 구성할지」라는 컨텍스트 구성 리즈닝에만 쓴다(ADR-0047). SFT
데이터는 규정·발전계획 묶음과 사업 구조·검색 활용 묶음 두 갈래로 나누고, 실적·예산 사실 문답은 넣지 않는다(ADR-0052).

### 4.11.2 사용 방법

학습셋은 학습 장비에서 만들고 승인하며, 운영 서버의 개발자 화면에서는 상태와 결과를 본다.

1. 「데이터·학습」(/dev/train)의 「문답 검수」에서 「원문과 답변 검수하기 ↗」로 Label Studio[18] 검수 화면을 열고, 검수가 끝나면 「완료한 검수 결과 반영」을 누른다.
2. 「승인 데이터·산출물」에서 학습셋별 파일(학습 허가 / 학습셋 / 학습 전 성적)을 본다. 「표본」을 누르면 「학습셋 표본」 화면에서 지시 / 질문 / 앞 답 / 학습할 답을
   한 쪽 20 줄씩 본다. 원문 파일은 개발자 계정만 내려받는다. [그림 4-35]
3. 「학습·평가」의 「학습 상태 보기」(/dev/train/run)에서 학습 점검을 보고(정상 / 확인 필요 / 문제 / 판단 전), 「TensorBoard 그래프 ↗」로 손실 곡선(TensorBoard[62])을 연다.
   [그림 4-36]
4. 학습본 비교 결과는 「개발 현황」의 모델 표에서 Writer 줄의 「모델 비교 결과」를 눌러 연다(/dev/models/compare). 「요약」, 「둘 중 나은 답 고르기」, 「항목별
   평균(1~5)」, 「지표」, 「속도」, 「문항 종류별」, 「표본 N건」, 「만든 문서」가 있다. [그림 4-37]

| 답 꼴 점검 | 평범한 업무 질문 15 개에서 학습셋 틀이 새는지(지시 없음 · 플랫폼 지시 · 학습셋 지시) |
| 속도 | 20 문항을 하나씩 흘려 받아 첫 글자 시간·초당 토큰 |

[표 4-21] SFT 비교의 네 묶음과 점검

채택 기준(제안)은 시험 문항의 나은 답 점수 95 % 구간 아래 끝이 0.5 이상, 맥락 이해·문서 작성에서 떨어진 항목 없음(지어낸 숫자 0 유지), 문서 작성 시나리오에서
작업본을 끝까지 만듦, 평범한 질문에 학습셋 틀이 나오지 않음, 속도가 운영 허용 범위(첫 글자 1 초 안팎, 초당 20 토큰 이상)다.

### 4.11.5 결과(10-24)

학습은 서빙에 들어갔고 학습 꼴 안에서는 좋아졌다(정답 로그확률 -1.845 → -1.153, 시험 문항 chrF 27.9 → 36.6, 질문에 없는 숫자가 든 답 4.1 % → 0 %).
그러나 플랫폼 꼴에서는 문서 작업 에이전트가 동작하지 않았다(문서 작성 시나리오 작업본 2/2 → 0/2). 학습셋 정답의 틀(「근거 설명: … 답변: …」)이 에이전트 단계
출력과 작업 메모 갱신에까지 들어가 형식 관문에 걸렸기 때문이다. 수치 전체와 해석, 어댑터 대조군에서 얻은 절차상의 교훈은 5.4.5 절과 [표 5-18] 에 있다.

판단. 플랫폼의 핵심 흐름이 멈추므로 이번 병합본은 채택하지 않았고 운영은 오픈 27B 를 유지한다(ADR-0069). 다음 판(Writer v2)은 플랫폼이 실제로 보내는
꼴(에이전트 단계 JSON·작업 메모 갱신·채팅 답·절 쓰기와 고쳐 쓰기 지시)로 학습 데이터를 만들어 같은 절차로 다시 비교한다(6.3.2 절).
