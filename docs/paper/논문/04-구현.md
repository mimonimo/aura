## 4.1 문서 반입·OCR·복원

### 4.1.1 목적

학교 원본 문서를 형식에 상관없이 읽어 검색할 수 있는 처리본으로 바꾸고 서류 종류·사업·연도로 정리한다. 원본에는 PDF(디지털·스캔),
한글(hwp·hwpx), 워드·엑셀·파워포인트, 옛 오피스 형식, 사진이 섞여 있다. 담당자는 라이브러리에서 파일 이름이 아닌 본문 제목으로 문서를
찾고, 원본 모양 그대로 열어 보며, 그 글을 검색과 초안의 근거로 쓴다.

### 4.1.2 사용 방법

문서가 들어오는 길은 넷이다. 라이브러리 「문서 올리기」 창에서 파일과 폴더·사업·「사업 연도(선택)」·「업무 종류」(기본 「자동으로
정하기」)를 정해 올리거나 [그림 4-1], 채팅 입력창에 파일을 붙이거나, 프로젝트 「문서 추가」에서 내 컴퓨터·문서함·구글 드라이브의 파일을
가져온다. 학교 원본 폴더에 들어온 원본은 주기 동기화로 원본 장부에 잡혀 자동으로 처리된다. 관리자는 「원본 관리」(/dev/archive)에서
장부를 「목록」·「카드」·「사업별로 보기」로 보고, 교직원은 라이브러리 문서만 보며 원본 파일은 문서의 「원본」으로 연다. [그림 4-2]

### 4.1.3 업무 시나리오

기획처 담당자가 지난 3 년치 결과보고서 묶음(스캔 PDF, hwp, 엑셀 현황표)을 한꺼번에 올리고 사업과 연도만 고른다. 몇 분 뒤 목록에는
「최종_수정본(2).hwp」 대신 본문 제목 「2024년 ○○사업 결과보고서」가 보이고 서류 종류가 붙으며, 스캔 PDF의 「원문」 탭에서는 표의 글자를
골라 복사할 수 있다. 같은 날 채팅에서 「2023년 결과보고서의 취업률 목표와 실적」을 묻자 답의 출처가 방금 올린 스캔본의 표로 이어진다.

### 4.1.4 설계 선택과 이유

하나의 처리기. 네 길로 들어온 문서는 모두 같은 처리기를 거친다(ADR-0049). 길마다 처리가 다르면
같은 문서가 길에 따라 다르게 검색된다.

형식별 읽기 길. 한 OCR 엔진으로 전부 읽으면 글자층이 멀쩡한 디지털 PDF까지 오인식한다. MinerU[19][20]가 글자층 있는 문서를 스캔으로
다뤄 「기초과학」을 「기추과하」로 읽은 일이 있었고, 반대로 스캔본을 글자층으로 읽으면 깨진 한자만 남는다. 그래서 문서마다 글자층을
먼저 재고 길을 나눈다.

복원 보기는 배경 그림 + 투명 글자층. 블록 좌표 재배치, 글자 좌표 직접 그리기, 원본 그림 위 투명 글자층의 세 방식을 실물 렌더로
비교했다. 첫째는 잘림·중복·왜곡이, 둘째는 표 괘선·서식 누락이 있어 원본 모양과 글자 고르기를 함께 지키는 셋째를 택했다(실험 로그 3절).

판정은 모델, 후보와 형식은 코드. 제목 낱말 규칙으로 서류 종류를 정하면 「주간업무보고」를 결과보고서로, 견적서를 계획서로 보는 오판이
많았다. 그래서 종류와 사업 판정은 Writer 27B가 하고 코드는 후보 목록·출력 형식·재확인 관문을 맡는다.

### 4.1.5 구현

[그림 4-4]는 한 문서가 처리되는 순서다.

확장자가 없거나 틀리면 파일 머리로 실제 형식을 확인한다. 디지털 PDF(표본 6쪽 글자 충분, 깨진 글자 비율 0.15 미만)는 pdfium[22] 글자 좌표를 직접 읽어 MinerU 구조(표·2 단·읽기 순서) 위에 원본 글자를 덮어쓴다. 스캔 PDF(쪽당 200자 미만 또는 깨진 글자 0.15 이상)는 MinerU가 기본이고, 짧은 문서는 27B 이미지 판독(최대 30쪽)을 쓴다. 사진은 27B 이미지 판독, MinerU OCR, tesseract[23] 순으로 시도한다. hwp는 kordoc(판 고정)으로 읽고 실패하면 pyhwp로, hwpx는 자체 OWPML 파서(표·글상자·머리말)로 읽는다. 오피스 문서는 kordoc 뒤 python-docx·openpyxl·python-pptx로 읽고, 쪽당 60자 미만이면 MinerU로 다시 읽는다. 옛 형식(xls·doc·ppt·hwp3)은 LibreOffice[27]로 새 형식으로 바꿔 같은 길을 탄다. 읽은 뒤에는 표 정리 → 개인정보(4.2) → 조각 나누기 → 서류 종류(27B) → 사업 분류 → 판본 묶기 → 문서 이름 → 색인(4.3)·그래프(4.4) 순서로 간다. 27B 이미지 판독은 표를 병합 칸이 살아 있는 HTML 표로, 제목을 머리말로 쓰고, 흘린 손글씨는 지어내지 않고 「(판독 불가)」로 적는다.

[그림 4-4] 문서 한 건의 처리 순서 (그림 docs/images/diagrams/c4-04-doc-process.png)

원본 장부와 동기화. 원본 장부는 원본 파일마다 경로·크기·수정 시각·사업·처리 상태·서류 종류·연도·차수·
중복 대상·등록 문서 번호를 한 줄로 담는다. 운영 서버는 10 분마다 원본 폴더를 훑어 새로·바뀜·옮김·없어짐을 장부에 반영하고(잠금으로
겹쳐 돌지 않음), 목록이 바뀌었다는 표시를 받으면 1분 안에 동기화한다. 같은 파일 찾기는 이름·크기가 같은 묶음 안에서만 sha256
을 낸다. 원본 폴더는 개발 화면 「서버 설정」에서 서버 안 폴더(NAS를 붙인 자리)나 원격 경로로 정한다.

표 처리. 표 조각은 칸마다 [행, 열, 행 병합, 열 병합, 머리칸 여부, 글]로 저장하고 화면은 이를 병합 표로 그린다. 검색·인용용 평문은
행마다 칸을 「 | 」로 잇되, 가로 병합은 첫 칸에 한 번만 쓰고 세로 병합 때문에 되풀이만 하는 행은 내지 않는다.
병합 칸을 칸마다 채우면 「예비군대대 | 예비군대대 | 예비군대대 …」 같은 줄이 검색 잡음이 되기 때문이다. 디지털 PDF의 표는 괘선 좌표와
글자층을 직접 읽어 칸 비율까지 복원한다.

조각 나누기. 사업 문서는 파서가 낸 블록(제목·문단·표·그림 글)을 하나씩 조각으로 만들고(본문 최대 2,000자, 문서당 최대 2,000 조각),
조각마다 쪽 번호와 소속 절의 제목 경로를 붙인다. 규정은 「제N조」가 셋 이상이면 조문 단위로 자른다.
40자 미만 조각은 다음 조각과 합치고, 1,400자를 넘으면 줄·문장 단위로 나누며, 실질 20자 미만 잡음 조각은 뺀다(ADR-0048).

서류 종류 판정. 27B에게 종류 19가지와 한 줄 설명, 제목, 폴더, 본문 앞 1,500자를 주고 {kind, why} JSON 하나를 받는다.
목록 밖 답이나 형식 오류는 버리고 규칙 판정을 남긴다. 검색에서 빠지는 종류(증빙)로 판정하면 본문 2,500자로 한 번 더 확인하고, 본문이
200자 미만이면 규칙과 엇갈리는 증빙 판정을 받지 않는다. 판정 줄마다 지시 판 번호와 모델 정보를 남겨 지시를 고치면 옛 판정을 다시 본다.

사업 분류. 기준은 사업 장부다. 사업마다 정식 이름·다른 이름·기간·주관 부처·전담기관·앞뒤 단계와 그 출처를 담고,
사업의 동일성과 이름 변경은 외부 검색으로 출처를 확인해 적는다. 분류는 규칙(폴더 경로·제목·본문의 장부 이름) → 폴더 단위 판정 →
파일 단위 판정의 세 층이며 뒤의 것이 앞선다. 파일 단위 판정에서 27B는 장부의 사업 하나, 「사업 아님」, 「모름」 가운데
하나를 근거 한 문장과 함께 고르고, 장부에 없는 이름과 「모름」은 적지 않는다.

판본 묶기와 이름. 제목에서 붙임 번호·괄호·공백을 뗀 열쇠로 후보를 찾고 본문을 8자 조각 집합으로 비교해, 겹침 0.95 이상은 같은 내용으로
보아 받지 않고 그 아래는 판본으로 잇는다. 가장 가까운 실제 판본 쌍이 0.90이어서 문턱을 0.95로 두었다. 문서 이름은
공문의 「제목:」 줄 → 본문 제목 줄 → 모델이 짚은 본문 제목 줄 → 군더더기를 걷은 파일 이름 → 「종류 · 사업 연도」 순으로 정한다.
본문 제목이 파일 이름에 있던 연도·차수·기관 같은 구별 정보를 잃으면 쓰지 않고, 사람 이름은 제목에서 뺀다.

정리. 지출·계약 증빙, 같은 본문 중복, 같은 제목에 본문이 거의 같은 여분, 빈 문서, 도면, 개인 제출물은 라이브러리에서 정리한다.
지우기 전에 문서 행과 딸린 조각·그림·색인·연결을 백업하고, 원본은 원본 관리의 정리함으로 옮기며, 관리자는 「정리」 칸에서 되돌릴 수 있다.

## 4.2 개인정보 가림

### 4.2.1 목적

문서 속 주민등록번호·전화·이메일·계좌·사업자번호·학번·생년월일·성명을 찾아 가린다. 교내 담당자가 업무로 보는 원문을 모두 가리면 일을
할 수 없고, 학습 데이터나 밖으로 나가는 글은 반드시 가려야 한다. 그래서 내부 열람과 학습 반출의 관문을 나눈다(ADR-0044).

### 4.2.2 사용 방법

관리자는 개발자 화면 「개인정보·반출 점검」(/dev/pii)의 「처리 정책」·「점검 도구」·「과거 처리 기록」 세 탭을 쓴다. [그림 4-5]
「처리 정책」의 「내부 마스킹 설정」에서 「내부 문서의 개인정보 가리기」(기본 꺼짐)와 「가릴 항목」을 정한다. 「점검 도구」에는 합성 표본으로
항목별 판정을 보이는 「마스커 자가 점검」과, 색인된 본문에 가렸어야 할 형식이 남았는지 문서 유형·위치·문맥 표본(값은 가림)으로 보이는
「저장 본문 잔여 검사」가 있다. 자가 점검은 매일, 잔여 검사는 주 1회 새벽 정리에서 자동으로 돌고, 결과가 그보다 오래되면
「자동 실행 확인 필요」가 뜬다. 「과거 처리 기록」은 반입 때 남긴 가리기 기록을 문서명·유형으로 찾는다. 내부 가림을 켰다가 꺼도 이미
가린 본문은 되살아나지 않으며, 되살리려면 원본에서 다시 반입한다.

[그림 4-5] 개인정보·반출 점검: 「내부 마스킹 설정」과 「마스커 자가 점검」 결과 표 (그림 docs/images/figures-1027/f4-05-pii-masking.jpg)

### 4.2.3 업무 시나리오

입학처 담당자가 「○○○ 학생의 연락처 알려 줘」라고 물으면 권한 점검이 모델을 부르지 않고 막고, 감사 기록에는 질문 앞부분만 남는다.
「신입생 장학 신청서 양식에서 개인정보 동의 문구가 어디 있지?」는 정상 질문으로 답한다. 관리자는 수집 자료를 학습 재료로 내보내기 전에
자가 점검과 잔여 검사 결과를 확인한다.

### 4.2.4 설계와 구현

탐지는 Presidio[47] 위에 한국형 패턴 인식기 8종을 얹었다. 주민등록번호와 사업자번호는 체크섬으로 검증해 우연히 같은 형식인
숫자를 거른다. 계좌·학번·생년월일·성명은 「계좌번호:」·「성명」 같은 이름표 문맥이 있을 때만 잡는다. 이름표 없는 이름까지 잡으면 사업·기관
이름이 대량으로 가려지기 때문이다. 표에서는 옆 칸의 직위 문맥으로 성명을 한 번 더 가린다.

가림 설정과 정책은 한 모듈에 둔다. 밖으로 나가는 글에는 설정과 상관없이 고위험 형식(주민번호·이메일·휴대전화·카드번호
정규식)을 한 번 더 적용하고, 가림에 실패하면 보내지 않는다(fail-closed). 학습 사본은 가림을 다시 해도 바뀌지 않는 파일만 반출한다.

잔여 검사는 마스커의 인식기 정의(정규식·체크섬)를 Presidio 분석 엔진 없이 따로 컴파일해 저장·색인된
본문(문서 본문, 문서 조각, 규정 조각)에 다시 돌린다. 엔진의 점수·임계값 배관이 잘못돼도 여기서 드러나게 하려는 것이다.

```
def find_spans(text: str, detectors: Sequence[tuple[str, Any, Any]]) -> list[tuple[int, int, str]]:
    """탐지 구간 (start, end, entity). 겹침은 앞선 것·긴 것 우선 — 마스커와 같은 규칙."""
    spans: list[tuple[int, int, str]] = []
    for entity, rx, validate in detectors:
        for m in rx.finditer(text):
            if validate(m.group()) is False:   # None은 검증 없음, False만 탈락
                continue
            if _already_masked(m.group()):     # 우리가 가려 놓은 자리는 잔여가 아니다
                continue
            spans.append((m.start(), m.end(), entity))
    …
    result["enforced_hits"] = sum(n for e, n in by_type.items() if e in set(pol.get("entities") or [])) if pol.get("enabled") else 0
```

별표나 「[KR_」·「[EMAIL]」 자리표를 품은 구간은 이미 가린 자리라 세지 않는다. 「가렸어야 할 잔여」(enforced_hits)는 내부 가림이 켜져 있을 때
그 설정에 든 항목만 세고, 설정 밖 항목은 전체 건수(hits)로 따로 보인다.

### 4.2.5 결과

배포 점검의 전체 잔여 검사(10-09)에서 문서 41,764건·조각 1,973,998개 가운데 가렸어야 할 잔여는 0건이었다. 정규식 기반이라 이름표 없는
이름·주소를 놓칠 수 있어 완전 제거의 증명은 아니며, 그래서 학습 반출에는 사람 검수를 함께 요구한다.

## 4.3 검색: 하이브리드와 리랭커

### 4.3.1 목적

질문에 맞는 근거 조각을 열람 권한 안에서 찾는다. 행정 질문에는 사업 약칭·규정 이름·숫자처럼 글자 그대로 맞아야 하는 말과 「학생이
휴학하려면」처럼 뜻으로 찾아야 하는 말이 섞여 있어, 한 방식만으로는 어느 한쪽을 놓친다.

### 4.3.2 사용 방법

검색은 채팅 질문마다 돌고, 근거는 답 아래 출처와 작업 패널의 「연관 자료」에 보인다. 제목·본문을 직접 찾을 때는 사이드바 「검색」(Ctrl+K)을
쓴다. 결과는 「문서」, 「본문 대목」, 「프로젝트」, 「대화」 네 묶음이고, 본문 대목을 누르면 문서 화면의 그 자리가 열린다. [그림 4-6]

[그림 4-6] 검색 결과: 「문서」·「본문 대목」·「프로젝트」·「대화」 묶음 (그림 docs/images/figures-1027/f4-06-search-groups.jpg)

관리자는 검색 범위를 「RAG 공간」(/dev/rag)에서 다룬다([표 4-5]). [그림 4-7]

[그림 4-7] RAG 공간: 「RAG 목록」과 「검색 범위 시험」 창 (그림 docs/images/figures-1027/f4-07-rag-spaces.jpg)

| 칸·단추 | 하는 일 |
|---|---|
| 「RAG 목록」 | 「공통 RAG」, 「{부서} 부서 RAG」, 「학생 RAG」의 문서 수·기준 문서·쓰는 계정·최소 등급. 줄을 누르면 오른쪽에 구성·「다른 부서에 열기」 |
| 「다른 부서에 열기」 | 부서 RAG를 받을 부서를 칩으로 고른다. 받는 쪽은 보기·검색만 한다. 관리자와 그 부서 총괄 책임자가 연다 |
| 「검색 범위 시험」 | RAG와 검색어를 넣으면 모델을 부르지 않고 「규정 색인」과 「사업 문서」 상위 5개만 보인다. 새 규정이 학생 RAG에 잡히는지 볼 때 쓴다 |
| 「기준 문서」 | 라이브러리 「기준」 목록으로 간다. 규정·지침의 등록·학생 공개 지정·검색에서 빼기는 라이브러리에서 한다(관리자) |

### 4.3.3 업무 시나리오

학사지원팀 담당자가 「현장실습 학점 인정 기준이 바뀌었나?」라고 물으면, 어휘 축은 「현장실습」·「학점」이 든 조문을, 의미 축은 「실습
이수 시간에 따른 학점 부여」처럼 표현이 다른 조문을 올린다. 리랭커가 후보 20개의 순서를 고치고, 옛 판 조문은 최신 판의 같은 조문으로 바뀌어
출처가 된다. 「2022년 기준으로는?」이라고 되물으면 연도를 지정했으므로 옛 판이 근거가 된다. 학생 계정에는 학생 공개로 지정된 학사 규정만
후보가 된다.

### 4.3.4 설계 선택과 이유

두 색인. 규정 색인(교내 규정·지침·공고, 조문 단위)과 사업 문서 색인(계획서·보고서·서식·공문 조각)을 따로 둔다([표 4-6]). 하나로 합치면
규정 질문에 사업 문서 조각이, 사업 질문에 규정이 섞인다. 두 검색은 서로 기대지 않아 동시에 돌린다.

| | 규정 색인 | 사업 문서 색인 |
|---|---|---|
| 조각 | 조문·표제 단위(regulation_chunks) | 블록 단위(doc_chunks) |
| 의미 | Embed v2 | Embed v2, pgvector(grant_vec) |
| 어휘 | Kiwi 명사·IDF | 미리 뽑은 낱말(grant_lex, GIN) |
| 리랭커 | 씀 | 끔 |
| 범위 | 열람 등급·부서·학생 공개 | 열람 등급·RAG 공간 부서, 증빙 종류 제외 |

[표 4-6] 두 색인의 차이

학습한 임베딩. 공개 한국어 임베딩 KURE-v1[29]은 「교원업적평가」·「차년도 사업비 이월」 같은 교내 용어와 규정 문체에 약했다. 채택 기준은
단독 지표가 아니라 운영 하이브리드에서 후보 진입률이 오르는지로 두었다. v1은 단독 지표만 오르고 운영 경로 이득이 없어, 학습 방식을 고친
v2를 운영에 넣었다(ADR-0021). 다중 벡터 모델 KURE-v2는 학습 전에도 근접했지만 역시 운영 경로 이득이 없어 쓰지 않았다(ADR-0025).

리랭커는 규정에만. 사업 문서 검색에서는 그래프 절 축·문서당 2개 규칙과 겹쳐 오히려 손해라 껐다. 생성 모델로 후보를 다시 매기는 방식은
덜 정확하고 53배 느렸다.

pgvector. 사업 문서 벡터는 PostgreSQL의 pgvector[36] HNSW[37] 색인에 둔다(ADR-0057). 권한·부서·종류 조건을 같은 SQL에 걸 수 있고,
운영 서버 메모리에 5GB 넘는 배열을 올리지 않아도 된다.

### 4.3.5 구현

[그림 4-8]은 검색 한 번의 흐름이다.

질문은 입력 정리(전각 → 반각) 뒤 RAG 공간의 열람 조건을 검색 SQL의 WHERE로 달고 두 갈래로 간다. 규정 검색은 어휘(Kiwi 명사·영문 약칭, IDF)와 의미(Embed v2) 순위를 순위 융합 RRF[35](k=60, 어휘 0.4·의미 1.0)로 섞고, 후보 20개를 Rerank v1이 다시 줄 세운 뒤 1 위 점수의 0.25배 아래 꼬리를 버린다. 사업 문서 검색은 그래프 범위 안에서 그래프 절 축(묶어 적은 절 제목)을 먼저 보고, 어휘(grant_lex, GIN)와 의미(grant_vec, HNSW)를 같은 가중의 RRF로 섞되 어휘 1 위 조각을 지키며, 판본 최종본만 문서당 2 조각씩 상위 5개를 고른다. 두 결과는 규정 묶음과 사업 문서 묶음으로 근거에 담겨 생성(4.5)으로 간다.

[그림 4-8] 검색의 흐름 (그림 docs/images/diagrams/c4-08-search-flow.png)

어휘 축은 색인과 질의가 같은 낱말 함수를 쓴다. Kiwi[33] 명사와 두 글자 이상 영문 약칭을 소문자로 모으고
띄어 쓴 복합 명사를 붙이며, 드문 낱말에 무게를 주는 IDF[34]로 점수를 낸다. 임베딩은 규정 조각마다 27B로 만든 합성 질의 세 형식(실무형·
공고 요구사항형·키워드형)과, 운영 하이브리드가 올린 후보 상위 20 가운데 정답이 아닌 조각(어려운 오답, 최대 6개)으로 대조학습(InfoNCE[31],
온도 0.05)을 2에폭 했다. 문서 단위로 20 %를 홀드아웃으로 뗐고, 서빙 장비 GPU에서 약 20분 걸렸다. 리랭커(bge-reranker-v2-m3[32]
바탕)는 운영 하이브리드가 올린 후보 목록 전체에서 정답 쪽 확률을 높이는 목록 단위 학습을 했다.

섞는 비율. 어휘 가중은 0.2~0.5에서 결과가 평평했고, 임베딩 학습 문서를 뺀 질의 22,084 건으로 다시 재도 가중 0~0.6에서 후보 진입률이 같아 0.4를
유지했다(실험 로그 10절).

서빙과 대체 경로. 색인에 모델 이름을 적어 질의 모델과 대조한다. 교내망 보안 장비가 긴 숫자열 요청을 끊어 9자리 이상 숫자열은 가린 뒤 보낸다.
서비스가 응답하지 않으면 규정 검색은 운영 서버 CPU 모델로, 사업 문서 검색은 어휘 축만으로 대신한다.

판본과 규정 등록. 검색 때 같은 판본 묶음에서 개정일(없으면 원본 수정 시각)이 가장 늦은 판만 남기고, 옛 판 조각이 걸리면 최신 판의 같은
글로 바꾼다. 학교 원본으로 들어온 규정은 처음에 사업 문서로 반입되고, 관리자가 판본 묶음마다 최신 판 하나를 「새 판·미등록
규정」에서 골라 「검색에 추가」하면 조문 단위로 다시 조각낸다(ADR-0064, 되돌리기 있음).

## 4.4 지식 그래프와 온톨로지

### 4.4.1 목적

문서가 수만 건이면 「LINC 3.0 2차년도 실적보고서의 취업 성과」 같은 질문은 조각 유사도만으로 풀기 어렵고, 사업·연차·종류를 먼저 좁혀야
한다. 「계획 대비 실적」·「앞 단계 사업」처럼 문서 사이 관계를 묻는 질문은 관계가 데이터로 있어야 답할 수 있다(ADR-0047). 지식 그래프는
사업 > 연차 > 문서 > 절 구조와 문서 사이 관계를 근거와 함께 담아 검색 범위를 정한다.

### 4.4.2 사용 방법

그래프는 「그래프 탐색」(/graph/explore)에서 보며, 라이브러리 머리·문서 화면·채팅 오른쪽 패널에서 연다. 사업 이름을 찾거나 「전체 보기」로
시작해, 노드마다 「이것만 보기」·「선택에 더하기」·「이웃 펼치기」로 그림을 좁히거나 넓히고, 문서 노드는 「문서 열기 ↗」로 연다. [그림 4-9]
「사업별 표」는 사업 그래프(/graph/program)에서 「연차별 문서」, 「성과지표」, 「계획 ↔ 실적 대응」(계획서 절 · 실적보고서 절 · 근거),
「연차 사이 같은 절 · 평가」를 표로 보인다. [그림 4-10] 관리자는 「온톨로지」 보기에서 노드 종류·관계·속성의 전체 스키마와
「구조 검사 {시각} · 세 쌍 N · 규칙 N개 · 위반 N건」 한 줄을 보고, 설계도와 검사 결과를 내려받는다([표 4-8]). [그림 4-11]

Protégé[45] 같은 온톨로지 도구로 열 수 있다.

### 4.4.3 업무 시나리오

산학협력단 담당자가 「LINC 3.0 2차년도 계획 대비 실적을 비교해 줘」라고 물으면 27B가 사업(LINC 3.0)·차수(2)·관계(계획↔실적)를 읽고, 코드는
그 사업의 2 차년도 계획서와 실적보고서에서 짝지은 절 쌍(예: 「취업 지원」 ↔ 「취업 지원 실적」)의 조각을 하나씩 근거에 담는다. 답에는 목표와
실적이 각자의 출처와 함께 나온다. 「그 전 단계 사업에서는?」이라고 이어 물으면 앞 단계 관계(succeeded_by)를 따라 LINC+ 문서로 범위가 넓어진다.

### 4.4.4 설계 선택과 이유

질문 읽기는 모델, 그래프 탐색은 코드. 사업 이름 맞추기와 「N차년도」·종류 낱말 정규식만으로 질문을 읽으면 「계획 대비 실적」을 계획 종류로만
보고, 앞 단계 사업을 물어도 질문에 적힌 사업만 본다. 질문 형식마다 정규식을 덧대는 대신 질문의 뜻은 모델이 읽고 그래프 탐색은 코드가
결정적으로 한다(ADR-0063).

근거 없는 관계는 만들지 않는다. 관계마다 기준(구조·분류·식별자 일치·추출·유사도 가운데 하나)과 근거(문서·절 위치나 외부 출처 URL)를
단다. 사업 사이 관계와 기관은 외부 확인 장부에서만 가져온다.

표준 층. 온톨로지가 코드 안 규칙으로만 있으면 검증할 수 없어, 설계도를 OWL[40]·RDF[41]로 내보내고 SHACL[42] 규칙으로 검사한다(ADR-0056).

### 4.4.5 구현

온톨로지. 노드 종류는 사업 묶음, 사업, 기관, 연차, 문서, 절, 단위과제, 성과지표의 여덟이다. 문서는 서류 종류를 하위 분류로 갖고, 어느
사업에도 속하지 않는 기관 업무 문서는 따로 둔다(ADR-0048·0055). [그림 4-12]는 주요 관계다.

사업 묶음 → 사업 → 연차 → 문서 → 절은 포함(contains)으로 잇는다. 사업은 주관 부처·전담기관(supervised_by·managed_by), 앞뒤 단계·편입 사업(succeeded_by·integrated_into)과 이어지며, 이 관계는 외부 확인 장부에서만 온다. 문서끼리는 계획↔실적(plans_reports)과 평가(evaluates)로, 절은 같은 사업에서 되풀이되는 단위과제로 잇고, 성과지표는 측정 관계로 단다.

[그림 4-12] 온톨로지의 노드와 관계 (그림 docs/images/diagrams/c4-12-ontology.png)

SHACL 규칙은 연차가 사업 하나에만 속하고 연도가 1990~2035 인지, 문서의 종류가 하나까지이고 사업·연차에 속하거나 기관
업무 문서인지, 관계마다 기준 다섯 중 하나에 근거가 하나 이상인지 등을 보며, 그래프를 다시 지을 때마다 검사한다.

그래프 구축. 그래프는 PostgreSQL의 노드 표(kg_nodes)와 관계 표(kg_edges)에 둔다.
사업 → 연차 → 문서는 사업 분류와 문서 연도·차수로 잇고, 연차를 모르는 문서는 연차에 넣지 않는다. 문서 → 절은 처리본의 제목 경로로 만든다.
계획↔실적은 같은 사업·연차의 계획서와 실적보고서를 잇고, 절끼리는 제목 맥락과 본문 유사도로 짝짓는다. 「차년도 계획」 절은 빼고, 연차가
맞지 않으면 잇지 않는다.

절 짝 판정은 번호를 뗀 제목 열쇠가 4자 이상 같은 절끼리만 후보로 놓고 맥락 점수를 매긴다.

```
    def score(x: Section, y: Section, generic: bool = False) -> float:
        ca, wa = ia[id(x)]
        cb, wb = ib[id(y)]
        weights = (0.6, 0.3, 0.1)
        anc = sum(w * _jac(p_, q_) for w, p_, q_ in zip(weights, ca, cb)) / (sum(weights[:min(len(ca), len(cb))]) or 1)
        if not ca and not cb:
            anc = 1.0                                         # 둘 다 최상위 절
        if not wa and not wb:
            return 0.0                                        # 본문도 하위 절도 없는 머리글(표지 줄 등)끼리는 잇지 않는다
        body = _wjac(wa, wb, idf)
        …
        if generic:
            return 0.3 * anc + 0.7 * body if body >= generic_body else 0.0
        return 0.5 * anc + 0.5 * body
```

상위 절 세 단계 제목의 글자 겹침(가까운 조상부터 0.6·0.3·0.1 무게)과 본문·하위 절 제목의 낱말 겹침(두 문서 안 희소성 가중)을 반씩 더해 0.25 이상이면
잇는다. 한 문서에 세 번 이상 나오는 흔한 제목은 바로 위 절 제목 겹침 0.5 이상, 본문 겹침 0.15 이상이고 2등 후보보다 0.08 이상 높아야 한다.
「우수사례 1」 같은 번호 붙은 사례는 본문 겹침 0.5 이상으로 1:1 로만 잇는다. 제목 짝이 하나도 없으면 본문으로 잇되, 200자 이상인
보고서 절에서 1등 겹침이 0.2 이상이고 2등과 0.05 이상 차이 날 때만이다. 성과지표는 표 칸 격자에서 「성과지표」 칸을 찾아 칸 이름으로
기준·목표·실적·달성률을 읽고 값을 그대로 꺼낸다. 모델은 값을 만들지 않는다.

GraphRAG[39]의 흐름은 [그림 4-13]과 같다.

27B에게 질문, 질문에 겹치는 사업 후보 목록(번호), 관계 7종을 건네면, 27B는 온도 0, 출력 120토큰, JSON 스키마 강제로 {사업 번호, 연도, 차수, 종류(계획·실적·평가), 따라갈 관계}를 낸다. 사업은 목록 번호로만 받고, 같은 질문은 10분 동안 기억한다. 나머지는 코드가 결정적으로 한다. 이름 맞추기에 모델 읽기를 보태 범위를 정하고 관계(짝·평가·앞뒤 단계·편입)를 따라 넓힌다. 연도를 물으면 연도 모르는 문서를 빼고, 「」로 묶은 이름이 문서·절 이름이면 그것으로 좁힌다. 범위 안에서 하이브리드 검색(4.3)을 하되 관계 질문은 양쪽 문서에서 한 조각씩 담고, 절 축 조각도 권한을 다시 거른다. 모델 읽기가 실패하면 이름 맞추기만으로 범위를 정한다.

## 4.5 채팅과 답변 방식

### 4.5.1 목적

질문하면 열람 권한 안의 근거 문서를 찾아 출처와 함께 답하고, 근거에 없는 숫자는 표시한다. 긴 대화에서도 담당자가 알려 준 값과 정한
방향을 잃지 않는다.

### 4.5.2 사용 방법

채팅 화면(/chat)의 입력창 아래 도구줄에 첨부, 「일반」·「RAG」 토글, 「RAG 범위」, 답변 깊이가 있다. [그림 4-14] 「RAG」는 내 계정의
RAG(공통·부서) 문서를 근거로 답하고 작업 문서를 고친다. 「일반」은 문서 없이 모델이 답하고, 인터넷 확인이 필요해 보이는 답에는 「인터넷에서
찾아보기」 선택지가 붙는다([표 4-10]). 프로젝트 대화와 파일을 붙인 질문은 「RAG」로 시작한다. 답변 깊이는 「꼼꼼하게」(기본, 단계 추론으로
자료를 넓게 보고 맡긴 절을 자기 점검하며 에이전트 단계 한도가 1.5배)와 「빠르게」(자기 점검 없이 바로 답)이고, 고른 값은 계정에 기억된다.

[그림 4-14] 채팅 첫 화면: 두 줄 입력창(일반·RAG 토글, 「RAG 범위」, 답변 깊이) (그림 docs/images/figures-1027/f4-14-chat-start-input.jpg)

답을 쓰는 중에 보낸 요청은 「다음 요청으로 넣기」로 대기열에 들어가 차례로 시작된다. 답 아래 출처를 누르면 오른쪽 패널에 그 대목이 열리고,
작업 패널의 「연관 자료」에는 근거 목록이, 「적용 기준」에는 이 대화에 적용한 기준 문서가 보인다. 「생각 과정 펼치기」는 [1단계: 질문 파악]
→ [2단계: 근거 확인] → [3단계: 답 구성]의 단계 추론을, 입력창의 「문맥 N% 사용」은 「문맥 관리」 창의 「지금 목표」와 모델 호출 횟수를
보인다. [그림 4-15] 「아쉬움」 평가는 까닭(「근거 문서가 틀림」, 「숫자·사실이 틀림」 등)을 여럿 고르고 한 줄 의견을 남기며, 「이 질문부터
다시 생성」은 그 질문부터 다시 답하고 이후 대화는 이력에 보관한다.

[그림 4-15] 답과 출처 패널, 「생각 과정 펼치기」 펼침, 「문맥 N% 사용」 (그림 docs/images/figures-1027/f4-15-answer-sources-thinking.jpg)

| 모드 | 근거 | 밖으로 나가는 것 | 학생 |
|---|---|---|---|
| 「RAG」(처음 값) | 계정 범위의 규정 색인 + 사업 문서 색인 + 그래프. 고른 RAG로 좁히기만 | 없음 | 학생은 학사 RAG 만(토글 숨김) |
| 「일반」 | 없음(모델 지식). 출처 없음을 밝힘 | 없음 | 없음 |
| 「인터넷에서 찾아보기」(일반 답의 선택지) | 웹 검색 결과 쪽 글(출처 번호) | 질문 글만. 개인정보가 있으면 보내지 않음 | 없음 |

[표 4-10] 답변 방식(ADR-0076, ADR-0038)

화면 아래 「수치와 최종 판단은 근거 문서에서 확인하세요.」는 AURA의 산출물이 사람이 검수할 초안이라는 원칙을 적은 것이고, 답 속 숫자에
붙은 「(근거 확인 필요)」는 모델에 건넨 근거에서 찾지 못한 값이라는 표시다.

### 4.5.3 업무 시나리오

기획처 담당자가 「AI 교육 쪽으로 뭔가 사업을 해 보고 싶은데」라고 쓰면, AURA는 비슷한 지난 사업과 관련 규정을 출처와 함께 보이고
대상·예산·기간을 묻는다. 담당자가 「2027년 1학년 대상, 예산 5천만원, 기간은 3월부터 12월」이라고 답하고 세 턴이 지나도, 「문맥 관리」의 「지금
목표」는 「2027년 1학년 대상 AI 교육 사업계획서 작성 및 목차 구성」이고 확정된 것에 세 값이 원문 그대로 남는다(실제 27B 세 턴 시험, 임시 DB).
「작년 비슷한 사업의 참여 인원은?」의 답에 「300명(근거 확인 필요)」이 붙으면 담당자는 출처 패널에서 실제 값을 확인한다.

### 4.5.4 설계 선택과 이유

권한은 검색 단계에서. 답을 만든 뒤에 거르면 모델이 이미 다른 부서 자료를 읽은 뒤이므로 권한은 검색 SQL 조건으로 건다(3.5절).
출처는 모델에 실제로 건넨 근거 목록에서만 만들고, 모델이 답에 쓴 출처 표시는 그대로 믿지 않는다. 모델이 쓴 숫자가 근거에 있는지는
코드가 기계적으로 대조한다. 대화 기억은 최근 대화를 개수로 자르지 않고 작업 메모와 문맥 한도 비율로 다룬다. 개수로
자르면 그 밖의 대화가 사라지고 모델마다 문맥 한도도 다르기 때문이다(ADR-0065).

### 4.5.5 구현

답 흐름은 열 단계다.

1. 입력 정리: 전각 문자를 반각으로 바꾼다.
2. 권한 점검: 특정인의 개인정보 질문은 모델을 부르지 않고 막고, 지시를 바꾸려는 질문과 범위 밖 부서 질문은 감사 기록에
   남기며, 계정의 RAG 공간으로 검색 범위를 정한다.
3. 문서 작업 에이전트가 먼저 받아 도구를 고른다(4.6). 모델에 닿지 못할 때만 낱말 규칙 경로를 쓴다.
4. 검색: 규정·사업 문서 검색을 동시에 돌리고, 프로젝트 대화면 그 프로젝트 문서를 앞에 둔다.
5. 근거 묶기: 두 묶음을 따로 표시해 건네고, 근거가 없거나 약하면 그렇다고 알린다.
6. 문맥 맞추기: 첨부 → 오래된 대화 → 출력 상한 → 검색 근거 순으로 줄이고, 그래도 넘으면 보내지 않는다.
7. 생성: 「첫머리 1~3 문장 답, 근거 요점 5개 이내, 표·문단 옮겨 적지 않기, 600자 안팎」. 만들어지는 대로 화면에 보이고, 출력 한도에서 끊기면 한 번 이어 쓴다.
8. 근거 밖 숫자 표시: 근거에 없는 숫자에 「(근거 확인 필요)」를 붙이고 끝에 안내한다.
9. 출처: 건넨 근거 목록에서만 만든다.
10. 기록: 답마다 실행 기록과 담당자 평가를 남긴다.

화면은 긴 일을 뒤에서 돌리고 진행 상태(/chat/{번호}/status)를 1~4초 간격으로 물어 단계 이름과 근거 개수만 받는다. 모델의 내부 추론·프롬프트·
원문은 진행 상태에 싣지 않는다.

수치 대조. 답과 근거에서 숫자를 뽑아 표면형(쉼표 제거)과 정준값(조·억·만·천 환산, 「3억 5천만」 합산, 「1만 1799명」 → 11,799)으로 비교한다.
같은 금액을 단위만 바꿔 쓴 값(5억 = 500,000,000 원 = 500 백만원 = 「(단위: 백만원)」 표의 500)은 같은 값으로 본다(ADR-0068). 우회를 막으려고
환산은 금액끼리만, 같은 덩이에서 가장 가까운 단위 선언 하나만 쓴다. 판정은 수치 검증기의 한 함수가 하고, 채팅 답에는
「(근거 확인 필요)」를 붙이고, 독스 초안에는 「○○」를 넣으며, 한글 절 본문은 같은 판정으로 되돌려 보낸다
(4.6.5절 본문 관문).

```
    for m in _NUM_UNIT.finditer(src):
        surface = m.group(1).replace(",", "")
        …
        if src[line_start:m.start()].strip() == "" and re.match(r"[.)]\s", after):
            continue                                          # 목록 번호 「1. 」「2) 」
        if _YEAR_LIKE.match(surface):
            continue
        …                                                     # 전화번호·날짜·코드(010-1234-5678, 2026.4.3, 3/4)는 수치가 아니다
        try:
            small = Decimal(surface) <= 10 and not unit and tail != "%"
        except Exception:
            small = False
        if small:
            continue
        if _supported(src, m, allowed_surface, allowed_canonical, allowed_money):
            continue
```

대조에서 빠지는 것은 연도 형식(1900~2099의 네 자리), 줄 첫머리의 목록 번호, 앞뒤에 숫자와 「-」·「/」·「:」·「.」가 붙은 형식(전화·날짜·코드),
단위도 %도 없는 10 이하 숫자뿐이다. 나머지 숫자는 근거의 표면형·정준값·금액 값 가운데 하나와 같아야 통과한다.

작업 메모와 단계 추론. 답이 끝나면 배경에서 「앞 메모 + 그 뒤 대화 → 새 메모」를 만든다. 메모는 지금 목표 / 확정된 것 /
진행 상황 / 남은 일·물어볼 것이고, 맨 앞 「최종 결과물」 한 줄은 담당자가 바꾸자고 하지 않으면 지킨다. 요청에는 메모(문맥 한도의 6 %까지)와
최근 대화 원문(30 % 몫)이 들어간다. 단계 추론의 형식은 학습 데이터의 구조 단계 문답과 같다.

대화 제목과 대기열. 새 대화를 만들면 배경에서 검토 연결 모델이 8~20자 명사구 제목을 지어 바꾸고, 모델이 늦거나 못 쓰는 답을 내면 첫 요청에서
딴 처음 제목을 둔다. 담당자가 바꾼 이름과 프로젝트 대화의 「[프로젝트 이름]」 머리는 지킨다. 답을 쓰는 동안 들어온 요청은
대화마다 100 건까지 대기열에 두고, 답이 끝나면 입력줄 보내기와 같은 길로 다음 요청을 시작한다. 꺼낼 때 대화 주인·함께 작업 권한과 계정의
역할·부서를 다시 읽고, 서버를 다시 켜면 남은 요청을 이어서 시작한다.

「인터넷에서 찾아보기」는 구글[70]·네이버[71] 검색 키가 있으면 그것을, 없으면 DuckDuckGo[72]를 쓰고, 가져온 쪽 글을 근거로
27B가 출처 번호를 달아 답한다. 검색 제공자와 키는 개발 화면 「서버 설정」에서 정한다.

## 4.6 문서 작업 에이전트

### 4.6.1 목적

대화의 요청(「작년 실적보고서 참고해서 추진 배경 절 써 줘」, 「이 표 채워 줘」, 「한글 파일로 내보내 줘」)을 처리한다. 요청 글을 낱말 규칙으로
해석하면 형식이 조금만 달라도 틀린 일을 하므로, 무엇을 할지는 모델이 판단하고 코드는 그 판단을 안전하게 실행한다. 목표는 로컬 27B가 맥락을
파악하고 문서함에서 재료를 찾아 양식대로 초안까지 쓰는 것이다.

### 4.6.2 사용 방법

문서 작업은 프로젝트에서 시작한다. 「프로젝트 추가」 창에서 업무와 자료(공고·지난 계획서)를 고르면 이름이 정해진다. [그림 4-16]
프로젝트 화면(/project/{번호})의 「대화·문서」 탭에서 공고·지침은 「기준으로 쓰기」로 기준 문서로 삼고, 「작성 원칙」에 「근거 조항 함께 적기」
같은 규칙을, 「관련 지난 사업」에 참조할 지난 사업 묶음을 잇는다. [그림 4-17] 프로젝트 채팅의 문서 패널에는 「작업 문서」, 「첨부 문서」,
「참고 문서」, 「기준 문서」가 있고 편집기는 「한글」/「구글」로 고른다. [그림 4-18]

「사업계획서 초안 써 줘」처럼 요청하면 에이전트가 양식을 고르거나 만들고 작업본을 연 뒤 절을 차례로 쓰며, 편집 화면에 AURA의 커서와
「AURA가 … 하는 중」이 보인다. 자료에 없는 값은 답 아래 「필요한 값 입력」 칸으로 묻는다. 자료에서 찾은 값은 「자료에서 찾음 · 확인 전」으로
미리 채워지고 담당자가 「확인」해야 담당자 값이 된다. [그림 4-19]이어서 「2번 절 더 구체적으로」, 「가로로 바꾸고 여백 좁게」처럼 고쳐 달라고
한다.

문서에 넣거나 바꾼 것은 답 아래 「반영한 것」에 실제 모양 그대로 작게 보인다. 채운 칸은 칸과 값의 표로, 쓴 절은 앞부분 글로, 만든 표는
머리줄과 앞 몇 행으로 보인다. 표 배치나 글꼴처럼 모양을 정할 일은 먼저 묻지 않는다. 양식 견본이나 지난 문서에 정해진 모양이 있으면 그대로
쓰고, 다 쓴 뒤 「다른 모양으로 바꾸기」 카드에 후보 두세 개를 견본과 함께 붙인다. 담당자가 하나를 누르면 그 모양으로 다시 꾸민다. 처음부터
담당자가 정해야 하는 것(표를 절 안에 넣을지 따로 둘지 같은 것)만 같은 카드로 먼저 묻는다.

공유 창에서는 사람이나 부서를 더하고 권한을 「읽기만」(기본값)이나 「함께 작업」으로 정한다. 공유는 고른 부서·사람만 받고 아래 팀으로
퍼지지 않는다. 다른 부서 사람은 대화의 질문과 답은 읽지만 근거 원문·첨부는 그 사람이 볼 수 있는 문서만 열리고 나머지는 「볼 수 없는
자료」로 가려진다(ADR-0075). [그림 4-20] 「진행 현황」 탭은 요청·참여자·작업 문서·사용량을 기간과 참여자별로 걸러 보인다.

### 4.6.3 업무 시나리오

기획처 담당자가 「2027 AI 교육 지원사업」 프로젝트에 공고와 지난해 비슷한 사업의 결과보고서를 올리고 「공고 기준으로 사업계획서 초안 써 줘」라고
한다. 에이전트는 문서함에서 한글 양식을 찾고(hwp_forms), 맞는 것이 없자 표지·사업 개요 요약표·「1. 추진 배경 → 가. 필요성」 형식의 절·절마다
【작성방법】 상자를 갖춘 양식을 설계하며(hwp_form_create), 코드가 이를 학교 서식 표 모양으로 빌드해 작업본을 연다. 빈 절 여럿을 서브에
맡기면(delegate_section), 서브는 공고의 평가 항목과 지난 결과보고서에서 근거를 찾아 [개요] → [본문]을 쓰고 근거 문장 끝에 「(출처: 문서
이름 N쪽)」을 단다. 공고에 없는 참여 인원 같은 숫자는 「○○명」으로 가려진다. 「추진 일정은 표로, 2번 절은 더 구체적으로」에는 고쳐 쓰기 도구가
지시를 점검표로 바꿔 다시 쓰고, 코드가 길이와 표 유무를 센다.

### 4.6.4 설계 선택과 이유

에이전트가 판단, 코드는 도구. 27B가 매 단계 상태를 보고 {생각, 도구, 인자}를 고르면(ReAct[48] 형식) 코드는 그 인자로 함수를 부른다. 요청 글을
코드가 다시 해석하지 않으며, 낱말 규칙 경로를 쓰는 것은 모델에 닿지 못했거나 형식 오류가 두 번 났을 때뿐이다.

양식 모양은 코드, 내용은 모델. 양식의 모양·구조·채우기 규칙은 코드가 지키고 27B는 내용만 쓴다. 공통 양식은 실제 서식 모양(2 단 머리행·병합
칸·서식 격자·합계 행)을 따른다(ADR-0058·0059). 어떤 양식으로 쓸지는 27B가 후보(프로젝트 작성 서식, 대화에서 정한 목차, 공통 양식) 안에서
고른다(ADR-0060).

필요할 때만 맡기기. 한 문맥에서 대화·검색·단계 기록·긴 본문을 다 다루자 절 41개 서식이 한 요청에 17절에서 멈췄다. 그래서 같은 27B를 다른
역할·깨끗한 문맥으로 한 번 더 부르는 서브 에이전트(절 맡기기)를 두었다. 기본은 메인이 직접 쓰고, 빈 절이 많거나 남은 문맥이 모자랄 때만
에이전트 판단으로 맡긴다(ADR-0065).

[표 4-13] 문서 작업 에이전트의 도구 묶음

절 작성. 절을 쓰기 전에 27B가 필요한 정보와 찾을 곳·검색어를 정하고 코드가 그대로 찾는다. 재료는 그 절의 작성방법,
문서 전체 규칙, 기준 문서, 프로젝트 문서, 보는 사람의 열람 범위 안의 사업 문서 RAG다. 사실은 그 요청에서 찾은 결과에 있는 것만 쓰며, 앞
대화에서 본 사실도 다시 찾아 쓴다.

받지 못한 값. 값은 사실(자료에 있을 수 있는 값)과 결정(담당자가 정할 목표·계획)으로 나눈다. 사실 값만 찾으며, 프로젝트 문서의 검색 결과에
글자 그대로 있을 때만 출처와 함께 확인 전 제안으로 남긴다. 세 번 찾아도 없으면 「자료에서 못 찾음」으로 둔다.

양식 설계는 문서함에 맞는 양식이 없을 때만 돈다. 깨끗한 문맥의 같은 모델이 제목·표지·요약 표 칸·절
단계와 제목·작성방법·분량·표 열 머리·도식 자리를 JSON으로 낸다. 재료는 작업 메모의 목표·확정 값, 공고의 작성·평가 항목, 목적이 비슷한 실물
양식 2~3개의 구조(값 제외)다. 코드는 빈 제목·절 0개·30개 초과·중복 절·단계 건너뛰기·긴 안내 같은 형식을 거르고, 번호를 학교 서식
형식(1. → 가. → 1))로 매겨 공통 양식과 같은 빌더로 작업본을 만든다.

표 디자인. 무엇을 표로 쓸지는 27B가 정하고, 표가 어떻게 보일지는 코드가 정한다. 코드는 머리줄 낱말, 열 값의 형식(날짜·기간, 금액, 수,
비율, 기호, 짧은 라벨, 긴 글), 행 수, 첫 열의 성격 같은 일반 특징으로 표를 여덟 종류(요약표, 일정표, 예산·금액표, 수치 현황표, 역할·담당표,
비교표, 목록형, 일반 표)로 나눈다. 종류마다 머리줄과 라벨 칸의 음영, 열 정렬(금액은 오른쪽, 긴 글은 왼쪽), 기호 열의 너비가 다르다. 값은
양식 견본 표가 있으면 그것을 따르고, 없으면 교내 실문서 188건의 표 4,091개에서 종류별로 뽑아 둔 값을, 그것도 없으면 기본값을 쓴다. 특정
문서나 사업 이름은 보지 않는다.

서브 맡기기와 고쳐 쓰기. 메인은 절 이름·요지·형식·분량만 정하고, 지시서의 필수 항목(작업 메모의 목표·확정 값,
문서 개요, 앞 절 요지, 담당자 원문 인용)은 코드가 채운다. 서브가 검색어 2~3개를 내면 코드가 찾아 번호·쪽을 붙인 근거를 문장 단위로
Rerank v1로 압축한다. 서브는 [개요] → [본문]을 쓰고 기준표(구체성·근거·작성방법·개요 반영)로 한 번 자기 점검한다. 여러 절은 모델 호출만
동시에 하고 찾기와 파일 쓰기는 차례로 한다. 고쳐 쓰기는 서브 호출 둘로, 첫째가 지시를 점검표 JSON(의도·길이·표·도식·더할 항목·뺄 항목·
문체·검색어)으로 바꾸고 둘째가 절 전체를 다시 쓴다. 코드는 셀 수 있는 것(바뀌었나, 길이 방향, 표·도식 유무, 더할 항목 낱말)만 보고, 어기면
까닭을 붙여 한 번 다시 청한다.

과제 10개·프로그램 21개가 생기고 필드 173개의 이름이 겹치지 않았다.

라벨 칸 채우기. 신청서·현황표의 값 칸은 누름틀이 없는 경우가 많다. 필드가 없는 이름이면 끝 낱말을 라벨 칸 글과
맞추고, 앞 낱말(「총괄책임자 성명」의 「총괄책임자」)로 같은 행의 왼쪽 칸·합친 칸을 살펴 행을 가린다. 값은 라벨 바로 오른쪽 칸이 비었거나
서식 예시 글자(OO대학교, http://www.)일 때만 넣고, 넣지 못한 이름은 까닭과 함께 모델에 돌려준다. 표 값 넣기도 값 자리가 분명한
라벨 칸은 덮지 않고 오른쪽 값 칸에 넣으며 단위를 살린다(「9」 → 「9개」).

지난 문서를 양식으로 쓸 때의 근거. 작년 결과보고서를 양식으로 쓰면 작업본은 그 값을 비운 사본이나 구조 사본이 된다. 작년 문서가 근거
찾기에 걸리면 지난해 값이 새 문서에 그대로 들어가므로, 작업본의 출처 기록을 읽어 그 원본과 다시 올려 원본에 이어진
문서를 근거 찾기에서 뺀다.

### 4.6.6 결과

여러 턴 시나리오 평가는 임시 DB와 실제 27B로 11 턴(시작 → 대상·예산 → 기간·양식 → 절 쓰기 → 계속 → 고쳐 쓰기 둘 → 디자인 넷)을
돌리며, 쓰기와 채점 모두 Writer 27B(당시 문맥 한도 16,384)다. ADR-0068 적용판은 절을 모두 쓰고 지어낸 숫자 없이 고쳐 쓰기 요청을 반영했다.
값은 5.4.4절 [표 5-6]에, 절 맡기기와 양식 만들기 결과는 5.4.2·5.4.3절에 있다. 쓰는 모델과 채점 모델이 같은 27B 라 채점은 판끼리 비교에만 쓴다.

### 4.7.1 목적

행정 서식은 대부분 한글이고, 제출본은 공고가 준 한글 서식 그대로여야 한다. AURA는 한글 문서를 읽기(반입), 열람·작업용 변환(독스),

교무처 담당자 셋이 공통 양식의 사본으로 학과 평가 보고서 요약표를 나눠 쓰고, 한 사람이 채팅에서 「현황 칸은 지난해 결과보고서 값으로 채워 줘」라고

지킨 채 새 판을 받는다. 완성본은 「⋯」 → 「내려받기」 → 「한글(hwpx)」로 받는다.

### 4.7.5 설계 선택과 이유

읽기는 대조 수치로 고른다. 옛 hwp 읽기는 kordoc[25]이 1 순위다(ADR-0033). 실물 비교에서 30MB 옛 hwp 읽기가 pyhwp[26] 경로의 3분에서 1초로
줄었고, 글자 양은 같았으며 표의 중첩·병합이 보존됐다. kordoc은 판을 고정하고, 판을 올릴 때는 대조 스크립트를 다시 돌려 통과해야
한다. 포크를 보관하고, 내장 OCR은 쓰지 않으며 자원 내려받기를 막는다. hwpx는 독스 변환과 같은 XML을 쓰고 이미 빨라 자체 OWPML[24] 파서를
유지한다.

완성본은 원본 서식에 채운다. 행정 서식은 표 테두리·칸 폭·글꼴이 정해져 있어 변환기로 새로 만든 한글 파일은 제출용으로 쓸 수 없다. 한글
프로그램을 원격 조작하는 윈도우 COM 에이전트 방식은 담당자 PC에 설치가 필요하고 불안정해 쓰지 않는다(ADR-0034). kordoc의 patch는 새 문단·표
블록을 더하지 못하고 generate는 서식을 새로 만드는 것이라, 「원본 서식을 보존하며 내용을 채우는」 원리만 가져와 채우기를 직접 만들었다(ADR-0035).

공동 편집은 칸 단위 임대. 한컴 웹 기안기(WebHwpCtrl 13.82)[51]의 공개 API에는 문서 변경 사건이 없고 문서 내부 모델에 닿을 수 없어, 글자 단위
병합 기법(OT[52]·CRDT[53])을 쓸 수 없다. 쓸 수 있는 것은 필드 API(칸 목록·칸 글 읽기·쓰기·커서 칸·칸으로 옮기기), 커서·선택 저장과 되돌리기,
칸을 서식째 꺼내고 넣는 블록 입출력이다. 이 조건에서 네 안을 비교했다(ADR-0070, [표 4-16]).

| 안 | 장점 | 단점 |
|---|---|---|
| 문서 전체 잠금만 | 단순 | 한 사람만 쓴다 |
| 기안기 내부 모델에 OT·CRDT | 글자 단위 병합 | 공개 API 밖이라 제품 판이 바뀌면 깨진다 |
| 별도 실시간 협업 페이지(Socket.IO[66]·React[67]) | 성숙한 도구 | 새 의존성과 빌드 단계, 앱은 빌드 없는 정적 JS |
| 칸 단위 비관적 임대 + 바뀐 부분 전송 + 서버 정답(채택) | 공개 API 만으로 된다, 같은 칸을 둘이 쓰지 않아 병합 불필요 | 주소로 쓸 칸을 문서에 심어야 한다, 표·그림·용지 고침은 한 사람씩 문서 전체로 |

[표 4-16] 공동 편집 방식의 비교(ADR-0070)

칸(누름틀)을 주소로 쓰는 까닭은 위치 번호(문단·글자)가 여럿이 치면 밀리기 때문이다. 이름으로 읽고 쓰고 옮겨 갈 수 있는 자리는 누름틀뿐이다.
기안기는 속을 고칠 수 없는 부품이라 주소를 문서에 심는다. 칸 밖 고침은 문서 전체 저장과 다른 화면의 다시 불러오기를 부르므로, 문서를 열 때
칸 밖 문단까지 칸으로 감싸 칸 밖 고침을 거의 없앴다.

### 4.7.6 구현

독스 변환. 구글 드라이브는 한글을 가져오기 형식으로 받지 않으므로 한글만 docx로 풀고 마지막 변환은 구글에 맡긴다. hwpx는 글자·문단·표·
글상자·그림·쪽 설정을 docx로 옮기고, 옛 hwp는 pyhwp의 구조 XML을 같은 변환기에 넣는다. 실측
사업계획서 95쪽에서 표 124(중첩 41)·그림 27·글상자 19가 모두 옮겨졌다. 문서함의 한글 문서 전부를 변환해 글자·표·그림 수와 워드 구조
오류를 대조하는 묶음 검사로 품질을 잰다.

서식 보존 채우기. hwpx는 XML을 담은 ZIP이며, 채우는 순서는 [그림 4-26]과 같다.

원본 hwpx의 구역 XML은 다시 직렬화하지 않는다. 작업본 절 본문(글·표·그림, 안내 상자 제외)마다 원본에서 번호·제목 글자로 절 제목 문단(또는 그 뒤 【작성방법】 상자)을 찾는다. 서식에 이미 있는 문단·표는 다시 넣지 않고 그 자리를 지나 이어 쓰며, 서식 표를 채웠으면 작업본 열 너비로 값 칸의 x 위치를 재어 원래 칸에 써 넣는다. 새 표의 id는 문서 최댓값 다음부터 매기고, 테두리는 그 구역 본문 표에서 가장 흔한 실선을 이어받는다. 문단·표·그림 XML은 글자열 위치에 끼워 넣어 손대지 않은 문단은 한 글자도 바뀌지 않는다. 바뀐 구역만 줄 배치 캐시를 지우고, ZIP 항목 순서와 압축 방식을 지킨 채 바뀐 항목만 다시 쓴다. 저장은 자가 점검을 통과할 때만 한다.

[그림 4-26] 원본 서식 보존 채우기 (그림 docs/images/diagrams/c4-26-hwpx-fill.png)

원본이 옛 .hwp면 hwpx로 저장한 서식을 반입하도록 안내한다. 이 층은 내용을 만들지 않고, 에이전트와 담당자가 작업본에 쓴 내용을 서식에 옮길
뿐이다.

자가 점검은 채운 파일을 다시 열어 문제 목록을 내고, 목록이 비어야 저장한다. 편집 도구도
고친 결과를 같은 함수로 본다.

```

            or z.read("mimetype").strip() != b"application/hwp+zip":
        probs.append("mimetype 이 무압축 첫 항목(application/hwp+zip)이 아니다")
    …
```

이 밖에 모든 XML이 웰폼드인지, header의 구역 수·목록 항목 수가 실제와 같은지, 본문이 가리키는 모양 id와 그림 참조가 header·manifest에
있는지를 본다. 모양을 새로 등록하거나 행을 늘리는 고침이 파일을 깨뜨리지 않게 막는 장치다.

한글 문서함과 양식 정리. 문서함은 부서 디렉터리 형식이다. 부서마다 저장 전 판(.판)과 휴지통(.휴지통)을 두고, 사람마다 「내 폴더」가 처음 열 때
생긴다. 지난 문서에서 모은 양식은 판정 모듈 하나가 공통 양식·지난 사업 문서·휴지통(개인 서류·채워진 제출본·깨짐·중복 등)으로
가른다. 규칙은 특정 파일·사업을 적지 않고 장부의 사업 이름, 제목 낱말, 본문에서 기계로 잰 값(빈 칸 비율·개인 정보 형식·양식 예시
글자 수)만 본다.

기안기 편집 도구. 에이전트의 편집 도구는 서버에서 hwpx 파일을 직접 고친다. 기안기가 열려 있지 않아도 되고, 고치기 전 판을 남기며, 자가 점검을
통과할 때만 저장한다. 표 서식의 기본값은 학교 서식 문서 1,459건의 표 20,441개에서 캔 값이다(머리줄 회색 음영·굵게, 바깥 0.4mm·안쪽 0.12mm 실선,
10pt). 열린 기안기에서 해야 하는 동작은 기안기 기본 기능을 동작 이름 그대로 부른다(hwp_action). 웹에 등록된 동작 467개를 확인해 쓸모 있는
73개를 허용 목록에 두었고, 기안기에 있는 기능은 따로 창을 만들지 않는다.

칸 단위 공동 편집(ADR-0070)은 세 겹이다. 어댑터만 기안기 API를 부르고, 공동 편집 층이
임대·보낼 줄·받을 줄·판 번호·지문 대조·충돌 사본과 화면 표시를 맡으며, 서버의 표 일곱(칸 임대·칸 글·받은 변경·고친 기록·
충돌 사본·알림 줄·같이 보는 사람)이 정답이다. 밀어 주기는 SSE[54], 변경은 fetch[69] POST다. 세 겹의 관계는 [그림 2-26]의 구성도와 같고,
[그림 4-27]은 글자 하나와 AURA의 절 하나가 다른 화면에 닿기까지다.

[그림 4-27] 칸 단위 공동 편집의 흐름: 사람이 칸에 칠 때와 AURA가 절을 쓸 때, 처리 흐름 화면과 같은 그림 (그림 docs/images/diagrams/c4-27-coedit-field.png · docs/images/diagrams/c4-27b-coedit-aura.png)

글은 바뀐 부분만 간다. 칸을 처음 고치면 임대를 잡고, 300ms 마다 「어느 칸의 몇 번째 글자부터 무엇을 지우고 무엇을 넣었는지」를 기준 판·지문과 함께
보낸다. 보낼 줄은 IndexedDB[68]에도 두어 연결이 끊겨도 잃지 않는다. 서버는 칸 판 번호를 올려 알림 줄에 넣고, 받는 화면은 입력이 300ms 멈추고
한글 조합 중이 아닐 때 그 칸에 글을 넣은 뒤 원래 커서·스크롤로 되돌린다. 30초마다 칸 글 지문을 서버와 대조해 놓친 알림을 메운다. 한글 파일에는
입력이 3초 멈추면 바뀐 글자만 제자리에서 고쳐 써 글자 묶음마다 든 서식을 지킨다. 운영 세 창에서 한 칸에 넣은 글은
다른 두 창에 0.14~0.26초 뒤 보였다.

서식은 따로 간다. 서식을 바꿀 수 있는 손놀림(툴바·메뉴·단축키) 뒤 0.7초 동안 입력이 없으면, 공동 편집 층이 지금 칸을 기안기 JSON 블록(글과
서식 전부)으로 꺼내 지난번과 견주고 다르면 보낸다. 받는 화면은 그 칸을 서식째 바꿔 넣고 커서·스크롤·선택 영역을 되살린다. JSON 블록은 남의
화면에 그대로 들어가므로 서버 관문이 해석해 허용된 열쇠와 개체만 든 블록을 다시 직렬화해 보내고, 표·그림·링크·누름틀이
든 블록은 글만 받는다.

문서 전체를 칸으로. 고칠 수 있는 사람이 문서를 열면 서버가 칸 밖의 글 문단(표 칸 안 포함)을 안내 글 없는 칸 「문단:n」으로 한 번 감싸 새 판으로
저장한다. 개체가 든 문단, 머리말·꼬리말·각주·글상자 안, 이미 칸 안인 문단은 건너뛰고, 1,500 문단이 넘는 문서는 감싸지
않으며, 에이전트의 칸 목록에서는 「문단:」 칸을 뺀다.

편집기는 일반 편집 모드로 연다. 양식 모드에서는 선택이 칸 경계를 넘지 못하고 복사가 글만 되기 때문이다. 양식 모드가 막던 것은 공동 편집 층이
막는다. 남이 쓰는 칸에 치는 키와 칸 표시를 지우는 칸 처음의 Backspace·칸 끝의 Delete를 막고, 고른 범위에 남의 칸이 들면 서식 단추를 막는다.
칸을 넘는 고침·칸째 붙여넣기는 알아채 구조 잠금을 잡고 문서 전체를 저장하며, 서버는 그 저장에서 새로 생긴 칸 밖 문단을 감싸고 남이 쓴 칸만
DB 글로 지킨다. 한글 조합 중에 기안기에 무엇이든 물으면 조합이 끊겨 자모가 따로 박히므로(「ㄱ기김」), 조합 중에는 칸 글 읽기·칸 속성 바꾸기·
칸 자리 재기를 하지 않는다. 이름표 자리는 기안기 내부의 커서 모델(쪽 번호와 쪽 안 좌표)로 재는데, 공개 API 밖이라 제품 판이 바뀌어 없어지면
칸 표시만 빠지고 편집은 그대로 돈다.

AURA도 참여자다. 27B의 절 초안은 검사를 지난 뒤 사람과 같은 칸 길(임대 확인·판 번호·알림)로 간다. 글만 든 절은 그 칸을 맡아 0.12초마다
몇 글자씩(초당 약 32자, 긴 절도 20초 안에 끝나게 보폭을 늘림) 흘려 보내고 다 쓰면 그 칸만 파일에 써 넣고 놓는다. 3초 넘게 손대지 않은 화면은
그 칸으로 따라간다. 표·도식이 든 절만 파일에 쓰고 새 판을 알리며, 사람이 쥔 칸은 쓰지 않는다. 화면이 보내는 창 번호는 로그인한 사람과 묶어
남의 변경을 막지 못하게 하고, 요청 본문 4MB, 문서마다 새 칸 줄 2,000개 같은 상한을 두었다. 시간 값(기본 임대 300초, 기다리는 사람이 있을 때
120초, 보내기 간격 300ms 등)은 모두 설정이다.

충돌 처리는 서버가 문서별 잠금 안에서 변경 하나씩 판정한다.

다르고 마지막으로 쓴 창도 다르면 반영하지 않고 충돌 사본 표에 넣는다. 바뀐 부분만 보낸 변경은 기준 판이 지금 판과 같고, 자리가 글 안이며, 넣은

공동 편집 시연(ADR-0071). 운영은 주소가 하나라 한 브라우저에서 세 사람의 세션을 동시에 가질 수 없다. 그래서 관리자 화면 「공동 편집 시연」
(/dev/coedit-demo)에 같은 문서를 세 칸으로 열고, 칸 표시를 단 편집 요청만 로그인할 수 없는 시연 계정으로 판정한다. 표시는 권한을 좁히기만 한다.
열면 제목만 있는 빈 문서가 세 칸에 뜨고, 「AURA 양식 만들기」를 누르면 27B가 시연 시나리오의 가상 사업에 맞는 짧은 사업계획서 양식과 요약 칸
값을 정해 이 문서에 넣는다. 「AURA 이어 쓰기」는 빈 본문 절을 1절부터 셋 쓰며, 숫자는 시나리오에 준 값만 쓴다(본문 관문). 그동안 세 사람은
절이든 제목이든 동시에 고친다. [그림 4-28]

쪽 넘김. 웹 기안기는 「글자처럼 취급」한 표를 쪽에서 나누지 못하고, 「셀 단위로 나눔」·「나누지 않음」 표는 한 칸이 쪽보다 길면 넘친 글이 잘린다.
그래서 필드가 든 표와 500자를 넘는 칸이 있는 표는 쪽 나눔을 「나눔」으로, 행이 10개를 넘거나 쪽 본문 절반보다 높은 겉 표는 「셀 단위로 나눔」으로
바꾸고, 글자처럼 취급한 표는 본문과 함께 흐르는 표로 바꾼다. 작은 표·글 사이 표·안쪽 표는 그대로 둔다. 이 정리는
문서를 열 때와 에이전트의 모든 고치기 뒤에 돈다. AURA가 새로 넣는 표도 본문과 함께 흐르게 넣고, 행 높이는 칸 글이 접히는 줄 수로 어림한다. 본문 폭으로 넣는 세로 긴 그림은 높이를 구역 본문 높이의 85 %로 눌러 제목만 남은 빈 쪽을 막는다.

화면 깜빡임. 남의 글을 넣은 뒤 0.4초 동안 보던 자리를 지키되, 그사이 내가 치거나 누르거나 굴리면 잡아 둔 자리를 버린다. 그러지 않으면 기안기가 내린 화면을 옛 자리로 되돌려 위아래로 오간다. 실제 기안기를 헤드리스 창 둘·셋으로 열어 잰 값은 5.5절에 있다.

## 4.8 구글 드라이브·독스 연동

### 4.8.1 목적

담당자 문서의 일부는 구글 드라이브에 있고, 여러 사람이 함께 쓰는 데는 구글 독스가 익숙하다. AURA는 드라이브를 문서 원천으로 붙이고, 대화에
이은 독스 작업본을 에이전트가 직접 고치게 한다. 주 편집기는 웹 한글 기안기이고 독스는 보조 경로다. 교내 내용이 구글로 나가는 일이므로 학교
계정 안에서만 하고, 가리고, 기록한다.

### 4.8.2 사용 방법

사용자는 「설정」(/settings)의 「구글 계정」 칸에서 학교 계정을 잇는다. [그림 4-29] 문서 패널의 「드라이브에서 문서 가져오기」로 가져온 문서는
업로드와 같은 처리 경로를 타고, 「이 문서로 작업」을 누르면 사본을 만들어 대화에 이으며 이후 대화의 명령은 그 문서의 편집이 된다.
「한글 파일로 내보내 줘」라고 쓰면 작업본의 절 본문이 원본 hwpx 서식에 채워져(4.7) 프로젝트 드라이브의 작성 폴더에 올라가고, 「제출본」이라고
하면 【작성방법】 상자를 뺀다. 부서 드라이브는 조직 관리(/team) 「부서 설정」 탭에서 그 부서 총괄 책임자가 부서 공용 학교 계정으로 잇고,
관리자는 「학교 계정 연결 현황」에서 구글 앱 등록, 허용 도메인(ync.ac.kr), 사람별 연결 상태를 다룬다. [그림 4-30]

### 4.8.3 업무 시나리오

산학협력단 담당자가 자기 드라이브의 계획서 초안을 프로젝트에 가져와 「이 문서로 작업」을 누르고, 「3장 추진 체계 아래에
협력 기관 역할 표 넣어 줘」라고 한다. 에이전트가 편집 계획(넣기·표)을 JSON으로 내면 플랫폼이 독스 API로 적용해 화면에 표가 나타난다. 제출
전날 「한글 파일로 내보내 줘, 제출본으로」라고 하면 원본 서식의 한글 완성본을 받는다.

### 4.8.4 설계와 구현

읽기와 쓰기를 나눴다. 드라이브는 읽기 전용 원천으로 붙인다(ADR-0028). 인증은 담당자 본인의 OAuth[57] 허용이고, 클라이언트 비밀과 갱신 토큰은
서버 파일에만 둔다. 구글 클라이언트 라이브러리 대신 드라이브[56]·독스[55] REST API를 직접 불러 의존성을 늘리지 않았다. 쓰기는 외부 전송이므로
규칙을 먼저 정했다(ADR-0029). 대화에 이은 문서의 명령은 에이전트가 편집 계획(넣기·바꾸기·표·칸 채우기·도식 등)을 JSON 스키마로 강제해[50]
내고 플랫폼이 documents.batchUpdate로 적용한다. 보내는 글은 개인정보 검사기를 한 번 더 거치고, 검색 근거 조각의 원문은 넣지 않고 에이전트가
쓴 글만 넣으며, 모든 쓰기는 시각·계정·문서·절·글자 수로 감사 기록에 남는다.

공통 양식. 작성 서식이 없는 사업이나 새 문서는 독스 공통 양식 5 종(사업계획서·실적보고서·단위 프로그램 실시계획서·결과보고서·회의록)으로
쓴다(ADR-0058). 한글 서식을 독스로 옮기면 쪽이 밀리고 표가 깨지므로 독스 API로 직접 짠 사양을 쓰고, 절·표·분량·근거 위치는 실문서 집계에서
골랐다.

계정 체계. 구글 앱은 관리자가 한 번 등록하고, 사용자마다 자기 학교 계정을 잇는다. 부서 계정 토큰은 그 부서 폴더 안 문서를 다룰 때만 쓰고,
드라이브 찾기·가져오기는 본인 계정만 받는다. 연결을 거절해도 한 번 쓴 인증 상태 값은 다시 쓰지 못하게 하고, 실패한 토큰은 지운다.

### 4.8.5 결과

운영 실측에서 독스 편집 명령 한 건이 65 초(27B 계획 생성 포함)에 세 항목 254자를 지정한 절 아래에 넣었다(ADR-0029). 공통 양식과 절 작성
에이전트의 시험 7 회(실물 세트, 임시 DB)에서는 한글 완성본의 서식 표가 제자리에 채워졌고(새 표 2 → 0), 문서함 RAG 재료로 쓴 「추진 배경」 절은
355~560자에서 1,567 자(실문서 중앙값 1,800자)가 됐다(ADR-0058).

## 4.9 업무 도우미

### 4.9.1 목적

플랫폼 사용법을 안내하고 화면에서 하는 일을 대신한다. 채팅 화면의 에이전트 대화와 따로 돌며, 사업 문서 내용 질문은 에이전트 대화로 넘긴다.

### 4.9.2 사용 방법

채팅·프로젝트 첫 화면을 뺀 화면의 오른쪽 아래 「업무 도우미」 단추로 연다(학생에게는 없음). [그림 4-31] 「학생에게 장학 규정을 보이게
하려면?」처럼 물으면 답에 제안이 붙고, 「실행」을 누르거나 「화면에서 직접」으로 화면 위 커서가 그 단추를 가리키게 한다. 「문서함에서 ○○
폴더 열어 줘」, 「성명 홍길동으로 넣어 줘」처럼 시키면 AURA 커서가 화면 이동 → 창 열기 → 칸 채우기를 차례로 한다. 저장·만들기·올리기 같은
마지막 단추는 「저장해 줘」처럼 직접 시켰을 때만 누르고, 아니면 가리키기만 한다. 화면의 글을 골라 「쉽게 설명」, 「관련 규정 찾기」 등을
고르면 답변 경로로 간다. 도우미가 제안하는 일은 [표 4-19]와 같다.

[그림 4-31] 업무 도우미 창: 제안과 「실행」·「화면에서 직접」, 화면 위 커서 (그림 docs/images/figures-1027/f4-31-helper-proposal.jpg + f4-31b-helper-screen-cursor.jpg)

| 제안하는 일 | 같은 화면 | 계정 |
|---|---|---|
| 기준 문서 학생 공개·교직원만 | 라이브러리 › 「기준」 칩 작업 줄 「학생 공개」 | 관리자 |
| 반입 자료의 규정 후보를 기준 문서로 | 라이브러리 › 「기준」 칩 「새 판·미등록」 「검색에 추가」 | 관리자 |
| 부서와 부서 RAG 만들기 | 조직 관리 › 트리 위 「부서」(아래 부서는 「부서 설정」 › 「하위 부서 추가」) | 관리자 |
| 프로젝트 만들고 첫 요청 보내기 | 사이드바 「프로젝트 추가」 | 관리자·교직원 |
| 에이전트 대화로 넘기기 | 채팅 | 관리자·교직원 |

[표 4-19] 업무 도우미가 제안하는 일

「실행」을 누르면 서버가 대화 주인·계정 역할·대상이 아직 맞는지 다시 보고 실행하며, 두 번 눌러도 한 번만 돈다.

### 4.9.3 업무 시나리오

새로 온 관리자가 라이브러리 「기준」 목록에서 「학칙을 학생이 볼 수 있게 하고 싶어」라고 쓰면, 도우미는 지금 화면과 화면 안내 자료를 보고
「학칙」의 학생 공개를 제안한다. 「화면에서 직접」은 커서로 그 문서 줄과 「학생 공개」 단추를 차례로 가리키고, 「실행」은 화면 단추와 같은 함수로
실행해 결과를 대화와 실행 기록에 남긴다.

### 4.9.4 설계와 구현

도우미는 문서 작업 에이전트와 같은 단계 구조(단계 8 번까지)이고 도구만 다르다. 도구는 화면 안내 찾기(platform_help), 내 대상
목록 보기(platform_lookup), 동작 제안(propose_action), 화면 열기(open_page), 마무리(finish)다. 요청이 사용법·할 일·문서 내용 가운데 무엇인지는 모델이
도구를 고르며 정하고 낱말 규칙은 두지 않는다. 화면이 지금 보이는 칸·단추에 번호를 붙여 보내면 모델은 그 번호나 이름으로 대상을 고르고, 못 찾으면
고를 수 있는 요소를 다시 받는다. 마지막 단추를 누를 수 있는지는 담당자가 직접 친 글에 시키는 말이 있는지로 서버가 판단하며,
문서·검색 결과 글로는 허락하지 않는다. 동작 실행은 언제나 「실행」 뒤 서버에서 한다. 화면 안내 자료는
화면마다 한 항목이고, 적힌 단추 이름이 템플릿에 실제로 있는지 자동 테스트가 확인한다.

### 4.10.3 업무 시나리오

관리자는 아침에 「개발 현황」의 「진행 현황」에서 남은 일을, 처리 흐름의 「반입 점검」에서 「빠진 원본」이 0 건인지와 「실패」 목록을 확인한다.
새 부서가 생기면 「조직 관리」 트리에서 「하위 부서 추가」로 부서와 부서 RAG를 만들고, 담당자 계정을 「부서 옮기기」로 옮기거나 엑셀·CSV 파일로
「일괄 등록」한다. 끝으로 「테스트 보기」로 그 담당자의 등급과 부서를 골라 라이브러리에 부서 문서와 공통 문서만 보이는지 확인한다.

### 4.10.4 설계와 구현

화면 이름은 한 표에서 나와 사이드바 묶음·머리·탭 제목이 같은 이름을 쓴다. 개발자 화면은 개발자 역할일 때만 보인다. 화면·역할
단위 권한이 없으면 「볼 수 없는 화면입니다」와 까닭 한 줄을 보이고, 개별 문서·프로젝트·대화는 404로 있는지 자체를 숨긴다. 「수집 자료」의
묶음은 늘 가린 사본이다. 글은 개인정보 탐지와 고위험 형식으로 가리고, 가림에 실패한 글은 통째로 「[가림 실패]」로 바꾸며, 사람 칸은 서버 비밀값으로
만든 가명으로 바꾼다. 학습·평가는 대화 단위로 나누고 평가 세트와 같은 질문은 뺀다. 묶음은 JSONL 하나와 스키마 판·필드 뜻·처리
규칙을 적은 manifest.json으로 이루어진다. 「테스트 보기」는 열람 판정 시험과 같은 판정 함수를 쓴다.

## 4.11 모델 학습(SFT) 파이프라인

### 4.11.1 목적

실제 도입 때 더 큰 모델에 적용할 학습 절차와 데이터를 Writer 27B로 미리 검증한다. 학습 데이터 만들기·검사·학습·서빙 반영·비교가 끝까지
도는지, 학습 효과가 서빙 모델에 들어가는지, 어떤 데이터가 플랫폼 동작을 좌우하는지를 27B에서 확인했다. 파인튜닝은 사실과 수치를 외우게
하지 않는다. 사업 자료는 해마다 바뀌고, 내부 원문을 학습에 넣으면 개인정보가 모델에 남기 때문이다. 그래서 학습 대상은 「질문을 보고 무엇을
어디서 찾아 어떤 근거로 답을 구성할지」라는 문맥 구성 추론이다(ADR-0047). SFT 데이터는 규정·발전계획 묶음과 사업 구조·검색 활용 묶음
두 갈래이고, 실적·예산 사실 문답은 넣지 않는다(ADR-0052).

### 4.11.2 사용 방법

학습셋은 학습 장비에서 만들고 승인하며, 운영 서버의 개발자 화면에서는 상태와 결과를 본다. 「데이터·학습」(/dev/train)의 「문답 검수」 표에서
Label Studio[18] 검수 화면을 열고, 끝나면 「완료한 검수 결과 반영」을 누른다. 검수를 맡은 교직원은 「SFT 문답 검수」 추가 권한이 있으면
사용자 메뉴의 「문답 검수」(/review)에서 자기 몫과 검수 매뉴얼을 본다. 「승인 데이터·산출물」에서는 학습셋별 파일과 「학습셋 표본」을 보고
[그림 4-35], 「학습 상태 보기」(/dev/train/run)에서 학습 점검과 손실 곡선(TensorBoard[62])을 본다. [그림 4-36] 학습 전후 비교는 「품질·성능」의
「모델 비교」 카드와 「자세히」(/dev/models/compare)에서 항목별 점수·지표·표본 답을 두 모델 나란히 본다. [그림 4-37]

학습셋 원문은 학습 장비 밖으로 나가지 않는다. 운영 서버의 목록에는 이름·상태·건수·지문·승인 범위만 1 분마다 들어온다.

### 4.11.3 파이프라인

[그림 4-38]은 학습 데이터에서 운영 모델 교체까지의 흐름이다.

학습 후보는 실문서 절 작성쌍(양식 × 완성본, 서빙 프롬프트 형식 입력 → 편집 계획 JSON 출력), 문서 구조 단계 문답([N단계] 사업명 → 개요 → 목차 → 요구 항목 → 뼈대), 근거 기반 연결 대화(사업·연차·문서·절 경로와 근거 위치, 2~6턴), 운영 기록(에이전트 단계·질문 읽기·양식 고르기·못 채운 까닭)의 가린 사본이다. 자동 검사는 경로·근거 기록, 근거가 그 턴에 글자 그대로 있는지, 숫자가 근거에 있는지(수치 검증기와 같은 함수), 순서, 중복을 본다. 사람 검수(Label Studio)는 근거·구조·맥락·개인정보 네 항목을 확인해 채택·수정만 승인본으로 둔다. 개인정보는 내부 설정과 상관없이 전체를 탐지해 다시 가려도 바뀌지 않는 파일만 반출하고(fail-closed), 사업 단위 학습·검증·시험 분리와 중복을 전체에서 다시 본다. 학습은 학습 장비에서 TRL[17]·PEFT[16]로 bf16 LoRA[15] SFT(문맥 16,384)를 하며, 베이스라인이 없으면 시작하지 않는다. 학습본은 병합 → NVFP4 재양자화 → 서빙 장비에 후보 이름으로 올린 뒤, 학습이 서빙에 들어갔는지(정답 로그확률)를 먼저 보고 같은 시험으로 학습 전 모델과 비교한다(ADR-0069). 운영 모델 교체는 시험 문항·맥락 이해·문서 작성 시나리오·평범한 질문의 답 형식을 모두 통과할 때 한다.

[그림 4-38] SFT 파이프라인 (그림 docs/images/diagrams/c4-38-sft-pipeline.png)

27B 검증 실험의 학습셋 writer-v1은 자동 의미 점검을 거쳐 10-18 승인했다(실험 로그). 학습 4,434 · 검증 346 · 시험 220건이며, 이 판은 사람 검수를
거치지 않았다(ADR-0069). 학습 장비에서 LoRA(r32, BF16 바탕, 2에폭)로 학습했고, 손실은 1.43에서 0.92로 내려갔다.

### 4.11.4 비교 방법(ADR-0069)

바꾸는 것은 모델 하나뿐이고 질문·생성 설정·채점 모델은 그대로 둔다. 비교 대상은 어댑터를 합친 뒤 운영과 같은 NVFP4[12]로 다시 줄인 학습본이다.
비교 방법은 [표 4-21]과 같고, 이와 함께 문서 작성 시나리오와 평범한 업무 질문의 답 형식을 학습 전후로 잰다.

| 묶음 | 방법 |
|---|---|
| 학습 반영 확인 | 생성 전에 정답의 토큰당 평균 로그확률(40문항). 샘플링 잡음이 없어 몇 분이면 갈린다 |
| 시험 문항 220 | 학습셋에서 떼어 둔 test(규정·제도 156, 사업 자료 활용 64). 학습 형식 그대로 생성(온도 0.2, 최대 2,048토큰, 생각 끔). 코드가 chrF[63]·ROUGE-L[64]·질문에 없는 숫자·잘림·길이·표를 세고, 채점 모델(토르 03)이 답 하나씩 여섯 항목을 1~5 점으로 매긴다[65]. 정답은 채점 모델에 보이지 않는다 |
| 맥락 이해 30문항 | 여러 번 주고받은 값 이어 쓰기, 약 1.16만 토큰 공개 자료 속 사실 찾기, 자료에 없는 칸을 「확인 필요」로 두기(가상 값, 코드 채점) |

[표 4-21] SFT 전후 비교 방법

### 4.11.5 결과(10-24)

27B 실험에서 확인한 것은 세 가지다.

첫째, 학습이 서빙 모델에 들어가 정답 로그확률·정답 겹침이 오르고 질문에 없는 숫자가 든 답이 없어졌다(수치는 5.4.5절 [표 5-7]).

둘째, 학습 데이터의 요청 형식이 플랫폼 동작을 좌우한다. 이번 학습쌍은 「한 줄 시스템 지시 + 질문 → 근거 설명·답변」 한 형식뿐이었고, 학습본은
플랫폼이 보내는 에이전트 단계 JSON과 작업 메모 갱신 요청에도 그 틀로 답했다. 그 결과 문서 작성 시나리오에서 작업본을 만들지 못했다(학습 전
2/2, 학습 뒤 0/2).

셋째, LoRA 어댑터를 서빙에 바로 얹으면 어댑터 층 이름이 서빙 모델과 맞지 않아 효과가 없었고, 병합 뒤 재양자화한 학습본에서 효과가 보였다.
그래서 생성 비교 전에 정답 로그확률로 학습 반영을 먼저 확인하는 단계를 두었다.

더 큰 모델에서는 이 결과를 보완해 같은 절차를 적용한다. 플랫폼 요청 형식(에이전트 단계 JSON, 작업 메모 갱신, 절 쓰기와 고쳐 쓰기, 평범한 채팅)을
학습쌍에 넣고, 사람 검수를 거친 승인본으로 학습하며, 학습 전후로 문서 작성 시나리오 완주와 평범한 질문의
답 형식을 함께 잰다. 운영 Writer는 그때까지 Qwen3.8-27B 바탕 모델로 둔다(6.3.2절).
