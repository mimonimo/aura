# 3. 환경 구축 및 시스템 설계

이 장은 AURA 가 어떤 장비 위에서 어떤 구조로 돌아가는지를 설명한다. 3.1 절은 장비와 소프트웨어 환경, 3.2 절은 전체
아키텍처, 3.3 절은 문서가 답과 초안이 되기까지의 데이터 흐름, 3.4 절은 저장 구조, 3.5 절은 권한·등급·부서 체계, 3.6 절은
모델 배치와 교체 구조를 다룬다. 기능별 구현의 세부는 4 장에서 다루고, 이 장은 그 바탕이 되는 설계 판단과 근거를 적는다.
설계 판단의 근거는 결정 기록(ADR)으로 남겼으며 본문에서는 (ADR-00NN) 꼴로 인용한다.

## 3.1 개발·운영 환경

### 3.1.1 설계 제약

AURA 의 환경은 세 가지 제약에서 출발한다. 첫째, 대학 행정 문서에는 개인정보와 기관 내부 정보가 들어 있어 상용 클라우드
AI 로 보낼 수 없다. 모든 모델은 교내 장비에서 돌아야 한다. 둘째, 쓸 수 있는 장비가 정해져 있다. GPU 가 없는 가상 서버 한
대, 젯슨 AGX 토르[11] 두 대, 학습용 DGX 한 대가 전부다. 셋째, 학교 원본 문서는 계속 들어오고 바뀐다. 한 번 적재하고 끝나는
시스템이 아니라 원본을 따라가며 처리본을 갱신하는 시스템이어야 한다.

이 제약에서 두 가지 원칙이 나온다. 하나는 장비마다 맡는 일을 나누어 서로 메모리와 처리량을 다투지 않게 하는 것이고,
다른 하나는 원본과 처리본을 분리해 운영 서버가 원본 저장소를 읽기만 하게 하는 것이다(ADR-0047·0049).

### 3.1.2 장비 구성과 역할

[표 3-1] 은 장비별 역할이다. 장비의 접속 정보와 주소는 운영 문서에만 두고 이 논문에는 싣지 않는다.

| 장비 | 사양(기록 기준) | 맡는 일 |
|---|---|---|
| 운영 서버 | 가상 서버, GPU 없음, 메모리 64GB | 웹 화면과 API, PostgreSQL(pgvector), 어휘·의미 검색, 지식 그래프, 문서 반입 처리(파싱·조각·색인), 웹 한글 기안기 서버, 주기 작업 |
| 서빙 장비 1(토르 02) | 젯슨 AGX 토르 | 생성 모델 Writer 27B(NVFP4). 대화 답, 문서 작업 에이전트, 업무 도우미처럼 사람이 기다리는 일 |
| 서빙 장비 2(토르 03) | 젯슨 AGX 토르 | 생성 모델 Writer 27B(NVFP4). 반입 검토, 이미지 판독, 서류 종류·사업 판정 같은 배치 일. 임베딩·리랭커 서비스 |
| 학습 장비(DGX) | GB10, 통합 메모리 121GB | 학교 원본 보관, 대량 처리(스캔 판독, 일괄 판정), 학습 데이터 생성·승인, 파인튜닝 |

[표 3-1] 장비 구성과 역할

생성 모델을 두 서빙 장비에 같은 판으로 올리고 일의 성격으로 나눈 것은 실측 때문이다. 처음에는 원본 정밀도(bf16)의 27B
모델을 토르 02 한 대에 올려 문서 작업, 반입 검토, 이미지 판독을 모두 맡겼다. 요청이 줄을 서서 요청 하나가 초당 5 토큰
남짓이었고, 답 하나에 100 초, 검토 한 건에 3 분, 판독 한 쪽에 1~2 분이 걸렸다. 젯슨 토르는 메모리 대역폭이 생성 속도를
정하므로 모델의 무게를 줄이는 것이 곧 속도이고, 토르는 FP4·FP8 을 하드웨어로 가속한다. 그래서 정밀도는 NVFP4[12] 를
우선하고, 사람이 기다리는 일(토르 02)과 배치 일(토르 03)을 장비로 나누었다(ADR-0023). 이렇게 하면 수만 건의 반입 검토가
도는 동안에도 대화 답이 밀리지 않는다.

학습 장비는 서빙하지 않는다. 학습은 메모리를 오래 크게 쓰므로 서빙과 같은 장비에 두면 둘 다 불안정해진다. 학습 장비에
상주 생성 모델을 두지 않은 것도 같은 까닭이다. 새로 들어온 문서의 서류 종류 판정은 운영 서버가 문서를 받는 즉시 토르 03
에 맡긴다. 대량 스캔 판독처럼 시간이 오래 걸리는 일괄 처리만 학습 장비에서 MinerU[19][20] 로 돌렸다(ADR-0007).

장비와 하는 일의 관계와 데이터·모델 호출 방향은 1.4.1 절의 [그림 1-2] 와 같다.

모델 캐시는 오프라인으로 두어 외부 서비스 없이 뜬다.

| 문서 읽기 | pdfium[22] 글자층 직독, MinerU[19], kordoc[25], 자체 OWPML(hwpx)[24] 파서, python-docx·openpyxl·python-pptx[28], LibreOffice[27], tesseract[23] | 형식마다 가장 정확한 길을 고른다. Docling[21] 은 판독 대결에서 뒤져 뺐다(ADR-0007·0033·0050·0051) |

[표 3-2] 층별 소프트웨어 구성

웹 한글 기안기 서버는 운영 서버 안에서만 열리고, 사용자는 AURA 의 로그인과 열람 범위 확인을 거친 프록시로만 닿는다.
기안기 서버에 밖에서 직접 접속하는 길은 없다.

### 3.1.4 외부 연결의 경계

모든 모델(생성·임베딩·리랭커)은 교내 장비에서 돈다. 착수 단계에 설계했던 외부 AI 참조 경로는 제거했다(ADR-0043·0061).
밖으로 나갈 수 있는 길은 코드 전체에서 목록으로 뽑아 하나씩 통제했다(31 개 경로). 지금 밖으로 나가는 것은 「웹 검색」
답변 방식의 질문 글(개인정보가 있으면 보내지 않음), 담당자 학교 계정의 구글 독스 작업본(넣는 글은 개인정보 검사와 감사 기록),
그리고 관리자가 개인정보 검토 확인을 거쳐 지정한 경우의 외부 GPU 서버 연결뿐이다. 외부 GPU 연결은 요청 속 개인정보를
되돌릴 수 있는 토큰으로 바꿔 보내고 답에서 원값으로 되돌리며, 가릴 수 없거나 그림이 든 요청은 보내지 않는다(ADR-0019).
반입 검토와 이미지 판독은 외부로 넘기지 않는다.

교내망에는 긴 숫자열이 든 요청을 끊는 보안 장비가 있다. 임베딩 요청은 9 자리 이상 숫자열을 가린 뒤 보내도록 했다. 서빙
장비가 응답하지 않으면 규정 검색은 운영 서버 CPU 의 같은 임베딩 모델로, 사업 문서 검색은 어휘 검색만으로 물러난다. 이런
물러남이 측정에 섞이면 수치가 거짓이 되므로, 모든 측정은 운영 연결 설정을 읽고 띄우며 어느 모델이 답했는지를 함께 남긴다.

### 3.1.5 개발과 배포 절차

코드는 하나의 저장소에서 관리하고 실제 문서·처리 결과·비밀값은 저장소에 넣지 않는다. 설계 판단은 결정 기록으로 남기며,
기존 기록은 고쳐 쓰지 않고 새 번호로 대체한다. 지금까지 ADR-0001 부터 ADR-0072 까지 70 여 건이 쌓였다. 코드를 바꾸는
커밋은 같은 커밋에서 현황 문서와 설계 문서를 함께 고치게 하고, 이를 커밋 훅이 검사한다.

검증은 세 겹이다. 자동 테스트(10-23 기준 2,492 건 통과)가 기능과 권한 판정을 지키고, 반입 자가 점검·개인정보 잔여 검사·
서빙 점검 스크립트가 운영 데이터 상태를 보며, 검색·답·문서 작성 측정 스크립트가 품질 수치를 낸다. 시험은 운영 설정이
아닌 시험 DB 에서 하고, 데이터를 바꾸는 운영 작업은 백업을 먼저 한 뒤 되돌리기 명령을 함께 둔다. 앱이 띄우는 긴 배경
작업(재측정·재색인·반입 점검)은 서비스와 떼어 돌려 배포 재시작에 끊기지 않게 했다.

## 3.2 전체 아키텍처

### 3.2.1 설계 원칙

AURA 의 구조는 다음 네 원칙을 따른다.

1. 판단은 모델, 실행은 코드. 질문의 뜻 읽기, 서류 종류·사업 판정, 도구 고르기, 양식 고르기처럼 문장의 뜻을 읽어야 하는
   판단은 Writer 27B 가 한다. 코드는 그 판단을 받아 도구를 실행하고, 권한·수치 근거·양식 모양 같은 관문을 지키고, 모든
   판단을 기록한다. 낱말 규칙으로 판단을 대신하면 꼴이 조금만 달라도 틀리고, 규칙을 덧대면 특정 사례에 맞춘 짜맞추기가
   된다(ADR-0060·0063).
2. 하나의 처리기. 문서가 들어오는 길(학교 원본 동기화, 라이브러리 업로드, 채팅 첨부, 구글 드라이브 가져오기)은 여럿이지만
   모두 같은 처리기를 거친다(ADR-0049). 길마다 처리가 다르면 같은 문서가 길에 따라 다르게 검색된다.
3. 도메인 중립 공통 계층. 파싱, 개인정보 인식, 분류, 열람 등급은 국고사업 전용 가정 없이 만들고, 실적 카드·배점 검증·예산
   같은 국고사업 고유 로직은 도메인 모듈로 분리한다(ADR-0003). 다음 도메인(채용 서류 검토 등)을 같은 공통 계층 위에 얹기
   위해서다.
4. 지식은 검색으로, 능력은 학습으로. 사업의 사실과 수치는 모델에 외우게 하지 않고 검색과 지식 그래프로 공급한다. 파인튜닝은
   질문을 보고 무엇을 어디서 찾아 어떻게 근거를 구성할지라는 능력에만 쓴다(ADR-0047).

도우미를 둔다. 도메인층은 처리 단계별 패키지이고, 저장층은 PostgreSQL 과 문서 폴더, 모델층은 교내 서빙 장비의 모델이다.

### 3.2.3 두 파이프라인

AURA 의 처리는 두 파이프라인으로 나뉘고, 둘이 만나는 곳은 저장층뿐이다. 구축 파이프라인(배치)은 문서를 검색할 수 있는
자산으로 바꾸고, 질의 파이프라인(대화형)은 질문과 작성 요청을 답과 초안으로 바꾼다. 둘을 저장층으로만 이은 덕에 반입이
수만 건씩 도는 동안에도 질의 쪽은 이미 적재된 처리본을 읽기만 한다. 3.3 절에서 두 흐름을 차례로 설명한다.

## 3.3 데이터 흐름

### 3.3.1 구축 흐름 — 반입에서 그래프까지

[그림 3-2] 는 학교 원본이 검색과 그래프의 자산이 되기까지의 흐름이다. 단계마다 담당 모듈과 실행 장비를 함께 적었다.

[그림 3-2] 구축 흐름(반입 → 개인정보 → 조각 → 색인 → 그래프) (그림 docs/images/diagrams/c3-02-build-flow.png)

각 단계의 핵심은 다음과 같다. 세부 구현과 수치는 4.1~4.4 절에 있다.

- 반입. 원본 장부는 원본 파일 하나가 한 줄이고 내용은 담지 않는다. 운영 서버는 1 분 주기로 업로드 원본·새 조각 색인·그래프
  표시를 맞추고, 10 분 주기로 학습 장비 원본 목록을 훑어 장부를 차이로 갱신한다. 학습 장비 쪽 목록이 바뀌면 그 표시를 받아
  주기를 기다리지 않고 바로 동기화한다. 학습 장비는 읽기 전용 연결로만 본다.
- 읽기와 개인정보. 형식마다 가장 정확한 읽기 길을 고르고(4.1), 개인정보는 내부 열람용 가림과 학습 반출용 가림을 서로 다른
  관문으로 둔다(4.2, ADR-0044).
- 조각과 판정. 조각은 절을 넘지 않게 자르고(ADR-0048), 서류 종류와 사업은 27B 가 판정하되 코드가 후보 목록과 형식을
  강제한다. 판정 줄마다 판정한 모델 정보를 남긴다.
- 색인과 그래프. 규정 색인과 사업 문서 색인을 따로 둔다. 문서 계열을 한 색인으로 합치면 규정 질문에 사업 문서 조각이, 사업
  질문에 규정이 섞이기 때문이다. 그래프는 요청 때마다 만들지 않고 노드·관계 표에 두며, 문서·조각이 바뀌면 최대 15 분,
  종류만 바뀌면 최대 한 시간 안에 다시 짓는다.

### 3.3.2 질의 흐름 — 검색에서 생성까지

[그림 3-3] 은 질문 하나가 출처가 달린 답이 되거나, 작성 요청이 양식대로 쓴 초안이 되기까지의 흐름이다.

[그림 3-3] 질의 흐름(검색 → 생성 → 검증) (그림 docs/images/diagrams/c3-03-query-flow.png)

질의 흐름의 설계에서 지킨 것은 세 가지다. 권한은 답을 만든 뒤가 아니라 검색 단계의 SQL 조건으로 건다. 화면에 보이는 출처는
모델에 실제로 건넨 근거 목록에서만 만든다. 생성된 숫자는 건넨 근거에 있는지 코드가 대조해, 없으면 답에서는 「(근거 확인
필요)」를 붙이고 문서 편집에서는 「○○」로 가린다. 수치는 인출하고 생성하지 않는다는 프로젝트의 첫째 규칙을 코드로 지키는
자리다.

## 3.4 저장 구조

### 3.4.1 원본과 처리본의 분리

학교 원본은 학습 장비에 두고, 운영 서버에는 처리본(글·조각·임베딩·그래프)과 보기용 캐시만 둔다(ADR-0047·0049). 원본을 두
곳에 복제하면 어느 쪽이 맞는지 판단할 수 없고, 운영 서버 디스크가 원본 증가를 따라가지 못한다. 담당자가 화면에서 원본 한
건을 열면 그때 읽기 전용으로 받아 크기·수정 시각이 장부와 같은지 대조한 뒤 보여 준다.

### 3.4.2 세 층의 데이터

자료는 성격에 따라 세 층으로 나눈다(ADR-0031). [표 3-4] 와 같다.

| 층 | 담는 것 | 특징 |
|---|---|---|
| 1 층 문서 | 반입 원본, 대화 첨부, 생성 문서(초안·완성본), 주간 보고, 한글 문서함 | 문서마다 접수번호와 제목으로 된 폴더, 모든 파일을 파일 장부에 적음 |
| 2 층 지식 | 조각 임베딩·문서 벡터·질문 색인, 검색 품질 측정, 내보내기 묶음 | 문서에서 뽑은 파생 자료. 열람 범위를 지켜 밖으로 낼 수 있음 |
| 3 층 모델 | 학습셋, 베이스라인, 모델(어댑터·병합본·NVFP4), 학습 기록 | 학습 장비와 같은 모양. 베이스라인이 없으면 학습 스크립트가 돌지 않음 |
| 캐시 | 줄 좌표, 쪽 그림, 복원 보기 | 다시 만들 수 있어 장부 밖에 둠 |

[표 3-4] 데이터 세 층

경로 규칙은 코드의 한 모듈(app/paths.py)에서만 나오고, 뿌리 경로 둘(문서·지식 뿌리와 모델 뿌리)만 바꾸면 전체가 따라온다.
새 반입 지점은 반드시 원본 채택 함수(storage.adopt_original)를 거쳐 파일 장부에 적힌다.

### 3.4.3 DB 가 정본

문서·조각·개체·장부의 정본은 PostgreSQL 이다(ADR-0037). 디스크의 문서 폴더는 사람이 찾기 쉽게 하는 배치이고, 파일의 실제
자리는 DB 의 파일 장부가 가리킨다. 그래서 폴더를 통째로 옮길 때는 경로 앞부분만 바꾸면 된다. [그림 3-4] 는 1 층 문서 폴더의
배치다.

반입·첨부·생성·보고·기안기 다섯 갈래 아래에 연도나 부서별로 문서 폴더를 둔다. 기안기에는 부서마다 저장 전 판(.판)과 지운 문서(.휴지통), 어디서나 쓰는 빈 양식(공통/공통 양식), 사업 전용 양식(공통/지난 사업 문서), 처음 열 때 생기는 내 폴더(~아이디)를 둔다.

### 3.4.4 옮기기

서버를 옮길 때 무엇을 옮길지는 이관 목록 도구(scripts/209)의 규칙표 한 곳에서 정한다. 경로마다 옮김, 비밀값, 다시 만듦,
옮기지 않음, 학습(학습 장비 담당) 가운데 하나를 붙이고, 어느 규칙에도 걸리지 않은 경로는 「규칙 없음」으로 드러내 조용히
빠지는 것이 없게 한다. 비밀값은 내용을 읽지 않고 경로만 적어 따로 옮기고, 운영 DB 는 덤프로 옮긴다. 운영 서버에서의 첫
실행(10-23)에서 옮김 4,819 개 13.8GB, 다시 만듦 26.4GB, 옮기지 않음 19.5GB 로 갈렸고, DB 가 옮김 밖을 가리키는 문서는
0 건이었다.

## 3.5 권한·등급·부서

### 3.5.1 열람과 작업 권한의 분리

권한은 두 축으로 나눈다. 열람 권한은 무엇을 볼 수 있고 무엇이 검색되는지이고, 작업 권한은 무엇을 만들고 바꾸고 관리할 수
있는지다. 열람은 계정의 역할·부서·추가 권한과 문서의 열람 등급이 정하고, 작업 권한은 교직원 등급이 정한다(ADR-0066). 두
축을 섞으면 등급을 하나 더할 때마다 검색 범위 규칙이 갈라진다.

### 3.5.2 역할과 등급

계정 역할은 교직원·학생·관리자 셋이다. 교수·부서장 역할은 교직원으로 합쳤다. 교직원 안에는 작업 권한 등급을 두고, 관리자는
둘로 한정한다. [표 3-6] 과 같다.

| 할 수 있는 일 | 일반 | 행정 담당자·사업 책임자 | 총괄 책임자 | 관리자(2 명까지) |
|---|---|---|---|---|
| 질문·검색·문서 열람 | 부서 규칙대로 | 부서 규칙대로 | 부서 규칙대로 | 전부 |
| 새 프로젝트 만들기 | 불가(공유받은 프로젝트에서 작업) | 가능 | 가능 | 가능 |
| 프로젝트 진행 현황 | 불가 | 자기 프로젝트, 맡은 사업의 프로젝트 | 맡은 처·단과 그 아래 팀·센터의 프로젝트 | 전부 |
| 사업 관리 화면 | 불가 | 맡은 사업 읽기 | 부서 사업 읽기, 사업 책임자 지정 | 편집·추가·숨기기 |
| 계정·RAG 공간 관리 | 불가 | 불가 | 불가 | 가능 |

[표 3-6] 교직원 등급과 작업 권한

부서는 두 단계로 본다. 총괄 책임자는 처·단 급, 사업 책임자와 행정 담당자는 팀·센터 급이다. 부서 목록은 학칙·직제·사무분장
규정과 학교 누리집의 기관 조직으로 맞췄고 운영 부서 82 개, 상위 관계 54 개다. 조직도는 관리자와 맡은 처·단의 총괄
책임자만 고치고, 고치는 검사·쓰기·되돌리기는 하나의 잠금 안에서 한 번에 한다. 일반 직원에게는 조직도를 보기만 열고
아이디·겸직·문서 수는 싣지 않는다.

### 3.5.3 열람 범위와 RAG 공간

문서마다 반입 때 부서와 열람 등급(전체 공개·부서 제한·담당자 한정)을 붙인다. 판정 규칙은 한 모듈(app/access_policy.py)에
모았다. 같은 규칙을 화면 판정용 함수와 같은 뜻의 SQL 조건 두 꼴로 내고, 라이브러리·폴더·문서 화면·검색·지식 그래프·원본
장부·채팅 근거가 모두 이것을 쓴다. 규칙이 화면마다 따로 있으면 어느 한 곳에서 새기 마련이다.

검색 범위는 RAG 공간으로 정한다(ADR-0053). 공간은 색인을 복제하지 않고 같은 색인 위의 검색 조건으로 얹는다. 학생 공간은
학생 공개로 지정한 학사 규정만, 부서 공간은 그 부서와 공통 사업 문서를, 관리자는 전부를 본다. 계정마다 다른 부서 자료를 더
열어 줄 수 있다(화면은 4.3.2 참고). 부서를 더해도 저장·갱신 비용이 늘지 않고, 공간마다 최소 등급을 걸 자리도 두었다(기본은 걸지 않음).

[그림 3-5] 는 질문 하나에 권한이 걸리는 자리다.

계정의 역할·소속 부서·추가 권한 부서·등급으로 검색 공간(student, dept:부서, staff, dev)을 정하고(rag_spaces.resolve), 그 공간의 열람 조건(열람 등급·부서·종류 제외)을 검색 SQL 의 WHERE 로 붙인다(access_policy.doc_sql). 규정 검색과 사업 문서 검색, 그래프 범위와 절 축 조각이 모두 이 조건을 거치고, 모델에 건넨 근거 목록이 그대로 화면 출처가 된다.

[그림 3-5] 검색 단계의 권한 적용 (그림 docs/images/diagrams/c3-05-access.png)

질문이 범위 밖 부서를 가리키면 답 머리에 그 부서 자료는 열람 권한이 없다고 알리고 감사 기록에 남긴다. 안내에는 부서
이름만 싣고 그 부서 문서의 제목·건수·있고 없음은 말하지 않는다. 모르는 역할은 가장 좁은 학생 범위로 본다. 다섯 개의 합성
계정으로 화면 판정과 SQL 판정, 채팅 근거가 어긋나지 않는지를 자동 테스트가 확인한다.

### 3.5.4 사용 방법 — 등급 정하기와 범위 확인

1. 관리자나 처·단 총괄 책임자가 「조직·구성원」(/team)의 「조직도」 탭에서 부서 나무를 본다. 관리자는 「부서 더하기」로 부서를 더하고 처·단의 총괄 책임자를
   지정한다. [그림 3-6]
2. 「구성원」 탭에서 사람마다 등급 칸을 「일반」·「행정 담당자」·「사업 책임자」 가운데 고르면 바로 저장된다. 부서를 옮길 때는 「부서 바꾸기」를 쓴다.
3. 관리자는 「사용자·계정」(/dev/users)에서 사용자를 추가하고 「＋ 겸직 부서 더하기」나 「추가 권한 — 등급과 따로 이 사람에게만」으로 예외를 준다.
4. 설정이 맞는지는 사이드바 아래 「테스트 보기」로 그 계정의 화면과 검색 범위를 그대로 보며 확인한다(4.10.2 참고).

[그림 3-6] 조직도 탭 — 처·단 카드와 팀·센터 줄 (그림 docs/images/06-org-chart.jpg)

> 참고: 사업별 책임자 지정은 「사업 관리」(/programs/admin)의 줄 메뉴 「편집」 › 「지정」에서 「총괄 책임자」·「사업 책임자」·「행정 담당자」를 고른다.
> 지정은 그 사업에 이어진 프로젝트의 진행 현황을 볼 권한으로 이어진다.

업무 시나리오로 보면, 교무처에 새 팀이 생겨 담당자 두 명이 들어왔다고 하자. 관리자가 조직도에서 교무처 아래에 팀을 더하고, 구성원 탭에서 두 사람을 그 팀으로
옮겨 한 사람은 「사업 책임자」, 한 사람은 「일반」으로 둔다. 「테스트 보기」로 일반 등급을 골라 보면 「프로젝트 추가」가 막히고, 공유받은 프로젝트에서만 작업할 수
있음을 확인한다. 검색 범위는 두 사람 모두 같은 부서 규칙을 따른다.

### 3.5.5 바꾸는 권한과 외부 계정

문서를 지우거나 고치는 요청은 올린 사람과 관리자만, 프로젝트는 담당자와 관리자만 바꾼다. 같은 부서 동료의 프로젝트는 읽기
전용이다. 구글 계정은 사용자가 각자 학교 계정을 연결하고, 부서 드라이브는 그 부서 총괄 책임자가 부서 공용 학교 계정으로
연결한다. 부서 계정의 토큰은 그 부서 폴더 안 문서를 만들고 다룰 때만 쓰고, 드라이브 찾기·가져오기는 본인 계정으로만 한다.
부서 계정으로 아무 폴더나 둘러볼 수 없게 하려는 것이다. 감사 기록에는 질문 앞부분만 남기고 원문 전체는 남기지 않는다.

## 3.6 모델 배치와 교체 구조

### 3.6.1 모델 네 개

모델 계획에 적은 네 모델만 쓴다. 모두 오픈웨이트이고 교내 장비에서 돈다. [표 3-7] 과 같다.

| 모델 | 바탕 | 역할 | 상태 |
|---|---|---|---|
| Embed | KURE-v1[29] | 질문·조각 임베딩(1,024 차원) | 학습본 Embed v2 운영(ADR-0021) |
| Rerank | bge-reranker-v2-m3[32] | 규정 검색 후보 재정렬 | 학습본 Rerank v1 운영(ADR-0020) |
| Writer | Qwen3.8-27B[3](dense, 멀티모달) | 답, 문서 작업 에이전트, 업무 도우미, 반입 검토, 이미지 판독, 질문 읽기, 종류·사업 판정 | 바탕 모델 운영, SFT 첫 학습본은 비교 뒤 채택하지 않음(4.11) |
| Extract | Qwen3.8-27B(Writer 와 같은 모델) | 구조화 추출 | 구조화 출력으로 Writer 가 겸함(ADR-0026) |

[표 3-7] 모델 네 개와 역할

생성 모델을 27B 하나로 묶은 까닭은 서빙 장비가 두 대뿐이라 여러 모델을 띄울 메모리가 없고, 이미지 입력이 되는 멀티모달
모델이라 판독까지 맡을 수 있기 때문이다. 판독용 소형 모델은 없는 문장을 지어내고 줄을 반복해 뺐다. dense 모델을 고른 것은
LoRA 학습과 vLLM 어댑터 서빙이 dense 모델에서 검증된 길이기 때문이다. MoE 모델은 학습 때 전문가 전체가 메모리에 올라가고
적은 데이터의 SFT 가 라우팅 때문에 불안정하다.

### 3.6.2 서빙 배치와 속도

두 서빙 장비에는 같은 판의 Writer 27B NVFP4[4] 를 vLLM 으로 올렸다(문맥 16,384 토큰). [표 3-8] 은 정밀도와 추측 디코딩에
따른 속도 변화다.

| 구성 | 요청 하나 생성 속도 | 비고 |
|---|---|---|
| bf16 원본(토르 02) | 초당 2.4~4.5 토큰 | 판독 5 쪽 128 초, 검토 1 건 225 초 |
| NVFP4(토르 03) | 초당 10.4~10.8 토큰 | 판독 5 쪽 29 초, 검토 1 건 82 초, 옮겨 적은 내용·검토 요지 같음 |
| NVFP4 + MTP 추측 디코딩 | 검토 쪽 10.6 → 23.8, 답 쪽 약 12 → 24.6 토큰/초 | 출력은 그대로, 맞힌 만큼 빨라짐 |

[표 3-8] Writer 27B 서빙 구성별 속도(ADR-0023, 실험 로그 16 절)

MTP 추측 디코딩은 모델 안에 든 다음 토큰 예측 층[14]이 토큰 두 개를 미리 짐작하고 본 모델이 검증해 받아들이는 방식이다[13].
본 모델이 검증하므로 출력은 바뀌지 않는다. Qwen 계열의 생각 모드는 기본으로 켜져 있어, 끄지 않은 호출이 출력 한도를 생각에
다 쓰고 값 없이 실패한 일이 있었다(질문 읽기 713 건 값 0). 그래서 클라이언트가 교내 호출의 생각 모드를 기본으로 끈다.
답 쓰기에서 생각 모드를 켠 비교는 7 배 느리고 채점이 나빠져(나빠짐 12, 나아짐 0) 끈 채로 둔다.

### 3.6.3 용도별 연결과 교체 구조

모델 호출은 모델 이름이 아니라 용도로 한다. 용도는 답(answer), 반입 검토(review), 이미지 판독(vision), 업무 도우미(helper)
등이고, 용도마다 어느 서버의 어느 모델을 쓸지는 개발자 화면 「도구·모델 연결」(/dev/tools)의 「LLM 연결」과 「단계별 모델」에서
정한다. 용도별 서버를 바꾸고 저장하면 코드 수정 없이 모델이 바뀐다(화면 조작은 4.10.2 참고). 실제 도입 때는 더 큰 모델이나
파인튜닝한 판으로 바뀌므로, 모델 이름·문맥 길이·생각 끄기 인자를 코드에 박아 두면 교체가 코드 수정이 된다. [그림 3-7] 은
교체 구조다.

호출하는 쪽은 용도 이름만 넘기고, 연결 설정(llm_connections)이 서버·모델·생각 끄기 인자·구조화 출력 방식·동시 상한을 정한다. 문맥 한도는 서버가 알려 주는 max_model_len 을 먼저 쓰고 없으면 설정값을 쓴다. 구조화 출력[50]을 서버가 거절하면 JSON 지시와 파싱으로 물러나고, 장애 때는 같은 모델을 내는 다른 교내 연결로만 넘긴다. 결과마다 서버가 알려 준 실제 모델 정보를 남기되 주소·가중치 경로는 남기지 않는다. 후보 모델은 교체 점검(scripts/195)으로 운영 설정을 바꾸지 않고 같은 데이터에서 검색·답·종류 판정을 나란히 재어, 비교표로 채택을 정한다.

[그림 3-7] 용도별 연결과 모델 교체 구조 (그림 docs/images/diagrams/c3-07-model-swap.png)

문맥 한도는 비율로 나눈다. 대화의 작업 메모는 문맥 한도의 6 %, 최근 대화 원문은 30 % 몫을 쓰고, 보내기 전에는 첨부 → 오래된
대화 → 출력 상한 → 검색 근거 순으로 줄여 한도에 맞춘다. 다 줄여도 넘으면 보내지 않는다. 비율이라 문맥이 긴 모델로 바꾸면
저절로 맞는다.

### 3.6.4 학습본 이관

학습은 학습 장비에서 bf16 LoRA SFT[15] 로 하고, 학습본은 어댑터를 바탕에 합친 뒤 운영과 같은 NVFP4 로 다시 양자화해 두 서빙
장비에 올린다. 이 절차는 이관 스크립트(scripts/116)로 자동화했고, 리랭커처럼 근거 하한이 있는 모델은 옮긴 뒤 하한을 다시
잰다. 학습본은 서빙 장비에 다른 서빙 이름으로 올려 후보로 재고, 나빠지지 않을 때만 용도를 옮긴다. 학습셋은 학습 장비에서
만들고 승인하며 원문은 학습 장비 밖으로 나가지 않는다. 운영 서버의 학습 화면에는 이름·상태·건수·지문·승인 범위만 담은
목록이 1 분마다 들어온다. 이 절차를 처음 실제로 돌린 결과는 4.11 절과 5.4.5 절에 있다.
