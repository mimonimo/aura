# 3. 환경 구축 및 시스템 설계

이 장은 AURA의 장비 환경(3.1), 전체 아키텍처(3.2), 데이터 흐름(3.3), 저장 구조(3.4), 권한·등급·부서 체계(3.5), 모델 배치와
교체 구조(3.6)를 다룬다. 기능별 구현은 4장에서 다루고, 이 장에서는 설계 판단과 그 근거를 기술한다.

## 3.1 개발·운영 환경

### 3.1.1 설계 제약

AURA의 환경에는 세 가지 제약이 있다. 첫째, 대학 행정 문서에는 개인정보와 기관 내부 정보가 포함되어 상용 클라우드 AI로 보낼 수
없으므로 모든 모델이 교내 장비에서 동작해야 한다. 둘째, 사용할 수 있는 장비는 GPU가 없는 가상 서버 한 대, 젯슨 AGX 토르[11] 두 대,
학습용 DGX 한 대뿐이다. 셋째, 학교 원본 문서는 계속 추가되고 수정되므로 처리 결과도 원본을 따라 갱신되어야 한다.

이에 따라 장비별로 역할을 나누어 메모리와 처리량의 경합을 피하고, 원본과 처리본을 분리해 운영 서버는 원본 저장소를 읽기만 하도록 설계했다.

### 3.1.2 장비 구성과 역할

[표 3-1]은 장비별 사양과 역할이다.

| 장비 | 사양 | 역할 |
|---|---|---|
| 운영 서버 | 가상 서버, CPU 8개, 메모리 64GB, GPU 없음 | 웹 화면과 API, PostgreSQL(pgvector), 어휘·의미 검색, 지식 그래프, 문서 반입 처리(파싱·조각·색인), 웹 한글 기안기 서버, 공동 편집, 주기 작업 |
| 서빙 장비 1(토르 02) | 젯슨 AGX 토르 | Writer 27B(NVFP4) 서빙. 대화 응답, 문서 작업 에이전트, 업무 도우미 등 대화형 작업 |
| 서빙 장비 2(토르 03) | 젯슨 AGX 토르 | Writer 27B(NVFP4) 서빙. 반입 검토, 이미지 판독, 질문 해석, 서류 종류·사업 판정 등 배치 작업. 질의 임베딩(Embed v2)과 리랭커(Rerank v1) 서비스 |

[표 3-1] 장비 구성과 역할

이 배치는 실측 결과에 따른 것이다. 초기에는 bf16 원본 27B 모델 하나를 토르 02에 올려 문서 작업, 반입 검토, 이미지 판독을 모두
처리했다. 그러나 요청이 대기열에 쌓여 요청 하나의 생성 속도가 초당 5토큰 남짓에 그쳤고, 답 하나에 100초, 검토 한 건에 3분, 판독
한 쪽에 1~2분이 걸렸다. 젯슨 토르는 메모리 대역폭이 생성 속도를 결정하고 FP4·FP8 연산을 하드웨어로 가속하므로 정밀도는 NVFP4[12]를
우선했다. 또한 대화형 작업(토르 02)과 배치 작업(토르 03)을 장비별로 나누어, 수만 건의 반입 검토가 진행되는 동안에도 대화 응답이
지연되지 않게 했다.

학습 장비는 메모리를 장시간 크게 점유하는 학습과 서빙을 함께 두면 둘 다 불안정해지므로 서빙에 사용하지 않는다. 새 문서의 서류 종류 판정은
반입 즉시 토르 03에서 처리하고, 대량 스캔 판독 같은 긴 일괄 처리만 학습 장비에서 MinerU[19][20]로 수행했다.

장비 사이의 관계와 데이터·모델 호출 방향은 1.4.1절의 [그림 1-2]와 같다.

설명했다.

### 3.1.4 외부 연결의 경계

착수 단계에 설계했던 외부 AI 참조 경로는 제거했다. 코드 전체에서 외부로 나갈 수 있는 경로 31개를 목록으로 추출해 하나씩 차단하거나
관문을 두었으며, 현재 남은 경로는 세 가지다. 첫째는 답 끝의 「인터넷에서 찾아보기」를 눌렀을 때 전송되는 질문 글로, 개인정보가 있으면
보내지 않는다. 둘째는 담당자 학교 계정의 구글 독스 작업본으로, 넣는 글은 개인정보 검사를 거치고 감사 기록에 남는다. 셋째는 관리자가
개인정보 검토를 확인한 뒤 지정한 외부 GPU 서버 연결이다. 외부 GPU 연결에서는 개인정보를 복원 가능한 토큰으로 바꿔 보내고 답에서 원래
값으로 되돌리며, 가릴 수 없는 요청, 이미지가 포함된 요청, 반입 검토, 이미지 판독은 보내지 않는다.

교내망 보안 장비가 긴 숫자열이 포함된 요청을 차단하므로, 임베딩 요청에서는 9자리 이상의 숫자열을 가려 보낸다. 서빙 장비가 응답하지
않으면 규정 검색은 운영 서버 CPU에서 실행한 같은 임베딩 모델로, 사업 문서 검색은 어휘 검색만으로 대체한다. 이렇게 대체된 결과가 성능
측정에 섞이지 않도록, 측정 시에는 운영 연결 설정을 읽어 실행하고 실제로 응답한 모델을 함께 기록한다.

### 3.1.5 개발과 배포 절차

코드는 하나의 저장소에서 관리하며, 실제 문서·처리 결과·비밀값은 저장소에 넣지 않는다. 설계 결정 기록은 고쳐 쓰지 않고 새 번호로
대체하는 방식으로 관리했으며 76건이 쌓였다. 코드를 바꾸는 커밋이 현황 문서와 설계 문서를 함께 수정했는지는 커밋 훅이 검사한다.

검증은 세 단계로 이루어진다. 자동 테스트가 기능과 권한 판정을 확인하고, 반입 자가 점검·개인정보 잔여 검사·서빙 점검 스크립트가 운영
데이터 상태를 점검하며, 검색·답·문서 작성 측정 스크립트가 품질 수치를 산출한다. 시험은 별도의 시험 DB에서 수행하고, 데이터를 바꾸는
운영 작업은 백업을 먼저 한 뒤 되돌리기 명령과 함께 실행한다.

환경은 저장소의 설치 묶음으로 재현할 수 있다. 앱 서버는 설치 스크립트 한 번으로 파이썬 환경, PostgreSQL·pgvector, 서비스, 주기 작업까지
설치하며(폐쇄망에서는 미리 만든 설치 묶음을 사용), GPU 서버는 별도 스크립트로 Writer 27B·임베딩·리랭커를 띄운다. 업데이트 후 새 버전이
기동하지 않으면 이전 버전으로 되돌리고, 매일 백업이 주기 작업으로 등록된다. 모델 서버 연결, 원본 폴더, 부서·사용자 등록은 설치 후
관리자가 웹 화면에서 설정한다(4.10.2절).

## 3.2 전체 아키텍처

### 3.2.1 설계 원칙

AURA의 구조는 다음 네 원칙을 따른다.

1. 판단은 모델이, 실행은 코드가 맡는다. 질문의 의미 해석, 서류 종류·사업 판정, 도구 선택, 양식 선택처럼 문장의 뜻을 읽어야 하는
   판단은 Writer 27B가 한다. 코드는 도구를 실행하고 권한·수치 근거·양식 형식 같은 관문을 지키며 판단을 기록한다. 낱말 규칙은
   표현이 조금만 달라도 틀리고, 규칙을 덧붙일수록 특정 사례에만 맞춘 임시방편이 되기 때문이다.
2. 모든 문서는 하나의 처리기를 거친다. 학교 원본 동기화, 라이브러리 업로드, 채팅 첨부, 구글 드라이브 가져오기가 모두 같은
   처리기를 사용한다. 경로마다 처리가 다르면 같은 문서가 다르게 검색되기 때문이다.
3. 공통 계층은 도메인에 중립적으로 만든다. 파싱, 개인정보 인식, 분류, 열람 등급은 국고사업 전용 가정 없이 구현하고, 실적 카드·
   배점 검증·예산 같은 국고사업 고유 로직은 도메인 모듈로 분리했다. 이로써 채용 서류 검토 같은 다른 도메인도 같은 계층 위에
   구현할 수 있다.
4. 지식은 검색으로, 능력은 학습으로 공급한다. 사업의 사실과 수치는 검색과 지식 그래프로 제공하고, 파인튜닝은 무엇을 어디서 찾아
   근거를 어떻게 구성할지 정하는 능력에만 사용한다.

### 3.2.2 계층 구조

AURA는 [그림 3-1]과 같이 화면층, 앱층, 도메인층, 저장층, 모델층의 다섯 계층으로 구성된다.

요청은 그림의 위에서 아래로 내려간다. 화면층은 서버에서 렌더링한 Jinja2 템플릿과 화면별 정적 자바스크립트로 이루어지며, 사용자의 조작을
HTTP 요청으로 앱층에 보낸다. 앱층은 하나의 FastAPI 앱이다. 앱 조립 모듈(main.py)이 인증, 공용 도우미, 배경 작업을 만들고, 대화·프로젝트·

[표 3-3] 최상위 패키지 구성

플랫폼의 핵심 기능은 대부분 app 패키지에 있다. 색인과 검색도 처음에는 index·retrieve 패키지로 분리할 계획이었으나, 권한 조건과 저장 표에
밀접하게 묶여 있어 app 안에 구현했다. app 디렉터리는 평면 구조이며, 주요 모듈을 역할별로 묶으면 다음과 같다.

### 3.2.3 두 파이프라인

처리는 구축 파이프라인(배치)과 질의 파이프라인(대화형)으로 나뉜다. 구축 파이프라인은 문서를 검색 자산으로, 질의 파이프라인은 질문과
작성 요청을 답과 초안으로 바꾼다. 두 파이프라인은 저장층에서만 만나므로, 반입이 수만 건씩 진행되는 동안에도 질의 파이프라인은 적재된
처리본을 읽기만 한다.

## 3.3 데이터 흐름

### 3.3.1 구축 흐름: 반입에서 그래프까지

[그림 3-2]는 학교 원본이 검색과 그래프의 자산이 되는 흐름이며, 단계마다 담당 모듈과 실행 장비를 표시했다.

[그림 3-2] 구축 흐름(반입 → 개인정보 → 조각 → 색인 → 그래프) (그림 docs/images/diagrams/c3-02-build-flow.png)

문서가 들어오는 경로는 학교 원본 동기화, 라이브러리 업로드, 채팅 첨부, 구글 드라이브 가져오기의 네 가지이지만, 모두 같은 반입 처리기
(pipeline.py)로 모인다. 처리기는 다음 순서로 동작하며, 세부 구현과 수치는 4.1~4.4절에서 다룬다.

첫째, 원본을 확인한다. 원본 장부는 원본 파일 하나를 한 행으로 기록하되 파일 내용은 담지 않는다. 운영 서버는 10분 주기로 원본 폴더(기본값은
학습 장비)의 목록을 확인해 바뀐 파일만 장부에 반영하고, 원본 목록이 바뀌면 주기를 기다리지 않고 즉시 반영한다. 원본은 읽기 전용으로만
연다. 처리기는 같은 내용의 문서가 이미 있으면 새 문서를 들이지 않고 실패 상태로 남긴다. 같은 조각이 두 번 색인되면 검색이 같은 근거를 중복해
올리기 때문이다.

둘째, 문서를 읽는다. 글자층이 있는 PDF는 원문 글자를 그대로 쓰고, 스캔본과 사진만 OCR 경로를 탄다(4.1). 읽은 뒤에는 문서 이름을 파일 이름이
아닌 본문의 제목으로 바꾼다. 이후 단계의 조각 제목, 검토, 인용, 목록은 모두 바뀐 이름을 사용한다.

셋째, 문서 성격에 따라 경로를 나눈다. 규정·지침 같은 기준 문서는 판단 근거이므로 원문 그대로 조문 단위로 잘라 규정 저장소에 적재한다.
업무 문서는 개인정보 처리 정책을 적용하고(4.2), 27B가 서류 종류와 사업을 판정한다. 이때 코드가 후보 목록과 출력 형식을 강제하며, 판정마다
판정한 모델 정보를 남긴다. 조각은 절 경계를 넘지 않게 자른다.

넷째, 색인과 그래프를 갱신한다. 규정 색인과 사업 문서 색인을 분리해 규정 질문에 사업 문서 조각이, 사업 질문에 규정이 섞이지 않게 한다.
사업 문서 색인은 1분 주기 작업이 새 조각만 임베딩해 덧붙이므로 전체를 다시 계산하지 않는다. 그래프는 노드·관계 표에 저장하며, 문서·조각이
바뀌면 15분, 서류 종류만 바뀌면 한 시간 안에 다시 구축한다.

이 처리기는 반입 경로와 관계없이 하나이므로, 같은 문서는 어느 경로로 들어와도 같은 조각과 같은 검색 결과를 얻는다.

### 3.3.2 질의 흐름: 검색에서 생성까지

[그림 3-3]은 질문이 출처 달린 답이 되고, 작성 요청이 양식대로 쓴 초안이 되는 흐름이다.

[그림 3-3] 질의 흐름(검색 → 생성 → 검증) (그림 docs/images/diagrams/c3-03-query-flow.png)

질문 하나는 다음 단계를 거친다. 첫째, 사용자가 대화 화면에서 질문을 보내면 대화 라우터(chat_routes.py)가 요청을 받아 답 만들기를 배경 작업으로
등록하고 바로 응답한다. 답 생성에는 수십 초가 걸릴 수 있으므로, 화면은 몇 초마다 진행 상태를 조회해 현재 단계와 근거 개수를 표시한다.
아래는 배경 작업을 등록하는 부분이다.

```python 답 만들기의 배경 작업 등록(app/main.py)
def _schedule_answer(background, session_id, q, stored, criteria, web=""):
    import time

    _chat_progress[session_id] = {"started_at": time.time(), "steps": ["요청 확인 중"], "at": [time.time()]}
    _chat_running.add(session_id)
    background.add_task(_answer_task, session_id, q, stored, criteria, web)
```

진행 표(_chat_progress)에 첫 단계를 적은 뒤 작업을 넘기므로, 화면은 요청 직후부터 진행 상황을 받을 수 있다.

둘째, 검색 범위를 정한다. 계정의 역할·소속 부서·겸직 부서·등급으로 RAG 공간을 고르고(rag_spaces.py), 그 공간의 열람 조건을 검색 SQL에 붙인다(3.5.3).

셋째, 근거를 찾는다. 규정 검색은 어휘 검색과 임베딩 검색의 순위를 가중 RRF로 합친 뒤 리랭커로 다시 정렬한다(regulations.py, embed_search.py,
rerank.py). 사업 문서 검색(grant_search.py)은 세 단계로 진행한다. 먼저 27B가 질문을 사업·연차·서류 종류·따라갈 관계로 해석하고, 그래프가 해당
사업의 문서로 후보를 좁힌다(graph/question_read.py, graph/retrieve.py). 다음으로 좁힌 범위 안에서 어휘 순위와 임베딩 순위를 RRF로 합친다.
마지막으로 상위 조각을 사업, 연차, 문서, 절의 경로와 함께 낸다. 좁힌 범위에서 맞는 조각이 없으면 그 사업의 문서 전체, 사업 문서 전체 순으로
범위를 넓히고, 넓힌 사실을 단계 기록에 남긴다.

넷째, 답을 생성한다. 찾은 규정·사업 문서 근거를 묶어 답(answer) 용도의 Writer 27B를 호출한다. 규정 근거의 응답은 응답기(responder.py)가 맡는다. 요청은 보내기 전에 문맥 한도 안으로 줄인다(3.6.3).

다섯째, 답을 검증하고 표시한다. 질의 흐름은 세 가지 원칙을 지킨다. 첫째, 권한은 답을 만든 뒤가 아니라 검색 단계의 SQL 조건으로 적용한다. 둘째, 화면의 출처는
모델에 실제로 전달한 근거 목록에서만 만든다. 셋째, 생성된 숫자가 전달한 근거에 있는지 코드가 대조해, 없으면 답에는 「(근거 확인 필요)」를
붙이고 문서 편집에서는 「○○」로 가린다. 이는 숫자를 지어내지 않고 근거에서 가져온다는 원칙을 코드로 강제하는 장치다. 답 속의 문서 이름은
근거 목록에 있는 것만 해당 문서로 가는 링크로 바뀐다(citations.py). 모델이 지어낸 문서 이름은 링크가 되지 않는다.

### 3.3.3 문서 작업 흐름: 에이전트에서 문서 파일까지

작성 요청은 질문과 같은 대화 경로로 들어오지만, 답 대신 문서 작업 에이전트(doc_agent.py)가 처리한다. 에이전트는 다음 과정을 반복한다.

첫째, 코드가 현재 상태를 만든다. 상태에는 요청, 최근 대화, 프로젝트 문서 제목, 연결된 작업본의 절 목록과 빈 절, 아직 받지 못한 값, 앞
단계의 결과가 들어간다. 둘째, Writer 27B가 상태를 보고 생각한 뒤 도구 하나를 골라 {thought, action, args} 형식의 JSON으로 답한다. 셋째, 코드는
고른 도구를 고른 인자 그대로 실행한다. 요청 글을 낱말 규칙으로 다시 해석하지 않는다. 검색 도구는 열람 범위 안에서만 찾고, 절 쓰기 도구는
재료 모으기, 수치 근거 대조, 품질 관문을 거친다. 넷째, 도구 결과를 다음 단계의 상태에 넣고, 단계 기록을 남긴다.

이 반복에는 코드의 관문이 걸려 있다. 단계 수와 쓰기 횟수에 상한이 있고, 되돌리기 어려운 도구는 담당자의 요청 글에 그 의도가 있을 때만
실행된다. 모델 응답의 형식이 깨지면 같은 단계를 한 번 더 요청하고, 같은 단계를 잇달아 세 번 반복하면 멈춘다. 도구가 끝내 실패하면 무엇이
실패했고 아무것도 바꾸지 않았다는 사실을 담당자에게 알린다.

편집기가 한글 기안기이면 양식 찾기·작업본 만들기·칸 채우기·절 쓰기 같은 기안기 도구(webhwp_agent.py)가 쓰인다. 절을 쓰기 전에는 27B가 필요한
정보와 찾을 곳을 먼저 계획하고 코드가 그 계획대로 검색한다(context_plan.py). 긴 절은 같은 모델을 새 문맥으로 다시 불러 맡긴다(delegate.py).
에이전트가 쓴 글은 사람의 편집과 같은 칸 단위 공동 편집 경로(webhwp_coedit.py)로 서버에 기록되고, 몇 초 뒤 한글 파일의 필드에 저장되며,
문서를 연 모든 화면에 알림으로 전달된다. 따라서 에이전트는 별도의 쓰기 경로가 없는 공동 편집 참여자 가운데 하나다. 세부 구현은 4장에서 다룬다.

## 3.4 저장 구조

### 3.4.1 원본과 처리본의 분리

학교 원본은 학습 장비에 두고, 운영 서버에는 처리본(글·조각·임베딩·그래프)과 열람용 캐시만 둔다. 두 곳에 복제하면 어느 쪽이 기준인지
가릴 수 없고, 운영 서버 디스크가 원본 증가를 감당하지 못하기 때문이다. 담당자가 원본을 열면 그 시점에 읽기 전용으로 받아 크기·수정
시각을 장부와 대조한 뒤 보여 준다. 다른 기관에 설치할 때는 운영 서버에 NAS를 연결한 폴더를 원본 폴더로 지정할 수도 있다.

### 3.4.2 세 층의 데이터

자료는 성격에 따라 [표 3-4]와 같이 세 층으로 나눈다.

| 계층 | 내용 | 특징 |
|---|---|---|
| 1층 문서 | 반입 원본, 대화 첨부, 생성 문서(초안·완성본), 주간 보고, 한글 문서함 | 문서마다 접수번호와 제목으로 폴더를 만들고, 모든 파일을 파일 장부에 기록한다. |
| 2층 지식 | 조각 임베딩·문서 벡터·질문 색인, 검색 품질 측정 결과, 내보내기 묶음 | 문서에서 추출한 파생 자료이며, 열람 범위를 지키는 조건에서 외부로 반출할 수 있다. |
| 3층 모델 | 학습셋, 베이스라인, 모델(어댑터·병합본·NVFP4), 학습 기록 | 학습 장비와 같은 구조를 따른다. 베이스라인이 없으면 학습 스크립트가 실행되지 않는다. |
| 캐시 | 줄 좌표, 쪽 이미지, 복원 보기 | 다시 생성할 수 있으므로 장부에 기록하지 않는다. |

[표 3-4] 데이터의 세 계층

경로 규칙은 코드의 한 모듈에서만 정의하므로, 최상위 경로 두 개(문서·지식 경로와 모델 경로)만 바꾸면 전체 경로가 따라 바뀐다.
새로운 문서 반입 경로를 만들 때도 같은 원본 등록 함수를 거쳐 파일 장부에 기록되게 했다.

### 3.4.3 DB가 정본

문서·조각·개체·장부의 정본은 PostgreSQL에 있다. 디스크의 문서 폴더는 사람이 찾기 쉽도록 배치한 것이고 파일의 실제 위치는 DB의
파일 장부가 가리키므로, 폴더를 통째로 옮길 때는 경로 앞부분만 바꾸면 된다. [그림 3-4]는 1층 문서 폴더의 배치다. 반입·첨부·생성·보고·

사업 전용 양식, 사용자별 개인 폴더를 둔다.

### 3.4.4 옮기기

서버를 이전할 때 옮길 대상은 이관 목록 도구의 규칙표 한 곳에서 정한다. 경로마다 옮김, 비밀값, 재생성, 옮기지 않음, 학습 장비 담당
가운데 하나를 지정하고, 어느 규칙에도 해당하지 않는 경로는 「규칙 없음」으로 표시한다. 비밀값은 내용을 읽지 않고 경로만 기록해 별도로
옮기며, 운영 DB는 덤프로 옮긴다. 운영 서버에서 처음 실행했을 때 DB가 옮김 대상 밖의 경로를 가리키는 문서는 0건이었다.

## 3.5 권한·등급·부서

### 3.5.1 열람과 작업 권한의 분리

권한은 열람(무엇을 보고 무엇이 검색되는지)과 작업(무엇을 만들고 바꾸고 관리하는지) 두 축으로 나눈다. 열람 권한은 계정의 역할·소속·
겸직 부서, 자기 부서에 공개된 다른 부서의 RAG, 문서의 열람 등급으로 정하고, 작업 권한은 교직원 등급으로 정한다. 두 축을 섞으면 등급을
하나 추가할 때마다 검색 범위 규칙이 늘어나 복잡해진다.

### 3.5.2 역할과 등급

계정 역할은 교직원·학생·관리자 셋이며 교수·부서장은 교직원으로 합쳤다. 교직원 안에는 작업 권한 등급을 두고, 관리자는 최대 2명으로
한정한다. 등급 판단은 모두 한 모듈(grades.py)의 함수로 모았다. 프로젝트를 만들 수 있는지(can_create_project), 프로젝트 진행 현황을 볼 수
있는지(can_view_activity), 총괄 책임자가 맡은 부서와 그 하위 부서가 어디까지인지(covered_depts), 관리자 수를 넘는지(admin_over)를 화면과
API가 모두 이 함수로 묻는다. 등급이 없는 기존 교직원 계정은 사업 책임자로 보아, 등급 도입 전에 프로젝트를 쓰던 사용자의 작업이 막히지
않게 했다. [표 3-6]은 등급별 작업 권한이다.

| 작업 | 일반 | 행정 담당자·사업 책임자 | 총괄 책임자 | 관리자(최대 2명) |
|---|---|---|---|---|
| 질문·검색·문서 열람 | 부서 규칙에 따름 | 부서 규칙에 따름 | 부서 규칙에 따름 | 전체 |
| 새 프로젝트 만들기 | 불가(공유받은 프로젝트에서만 작업) | 가능 | 가능 | 가능 |
| 프로젝트 진행 현황 | 불가 | 자기 프로젝트와 맡은 사업의 프로젝트 | 맡은 처·단과 하위 팀·센터의 프로젝트 | 전체 |
| 사업 관리 화면 | 불가 | 맡은 사업 열람 | 부서 사업 열람, 사업 책임자 지정 | 편집·추가·숨기기 |

[표 3-6] 교직원 등급과 작업 권한

표에서 보듯 등급은 만들고 관리하는 범위만 바꾸며, 질문·검색·문서 열람의 범위는 등급이 아닌 부서 규칙이 정한다. 이것이 3.5.1의 두 축
분리가 실제 권한에 나타난 모습이다.

부서는 상하 관계를 가진 트리 구조다. 총괄 책임자는 최상위인 처·단 단위에, 사업 책임자와 행정 담당자는 그 아래 팀·센터 단위에 속한다.
단계 수는 제한하지 않고 순환만 막는다. 부서 목록은 학칙·직제·사무분장 규정과 누리집의 기관 조직을 기준으로 하되 실제로 쓰는 부서만
등록한다. 트리는 교직원 누구나 볼 수 있지만 수정은 관리자와 해당 처·단의 총괄 책임자만 할 수 있으며, 수정할 때는 검사·쓰기·되돌리기를
하나의 잠금 안에서 수행한다. 권한이 없는 사용자에게는 아이디·겸직·문서 수를 보내지 않는다. 부서와 등급은 「조직 관리」 화면에서
관리하며, [그림 3-5]은 그 화면이다.

[그림 3-5] 조직 관리: 왼쪽 부서 트리와 고른 부서의 구성원 (그림 docs/images/figures-1027/f3-06-org-chart.jpg)

부서 트리에서 부서를 고르면 그 부서의 구성원과 등급이 함께 표시되므로, 조직 구조와 권한을 한 화면에서 확인하고 수정할 수 있다. 화면 조작
방법은 부록에서 다룬다.

### 3.5.3 열람 범위와 RAG 공간

문서에는 반입 시 부서와 열람 등급(전체 공개·부서 제한·담당자 한정)을 부여한다. 나중에 붙이면 전체를 다시 색인해야 하므로 반입 단계에서
정한다. 판정 규칙은 한 모듈(access_policy.py)에서 두 형식으로 제공한다. 하나는 문서 하나를 볼 수 있는지 답하는 판정 함수(visible)이고, 다른
하나는 같은 뜻을 SQL 조건으로 옮긴 함수(doc_sql)다. 화면에서 문서 하나를 열 때는 판정 함수를, 목록·건수·검색처럼 여러 문서를 고를 때는
SQL 조건을 쓴다. 아래는 SQL 조건을 만드는 부분이다(설명 문자열은 생략했다).

```python 열람 범위의 SQL 조건(app/access_policy.py)
def doc_sql(v: dict, alias: str = "d.") -> tuple[str, list]:
    a = alias
    role = v.get("role") or ""
    if role == "dev":
        return "", []
    if role == "student":
        return (f" AND COALESCE({a}access_level, 'public') = 'public' AND {a}doc_type = 'regulation'"
                f" AND COALESCE({a}audience, 'staff') = 'student'"), []
    mine = list(dict.fromkeys(x for x in [v.get("dept") or "", *(v.get("also") or ()), *(v.get("lent") or ())] if x))
    dept_in = f" OR COALESCE({a}dept, '{DEFAULT_DEPT}') IN ({','.join('?' * len(mine))})" if mine else ""
    user = v.get("user") or ""
    own = f" OR ({a}owner = ? AND {a}owner <> '')" if user else ""
    sql = (f" AND (COALESCE({a}access_level, 'public') = 'public'"
           f" OR ({a}access_level = 'dept' AND (COALESCE({a}dept, '{DEFAULT_DEPT}') = '{DEFAULT_DEPT}'{dept_in})){own})")
    return sql, [*mine, *([user] if user else [])]
```

관리자에게는 조건을 붙이지 않고, 학생에게는 학생 공개로 지정된 규정만 허용한다. 교직원에게는 전체 공개 문서, 공통·소속·겸직(also)·자기 부서에
공개된 부서(lent)의 부서 제한 문서, 자기가 올린 문서를 허용한다. 판정 함수도 같은 규칙을 따르며, 두 형식이 어긋나지 않는지는 자동 테스트가
확인한다. 라이브러리·폴더·문서 화면·검색·지식 그래프·원본 장부·채팅 근거가 모두 이 규칙을 사용하므로, 화면마다 규칙이 달라 정보가 새는
일이 없다.

열람 권한이 누가 어떤 문서를 볼 수 있는지 정한다면, 검색 범위는 어떤 자료로 답을 받는지 정한다. 검색 범위는 RAG 공간(rag_spaces.py)으로
정한다. RAG 공간은 색인을 복제하지 않고 같은 색인 위에 검색 조건을 더하는 방식이다. 학생 공간은 학생 공개로
지정한 학사 규정만, 부서 공간은 해당 부서와 공통 사업 문서를 검색하며, 관리자는 전체를 검색한다. 다른 부서가 특정 부서의 RAG를 검색하게
하려면 계정이 아니라 부서 단위로 「다른 부서에 열기」를 설정한다(4.3.2절). 새 부서 RAG는 설정에 공간을 더하는 것만으로 생기며 코드를 고치지
않는다. 따라서 부서를 추가해도 저장·갱신 비용이 늘지 않는다. 공간별로 최소 등급을 지정하는 설정도 두었으며, 기본값은 지정하지 않는 것이다.
최소 등급이 걸린 공간에 등급이 미치지 못하는 계정은 그 부서가 검색 범위에서 빠진다.

[그림 3-6]는 질문 하나에 권한이 적용되는 위치를 보여 준다. 계정의 역할·소속 부서·겸직 부서·자기 부서에 공개된 부서 RAG·등급으로
검색 공간(학생, 부서, 교직원 공통, 관리자)을 정하고, 그 공간의 열람 조건(열람 등급·부서·제외 종류)을 검색 SQL의 WHERE 조건으로 붙인다.
규정 검색, 사업 문서 검색, 그래프 범위 검색, 절 단위 조각 검색이 모두 이 조건을 거치며, 모델에 전달한 근거 목록이 그대로 화면의 출처가 된다.

[그림 3-6] 검색 단계의 권한 적용 (그림 docs/images/diagrams/c3-05-access.png)

권한은 검색 이후가 아니라 검색 SQL 안에서 적용되므로, 열람 범위 밖의 조각은 모델에 전달되는 근거 후보에 처음부터 들어가지 않는다.
질문이 열람 범위 밖의 부서를 가리키면 답의 첫머리에 해당 부서에 대한 열람 권한이 없다는 사실만 알리고(문서 제목·건수·존재 여부는
밝히지 않음) 감사 기록에 남긴다. 알 수 없는 역할은 가장 좁은 학생 범위로 처리한다. 합성 계정 다섯 개를 이용해 화면 판정, SQL 판정,
채팅 근거가 서로 어긋나지 않는지 자동 테스트로 확인한다.

### 3.5.4 바꾸는 권한과 외부 계정

문서의 삭제와 수정은 올린 사람과 관리자만, 프로젝트 변경은 담당자와 관리자만 할 수 있다. 다른 사용자는 담당자가 공유한 부서나 사람에
한해 「읽기만」(대화·작업 문서 보기) 또는 「함께 작업」(보기와 수정) 권한으로 사용한다. 프로젝트 권한 판정(project_access.py)은 담당자이면
수정 권한을 주고, 그렇지 않으면 공유 목록에서 사용자 본인이나 소속·겸직 부서에 해당하는 항목을 찾아 가장 높은 권한을 준다. 프로젝트 공유는
열람 권한이나 RAG 공간과 별개다. 프로젝트를 공유받아도 그 사람의 문서 열람 범위와 검색 범위는 그대로이며, 공유된 프로젝트의 대화와 작업
문서만 추가로 열린다. 사업별 책임자는 사업 관리 화면에서 지정하며, 지정된 사람은 그 사업에 연결된 프로젝트의 진행 현황을 볼 수 있다. 구글 계정은 사용자가 각자 학교 계정을 연결하고,
부서 드라이브는 해당 부서의 총괄 책임자가 부서 공용 학교 계정으로 연결한다. 부서 계정의 토큰은 그 부서 폴더 안의 문서를 다룰 때만
사용하고, 드라이브 탐색과 가져오기는 본인 계정으로만 하게 하여 부서 계정으로 임의의 폴더를 열람하지 못하게 했다. 감사 기록에는 질문의
앞부분만 남기고 원문 전체는 남기지 않는다.

| Embed | KURE-v1[29] | 질문·조각 임베딩(1,024차원) | 학습본 Embed v2를 운영한다. |
| Rerank | bge-reranker-v2-m3[32] | 규정 검색 후보 재정렬 | 학습본 Rerank v1을 운영한다. |
| Writer | Qwen3.8-27B[3](dense, 멀티모달) | 답, 문서 작업 에이전트, 업무 도우미, 반입 검토, 이미지 판독, 질문 해석, 서류 종류·사업 판정 | 기본 모델을 운영한다. 더 큰 모델에 적용할 SFT 절차와 데이터를 27B로 검증했다(4.11절). |
| Extract | Qwen3.8-27B(Writer와 같은 모델) | 구조화 추출 | 구조화 출력을 이용해 Writer가 겸한다. |

[표 3-7] 모델 네 개와 역할

생성 모델을 27B 하나로 통합한 이유는 서빙 장비 두 대에 여러 모델을 올릴 메모리가 없고, 멀티모달 모델이어서 판독까지 맡길 수 있기
때문이다(2.1.1). dense 모델은 LoRA 학습과 vLLM 어댑터 서빙이 검증된 구조이며, 교내 학습쌍 수천 쌍 규모의 SFT도 안정적으로 수행된다.

### 3.6.2 서빙 배치와 속도

두 서빙 장비에는 같은 버전의 Writer 27B NVFP4[4]를 vLLM으로 올렸고, 서빙 문맥 길이는 모델 최대치인 262,144토큰이다. [표 3-8]은
정밀도와 추측 디코딩에 따른 속도 변화다.

| 구성 | 요청 하나의 생성 속도 | 비고 |
|---|---|---|
| bf16 원본(토르 02) | 초당 2.4~4.5토큰 | 판독 5쪽 128초, 검토 1건 225초 |
| NVFP4(토르 03) | 초당 10.4~10.8토큰 | 판독 5쪽 29초, 검토 1건 82초. 판독 내용과 검토 요지는 원본과 같다. |
| NVFP4 + MTP 추측 디코딩 | 검토 초당 10.6→23.8토큰, 답 초당 약 12→24.6토큰 | 출력은 바뀌지 않고, 예측이 맞은 만큼 빨라진다. |

[표 3-8] Writer 27B 서빙 구성별 속도

NVFP4 양자화로 생성 속도가 두 배 이상 빨라졌고, MTP 추측 디코딩을 더해 다시 약 두 배 빨라졌다. 두 단계 모두 같은 입력에 대한 출력 품질은
원본과 같았다. MTP 추측 디코딩은 모델 내부의 다음 토큰 예측 층[14]이 토큰 두 개를 미리 예측하고 본 모델이 이를 검증해 받아들이는 방식이므로[13]
출력이 바뀌지 않는다. 한편 Qwen 계열은 생각 모드가 기본으로 켜져 있어, 이를 끄지 않은 호출이 출력 한도를 추론에 모두 소모하고 값 없이
실패한 일이 있었다(업로드 문서 713건의 문서 식별 정보 추출 값이 모두 0). 이에 클라이언트가 교내 호출의 생각 모드를 기본으로 끈다. 답 생성에서
생각 모드를 켜면 7배 느렸고 채점 결과도 나빠졌다(나빠짐 12, 나아짐 0).

### 3.6.3 용도별 연결과 교체 구조

모델은 이름이 아니라 답(answer), 반입 검토(review), 이미지 판독(vision), 업무 도우미(helper) 같은 용도로 호출한다. 용도별 서버와
모델, 임베딩·리랭커 서버 주소와 접근 키는 개발자 화면의 연결 설정에서 정하며, 설정을 저장하면 코드 수정 없이 모델이 바뀐다(4.10.2절).
실제 도입 시 더 큰 모델이나 파인튜닝한 모델로 교체할 수 있도록 모델 이름·문맥 길이·생각 모드 인자를 코드에 고정하지 않았다. [그림 3-7]은
이 교체 구조를 나타낸다.

[그림 3-7] 용도별 연결과 모델 교체 구조 (그림 docs/images/diagrams/c3-07-model-swap.png)

모델을 바꿀 때 고치는 곳은 연결 설정 한 곳뿐이며, 호출하는 코드는 바뀌지 않는다. 호출하는 코드는 용도 이름만 넘기고, 서버·모델·생각 모드
인자·구조화 출력 방식·동시 요청 상한은 연결 설정이 정한다. 용도에서 연결을 찾는 함수는 다음과 같다(설명 문자열과 주석은 생략했다).

```python 용도별 연결 찾기(src/zzaimy/generate/llm_connections.py)
def role_conn(role: str) -> dict | None:
    data = _load()
    cid, model = _role_entry(data, role)
    for pair in (os.environ.get("ZZAIMY_ROLE_CONN") or "").split(","):
        r, _, c = pair.partition("=")
        if r.strip() == role and c.strip() and get(c.strip()) and not _is_external(get(c.strip())):
            cid = c.strip()
    conn = get(cid) if cid else None
    if conn is not None and _is_external(conn):
        _warn_once(f"role-ext:{role}", "외부 서버가 용도 %s 에 지정돼 있어 무시합니다", role)
        conn = None
    if conn is None:
        conn = get(data["active"]) if data["active"] else None
        if conn is not None and role != "answer" and _is_external(conn):
            return None
        return _failover(data, conn, "") if conn else conn
    conn = dict(conn, model=model) if model else conn
    return _failover(data, conn, model)
```

용도에 지정된 연결이 있으면 그 연결과 모델을 쓰고, 없으면 문서 작업 기본 연결을 쓴다. 외부 서버는 어떤 용도에도 직접 지정될 수 없으며,
기본 연결이 외부 서버이더라도 답(answer) 이외의 용도, 즉 반입 검토나 이미지 판독은 외부로 넘기지 않는다. 마지막 단계(_failover)는 지정된
서버가 응답하지 않을 때 같은 모델을 제공하는 다른 교내 연결로 전환한다. 같은 모델을 올린 교내 서버가 여럿이면 처리 중인 호출이 가장 적은
서버로 요청을 나누어 보낸다(llm_pool.py). 일괄 작업은 환경 변수로 그 프로세스에서만 용도의 연결을 바꿀 수 있어, 화면의 운영 설정을 건드리지
않고 반입 배치를 다른 교내 서버로 돌릴 수 있다.

문맥 한도는 서버가 알려 주는 값을 우선 사용하고, 없으면 설정값을 쓴다. 서버가 구조화 출력[50]을 지원하지 않으면 JSON 형식을 지시한 뒤
결과를 파싱한다. 결과마다 실제로 응답한 모델 정보를 기록하되 서버 주소와 가중치 경로는 남기지 않는다. 후보 모델은 교체 점검 도구로 운영
설정을 바꾸지 않은 채 같은 데이터에서 검색·답·서류 종류 판정 성능을 나란히 측정해 채택 여부를 정한다.

문맥 한도는 비율로 배분한다. 대화의 작업 메모에는 문맥 한도의 6%, 최근 대화 원문에는 30%를 배정하고, 전송 전에는 첨부, 오래된 대화,
출력 상한, 검색 근거 순으로 줄여 한도에 맞춘다. 끝까지 줄여도 한도를 넘으면 요청을 보내지 않는다. 비율로 배분하므로 문맥이 긴 모델로
바꾸면 자동으로 맞춰진다.

### 3.6.4 학습본 이관

학습은 학습 장비에서 bf16 LoRA SFT[15]로 수행하고, 학습본은 어댑터를 기본 모델에 병합한 뒤 운영과 같은 NVFP4로 다시 양자화해 이관
스크립트로 두 서빙 장비에 올린다. 리랭커처럼 근거 점수 하한이 있는 모델은 이관 후 하한을 다시 측정한다. 학습본은 별도 서빙 이름으로
올려 학습 전 모델과 같은 시험으로 평가하고, 성능이 나아진 경우에만 운영 용도로 전환한다. 학습셋은 학습 장비에서 생성·승인하며 원문은
외부로 나가지 않는다. 운영 서버의 학습 화면에는 이름·상태·건수·지문·승인 범위만 담은 목록이 1분마다 전달된다. 이 절차를 더 큰 모델에
적용하기 전에 Writer 27B로 검증한 결과는 4.11절과 5.4.5절에서 다룬다.
