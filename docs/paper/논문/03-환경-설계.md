# 3. 환경 구축 및 시스템 설계

AURA의 설계는 세 가지 제약에서 출발한다. 문서 내용은 교외로 나가서는 안 되고, 사용할 수 있는 장비는 네 대뿐이며, 학교 원본은 계속
바뀐다. 이에 맞춰 장비마다 역할을 하나씩 나누었다. 판단은 Writer 27B가, 실행과 검증은 코드가 담당하게 했으며, 권한은 검색 SQL
안에서 적용하고, 모델은 용도 이름으로 호출해 설정 한 곳에서 교체하게 했다. 이 장은 장비 환경(3.1절), 전체 구조(3.2절),
데이터 흐름과 공동 편집(3.3절), 저장 구조(3.4절), 권한과 보안(3.5절), 모델 배치(3.6절)의 순서로 이러한 설계 판단과 근거를 설명한다. 기능별
구현은 4장에서 다룬다.

## 3.1 개발·운영 환경

장비 네 대에 역할을 하나씩 배정해 메모리와 처리량의 경합을 없애고, 문서 내용을 다루는 구성 요소는 모두 교내에 두었다. 이 배치에
NVFP4 양자화와 추측 디코딩을 더해 Writer 27B의 요청당 생성 속도는 초당 2.4~4.5토큰에서 23.8~24.6토큰으로 향상되었다(3.6.1절).

### 3.1.1 설계 제약과 장비 구성

대학 행정 문서에는 개인정보와 기관 내부 정보가 들어 있어 상용 클라우드 AI로 보낼 수 없다. 따라서 모든 모델이 교내 장비에서 동작해야
한다. 사용할 수 있는 장비는 GPU가 없는 가상 서버 한 대, 젯슨 AGX 토르[13] 두 대, 학습용 DGX 한 대다. 학교 원본 문서는 계속 추가·수정되므로
처리 결과도 원본에 맞춰 갱신되어야 한다. 이러한 조건에서 장비별로 역할을 나누고, 원본과 처리 데이터를 분리해 운영 서버는 원본을 읽기만
하도록 했다. [표 3-1]은 장비별 사양과 역할이다.

| 장비 | 사양 | 역할 |
|---|---|---|
| 운영 서버 | 가상 서버, CPU 8개, 메모리 64GB, GPU 없음 | 웹 화면과 API, PostgreSQL(pgvector), 어휘·의미 검색, 지식 그래프, 문서 수집(파싱, 청크(chunk) 분할, 색인), 웹 한글 기안기 서버, 공동 편집, 주기 작업 |
| 서빙 장비 1(토르 02) | 젯슨 AGX 토르 | Writer 27B(NVFP4) 서빙. 대화 응답, 문서 작성 에이전트, 업무 도우미 등 대화형 작업 |
| 서빙 장비 2(토르 03) | 젯슨 AGX 토르 | Writer 27B(NVFP4) 서빙. 수집 검토, 이미지 판독, 질문 해석, 서류 종류·사업 판정 등 배치 작업. 질의 임베딩(Embed v2)과 리랭커(Rerank v1) 서비스 |
| 학습 장비(DGX) | GB10, 통합 메모리 121GB, 디스크 3.7TB | 학교 원본 보관, 대량 처리(스캔 판독·일괄 판정), 학습 데이터 생성·승인, 파인튜닝 |

[표 3-1] 장비 구성과 역할

이 배치는 실측 결과에 따른 것이다. 처음에는 bf16 원본 27B 하나를 토르 02에 올려 문서 작업, 수집 검토, 이미지 판독을 모두 처리하게
했으나, 요청이 대기열에 쌓여 요청 하나의 생성 속도가 초당 2.4~4.5토큰에 그쳤다. 답변 하나에 100초, 검토 한 건에 3분, 판독 한 쪽에
1~2분이 걸렸다. 젯슨 토르에서는 가중치가 작을수록 생성이 빠르므로(2.1.3절) 정밀도는 NVFP4[14]를 우선했다. 대화형 작업(토르 02)과 배치 작업(토르 03)도 장비를 분리해, 수만 건의 수집 검토가 진행되는 동안에도 대화 응답이 지연되지
않게 했다.

메모리를 장시간 대량으로 점유하는 학습과 서빙을 함께 두면 둘 다 불안정해지므로 학습 장비는 서빙에 사용하지 않는다. 새 문서의
서류 종류 판정은 수집 즉시 토르 03에서 수행하고, 대량 스캔 판독 같은 긴 일괄 처리만 학습 장비에서 MinerU[21][22]로 수행했다. 장비 간
관계와 호출 방향은 1.4절 [그림 1-2]와 같다.

### 3.1.2 소프트웨어와 외부 연결

[표 3-2]는 계층별 소프트웨어와 선정 이유다. 새 의존성은 운영 서버가 외부 인터넷 없이 설치·기동할 수 있는지를 첫째 조건으로 삼았고,
모델 캐시도 오프라인으로 둔다.

| 계층 | 소프트웨어 | 선정 이유 |

| 저장 | PostgreSQL[39], pgvector[40](HNSW[41], halfvec 1,024차원) | 문서·청크·권한·벡터를 한 DB에 두고 권한 조건을 같은 SQL에 적용 |
| 서빙 | vLLM[10][11] | 어댑터 서빙·동시 처리·정밀도 선택을 한 엔진에서 지원 |
| 문서 읽기 | pdfium[25] 텍스트 레이어 추출, MinerU[21], kordoc[28], 자체 OWPML(hwpx)[27] 파서, python-docx·openpyxl·python-pptx[31], LibreOffice[30], tesseract[26] | 형식별 최적 읽기 경로. Docling[23]은 판독 비교 성능이 낮아 제외 |

| 지식 표현 | rdflib[46](OWL[44]·RDF[43]), pySHACL[47] | 온톨로지의 표준 형식 내보내기와 규칙 검사 |

[표 3-2] 계층별 소프트웨어 구성

모든 구성 요소는 오픈소스이거나 교내 설치형이며, 문서 내용을 외부 서비스로 보내는 구성 요소는 없다. 각 기술의 원리는 2장에서 설명했다.

착수 단계에 두었던 외부 AI 참조 경로는 제거했다. 코드에서 외부로 나갈 수 있는 경로 31개를 목록으로 추출해 하나씩 차단하거나 검증
단계를 두었으며, 현재 남은 경로는 세 가지다. 첫째, 답변 끝의 「인터넷에서 찾아보기」를 누르면 질문 글을 외부로 보내는데, 개인정보가
있으면 보내지 않는다. 둘째, 담당자 학교 계정의 구글 독스 작업 문서에 입력하는 글은 개인정보 검사를 거치고 감사 기록에 남는다. 셋째, 관리자가
개인정보 검토를 확인한 뒤 지정하는 외부 GPU 서버 연결에서는 개인정보를 복원 가능한 토큰으로 바꿔 보내고 응답에서 원래 값으로
되돌린다. 다만 개인정보를 토큰으로 바꿀 수 없는 요청, 이미지가 포함된 요청, 수집 검토, 이미지 판독은 이 연결로도 보내지 않는다.

교내망 보안 장비가 긴 숫자열이 포함된 요청을 차단하므로, 임베딩 요청에서는 9자리 이상의 숫자열을 마스킹해 보낸다. 서빙 장비가 응답하지
않으면 규정 검색은 운영 서버 CPU에서 같은 임베딩 모델로, 사업 문서 검색은 어휘 검색만으로 대체한다. 이 대체 결과가 성능 측정에 섞이지
않도록, 측정은 운영 연결 설정을 읽어 실행하고 실제로 응답한 모델을 함께 기록한다.

### 3.1.3 개발과 배포 절차

코드는 저장소 하나에서 관리하며, 실제 문서·처리 결과·비밀값은 저장소에 넣지 않는다. 설계 결정 기록은 기존 기록을 수정하지 않고 새
번호로 대체하는 방식으로 76건을 축적했다. 코드를 변경하는 커밋이 현황 문서와 설계 문서를 함께 수정했는지는 커밋 훅이 검사한다.

검증은 세 단계로 이루어진다. 자동 테스트가 기능과 권한 판정을 확인하고, 수집 자가 점검·개인정보 잔여 검사·서빙 점검 스크립트가 운영
데이터 상태를 점검하며, 검색·답변·문서 작성 측정 스크립트가 품질 수치를 산출한다. 테스트는 별도의 테스트 DB에서 수행하고, 데이터를 변경하는
운영 작업은 먼저 백업한 뒤 되돌리기 명령과 함께 실행한다.

환경은 저장소의 설치 패키지로 재현한다. 앱 서버는 설치 스크립트 한 번으로 파이썬 환경, PostgreSQL·pgvector, 서비스, 주기 작업까지
설치하고(폐쇄망에서는 미리 만든 설치 패키지 사용), GPU 서버는 별도 스크립트로 Writer 27B·임베딩·리랭커를 기동한다. 업데이트 후 새 버전이
기동하지 않으면 이전 버전으로 되돌리며, 매일 백업이 주기 작업으로 등록된다. 모델 서버 연결, 원본 폴더, 부서·사용자 등록은 설치 후
관리자가 웹 화면에서 설정한다(4.9.2절).

## 3.2 전체 아키텍처

AURA는 문장의 의미를 이해해야 하는 판단을 Writer 27B가 하게 하고, 코드는 도구 실행과 검증을 담당하게 했다. 또한 어느 경로로 들어온
문서든 같은 처리기에서 처리하게 했다. 이렇게 하면 새로운 표현이나 문서 형식이 나타나도 규칙을 추가하지 않고 같은 구조 안에서 처리할 수 있다.

### 3.2.1 설계 원칙

AURA의 구조는 다음 네 가지 원칙에 따라 설계했다.

1. 의미를 판단하는 일은 Writer 27B가 하고, 코드는 선택된 작업을 실행하고 검증한다. 질문이 무엇을 묻는지, 문서가 어떤 서류이고 어느
   사업에 속하는지, 어떤 도구와 양식을 사용할지는 27B가 정한다. 코드는 선택된 도구를 실행하고, 권한·수치 근거·양식 형식을 검사하며,
   27B의 판단을 기록으로 남긴다. 특정 단어가 들어 있는지로 판단하는 키워드 규칙은 사용하지 않는다. 이런 규칙은 같은 뜻을 다른 말로
   표현하면 틀리고, 틀릴 때마다 규칙을 덧붙이면 결국 몇몇 사례에만 맞는 규칙이 쌓이기 때문이다.
2. 문서는 어느 경로로 들어오든 같은 처리기에서 처리한다. 학교 원본 동기화, 라이브러리 업로드, 채팅 첨부, 구글 드라이브 가져오기가 모두
   같은 처리기를 사용한다. 경로마다 처리 방식이 다르면 같은 문서라도 들어온 경로에 따라 다르게 검색될 수 있으므로, 처리기를 하나로
   두어 결과를 일정하게 유지한다.
3. 여러 업무에 공통으로 쓰이는 기능은 특정 업무를 전제하지 않고 만든다. 파싱, 개인정보 인식, 분류, 열람 등급은 국고사업만을 가정하지
   않고 구현했으며, 실적 카드·배점 검증·예산처럼 국고사업에만 필요한 기능은 별도의 도메인 모듈로 분리했다. 이렇게 나누어 두면 채용
   서류 검토 같은 다른 업무도 공통 기능은 그대로 사용하고 업무별 모듈만 추가하면 된다.
4. 사실과 수치는 검색으로 제공하고, 파인튜닝은 작업 방법을 익히는 데만 사용한다. 사업의 사실과 수치는 검색과 지식 그래프가
   제공하며, 파인튜닝은 무엇을 어디서 찾아 근거를 어떻게 구성할지 판단하는 능력에만 사용한다. 사실을 모델에 학습시키면 문서가 바뀔
   때마다 다시 학습해야 하고 답의 출처도 제시하기 어렵지만, 검색으로 제공하면 최신 문서를 바로 반영하고 근거를 함께 보여 줄 수 있다.

### 3.2.2 계층 구조와 두 파이프라인

AURA는 [그림 3-1]과 같이 화면층, 앱층, 도메인층, 저장층, 모델층의 다섯 계층으로 이루어진다.

[그림 3-1] AURA 계층 구조 (그림 docs/images/diagrams/c3-01-layers.png)

요청은 그림의 위에서 아래로 전달된다. 화면층은 서버에서 렌더링한 Jinja2 템플릿과 화면별 정적 자바스크립트로 구성되며, 사용자의 조작을
HTTP 요청으로 앱층에 보낸다. 앱층은 하나의 FastAPI 앱이다. 앱을 조립하는 모듈이 인증, 공용 도우미, 배경 작업을 생성하고,
대화·프로젝트·문서·한글 기안기·지식 그래프·운영 관리 화면 같은 경로는 영역별 라우터 모듈 39개가 나누어 처리한다. 도메인층은 문서 읽기,
지식 그래프, 모델 연결, 검증처럼 화면과 무관한 처리를 모은 패키지다. 저장층은 PostgreSQL과 문서 폴더이고, 모델층은 교내 서빙 장비의
생성 모델·임베딩·리랭커 서비스다. 생성 모델은 모두 공용 모델 클라이언트가 용도별 연결 설정에 따라 호출한다(3.6.2절).

코드는 하나의 파이썬 패키지(zzaimy)로 관리한다. 패키지 이름은 서비스 이름과 다르지만 같은 시스템이다. [표 3-3]은 최상위 패키지와
주요 모듈이다.

[표 3-3] 소스 코드 구성

핵심 기능은 대부분 app 패키지에 있다. 색인과 검색도 처음에는 index·retrieve 패키지로 분리할 계획이었으나, 권한 조건 및 저장 표와
밀접하게 묶여 있어 app 안에 두었다. app 디렉터리는 평면 구조이며, 주요 모듈을 역할별로 분류하면 다음과 같다(분류 이름은 설명을 위한
것이며 실제 디렉터리가 아니다).

```text app 패키지의 역할별 주요 모듈
src/zzaimy/app/
├── main.py         앱 조립: 인증, 공용 도우미, 배경 작업, 라우터 등록
├── 화면·라우터     chat_routes, project_routes, doc_routes, webhwp_routes
├── 권한            access_policy(열람 판정·SQL 조건), rag_spaces, grades, project_access
├── 검색·응답       responder, regulations, embed_search(가중 RRF), rerank, grant_search, citations
├── 수집            pipeline, doc_routing, storage, paths
├── 문서 작업       doc_agent, webhwp_agent, context_plan, delegate, llm_budget
└── 공동 편집       webhwp_coedit(편집 잠금, 버전 번호, 충돌 사본, 알림)
```

권한 모듈은 검색·수집·문서 작업 모듈이 모두 호출하는 공통 검증 단계이고(3.5절), 검색·응답 모듈과 문서 작업 모듈은 모델 연결 패키지(generate)를
통해 모델을 호출한다. 요청 하나가 이 모듈들을 어떤 순서로 지나는지는 3.3절에서 설명한다.

처리는 구축 파이프라인(배치)과 질의 파이프라인(대화형)으로 나뉜다. 구축 파이프라인은 문서를 검색 자산으로, 질의 파이프라인은 질문과
작성 요청을 답변과 초안으로 바꾼다. 두 파이프라인은 저장층에서만 만나므로, 수집이 수만 건씩 진행되는 동안에도 질의 파이프라인은
적재된 처리 데이터를 읽기만 한다.

## 3.3 데이터 흐름

문서는 어느 경로로 들어오든 같은 처리기에서 같은 방식으로 청크와 색인이 되고, 질문과 작성 요청은 권한이 적용된 검색 결과를 근거로
답변과 초안이 되며 그 근거는 코드가 확인한다. 에이전트가 작성한 글도 사람의 편집과 같은 편집 영역 경로로 문서에 들어가므로, AURA는 공동 편집 참여자의 하나로
동작한다.

### 3.3.1 문서 구축 흐름

[그림 3-2]는 문서가 들어와 검색 색인과 지식 그래프에 등록되기까지의 흐름이다. 어느 경로로 들어온 문서든 하나의 처리기에서 여섯 단계로 처리된다.

[그림 3-2] 문서 구축 흐름 (그림 docs/images/diagrams/c3-02-build-flow.png)

문서가 들어오는 경로는 학교 원본 동기화, 라이브러리 업로드, 채팅 첨부, 구글 드라이브 가져오기의 네 가지이고, 모두 같은 수집 처리기로
모인다. 세부 구현과 수치는 4.1~4.4절에서 다룬다.

처리기는 먼저 원본을 확인한다. 원본 대장은 원본 파일 하나를 한 행으로 기록하되 파일 내용은 담지 않는다. 운영 서버는 10분 주기로 원본
폴더(기본값은 학습 장비)의 목록을 확인해 바뀐 파일만 대장에 반영하며, 원본 목록이 바뀌었다는 신호가 오면 주기를 기다리지 않고 바로
반영한다. 원본은 읽기 전용으로만 연다. 같은 내용의 문서가 이미 있으면 다시 등록하지 않으므로, 같은 청크가 두 번 색인되어
검색 결과에 같은 근거가 중복되는 일이 없다.

다음으로 문서를 읽는다. 텍스트 레이어가 있는 PDF는 텍스트 레이어를 그대로 추출하고, 스캔본과 사진만 OCR 경로로 보낸다(4.1절). 읽은
뒤에는 문서 이름을 파일 이름이 아닌 본문 제목으로 바꾸며, 이후 단계의 청크 제목, 검토, 인용, 목록은 모두 바뀐 이름을 사용한다.

읽은 문서는 성격에 따라 경로가 나뉜다. 규정·지침 같은 기준 문서[^c3-criteria]는 판단 근거이므로 원문 그대로 조문 단위로 잘라 규정
저장소에 적재한다. 업무 문서는 개인정보 처리 정책을 적용하고(4.2절) 27B가 서류 종류와 사업을 판정한다. 코드는 후보 목록과 출력 형식을
강제하고, 판정마다 판정한 모델 정보를 남긴다. 청크는 절 경계를 넘지 않게 자른다.

[^c3-criteria]: 기준 문서는 규정·지침·공고처럼 답변과 초안의 판단 근거가 되는 문서다. 마스킹하거나 수정하지 않고 원문 그대로 조문 단위로 색인한다.

마지막으로 색인과 그래프를 갱신한다. 규정 색인과 사업 문서 색인을 분리해, 규정 질문에 사업 문서 청크가, 사업 질문에 규정이 섞이지
않게 한다. 사업 문서 색인은 1분 주기 작업이 새 청크만 임베딩해 추가하므로 전체를 다시 계산하지 않는다. 그래프는 노드·관계 표에
저장하며, 문서·청크가 바뀌면 15분, 서류 종류만 바뀌면 한 시간 안에 다시 구축한다.

### 3.3.2 질의응답과 문서 작성 흐름

[그림 3-3]은 질문이 출처가 달린 답변이 되기까지의 흐름이다. 문서 작성 요청도 같은 검색을 거친 뒤 문서 작성 에이전트가 처리한다(4.6절).

[그림 3-3] 질의응답 흐름 (그림 docs/images/diagrams/c3-03-query-flow.png)

사용자가 대화 화면에서 질문을 보내면 대화 라우터가 답변 생성을 배경 작업으로 등록하고 즉시 응답한다. 답변 생성에는
수십 초가 걸릴 수 있으므로, 진행 표에 첫 단계를 기록한 뒤 작업을 넘겨 화면이 요청 직후부터 몇 초마다 현재 단계와 근거 개수를 조회할
수 있게 했다.

검색 범위는 계정의 역할·소속 부서·겸직 부서·등급에 따라 선택된 RAG 공간[^c3-ragspace]이 정하며, 그 공간의 열람 조건이
검색 SQL에 추가된다. 열람 조건은 3.5절에서 자세히 다룬다. 규정 검색은 어휘 검색과 임베딩 검색의 순위를 가중 RRF로 합친 뒤 리랭커로 다시 정렬한다.
사업 문서 검색에서는 27B가 질문을 사업·연차·서류 종류·따라갈 관계로 해석하면 그래프가
해당 사업의 문서로 후보를 좁히고, 그 범위 안에서 어휘 순위와 임베딩 순위를 RRF로 합쳐 상위
청크를 사업·연차·문서·절 경로와 함께 반환한다. 좁힌 범위에서 맞는 청크가 없으면 그 사업의 문서 전체, 사업 문서 전체 순으로 범위를
넓히고, 넓힌 사실을 단계 기록에 남긴다.

[^c3-ragspace]: RAG 공간은 검색 대상 문서의 집합이다. 모든 교직원이 사용하는 공통 RAG, 부서별 RAG, 학생 RAG가 있으며, 색인을 복제하지 않고 같은 색인 위에 검색 조건만 더한다.

찾은 근거는 모아서 답변 작성(answer) 용도의 Writer 27B에 전달하며, 요청은 보내기 전에 모델의 컨텍스트 길이 안으로 줄인다. 길이를 맞추는 방법은 3.6.2절에서 설명한다. 규정 근거의 응답은
별도의 응답 모듈이 담당한다.

권한은 검색 단계에서 SQL 조건으로 이미 적용되므로, 생성 뒤에는 답변이 근거를 벗어나지 않았는지를 확인한다. 화면에 표시하는 출처는
모델에 실제로 전달한 근거 목록에서만 만들고, 답변에 나오는 문서 이름도 그 목록에 있는 것만 링크로 연결한다. 답변 속
숫자는 코드가 근거와 하나씩 대조한다. 근거에서 찾을 수 없는 숫자에는 답변에서 「(근거 확인 필요)」를 덧붙이고, 문서 편집에서는
「○○」로 바꾼다. 숫자를 지어내지 않는다는 원칙을 모델 지시문에만 기대지 않고 코드로 지키게 한 것이다.

작성 요청은 질문과 같은 대화 경로로 들어오지만 문서 작성 에이전트가 처리한다. 매 단계 코드가 현재 상태(요청, 최근 대화,
프로젝트 문서 제목, 작업 문서의 절 목록과 빈 절, 아직 받지 못한 값, 앞 단계의 결과)를 만들면, Writer 27B가 이를 바탕으로 도구 하나를
선택하고, 판단 근거·도구 이름·인자를 담은 JSON으로 응답한다. 코드는 선택된 도구를 지정된 인자 그대로 실행하며, 요청 글을 키워드 규칙으로 다시
해석하지 않는다. 검색 도구는 열람 범위 안에서만 검색하고, 절 쓰기 도구는 자료 취합, 수치 근거 대조, 품질 검증을 차례로 수행한다. 도구 결과는
다음 단계의 상태에 들어가고 단계 기록으로 남는다.

이 반복 과정에는 코드 검증이 적용된다. 단계 수와 쓰기 횟수에 상한이 있고, 되돌리기 어려운 도구는 담당자의 요청 글에 그 의도가 드러날
때만 실행된다. 모델 응답의 형식이 깨지면 같은 단계를 한 번 더 요청하고, 같은 단계를 연속 세 번 반복하면 중단한다. 도구가 끝내 실패하면
무엇이 실패했는지와 아무것도 변경하지 않았다는 사실을 담당자에게 알린다.

편집기가 한글 기안기이면 양식 찾기·작업 문서 만들기·입력란 채우기·절 쓰기 같은 기안기 도구를 사용한다. 절을 쓰기 전에는
27B가 필요한 정보와 찾을 위치를 먼저 계획하고 코드가 그 계획대로 검색하며, 긴 절은 같은 모델을 새 컨텍스트로 다시 호출해
맡긴다. 에이전트가 작성한 글은 사람의 편집과 같은 영역 단위 공동 편집 경로로 서버에 기록되고, 몇 초 뒤
한글 파일의 해당 영역에 저장되며, 문서를 연 모든 화면에 알림으로 전달된다.

### 3.3.3 공동 편집 흐름

공동 편집은 글자 단위 병합 대신 영역 단위 편집 잠금(lease)으로 설계했다. 한 편집 영역은 한 번에 한 사람만 쓸 수 있게 해 충돌을
원천적으로 막고, 사람과 AURA가 같은 쓰기 경로를 쓰게 했다. 그 결과 병합 알고리즘 없이 편집기의 공개 API만으로 여러 사람과 에이전트의
동시 편집을 구현할 수 있었다.

여러 사람이 한 문서를 동시에 수정하는 편집기는 보통 OT나 CRDT로 글자 단위 변경을 병합하지만, 한컴 웹 기안기[53]의 공개 API로는 이 기법을
적용할 수 없다(2.8.2절). 편집기를 새로
만들면 병합은 가능하지만 행정 서식이 요구하는 한글 서식을 그대로 다룰 수 없다. 공개 API가 제공하는 것은 이름 붙은 입력란(누름틀)을
읽고 쓰고 그 위치로 이동하는 기능이므로, 이 입력란을 편집과 동기화의 단위인 편집 영역으로 삼았다. 편집 영역은 이름으로 찾으므로 여러
사람이 입력해도 문단 번호나 글자 위치처럼 주소가 밀리지 않는다.

이 단위 위에서 세 가지 규칙을 정했다. 첫째, 영역을 처음 수정하는 사람이 그 영역의 편집 잠금을 얻고, 다른 사람은 잠금이 끝나거나
넘겨받을 때까지 그 영역에 쓰지 않는다. 둘째, 서버는 영역마다 버전 번호(version)와 기준 상태를 유지하며, 화면은 바뀐 부분만 보내고
서버가 버전 번호와 지문으로 수용 여부를 판정한다. 셋째, 수용되지 않은 글은 버리지 않고 충돌 사본으로 남겨 입력이 사라지지 않게 한다.
이 방식의 한계는 영역 밖의 변경이다. 표 구조나 용지 같은 변경은 영역으로 나눌 수 없어 한 사람씩 문서 전체 단위로 처리하며, 이런 경우를 줄이기
위해 문서를 열 때 영역 밖 문단도 편집 영역으로 감싼다.

AURA에는 별도의 쓰기 경로가 없다. 에이전트가 작성한 절도 편집 잠금 확인, 버전 번호, 알림이라는 같은 경로로 들어가므로 사람이 점유한
영역을 덮어쓰지 않고, 사람과 에이전트 사이의 동기화를 따로 만들 필요가 없다. 권한 검사와 수정 기록도 사람의 편집과 같은 곳에서
이루어진다. 방안 비교와 구현 세부는 4.7절에서 다룬다.

## 3.4 저장 구조

원본은 학습 장비에, 처리 데이터는 운영 서버에 두고, 문서·청크·그래프의 기준 데이터는 PostgreSQL 한 곳에서 관리한다. 디스크의 폴더
구조는 사람이 찾기 쉽도록 정한 것이고, 파일의 실제 위치는 DB의 파일 대장에 기록된다. 그래서 경로 규칙 하나만 바꾸면 저장 위치 전체를
옮길 수 있다.

### 3.4.1 원본 분리와 데이터 계층

학교 원본은 학습 장비에 두고, 운영 서버에는 처리 데이터(텍스트·청크·임베딩·그래프)와 열람용 캐시만 둔다. 원본을 두 곳에 복제하면
어느 쪽이 기준인지 알 수 없게 되고, 원본이 늘어나는 만큼 운영 서버의 디스크도 부족해진다. 담당자가 원본을 열 때는 그때 학습 장비에서
읽기 전용으로 받아 크기와 수정 시각을 대장과 대조한 뒤 보여 준다. 다른 기관에 설치할 때는 운영 서버에 연결한 NAS 폴더를 원본 폴더로
지정할 수도 있다.

운영 서버의 자료는 [표 3-4]와 같이 문서, 지식, 모델의 세 계층으로 나눈다. 캐시는 언제든 다시 만들 수 있는 자료이므로 계층에 넣지
않고 따로 둔다.

| 계층 | 내용 | 특징 |
|---|---|---|
| 1층 문서 | 수집 원본, 대화 첨부, 생성 문서(초안·완성본), 주간 보고, 한글 문서함 | 문서별 접수번호·제목 폴더, 모든 파일의 파일 대장 기록 |
| 2층 지식 | 청크 임베딩·문서 벡터·질문 색인, 검색 품질 측정 결과, 내보내기 패키지 | 문서에서 추출한 파생 자료, 열람 범위를 지키는 조건에서 외부 반출 허용 |

| (별도) 캐시 | 줄 좌표, 쪽 이미지, 복원 보기 | 계층 밖 임시 자료, 재생성할 수 있어 대장 기록 제외 |

경로 규칙은 코드의 한 모듈에서만 정의한다. 따라서 최상위 경로 두 개(문서·지식 경로와 모델 경로)만 바꾸면 전체 경로가 함께 바뀐다.
새로운 문서 수집 경로를 추가할 때도 같은 원본 등록 함수로 파일을 등록하게 하여, 모든 파일이 파일 대장에 기록되도록 했다.

기록해 따로 옮기고, 운영 DB는 덤프로 옮긴다. 운영 서버를 이 도구로 점검한 결과, 옮김 대상 밖의 경로를 DB가 가리키는 문서는
0건이었다.

## 3.5 권한 설계

권한은 열람과 작업의 두 축으로 나누고, 열람 조건은 검색 SQL에 직접 적용한다. 따라서 열람 범위 밖의 청크는 처음부터 모델에 전달되는
근거 후보에 들어갈 수 없다. 로그인, 전송 암호화, 모델 서버 접근 제한, 감사 기록이 이 권한 체계를 외곽에서 뒷받침한다.

### 3.5.1 권한 구조

열람 권한은 무엇을 보고 무엇이 검색되는지를, 작업 권한은 무엇을 만들고 바꾸고 관리하는지를 정한다. 열람 권한은 계정의 역할·소속·겸직
부서, 자기 부서에 공개된 다른 부서의 RAG, 문서의 열람 등급으로 정하고, 작업 권한은 교직원 등급으로 정한다. 두 축을 섞으면 등급을 하나
추가할 때마다 검색 범위 규칙이 늘어난다.

계정 역할은 교직원·학생·관리자 셋이며 교수·부서장은 교직원으로 합쳤다. 교직원 안에는 작업 권한 등급을 두고, 관리자는 보안을 위해 최대 2명으로
한정한다. 등급 판단은 한 모듈의 함수로 모았다. 프로젝트를 만들 수 있는지, 진행 현황을 볼 수
있는지, 총괄 책임자가 맡은 부서와 하위 부서가 어디까지인지, 관리자 수를 넘는지를 화면과
API가 모두 이 함수로 확인한다. 등급이 정해지지 않은 교직원 계정은 사업 책임자로 간주하므로, 등급을 부여하기 전에도 사용자의 작업이
막히지 않는다. [표 3-6]은 등급별 작업 권한이다.

| 작업 | 일반 | 행정 담당자·사업 책임자 | 총괄 책임자 | 관리자 |
|---|---|---|---|---|
| 질문·검색·문서 열람 | 부서 규칙 | 부서 규칙 | 부서 규칙 | 전체 |
| 새 프로젝트 만들기 | × | ○ | ○ | ○ |
| 프로젝트 진행 현황 | × | 자기 프로젝트, 담당 사업의 프로젝트 | 담당 처·단과 하위 팀·센터의 프로젝트 | 전체 |
| 사업 관리 화면 | × | 담당 사업 열람 | 부서 사업 열람, 사업 책임자 지정 | 편집·추가·숨기기 |
| 계정·RAG 공간 관리 | × | × | × | ○ |

주: ○는 허용, ×는 허용하지 않음이다. 일반 등급은 공유받은 프로젝트에서만 작업한다. 관리자 계정은 보안을 위해 최대 2명으로 제한한다.

[표 3-6] 교직원 등급과 작업 권한

등급은 생성·관리 범위만 바꾸고, 질문·검색·문서 열람의 범위는 부서 규칙이 정한다. 앞에서 설명한 두 축 분리가 실제 권한에 반영된
모습이다.

부서는 상하 관계로 구성된 트리 구조다. 총괄 책임자는 최상위인 처·단 단위에, 사업 책임자와 행정 담당자는 그 아래 팀·센터 단위에 속한다. 단계
수는 제한하지 않고 순환만 막는다. 부서 목록은 학칙·직제·사무분장 규정과 누리집의 기관 조직을 기준으로 하되 실제로 사용하는 부서만
등록한다. 트리는 교직원 누구나 볼 수 있지만 수정은 관리자와 해당 처·단의 총괄 책임자만 할 수 있고, 수정할 때는 검사·쓰기·되돌리기를
하나의 잠금 안에서 수행한다. 권한이 없는 사용자에게는 아이디·겸직·문서 수를 보내지 않는다. 부서와 등급은 「조직 관리」 화면에서
관리한다([그림 3-5]).

[그림 3-5] 조직 관리 화면 (그림 docs/images/figures-1027/f3-06-org-chart.jpg)

부서 트리에서 부서를 선택하면 그 부서의 구성원과 등급이 함께 나타나므로, 조직 구조와 권한을 한 화면에서 확인하고 수정한다. 화면
조작 방법은 부록에서 다룬다.

### 3.5.2 열람 범위와 RAG 공간

부서와 열람 등급(전체 공개·부서 제한·담당자 한정)은 나중에 부여하면 전체를 다시 색인해야 하므로 수집 시점에 문서에 부여한다.
판정 규칙은 한 모듈에서 두 형식으로 제공한다. 문서 하나의 열람 가능 여부를 답하는 판정 함수와, 같은 규칙을
SQL 조건으로 옮긴 함수다. 문서 하나를 열 때는 판정 함수를, 목록·건수·검색처럼 여러 문서를 조회할 때는 SQL 조건을 사용한다.
아래는 SQL 조건을 만드는 부분이다.

```python 열람 범위의 SQL 조건
def doc_sql(v: dict, alias: str = "d.") -> tuple[str, list]:
    a = alias
    role = v.get("role") or ""
    if role == "dev":
        return "", []
    if role == "student":
        return (f" AND COALESCE({a}access_level, 'public') = 'public' AND {a}doc_type = 'regulation'"
                f" AND COALESCE({a}audience, 'staff') = 'student'"), []
    mine = list(dict.fromkeys(x for x in [v.get("dept") or "", *(v.get("also") or ()), *(v.get("lent") or ())] if x))
    dept_in = f" OR COALESCE({a}dept, '{DEFAULT_DEPT}') IN ({','.join('?' * len(mine))})" if mine else ""
    user = v.get("user") or ""
    own = f" OR ({a}owner = ? AND {a}owner <> '')" if user else ""
    sql = (f" AND (COALESCE({a}access_level, 'public') = 'public'"
           f" OR ({a}access_level = 'dept' AND (COALESCE({a}dept, '{DEFAULT_DEPT}') = '{DEFAULT_DEPT}'{dept_in})){own})")
    return sql, [*mine, *([user] if user else [])]
```

관리자에게는 조건을 적용하지 않고, 학생에게는 학생 공개로 지정된 규정만 허용한다. 교직원에게는 전체 공개 문서, 공통·소속·겸직 부서와 자기
부서에 공개된 부서의 부서 제한 문서, 자기가 올린 문서를 허용한다. 판정 함수도 같은 규칙을 따르며, 두 형식이 어긋나지 않는지는
자동 테스트가 확인한다. 라이브러리·폴더·문서 화면·검색·지식 그래프·원본 대장·채팅 근거가 모두 이 규칙을 사용하므로, 화면마다 규칙이
달라 정보가 새는 일이 없다.

열람 권한이 누가 어떤 문서를 볼 수 있는지 정한다면, 검색 범위는 어떤 자료를 근거로 답변을 받는지 정한다. 검색 범위는 RAG
공간이 정한다. 학생 공간은 학생 공개로 지정한 학사 규정만, 부서 공간은 해당 부서와 공통 사업 문서를 검색하며, 관리자는
전체를 검색한다. 다른 부서가 특정 부서의 RAG를 검색하게 하려면 계정별로 정하지 않고 부서 단위로 「다른 부서에 열기」를 설정한다(4.3절). 새
부서 RAG는 설정에 공간을 추가하기만 하면 생성되고 색인을 복제하지 않으므로, 부서를 추가해도 저장·갱신 비용이 늘지 않는다. 공간별로
최소 등급을 지정할 수도 있으며(기본값은 지정하지 않음), 등급이 미치지 못하는 계정은 그 부서가 검색 범위에서 빠진다.

[그림 3-6]은 질문 하나에 권한이 적용되는 위치다. 계정의 역할·소속 부서·겸직 부서·자기 부서에 공개된 부서 RAG·등급으로 검색
공간(학생, 부서, 교직원 공통, 관리자)을 정하고, 그 공간의 열람 조건(열람 등급·부서·제외 종류)을 검색 SQL의 WHERE 조건으로 추가한다.
규정 검색, 사업 문서 검색, 그래프 범위 검색, 절 단위 청크 검색에 모두 이 조건이 적용되며, 모델에 전달한 근거 목록이 그대로 화면의
출처가 된다.

[그림 3-6] 검색 단계의 권한 적용 (그림 docs/images/diagrams/c3-05-access.png)

질문이 열람 범위 밖의 부서를 가리키면 답변 첫머리에 해당 부서의 열람 권한이 없다는 사실만 알리고 문서 제목·건수·존재 여부는
밝히지 않으며, 이 질문을 감사 기록에 남긴다. 알 수 없는 역할은 가장 좁은 학생 범위로 처리한다. 합성 계정 다섯 개로 화면 판정, SQL 판정, 채팅
근거가 서로 어긋나지 않는지 자동 테스트로 확인한다.

### 3.5.3 수정 권한과 보안

문서의 삭제와 수정은 올린 사람과 관리자만, 프로젝트 변경은 담당자와 관리자만 할 수 있다. 다른 사용자는 담당자가 공유한 부서나 사람에
한해 「읽기만」(대화·작업 문서 보기) 또는 「함께 작업」(보기와 수정) 권한으로 사용한다. 프로젝트 권한 판정은
담당자이면 수정 권한을 주고, 아니면 공유 목록에서 본인이나 소속·겸직 부서에 해당하는 항목을 찾아 가장 높은 권한을 부여한다. 프로젝트
공유는 열람 권한이나 RAG 공간과 별개다. 공유받아도 그 사람의 문서 열람 범위와 검색 범위는 그대로이며, 공유된 프로젝트의 대화와 작업
문서만 추가로 열린다. 사업별 책임자는 사업 관리 화면에서 지정하며, 지정된 사람은 그 사업에 연결된 프로젝트의 진행 현황을 볼 수 있다.

구글 계정은 사용자가 각자 학교 계정을 연결하고, 부서 드라이브는 해당 부서의 총괄 책임자가 부서 공용 학교 계정으로 연결한다. 부서
계정의 토큰은 그 부서 폴더 안의 문서를 다룰 때만 사용하고, 드라이브 탐색과 가져오기는 본인 계정으로만 하게 해 부서 계정으로 임의의
폴더를 열람하지 못하게 했다.

로그인은 앱 서버가 직접 처리한다. 비밀번호는 계정마다 다른 솔트(salt)를 적용한 PBKDF2-SHA256 해시로만 저장하고, 예전 형식의 계정은
로그인에 성공하는 순간 해시로 변환한다. 로그인하면 만료 시각과 계정 이름을 서버 비밀 키로 서명(HMAC-SHA256)한 세션 토큰을
HttpOnly·SameSite=Lax 쿠키로 발급하며, 유효 기간은 7일이다. 서명 키는 처음 기동할 때 무작위로 생성해 서버 파일에 두고, 요청마다
서명·만료·계정 활성 여부를 확인하므로 비활성으로 바꾼 계정의 세션은 즉시 무효가 된다. 학생 계정은 허용된 대화·문서 읽기 경로만 사용할
수 있다.

전송 구간은 HTTPS로 보호한다. 설치 스크립트는 TLS 인증서와 키가 없으면 앱을 서버 자신(127.0.0.1)에만 열고, 외부 접속을 받으려면
인증서를 지정하거나 앞단 프록시를 두게 한다. 운영 서버는 현재 자체 서명 인증서를 사용하며, 플랫폼 이름(aura.ync.ac.kr)은 교내 DNS에
등록되기 전이라 관리자 PC의 hosts 파일로만 연결된다. 자체 서명 인증서에서는 크롬이 HTTP 캐시를 사용하지 않아 웹 기안기의 큰 파일을
열 때마다 다시 받으므로, 이 파일은 브라우저 저장소에 따로 보관한다(4.7절). 학교가 발급하는 신뢰된 인증서로 교체하는 일이 남아 있다.

모델 서버는 교내망 안에서만 응답하게 했다. GPU 서버의 기동 스크립트는 Writer 27B·임베딩·리랭커 포트를 모든 주소(0.0.0.0)에 열지 않고
그 서버의 내부망 주소에만 연다. 접근 키를 설정하면 vLLM과 임베딩·리랭커 서비스가 키 없는 요청을 거절하고, 앱은 연결 설정에 같은 키를
두어 보낸다. 화면에서 설정한 비밀값은 끝 네 글자만 표시한다(4.9.2절).

감사 기록은 용도별 표에 남는다. 권한 밖 부서를 묻는 질문과 특정인의 개인정보를 묻는 요청은 접근 감사 표에, 구글 문서 쓰기는
사용자·문서·절·글자 수와 함께 구글 문서 쓰기 기록 표에, 업무 도우미가 실행한 화면 동작은 도우미 실행 기록 표에 남긴다([표 3-5]). 감사 기록에는 질문의
앞부분만 남기고 원문 전체는 남기지 않는다.

## 3.6 모델 배치와 교체 구조

생성 모델은 Writer 27B 하나로 통합해 두 서빙 장비에 같은 버전을 올렸고, 호출하는 코드는 용도 이름만 넘긴다.
서버·모델·컨텍스트 길이·추론 모드(thinking mode)는 연결 설정 한 곳에서 정하므로, 실제 도입 때 더 큰 모델로 바꿔도 호출 코드는 그대로다.

### 3.6.1 사용 모델과 서빙 속도

본 프로젝트의 모델 계획에서 정한 오픈웨이트 모델 네 개만 교내 장비에서 사용한다([표 3-7]).

| 모델 | 기반 모델 | 역할 | 상태 |
|---|---|---|---|
| Embed | KURE-v1[33] | 질문·청크 임베딩(1,024차원) | 학습 모델 Embed v2 운영 |
| Rerank | bge-reranker-v2-m3[35] | 규정 검색 후보 재정렬 | 학습 모델 Rerank v1 운영 |
| Writer | Qwen3.8-27B[4](dense, 멀티모달) | 답변, 문서 작성 에이전트, 업무 도우미, 수집 검토, 이미지 판독, 질문 해석, 서류 종류·사업 판정 | 기본 모델 운영. 더 큰 모델에 적용할 SFT 절차와 데이터는 27B로 검증(4.10절) |
| Extract | Qwen3.8-27B(Writer와 같은 모델) | 구조화 추출 | Writer가 구조화 출력으로 겸임 |

[표 3-7] 사용 모델과 역할

서빙 장비 두 대에는 여러 모델을 올릴 메모리가 없고 멀티모달 모델은 판독까지 담당하므로, 생성 모델을 27B 하나로
통합했다(2.1.1절). dense 모델은 LoRA 학습과 vLLM 어댑터 서빙이 검증된 구조이며, 교내 학습 데이터 수천 쌍 규모의 SFT도 안정적으로 수행된다.

두 서빙 장비에는 같은 버전의 Writer 27B NVFP4[5]를 vLLM으로 올렸고, 서빙 컨텍스트 길이는 모델 최대치인 262,144토큰이다. [표 3-8]은
정밀도와 추측 디코딩에 따른 속도 변화다.

| 구성 | 요청 하나의 생성 속도(토큰/초) | 비고 |
|---|---|---|
| bf16 원본(토르 02) | 2.4~4.5 | 판독 5쪽 128초, 검토 1건 225초 |
| NVFP4(토르 03) | 10.4~10.8 | 판독 5쪽 29초, 검토 1건 82초. 판독 내용·검토 요지는 원본과 동일 |
| NVFP4 + MTP 추측 디코딩 | 검토 10.6 → 23.8, 답변 약 12 → 24.6 | 출력 변화 없음, 예측 적중만큼 속도 향상 |

[표 3-8] 생성 모델 서빙 구성별 속도

NVFP4 양자화로 생성 속도가 두 배 이상 빨라졌고, MTP 추측 디코딩을 더해 다시 약 두 배 빨라졌다. 두 단계 모두 같은 입력의 판독
내용과 검토 요지는 원본과 같았다. MTP 추측 디코딩은 모델 내부의 예측 층[15]이 미리 예측한 토큰 두 개를 본 모델이 검증해 수용하므로[16]
출력이 바뀌지 않는다(2.1.3절).

Qwen 계열은 추론 모드가 기본으로 켜져 있으나, AURA의 클라이언트는 교내 호출에서 이를 기본으로 끈다. 측정 당시 서빙에는 추론 글을
답과 분리하는 설정이 없어, 추론 모드를 켜면 질문 24개 가운데 16개에서 추론 글이 답에 섞이거나 출력 한도에서 끊겼다. 그 결과 답변
시간은 평균 7배 길어졌고, 같은 질문 24개 가운데 12개는 답이 나빠졌으며 나아진 것은 없었다. 자세한 결과는 5.4.1절에서 다룬다.

### 3.6.2 모델 교체 구조

AURA는 모델을 용도별로 연결한다. 답변 작성(answer), 수집 검토(review), 이미지 판독(vision), 업무 도우미(helper)마다 사용할 서버와
모델을 운영 관리 화면의 연결 설정에서 지정하고, 임베딩·리랭커 서버 주소와 접근 키도 같은 곳에서 정한다. 모델 이름·컨텍스트 길이·추론
모드 인자를 코드에 고정하지 않았으므로, 설정을 저장하면 코드 수정 없이 모델이 교체된다(4.9.2절). [그림 3-7]은 이 교체 구조다.

[그림 3-7] 용도별 연결과 모델 교체 구조 (그림 docs/images/diagrams/c3-07-model-swap.png)

호출하는 코드는 용도 이름만 넘기고, 서버·모델·추론 모드 인자·구조화 출력 방식·동시 요청 상한은 연결 설정이 정한다. 용도에서 연결을
찾는 함수는 다음과 같다.

```python 용도별 연결 찾기
def role_conn(role: str) -> dict | None:
    data = _load()
    cid, model = _role_entry(data, role)
    # … (일괄 작업은 환경 변수로 이 프로세스의 연결만 바꿀 수 있다)
    conn = get(cid) if cid else None
    if conn is not None and _is_external(conn):
        _warn_once(f"role-ext:{role}", "외부 서버가 용도 %s 에 지정돼 있어 무시합니다", role)
        conn = None
    if conn is None:
        conn = get(data["active"]) if data["active"] else None
        if conn is not None and role != "answer" and _is_external(conn):
            return None
        return _failover(data, conn, "") if conn else conn
    conn = dict(conn, model=model) if model else conn
    return _failover(data, conn, model)
```

용도에 지정된 연결이 있으면 그 연결과 모델을 사용하고, 없으면 문서 작업 기본 연결을 사용한다. 외부 서버는 어떤 용도에도 직접 지정할
수 없다. 수집 검토, 이미지 판독처럼 답변 작성(answer) 이외의 용도에는 수집 문서 전체와 쪽 이미지가 실리므로, 기본 연결이
외부 서버이더라도 이 용도의 요청은 외부로 보내지 않는다. 함수의 마지막 단계는 지정된 서버가 응답하지 않을 때 같은 모델을 제공하는 다른 교내
연결로 전환한다. 같은 모델을 올린 교내 서버가 여럿이면 처리 중인 호출이 가장 적은 서버로 요청을 분산한다. 일괄 작업은
환경 변수로 해당 프로세스에서만 연결을 바꾸므로, 화면의 운영 설정을 건드리지 않고 수집 배치를 다른 교내 서버에서 실행할 수 있다.

컨텍스트 길이는 서버가 제공하는 값을 우선 사용하고, 없으면 설정값을 사용한다. 서버가 구조화 출력[12]을 지원하지 않으면 JSON 형식을
지시한 뒤 결과를 파싱한다. 결과마다 실제로 응답한 모델 정보를 기록하되 서버 주소와 가중치 경로는 남기지 않는다. 후보 모델은 교체 점검
도구로 운영 설정을 바꾸지 않은 채 같은 데이터에서 검색·답변·서류 종류 판정 성능을 나란히 측정해 채택 여부를 정한다.

컨텍스트 길이는 비율로 배분한다. 대화의 작업 메모(2.7절)에는 컨텍스트 길이의 6%, 최근 대화 원문에는 30%를 배정한다. 출력 길이는
고정하지 않는다. 모든 모델 호출은 메인 에이전트, 서브 에이전트, 답변, 분류의 구분 없이 하나의 연결 계층에서 이루어지며, 이 계층이 컨텍스트
길이에서 입력 길이를 뺀 나머지 전부를 출력에 허용한다. vLLM은 출력에 쓸 메모리를 미리 확보하지 않고 실제로 생성한 만큼만 메모리를 쓰므로,
허용 길이를 크게 두어도 동시에 실행되는 서브 에이전트에 부담이 없다. 끝없이 생성되는 경우는 출력 길이 대신 호출 시간 제한으로 막는다.
입력이 컨텍스트 길이를 넘으면 첨부, 오래된 대화, 검색 근거 순으로, 잘라 내는 대신 모델로 압축한다. 압축할 때는 담당자의 요청과
조건, 이미 정한 것과 남은 일, 수치·날짜·이름·출처를 그대로 남기고 되풀이와 군더더기만 뺀다. 압축이 실패하면 뒤부터 잘라 내고, 그래도
한도를 넘으면 요청을 보내지 않는다. 비율로 배분하므로 컨텍스트가 긴 모델로 바꾸면 배정량도 자동으로 늘어난다.

### 3.6.3 학습 모델 반영

학습은 학습 장비에서 bf16 LoRA SFT[17]로 수행하고, 어댑터를 병합하고 NVFP4로 다시 양자화한(2.2절) 학습 모델을 이관 스크립트로
두 서빙 장비에 올린다. 리랭커처럼 근거 점수 하한이 있는 모델은 이관 뒤 하한을 다시 측정한다. 학습 모델은 별도 서빙 이름으로
올려 학습 전 모델과 같은 평가 데이터셋으로 평가하고, 성능이 개선된 경우에만 운영 용도로 전환한다. 학습 데이터셋은 학습 장비에서 생성하고 승인하며
원문은 밖으로 나가지 않는다. 운영 서버의 학습 화면에는 이름·상태·건수·지문·승인 범위만 담은 목록이 1분마다 전달된다. 이 절차를 더 큰
모델에 적용하기 전에 Writer 27B로 검증한 결과는 4.10절과 5.4.3절에서 다룬다.
