# 3. 환경 구축 및 시스템 설계

이 장은 AURA의 장비 환경(3.1), 전체 아키텍처(3.2), 데이터 흐름(3.3), 저장 구조(3.4), 권한·등급·부서 체계(3.5), 모델 배치와
교체 구조(3.6)를 다룬다. 기능별 구현은 4 장으로 미루고 여기서는 설계 판단과 근거를 적는다. 근거는 결정 기록(ADR)으로 남겼으며
(ADR-00NN) 형식으로 인용한다.

## 3.1 개발·운영 환경

### 3.1.1 설계 제약

환경에는 세 가지 제약이 있다. 첫째, 대학 행정 문서에는 개인정보와 기관 내부 정보가 들어 있어 상용 클라우드 AI로 보낼 수
없으므로 모든 모델이 교내 장비에서 돌아야 한다. 둘째, 장비는 GPU가 없는 가상 서버 한 대, 젯슨 AGX 토르[11] 두 대, 학습용
DGX 한 대뿐이다. 셋째, 학교 원본 문서는 계속 들어오고 바뀌므로 원본을 따라가며 처리본을 갱신해야 한다.

그래서 장비마다 맡는 일을 나누어 메모리와 처리량을 다투지 않게 하고, 원본과 처리본을 분리해 운영 서버는 원본 저장소를
읽기만 한다(ADR-0047·0049).

### 3.1.2 장비 구성과 역할

[표 3-1]은 장비별 역할이다. 접속 정보와 주소는 운영 문서에만 두고 이 논문에는 싣지 않는다.

| 장비 | 사양(기록 기준) | 맡는 일 |
|---|---|---|
| 운영 서버 | 가상 서버, CPU 8, 메모리 64GB, GPU 없음 | 웹 화면과 API, PostgreSQL(pgvector), 어휘·의미 검색, 지식 그래프, 문서 반입 처리(파싱·조각·색인), 웹 한글 기안기 서버, 공동 편집, 주기 작업 |
| 서빙 장비 1(토르 02) | 젯슨 AGX 토르 | 생성 모델 Writer 27B(NVFP4). 대화 답, 문서 작업 에이전트, 업무 도우미처럼 사람이 기다리는 일 |
| 서빙 장비 2(토르 03) | 젯슨 AGX 토르 | 생성 모델 Writer 27B(NVFP4). 반입 검토, 이미지 판독, 질문 읽기, 서류 종류·사업 판정 같은 배치 일. 질의 임베딩(Embed v2)·리랭커(Rerank v1) 서비스 |
| 학습 장비(DGX) | GB10, 통합 메모리 121GB, 디스크 3.7TB | 학교 원본 보관, 대량 처리(스캔 판독, 일괄 판정), 학습 데이터 생성·승인, 파인튜닝 |

[표 3-1] 장비 구성과 역할

이 배치는 실측에서 나왔다. 처음에는 bf16 원본 27B 모델 하나를 토르 02에 올려 문서 작업, 반입 검토, 이미지 판독을 모두
맡겼는데, 요청이 줄을 서서 요청 하나가 초당 5토큰 남짓이었고 답 하나에 100초, 검토 한 건에 3분, 판독 한 쪽에 1~2분이
걸렸다. 젯슨 토르는 메모리 대역폭이 생성 속도를 정하고 FP4·FP8 연산을 하드웨어로 가속하므로, 정밀도는 NVFP4[12]를 우선했다.
그리고 사람이 기다리는 일(토르 02)과 배치 일(토르 03)을 장비로 나누어, 수만 건의 반입 검토가 도는 동안에도 대화 답이 밀리지
않게 했다(ADR-0023).

학습 장비는 메모리를 오래 크게 쓰는 학습과 함께 두면 둘 다 불안정해지므로 서빙하지 않는다. 새 문서의 서류 종류 판정은
받는 즉시 토르 03에 맡기고, 대량 스캔 판독 같은 긴 일괄 처리만 학습 장비에서 MinerU[19][20]로 돌렸다(ADR-0007).

장비와 하는 일의 관계, 데이터·모델 호출 방향은 1.4.1절의 [그림 1-2]와 같다.

### 3.1.4 외부 연결의 경계

착수 단계에 설계했던 외부 AI 참조 경로는 제거했다(ADR-0043·0061). 밖으로 나갈 수 있는 길 31개를 코드 전체에서 목록으로 뽑아
하나씩 막거나 관문을 두었고, 지금 남은 것은 세 가지다.
답 끝의 「인터넷에서 찾아보기」를 눌렀을 때의 질문 글(개인정보가 있으면 보내지 않음), 담당자 학교 계정의 구글 독스 작업본(넣는 글은 개인정보 검사와
감사 기록), 관리자가 개인정보 검토 확인을 거쳐 지정한 외부 GPU 서버 연결이다. 외부 GPU 연결은 개인정보를 되돌릴 수 있는
토큰으로 바꿔 보내고 답에서 원값으로 되돌리며, 가릴 수 없거나 그림이 든 요청, 반입 검토, 이미지 판독은 보내지 않는다(ADR-0019).

교내망 보안 장비가 긴 숫자열이 든 요청을 끊으므로 임베딩 요청은 9자리 이상 숫자열을 가려 보낸다. 서빙 장비가
응답하지 않으면 규정 검색은 운영 서버 CPU에서 돌린 같은 임베딩 모델로, 사업 문서 검색은 어휘 검색만으로 대신한다. 이렇게 대신한
결과가 측정에 섞이지 않도록 측정은 운영 연결 설정을 읽고 띄우며 답한 모델을 함께 남긴다.

### 3.1.5 개발과 배포 절차

코드는 한 저장소에서 관리하고 실제 문서·처리 결과·비밀값은 넣지 않는다. 결정 기록은 고쳐 쓰지 않고 새 번호로 대체하며
ADR-0076까지 쌓였다. 코드를 바꾸는 커밋이 현황 문서와 설계 문서를 함께 고쳤는지는 커밋 훅이 검사한다.

검증은 세 겹이다. 자동 테스트가 기능과 권한 판정을 지키고, 반입 자가 점검·개인정보 잔여 검사·
서빙 점검 스크립트가 운영 데이터 상태를 보며, 검색·답·문서 작성 측정 스크립트가 품질 수치를 낸다. 시험은 시험 DB에서
하고, 데이터를 바꾸는 운영 작업은 백업 뒤 되돌리기 명령과 함께 한다. 긴 배경 작업(재측정·재색인·반입 점검)은 서비스와 떼어
돌려 배포 재시작에 끊기지 않는다.

환경은 저장소의 설치 묶음(deploy/)으로 다시 만들 수 있다. 앱 서버는 deploy/install.sh 한 번으로 파이썬 환경, PostgreSQL·pgvector,
서비스, 주기 작업까지 설치하고(폐쇄망은 미리 만든 묶음으로), GPU 서버는 deploy/model-server/serve.sh로 Writer 27B·임베딩·리랭커를
띄운다. 업데이트는 새 판이 뜨지 않으면 앞 판으로 되돌리고, 설치 때 매일 백업이 주기 작업으로 걸린다. 설치 뒤 모델 서버 연결, 원본 폴더,
부서·사용자 등록은 관리자가 웹 화면의 「초기 설정」·「서버 설정」 카드에서 한다(4.10.2 참고).

## 3.2 전체 아키텍처

### 3.2.1 설계 원칙

AURA의 구조는 다음 네 원칙을 따른다.

1. 판단은 모델, 실행은 코드. 질문의 뜻 읽기, 서류 종류·사업 판정, 도구 고르기, 양식 고르기처럼 문장의 뜻을 읽어야 하는
   판단은 Writer 27B가 한다. 코드는 도구를 실행하고 권한·수치 근거·양식 모양 같은 관문을 지키며 판단을 기록한다. 낱말
   규칙은 표현이 조금만 달라도 틀리고, 덧댈수록 특정 사례에 맞춘 짜맞추기가 된다(ADR-0060·0063).
2. 하나의 처리기. 학교 원본 동기화, 라이브러리 업로드, 채팅 첨부, 구글 드라이브 가져오기가 모두 같은 처리기를 거친다
   (ADR-0049). 길마다 처리가 다르면 같은 문서가 다르게 검색된다.
3. 도메인 중립 공통 계층. 파싱, 개인정보 인식, 분류, 열람 등급은 국고사업 전용 가정 없이 만들고, 실적 카드·배점 검증·예산
   같은 국고사업 고유 로직은 도메인 모듈로 분리해, 채용 서류 검토 같은 다음 도메인을 같은 계층 위에 얹을 수 있게 한다(ADR-0003).
4. 지식은 검색으로, 능력은 학습으로. 사업의 사실과 수치는 검색과 지식 그래프로 공급하고, 파인튜닝은 무엇을 어디서 찾아
   근거를 어떻게 구성할지 정하는 능력에만 쓴다(ADR-0047).

### 3.2.3 두 파이프라인

처리는 구축 파이프라인(배치)과 질의 파이프라인(대화형)으로 나뉜다. 구축은 문서를 검색 자산으로, 질의는 질문과 작성 요청을
답과 초안으로 바꾼다. 둘은 저장층에서만 만나므로 반입이 수만 건씩 도는 동안에도 질의 쪽은 적재된 처리본을 읽기만 한다.

## 3.3 데이터 흐름

### 3.3.1 구축 흐름: 반입에서 그래프까지

[그림 3-2]는 학교 원본이 검색과 그래프의 자산이 되는 흐름이며, 단계마다 담당 모듈과 실행 장비를 적었다.

[그림 3-2] 구축 흐름(반입 → 개인정보 → 조각 → 색인 → 그래프) (그림 docs/images/diagrams/c3-02-build-flow.png)

단계별 요점은 다음과 같고, 세부 구현과 수치는 4.1~4.4절에 있다.

- 반입. 원본 장부는 원본 파일 하나를 한 줄로 적고 내용은 담지 않는다. 운영 서버는 1분 주기로 업로드 원본·새 조각 색인·그래프
  표시를 맞추고, 10분 주기로 원본 폴더(기본은 학습 장비)의 목록을 훑어 바뀐 것만 장부에 반영한다. 원본 쪽 목록이 바뀌면
  주기를 기다리지 않고 맞추며, 원본은 읽기 전용으로만 연다.
- 읽기와 개인정보. 형식마다 가장 정확한 읽기 길을 고르고(4.1), 개인정보는 내부 열람용 가림과 학습 반출용 가림을 서로 다른
  관문으로 둔다(4.2, ADR-0044).
- 조각과 판정. 조각은 절을 넘지 않게 자르고(ADR-0048), 서류 종류와 사업은 27B가 판정하되 코드가 후보 목록과 형식을
  강제한다. 판정 줄마다 판정한 모델 정보를 남긴다.
- 색인과 그래프. 규정 색인과 사업 문서 색인을 따로 두어 규정 질문에 사업 문서 조각이, 사업 질문에 규정이 섞이지 않게 한다. 그래프는 노드·관계 표에 두고, 문서·조각이 바뀌면 15분, 종류만 바뀌면 한 시간
  안에 다시 짓는다.

### 3.3.2 질의 흐름: 검색에서 생성까지

[그림 3-3]은 질문이 출처 달린 답이 되고, 작성 요청이 양식대로 쓴 초안이 되는 흐름이다.

[그림 3-3] 질의 흐름(검색 → 생성 → 검증) (그림 docs/images/diagrams/c3-03-query-flow.png)

질의 흐름은 세 가지를 지킨다. 권한은 답을 만든 뒤가 아니라 검색 단계의 SQL 조건으로 건다. 화면의 출처는 모델에 실제로 건넨
근거 목록에서만 만든다. 생성된 숫자는 건넨 근거에 있는지 코드가 대조해, 없으면 답에는 「(근거 확인 필요)」를 붙이고 문서
편집에서는 「○○」로 가린다. 숫자는 지어내지 않고 근거에서 가져온다는 원칙을 코드로 지키는 자리다.

## 3.4 저장 구조

### 3.4.1 원본과 처리본의 분리

학교 원본은 학습 장비에 두고, 운영 서버에는 처리본(글·조각·임베딩·그래프)과 보기용 캐시만 둔다(ADR-0047·0049). 두 곳에
복제하면 어느 쪽이 맞는지 가릴 수 없고 운영 서버 디스크가 원본 증가를 따라가지 못하기 때문이다. 담당자가 원본을 열면 그때
읽기 전용으로 받아 크기·수정 시각을 장부와 대조한 뒤 보여 준다. 다른 기관에 설치할 때는 원본 폴더를 운영 서버 안 폴더(NAS를 붙인 자리)로
지정할 수도 있다.

자료는 성격에 따라 [표 3-4]와 같이 세 층으로 나눈다(ADR-0031).

### 3.4.4 옮기기

서버를 옮길 때 무엇을 옮길지는 이관 목록 도구의 규칙표 한 곳에서 정한다. 경로마다 옮김, 비밀값, 다시 만듦,
옮기지 않음, 학습(학습 장비 담당) 가운데 하나를 붙이고, 걸리지 않은 경로는 「규칙 없음」으로 드러낸다. 비밀값은 내용을 읽지 않고 경로만 적어 따로 옮기고, 운영 DB는 덤프로 옮긴다. 운영 서버에서 처음
돌렸을 때 DB가 옮김 대상 밖을 가리키는 문서는 0건이었다.

## 3.5 권한·등급·부서

### 3.5.1 열람과 작업 권한의 분리

권한은 열람(무엇을 보고 무엇이 검색되는지)과 작업(무엇을 만들고 바꾸고 관리하는지) 두 축으로 나눈다. 열람은 계정의
역할·소속·겸직 부서, 부서에 열어 준 다른 부서 RAG, 문서의 열람 등급이 정하고, 작업은 교직원 등급이 정한다(ADR-0066).
두 축을 섞으면 등급을 하나 더할 때마다 검색 범위 규칙이 갈라진다.

### 3.5.2 역할과 등급

계정 역할은 교직원·학생·관리자 셋이며 교수·부서장은 교직원으로 합쳤다. 교직원 안에는 [표 3-6]의 작업 권한 등급을 두고,
관리자는 둘로 한정한다.

| 할 수 있는 일 | 일반 | 행정 담당자·사업 책임자 | 총괄 책임자 | 관리자(2 명까지) |
|---|---|---|---|---|
| 질문·검색·문서 열람 | 부서 규칙대로 | 부서 규칙대로 | 부서 규칙대로 | 전부 |
| 새 프로젝트 만들기 | 불가(공유받은 프로젝트에서 작업) | 가능 | 가능 | 가능 |
| 프로젝트 진행 현황 | 불가 | 자기 프로젝트, 맡은 사업의 프로젝트 | 맡은 처·단과 그 아래 팀·센터의 프로젝트 | 전부 |
| 사업 관리 화면 | 불가 | 맡은 사업 읽기 | 부서 사업 읽기, 사업 책임자 지정 | 편집·추가·숨기기 |
| 계정·RAG 공간 관리 | 불가 | 불가 | 불가 | 가능 |

[표 3-6] 교직원 등급과 작업 권한

부서는 위아래 관계를 가진 트리다. 총괄 책임자는 맨 위 처·단 급, 사업 책임자와 행정 담당자는 그 아래 팀·센터 급이다.
단계 수는 제한하지 않고 순환만 막는다(ADR-0073). 부서 목록은 학칙·직제·사무분장 규정과 누리집의 기관 조직을
기준으로 하되 실제로 쓰는 부서만 올린다. 트리는 교직원 누구나 보지만 고치는
것은 관리자와 맡은 처·단의 총괄 책임자뿐이고, 고칠 때는 검사·쓰기·되돌리기를 한 잠금 안에서 한다. 권한이 없는 사람에게는
아이디·겸직·문서 수를 싣지 않는다.

### 3.5.3 열람 범위와 RAG 공간

문서에는 반입 때 부서와 열람 등급(전체 공개·부서 제한·담당자 한정)을 붙이고, 판정 규칙은 한 모듈에서
화면 판정 함수와 같은 뜻의 SQL 조건 두 형식으로 낸다. 라이브러리·폴더·문서 화면·검색·지식 그래프·원본 장부·채팅 근거가
모두 이것을 써서, 화면마다 규칙이 달라 새는 곳이 없게 했다.

검색 범위는 RAG 공간으로 정한다(ADR-0053). 공간은 색인을 복제하지 않고 같은 색인 위의 검색 조건으로 얹는다. 학생 공간은
학생 공개로 지정한 학사 규정만, 부서 공간은 그 부서와 공통 사업 문서를, 관리자는 전부를 본다. 다른 부서가 부서 RAG를 찾게
하려면 계정이 아니라 부서 단위로 「다른 부서에 열기」를 준다(4.3.2 참고). 부서를 더해도 저장·갱신 비용이 늘지 않으며, 공간마다 최소 등급을 걸 자리도 두었다(기본은 걸지 않음).

[그림 3-5]는 질문 하나에 권한이 걸리는 자리다.

계정의 역할·소속 부서·겸직 부서·내 부서에 열린 부서 RAG·등급으로 검색 공간(학생, 부서, 교직원 공통, 관리자)을 정하고, 그 공간의 열람 조건(열람 등급·부서·종류 제외)을 검색 SQL의 WHERE 조건으로 붙인다. 규정 검색, 사업 문서 검색, 그래프 범위, 절 축 조각이 모두 이 조건을 거치고, 모델에 건넨 근거 목록이 그대로 화면 출처가 된다.

[그림 3-5] 검색 단계의 권한 적용 (그림 docs/images/diagrams/c3-05-access.png)

질문이 범위 밖 부서를 가리키면 답 머리에 열람 권한이 없다고 부서 이름만 알리고(문서 제목·건수·유무는 말하지 않음) 감사
기록에 남긴다. 모르는 역할은 가장 좁은 학생 범위로 본다. 합성 계정 다섯 개로
화면 판정, SQL 판정, 채팅 근거가 어긋나지 않는지를 자동 테스트가 확인한다.

### 3.5.4 사용 방법: 등급 정하기와 범위 확인

부서와 등급은 「조직 관리」(/team) 한 화면에서 다룬다. 왼쪽 부서 트리에서 부서를 더하고 총괄 책임자를 정하며, 오른쪽 「구성원」 탭에서 사람을
골라 등급을 바꾸거나 부서를 옮긴다. 계정은 관리자가 「전체 사용자」에서 하나씩 만들거나 엑셀·CSV로 일괄 등록하고, 겸직 부서와 추가 권한도
여기서 준다. 설정이 맞는지는 「테스트 보기」로 그 계정의 화면과 검색 범위를 직접 보며 확인한다(4.10.2 참고).

[그림 3-6]
2. 「구성원」 탭에서 사람을 체크하면 작업 줄이 뜬다. 「등급 바꾸기」로 「일반」·「행정 담당자」·「사업 책임자」 가운데 고르고, 「옮기기」로 부서를 옮긴다.
3. 관리자는 「전체 사용자」의 「계정 추가」로 사용자를 만들거나(여럿이면 엑셀·CSV로 「일괄 등록」), 줄 끝 … › 「편집」에서 겸직 부서와 추가 권한을 준다.

「일반」으로 둔다. 「테스트 보기」로 일반 계정을 보면 「프로젝트 추가」가 막혀 있고, 검색 범위는 두 사람이 같다.

### 3.5.5 바꾸는 권한과 외부 계정

문서를 지우거나 고치는 일은 올린 사람과 관리자만, 프로젝트를 바꾸는 일은 담당자와 관리자만 한다. 다른 사람은 담당자가
공유한 부서·사람만 「읽기만」(대화·작업 문서 보기) 또는 「함께 작업」(보기와 고치기)으로 쓴다(ADR-0075). 구글 계정은 사용자가 각자 학교 계정을 연결하고, 부서 드라이브는 그 부서 총괄 책임자가 부서 공용 학교 계정으로
연결한다. 부서 계정의 토큰은 그 부서 폴더 안 문서를 다룰 때만 쓰고, 드라이브 찾기·가져오기는 본인 계정으로만 해 부서 계정으로 아무
폴더나 둘러보지 못하게 했다. 감사 기록에는 질문 앞부분만 남기고 원문 전체는 남기지 않는다.

## 3.6 모델 배치와 교체 구조

### 3.6.1 모델 네 개

모델 계획에 적은 오픈웨이트 모델 네 개만 교내 장비에서 쓴다([표 3-7]).

| 모델 | 바탕 | 역할 | 상태 |
|---|---|---|---|
| Embed | KURE-v1[29] | 질문·조각 임베딩(1,024차원) | 학습본 Embed v2 운영(ADR-0021) |
| Rerank | bge-reranker-v2-m3[32] | 규정 검색 후보 재정렬 | 학습본 Rerank v1 운영(ADR-0020) |
| Writer | Qwen3.8-27B[3](dense, 멀티모달) | 답, 문서 작업 에이전트, 업무 도우미, 반입 검토, 이미지 판독, 질문 읽기, 종류·사업 판정 | 바탕 모델 운영. 더 큰 모델에 적용할 SFT 절차·데이터를 27B로 검증(ADR-0069, 4.11) |
| Extract | Qwen3.8-27B(Writer와 같은 모델) | 구조화 추출 | 구조화 출력으로 Writer가 겸함(ADR-0026) |

[표 3-7] 모델 네 개와 역할

생성 모델을 27B 하나로 묶은 것은 서빙 장비 두 대에 여러 모델을 띄울 메모리가 없고, 멀티모달 모델이라 판독까지 맡길 수 있기
때문이다. 판독용 소형 모델은 없는 문장을 지어내고 줄을 반복해 뺐다. dense 모델은 LoRA 학습과 vLLM 어댑터 서빙이 검증된
길이고, 교내 학습쌍 수천 쌍 규모의 SFT도 안정적으로 돈다.

### 3.6.2 서빙 배치와 속도

두 서빙 장비에는 같은 판의 Writer 27B NVFP4[4]를 vLLM으로 올렸고, 문맥은 모델 최대치인 262,144 토큰으로 서빙한다. [표 3-8]은
정밀도와 추측 디코딩에 따른 속도 변화다.

| 구성 | 요청 하나 생성 속도 | 비고 |
|---|---|---|
| bf16 원본(토르 02) | 초당 2.4~4.5토큰 | 판독 5쪽 128초, 검토 1건 225초 |
| NVFP4(토르 03) | 초당 10.4~10.8토큰 | 판독 5쪽 29초, 검토 1건 82초, 옮겨 적은 내용·검토 요지 같음 |
| NVFP4 + MTP 추측 디코딩 | 검토 쪽 10.6 → 23.8, 답 쪽 약 12 → 24.6토큰/초 | 출력은 그대로, 맞힌 만큼 빨라짐 |

[표 3-8] Writer 27B 서빙 구성별 속도(ADR-0023, 실험 로그 16절)

MTP 추측 디코딩은 모델 안의 다음 토큰 예측 층[14]이 토큰 두 개를 미리 짐작하고 본 모델이 검증해 받아들이는 방식이라[13]
출력이 바뀌지 않는다. Qwen 계열은 생각 모드가 기본으로 켜져 있어, 끄지 않은 호출이 출력 한도를 생각에 다 쓰고 값 없이
실패한 일이 있었다(올린 문서 713건의 문서 정체 읽기 값 모두 0). 그래서 클라이언트가 교내 호출의 생각 모드를 기본으로 끈다. 답 쓰기에서 생각
모드를 켜면 7배 느리고 채점도 나빠졌다(나빠짐 12, 나아짐 0).

### 3.6.3 용도별 연결과 교체 구조

모델은 이름이 아니라 답(answer), 반입 검토(review), 이미지 판독(vision), 업무 도우미(helper) 같은 용도로 호출하고, 용도별
서버와 모델은 개발자 화면 「도구·모델 연결」(/dev/tools)의 「LLM 연결」과 「단계별 모델」에서, 임베딩·리랭커 서버 주소와 접근 키는 같은 화면의
「서버 설정」에서 정한다. 서버를 바꾸고 저장하면 코드 수정 없이 모델이 바뀐다(4.10.2 참고). 실제 도입 때 더 큰 모델이나 파인튜닝한 판으로 바꿀 수 있도록
모델 이름·문맥 길이·생각 끄기 인자를 코드에 두지 않았다. [그림 3-7]은 교체 구조다.

호출하는 쪽은 용도 이름만 넘기고 서버·모델·생각 끄기 인자·구조화 출력 방식·동시 상한은 연결 설정이 정한다. 문맥 한도는 서버가 알려 주는 값을 먼저 쓰고 없으면 설정값을 쓴다. 구조화 출력[50]을 서버가 받지 않으면 JSON으로 답하라고 지시한 뒤 파싱하고, 장애 때는 같은 모델을 내는 다른 교내 연결로만 넘긴다. 결과마다 실제 모델 정보를 남기되 주소·가중치 경로는 남기지 않는다. 후보 모델은 교체 점검 도구로 운영 설정을 바꾸지 않고 같은 데이터에서 검색·답·종류 판정을 나란히 재어 채택을 정한다.

[그림 3-7] 용도별 연결과 모델 교체 구조 (그림 docs/images/diagrams/c3-07-model-swap.png)

문맥 한도는 비율로 나눈다. 대화의 작업 메모는 문맥 한도의 6 %, 최근 대화 원문은 30 % 몫을 쓰고, 보내기 전에는 첨부 → 오래된
대화 → 출력 상한 → 검색 근거 순으로 줄여 한도에 맞춘다. 다 줄여도 넘으면 보내지 않는다. 문맥이 긴 모델로 바꾸면 비율에 따라
저절로 맞는다.

### 3.6.4 학습본 이관

학습은 학습 장비에서 bf16 LoRA SFT[15]로 하고, 학습본은 어댑터를 바탕에 합쳐 운영과 같은 NVFP4로 다시 양자화한 뒤 이관
스크립트로 두 서빙 장비에 올린다. 리랭커처럼 근거 하한이 있는 모델은 옮긴 뒤 하한을 다시
잰다. 학습본은 다른 서빙 이름으로 올려 학습 전 모델과 같은 시험으로 재고, 나아진 것만 운영 용도로 옮긴다. 학습셋은
학습 장비에서 만들고 승인하며 원문은 밖으로 나가지 않는다. 운영 서버의 학습 화면에는 이름·상태·건수·지문·승인
범위만 담은 목록이 1 분마다 들어온다. 이 절차를 더 큰 모델에 적용하기 전에 Writer 27B로 검증한 결과는 4.11절과 5.4.5절에 있다.
