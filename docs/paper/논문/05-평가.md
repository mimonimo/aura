# 5. 평가 및 결과

이 장은 AURA가 행정 문서 업무에 활용할 수 있는 정확도와 속도를 갖추었는지, 그리고 그 성능이 어디에서 비롯되는지를 단계별로 확인한다.
결론부터 정리하면, 스캔 판독은 정확도와 처리량에 따라 엔진을 나누어 사용하게 되었고, 검색 정확도는 리랭커와 사업 구조(그래프)에서 비롯되었으며, 문서 작성은 근거 밖 숫자를 0건으로 억제하면서 긴 서식도 끝까지
작성할 수 있게 되었으며, 공동 편집과 서빙 속도는 교내 장비에서 대화형으로 사용할 수 있는 수준이다. 수치는 측정 스크립트가 남긴 결과 파일과
측정 기록에 있는 값만 사용하고, 측정하지 않은 항목은 「미측정」, 기록을 확인하지 못한 항목은 「미확인」으로 적는다. 측정 연도는 모두 2026년이며,
같은 지표라도 회차·표본이 다르면 값 옆에 측정일과 표본을 함께 적는다.

## 5.1 평가 방법

평가는 같은 시험지끼리만 비교하였고, 코드가 계산한 지표를 주 근거로 삼았다.

### 5.1.1 평가 원칙과 지표

구성을 바꾸기 전에는 같은 시험지(benchmark)로 현재 구성을 측정해 기준선(baseline)을 정하고, 바꾼 뒤 같은 방식으로 다시 측정했다.
측정은 운영 연결 설정을 읽어 실행하고, 실제로 답한 모델과 대체 실행 횟수를 함께 기록했다(5.7절). 시험지를 수정하면 버전(version) 번호를 올리고
기준선을 다시 측정해, 같은 버전의 시험지끼리만 비교했다. 근거 밖 숫자, 정답 문서 적중, 서식 깨짐처럼 코드가 세는 지표를 주 근거로 삼았고,
언어 모델 채점은 버전 비교용 보조 지표로만 사용했다. 같은 구성을 반복 측정하여 실행 간 변동보다 큰 차이만 의미 있는 차이로 해석했다.

지표는 문서 처리의 판독 정확도, 검색 정확도, 답변과 작성 결과의 근거 충실도, 공동 편집 지연, 서빙 속도로 나뉜다. 각 지표의 정의는 처음 나오는
문장에 각주로 단다. 숫자를 세는 지표는 모두 코드가 계산하며, 언어 모델이 매긴 점수는 같은 시험지에서 버전을 비교하는 데에만 사용한다.

### 5.1.2 시험지와 측정 도구

평가 대상별 시험지는 [표 5-1]과 같다. 모든 측정은 저장소의 측정 스크립트로 다시 실행할 수 있다.

| 구분 | 시험지 | 비고 |
|---|---|---|
| 판독 | 사업 문서 24건의 본문 3쪽 | 세 엔진 공통 처리 23건으로 어절 F1 산출 |
| 규정 검색 | 규정 청크마다 27B로 만든 합성 질의 29,271건(10-18 회차) | 방식 비교용(질의가 자기 청크를 찾는 구조라 절대치는 낙관적) |
| 검색 모델 학습 | 문서 단위 홀드아웃(리랭커 12문서) | 같은 문서의 질의는 학습·평가 중 한쪽에만 포함 |
| GraphRAG | 그래프에서 추출한 절 질문 73문, 관계 질문 75문, 답변 36문 | 세 방식의 같은 시험지 비교 |
| 생성 모델 기준 | v1 80문(답변 10), v2 136문(답변 30) | 모델 교체 시 같은 방식의 후보 모델 비교 |
| 실서식 작성 | 공개 국고사업 서식(지방대학 특성화 사업계획서 단독형) 등 서식 4종 | 운영 서버의 실제 27B 사용 |

| 공동 편집 | 헤드리스 크롬으로 접속한 시험 계정 세 개, 실제 기안기 세 창 | 로컬 앱과 운영 기안기 서버 |

[표 5-1] 시험지와 측정 도구

검색과 생성 모델 시험지는 대부분 합성 질의(synthetic query)이거나 그래프에서 자동으로 추출한 질문이다. 따라서 방식 간 상대 비교에는 적합하지만,
실제 담당자 질문에서의 절대 성능을 그대로 나타내지는 않는다. 시험은 임시 DB에서 수행했고 운영 데이터는 읽기만 했다. 시험지 원문과 결과 원자료는
개인정보와 교내 문서를 포함할 수 있어 저장소 밖에 두고, 저장소에는 집계 결과와 해석만 남겼다.

## 5.2 문서 수집과 OCR

판독은 정확도와 처리량을 함께 고려하여 엔진을 나누어 사용하기로 했고, 수집(ingestion) 품질은 검색 점수와 별도로 관리해야 함을 확인했다.

### 5.2.1 OCR 엔진 비교

스캔 PDF는 Writer 27B의 이미지 판독이 가장 정확했지만 느려서, 대량 처리에는 MinerU를 사용하고 짧은 스캔 문서에만 27B를 사용한다. 판독(OCR) 품질이
이후 검색과 인용의 정확도를 좌우하므로 엔진을 정하기 전에 후보를 비교했다. 사업 문서 24건(사업마다 1건, 본문 3쪽)을 세 엔진으로 판독하고,
세 엔진이 모두 처리한 23건에서 어절 F1(word-level F1)[^c5-f1]과 쪽당 처리 시간을 측정했다. 결과는 [표 5-2]와 같다.

[^c5-f1]: 어절 F1은 판독 결과와 원문을 어절 단위로 비교해 구한 정밀도와 재현율의 조화 평균이다. 1에 가까울수록 원문과 일치한다.

| 엔진 | 어절 F1 평균 | 쪽당 시간(초) |
|---|---|---|
| Writer 27B 이미지 판독 | 0.839 | 165(서빙 장비, 다른 작업과 병행) |
| MinerU[21][22](한국어 OCR) | 0.690 | 7.6(학습 장비 GPU) |
| docling[23](기본 OCR) | 0.334 | 5.5.2 |

[표 5-2] 스캔 판독 엔진 비교

docling은 깨진 한국어 출력이 텍스트 분량 검사를 통과하는 문제가 있어 제외했다. 정확도와 처리량이 서로 상충하므로 엔진 하나를 선택하기보다
문서의 양과 종류에 따라 나누어 사용하는 편이 낫다고 판단했다. 디지털 PDF는 판독하지 않고 원본의 텍스트 레이어를 글자 좌표와 함께 추출한다.

### 5.2.2 수집 충실도와 분류

수집 과정을 개선하여 화면 표시와 인용의 충실도는 크게 향상되었지만 검색 점수는 달라지지 않았다. 수집 개선의 목적은 검색 점수가 아니라 화면 표시,
인용, 문서 간 연결의 충실도다. 개선 후 서류 종류가 없는 문서는 192건에서 1건으로, 공개 수집 문서의 개인정보 잔여는 208건에서 0건으로,
쪽 번호가 없는 문서는 10건에서 2건으로 줄었다. 같은 합성 질의(09-22, 1,023건, 리랭커 표본 300)로 다시 측정한 운영 구성(하이브리드 검색과 리랭커, 5.3.1절)의 R@1(정답 청크가 1위에 오른 질의의 비율)은 0.707로,
직전 측정값 0.723과의 차이가 실행 간 변동 폭(±0.013) 수준이었다. 본문 품질이 좋아져도 검색 점수가 그대로였으므로, 수집 품질은 검색 점수와
별도의 지표로 관리한다.

수집 규모는 4.1절 [표 4-2]와 같다. 서류 종류에서 27B 판정이 규칙 판정과 다른 11,823건(판정한 29,444건의 약 40%)은 표본 확인에서 대부분 27B의 판정이 옳았고, 사업 파일 단위 재판정에서는
1,034건 가운데 734건의 사업을 변경했다. 사람이 매긴 정답 대비 정확도는 두 판정 모두 미측정이다. 업로드한 문서가 어떤 문서인지 판별하는
작업은 추론 모드(thinking mode)를 끄자 건당 약 100초에서 약 10초로 줄었고, 다시 판별한 708건 가운데 695건에서 결과를 얻었다. 학교 원본은 원본 대장으로
추적하며 선별해 수집했고, 지난 문서의 한글 양식은 특정 파일을 지목하는 규칙 없이 대장과 본문에서 측정한 값만으로 공통 양식과 지난 사업 문서로 나누었다.

## 5.3 검색 품질

검색 정확도를 높인 요인은 규정 검색에서는 리랭커, 사업 문서 검색에서는 사업 구조로 범위를 좁히는 그래프 단계였다.

### 5.3.1 규정 검색

규정 검색에서는 하이브리드 검색에 리랭커를 더한 운영 구성이 모든 단독 방식보다 정확했고, 그 차이는 대부분 리랭커의 재정렬에서 비롯되었다.
규정 질문에 대한 답변의 품질이 이 단계에서 결정되므로 가장 먼저 측정했다. 규정 청크(chunk)마다 27B로 만든 합성 질의를 입력해 원래 청크가 몇 위에
오는지를 R@k[^c5-rk]로 측정하고, 어휘 검색, 임베딩(KURE-v1[33]) 검색, 둘을 RRF[38]로 결합한 하이브리드 검색, 하이브리드 후보 20개를 리랭커(reranker,
Rerank v1, 기반 모델 bge-reranker-v2-m3[35])로 다시 정렬하는 운영 구성을 같은 질의로 비교했다. 회차별 결과는 [표 5-3]과 같다.

[^c5-rk]: R@k(Recall@k)는 정답 청크가 검색 결과 상위 k개 안에 든 질의의 비율이다.

| 측정 | 질의 | 어휘 R@1 | 임베딩 R@1 | 하이브리드 R@1 | 운영 구성 R@1 | 운영 구성 R@5 또는 R@10 |
|---|---|---|---|---|---|---|
| 09-21 | 1,026(운영 구성 표본 300) | 0.430 | 0.691 | 0.671 | 0.763 | R@10 0.927 |
| 10-18 | 29,271(운영 구성 표본 300) | 0.423 | 0.621 | 0.606 | 0.740 | R@5 0.857 |

[표 5-3] 규정 검색 운영 구성의 회차별 값

하이브리드 검색만으로는 임베딩 단독보다 R@1이 다소 낮았지만, 리랭커를 더한 운영 구성은 두 회차 모두 모든 단독 방식보다 높았다.
10-18 회차는 같은 규정이 버전만 달리하여 여러 번 등록된 경우 같은 본문도 정답으로 인정하도록 채점 방식을 수정한 뒤의 값이다. 이 채점 보정만으로
리랭커 적용 후 R@1이 0.707에서 0.760으로 올랐으므로(10-15, 학습 문서를 제외한 합성 질의 22,084건 중 고정 표본 600건, 같은 후보), 09-21과 10-18의
차이(0.763 → 0.740)는 검색 개선 폭으로 해석하지 않는다. 같은 10-15 표본에서 어휘 검색 가중치를 0~0.6으로 바꾸어도 리랭커 적용 후 R@1 차이는
600건 중 3~4건에 그쳐 가중치 0.4를 유지했다.

검색 학습 모델 가운데 리랭커는 홀드아웃(held-out)에서 기반 모델보다 우수하여 채택했다(4.3절 [표 4-5]). 임베딩은 첫 시험 학습 모델(09-03, 홀드아웃 질의
96건)의 R@1이 기반 모델보다 낮아(0.271 → 0.219) 배포하지 않았고, 채택 기준을 바꾸어 다시 학습한 Embed v2를 운영 규정 색인에 사용한다. 공개 모델
KURE-v2로 임베딩을 교체한 구성은 리랭커 적용 후 R@1이 0.743으로, 같은 표본의 운영 구성 0.737과 300건 중 2건 차이여서 도입하지 않았다(09-22,
합성 질의 1,023건 중 표본 300건).

남은 오답은 대부분 시행일·부칙처럼 어느 규정에나 있는 조문을 묻거나 규정 이름을 밝히지 않은 합성 질의였다. 이러한 질의는 사람이 보아도
정답 조문을 하나로 정하기 어렵다. 다만 합성 질의는 원래 청크의 표현과 비슷해지기 쉬워 절대치가 실제보다 높게 나왔을 수 있다.

### 5.3.2 사업 문서 검색과 벡터 색인

사업·연도·문서를 지목하는 질문은 그래프 단계만으로 정답 문서 적중이 18%에서 64%로 올랐고, 사업 간 관계를 묻는 질문은 27B의 질문 해석이
더해져야 전문 검색을 넘어섰다. 같은 사업이 해마다 비슷한 문서를 남기므로, 단순 전문 검색에서는 연도나 사업이 다른 유사 문서가 먼저 검색되기 쉽다.
이에 AURA는 온톨로지 그래프로 사업·연차·서류 종류를 먼저 좁힌 뒤 하이브리드 검색을 수행한다. 그래프 단계의 효과를 확인하기 위해 같은 시험지에서
그래프 단계만 바꾼 세 구성을 비교했다. A는 그래프 단계를 끈 전문 검색 RAG, B는 사업·문서 이름 일치로 범위를 좁히는 그래프 검색, C는 B에
27B의 질문 해석을 더해 사업 간 관계까지 탐색하는 구성이다. 검색 단계는 정답 문서@k[^c5-dk]로, 답변 단계는 근거의 정답 문서 포함 비율[^c5-gold]과
근거 밖 숫자(ungrounded number)[^c5-ungr]로 평가했으며, 결과는 [표 5-4]와 같다.

[^c5-dk]: 정답 문서@k는 사업 문서 검색에서 정답 문서가 상위 k개 안에 든 질문의 비율이다. 절 질문은 k=5, 관계 질문은 k=6으로 측정하였다.
[^c5-gold]: 모델에 실제로 제공한 근거 목록에 정답 문서가 포함된 답변의 비율이다.
[^c5-ungr]: 답변에 사용된 숫자 가운데 모델에 제공한 근거에 없는 숫자의 수다. 코드가 대조해 세며, 「(근거 확인 필요)」로 표시한 숫자는 제외한다.

C는 A보다 답변 한 건에 12.5초가 더 걸렸지만(중앙값 42.3초 대 29.8초) 근거의 정답 문서 비율과 정답성이 높아, 27B 질문 해석을 운영에 적용했다.
정답성은 어느 방식의 답변인지 알 수 없게 한 LLM 판정자(LLM-as-a-judge)[73] 세 개가 판정했고, 10문에 대한 사람 판정과 모두 1점 이내로 일치했다.

이후 두 가지 개선을 따로 측정했다. 먼저 계획서와 그에 대응하는 실적보고서를 서로 다른 문서로 고르게 포함하도록 수정하자, C의 관계 질문 적중률이 46.7%에서
58.7%로 올랐다(검색만 측정, 재순위 꺼짐). 이 실험의 기준선 46.7%는 [표 5-4]의 45%와 같은 시험지를 개선 직전에 다시 측정한 별도 회차의 값이다.
다음으로 질문에 포함된 문서 이름을 절 이름이나 연차로 잘못 해석하던 문제를 수정하자, 문서 이름을 포함한 질문의 정답 문서 비율이 53.8%에서
70.0%가 되었다(10-15, 절 질문 시험지 80문, 상위 5위). 이 절의 결론은 행정 문서 검색에서는 사업 구조를 이용한 범위 제한이 효과적이고, 관계를 묻는
질문에는 모델의 질문 해석이 필요하다는 것이다. 다만 시험지가 그래프에서 자동으로 추출한 질문이어서 그래프 방식에 유리할 수 있다.

한편 사업 문서 벡터를 pgvector 근사 색인으로 옮겨도 검색 품질은 유지되었고 자원 사용은 줄었다. GPU가 없는 운영 서버에서 벡터를 메모리 배열로
유지하면 부담이 크므로, 이를 PostgreSQL pgvector[40]의 HNSW[41] 색인으로 옮기고 이전 전후를 같은 시험지로 비교했다. 정답 문서 적중은 1문 이내의
차이로 유지되었고, 검색 시간은 절반 가까이 줄었으며, 운영 서버 메모리에서 5GB가 넘는 배열이 제거되었다(수치는 4.3절 [표 4-5]).

### 5.3.3 생성 모델 비교

후보 모델을 같은 조건에서 비교한 결과, 교체 여부를 가른 것은 매개변수 수보다 플랫폼이 요구하는 출력 형식의 준수 여부였다. AURA는 실제 도입 시
더 큰 모델로 교체하는 것을 전제로 하므로, 검색·답변·서류 종류 판정을 한 번에 측정하는 모델 교체 기준을 만들고, 모호한 문항과 삭제된 정답을 수정한
v2 시험지를 확정했다. v2의 검색 단계 정답 문서@k(136문)는 89%였고, 답변 결과(답변 30문의 답변 시간 중앙값 16.6초 등)는 4.5절 [표 4-8]에 실었다.

같은 도구로 운영 모델 Writer 27B와 gpt-oss:120b를 비교했다(11-11, v1 시험지). 27B가 근거 밖 숫자를 제외한 모든 항목에서 앞섰고, 이 회차의 답변 시간
중앙값도 40.2초로 gpt-oss의 153.7초보다 짧았다. gpt-oss는 정해진 형식의 종류 판정 50건을 모두 실패하여 운영 모델은 교체하지 않았다. 이 비교는
답변 10문이 포함된 v1 시험지 결과여서 표본이 작고, 답변 시간도 v2 기준(16.6초)과 시험지가 달라 직접 비교하지 않는다.

## 5.4 답변·문서 작성 품질

문서 작성에서는 근거 밖 숫자를 표시 없이 출력하지 않게 되었고, 절 단위 위임과 개요·자기 점검으로 긴 서식과 재작성 요청을 처리할 수 있게 되었다.
남은 약점은 회차마다 달라지는 모델의 판단이다.

### 5.4.1 답변의 근거 정확성

행정 문서에서 근거 없는 숫자는 허위 기재로 이어질 수 있으므로, 수치 검증기가 답변의 숫자를 근거와 대조해 근거에 없는
숫자에 「(근거 확인 필요)」를 표시하고, 답변 형식은 「핵심 먼저, 요점 5개 이내, 600자 안팎」으로 정한다. 이 상태에서 표시되지 않은 근거 밖 숫자는 0건이다.
결과는 4.5절 [표 4-8]과 같다. 답변 작성에서 추론 모드를 켜면 블라인드 채점(blind evaluation) 평균이 0.875에서 0.333으로 떨어지고 속도는
평균 7배 느려졌다(같은 질문 24쌍 가운데 나빠짐 12쌍, 나아짐 0쌍). 따라서 답변 작성에서는 추론 모드를 끈 상태로 둔다.

### 5.4.2 긴 서식 작성과 양식 생성

같은 27B를 새 문맥으로 호출해 절을 위임하자 긴 사업계획서에서 작성된 절이 0에서 21까지 늘었으나, 위임 여부의 판단은 회차마다 달랐다. 수십 쪽 분량의
사업계획서를 끝까지 작성할 수 있는지 확인하기 위해 실서식 사업계획서(지방대학 특성화 사업계획서 단독형, 이 회차 작업본 기준 절 47개)로 작성된 절[^c5-sec]의 수를
측정했다. 한 문맥에서 모든 절을 처리하면 문맥이 길어져 작성이 중간에 멈췄다. 필요할 때 절을 위임하는 방식을 도입하자,
작성된 절이 「항상 직접 작성」 설정의 0/47에서 한 회차에 21/47까지 늘었다. 그러나 다른 회차에서는 한 번만 위임하여 1/47에 그쳤으므로, 평균 효과를 말하려면
표본을 더 모아야 한다. 소요 시간도 3~4배로 늘었다.

[^c5-sec]: 작성된 절은 서식에서 작성해야 할 절 가운데 에이전트가 실제로 채운 절의 수다.

양식 생성에서는 맞는 양식이 없어도 27B가 양식 설계와 첫 작성까지 안정적으로 수행했지만, 재작성 요청의 반영이 가장 약했다. 27B가 양식부터 설계한 뒤
내용을 작성하고 담당자의 수정 요청을 반영하는 11턴 대화를 회차별로 측정했다. 마지막 회차에서 생성한 양식의 구조 점수는 8/8, 작성된 절은 10/10이었고,
서식 깨짐은 0건, 디자인 요청 4건은 모든 버전에 반영되었다. 반면 「더 구체적으로」 같은 재작성 요청은 1/6만 반영되었다.

### 5.4.3 재작성·자기 점검과 SFT 결과

개요와 자기 점검 단계를 도입하자 재작성 반영과 근거 점수가 가장 크게 올랐고, 대신 작성 시간이 약 18% 늘었다. 5.4.2에서 드러난 재작성의
약점을 보완하는 장치는 사례별 규칙이 아닌 일반 메커니즘이다. 재작성 전용 도구를 두고, 하위 절을 작성할 때 [개요] → [본문] → 자기 점검 순서를 거치게 하며,
문단 끝에 근거 출처를 적게 했다. 이 기능을 끈 이전 버전과 같은 시나리오로 3회씩 비교했으며(운영 서버, 작성과 채점 모두 Writer 27B),
작성방법 반영과 재작성 반영[^c5-rev], 지어낸 숫자[^c5-fab], 채점 점수[^c5-rub]를 측정했다. 결과는 [표 5-5]와 같다.

[^c5-rev]: 작성방법 반영은 서식의 작성방법이 요구한 표·도식·출처가 실제로 들어갔는지의 여부이고, 재작성 반영은 「더 구체적으로」 요청 뒤 해당 절의 분량이 1.15배를 넘게 늘었는지의 여부다. 둘 다 코드가 계산한다.
[^c5-fab]: 지어낸 숫자는 작업본 본문의 숫자 가운데 근거나 담당자 입력에 없는 숫자의 수다. 단위만 다른 같은 금액은 같은 값으로 간주한다.
[^c5-rub]: 채점 점수는 같은 27B가 채점 기준표(rubric)에 따라 구체성·논리·문체·근거를 5점 만점으로 매긴 값으로, 버전 비교에만 사용한다.

재작성 반영은 1/3에서 3/3으로 늘었고, 근거 점수는 0.63점 올랐다. 디자인 지시 반영(12/12)과 서식 깨짐(0건)은 두 버전이 같았다. 버전마다 3회만 측정했고
채점이 같은 27B의 자기 평가이므로, 기본 설정은 회차를 더 모은 뒤 정한다.

SFT는 학습 형식의 답변 품질을 뚜렷이 높였지만, 학습쌍이 한 가지 형식뿐이어서 에이전트 단계의 요청에는 맞지 않았다. SFT는 더 큰 모델에 적용하기
위한 실험으로, 교내 실문서로 만든 학습 절차와 데이터가 실제로 효과가 있는지를 27B에서 먼저 확인하는 데 목적이 있다. Writer 27B에 교내 실문서
학습쌍 4,434쌍으로 LoRA[17] SFT를 수행하고, 병합한 모델을 운영과 같은 NVFP4로 양자화한 뒤 학습 전 모델과 비교했다(방법은 4.10절). 학습이 서빙 모델에
반영되었는지는 정답 토큰당 평균 로그확률(log-probability)[^c5-lp]로 먼저 확인하고, 생성 품질은 시험 문항 정답과의 겹침(chrF·ROUGE-L)과
코드가 세는 숫자·잘림 지표로 비교했다. 결과는 [표 5-6]과 같다.

로그확률이 -1.845에서 -1.153으로 올라 학습 결과가 서빙 모델에 반영된 것을 확인했고, 코드가 세는 지표는 모두 SFT 모델이 우수했다. 특히 답변 길이가
정답의 1.81배에서 0.96배로 줄어 불필요하게 길게 작성하던 경향이 개선되었다. 항목별 채점 점수는 두 모델 모두 5점에 가까워 변별력이 낮았다. 채점 모델에게
두 답변 가운데 나은 답변을 선택하게 하면 학습 전 모델의 답변을 더 자주 선택했으나(220문 중 SFT 답변이 이김 28·비김 80·짐 112, 비김을 반으로 계산한 점수 30.9%), 채점 모델이 학습 전 모델과 같은 기반 모델이고
긴 답변을 선호하는 경향이 있어 이 값으로 우열을 가리지 않았다. 문서 작성 시나리오에서는 SFT 병합 모델이 작업본을 생성하지 못했다(학습 전 2/2 → 0/2).
학습쌍이 질문→답변 한 가지 형식뿐이어서 에이전트 단계의 요청에도 학습한 형식으로 답했기 때문이다. 따라서 더 큰 모델에서는 플랫폼이 실제로 보내는
요청 형식을 학습 데이터에 고르게 포함한다(4.10절, 6.3.2절).

## 5.5 응답 속도

공동 편집에서 글자가 다른 화면에 나타나기까지의 지연과, 생성 모델의 서빙 속도를 차례로 제시한다.

### 5.5.1 공동 편집 지연

영역 단위 편집권 설계는 동시 입력, 연결 끊김, 문서 구조 변경, 실제 기안기 세 창 동시 입력에서 글자를 잃지 않았고, 글자 지연(latency)은 약 0.2초였다.
확인할 사항은 세 가지였다. 한 사람이 입력한 글이 다른 사람 화면에 얼마나 빨리 나타나는지, 여러 사람이 동시에 입력하거나 연결이 끊겨도 글이 사라지지 않는지,
AURA가 사람과 같은 문서에 작성할 때도 같은 규칙이 지켜지는지다. 로컬 앱과 운영 기안기 서버를 연결하고, 화면 없이 동작하는 브라우저인 헤드리스 크롬으로
시험 계정 세 개를 동시에 접속시켜 글자 지연[^c5-lat]을 측정했다. 한글 입력은 자모 조합 단계(ㄱ → 기 → 김)를 재현해 입력했다. 마지막 두 시험은 실제
기안기 창에서 수행했다. 아래 표에서 A와 B는 서로 다른 시험 사용자다. 결과는 [표 5-7]과 같다.

[^c5-lat]: 글자 지연은 한 화면에서 확정한 글자가 다른 화면에 나타나기까지의 시간이다. 중앙값, 상위 90% 값, 최댓값으로 보고한다.

글자 지연의 중앙값은 변경을 모아 보내는 간격(300ms)보다 짧아, 사용자는 사실상 실시간으로 상대의 입력을 보게 된다. 실제 기안기에서 세 사람이 빠르게, Enter를 섞어,
AURA가 다른 절을 작성하는 동안 동시에 입력해도 글자는 누락되지 않았다. AURA의 작성은 사람보다 느리게 반영되는데, 이는 서버 프로세스 사이의
알림을 1초 주기로 확인하는 구조 때문이며 6.3.3절의 개선 과제로 남겼다. 큰 문서(합성 451쪽, 편집 영역 942개)에서도 긴 절 끝의 입력 지연은 142ms다.
줄바꿈을 기준으로 문단 단위로 나누고 바뀐 부분만 주고받기 때문이며, 절 전체를 한 덩어리로 주고받던 초기 구조에서는 1,727ms였다. 지연 수치는 헤드리스 크롬에서 측정한 값이므로 실제 사용자
환경의 네트워크 조건은 반영하지 않는다.

### 5.5.2 서빙 속도

NVFP4 양자화와 MTP 추측 디코딩을 거쳐 27B의 생성 속도는 bf16 대비 약 5~10배가 되었고, 품질 저하는 관찰되지 않았다. 온프레미스 구성은 상용
클라우드보다 연산 자원이 적으므로, 교내 장비에서 대화형으로 사용할 수 있는 속도가 나오는지가 중요하다. 27B는 젯슨 AGX 토르[13] 두 대에서
vLLM[10]으로 서빙하며, 정밀도와 디코딩 방식을 바꾸어 가며 초당 토큰(tokens per second)[^c5-tps]과 대표 작업의 소요 시간을 측정했다. 결과는 [표 5-8]과 같다.

[^c5-tps]: 초당 토큰은 요청 하나를 처리할 때 모델이 1초에 생성하는 토큰 수다.

| 구성 | 초당 토큰(요청 1건) | 판독 5쪽 소요 시간(초) | 검토 1건 소요 시간(초) |
|---|---|---|---|
| bf16 원본 | 2.4~4.5 | 128 | 225 |
| NVFP4[14] 양자화 | 10.4~10.8 | 29 | 82 |
| NVFP4 + MTP[15] 추측 디코딩[16](검토 장비) | 10.6 → 23.8(2.25배, 평균 수용 길이 2.2) | 미측정 | 미측정 |
| NVFP4 + MTP 추측 디코딩(답변 장비) | 약 12 → 24.6 | 미측정 | 미측정 |

[표 5-8] 27B 서빙 정밀도와 추측 디코딩

NVFP4 양자화로 초당 토큰이 bf16의 2.4~4.5에서 10.4~10.8로 오르고 판독·검토 시간이 크게 줄었으며, MTP 추측 디코딩(speculative decoding)을 더하자
다시 약 두 배가 되었다. NVFP4 모델의 판독 결과는 bf16과 같았고, 추측 디코딩은 출력 분포를 바꾸지 않으며, 실제로 적용한 뒤에도 종류 판정 표본의
규칙 일치율(92%)과 답변 근거의 정답 문서 비율이 변하지 않았다. 답변 전체 시간의 단축(4.5절 [표 4-8])은 답변 형식 정리와 추측 디코딩이 함께 만든 결과여서
두 요인의 기여를 따로 나누지 않았다. 이 속도는 한 번에 요청 하나를 보낸 측정값이므로, 여러 사용자가 동시에 요청할 때의 지연은 별도로 측정해야 한다.

### 5.6.1 실물 검증 사례

지표 측정과 별도로 실제 서식과 실제 수집 경로에서 전 과정을 실행하여, 에이전트가 빈 서식의 입력란 구조를 읽고 채울 수 있으며 완성본이 원본 서식을
유지한다는 것을 확인했다. 측정 절차가 틀린 수치를 산출한 사례는 5.7절 끝에서 다룬다.

공개 국고사업 서식(지방대학 특성화 사업계획서 단독형)을 운영 서버에서 실제 27B 에이전트로 채웠다. 짧은 서식(예산 변경·출장 보고·기안문)은
모든 절을 채웠지만, 긴 사업계획서는 한 번의 요청으로 절 41개 가운데 17개를 작성한 뒤 멈췄다. 지어낸 숫자는 0건이었다. 5.4.2와 같은 서식이지만
측정 회차마다 작업본에서 센 절 수가 달라(이 회차 41절, 절 단위 위임 비교 47절) 두 회차의 작성된 절 수는 직접 비교하지 않는다. 이 한계가 5.4.2의

### 5.6.2 시연 결과

시연은 담당자의 업무 순서(공동 편집, 대화형 문서 작업, 질문과 근거 확인, 개발 현황)에 따라 구현한 기능이 실제 화면에서 연결되는지를 보여 준다.
모든 화면은 시험 환경(시험 계정, 가상의 부서·인물·사업, 공통 양식, 공개 공고 서식)에서 촬영하여 학교 내부 문서나 개인정보를 포함하지 않는다.

관리자 화면의 공동 편집 시연은 같은 빈 문서를 세 화면으로 나란히 열고, 세 사람이 절을 동시에 작성하는 동안 「AURA 양식 만들기」와 「AURA 이어 쓰기」로
27B가 양식과 빈 절을 작성해 세 화면에 함께 나타나는 과정을 보여 준다(4.7절 [그림 4-13]·[그림 4-12]). 시연 주제는 설정에서 선택하며,
가상 사업계획서와 신규 교직원 연수 결과 보고서 두 가지를 제공한다.

채팅 화면은 왼쪽에 에이전트 대화, 오른쪽에 웹 한글 기안기 작업본을 배치하며, 에이전트가 작성하는 편집 영역에는 AURA와 요청한 사람의 이름표가 표시된다
(1장 [그림 1-1]). 아래 [그림 5-3]은 에이전트가 공통 양식에 추진 체계 도식과 추진 일정 표를 작성한 결과로, 문장뿐 아니라 도식과 표도
대화 요청만으로 문서에 넣을 수 있다.

## 5.7 평가의 한계

가장 큰 한계는 시험지가 실제 담당자 질문이 아니라는 점이다. 규정 검색은 합성 질의로 자기 청크를 찾는 측정이어서 절대치가 낙관적이고,
GraphRAG와 모델 교체 기준 v2는 그래프에서 자동으로 추출한 질문이다. 사람이 만든 골드셋(gold set)으로 측정한 값은 아직 없다.

표본도 작다. 기준 v2의 답변은 30문이고 문서 작성 시나리오는 버전마다 3회여서, 회차 간 차이가 버전 간 차이만큼 클 수 있다. 문서 작성 채점과
SFT 비교의 우열 판정은 같은 27B 계열 모델이 매겼으므로 버전 비교에만 사용했고, 사람 판정은 GraphRAG 10문 대조에 그친다. 서류 종류 판정과
사업 재판정의 사람 정답 대비 정확도는 미측정이다. 개인정보 잔여 0건은 정규식 검사 결과이며 완전한 제거를 뜻하지 않는다.

공동 편집 지연 수치는 헤드리스 크롬에서 측정한 값뿐이고, 실제 기안기 세 창 시험에서는 글자 누락 여부만 확인했다. 서빙 속도는 대부분 한 번에 요청 하나를 보낸 측정이어서 동시 부하 상황의 지연은 미측정이다.

끝으로, 측정 절차가 틀린 수치를 산출한 사례도 세 번 있었다. 운영 설정을 읽지 않은 측정에서 리랭커와 임베딩이 CPU용 기반 모델로 경고 없이 대체되어 운영 구성 값이
0.1 낮게 나왔고, 재색인 때 색인 모델과 질의 모델이 일치하지 않았으며, SFT 어댑터가 서빙 모델에 적용되지 않았다. 세 경우 모두 수치만으로는 이상을
알아차리기 어려웠고, 실제로 답한 모델을 함께 기록하는 절차를 도입한 뒤에 발견했다.
