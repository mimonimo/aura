# 5. 평가 및 결과

이 장에서는 AURA가 행정 문서 업무에 활용할 수 있을 만큼 정확하고 빠른지, 그리고 그 성능이 어느 구성 요소에서 나오는지를 단계별로 확인한다.
측정 결과를 요약하면, 스캔 문서 판독은 정확도와 처리량을 함께 고려해 엔진을 나누어 사용하게 되었다. 검색 정확도를 높인 것은 주로 리랭커와
사업 구조 그래프였다. 문서 작성에서는 근거에 없는 수치가 표시 없이 들어간 경우가 0건이었고, 긴 서식도 끝까지 작성할 수 있게 되었다.
공동 편집과 서빙 속도는 교내 장비에서 대화형으로 사용하기에 충분한 수준이었다. 수치는 측정 프로그램이 남긴 결과 파일과 측정 기록에 있는 값만
사용하였다. 측정하지 않은 항목은 「미측정」, 기록을 확인하지 못한 항목은 「미확인」으로 적었다. 측정 연도는 모두 2026년이며, 같은 지표라도
측정 시점이나 표본이 다르면 값 옆에 측정일과 표본을 함께 적었다.

## 5.1 평가 방법

평가는 같은 평가 데이터셋끼리만 비교하였고, 코드가 계산한 지표를 주 근거로 삼았다.

### 5.1.1 평가 원칙과 지표

구성을 바꾸기 전에는 같은 평가 데이터셋(benchmark)으로 현재 구성을 측정해 기준선(baseline)을 정하고, 바꾼 뒤 같은 방식으로 다시 측정했다.
측정은 운영 연결 설정을 읽어 실행하고, 실제로 답한 모델과 운영 모델 대신 다른 모델로 대체 실행된 횟수를 함께 기록했다. 이 기록이 필요했던 이유는 5.7절에서 설명한다. 평가 데이터셋을 수정하면 버전(version) 번호를 올리고
기준선을 다시 측정해, 같은 버전의 평가 데이터셋끼리만 비교했다. 근거에 없는 수치, 정답 문서 적중, 서식 깨짐처럼 코드가 세는 지표를 주 근거로 삼았고,
언어 모델 채점은 버전 비교용 보조 지표로만 사용했다. 같은 구성을 반복 측정하여 실행 간 변동보다 큰 차이만 의미 있는 차이로 해석했다.

지표는 문서 처리의 판독 정확도, 검색 정확도, 답변과 작성 결과의 근거 충실도, 공동 편집 지연, 서빙 속도로 나뉜다. 각 지표의 정의는 처음 나오는
문장의 각주로 제시한다.

### 5.1.2 평가 데이터셋과 측정 도구

평가 대상별 평가 데이터셋은 [표 5-1]과 같다. 모든 측정은 저장소에 포함된 측정 프로그램으로 다시 실행해 재현할 수 있다.

| 구분 | 평가 데이터셋 | 비고 |
|---|---|---|
| 판독 | 사업 문서 24건의 본문 3쪽 | 세 엔진이 모두 처리한 23건으로 어절 F1 계산 |
| 규정 검색 | 규정 청크마다 27B로 만든 합성 질의 29,271건(10-18 측정) | 방식 비교용. 질의가 자신을 만든 청크를 다시 찾는 구조여서 절대치가 실제보다 높게 나오는 경향 |
| 검색 모델 학습 | 문서 단위 홀드아웃(리랭커 12문서) | 같은 문서에서 나온 질의는 학습과 평가 가운데 한쪽에만 포함 |
| GraphRAG | 그래프에서 추출한 절 질문 73문, 관계 질문 75문, 답변 36문 | 세 방식을 같은 평가 데이터셋으로 비교 |
| 생성 모델 기준 | v1 80문(답변 10), v2 136문(답변 30) | 모델 교체 때 후보 모델을 같은 방식으로 비교 |
| 실서식 작성 | 공개 국고사업 서식(지방대학 특성화 사업계획서 단독형) 등 서식 4종 | 운영 서버의 실제 27B 사용 |
| 문서 작성 시나리오 | 「양식 없이 시작」 11턴 대화 | 임시 DB와 실제 27B 사용, 버전마다 3회 |
| SFT 전후 비교 | 학습셋에서 분리해 둔 시험 220문항, 맥락 30문항 | 모델 외 조건은 동일 |
| 공동 편집 | 헤드리스 크롬으로 접속한 시험 계정 세 개, 실제 기안기 세 창 | 로컬 앱과 운영 기안기 서버 |

[표 5-1] 평가 데이터셋과 측정 도구

검색과 생성 모델 평가 데이터셋은 대부분 합성 질의(synthetic query)이거나 그래프에서 자동으로 추출한 질문이다. 따라서 방식 간 상대 비교에는 적합하지만,
실제 담당자 질문에서의 절대 성능을 그대로 나타내지는 않는다. 시험은 임시 DB에서 수행했고 운영 데이터는 읽기만 했다. 평가 데이터셋 원문과 결과 원자료는
개인정보와 교내 문서를 포함할 수 있어 저장소 밖에 두고, 저장소에는 집계 결과와 해석만 남겼다.

## 5.2 문서 수집과 OCR

판독은 정확도와 처리량을 함께 고려하여 엔진을 나누어 사용하기로 했고, 수집(ingestion) 품질은 검색 점수와 별도로 관리해야 함을 확인했다.

### 5.2.1 OCR 엔진 비교

스캔 PDF는 Writer 27B의 이미지 판독이 가장 정확했으나 처리 속도가 느렸다. 그래서 대량 처리에는 MinerU를 사용하고 짧은 스캔 문서에만 27B를 사용한다. 판독(OCR) 품질이
이후 검색과 인용의 정확도를 좌우하므로 엔진을 정하기 전에 후보를 비교했다. 사업 문서 24건(사업마다 1건, 본문 3쪽)을 세 엔진으로 판독하고,
세 엔진이 모두 처리한 23건에서 어절 F1(word-level F1)[^c5-f1]과 쪽당 처리 시간을 측정했다. 결과는 [표 5-2]와 같다.

[^c5-f1]: 어절 F1은 판독 결과와 원문을 어절 단위로 비교해 구한 정밀도와 재현율의 조화 평균이다. 1에 가까울수록 원문과 일치한다.

| 엔진 | 어절 F1 평균 | 쪽당 시간(초) |
|---|---|---|
| Writer 27B 이미지 판독 | 0.839 | 165(서빙 장비, 다른 작업과 병행) |
| MinerU[21][22](한국어 OCR) | 0.690 | 7.6(학습 장비 GPU) |
| docling[23](기본 OCR) | 0.334 | 5.6 |

[표 5-2] 스캔 판독 엔진 비교

docling은 한국어가 깨진 출력도 텍스트 분량 검사를 통과해 판독 실패를 걸러 낼 수 없었으므로 제외했다. 정확도와 처리량이 서로 상충하므로 엔진 하나를 선택하기보다
문서의 양과 종류에 따라 나누어 사용하는 편이 낫다고 판단했다. 디지털 PDF는 판독하지 않고 원본의 텍스트 레이어를 글자 좌표와 함께 추출한다.

### 5.2.2 수집 충실도와 분류

수집 과정을 개선한 결과 화면 표시와 인용의 충실도는 크게 향상되었으나 검색 점수는 달라지지 않았다. 이 개선은 처음부터 화면 표시, 인용,
문서 간 연결의 충실도를 높이기 위한 것이었다. 개선 후 서류 종류가 비어 있는 문서는 192건에서 1건으로, 공개 수집 문서 가운데 개인정보가 남은
문서는 208건에서 0건으로, 쪽 번호가 없는 문서는 10건에서 2건으로 줄었다. 운영 구성은 하이브리드 검색에 리랭커를 더한 구성이며 5.3.1절에서
설명한다. 같은 합성 질의(09-22, 1,023건, 리랭커 표본 300)로 이 구성을 다시 측정한 R@1(정답 청크가 1위에 오른 질의의 비율)은 0.707이었다.
직전 측정값 0.723과의 차이는 같은 구성을 반복 측정할 때 생기는 변동 폭(±0.013)과 비슷한 수준이었다. 본문 품질이 좋아져도 검색 점수가
그대로였으므로, 수집 품질은 검색 점수와 별도의 지표로 관리한다.

수집 규모는 4.1절 [표 4-2]와 같다. 서류 종류를 판정한 29,444건 가운데 27B의 판정이 기존 규칙 판정과 다른 문서는 11,823건(약 40%)이었다.
이 가운데 일부를 표본으로 확인한 결과 대부분 27B의 판정이 옳았다. 문서가 속한 사업을 파일 단위로 다시 판정한 결과에서는 1,034건 가운데
734건의 사업이 바뀌었다. 사람이 정한 정답과 비교한 정확도는 두 판정 모두 미측정이다. 업로드한 문서가 어떤 문서인지 판별하는 작업은
추론 모드(thinking mode, 답하기 전에 생각 과정을 먼저 생성하는 방식)를 끄자 건당 약 100초에서 약 10초로 줄었고, 다시 판별한 708건 가운데
695건에서 결과를 얻었다. 학교 원본은 원본 대장으로 목록을 관리하면서 필요한 문서를 선별해 수집했다. 지난 문서의 한글 양식은 특정 파일을
지목하는 규칙을 두지 않고, 대장 정보와 본문에서 측정한 값만으로 공통 양식과 지난 사업 문서로 구분했다.

## 5.3 검색 품질

검색 정확도를 높인 요인은 규정 검색에서는 리랭커, 사업 문서 검색에서는 사업 구조로 범위를 좁히는 그래프 단계였다.

### 5.3.1 규정 검색

규정 검색에서는 하이브리드 검색에 리랭커를 더한 운영 구성이 모든 단독 방식보다 정확했고, 그 차이는 대부분 리랭커의 재정렬에서 비롯되었다.
규정 질문 답변의 품질이 이 단계에서 결정되므로 가장 먼저 측정했다. 규정 청크(chunk)마다 27B로 만든 합성 질의를 입력해 원래 청크가 몇 위에
오는지를 R@k[^c5-rk]로 측정하고, 어휘 검색, 임베딩(KURE-v1[33]) 검색, 둘을 RRF[38]로 결합한 하이브리드 검색, 하이브리드 후보 20개를 리랭커(reranker,
Rerank v1, 기반 모델 bge-reranker-v2-m3[35])로 다시 정렬하는 운영 구성을 같은 질의로 비교했다. 측정 시점별 결과는 [표 5-3]과 같다.

[^c5-rk]: R@k(Recall@k)는 정답 청크가 검색 결과 상위 k개 안에 든 질의의 비율이다.

| 측정 | 질의 | 어휘 R@1 | 임베딩 R@1 | 하이브리드 R@1 | 운영 구성 R@1 | 운영 구성 R@5 또는 R@10 |
|---|---|---|---|---|---|---|
| 09-21 | 1,026(운영 구성 표본 300) | 0.430 | 0.691 | 0.671 | 0.763 | R@10 0.927 |
| 10-18 | 29,271(운영 구성 표본 300) | 0.423 | 0.621 | 0.606 | 0.740 | R@5 0.857 |

[표 5-3] 규정 검색 운영 구성의 측정별 값

하이브리드 검색만으로는 임베딩 단독보다 R@1이 다소 낮았지만, 리랭커를 더한 운영 구성은 두 측정 모두 모든 단독 방식보다 높았다.
10-18 측정은 같은 규정이 버전만 달리하여 여러 번 등록된 경우 같은 본문도 정답으로 인정하도록 채점 방식을 수정한 뒤의 값이다. 10-15에 학습
문서를 제외한 합성 질의 22,084건 가운데 고정 표본 600건으로 확인해 보면, 검색 후보는 그대로 두고 이 채점 보정만 적용해도 리랭커 적용 후
R@1이 0.707에서 0.760으로 올랐다. 따라서 09-21과 10-18 측정의 차이(0.763 → 0.740)는 검색 성능의 변화로 해석하지 않는다. 같은 10-15 표본에서
어휘 검색 가중치를 0에서 0.6 사이로 바꾸어 보았으나 리랭커 적용 후 R@1은 600건 가운데 3~4건만큼만 달라졌으므로 가중치는 0.4를 유지했다.

학습한 검색 모델 가운데 리랭커는 학습에 사용하지 않은 문서로 만든 홀드아웃(held-out) 평가에서 기반 모델보다 우수하여 채택했으며, 수치는 4.3절
[표 4-5]와 같다. 임베딩 모델은 처음 학습한 시험 모델의 R@1이 홀드아웃 질의 96건에서 기반 모델보다 낮았으므로(09-03, 0.271 → 0.219) 배포하지
않았다. 이후 채택 기준을 바꾸어 다시 학습한 Embed v2를 운영 규정 색인에 사용한다. 공개 모델 KURE-v2로 임베딩을 교체한 구성도 09-22 합성 질의
1,023건 가운데 표본 300건으로 비교했다. 리랭커 적용 후 R@1은 0.743으로 같은 표본의 운영 구성 0.737과 300건 가운데 2건 차이에 그쳐 도입하지 않았다.

남은 오답은 대부분 시행일·부칙처럼 어느 규정에나 있는 조문을 묻거나 규정 이름을 밝히지 않은 합성 질의였다. 이러한 질의는 사람이 보아도
정답 조문을 하나로 정하기 어렵다. 다만 합성 질의는 원래 청크의 표현과 비슷해지기 쉬워 절대치가 실제보다 높게 나왔을 수 있다.

### 5.3.2 사업 문서 검색과 벡터 색인

사업·연도·문서를 지목하는 질문은 그래프 단계만으로 정답 문서 적중이 18%에서 64%로 올랐고, 사업 간 관계를 묻는 질문은 27B의 질문 해석이
더해져야 전문 검색을 넘어섰다. 같은 사업이 해마다 비슷한 문서를 남기므로, 단순 전문 검색에서는 연도나 사업이 다른 유사 문서가 먼저 검색되기 쉽다.
이에 AURA는 온톨로지 그래프로 사업·연차·서류 종류를 먼저 좁힌 뒤 하이브리드 검색을 수행한다. 그래프 단계의 효과를 확인하기 위해 같은 평가 데이터셋에서
그래프 단계만 바꾼 세 구성을 비교했다. A는 그래프 단계를 끈 전문 검색 RAG, B는 사업·문서 이름 일치로 범위를 좁히는 그래프 검색, C는 B에
27B의 질문 해석을 더해 사업 간 관계까지 탐색하는 구성이다. 검색 단계는 정답 문서@k[^c5-dk]로, 답변 단계는 근거의 정답 문서 포함 비율[^c5-gold]과
근거에 없는 수치(ungrounded number)[^c5-ungr]로 평가했으며, 결과는 [표 5-4]와 같다.

[^c5-dk]: 정답 문서@k는 사업 문서 검색에서 정답 문서가 상위 k개 안에 든 질문의 비율이다. 절 질문은 k=5, 관계 질문은 k=6으로 측정하였다.
[^c5-gold]: 모델에 실제로 제공한 근거 목록에 정답 문서가 포함된 답변의 비율이다.
[^c5-ungr]: 답변에 사용된 숫자 가운데 모델에 제공한 근거에 없는 숫자의 수다. 코드가 대조해 세며, 「(근거 확인 필요)」로 표시한 숫자는 제외한다.

| 지표 | A 전문 검색 | B 그래프 | C 그래프 + 27B 질문 해석 |
|---|---|---|---|
| 절 질문: 정답 문서가 상위 5위 안에 든 비율(73문) | 18%(13문) | 64%(47문) | 70%(51문) |
| 관계 질문: 정답 문서가 상위 6위 안에 든 비율(75문) | 13% | 9% | 45% |
| 검색 1회 소요 시간(중앙값, 초) | 1.21 | 1.58 | 6.45 |
| 근거에 정답 문서가 포함된 답변의 비율(36문) | 31% | 53% | 75% |
| 근거에 없는 수치(전체 숫자 대비) | 1/152 | 1/111 | 0/169 |
| 답변 1건 소요 시간(중앙값, 초) | 29.8 | 37.7 | 42.3 |
| 블라인드 판정의 정답성 평균(0~2점) | 0.36 | 0.75 | 0.92 |

[표 5-4] 전문 검색 RAG와 GraphRAG 비교(10-14)

관계 질문은 B에서 오히려 9%로 떨어졌다. 이름 일치만으로는 질문 문장에 담긴 사업 간 관계를 파악하지 못한 것이 원인으로 보인다. 10-14 측정에서
C는 A보다 답변 한 건에 12.5초가 더 걸렸지만(중앙값 42.3초 대 29.8초) 근거의 정답 문서 비율과 정답성이 높아, 27B 질문 해석을 운영에 적용했다.
정답성은 답변이 어느 방식에서 나왔는지 알리지 않은 상태에서 LLM 판정자(LLM-as-a-judge)[73] 세 개가 판정했다. 10문은 사람이 따로 판정해
비교했으며, 모든 문항에서 두 판정의 차이가 1점 이내였다.

이후 두 가지 개선을 따로 측정했다. 먼저 검색 결과에 계획서와 그에 대응하는 실적보고서가 서로 다른 문서로 고르게 들어가도록 수정했다. 재순위
없이 검색 단계만 측정한 결과 C의 관계 질문 적중률이 46.7%에서 58.7%로 올랐다. 이 실험의 기준선 46.7%는 [표 5-4]의 45%와 같은 평가 데이터셋을
개선 직전에 다시 측정한 값이어서 두 값이 조금 다르다. 다음으로 질문에 포함된 문서 이름을 절 이름이나 연차로 잘못 해석하던 문제를 수정했다.
10-15에 절 질문 평가 데이터셋 80문으로 측정한 결과, 문서 이름이 들어간 질문에서 정답 문서가 상위 5위 안에 든 비율이 53.8%에서 70.0%로 올랐다.
이상의 결과로 볼 때 행정 문서 검색에서는 사업 구조를 이용해 범위를 좁히는 방법이 효과적이며, 관계를 묻는 질문에는 모델의 질문 해석이 필요하다.
다만 평가 데이터셋이 그래프에서 자동으로 추출한 질문이어서 그래프 방식에 유리하게 나왔을 수 있다.

한편 사업 문서 벡터를 pgvector의 근사 최근접 이웃 색인으로 옮겨도 검색 품질은 유지되었고 자원 사용은 줄었다. GPU가 없는 운영 서버에서 벡터를
메모리 배열로 유지하면 부담이 크므로, 이를 PostgreSQL pgvector[40]의 HNSW[41] 색인으로 옮기고 이전 전후를 같은 평가 데이터셋으로 비교했다.
정답 문서 적중은 1문 이내의 차이로 유지되었고, 검색 시간은 절반 가까이 줄었으며, 운영 서버 메모리에 5GB가 넘는 배열을 둘 필요가 없어졌다.
세부 수치는 4.3절 [표 4-5]에 제시하였다.

### 5.3.3 생성 모델 비교

후보 모델을 같은 조건에서 비교한 결과, 교체 여부를 가른 것은 매개변수 수보다 플랫폼이 요구하는 출력 형식의 준수 여부였다. AURA는 실제 도입 시
더 큰 모델로 교체하는 것을 전제로 하므로, 검색·답변·서류 종류 판정을 한 번에 측정하는 모델 교체 기준을 만들고, 모호한 문항과 삭제된 정답을 수정한
v2 평가 데이터셋을 확정했다. v2 136문에서 검색 단계의 정답 문서@k는 89%였다. 답변 30문의 결과는 답변 시간 중앙값 16.6초를 포함해 4.5절 [표 4-8]에 실었다.

같은 도구로 운영 모델 Writer 27B와 gpt-oss:120b를 비교했다(11-11, v1 평가 데이터셋). 27B가 근거에 없는 수치를 제외한 모든 항목에서 앞섰고, 이 측정의 답변 시간
중앙값도 40.2초로 gpt-oss의 153.7초보다 짧았다. gpt-oss는 정해진 형식으로 답해야 하는 서류 종류 판정 50건에서 모두 형식을 지키지 못했으므로
운영 모델은 교체하지 않았다. 이 비교는 답변이 10문뿐인 v1 평가 데이터셋의 결과여서 표본이 작다. 답변 시간 역시 v2 기준의 16.6초와는
평가 데이터셋이 달라 직접 비교하지 않는다.

## 5.4 답변·문서 작성 품질

문서 작성에서는 근거에 없는 수치를 표시 없이 출력하지 않게 되었고, 절 단위 위임과 개요 작성, 자기 점검을 도입해 긴 서식과 재작성 요청을 처리할 수 있게 되었다.
남은 약점은 실행마다 달라지는 모델의 판단이다.

### 5.4.1 답변의 근거 정확성

행정 문서에서 근거 없는 숫자는 허위 기재로 이어질 수 있으므로, 수치 검증기가 답변의 숫자를 근거와 대조해 근거에 없는
숫자에 「(근거 확인 필요)」를 표시하고, 답변 형식은 「핵심 먼저, 요점 5개 이내, 600자 안팎」으로 정한다. 이 상태에서 표시 없이 출력된 근거에 없는 수치는 0건이다.
결과는 4.5절 [표 4-8]과 같다. 답변 작성에서 추론 모드를 켜면 어느 설정의 답변인지 알리지 않고 채점하는 블라인드 채점(blind evaluation)의 평균이
0.875에서 0.333으로 떨어지고, 속도는 평균 7배 느려졌다. 같은 질문 24쌍을 두 설정으로 비교하면 12쌍에서 결과가 나빠졌고 나아진 것은 0쌍이었다.
이는 측정 당시 서빙 컨텍스트 길이(16,384토큰) 안에서 추론 과정이 답변에 쓸 토큰을 먼저 차지한 결과로 판단된다. 서류 종류 판정에서도 출력
한도를 추론에 모두 사용해 결과 없이 끝난 호출이 713건이었다. 따라서 답변 작성에서는 추론 모드를 끈 상태로 둔다. 현재 서빙 컨텍스트 길이는
262,144토큰이며, 이 설정에서의 재비교는 미측정이다.

### 5.4.2 긴 서식 작성과 양식 생성

같은 27B를 새 컨텍스트로 호출해 절을 위임한 결과 긴 사업계획서에서 작성된 절이 0에서 21까지 늘었으나, 위임 여부의 판단은 실행마다 달랐다. 수십 쪽 분량의
사업계획서를 끝까지 작성할 수 있는지 확인하기 위해 실서식 사업계획서(지방대학 특성화 사업계획서 단독형, 이 측정의 작업 문서 기준 절 47개)로 작성된 절[^c5-sec]의 수를
측정했다. 한 컨텍스트에서 모든 절을 처리하면 컨텍스트가 길어져 작성이 중간에 멈췄다. 그래서 에이전트가 필요하다고 판단할 때 절 작성을 새
컨텍스트의 27B 호출에 넘기는 방식을 도입했다. 그 결과 작성된 절이 「항상 직접 작성」 설정의 0/47에서 한 실행에 21/47까지 늘었다. 그러나
다른 실행에서는 한 번만 위임하여 1/47에 그쳤으므로, 평균적인 효과를 판단하려면 측정을 더 반복해야 한다. 소요 시간도 3~4배로 늘었다.

[^c5-sec]: 작성된 절은 서식에서 작성해야 할 절 가운데 에이전트가 실제로 채운 절의 수다.

양식 생성에서는 맞는 양식이 없어도 27B가 양식 설계와 첫 작성까지 안정적으로 수행했지만, 재작성 요청의 반영이 가장 약했다. 27B가 양식부터 설계한 뒤
내용을 작성하고 담당자의 수정 요청을 반영하는 11턴 대화를 여러 차례 측정했다. 마지막 측정에서 생성한 양식의 구조 점수는 8/8, 작성된 절은 10/10이었고,
서식 깨짐은 0건, 디자인 요청 4건은 모든 버전에 반영되었다. 반면 「더 구체적으로」 같은 재작성 요청은 6번 가운데 1번만 반영되었다.

### 5.4.3 재작성·자기 점검과 SFT 결과

개요와 자기 점검 단계를 도입한 결과 재작성 반영과 근거 점수가 가장 크게 올랐고, 대신 작성 시간이 약 18% 늘었다. 5.4.2에서 드러난 재작성의
약점은 특정 사례에 맞춘 규칙을 덧붙이지 않고, 모든 절 작성에 공통으로 적용되는 절차로 보완했다. 재작성 전용 도구를 두고, 하위 절은 [개요] → [본문] → 자기 점검
순서로 작성하게 하며, 문단 끝에 근거 출처를 적게 했다. 이 기능을 끈 이전 버전과 같은 시나리오로 3회씩 비교했다. 측정은 운영 서버에서 수행했고
작성과 채점은 모두 Writer 27B가 맡았다. 측정 항목은 작성방법 반영과 재작성 반영[^c5-rev], 지어낸 숫자[^c5-fab], 채점 점수[^c5-rub]이며, 결과는 [표 5-5]와 같다.

[^c5-rev]: 작성방법 반영은 서식의 작성방법이 요구한 표·도식·출처가 실제로 들어갔는지의 여부이고, 재작성 반영은 「더 구체적으로」 요청 뒤 해당 절의 분량이 1.15배를 넘게 늘었는지의 여부다. 둘 다 코드가 계산한다.
[^c5-fab]: 지어낸 숫자는 작업 문서 본문의 숫자 가운데 근거나 담당자 입력에 없는 숫자의 수다. 단위만 다른 같은 금액은 같은 값으로 간주한다.
[^c5-rub]: 채점 점수는 같은 27B가 채점 기준표(rubric)에 따라 구체성·논리·문체·근거를 5점 만점으로 매긴 값으로, 버전 비교에만 사용한다.

| 항목 | 개선 버전(3회) | 이전 버전(3회) |
|---|---|---|
| 작성된 절 | 21/21 | 17/17 |
| 작성방법이 요구한 표·도식·출처의 반영 | 19/20 | 17/20 |
| 「더 구체적으로」 재작성 반영 | 3/3 | 1/3 |
| 지어낸 숫자(건) | 0 | 0 |
| 채점 평균(구체성·논리·문체·근거, 5점 만점) | 2.94·3.39·3.89·3.33 | 2.83·3.19·3.89·2.70 |
| 평균 소요 시간(초)·평균 모델 호출 수(회) | 924·73 | 782·62 |

[표 5-5] 개선 버전과 이전 버전 비교

재작성 반영은 1/3에서 3/3으로 늘었고, 근거 점수는 0.63점 올랐다. 디자인 지시 반영(12/12)과 서식 깨짐(0건)은 두 버전이 같았다. 버전마다 3회만 측정했고
채점이 같은 27B의 자기 평가이므로, 기본 설정은 측정을 더 반복한 뒤 정한다.

SFT는 학습 형식의 답변 품질을 뚜렷이 높였지만, 학습쌍이 한 가지 형식뿐이어서 에이전트 단계의 요청에는 맞지 않았다. SFT는 더 큰 모델에 적용하기
위한 실험으로, 교내 실문서로 만든 학습 절차와 데이터가 실제로 효과가 있는지를 27B에서 먼저 확인하는 데 목적이 있다. Writer 27B에 교내 실문서
학습쌍 4,434쌍으로 LoRA[17] SFT를 수행하고, 병합한 모델을 운영과 같은 NVFP4로 양자화한 뒤 학습 전 모델과 비교했다. 학습 방법은 4.10절에서 설명하였다.
학습이 서빙 모델에 반영되었는지는 정답 토큰당 평균 로그확률(log-probability)[^c5-lp]로 먼저 확인했다. 생성 품질은 시험 문항 정답과 글자·단어가
얼마나 겹치는지를 나타내는 chrF와 ROUGE-L, 그리고 코드가 세는 질문에 없는 숫자와 잘린 답변의 비율로 비교했다. 결과는 [표 5-6]과 같다.

[^c5-lp]: 정답 토큰당 평균 로그확률은 정답 글을 모델에 입력했을 때 토큰마다 매긴 확률의 로그 평균이다. 생성 없이 측정하므로 샘플링에 따른 변동이 없으며, 값이 0에 가까울수록 모델이 정답 글을 자연스럽게 여긴다는 뜻이다.

로그확률이 -1.845에서 -1.153으로 올라 학습 결과가 서빙 모델에 반영된 것을 확인했고, 코드가 세는 지표는 모두 SFT 모델이 우수했다. 특히 답변 길이가
정답의 1.81배에서 0.96배로 줄어 불필요하게 길게 작성하던 경향이 개선되었다. 항목별 채점 점수는 두 모델 모두 5점에 가까워 변별력이 낮았다. 채점 모델에게
두 답변 가운데 나은 답변을 고르게 하면 학습 전 모델의 답변이 더 자주 선택되었다. 220문 가운데 SFT 답변이 이긴 것은 28문, 비긴 것은 80문,
진 것은 112문이었고, 비긴 경우를 반 승으로 계산한 점수는 30.9%였다. 그러나 채점 모델이 학습 전 모델과 같은 기반 모델이고 긴 답변을 선호하는
경향이 있어 이 값으로 우열을 가리지 않았다. 문서 작성 시나리오에서는 학습 전 모델이 두 번 모두(2/2) 작업 문서를 생성한 반면, SFT 병합 모델은
한 번도 생성하지 못했다(0/2). 학습쌍이 질문과 답변으로 이루어진 한 가지 형식뿐이어서, 에이전트가 다음 작업을 JSON으로 정하는 단계의 요청에도
학습한 답변 형식으로 응답했기 때문이다. 따라서 더 큰 모델에서는 플랫폼이 실제로 보내는 요청 형식을 학습 데이터에 고르게 포함할 계획이며,
그 방법은 4.10절과 6.3.2절에서 다룬다.

## 5.5 응답 속도

공동 편집에서 글자가 다른 화면에 나타나기까지의 지연과, 생성 모델의 서빙 속도를 차례로 제시한다.

### 5.5.1 공동 편집 지연

영역 단위 편집권 방식에서는 동시 입력, 연결 끊김, 문서 구조 변경, 실제 기안기 세 창 동시 입력의 어느 경우에도 입력한 글자가 사라지지 않았고, 글자 지연(latency)은 약 0.2초였다.
확인할 사항은 세 가지였다. 한 사람이 입력한 글이 다른 사람 화면에 얼마나 빨리 나타나는지, 여러 사람이 동시에 입력하거나 연결이 끊겨도 글이 사라지지 않는지,
AURA가 사람과 같은 문서에 작성할 때도 같은 규칙이 지켜지는지다. 로컬 앱과 운영 기안기 서버를 연결하고, 화면 없이 동작하는 브라우저인 헤드리스 크롬으로
시험 계정 세 개로 동시에 접속해 글자 지연[^c5-lat]을 측정했다. 한글은 자모가 조합되는 단계(ㄱ → 기 → 김)를 그대로 재현해 입력했다. 마지막 두 시험은 실제
기안기 창에서 수행했다. 아래 표에서 A와 B는 서로 다른 시험 사용자다. 결과는 [표 5-7]과 같다.

[^c5-lat]: 글자 지연은 한 화면에서 확정한 글자가 다른 화면에 나타나기까지의 시간이다. 중앙값, 상위 90% 값, 최댓값으로 보고한다.

| 화면 폭이 다른 세 창(1440·1000·570px)과 같은 사용자의 둘째 창에서 입력 | 글자당 지연 중앙값 204~216ms, 글자 누락 없음 |

글자 지연의 중앙값은 변경을 모아 보내는 간격(300ms)보다 짧아, 사용자는 사실상 실시간으로 상대의 입력을 보게 된다. 실제 기안기에서도 AURA가
다른 절을 작성하는 동안 세 사람이 Enter를 섞어 가며 빠르게 동시에 입력했으나 글자는 누락되지 않았다. AURA가 작성한 내용은 서버 프로세스
사이의 알림을 1초 주기로 확인하는 구조여서 사람의 입력보다 늦게 반영되며, 이 점은 6.3.3절의 개선 과제로 남겼다. 합성으로 만든 451쪽 문서
(편집 영역 942개)에서도 긴 절 끝에서의 입력 지연은 142ms였다. 절을 줄바꿈 기준의 문단 단위로 나누어 바뀐 문단만 주고받도록 한 결과이며,
절 전체를 한 덩어리로 주고받던 초기 구조에서는 같은 지연이 1,727ms였다. 지연 수치는 헤드리스 크롬에서 측정한 값이므로 실제 사용자 환경의
네트워크 조건은 반영되지 않았다.

### 5.5.2 서빙 속도

NVFP4 양자화와 MTP 추측 디코딩을 적용한 결과 27B의 생성 속도는 bf16 원본의 약 5~10배가 되었고, 품질 저하는 관찰되지 않았다. NVFP4는 모델
가중치를 4비트 부동소수점으로 줄여 저장하고 계산하는 양자화 형식이다. MTP 추측 디코딩은 모델이 다음 몇 토큰을 미리 예측해 두고 본 모델이
이를 한 번에 검증하여 생성 속도를 높이는 방법이다. 온프레미스 구성은 상용
클라우드보다 연산 자원이 적으므로, 교내 장비에서 대화형으로 사용할 수 있는 속도가 나오는지가 중요하다. 27B는 젯슨 AGX 토르[13] 두 대에서
vLLM[10]으로 서빙하며, 정밀도와 디코딩 방식을 바꾸어 가며 초당 토큰(tokens per second)[^c5-tps]과 대표 작업의 소요 시간을 측정했다. 결과는 [표 5-8]과 같다.

[^c5-tps]: 초당 토큰은 요청 하나를 처리할 때 모델이 1초에 생성하는 토큰 수다.

| 구성 | 초당 토큰(요청 1건) | 판독 5쪽 소요 시간(초) | 검토 1건 소요 시간(초) |
|---|---|---|---|
| bf16 원본 | 2.4~4.5 | 128 | 225 |
| NVFP4[14] 양자화 | 10.4~10.8 | 29 | 82 |
| NVFP4 + MTP[15] 추측 디코딩[16](검토 장비) | 10.6 → 23.8(2.25배, 평균 수용 길이 2.2) | 미측정 | 미측정 |
| NVFP4 + MTP 추측 디코딩(답변 장비) | 약 12 → 24.6 | 미측정 | 미측정 |

[표 5-8] 27B 서빙 정밀도와 추측 디코딩

NVFP4 양자화로 초당 토큰이 bf16의 2.4~4.5에서 10.4~10.8로 오르고 판독·검토 시간이 크게 줄었으며, MTP 추측 디코딩(speculative decoding)을 더하자
다시 약 두 배가 되었다. 표의 평균 수용 길이는 한 번의 검증에서 받아들여진 토큰 수의 평균이다. NVFP4 모델의 판독 결과는 bf16과 같았다.
추측 디코딩은 원리상 출력 분포를 바꾸지 않으며, 실제로 적용한 뒤에도 종류 판정 표본의 규칙 일치율(92%)과 답변 근거의 정답 문서 비율이 변하지 않았다. 답변 전체 시간의 단축(4.5절 [표 4-8])은 답변 형식 정리와 추측 디코딩이 함께 만든 결과여서
두 요인의 기여를 따로 나누지 않았다. 이 속도는 한 번에 요청 하나를 보낸 측정값이므로, 여러 사용자가 동시에 요청할 때의 지연은 별도로 측정해야 한다.

### 5.6.1 실물 검증 사례

### 5.6.2 시연 결과

## 5.7 평가의 한계

가장 큰 한계는 평가 데이터셋이 실제 담당자의 질문으로 만들어지지 않았다는 점이다. 규정 검색은 합성 질의가 자신을 만든 청크를 다시 찾는
측정이어서 절대치가 실제보다 높게 나왔을 수 있고, GraphRAG와 모델 교체 기준 v2는 그래프에서 자동으로 추출한 질문이다. 사람이 직접 질문과
정답을 정한 평가 데이터셋인 골드셋(gold set)으로 측정한 값은 아직 없다.

표본도 작다. 기준 v2의 답변은 30문이고 문서 작성 시나리오는 버전마다 3회여서, 실행 간 차이가 버전 간 차이만큼 클 수 있다. 문서 작성 채점과
SFT 비교의 우열 판정은 같은 27B 계열 모델이 매겼으므로 버전 비교에만 사용했고, 사람 판정은 GraphRAG 10문 대조에 그친다. 서류 종류 판정과
사업 재판정의 사람 정답 대비 정확도는 미측정이다. 개인정보가 남은 문서 0건은 정규식 검사로 찾은 결과이므로, 개인정보가 완전히 제거되었다는 뜻은 아니다.

공동 편집 지연 수치는 헤드리스 크롬에서 측정한 값뿐이고, 실제 기안기 세 창 시험에서는 글자 누락 여부만 확인했다. 서빙 속도는 대부분 한 번에 요청 하나를 보낸 측정이어서 동시 부하 상황의 지연은 미측정이다.

끝으로, 측정 절차 자체가 틀린 수치를 만들 수 있다는 점도 한계로 확인되었다. 운영 설정을 읽지 않은 측정에서는 리랭커와 임베딩이 경고 없이 CPU용
기반 모델로 대체되어 운영 구성 값이 0.1 낮게 나왔다. 재색인할 때 색인 모델과 질의 모델이 일치하지 않은 경우와 SFT 어댑터가 서빙 모델에 적용되지
않은 경우에도 수치가 틀렸다. 세 경우 모두 수치만으로는 이상을 알아차리기 어려웠으며, 실제로 답한 모델을 함께 기록하는 절차를 도입하고 나서야 찾아냈다.
