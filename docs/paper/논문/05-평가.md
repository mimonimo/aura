# 5. 평가 및 결과

이 장은 AURA 각 단계를 무엇으로 쟀고 결과가 어떤지를 정리한다. 수치는 저장소의 측정 기록(실험 로그, ADR, 개발 현황 문서, 측정 결과 파일)에
있는 값만 쓰고, 재지 않은 것은 「미측정」, 기록을 확인하지 못한 것은 「미확인」으로 둔다. 측정 일자는 모두 2026년이다.

## 5.1 평가 방법

### 5.1.1 평가 원칙

평가는 프로젝트의 평가 계획과 품질 기준을 따른다.

- 기준선 먼저: 바꾸기 전에 같은 시험지로 현재 구성을 재어 두고, 바꾼 뒤 같은 실행으로 다시 잰다.
- 운영 설정으로: 운영 연결 설정을 읽고 띄우며, 실제로 답한 모델과 대체 실행 수를 함께 기록한다(5.7.4).
- 같은 시험지끼리: 시험지를 고치면 판 번호를 올리고 기준선을 다시 잰다.
- 코드가 세는 지표 우선: 근거 밖 숫자, 정답 문서 적중, 서식 깨짐을 주 근거로 하고 언어 모델 채점은 판 비교용 보조 지표로만 쓴다.
- 잡음 폭 확인: 같은 구성을 반복해 흔들림보다 큰 차이만 차이로 읽는다.

### 5.1.2 지표 정의

이 장의 표에 쓰는 지표는 [표 5-1]과 같다.

| 대상 | 지표 | 정의 |
|---|---|---|
| 검색 | R@k (Recall@k) | 정답 조각이 상위 k 안에 든 질의의 비율 |
| 검색 | 정답 문서@k | 사업 문서 검색에서 정답 문서가 상위 k(절 질문 5, 관계 질문 6) 안에 든 비율 |
| 답 | 근거에 정답 문서 | 모델에 실제로 건넨 근거 묶음에 정답 문서가 든 답의 비율 |
| 답 | 근거 밖 숫자 | 답의 숫자 가운데 모델에 건넨 근거에 없는 것(코드가 셈, 「(근거 확인 필요)」 표시 숫자 제외) |
| 문서 처리 | 어절 F1 | 판독 결과와 원문의 어절 단위 정밀도·재현율의 조화 평균 |
| 문서 작성 | 쓴 절 | 서식의 쓸 자리 가운데 에이전트가 채운 절 수 |
| 문서 작성 | 지어낸 숫자 | 작업본 본문의 숫자 가운데 근거·담당자 글에 없는 것(단위만 바꾼 같은 금액은 같은 값, ADR-0068) |
| 문서 작성 | 작성방법 반영 · 고쳐 쓰기 반영 | 작성방법이 요구한 표·도식·출처의 유무, 「더 구체적으로」 요청 뒤 글이 1.15배 넘게 늘었는지(코드가 셈) |
| 문서 작성 | 채점 점수(5점) | 같은 27B가 기준표로 매긴 구체성·논리·문체·근거(판 비교용) |
| 모델 비교 | chrF · ROUGE-L | 시험 문항 정답과 생성 답의 글자 n-gram F 점수[63], 최장 공통 부분열 F 점수[64] |
| 모델 비교 | 정답 토큰당 평균 로그확률 | 정답 글을 모델에 넣었을 때의 토큰당 평균 로그확률. 생성 없이 재므로 샘플링 잡음이 없고, 학습이 서빙에 들어갔는지 본다 |
| 공동 편집 | 글자 지연 | 한 화면에서 확정한 글자가 다른 화면에 나타나기까지의 시간(중앙값·90%·최대) |
| 서빙 | 초당 토큰 | 요청 하나의 생성 속도 |

### 5.1.3 시험지와 측정 도구

지표마다 쓴 시험지는 [표 5-2]와 같다. 측정은 모두 저장소의 측정 스크립트로 다시 돌릴 수 있다.

| 묶음 | 시험지 | 비고 |
|---|---|---|
| 규정 검색 | 규정 조각마다 27B로 만든 합성 질의(1,026건 → 22,084건 깨끗한 질의 → 29,271건) | 자기 조각 찾기라 절대치 낙관적, 방식 비교용 |
| 검색 학습본 | 문서 단위 홀드아웃(리랭커 12문서) | 같은 문서의 질의는 학습·평가 한쪽에만 |
| GraphRAG | 그래프에서 뽑은 절 질문 73문, 관계 질문 75문, 답 36문 | 세 모드를 같은 시험지로 비교 |
| 생성 모델 기준 | v1 80문(답 10), v2 136문(답 30) | 모델 교체 때 같은 실행으로 후보를 잰다 |
| 판독 | 사업 문서 24건의 본문 3쪽 | 세 엔진 모두 성공한 23건으로 어절 F1 |
| 실서식 작성 | 공개 국고사업 서식(지방대학 특성화 사업계획서 단독형) 등 서식 4종 | 운영 서버에서 실제 27B로 |
| 문서 작성 시나리오 | 「양식 없이 시작」 11턴 대화 | 임시 DB, 실제 27B, 판마다 3회 |
| SFT 전후 비교 | 학습셋에서 떼어 둔 시험 220문항, 맥락 30문항 | 모델만 바꿈 |
| 공동 편집 | 헤드리스 크롬 세 사용자(가짜 계정) | 로컬 앱 + 운영 기안기 서버 |

[표 5-2] 시험지와 측정 도구

시험은 임시 DB에서 하고 운영 데이터는 읽기만 한다. 시험지 원문과 결과 원자료는 개인정보와 교내 문서를 담을 수 있어 저장소 밖에 두고,
저장소에는 집계와 판단만 남겼다.

## 5.2 검색 품질

### 5.2.1 규정 검색

규정 검색은 교내 규정·지침을 조문 단위로 찾는다. 운영 구성은 어휘와 임베딩(KURE-v1[29])을 RRF[35]로 합친 하이브리드에서 후보 20개를 뽑아
리랭커(Rerank v1, 바탕 bge-reranker-v2-m3[32])로 다시 정렬한다. 단독 방식과 운영 구성의 값은 [표 5-3]과 같다.

| 측정 | 질의 | 어휘 R@1 | 임베딩 R@1 | 하이브리드 R@1 | 운영 구성 R@1 | 운영 구성 R@5 · R@10 |
|---|---|---|---|---|---|---|
| 09-21 | 1,026(운영 구성 표본 300) | 0.430 | 0.691 | 0.671 | 0.763 | — · 0.927 |
| 10-18 | 29,271(표본 300) | 0.423 | 0.621 | 0.606 | 0.740 | 0.857 · — |

[표 5-3] 규정 검색 운영 구성 회차별 값(실험 로그 5·20절)

두 회차 모두 리랭커를 얹은 운영 구성이 어느 단독 방식보다 높았다. 10-18 값은 같은 규정이 판본만 달리해 여러 번 등록된 경우 같은 본문도
정답으로 세도록 채점을 고친 뒤의 값이다. 이 보정만으로 같은 후보의 리랭커 뒤 R@1이 0.707에서 0.760으로 올랐으므로(표본 600, 실험 로그
11절) 회차 사이 차이를 검색 개선 폭으로 읽지 않는다. 어휘 가중은 0~0.6에서 리랭커 뒤 R@1차가 600건 가운데 3~4건이라 0.4를 유지했다.

리랭커 학습본은 홀드아웃에서 바탕보다 나아 채택했고(4.3.6절 [표 4-7]), 임베딩 학습본 첫 리허설은 바탕보다 낮아(R@1 0.271 → 0.219) 배포하지
않았다. 공개 KURE-v2는 리랭커 뒤 R@1이 0.737대 0.743으로 운영과 차이가 없어 쓰지 않았다(ADR-0025). 남은 놓침은 대부분 시행일·부칙처럼
어느 규정에나 있는 조문이나 규정 이름을 대지 않은 합성 질의였다.

### 5.2.2 사업 문서 검색과 GraphRAG

사업 문서 검색은 온톨로지 그래프로 사업·연차·서류 갈래를 좁힌 뒤 하이브리드 검색을 한다. 같은 시험지에서 그래프 단계만 바꿔 쟀다(실험 로그
9절). A는 그래프 단계를 끈 전문 검색 RAG, B는 이름 맞추기로 범위를 좁히는 그래프, C는 B에 27B 질문 읽기를 더해 관계를 따라가는 구성이다.

| 지표 | A 전문 검색 | B 그래프 | C 그래프 + 27B 읽기 |
|---|---|---|---|
| 절 질문 정답 문서 상위 5(73문) | 18% (13) | 64% (47) | 70% (51) |
| 관계 질문 전체(75문) | 13% | 9% | 45% |
| 검색 한 번 중앙값 | 1.21초 | 1.58초 | 6.45초 |
| 답 근거에 정답 문서(36문) | 31% | 53% | 75% |
| 근거 밖 숫자 | 1/152 | 1/111 | 0/169 |
| 답 전체 시간 중앙값 | 29.8초 | 37.7초 | 42.3초 |
| 블라인드 판정 정답성 평균(0~2) | 0.36 | 0.75 | 0.92 |

[표 5-4] 전문 검색 RAG와 GraphRAG 비교(10-14)

사업·연도·문서를 지목하는 절 질문은 그래프(B)만으로 정답 문서 적중이 18%에서 64%로 올랐고, 관계 질문은 27B 질문 읽기를 더한 C 에서만
전문 검색을 넘었다. C는 A보다 답 하나에 12.5초를 더 쓰는 대신 근거의 정답 문서 비율과 정답성을 올려, 27B 질문
읽기를 운영에 켰다. 답 판정은 모드를 가린 LLM 판정자[65] 셋이 했고, 10문 사람 판정과 1점 이내로 모두 일치했다.

이어 계획서와 실적보고서 짝을 함께 담도록 고쳐 C의 관계 질문 전체가 46.7%에서 58.7%로 올랐고(실험 로그 9.1절), 질문에 문서 이름을 넣은
경우의 정답 문서 비율은 53.8%에서 70.0%가 됐다(실험 로그 13절).

### 5.2.3 생성 모델 교체 기준

검색·답·갈래 판정을 한 실행으로 재는 모델 교체 기준을 만들고, 모호한 문항과 지워진 정답을 고친 v2 시험지를 확정했다(실험 로그 14·17절). v2
에서 정답 문서@k는 0.89 였고, 답 결과는 4.5.6절 [표 4-11]에 있다. 같은 도구로 운영 모델 Qwen3.8-27B와 gpt-oss:120b를 비교하자(11-11, v1
시험지) 27B가 근거 밖 숫자 한 항목을 빼고 모두 앞섰고, 답 시간 중앙값은 40.2초 대 153.7초였으며, gpt-oss는 정해진 형식의 갈래 판정 50건을
모두 실패해 운영 모델을 바꾸지 않았다.

### 5.2.4 벡터 색인 이전

사업 문서 벡터를 운영 서버 메모리의 배열에서 PostgreSQL pgvector[36]의 HNSW[37] 색인으로 옮겼다(ADR-0057). 정답 문서 적중은 1문 차로 유지되고
검색 시간은 절반 가까이 줄었으며 운영 서버 메모리에서 5GB 넘는 배열이 빠졌다(수치는 4.3.6절 [표 4-7]).

## 5.3 문서 처리(판독·반입)

### 5.3.1 판독 엔진 선택

스캔 PDF 판독 엔진은 사업 문서 24건(사업마다 하나, 본문 3쪽)을 세 엔진으로 읽어 같은 잣대로 골랐다(ADR-0050).

| 엔진 | 어절 F1 평균 | 쪽당 시간 |
|---|---|---|
| Writer 27B 이미지 판독 | 0.839 | 165초(서빙 장비, 다른 일과 겹침) |
| MinerU[19][20](한국어 OCR) | 0.690 | 7.6초(학습 장비 GPU) |
| docling[21](기본 OCR) | 0.334 | 5.6초 |

[표 5-5] 스캔 판독 엔진 비교

27B가 가장 정확했지만 처리량 때문에 대량 처리는 MinerU, 짧은 스캔 문서와 사진은 27B 판독을 쓴다. docling은 깨진 한국어로 「글이 충분하다」
검사를 통과해 버려 뺐다. 디지털 PDF는 판독하지 않고 원본 글자층을 글자 좌표째 읽는다.

### 5.3.2 반입 충실도

반입 단계 개선의 목적은 검색 점수가 아니라 화면·인용·연관의 충실도다. 서류 갈래 없는 문서가 192건에서 1건으로, 공개 수집 문서의 개인정보
잔여가 208건에서 0건으로, 쪽 번호 없는 문서가 10건에서 2건으로 줄었다(ADR-0027). 같은 질의로 다시 잰 운영 구성 R@1은 0.707로 전날(0.723)과 실행 간
흔들림(±0.013) 언저리여서, 본문이 깨끗해져도 검색 값은 그대로였다.

### 5.3.3 반입 문서 규모와 판정

반입 규모는 4.1.6절 [표 4-3]과 같다. 27B 서류 갈래 판정이 규칙과 다른 11,823건은 표본에서 대부분 27B 쪽이 맞았고, 사업 파일 단위 재판정은
1,034건 가운데 734건을 옮겼다. 사람 정답 대비 정확도는 두 판정 모두 미측정이다. 올린 문서의 정체 읽기는 생각 모드를 끄자 한 건이 약 100초에서
약 10초로 줄고 다시 읽은 708건 가운데 695건에 값이 나왔다.

## 5.4 생성·문서 작성 품질

### 5.4.1 답의 근거와 숫자

수치 검증기가 답의 숫자를 근거와 대조해 없는 숫자에 「(근거 확인 필요)」를 붙이고, 답 꼴을 「핵심 먼저, 요점 5개 이내, 600자 안팎」으로
바꿨다. 그 결과는 4.5.6절 [표 4-11]과 같다. 답 쓰기에서 생각 모드를 켜면 블라인드 채점 평균이 0.875에서 0.333으로 떨어지고 평균 7배
느려져(같은 질문 24쌍 가운데 나빠짐 12, 나아짐 0) 끈 채 두었다(실험 로그 12절).

### 5.4.2 긴 서식 작성과 절 맡기기

긴 서식은 한 문맥에서 모든 것을 다루면 중간에 멈췄다. 필요할 때 같은 27B를 깨끗한 문맥으로 불러 절을 맡기자 실서식 사업계획서(절 47)에서
「항상 직접」의 0/47이 한 회차에 21/47까지 늘었다(ADR-0065). 다만 맡길지 고르는 판단이 회차마다 흔들려(다른 회차 1/47) 평균 효과는 표본을
더 모아야 하고, 시간은 3~4배다.

### 5.4.3 양식 만들기와 여러 턴 시나리오

맞는 양식이 없을 때 27B가 양식부터 설계하는 11턴 대화를 회차별로 쟀다(ADR-0067). 마지막 회차에서 만든 양식 구조 점수 8/8, 쓴 절 10/10 이었고,
서식 깨짐은 0, 디자인 요청 넷은 모든 판에 반영됐다. 약점은 고쳐 쓰기(반영 1/6)였다.

### 5.4.4 고쳐 쓰기·개요·자기 점검(ADR-0068)

플랫폼이 실제로 보내는 요청 꼴을 학습 데이터에 넣는다(4.11.5절, 6.3.2절).

## 5.5 공동 편집 지연

웹 한글 기안기의 칸 단위 실시간 공동 편집(ADR-0070)은 로컬 앱과 운영 서버의 기안기 서버, 헤드리스 크롬 세 사용자(가짜 계정)로 쟀다. 한글 조합은
자모 단계(ㄱ → 기 → 김)로 흉내 냈다.

| 시험 | 결과 |
|---|---|
| 한 글자씩 21회, A 확정 → B 화면 | 중앙값 221ms · 90% 299ms · 최대 302ms, 잃은 글자 0 |
| 세 창(1440 · 1000 · 570px) + 같은 사람 둘째 창 | 글자당 지연 중앙값 204~216ms, 잃은 글자 0 |
| 다른 칸 동시 입력 | 서로 보임 3~265ms. 남이 쥔 칸에 친 글자는 들어가지 않음 |
| 칸 넘기기(시험 유예 3초) | B가 잡기까지 3.1~3.8초 |
| 오프라인 중 입력 → 다시 연결 | A 화면까지 19~40ms |
| 다른 프로세스의 AURA 칸 쓰기 | A 화면 863ms(프로세스 사이는 1초 주기 읽기) |
| 구조 고침 저장(표·용지) | B 새 판 389~499ms, 칸 글 유지, 다시 열어 다섯 칸 일치, hwpx 반영, 충돌 0 |
| 화면 깜빡임(11-12, 실제 기안기 헤드리스 둘·셋, 둘 다 치고 Enter) | 4초 동안 화면 튐 24 → 0(고친 뒤 두 번, 세 사람 각 0) |

[표 5-8] 기안기 칸 단위 공동 편집 측정(ADR-0070)

글자 지연은 보내기 간격 300ms 안에서 중앙값 0.2초 남짓이고, 끊김·재연결·동시 입력에서도 잃은 글자가 없었다. 큰 문서(합성 451쪽, 필드 942)는
처음 구조에서 긴 절 끝 입력 지연이 1,727ms 였으나, 줄바꿈을 문단으로 바꾸고 바뀐 부분만 주고받게 고친 뒤 142ms가 됐다.

## 5.6 서빙 속도

생성 모델 27B는 젯슨 AGX 토르[11] 두 대에서 vLLM[9]으로 서빙한다. 정밀도와 디코딩 방식에 따른 속도는 [표 5-9]와 같다.

|---|---|---|---|---|
| bf16 원본 | 2.4~4.5 | 128초 | 225초 | ADR-0023 |
| NVFP4[12] 양자화 | 10.4~10.8 | 29초 | 82초 | ADR-0023 |

| NVFP4 + MTP 추측 디코딩(답 장비) | 약 12 → 24.6 | — | — | 실험 로그 16절 |

[표 5-9] 27B 서빙 정밀도와 추측 디코딩

NVFP4판은 판독 내용이 bf16과 같았다. 추측 디코딩은 출력 분포를 바꾸지 않으며, 켠 뒤에도 갈래 판정 표본의 규칙 일치(0.92)와 답 근거의 정답
문서 비율이 같았다. 답 전체 시간 단축(4.5.6절 [표 4-11])은 답 꼴 정리와 추측 디코딩이 함께 낸 결과라 둘을 가르지 않았다.

어긋난 일, SFT 어댑터가 서빙에 붙지 않은 일이 있었다. 모두 값만으로는 그럴듯했고, 실제로 답한 모델을 함께 기록하는 절차로 잡혔다.

## 5.9 평가의 한계

- 시험지. 규정 검색은 합성 질의로 자기 조각을 찾는 측정이라 절대치가 낙관적이고, GraphRAG와 기준 v2는 그래프에서 뽑은 질문이다. 사람이 쓴
  골드셋으로 잰 값은 아직 없다.
- 표본 크기. 기준 v2의 답은 30문, 문서 작성 시나리오는 판마다 3회라 회차 차이가 판 차이만큼 클 수 있다.
- 자기 채점. 문서 작성 채점과 SFT 비교의 나은 답 고르기는 같은 27B 계열이 매겨 판 비교에만 썼다. 사람 판정은 GraphRAG 10문 대조뿐이다.
- 정확도 미측정. 서류 갈래 판정과 사업 재판정의 사람 정답 대비 정확도는 미측정이다.
- 개인정보. 잔여 0은 정규식 검사 결과이며 완전 제거를 뜻하지 않는다.
- 공동 편집. 지연은 헤드리스 크롬 측정이고, 실브라우저 세 칸 동시 편집은 동작만 확인했다.
- 서빙. 속도는 대부분 한 번에 한 요청을 보낸 측정이라 동시 부하 지연은 미측정이다.
