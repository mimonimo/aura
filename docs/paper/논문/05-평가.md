# 5. 평가 및 결과

이 장에서는 AURA가 행정 문서 업무에 활용할 수 있을 만큼 정확하고 빠른지, 그리고 그 성능이 어느 구성 요소에서 나오는지를 단계별로 확인한다.
측정 결과를 요약하면, 스캔 문서 판독은 정확도와 처리량을 함께 고려해 엔진을 나누어 사용하게 되었다. 검색 정확도를 높인 것은 주로 리랭커와
사업 구조 그래프였다. 문서 작성에서는 근거에 없는 수치가 표시 없이 들어간 경우가 0건이었고, 긴 서식도 끝까지 작성할 수 있게 되었다.
공동 편집과 서빙 속도는 교내 장비에서 대화형으로 사용하기에 충분한 수준이었다. 수치는 측정 프로그램이 남긴 결과 파일과 측정 기록에 있는 값만
사용하였다. 측정하지 않은 항목은 「미측정」, 기록을 확인하지 못한 항목은 「미확인」으로 적었다. 측정 연도는 모두 2026년이며, 같은 지표라도
측정 시점이나 표본이 다르면 값 옆에 측정일과 표본을 함께 적었다.

## 5.1 평가 방법

평가에서는 같은 평가 데이터셋으로 측정한 값끼리만 비교하였고, 코드가 계산한 지표를 주 근거로 삼았다.

### 5.1.1 평가 원칙과 지표

구성을 바꾸기 전에는 같은 평가 데이터셋(benchmark)으로 현재 구성을 측정해 기준선(baseline)을 정하고, 바꾼 뒤 같은 방식으로 다시 측정했다.
측정은 운영 연결 설정을 읽어 실행하고, 실제로 답한 모델과 운영 모델 대신 다른 모델로 대체 실행된 횟수를 함께 기록했다. 이 기록이 필요했던 이유는 5.7절에서 설명한다. 평가 데이터셋을 수정하면 버전(version) 번호를 올리고
기준선을 다시 측정해, 같은 버전의 평가 데이터셋으로 측정한 값끼리만 비교했다. 근거에 없는 수치, 정답 문서 적중, 서식 깨짐처럼 코드가 세는 지표를 주 근거로 삼았고,
언어 모델 채점은 실행마다 점수가 흔들리고 채점 모델의 취향이 섞이므로 버전 비교용 보조 지표로만 사용했다. 같은 구성을 반복 측정하여 실행 간 변동보다 큰 차이만 의미 있는 차이로 해석했다.

지표는 문서 처리의 판독 정확도, 검색 정확도, 답변과 작성 결과의 근거 충실도, 공동 편집 지연, 서빙 속도로 나뉜다. 각 지표의 정의는 처음 나오는
문장의 각주로 제시한다.

### 5.1.2 평가 데이터셋과 측정 도구

평가 대상별 평가 데이터셋은 [표 5-1]과 같다. 모든 측정은 저장소에 포함된 측정 프로그램으로 다시 실행해 재현할 수 있다.

| 구분 | 평가 데이터셋 | 비고 |
|---|---|---|
| 판독 | 사업 문서 24건의 본문 3쪽 | 세 엔진이 모두 처리한 23건에서 원문과의 어절 일치도(어절 F1) 계산 |
| 규정 검색 | 규정 청크마다 27B로 만든 합성 질의 29,271건 | 방식 비교용. 질의가 자신을 만든 청크를 다시 찾는 구조여서 절대치가 실제보다 높게 나오는 경향 |
| 검색 모델 학습 | 학습에 쓰지 않고 남겨 둔 문서(리랭커 12문서) | 같은 문서에서 나온 질의는 학습과 평가 가운데 한쪽에만 포함 |
| GraphRAG | 그래프에서 추출한 절 질문 70문, 관계 질문 74문, 답변 36문(정답 문서가 지워진 4문 제외) | 세 방식을 같은 평가 데이터셋으로 비교 |
| 생성 모델 기준 | v1 80문(답변 10), v2 136문(답변 30) | 모델 교체 때 후보 모델을 같은 방식으로 비교 |
| 실서식 작성 | 공개 국고사업 서식(지방대학 특성화 사업계획서 단독형) 등 서식 4종 | 운영 서버의 실제 27B 사용 |
| 문서 작성 시나리오 | 「양식 없이 시작」 11턴 대화 | 임시 DB와 실제 27B 사용, 버전마다 3회 |
| SFT 전후 비교 | 학습셋에서 분리해 둔 시험 220문항, 맥락 30문항 | 모델 외 조건은 동일 |
| 공동 편집 | 헤드리스 크롬으로 접속한 시험 계정 세 개, 실제 기안기 세 창 | 로컬 앱과 운영 기안기 서버 |

[표 5-1] 평가 데이터셋과 측정 도구

검색과 생성 모델 평가 데이터셋은 대부분 문서에서 모델이 자동으로 만든 합성 질의(synthetic query)이거나 그래프에서 자동으로 추출한 질문이다. 따라서 방식 간 상대 비교에는 적합하지만,
실제 담당자 질문에서의 절대 성능을 그대로 나타내지는 않는다. 시험은 임시 DB에서 수행했고 운영 데이터는 읽기만 했다. 평가 데이터셋 원문과 결과 원자료는
개인정보와 교내 문서를 포함할 수 있어 저장소 밖에 두고, 저장소에는 집계 결과와 해석만 남겼다.

## 5.2 문서 수집과 OCR

판독은 정확도와 처리량을 함께 고려하여 엔진을 나누어 사용하기로 했고, 수집(ingestion) 품질은 검색 점수와 별도로 관리해야 함을 확인했다.

### 5.2.1 OCR 엔진 비교

스캔 PDF는 Writer 27B의 이미지 판독이 가장 정확했으나 처리 속도가 느렸다. 따라서 대량 처리에는 MinerU를, 짧은 스캔 문서에만 27B를 사용한다.
사업 문서 24건(사업마다 1건, 본문 3쪽)을 세 엔진으로 판독하고, 세 엔진이 모두 처리한 23건에서 원문과 어절이 얼마나 맞는지(어절 F1, word-level F1)[^c5-f1]와
쪽당 처리 시간을 재어 [표 5-2]에 정리했다.

[^c5-f1]: 어절 F1은 판독 결과와 원문을 어절 단위로 비교해 구한 정밀도와 재현율의 조화 평균이다. 1에 가까울수록 원문과 일치한다.

| 엔진 | 어절 F1 평균(원문 일치도, 1이 완전 일치) | 쪽당 시간(초) |
|---|---|---|
| Writer 27B 이미지 판독 | 0.839 | 165(서빙 장비, 다른 작업과 병행) |
| MinerU[21][22](한국어 OCR) | 0.690 | 7.6(학습 장비 GPU) |
| docling[23](기본 OCR) | 0.334 | 5.6 |

[표 5-2] 스캔 판독 엔진 비교

27B는 가장 정확했지만 쪽당 165초로 MinerU의 7.6초보다 훨씬 느려 엔진을 문서의 양과 종류에 따라 나누어 쓴다. docling은 한국어가 깨진 출력도
글자 수만 보는 분량 검사를 통과해 판독 실패를 걸러 낼 수 없어 제외했다. 디지털 PDF는 판독하지 않고, 파일 안에 글자로 저장된 텍스트 레이어를 글자 좌표와 함께 추출한다.

### 5.2.2 수집 정확도와 문서 분류

수집 과정 개선으로 화면 표시와 인용의 충실도는 크게 나아졌으나 검색 점수는 달라지지 않았다. 개선 후 서류 종류가 비어 있는 문서는 192건에서
1건으로, 공개 수집 문서 가운데 개인정보가 남은 문서는 208건에서 0건으로, 쪽 번호가 없는 문서는 10건에서 2건으로 줄었다. 같은 합성 질의
(1,023건, 리랭커 표본 300)로 운영 구성(5.3.1절)을 다시 잰 결과, 정답 조각이 1위에 오른 비율은 70.7%로 직전 72.3%와의 차이가 같은 구성을
반복 측정할 때의 변동 폭(±0.013)과 비슷했다. 본문이 좋아져도 검색 점수는 그대로이므로 수집 품질은 별도의 지표로 관리한다.

서류 종류와 사업 판정을 규칙 대신 27B에 맡기자 판정 결과가 크게 바뀌었고 판별 속도도 빨라졌다. 수집 규모는 4.1절 [표 4-2]와 같다. 서류 종류를 판정한 29,444건 가운데 27B의 판정이 기존 규칙 판정과 다른 문서는 11,823건(약 40%)이었고,
일부를 표본으로 확인한 결과 대부분 27B의 판정이 옳았다. 문서가 속한 사업을 파일 단위로 다시 판정하자 1,034건 가운데 734건의 사업이 바뀌었다.
두 판정의 정답률은 5.7절에서 다룬다. 업로드한 문서가 어떤 문서인지 판별하는 시간은 추론 모드(thinking mode, 답하기 전에 생각 과정을 먼저
생성하는 방식)를 끄자 건당 약 100초에서 약 10초로 줄었고, 다시 판별한 708건 가운데 695건에서 결과를 얻었다. 지난 문서의 한글 양식도 특정
파일을 지목하는 규칙 없이 원본 목록의 정보와 본문에서 잰 값만으로 공통 양식과 지난 사업 문서로 구분했다.

## 5.3 검색 품질

검색 정확도를 높인 요인은 규정 검색에서는 리랭커, 사업 문서 검색에서는 사업 구조로 범위를 좁히는 그래프 단계였다.

### 5.3.1 규정 검색

규정 검색에서는 하이브리드 검색에 리랭커를 더한 운영 구성이 모든 단독 방식보다 정확했고, 그 차이는 대부분 리랭커의 재정렬에서 비롯되었다.
규정 조각(chunk)마다 27B로 만든 합성 질의를 넣고, 원래 조각이 몇 위에 오는지를 R@k[^c5-rk]로 쟀다. 비교한 방식은 네 가지다. 낱말로 찾는 어휘 검색, 뜻으로 찾는 임베딩(KURE-v1[33])
검색, 두 결과의 순위를 RRF[38]로 합친 하이브리드 검색, 그리고 하이브리드 후보 20개를 리랭커(reranker, Rerank v1, 기반 모델 bge-reranker-v2-m3[35])로 다시 정렬하는
운영 구성이다. 결과는 [표 5-3]과 같다.

[^c5-rk]: R@k(Recall@k)는 정답 조각이 검색 결과 상위 k개 안에 든 질의의 비율이다. R@1은 정답이 1위에 오른 비율이다.

| 검색 방식 | 측정 1 R@1(질의 1,026건) | 측정 2 R@1(질의 29,271건) |
|---|---|---|
| 어휘 검색(낱말 일치) | 43.0% | 42.3% |
| 의미 검색(임베딩) | 69.1% | 62.1% |
| 하이브리드(어휘+의미, RRF 결합) | 67.1% | 60.6% |
| 하이브리드 + 리랭커(운영 구성, 표본 300건) | 76.3% | 74.0% |
| 운영 구성 R@10(측정 1)·R@5(측정 2) | 92.7% | 85.7% |

[표 5-3] 규정 검색 성능

둘을 합친 검색만으로는 뜻 검색 단독보다 1위 정답 비율이 다소 낮았지만, 리랭커를 더한 운영 구성은 두 측정 모두 모든 단독 방식보다 높았다.
측정 2는 같은 규정이 판만 달리해 여러 번 등록된 경우 같은 본문도 정답으로 인정하도록 채점을 고친 뒤의 값이다. 학습 문서를 제외한 합성 질의
22,084건 가운데 고정 표본 600건에서는 검색 후보를 그대로 두고 채점만 고쳐도 1위 정답 비율이 70.7%에서 76.0%로 올랐다. 따라서 두 측정의 차이(76.3% → 74.0%)는
검색 성능의 변화로 보지 않는다. 같은 표본에서 낱말 검색의 가중치를 0~0.6으로 바꾸어도 600건 가운데 3~4건만 달라졌으므로 기존 값 0.4를 유지했다.

학습한 리랭커는 학습에 쓰지 않고 남겨 둔 문서(held-out)로 만든 평가에서 기반 모델보다 나아 채택했으며, 수치는 4.3절 [표 4-5]와 같다. 처음 학습한
임베딩 시험 모델은 남겨 둔 질의 96건에서 1위 정답 비율이 기반 모델보다 낮아(0.271 → 0.219) 배포하지 않았고, 채택 기준을 바꾸어 다시 학습한 Embed v2를
운영 규정 색인에 쓴다. 공개 모델 KURE-v2로 바꾼 구성은 합성 질의 1,023건 가운데 표본 300건에서 1위 정답 비율 74.3%로 운영 구성 73.7%와 2건 차이에 그쳐
도입하지 않았다.

남은 오답은 대부분 시행일·부칙처럼 어느 규정에나 있는 조문을 묻거나 규정 이름을 밝히지 않은 합성 질의였다. 이러한 질의는 사람이 보아도
정답 조문을 하나로 정하기 어렵다.

### 5.3.2 사업 문서 검색과 벡터 색인

AURA가 사용자의 질문을 제대로 이해하고 원하는 내용을 찾아오는지를 같은 평가 데이터셋에서 세 구성으로 비교했다. 같은 사업이 해마다 비슷한 문서를
남기므로, 본문 글자만으로 찾는 전문 검색에서는 연도나 사업이 다른 유사 문서가 먼저 검색되기 쉽다. 이에 AURA는 지식 그래프로 사업·연차·서류 종류를 먼저 좁힌 뒤
하이브리드 검색을 수행한다. A는 그래프 단계를 끈 일반 RAG(전문 검색), B는 사업·문서 이름 일치로 범위를 좁히는 그래프 검색, C는 B에 27B의 질문
해석을 더해 사업 간 관계까지 탐색하는 운영 구성이다. 질문은 교내 문서에서 만든 144문(절 질문 70문, 관계 질문 74문)이며, 상위 k(절 5, 관계 6)와
리랭커를 쓰지 않는 설정은 이전 측정과 같다.

평가는 사용자 요청에서 답변까지의 단계 순으로 했다. 요청 이해는 27B가 질문에서 사업·연도·서류 종류를 모두 맞게 해석했는지[^c5-und]로 보았다.
찾기는 질문한 절이 든 문서를 상위 결과 안에 찾아왔는지[^c5-want], 옛 사업 이름으로 물어도 후속·전신 사업 문서를 찾는지로 보았다. 답변은 모델에 제공한
근거에 질문한 절이 든 문서가 포함되었는지와 근거에 없는 수치(ungrounded number)[^c5-ungr]로 보았다. 시험지에 적어 둔 문서 한 건을 찾았는지[^c5-dk]는
참고 지표로 함께 기록했다. 결과는 [표 5-4]와 같다.

[^c5-und]: 질문 해석 결과의 사업·연도·서류 종류(계획서·실적보고서)가 시험지의 값과 모두 같은 질문의 비율이다.
[^c5-want]: 질문한 사업·연도에 질문한 제목의 절을 가진 문서가 상위 5건 안에 든 질문의 비율이다. 같은 계획서가 판본·협약반별로 여러 건 있어, 그중 어느 문서를 찾아와도 사용자에게는 같은 내용이다.
[^c5-dk]: 시험지가 정답으로 적어 둔 문서 한 건이 상위 k개 안에 든 질문의 비율이다. 절 질문은 k=5, 관계 질문은 k=6으로 측정하였다.
[^c5-ungr]: 답변에 사용된 숫자 가운데 모델에 제공한 근거에 없는 숫자의 수다. 코드가 대조해 세며, 「(근거 확인 필요)」로 표시한 숫자는 제외한다.

[표 5-4] 일반 RAG와 GraphRAG 비교

(참고) 행은 같은 계획서가 판본별로 여러 건 있어도 시험지에 적어 둔 문서 한 건만 정답으로 센 값이다.

그래프로 범위를 좁히자 질문한 내용을 찾아오는 비율이 47%에서 93%로, 그 내용을 근거로 답한 비율이 50%에서 100%로 올랐다. 27B의 질문 해석은
사업 간 관계를 묻는 질문에서 효과가 컸다. 「○○사업의 후속 사업에서는」처럼 옛 사업 이름으로 묻는 질문에서 이름 일치만 쓰는 B는 질문에 나온
사업 안에서만 찾아 16%에 그쳤지만, C는 관계를 해석해 그래프의 사업 연결을 따라가 19문을 모두 찾았다. 검색 시간은 질문 해석 때문에 C가 2초가량 더
걸렸으나 답변 1건의 소요 시간은 세 구성이 비슷했고, 근거에 없는 수치는 세 구성 모두 0건이었다. 참고 지표가 낮게 나온 것은 같은 계획서가 판본별로
여러 건 있어 시험지에 적힌 것과 다른 판본을 찾아온 경우와, 계획 대비 실적 질문처럼 두 문서를 모두 맞혀야 하는 경우 때문이다.

이 측정 과정에서 지식 그래프에 이름이 같은 사업 노드가 여덟 쌍 생겨 있는 문제를 발견해 수정했다. 사업 이름이 바뀐 경우(RISE에서 앵커로) 사업 목록에 등록된
식별자와 약칭으로 만든 식별자가 갈라져 같은 사업이 두 노드가 되었다. 질문 해석이 문서가 적은 쪽 노드를 고르면 그 사업 문서 대부분이 검색 범위에서 빠졌다.
그래프를 다시 만들 때 이름이 같은 사업 노드를 하나로 합치도록 한 뒤 측정한 값이 [표 5-4]이며, 수정 전 C의 질문한 내용 찾기는 87%였다.

평가 질문도 일부 정리했다. 이전
측정(10-14) 이후 문서함 정리로 정답 문서가 지워진 질문 4문은 같은 내용의 판본이 여러 건이라 정답을 하나로 정할 수 없어 제외했다. 정답 문서가 다른
번호로 다시 등록된 1문은 정답 절의 본문으로 다시 찾은 새 번호를 정답으로 삼았다. 이전 측정에서는 언어 모델이 채점자 역할을 하는 LLM 판정자(LLM-as-a-judge)[73] 세 개가 어느 구성의 답변인지 모른 채
정답성을 매겼고, 평균은 A 0.36, B 0.75, C 0.92점(0~2점)이었다. 사람이 따로 판정한 10문과의 차이는 모두 1점 이내였다.
다만 평가 데이터셋이 그래프에서 자동으로 추출한 질문이어서 그래프 방식에 유리하게 나왔을 수 있다.

사업 문서 벡터는 데이터베이스 색인으로 옮겨도 검색 품질이 유지되고 자원 사용은 줄었다. GPU가 없는 운영 서버에서 벡터를
메모리 배열로 유지하면 부담이 크므로, 가까운 벡터를 근사로 빠르게 찾는 PostgreSQL pgvector[40]의 HNSW[41] 색인으로 옮기고 이전 전후를 같은 평가 데이터셋으로 비교했다.
정답 문서 적중은 1문 이내의 차이로 유지되었고, 검색 시간은 절반 가까이 줄었으며, 운영 서버 메모리에 5GB가 넘는 배열을 둘 필요가 없어졌다.
세부 수치는 4.3절 [표 4-5]에 제시하였다.

### 5.3.3 생성 모델 비교

후보 모델을 같은 조건에서 비교한 결과, 교체 여부를 가른 것은 매개변수 수보다 플랫폼이 요구하는 출력 형식을 지키는지였다. 실제 도입 때 더 큰
모델로 바꾸는 것을 전제로, 검색·답변·서류 종류 판정을 한 번에 재는 모델 교체 기준과 모호한 문항·삭제된 정답을 고친 v2 평가 데이터셋을 만들었다.
v2 136문에서 검색 단계가 정답 문서를 찾아온 비율(정답 문서@k)은 89%였고, 답변 30문의 결과는 4.5절 [표 4-8]에 있다.

같은 도구와 v1 평가 데이터셋으로 운영 모델 Writer 27B와 gpt-oss:120b를 비교했다. 27B가 근거에 없는 수치를 제외한 모든 항목에서 앞섰고 답변 시간
중앙값도 40.2초로 gpt-oss의 153.7초보다 짧았다. gpt-oss는 정해진 형식으로 답해야 하는 서류 종류 판정 50건에서 모두 형식을 지키지 못해 교체하지
않았다. 다만 답변이 10문뿐인 v1의 결과이며, 평가 데이터셋 버전이 다르므로 답변 시간도 v2의 16.6초와 직접 비교하지 않는다.

## 5.4 질의응답과 문서 작성 품질

문서 작성에서는 근거에 없는 수치를 표시 없이 출력하지 않게 되었다. 또 절을 별도 27B 호출에 나누어 맡기는 절 단위 위임과 개요 작성, 작성 후 검토를 도입해 긴 서식과 재작성 요청을 처리할 수 있게 되었다.
남은 약점은 실행마다 달라지는 모델의 판단이다.

### 5.4.1 답변의 근거 정확성

행정 문서에서 근거 없는 숫자는 허위 기재로 이어질 수 있으므로, 수치 검증기가 답변의 숫자를 근거와 대조해 근거에 없는
숫자에 「(근거 확인 필요)」를 표시하고, 답변 형식은 「핵심 먼저, 요점 5개 이내, 600자 안팎」으로 정한다. 이 상태에서 표시 없이 출력된 근거에 없는 수치는 0건이다.
결과는 4.5절 [표 4-8]과 같다.

추론 모드를 켰을 때의 효과는 현재 설정(컨텍스트 262,144토큰, 출력 한도 고정 없음)에서 같은 질문 24개로 다시 비교했다. 추론을 켜도 빈 답과
근거에 없는 숫자는 0건이었고, 정답 절의 핵심 사실을 답에 담은 비율(사실 재현율)은 평균 17.2%에서 27.4%로 올랐다. 그러나 답 생성 시간의
중앙값은 27.8초에서 217.9초로 약 8배, 생성한 토큰 수의 중앙값은 604개에서 4,424개로 늘었다. 출력 한도를 16,384토큰 안에서 고정하던 이전
측정에서는 추론이 한도를 먼저 써서 답이 비거나 나빠졌지만(24개 가운데 12개 악화), 한도를 푼 뒤에는 답의 사실 재현율이 오히려 조금 높아졌다.
다만 답 하나에 3~4분이 걸려 대화형 답변에는 맞지 않으므로 기본값은 끈 상태로 두고, 시간보다 정확도가 중요한 요청에서 선택해 쓰는 방안을 검토한다.

### 5.4.2 장문 서식 작성과 양식 생성

같은 27B를 앞선 대화 없이 새로 호출해 절을 맡기자 긴 사업계획서에서 작성된 절이 0에서 21까지 늘었으나, 맡길지의 판단은 실행마다 달랐다. 한 번의 호출에서 모든 절을
처리하면 대화 내용이 쌓여 컨텍스트가 길어지고 작성이 중간에 멈춘다. 그래서 에이전트가 필요할 때 절 작성을 새 27B 호출에 넘기게 하고, 실서식
사업계획서(지방대학 특성화 사업계획서 단독형, 에이전트가 편집하는 작업 문서 기준 절 47개)에서 채운 절[^c5-sec]의 수를 셌다. 그 결과 「항상 직접
작성」 설정의 0/47에서 한 실행은 21/47까지 늘었지만, 다른 실행은 한 번만 맡겨 1/47에 그쳤고 소요 시간도 3~4배로 늘었다. 평균 효과를 말하려면
반복 측정이 더 필요하다.

[^c5-sec]: 작성된 절은 서식에서 작성해야 할 절 가운데 에이전트가 실제로 채운 절의 수다.

양식 생성에서는 맞는 양식이 없어도 27B가 양식 설계와 첫 작성까지 안정적으로 수행했지만, 재작성 요청의 반영이 가장 약했다. 양식 설계, 내용
작성, 수정 요청 반영으로 이어지는 11턴 대화를 여러 차례 잰 마지막 측정에서 양식의 구조 점수는 8/8, 채운 절은 10/10, 서식 깨짐은 0건이었고
디자인 요청 4건은 모든 버전에 반영되었다. 반면 「더 구체적으로」 같은 재작성 요청은 6번 가운데 1번만 반영되었다.

### 5.4.3 작성 절차 개선과 모델 미세조정

5.4.2에서 드러난 재작성의 약점을 보완하려고, 특정 사례에 맞춘 규칙 대신 모든 절 작성에 공통으로 적용되는 절차를 두었다. 재작성 전용
도구를 두고, 하위 절은 [개요] → [본문] → 검토 순서로 작성하게 하며, 문단 끝에 근거 출처를 적게 했다(개선 버전). 이 기능을 끈 이전 버전과
같은 11턴 시나리오로 3회씩 비교했다. 측정은 현재 운영 설정(컨텍스트 262,144토큰)에서 수행했고, 작성과 채점은 모두 Writer 27B가 맡았다.
측정 항목은 작성방법 반영과 재작성 반영[^c5-rev], 지어낸 숫자[^c5-fab], 채점 점수[^c5-rub]이며, 결과는 [표 5-5]와 같다.

[^c5-rev]: 작성방법 반영은 서식의 작성방법이 요구한 표·도식·출처가 실제로 들어갔는지의 여부이고, 재작성 반영은 「더 구체적으로」 요청 뒤 해당 절의 분량이 1.15배를 넘게 늘었는지의 여부다. 둘 다 코드가 계산한다.
[^c5-fab]: 지어낸 숫자는 작업 문서 본문의 숫자 가운데 근거나 담당자 입력에 없는 숫자의 수다. 단위만 다른 같은 금액은 같은 값으로 간주한다.
[^c5-rub]: 채점 점수는 같은 27B가 채점 기준표(rubric)에 따라 구체성·논리·문체·근거를 5점 만점으로 매긴 값으로, 버전 비교에만 사용한다.

[표 5-5] 문서 작성 에이전트 개선 전후 비교

두 버전은 모든 절과 작성방법을 반영해 이번 측정에서는 차이가 거의 없었다. 컨텍스트 16,384토큰에서 잰 이전 결과(재작성 반영 개선 3/3, 이전 1/3)는
짧은 컨텍스트에서 앞선 대화가 잘려 재작성 대상을 놓치던 문제를 개요·검토 단계가 보완한 것으로 보이며, 컨텍스트를 늘리고 출력 한도를 푼 뒤에는
이전 버전도 같은 수준에 이르렀다. 개요·검토 단계는 시간이 약 38% 늘고 채점 점수는 비슷하거나 조금 낮았으므로, 짧은 컨텍스트의 모델이나 긴
서식(5.4.2절)에서만 켜도록 조정할 계획이다.

디자인 지시 반영(버전마다 12/12)과 서식 깨짐(0건)도 두 버전이 같았다. 버전마다 3회만 측정했고
채점이 같은 27B의 자기 평가이므로, 기본 설정은 측정을 더 반복한 뒤 정한다.

SFT는 학습 형식의 답변 품질을 뚜렷이 높였지만, 학습쌍이 한 가지 형식뿐이어서 에이전트 단계의 요청에는 맞지 않았다. SFT는 더 큰 모델에 적용하기
위한 실험으로, 교내 실문서로 만든 학습 절차와 데이터가 실제로 효과가 있는지를 27B에서 먼저 확인하는 데 목적이 있다. Writer 27B에 교내 실문서
학습쌍 4,434쌍으로 LoRA[17] 방식의 SFT(정답 예시로 추가 학습하는 지도 미세조정)를 수행하고, 병합한 모델을 운영과 같은 NVFP4로 양자화한 뒤 학습 전 모델과 비교했다. 학습 방법은 4.10절에서 설명하였다.
학습이 서빙 모델에 반영되었는지는 정답 토큰당 평균 로그확률(log-probability)[^c5-lp]로 먼저 확인했다. 생성 품질은 시험 문항 정답과 글자·단어가
얼마나 겹치는지를 나타내는 chrF와 ROUGE-L, 그리고 코드가 세는 질문에 없는 숫자와 잘린 답변의 비율로 비교했다. 결과는 [표 5-6]과 같다.

[^c5-lp]: 정답 토큰당 평균 로그확률은 정답 글을 모델에 입력했을 때 토큰마다 매긴 확률의 로그 평균이다. 생성 없이 측정하므로 샘플링에 따른 변동이 없으며, 값이 0에 가까울수록 모델이 정답 글에 높은 확률을 부여한다는 뜻이다.

| 지표 | 학습 전(Writer 27B) | SFT 뒤 |
|---|---|---|
| 정답 토큰 평균 로그확률(0에 가까울수록 좋음, 40문항) | -1.845 | -1.153 |
| 정답 겹침 chrF(글자) · ROUGE-L(단어)(100점 만점, 220문항) | 27.9 · 16.8 | 36.6 · 27.3 |
| 정답 대비 답변 길이 | 1.81배 | 0.96배 |
| 질문에 없는 숫자가 든 답 · 잘린 답의 비율 | 4.1% · 2.7% | 0% · 0% |
| 맥락 이해 문항 정답(30문항) | 30/30 | 30/30 |

[표 5-6] 모델 미세조정 전후 비교

로그확률이 -1.845에서 -1.153으로 올라 학습 결과가 서빙 모델에 반영된 것을 확인했고, 코드가 세는 지표는 모두 SFT 모델이 우수했다. 특히 답변 길이가
정답의 1.81배에서 0.96배로 줄어 불필요하게 길게 작성하던 경향이 개선되었다. 항목별 채점 점수는 두 모델 모두 5점에 가까워 변별력이 낮았다. 채점 모델에게
두 답변 가운데 나은 답변을 고르게 하면 학습 전 모델의 답변이 더 자주 선택되었다. 220문 가운데 SFT 답변이 이긴 것은 28문, 비긴 것은 80문,
진 것은 112문이었고, 비긴 경우를 반 승으로 계산한 점수는 30.9%였다. 그러나 채점 모델이 학습 전 모델과 같은 기반 모델이고 긴 답변을 선호하는
경향이 있어 이 값으로 우열을 가리지 않았다. 문서 작성 시나리오에서는 학습 전 모델이 두 번 모두(2/2) 작업 문서를 생성한 반면, SFT 병합 모델은
한 번도 생성하지 못했다(0/2). 학습쌍이 질문과 답변으로 이루어진 한 가지 형식뿐이어서, 에이전트가 다음 작업을 JSON으로 정하는 단계의 요청에도
학습한 답변 형식으로 응답했기 때문이다. 따라서 더 큰 모델에서는 플랫폼이 실제로 보내는 요청 형식을 학습 데이터에 고르게 포함할 계획이며,
그 방법은 4.10절과 6.3.2절에서 다룬다.

## 5.5 응답 속도

공동 편집에서 글자가 다른 화면에 나타나기까지의 지연과, 생성 모델의 서빙 속도를 차례로 제시한다.

### 5.5.1 공동 편집 지연

문서를 편집 영역으로 나누고 한 영역은 한 사람만 고치게 하는 영역 단위 편집권 방식에서, 입력한 글자는 어떤 시험에서도 사라지지 않았고 글자 지연(latency)은 약 0.2초였다.
로컬 앱과 운영 기안기 서버를 연결하고, 화면 없이 동작하는 브라우저인 헤드리스 크롬으로 시험 계정 세 개가 동시에 접속해 글자 지연[^c5-lat]과
동시 입력·연결 끊김·AURA가 함께 작성할 때의 글자 보존을 쟀다. 한글은 자모가 조합되는 단계(ㄱ → 기 → 김)를 그대로 재현해 입력했고, 마지막 두 시험은
실제 기안기 창에서 수행했다. 표의 A와 B는 서로 다른 시험 사용자이며, 결과는 [표 5-7]과 같다.

[^c5-lat]: 글자 지연은 한 화면에서 확정한 글자가 다른 화면에 나타나기까지의 시간이다. 중앙값(가운데 값), 상위 90% 값(열 번 가운데 아홉 번은 이보다 빠름), 최댓값으로 보고한다.

| 시험 | 결과 |
|---|---|
| 글자 전달: A가 한 글자씩 21회 입력 | B 화면 표시까지 중앙값 221ms, 상위 90% 값 299ms, 최대 302ms, 글자 누락 없음 |
| 화면 폭이 다른 세 창(1440·1000·570px)과 같은 사용자의 둘째 창에서 입력 | 글자당 지연 중앙값 204~216ms, 글자 누락 없음 |

| A가 떠난 편집 영역의 편집권을 B가 넘겨받음(시험용 대기 시간 3초) | B 편집 시작까지 3.1~3.8초 |
| 연결이 끊긴 상태에서 입력한 뒤 다시 연결 | 재연결 뒤 A 화면 반영까지 19~40ms |
| AURA가 다른 서버 프로세스에서 편집 영역에 작성 | A 화면 반영까지 863ms(프로세스 사이 변경 확인 주기 1초) |

| 실제 기안기에서 2~3명이 동시에 입력하고 Enter | 4초 동안 세 사용자 화면 모두에서 화면이 튀는 현상 0회(2회 반복) |

[표 5-7] 공동 편집 지연 시간

글자 지연의 중앙값은 변경을 모아 보내는 간격(300ms)보다 짧아 사용자는 사실상 실시간으로 상대의 입력을 본다. 시험용으로 만든 451쪽 문서(편집
영역 942개)에서도 긴 절 끝의 입력 지연은 142ms로, 절 전체를 한 덩어리로 주고받던 초기 구조의 1,727ms보다 크게 줄었다. 절을 문단 단위로 나누어
바뀐 문단만 주고받게 한 결과다. 감수한 점은 AURA의 작성이 서버 프로세스 사이의 알림을 1초 주기로 확인하는 구조여서 사람의 입력보다 늦게
반영된다는 것이며, 6.3.3절의 개선 과제로 남겼다.

### 5.5.2 서빙 속도

NVFP4 양자화와 MTP 추측 디코딩을 적용한 결과 27B의 생성 속도는 16비트로 저장한 원본(bf16)의 약 5~10배가 되었고, 품질 저하는 관찰되지 않았다. NVFP4는 모델
가중치를 4비트 부동소수점으로 줄여 저장하고 계산하는 양자화 형식이다. MTP 추측 디코딩은 모델이 다음 몇 토큰을 미리 예측해 두고 본 모델이
이를 한 번에 검증하여 생성 속도를 높이는 방법이다. 27B는 젯슨 AGX 토르[13] 두 대에서
언어 모델 서빙 프로그램인 vLLM[10]으로 서빙한다. 정밀도와 디코딩 방식을 바꾸어 가며 요청을 하나씩 보내 초당 토큰(tokens per second)[^c5-tps]과 대표 작업의 소요 시간을 쟀다. 결과는 [표 5-8]과 같다.

[^c5-tps]: 초당 토큰은 요청 하나를 처리할 때 모델이 1초에 생성하는 토큰 수다.

| 구성 | 초당 생성 토큰(요청 1건) | 판독 5쪽 소요 시간(초) | 검토 1건 소요 시간(초) |
|---|---|---|---|
| bf16 원본 | 2.4~4.5 | 128 | 225 |
| NVFP4[14] 양자화 | 10.4~10.8 | 29 | 82 |
| NVFP4 + MTP[15] 추측 디코딩[16](검토 장비) | 10.6 → 23.8(2.25배, 평균 수용 토큰 2.2개) | 미측정 | 미측정 |
| NVFP4 + MTP 추측 디코딩(답변 장비) | 약 12 → 24.6 | 미측정 | 미측정 |

[표 5-8] 서빙 정밀도별 속도

NVFP4 양자화로 초당 토큰이 bf16의 2.4~4.5에서 10.4~10.8로 오르고 판독·검토 시간이 크게 줄었으며, MTP 추측 디코딩(speculative decoding)을 더하자
다시 약 두 배가 되었다. NVFP4 모델의 판독 결과는 bf16과 같았고, 추측 디코딩을 적용한 뒤에도 서류 종류 판정 표본이 기존 규칙과 일치한 비율(92%)과 답변 근거의 정답
문서 비율이 변하지 않았다. 답변 전체 시간의 단축(4.5절 [표 4-8])은 답변 형식 정리와 추측 디코딩이 함께 만든 결과여서 두 요인의 기여를 따로
나누지 않았다.

## 5.6 실제 문서 적용과 시연

### 5.6.1 실제 문서 적용 사례

지표 측정과 별도로 실제 서식과 실제 수집 경로에서 전 과정을 실행하여, 에이전트가 빈 서식의 입력란 구조를 읽고 채울 수 있으며 완성본이 원본 서식을
유지함을 확인했다.

공개 국고사업 서식(지방대학 특성화 사업계획서 단독형)을 운영 서버에서 실제 27B 에이전트로 채웠다. 짧은 서식(예산 변경·출장 보고·기안문)은
모든 절을 채웠지만, 긴 사업계획서는 한 번의 요청으로 절 41개 가운데 17개를 작성한 뒤 멈췄다. 지어낸 숫자는 0건이었다. 5.4.2와 같은 서식이지만
작업 문서에서 센 전체 절 수가 이 측정에서는 41개, 절 단위 위임 비교에서는 47개로 달라 두 측정의 작성된 절 수는 직접 비교하지 않는다. 이 한계를
보완하기 위해 5.4.2의 절 단위 위임과 5.4.3의 개선을 도입했다. [그림 5-1]은 이 서식의 요약표 셀을 27B 에이전트가 공고와 기본계획을 근거로 채운 결과다.

### 5.6.2 시연 결과

시연은 담당자의 업무 순서(공동 편집, 대화형 문서 작업, 질문과 근거 확인, 개발 현황)에 따라 구현한 기능이 실제 화면에서 연결되는지를 보여 준다.
모든 화면은 시험 환경(시험 계정, 가상의 부서·인물·사업, 공통 양식, 공개 공고 서식)에서 촬영하여 학교 내부 문서나 개인정보를 포함하지 않는다.

관리자 화면의 공동 편집 시연은 같은 빈 문서를 세 화면으로 나란히 열고, 세 사람이 절을 동시에 작성하는 동안 「AURA 양식 만들기」와 「AURA 이어 쓰기」로
27B가 양식과 빈 절을 작성해 세 화면에 함께 나타나는 과정을 보여 준다. 이 화면은 4.7절의 [그림 4-12]와 [그림 4-13]에 실었다. 시연 주제는 설정에서 선택하며,
가상 사업계획서와 신규 교직원 연수 결과 보고서 두 가지를 제공한다.

## 5.7 평가의 한계와 보완 계획

이번 평가는 개발 과정에서 구성한 평가 데이터셋으로 수행했으므로, 실제 업무 환경에서의 효과를 확정하려면 다음 보완이 필요하다. 각 항목은
측정 도구와 절차가 이미 갖추어져 있어, 평가 데이터만 더하면 같은 방식으로 다시 측정할 수 있다.

첫째, 평가 질문을 실제 담당자의 질문으로 넓힌다. 규정 검색은 문서에서 자동으로 만든 질의로, GraphRAG와 모델 교체 기준 v2는 지식 그래프에서
추출한 질문으로 측정했다. 교내 TF 담당자들이 실제 업무에 AURA를 사용하기 시작했으므로, 이때 나온 질문과 담당자가 확인한 정답을 모아
골드셋(gold set)을 만들고 같은 도구로 다시 측정할 계획이다.

둘째, 표본을 늘리고 사람의 판정을 더한다. 기준 v2의 답변은 30문, 문서 작성 시나리오는 버전마다 3회로, 버전 간 비교에는 충분하지만 절대 수준을
말하기에는 작다. 문서 작성과 SFT 비교의 채점은 같은 27B 계열 모델이 맡았고, 사람 판정은 GraphRAG 10문에서 모델 판정과 1점 이내로 일치함을
확인했다. 시범 운영에서 담당자 평가를 함께 기록하도록 화면을 이미 마련해 두었으므로, 문서 작성 품질도 사람 기준으로 측정할 수 있다.

셋째, 사업 간 관계를 묻는 질문의 검색을 보강한다. 후속·전신 사업을 찾는 질문은 모두 맞혔지만, 「계획 대비 실적」처럼 같은 해의 계획서와
실적보고서를 함께 찾아야 하는 질문은 시험지의 두 문서를 모두 찾은 비율이 아직 낮다([표 5-4] 참고 행). 계획서와 실적보고서를 쌍으로 가져오는
단계를 이미 넣어 효과를 확인했으므로(4.4절), 판본이 여러 건인 문서에서 같은 내용의 판본을 함께 인정하는 평가와 쌍 찾기 보정을 넓혀 다시 측정한다.

넷째, 실제 사용 환경의 속도를 측정한다. 공동 편집 지연은 브라우저 자동화 환경에서, 서빙 속도는 주로 요청 하나씩 보낸 조건에서 측정했다. 여러
담당자가 동시에 쓰는 시범 운영에서 실제 계정과 동시 접속 측정 도구로 지연을 다시 재고, 필요하면 모델 서버를 늘려 대응한다.

다섯째, 사람이 정한 정답이 필요한 지표를 측정한다. 이 지표들은 정답을 자동으로 만들 수 없어 이번에는 재지 못했다. 개인정보 탐지 재현율, 서류 종류와 사업 판정의 정답률, 계획서와 실적보고서의 절 대응
정확도, 업무 도우미의 작업 선택 정확도와 화면 조작 성공률, 구글 문서 편집 계획의 적용률이 여기에 해당한다. 담당자가 정답을 표시한 표본만 모으면
이미 갖춘 측정 도구로 잴 수 있다. 기관별 글꼴·여백 같은 서식 설정을 담은 기관 서식 프로필도 같은 사업의 지난 문서를 기준으로 고르도록 보완한 뒤 정답 문서와의 서식 일치율을 측정한다.

또한 측정값 자체의 신뢰성을 지키는 장치를 두었다. 모든 측정은 운영 설정을 읽어 실행하고, 결과마다 실제로 응답한 모델과 색인을 만든 임베딩 모델을 함께 기록한다.
이 기록 덕분에 설정이 다른 측정값이 섞이는 것을 막을 수 있으며, 앞으로 모델을 교체하거나 다시 학습할 때도 같은 기준으로 비교할 수 있다.
