# 5. 평가 및 결과

이 장은 AURA 의 각 단계를 어떤 잣대로 쟀고 어떤 값이 나왔는지를 정리한다. 수치는 저장소에 남은 측정 기록(실험 로그, 결정 기록 ADR,
개발 현황 문서, 측정 스크립트의 결과 파일)에 있는 값만 쓰고, 표마다 출처를 적는다. 재지 않은 것은 「미측정」, 기록을 확인하지 못한 것은
「미확인」으로 둔다. 측정 일자는 2026년이며 월-일로 적는다. 실패한 실험과 채택하지 않은 결과도 그대로 싣는다. 무엇을 쓰지 않기로 했는지와 그 까닭이
설계 판단의 근거이기 때문이다.

## 5.1 평가 방법

### 5.1.1 평가 원칙

평가는 착수 단계의 평가 계획(docs/eval-plan.md)과 품질 체계(docs/quality-system.md)를 따른다. 원칙은 다섯이다.

첫째, 기준선 없이 개선을 주장하지 않는다. 학습본이나 새 경로를 들이기 전에 같은 시험지로 지금 구성의 값을 먼저 재어 저장하고, 바꾼 뒤에
같은 실행으로 다시 잰다. 생성 모델 교체 기준(scripts/195)과 시험지 v2 는 이 원칙으로 만든 기준이다.

둘째, 운영 연결 설정과 함께 잰다. 9-21 에 서빙 장비 설정을 읽지 않고 띄운 측정이 임베딩과 리랭커를 운영 서버 CPU 의 바탕 모델로 조용히
물려 운영 구성 값이 실제보다 0.1 낮게 나온 일이 있었다(실험 로그 2절). 그 뒤로 모든 측정은 운영 설정 파일을 읽고 띄우며, 보고서에 어느
모델이 답했는지와 대체 실행 수를 적는다. 서빙 장비가 답하지 않은 측정은 운영 구성이라 부르지 않는다.

셋째, 같은 시험지, 같은 채점끼리만 비교한다. 시험지를 고치면 판 번호를 올리고 기준선을 다시 잰다. 예를 들어 생성 모델 기준 v1(80문)과
v2(136문)는 시험지가 달라 둘의 차를 개선 폭으로 읽지 않는다. 채점 규칙이 바뀐 규정 검색 값도 같은 규칙끼리만 비교한다.

넷째, 결정론적 지표를 주 근거로 삼는다. 근거 밖 숫자, 정답 문서 적중, 서식 깨짐처럼 코드가 세는 값을 앞에 두고, 언어 모델의 채점은 판끼리
비교하는 보조 지표로만 쓴다. 문서 작성 시나리오는 쓰는 모델과 채점 모델이 같은 27B 여서 자기 평가의 한계가 있다.

다섯째, 잡음 폭을 먼저 잰다. 회차마다 흔들리는 지표는 같은 구성을 두 번 돌려 흔들림 크기를 보고, 그보다 큰 차이만 차이로 읽는다. 5.4.5 의
대조군이 그 예다.

### 5.1.2 지표 정의

| 대상 | 지표 | 정의 |
|---|---|---|
| 검색 | R@k (Recall@k) | 정답 조각이 상위 k 안에 든 질의의 비율 |
| 검색 | MRR@10 | 정답 조각 순위의 역수 평균(10위 밖은 0) |
| 검색 | 후보 진입률 | 리랭커에 넘기는 후보 20개 안에 정답이 든 비율. 리랭커는 후보 안에서만 순서를 바꾸므로 운영 상한을 정한다 |
| 검색 | 정답 문서@k | 사업 문서 검색에서 시험지의 정답 문서가 상위 k(절 질문 5, 관계 질문 6) 안에 든 비율 |
| 검색 | 같은 판 · 같은 사업 | 정답 문서와 같은 판본 묶음의 문서, 같은 사업의 문서가 상위 k 안에 든 비율 |
| 검색 | recall@10(근사 검색) | 정확 계산 상위 10 가운데 근사 색인(HNSW[37])이 돌려준 비율 |
| 답 | 근거에 정답 문서 | 모델에 실제로 건넨 근거 묶음에 정답 문서가 든 답의 비율 |
| 답 | 근거 밖 숫자 | 답의 숫자 가운데 모델에 건넨 근거에 없는 것. 수치 검증기(verify/numbers.py)로 센다. 「(근거 확인 필요)」로 표시한 숫자는 세지 않는다 |
| 답 | 정답 사실 재현율 | 정답 절의 숫자 사실 가운데 답에 나온 비율. 요약 답에서는 낮게 나오므로 모델끼리 비교하는 상대 지표로만 쓴다 |
| 문서 처리 | 어절 F1 | 판독 결과와 원문의 어절 단위 정밀도·재현율의 조화 평균 |
| 문서 처리 | 규칙 일치 · 빈칸 채움 | 27B 서류 갈래 판정이 규칙 판정과 같은 비율, 규칙이 비운 문서에 갈래를 붙인 비율 |
| 문서 작성 | 쓴 절 · 칸 채움 | 서식의 쓸 자리 가운데 에이전트가 채운 절 수, 칸 채움 비율 |
| 문서 작성 | 지어낸 숫자 | 작업본 본문의 숫자 가운데 근거·담당자 글에 없는 것. 단위만 바꾼 같은 금액(5억 = 500백만원)은 같은 값으로 본다(ADR-0068) |
| 문서 작성 | 작성방법 반영 · 고쳐 쓰기 반영 | 작성방법이 요구한 표·도식·출처가 있는지, 「더 구체적으로」 요청 뒤 글이 1.15배 넘게 늘었는지를 코드가 센다 |
| 문서 작성 | 채점 점수(5점) | 같은 27B 가 기준표로 매긴 구체성·논리·문체·근거. 판끼리 비교하는 데만 쓴다 |
| 모델 비교 | chrF · ROUGE-L | 시험 문항 정답과 생성 답의 글자 n-gram F 점수[63], 최장 공통 부분열 F 점수[64] |
| 모델 비교 | 정답 토큰당 평균 로그확률 | 정답 글을 모델에 넣었을 때 토큰당 평균 로그확률. 생성 전에 재므로 샘플링 잡음이 없고, 학습이 서빙에 실제로 들어갔는지를 본다 |
| 모델 비교 | 둘 중 나은 답 고르기 점수 | 언어 모델 채점[65] 방식으로, 채점 모델이 두 답의 순서를 바꿔 두 번 고른 결과로 (이김 + 비김 × 0.5) ÷ 문항 수. 0.5 가 같음이다 |
| 공동 편집 | 글자 지연 | 한 화면에서 글자를 확정한 때부터 다른 화면에 그 글자가 나타날 때까지의 시간(중앙값·90%·최대) |
| 서빙 | 초당 토큰 · 첫 글자 시간 | 요청 하나의 생성 속도, 요청부터 첫 토큰까지의 시간 |

[표 5-2] 시험지와 측정 도구

시험은 운영 설정이 아니라 임시 DB 에서 하고, 운영은 읽기만 한다. 시험지 원문과 결과 원자료는 개인정보와 교내 문서가 들어 있을 수 있어 저장소
밖(운영 서버와 학습 장비의 작업 폴더)에 두고, 저장소에는 집계와 판단만 남겼다.

## 5.2 검색 품질

### 5.2.1 규정 검색

규정 검색은 교내 규정·지침을 조문 단위로 찾는다. 첫 기준선은 9-04 에 조각 1,236개와 합성 질의 2,595건으로 쟀다(실험 로그 1절).

| 방식 | R@1 | MRR@10 | R@10 |
|---|---|---|---|
| 어휘(Kiwi[33] 명사 + IDF[34]) | 0.338 | 0.413 | 0.567 |
| 임베딩(KURE-v1[29]) | 0.611 | 0.700 | 0.877 |
| 하이브리드(RRF[35], 같은 가중) | 0.520 | 0.647 | 0.879 |
| 하이브리드(임베딩 우세) | 0.595 | 0.692 | 0.877 |

[표 5-3] 규정 검색 첫 기준선(09-04, 질의 2,595건)

어휘 가중을 0.2~1.2 로 바꿔 보니 0.2~0.5 에서 MRR 0.692~0.693 의 고원이 나왔고, 서비스 기본값 0.4 를 유지했다. 같은 날 바탕 리랭커
(bge-reranker-v2-m3)로 하이브리드 상위 10 을 다시 줄 세우자 표본 300건에서 R@1 이 0.490 에서 0.623 으로 올랐다.

학습본의 결과는 [표 5-4] 와 같다. 리랭커 학습본(Rerank v1, 바탕 bge-reranker-v2-m3[32])은 운영 하이브리드가 실제로 올린 후보 20개로 목록 단위 학습을 했고,
문서 단위 홀드아웃에서 바탕보다 나았다. 임베딩은 첫 리허설(9-03)에서 홀드아웃 R@1 이 바탕보다 낮아(0.219 대 0.271) 배포하지 않았고, v1 은 단독
지표만 오르고 운영 경로에서 이득이 없어 버렸으며, 운영 하이브리드 위에서 후보 진입률이 오른 v2 를 채택했다(ADR-0021). 공개 KURE-v2(다중 벡터)[29]는
학습 전인데도 학습본에 근접했으나 운영 경로에서 이득이 없어 쓰지 않았다(ADR-0025).

[표 5-5] 규정 검색 운영 구성 회차별 값(실험 로그 5·20절)

10-18 의 운영 구성은 정답이 5위 안에 드는 비율이 85.7% 다. 10-14 에서 10-18 로 오른 몫의 상당 부분은 검색이 나아져서가 아니라 채점 규칙과
조각 증가 때문이다. 이 채점 규칙의 변화는 다음 두 실험에서 나왔다.

하이브리드 가중 재측정(10-14~15). 운영 임베딩이 같은 생성기의 합성 질의로 학습됐으므로 임베딩 단독 값이 부풀었을 수 있다. 그래서 학습 문서와
겹치는 질의를 빼고 깨끗한 질의 22,084건으로 가중을 다시 쟀다.

[표 5-6] 깨끗한 질의로 다시 잰 하이브리드 가중(실험 로그 10절)

가중 0~0.6 에서 후보 진입률 차는 0.05%p 이하이고, 리랭커 뒤 R@1 차는 600건 가운데 3~4건이라 95% 구간이 0 에 닿는다. 가중은 융합 순서만 바꾸고
리랭커가 그 순서를 다시 세우므로 운영 값을 움직이는 것은 진입률뿐이다. 그래서 0.4 를 바꾸지 않았다.

후보 단계 손실 감사(10-15). 임베딩 원순위 상위 20 의 진입률(0.955)보다 운영 후보 정리를 거친 진입률(0.906)이 낮아 후보 정리가 손실을 내는
것처럼 보였다. 빠진 2,081건을 단계별로 나누자 1,247건은 같은 규정이 판본·파일만 달리해 여러 번 등록된 경우였고, 정답과 같은 본문의 조각이 후보
안에 남아 있었다. 채점이 원래 조각 하나만 정답으로 셌기 때문이다. 채점이 같은 본문(공백을 지운 글자 8-gram 의 90% 이상)을 정답으로 인정하도록
고치자 [표 5-7] 처럼 값이 달라졌다. 운영 코드는 바꾸지 않았다.

| 같은 후보, 채점만 다름 | 진입률 | R@1 | MRR@10 |
|---|---|---|---|
| 하이브리드 후보 20, 옛 채점 | 0.906 | 0.611 | 0.706 |
| 하이브리드 후보 20, 새 채점 | 0.963 | 0.662 | 0.759 |
| 리랭커 뒤 표본 600, 옛 채점 | 0.913 | 0.707 | 0.786 |
| 리랭커 뒤 표본 600, 새 채점 | 0.975 | 0.760 | 0.842 |

[표 5-7] 채점 보정 전후(실험 로그 11절)

새 채점으로도 남은 융합 놓침 2.5%(22,084문 가운데 541)를 다시 나누면 58% 는 시행일·부칙·정족수처럼 어느 규정에나 있는 조문, 13% 는
「이 규정」 처럼 규정 이름을 대지 않은 지시어 질의였다. 실제 놓침 후보는 154건으로 전체 질의의 0.70% 다(실험 로그 21절). 대부분이 합성 시험지가
만든 답할 수 없는 질의라 검색 단계를 바꿀 근거가 되지 않는다. 다만 용어를 모르고 상황으로 묻는 질의의 22.7%(9-20 측정)는 두 축 모두 상위 20 에
넣지 못하며, 이 몫은 리랭커나 후보 수로 줄지 않는다(실험 로그 4절).

리랭커를 서빙 장비 GPU 로 옮기자 질의당 시간이 3.75초에서 0.07초가 됐고, 이 덕분에 후보를 10개에서 20개로 늘렸다. 생성 모델로 후보를 다시
매기는 방식은 덜 정확하고 53배 느려 쓰지 않았다.

### 5.2.2 사업 문서 검색과 GraphRAG

사업 문서 검색은 온톨로지 그래프로 사업·연차·서류 갈래를 먼저 좁히고 그 안에서 하이브리드 검색을 한다. 효과를 보려고 같은 시험지에서 그래프
단계만 바꿔 쟀다(10-14, 실험 로그 9절). A 는 그래프 단계를 끈 풀텍스트 RAG, B 는 운영 기본(이름 맞추기로 범위를 좁힘), C 는 B 에 27B 질문 읽기를
더해 관계를 따라가는 구성이다.

| 지표 | A 풀텍스트 | B 그래프 | C 그래프 + 27B 읽기 |
|---|---|---|---|
| 절 질문 정답 문서 상위 5(73문) | 18% (13) | 64% (47) | 70% (51) |
| 절 질문 MRR | 0.120 | 0.546 | 0.602 |
| 관계 질문 전체(75문) | 13% | 9% | 45% |
| 관계 — 앞·뒤 단계(19문) | 47% | 5% | 100% |
| 관계 — 평가(20문) | 5% | 25% | 50% |
| 관계 — 계획↔실적 둘 다(36문) | 0% | 3% | 14% |
| 검색 한 번 중앙값 | 1.21초 | 1.58초 | 6.45초 |
| 답 근거에 정답 문서(36문) | 31% | 53% | 75% |
| 근거 밖 숫자 | 1/152 | 1/111 | 0/169 |
| 답 전체 시간 중앙값 | 29.8초 | 37.7초 | 42.3초 |
| 블라인드 판정 정답성 평균(0~2) | 0.36 | 0.75 | 0.92 |
| 블라인드 판정 완결성 평균(0~2) | 0.44 | 0.64 | 0.94 |

[표 5-8] 풀텍스트 RAG 와 GraphRAG 비교(10-14, scripts/188)

사업·연도·문서를 지목하는 절 질문은 이름 맞추기 그래프만으로 정답 문서 적중이 18% 에서 64% 로 올랐다(95% 구간 11~28% 대 53~74%). 관계 질문은
27B 가 관계를 읽어야 풀텍스트를 넘었다. B 가 앞·뒤 단계 질문에서 풀텍스트보다 낮은 것은 질문에 적힌 사업으로 범위를 좁혀 물은 쪽 사업을 밀어내기
때문이고, C 는 앞 단계·편입 관계를 따라가 19문을 모두 맞혔다. 판정은 모드를 가린 LLM 판정자[65] 셋이 했고, 10문 30답을 사람 판정과 대조해 완전
일치 60%, 1점 이내 100% 를 확인했다. 지어낸 숫자는 세 모드 모두 1% 안이라 차이가 없었다. 이 결과로 27B 질문 읽기를 운영에 켰다.

이어 계획↔실적 짝 담기를 고쳤다(실험 로그 9.1절). 물은 갈래가 관계의 양 끝이면 모델 읽기 없이도 그 관계를 따르게 하고, 근거 문서마다 아직 담지
않은 짝 가운데 순위가 앞선 것을 담게 했다.

| 지표 | B 전 | B 후 | C 전 | C 후 |
|---|---|---|---|---|
| 계획↔실적 둘 다(36문) | 2.8% | 11.1% | 13.9% | 33.3% |
| 짝 성립(같은 절 계획서 + 짝 실적보고서) | 8.3% | 38.9% | 80.6% | 80.6% |
| 관계 질문 전체(75문) | 10.7% | 12.0% | 46.7% | 58.7% |

[표 5-9] 계획↔실적 짝 개선 전후

질문에 문서 이름을 넣은 경우도 쟀다(실험 로그 13절). 처음에는 묶어 적은 이름을 절 이름으로 읽어 오히려 나빠졌고(정답 문서 53.8%), 이름이 그
사업의 문서 이름이면 그 문서로 좁히도록 고친 뒤 70.0% 가 됐다.

### 5.2.3 생성 모델 교체 기준

모델 교체에 대비해 검색·답·갈래 판정을 한 실행으로 재는 기준을 만들었다(scripts/195). v1 의 검색 놓침을 하나씩 보니 대부분 시험지 문제(같은 제목의
절을 가진 문서가 여럿, 지워진 정답)여서 시험지를 고친 v2 를 확정했다(실험 로그 14·17절).

| 항목 | v1(80문 · 답 10) | v2(136문 · 답 30) |
|---|---|---|
| 검색 정답 문서@k · 같은 판 · 같은 사업 | 0.60 · 0.85 · 0.988 | 0.89 · 0.993 · 1.0 |
| 검색 시간 중앙값 | 6.9초 | 3.4초 |
| 답 오류 · 빈 답 · 근거 밖 숫자 있는 답 | 0 · 0 · 2 | 0 · 0 · 0 |
| 근거에 정답 문서 | 0.8 | 0.9 |
| 답 전체 · 생성 시간 중앙값 | 134초 · 105초 | 16.6초 · 13.1초 |
| 갈래 판정 50 — 규칙 일치 · 빈칸 채움 | 0.92 · 0.96 | 0.92 · 0.96 |

[표 5-10] 생성 모델 교체 기준 v1 과 v2

시험지가 달라 v1 과 v2 의 차를 개선 폭으로 읽지 않는다. 검색 값의 상승은 대부분 모호한 문항과 지워진 정답을 뺀 몫이고, 답 시간 단축은 답 꼴 정리와
추측 디코딩(5.6절)이 낸 것이다.

### 5.2.4 벡터 색인 이전

사업 문서 벡터(10-18 운영 1,586,051개)를 운영 서버 메모리의 배열에서 PostgreSQL pgvector[36] 의 HNSW[37] 색인으로 옮겼다(ADR-0057). 같은 고정 질문
80문에서 정답 문서 적중은 0.688 에서 0.675 로 1문 차였고, 검색 시간은 3.49초에서 1.85초로 줄었으며, 운영 서버 메모리에서 5GB 넘는 배열이 빠졌다.
근사 검색의 정확 계산 대비 recall@10 은 0.915 다.

## 5.3 문서 처리(판독·반입)

### 5.3.1 판독 엔진 선택

스캔 PDF 판독 엔진은 같은 쪽·같은 잣대로 비교해 골랐다. 사업 문서 24건(사업마다 하나, 본문 3쪽)을 세 엔진으로 읽었다(ADR-0050).

| 엔진 | 어절 F1 평균 | 쪽당 시간 |
|---|---|---|
| Writer 27B 이미지 판독 | 0.839 | 165초(서빙 장비, 다른 일과 겹침) |
| MinerU[19][20](한국어 OCR) | 0.690 | 7.6초(학습 장비 GPU) |
| docling[21](기본 OCR) | 0.334 | 5.6초 |

[표 5-11] 스캔 판독 엔진 비교(scripts/171, 세 엔진 모두 성공한 23건)

docling 은 한국어를 깨진 글로라도 많이 내 「글이 충분하다」 는 검사를 통과했기 때문에 판독 경로에서 뺐다. 대량 처리는 처리량 때문에 MinerU 로
두고, 짧은 스캔 문서와 사진은 27B 판독을 먼저 쓴다. 앞서 MinerU 의 다른 엔진(hybrid-engine), dots.ocr[73] 와도 비교했는데 각각 「Ⅱ유형」 → 「표유형」
같은 오독과 본문 추출량 절반, 고유명사 오독과 영어 환각이 나와 쓰지 않았다(실험 로그 1절).

판독 모델은 글자층의 65.7% 가 깨진 36쪽 스캔 매뉴얼로도 비교했다(실험 로그 6절). 계획 밖의 소형 판독 모델은 5쪽을 21초에 읽었지만 없는 문장을
지어내고 줄을 반복했고, 27B 원본은 128초가 걸렸지만 원문을 그대로 읽었다. 이 결과로 판독을 27B 로 통일했다.

디지털 PDF 는 판독하지 않고 원본 글자층을 글자 좌표째 읽는다. MinerU 가 글자층이 있는 문서를 스캔으로 다뤄 「기초과학」 을 「기추과하」 로 읽은
사고가 있었고, 글자층을 먼저 감지해 경로를 나누는 것으로 원천에서 막았다(실험 로그 2절).

## 5.4 생성·문서 작성 품질

### 5.4.1 답의 근거와 숫자

답의 핵심 위험은 근거에 없는 숫자다. 답을 내기 전에 수치 검증기가 답의 숫자를 모델에 실제로 건넨 근거와 대조해 근거에 없는 숫자에 「(근거 확인
필요)」 를 붙이게 하고, 답 꼴을 「핵심 먼저, 요점 5개 이내, 600자 안팎」 으로 바꿨다(실험 로그 15절). 표시하지 않은 근거 밖 숫자가 있는 답은
2/10 에서 0/10 이 됐고, 시험지 v2 의 답 30문에서도 0 이었다. 배점 반영 판정은 합성 표본에서 낱말 맞추기만으로 0/55 이던 것을 학습된 표현의 돋보임

### 5.4.5 오픈 모델과 SFT 학습 모델 비교(ADR-0069)

Writer 의 첫 SFT 학습본(LoRA[15] r32, BF16 바탕, 2에폭, 학습 4,434쌍)을 운영에 넣을지를 정하려고, 모델 하나만 바꾸고 질문·플랫폼 코드·생성 설정·채점
모델은 그대로 둔 채 운영 오픈 모델(Qwen3.8-27B NVFP4)과 비교했다. 비교 대상(어댑터를 합쳐 NVFP4 로 다시 줄인 병합본)과 네 묶음(시험 220문항, 맥락 이해
30문항, 문서 작성 시나리오, 속도), 채택 기준은 4.11.4 절의 [표 4-21] 에 적었다.

학습이 서빙에 실제로 들어갔는지는 생성 전에 정답의 토큰당 평균 로그확률로 먼저 본다. 이 절차가 필요했던 까닭은 첫 시도에서 드러났다. 서빙 장비에
LoRA 어댑터로 얹은 판은 정답 로그확률과 첫 토큰 확률이 오픈 모델과 소수 다섯째 자리까지 같았다. 어댑터의 키 접두(model.layers)가 서빙 모델의 이름
(model.language_model.layers)과 맞지 않아 어댑터가 적용되지 않은 것으로 본다. 생성 결과만 봤다면 「SFT 가 별 차이 없다」 로 잘못 읽었을 것이다.

이 어댑터 판은 결과적으로 같은 모델을 두 번 돌린 대조군이 됐다. 둘 중 나은 답 고르기 220문항에서 이김 49 · 비김 129 · 짐 42, 점수 0.516(95% 구간
0.475~0.559)이었다. 채점 모델이 같은 모델끼리도 41% 문항에서 한쪽을 골랐고, 두 순서의 판정이 23% 엇갈렸다. 이 폭이 채점 잡음이며, 병합본의
차이는 이 폭을 넘을 때만 차이로 읽는다.

|---|---|---|
| 정답 토큰당 평균 로그확률(40문항) | -1.845 | -1.153 |
| 시험 220문항 chrF · ROUGE-L | 27.9 · 16.8 | 36.6 · 27.3 |

| 둘 중 나은 답 고르기(병합본 기준) | — | 0.309(95% 0.264~0.355), 이김 28 · 비김 80 · 짐 112 |
| 같은 모델 두 번 대조군 | 0.516(0.475~0.559) | — |
| 항목 점수(1~5) 지시 · 맥락 · 형식 · 근거 · 문체 · 완결 | 4.95 · 4.96 · 4.87 · 4.98 · 4.52 · 4.94 | 5.00 · 5.00 · 4.91 · 5.00 · 4.77 · 4.995 |

[표 5-18] 오픈 모델과 SFT 병합본 비교(10-24 운영 서버)

결과는 세 가지로 읽힌다.

첫째, 학습은 들어갔고 학습 꼴 안에서는 좋아졌다. 정답 로그확률이 -1.845 에서 -1.153 으로 올랐고, 정답 겹침·길이·질문에 없는 숫자·잘림이 모두
나아졌다.

둘째, 플랫폼 꼴에서는 문서 작업 에이전트가 동작하지 않았다. 학습셋 정답의 틀(「근거 설명: … 답변: …」)이 에이전트의 단계 출력과 작업 메모 갱신에까지
들어가 형식 관문에 걸렸고, 에이전트는 묻기만 되풀이했다. 작업 메모 갱신 출력이 1회차 11턴 모두 학습셋 틀이었고, 평범한 업무 질문에도 플랫폼 답변
지시를 줬을 때 15개 모두 틀이 나왔다(오픈 모델은 45개 모두 0). 학습쌍이 「한 줄 시스템 지시 + 질문 → 틀 답」 한 가지 꼴뿐이었던 것이 원인이다.
시험 문항의 정답 겹침만 봤다면 「SFT 가 낫다」 로 읽었을 것이다.

셋째, 둘 중 나은 답 고르기는 오픈 모델 쪽으로 기울었다(0.309, 대조군 잡음 폭 0.475~0.559 밖). 다만 병합본이 진 문항은 병합본 답이 오픈 답 길이의
0.63배(중앙값), 이긴 문항은 1.10배여서 채점 모델이 자세한 답을 고르는 쪽으로 기운다. 채점 모델이 오픈 모델과 같은 바탕인 점도 있다. 정답 겹침과
판정이 서로 다른 쪽을 가리키므로 시험 문항만으로는 우열을 정하지 않았다. 항목 점수와 맥락 이해는 두 모델 모두 거의 만점이라 위쪽이 막혀 있어 차이를
가르지 못한다.

판단은 이번 병합본을 채택하지 않는 것이다. 운영은 오픈 27B 를 그대로 쓰고, 다음 학습셋에는 플랫폼이 실제로 보내는 꼴(에이전트 단계 JSON, 작업 메모
갱신, 채팅 답, 절 쓰기·고쳐 쓰기 지시)을 넣는다(6.3절). 이 비교에서 얻은 가장 큰 결과는 학습본의 성패를 학습 꼴 시험만으로 판정하면 안 된다는
것, 그리고 정답 로그확률 확인과 대조군 잡음 폭을 비교 절차의 앞에 두어야 한다는 것이다.

## 5.6 서빙 속도

생성 모델 27B 는 젯슨 AGX 토르[11] 두 대에서 vLLM[9] 으로 서빙한다. 정밀도와 디코딩 방식에 따른 속도는 [표 5-20] 과 같다.

| 단계 | 요청 하나 초당 토큰 | 판독 5쪽 | 검토 1건 | 출처 |
|---|---|---|---|---|
| bf16 원본 | 2.4~4.5 | 128초 | 225초 | ADR-0023 |
| NVFP4[12] 양자화 | 10.4~10.8 | 29초 | 82초 | ADR-0023 |
| NVFP4 + MTP[14] 추측 디코딩[13](검토 장비) | 10.6 → 23.8(2.25배, 평균 수용 길이 2.2) | — | — | 실험 로그 16절 |
| NVFP4 + MTP 추측 디코딩(답 장비) | 약 12 → 24.6 | — | — | 실험 로그 16절 |

[표 5-20] 27B 서빙 정밀도와 추측 디코딩

NVFP4 판은 판독 내용이 bf16 과 같았고, 추측 디코딩은 본 모델이 짐작한 토큰을 검증해 받아들이므로 출력 분포가 바뀌지 않는다. 실제로 켠 뒤 갈래 판정
표본 50의 규칙 일치·빈칸 채움(0.92 · 0.96)과 답 근거의 정답 문서(0.8)가 그대로였고, 갈래 판정 한 건은 4.4초에서 2.8초가 됐다.

사람이 기다리는 시간으로 보면 답 전체 시간 중앙값이 기준 v1 134초에서 기준 v2 16.6초가 됐다. 이 단축은 답 꼴 정리(평균 약 1,200 토큰이던 답을
600자 안팎으로)와 추측 디코딩이 함께 낸 것이라 둘을 따로 가르지 않았다. GraphRAG 의 27B 질문 읽기는 검색 한 번에 약 5초를 더하고(1.58초 →
6.45초), 그 대가로 관계 질문 적중을 9% 에서 45% 로 올린다(5.2.2절). SFT 병합본은 첫 글자 0.65초 · 초당 21.5 토큰으로 오픈 모델(0.56초 · 24.3)과
비슷했고, 답이 짧아 문항당 시간은 16.8초로 오픈 모델(29.6초)보다 짧았다.

운영 중의 사고도 서빙 설정을 정하는 근거가 됐다. 추측 디코딩을 켤 때 GPU 메모리 비율 0.35(43GB)가 시작 때 비어 있던 메모리(36GB)보다 커 엔진이 뜨지
못했고 검토·판독이 약 25분 멈췄다. 비율을 0.28(가중치 약 16GB + 캐시 약 27만 토큰)로 낮춰 띄웠고, 켜는 스크립트와 되돌리는 스크립트를 함께 두었다.

물려 운영 구성 값이 0.1 낮게 나왔다. 재색인 때 한 번은 기본 모델이 KURE-v1 로 돌아 색인과 질의 모델이 어긋났고, 서빙 점검(scripts/110)이 잡아내어
다시 만들었다. 5.4.5 의 어댑터 사례도 같은 갈래다. 세 경우 모두 결과만 보면 그럴듯한 값이었고, 어느 모델이 실제로 답했는지를 함께 기록하는 절차가
있어서 잡혔다.

## 5.9 평가의 한계

이 장의 값은 다음 한계 안에서 읽어야 한다.

- 시험지의 성질. 규정 검색의 R@k 는 27B 로 만든 합성 질의로 자기 조각을 찾는 측정이라 절대치가 낙관적이다. GraphRAG 와 기준 v2 의 시험지는
  그래프에서 자동으로 뽑은 절·관계 질문이라 실제 담당자 질문과 다르다. 사람이 쓴 골드셋(평가 계획의 200~500문항)으로 잰 값은 아직 없다.
- 표본 크기. 기준 v2 의 답은 30문, 문서 작성 시나리오는 판마다 3회(SFT 비교는 모델마다 2회)다. 10문 답의 「근거에 정답 문서」 는 잴 때마다 0.5~0.8
  사이로 흔들렸고, 양식 만들기 묶음은 같은 판의 회차 차이가 판 차이만큼 컸다.
- 자기 채점. 문서 작성의 채점 점수와 SFT 비교의 판정은 같은 27B 계열 모델이 매겼다. 판끼리 비교하는 데만 쓰고, 대조군으로 잰 잡음 폭(0.475~0.559)을
  넘는 차이만 읽었다. 사람 블라인드 평가는 GraphRAG 판정의 10문 대조 말고는 아직 없다.
- 정확도 미측정. 서류 갈래 판정과 사업 재판정은 규칙과의 일치율, 옮긴 건수만 있고 사람 정답 대비 정확도는 미측정이다. 학습 전 측정의 30건은
  문항 구성과 통과 기준이 학습 장비 기록에 있어 저장소에서는 미확인이다.
- 개인정보. 잔여 0 은 정규식 기반 검사 결과이며 완전 제거의 증명이 아니다.
- 공동 편집. 지연 값은 헤드리스 크롬 세 창의 측정이다. 큰 문서의 지연과 실브라우저 세 칸 동시 편집은 미측정이다.
- 서빙. 속도 값은 한 번에 한 요청을 보낸 측정이 많아, 여러 사람이 동시에 쓰는 실사용 부하에서의 지연은 미측정이다.
