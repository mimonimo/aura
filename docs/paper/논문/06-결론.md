# 6. 결론

## 6.1 연구 요약 및 기여점

본 프로젝트는 대학 행정 문서를 교외로 내보내지 않고 교내 장비만으로 읽고, 찾고, 쓰는 플랫폼 AURA 를 설계하고 구현했다. 대학 행정은 국고
재정지원사업의 계획서·실적보고서, 규정과 지침, 공문과 서식으로 돌아가며, 이 문서들에는 개인정보와 기관 내부 정보가 들어 있어 상용 클라우드 AI 에
보낼 수 없다. AURA 는 이 제약을 출발점으로 삼아 모든 모델(생성·임베딩·리랭커)을 교내 장비에서 돌리고, 운영 서버·서빙 장비 두 대·학습 장비로 일을
나눴다.

구현한 경로는 다음과 같다. 학교 원본은 원본 장부로 따라가며 형식마다 가장 정확한 길로 읽고(디지털 PDF 는 글자층 직독, 스캔은 MinerU 와 27B 판독,
한글은 자체 hwpx 파서와 kordoc), 표·개인정보·조각·서류 갈래·사업·판본을 정리해 색인과 지식그래프로 만든다. 질문은 27B 가 온톨로지의 말로 읽어
그래프에서 범위를 정하고, 그 안에서 어휘와 의미 검색을 섞어 근거를 찾는다. 답에는 출처를 달고, 근거에 없는 숫자는 수치 검증기가 표시한다. 문서 작성은
같은 검색 위에서 문서 작업 에이전트가 양식을 고르고 절마다 쓰며, 끝에 원본 한글 서식 그대로 완성본을 낸다. 웹 한글 기안기에서는 여러 사람과 AURA 가
한 문서의 서로 다른 칸을 동시에 고친다.

본 프로젝트의 기여는 네 가지로 정리된다.

첫째, 온프레미스 제약 아래에서 대학 행정 문서의 전 경로(반입 → 검색 → 답 → 작성 → 한글 완성본)를 실제 운영 규모로 구현했다. 10-18 운영 기준으로
원본 장부 167,146건, 라이브러리 문서 35,469건, 문서 조각 1,848,580개, 지식그래프 노드 415,834개를 다룬다.

둘째, 판단은 모델이, 실행·관문·기록은 코드가 맡는 구조를 일관되게 적용했다. 서류 갈래, 사업 분류, 질문 읽기, 도구 고르기, 양식 고르기를 27B 가
판단하고, 코드는 그 판단을 안전하게 실행하며 열람 범위·수치 대조·되돌리기 어려운 도구의 관문을 지킨다. 사례마다 규칙을 덧대는 대신 일반 메커니즘으로
고쳤고, 그 결과 GraphRAG 의 관계 질문 적중이 풀텍스트 13% 에서 27B 읽기 58.7% 로 올랐으며 문서 작성의 고쳐 쓰기 반영이 1/3 에서 3/3 으로 나아졌다.

셋째, 온톨로지 기반 GraphRAG 의 효과를 같은 시험지에서 단계만 바꿔 쟀다. 절 질문의 정답 문서 적중은 풀텍스트 18% 에서 그래프 64%, 27B 읽기 70% 로
올랐고, 답 근거에 정답 문서가 든 비율은 31% 에서 75% 가 됐다.

넷째, 측정이 거짓 수치를 내는 경로를 찾아 절차로 막았다. 서빙 장비 설정 없이 뜬 측정의 CPU 대체, 색인과 질의 모델의 어긋남, 채점이 같은 본문의 다른
판본을 놓친 일, 서빙에 적용되지 않은 LoRA 어댑터, 학습 꼴 시험만으로는 보이지 않는 에이전트 깨짐이 그것이다. 모델 교체 기준(scripts/195), 정답
로그확률 확인, 같은 모델 두 번 대조군의 잡음 폭은 다음 모델을 들일 때 그대로 쓰는 비교 절차로 남았다.

## 6.2 결과 평가 및 한계점

5장의 결과를 목표에 비추어 평가하면 다음과 같다.

검색과 답. 규정 검색 운영 구성은 합성 질의 기준 R@1 0.740, 정답 5위 안 85.7%(10-18)이고, 생성 모델 기준 v2 에서 답 30문의 오류·빈 답·표시하지 않은
근거 밖 숫자가 모두 0, 근거에 정답 문서 0.9, 답 전체 시간 중앙값 16.6초다. 근거를 갖춘 초안과 출처라는 목표는 시험지 수준에서 충족됐다. 다만 시험지가
합성 질의이거나 그래프에서 자동으로 뽑은 질문이라 실제 담당자 질문의 성능은 아직 모른다.

문서 처리. 스캔 판독은 비교 측정으로 엔진을 골랐고(어절 F1 27B 0.839, MinerU 0.690, docling 0.334), 반입 충실도는 표 평문·쪽 번호·판본·갈래에서
측정 가능한 개선을 냈다. 서류 갈래와 사업 판정은 규칙과의 일치율만 있고 사람 정답 대비 정확도는 미측정이다. 처리 실패 111건(암호·손상)은 읽지
못하고, 표 칸 배경색 같은 시각 서식은 보존하지 못한다.

문서 작성. 짧은 서식(예산 변경·출장 보고·기안문)은 끝까지 채우고, 지어낸 숫자는 모든 측정에서 0 이었다. 긴 사업계획서는 절 맡기기로 끝까지 쓰는
판이 나왔지만 맡길지의 판단이 판마다 흔들리고 시간이 3~4배 든다. 시나리오 평가는 판마다 3회이고 채점이 같은 27B 의 자기 평가라 판 비교에만 쓸 수
있다. 목표 유지와 「표로」 고쳐 쓰기는 고친 잣대로 다시 재야 한다.

파인튜닝. Writer 의 첫 SFT 학습본은 학습 꼴 시험에서 나아졌으나(chrF 27.9 → 36.6) 플랫폼 꼴에서 문서 작업 에이전트가 동작하지 않아 채택하지 않았다.
지금 서비스의 답과 문서 작성은 학습하지 않은 오픈 27B 가 RAG·GraphRAG 근거로 만든다. 파인튜닝은 실문서의 사실을 외우게 하지 않고 컨텍스트 구성
리즈닝에만 쓴다는 방향은 유지하되, 그 효과는 아직 입증하지 못했다.

공동 편집. 칸 단위 공동 편집은 글자 지연 중앙값 221ms, 잃은 글자 0 으로 동작한다. 그러나 한 칸은 먼저 잡은 사람만 쓰고 칸 밖 고침은 한 사람씩이며,
서버가 파일에 써 넣는 칸 글은 글만이라 칸 안 서식은 문서 전체 저장 때만 남는다. 칸 자리 재기는 기안기 내부(공개 API 밖)에 기대므로 제품 판이 바뀌면
칸 표시가 빠질 수 있다. 측정은 헤드리스 크롬 세 창이었다.

운영과 제도. 열람 등급 값 체계, 개인정보의 부서 검토, 보관·삭제 범위, 외부 전송 관련 남은 결정 6건은 학교 확인이 필요하다. 부서 드라이브는 각 부서
총괄 책임자의 실제 연결이 남았다. 개인정보 탐지는 정규식과 이름표 문맥 기반이라 이름표 없는 이름·주소를 놓칠 수 있어, 학습 반출에는 사람 검수를 함께
요구한다.

요컨대 AURA 는 사람이 검수하는 초안을 내는 도구로서 경로와 안전장치를 갖추었고, 그 품질은 자동 시험지 수준에서 확인됐다. 실제 담당자의 질문과 문서로
잰 품질, 사람 평가, 학습본의 효과가 남은 과제다.

## 6.3 향후 연구 방향

### 6.3.1 파일럿 운영과 실사용 평가

파일럿 계획(docs/pilot-plan.md)대로 최근 3~5년의 유사 유형 사업 계획서 20~30건과 대응 결과보고서로 범위를 고정해 실제 공고 한 건을 처음부터 끝까지
진행한다. 공고에서 출처가 붙은 초안과 배점 반영 보고서까지 내고, 담당자가 그 초안을 실제로 고친 양과 까닭을 기록한다. 같은 기간에 담당자가 직접
쓴 질의로 검색 골드셋(200~500문항, 검수자 2인 판정과 일치율 기록)을 만들어 합성 시험지의 낙관을 걷어 낸 값을 잰다. 생성 결과는 어느 모델의 것인지
가린 사람 평가(문체·논리 5점)로 보고, 언어 모델 판정은 보조로만 쓴다. 서류 갈래와 사업 판정도 표본을 사람이 판정해 정확도를 잰다.

### 6.3.2 Writer v2 학습 데이터

첫 SFT 의 실패 원인은 학습쌍이 한 가지 꼴뿐이었다는 것이다. 다음 학습셋은 플랫폼이 실제로 모델에 보내는 꼴로 만든다(협업 기록 요청 K61). 방법은
대부분 자동이다.

1. 시험 DB(운영 아님)에서 공개 문서와 가상 사업으로 문서 작업 시나리오(scripts/202 꼴)를 많이 돌리며, 플랫폼이 모델에 보내는 메시지(시스템 지시·도구
   목록·대화)를 LLM 클라이언트 한 곳에서 그대로 기록한다. 대상은 에이전트 단계 JSON, 작업 메모 갱신, 채팅 답, 절 쓰기·고쳐 쓰기다.
2. 지금 운영 중인 오픈 27B 로 답을 만들고, 자동 점검(형식 관문 통과, 202 채점 점수, 자료에 없는 숫자 없음, 학습셋 틀 0)을 통과한 것만 남긴다.
3. 절 본문은 v1 의 좋은 답(4,434쌍)을 실제 절 쓰기 요청 꼴 안에 넣어, 정답 근접·짧음·지어낸 숫자 0 이라는 v1 의 장점을 살린다.
4. 사람 검토는 종류마다 수십 건 표본으로 한다.

넘기기 전 점검은 이번 비교 도구를 그대로 쓴다. 평범한 질문의 학습셋 틀 0/45, 문서 작성 시나리오 두 회차 모두 작업본 생성과 절 채움, 시험 문항 chrF 가
v1 이상, 맥락 30/30 이다. 서빙은 병합본을 NVFP4 로 다시 줄인 판으로 하거나, 어댑터 키를 서빙 모델의 이름 접두에 맞춘다. 비교 때는 정답 로그확률로
학습이 실제로 들어갔는지를 먼저 보고, 같은 모델 두 번 대조군의 잡음 폭을 넘는 차이만 읽는다.

### 6.3.3 큰 문서의 공동 편집

행정 서식은 100~400쪽에 이르는 것이 있다. 이런 문서에서 칸 목록 읽기, 칸 자리 재기, 파일 써 넣기가 얼마나 걸리는지를 재고, 느린 단계는 보이는 쪽의
칸만 재기, 써 넣기 묶음 늘리기처럼 일반 방법으로 줄인다. 실브라우저 세 칸 동시 편집 시연과 실제 계정 여럿의 운영 확인을 마치고, 여러 앱 프로세스가
같은 DB 를 쓸 때 1초 주기로 건너가는 알림 지연을 줄인다. 칸 서식째 주고받기(지금 시험 기능, 기본 꺼짐)는 서버가 파일에 써 넣는 단계까지 서식을 지키게
한 뒤 켤지를 정한다.

### 6.3.4 모델 교체

실제 도입 때는 더 큰 모델이나 파인튜닝한 판으로 바뀐다. 이를 위해 모델 이름·문맥 길이·생각 끄기 인자를 코드에 두지 않고 연결 설정에 두었고, 문맥
한도는 서버가 알려 주는 값을 쓰며, 작업 메모와 최근 대화의 몫도 한도에 대한 비율로 정했다. 교체 절차는 후보 모델을 운영 설정을 바꾸지 않고 같은
데이터 상태에서 운영 모델과 나란히 재는 것이다(scripts/195 의 검색·답·갈래 판정과 ADR-0069 의 네 묶음). 문맥이 큰 모델로 바꾸면 긴 서식을 한 문맥에서
다룰 수 있어 절 맡기기가 필요한 경우가 줄 것으로 기대되며, 이 효과도 같은 시나리오로 잰다.

### 6.3.5 그 밖의 과제

- 한글 완성본을 한글 프로그램에서 직접 열어 확인하고, 예산표·명단표의 행 순서 대응을 넣는다.
- 용어를 모르고 상황으로 묻는 규정 질의(9-20 측정 22.7%)를 위해 구현해 둔 질의 확장의 운영 모델을 정한다.
- 계획↔실적 짝의 엄격 지표(33.3%)를 올리고, 사업별 목표 대비 실적 화면과 결과보고서 초안 연결을 잇는다.
- 같은 부서 안 동료 문서 검토 의견, 그래프의 사업 별칭·연관 관계를 열람 범위로 거를지를 정한다.
- 열람 등급 값 체계, 보관·삭제 범위, 외부 전송 결정 6건을 학교 기준에 맞춰 확정한다.

본 프로젝트가 만든 것은 사람이 검수하는 초안을 내는 교내 행정 AI 의 뼈대와, 그 품질을 속지 않고 재는 절차다. 실제 담당자의 문서와 질문으로 이 절차를
돌리는 파일럿을 거치면, 교내 행정의 반복적인 문서 탐색과 초안 작성 부담을 줄이는 데 실질적으로 쓰일 것으로 기대된다.
