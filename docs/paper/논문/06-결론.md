# 6. 결론

## 6.1 연구 요약 및 기여점

본 프로젝트는 대학 행정 문서를 교외로 내보내지 않고 교내 장비만으로 읽고, 찾고, 쓰는 플랫폼 AURA를 설계하고 구현했다. 국고 재정지원사업의
계획서·실적보고서, 규정과 지침, 공문과 서식에는 개인정보와 기관 내부 정보가 들어 있어 상용 클라우드 AI에 보낼 수 없다. 그래서 생성·임베딩·리랭커 모델을 모두 교내에서 돌리고, 운영 서버·서빙 장비 두 대·학습 장비로 일을 나눴다.

원본은 글자층 직독, MinerU[19]·27B 판독, kordoc[25] 가운데 형식에 맞는 방법으로 읽고, 표·개인정보·조각·서류 종류·사업·판본을
정리한 뒤 색인과 지식그래프로 만든다. 질문은 27B가 온톨로지의 말로 읽어 그래프에서 범위를 정하고, 그 안에서 어휘·의미 검색을
RRF[35]로 섞어 근거를 찾는다. 답에는 출처를 달고, 근거에 없는 숫자는 수치 검증기가 표시한다. 문서 작업 에이전트는 양식을 고르고 절마다 쓴 뒤 원본 한글
서식 그대로 완성본을 내며, 웹 한글 기안기에서는 여러 사람과 AURA가 한 문서의 서로 다른 칸을 동시에 고친다.

기여는 네 가지다.

첫째, 온프레미스 제약 아래에서 반입 → 검색 → 답 → 작성 → 한글 완성본의 전 경로를 교내 문서 약 3만 5천 건 규모로 구현했다.

둘째, 판단은 모델이, 실행·관문·기록은 코드가 맡는 구조를 일관되게 적용했다. 27B가 서류 종류, 사업 분류, 질문 읽기, 도구·양식 고르기를 판단하고,
코드는 그 판단을 실행하며 열람 범위·수치 대조·되돌리기 어려운 도구의 관문을 지킨다. 사례별 규칙 대신 일반 메커니즘으로 고친 결과 GraphRAG의 관계
질문 적중은 전문 검색 13%에서 27B 질문 해석과 후보 보정을 더한 뒤 58.7%로, 「더 구체적으로」 고쳐 쓰기 반영은 1/3에서 3/3으로 올랐다.

셋째, 온톨로지 기반 GraphRAG[39]의 효과를 같은 시험지에서 단계만 바꿔 쟀다. 절 질문의 정답 문서 적중은 전문 검색 18%, 그래프 64%, 27B 질문 해석까지 더하면 70%
였고, 답 근거에 정답 문서가 든 비율은 31%에서 75%로 올랐다.

넷째, 측정이 거짓 수치를 내는 경로 세 가지(서빙 장비 설정 없이 뜬 측정의 CPU 대체, 색인과 질의 모델의 어긋남, 채점이 같은
본문의 다른 판본을 놓친 일)를 찾아 절차로 막았다. 모델 교체 기준과 정답 로그확률 확인은 다음 모델을 들일 때 쓸 비교 절차로 남았다.

## 6.2 결과 평가 및 한계점

검색과 답. 규정 검색 운영 구성은 합성 질의 기준 R@1 0.740, 정답 5위 안 85.7%다. 생성 모델 기준선 측정(v2)에서 답 30문은 오류·빈 답·표시하지 않은
근거 밖 숫자가 모두 0, 근거에 정답 문서 0.9, 답 전체 시간 중앙값 16.6초였다. 출처를 단 근거 기반 답이라는 목표는 시험지 수준에서 충족됐으나, 시험지가 합성 질의이거나 그래프에서
자동으로 뽑은 질문이어서 실제 담당자 질문에서의 성능은 모른다.

문서 처리. 스캔 판독 엔진은 어절 F1 비교로 골랐고(27B 0.839, MinerU 0.690), 반입 충실도는 표 평문·쪽 번호·판본·종류에서
개선을 측정했다. 서류 종류와 사업 판정은 규칙과의 일치율만 있고 사람 정답 대비 정확도는 재지 않았다. 처리 실패 111건(암호·손상)은 읽지
못하고, 표 칸 배경색 같은 시각 서식은 보존하지 못한다.

문서 작성. 짧은 서식(예산 변경·출장 보고·기안문)은 끝까지 채우고, 지어낸 숫자는 모든 측정에서 0이었다. 긴 사업계획서는 절 맡기기로 끝까지 쓴
판이 나왔지만 맡길지의 판단이 판마다 흔들리고 시간이 3~4배 든다. 시나리오 평가는 판마다 3회이고 채점이 같은 27B의 자기 평가여서 판 비교에만
쓴다. 목표 유지와 「표로」 고쳐 쓰기는 고친 잣대로 다시 재야 한다. 행을 늘린 서식 표가 쪽 아래로 넘치던 문제는 큰 표를 셀 단위로 나누고 본문과
함께 흐르게 해 고쳤다. 완성본 서식을 위해 기관 서식 프로필과 서식 대조 도구를 더했으나, 기준 문서의 모양에 가깝게 맞추는 일은 아직 진행 중이다.

파인튜닝. 더 큰 모델에 적용하기 위해 Writer 27B로 학습 절차와 데이터를 검증했다. 교내 실문서 학습쌍 4,434쌍으로 LoRA[15] SFT를 하자 시험 문항
220개의 chrF가 27.9에서 36.6으로 오르고 질문에 없는 숫자가 든 답이 4.1%에서 0%가 됐다. 사실 대신 근거를 모아 답을 구성하는 방식만 학습해도
학습한 형식의 요청에서는 정확성과 형식이 함께 나아진다는 것을 확인했다. 한편 학습쌍이 한 가지 형식뿐이라 에이전트 단계의 JSON 요청에도 학습 틀로
답해, 문서 작성 시나리오에서 작업본을 만들지 못했다(2/2 → 0/2). 더 큰 모델에서는 플랫폼 요청 형식을 학습 데이터에 넣어 이를 보완한다.
지금 서비스는 바탕 27B가 RAG·GraphRAG 근거로 답한다.

공동 편집. 칸 단위 공동 편집은 글자 지연 중앙값 221ms, 잃은 글자 0으로 동작하고, 제목·표 칸의 고침과 서식, AURA가 쓴 절이 다시 불러오기 없이
열린 화면에 들어간다. 다만 한 칸은 먼저 잡은 사람만 쓰고, 표·그림·용지처럼 칸에 담기지 않는 고침은 한 사람씩 문서 전체를 저장해 다른 화면이 새
판을 받는다. 칸 자리 재기는 공개 API 밖의 기안기 내부에 기대어 제품 판이 바뀌면 칸 표시가 빠질 수 있고, 지연 값은 헤드리스 크롬 세 창의 측정이다.

운영과 제도. 열람 등급 값 체계, 개인정보의 부서 검토, 보관·삭제 범위, 외부 전송에 관한 남은 결정 6건은 학교 확인이 필요하다. 부서 드라이브는 각
부서 총괄 책임자의 실제 연결이 남았다. 개인정보 탐지는 정규식과 이름표 문맥에 기대어 이름표 없는 이름·주소를 놓칠 수 있으므로, 학습 반출에는 사람
검수를 함께 요구한다. 설치·운영 묶음(deploy/)으로 다른 기관도 플랫폼을 설치하고 자체 LLM 서버·사용자·원본 폴더를 관리 화면에서 연결할 수 있으나,
설치부터 백업·복구·업데이트까지의 검증은 빈 Ubuntu 컨테이너에서만 했다.

## 6.3 향후 연구 방향

### 6.3.1 파일럿 운영과 실사용 평가

파일럿 계획대로 최근 3~5년의 유사 유형 사업 계획서 20~30건과 대응 결과보고서로 범위를 고정하고, 실제 공고 한 건을 처음부터
끝까지 처리한다. 출처가 붙은 초안과 배점 반영 보고서를 내고, 담당자가 고친 양과 까닭을 기록한다. 같은 기간에 담당자가 직접 쓴 질의로 검색
골드셋(200~500문항, 검수자 2인 판정과 일치율 기록)을 만들어 합성 시험지보다 현실에 가까운 값을 잰다. 생성 결과는 모델을 가린 사람 평가(문체·논리
5점)로 보고, 언어 모델 판정[65]은 보조로만 쓴다. 서류 종류와 사업 판정도 표본을 사람이 판정해 정확도를 잰다.

### 6.3.2 SFT를 더 큰 모델로

27B로 검증한 학습 절차와 데이터(교내 실문서 학습쌍, 사람 검수, 개인정보 반출 관문, 사업 단위 학습·검증·시험 분리)를 더 큰 모델에 그대로 적용해
운영 모델로 쓴다. 27B 실험에서 드러난 에이전트 단계 JSON 형식 문제를 막기 위해, 학습 데이터에는 플랫폼이 실제로 모델에 보내는 요청 형식을 대부분
자동으로 만들어 더한다.

1. 시험 DB(운영 아님)에서 공개 문서와 가상 사업으로 문서 작업 시나리오를 돌리며, 에이전트 단계 JSON·작업 메모 갱신·채팅 답·절 쓰기·
   고쳐 쓰기 요청의 메시지(시스템 지시·도구 목록·대화)를 LLM 클라이언트에서 기록한다.
2. 자동 점검(형식 관문 통과, 시나리오 채점 점수, 자료에 없는 숫자 없음)을 통과한 답만 남긴다.
3. 절 본문은 이번 학습쌍(4,434쌍)의 좋은 답을 실제 절 쓰기 요청 형식에 넣어, 정답 근접·알맞은 길이·지어낸 숫자 0이라는 장점을 잇는다.
4. 사람 검토는 종류마다 수십 건 표본으로 한다.

학습 전후는 정답 로그확률로 학습이 들어갔는지 먼저 본 뒤, 시험 문항 chrF·ROUGE-L·항목 점수, 맥락 이해 30문항, 문서 작성 시나리오를 같은 조건으로
비교한다.

### 6.3.3 큰 문서의 공동 편집

행정 서식에는 100~400쪽에 이르는 것이 있다. 451쪽 문서까지 칸 목록 읽기·칸 자리 재기·파일 써 넣기의 지연을 재어 바뀐 부분만 주고받기로 줄였고(5.5절), 실브라우저 세 칸 동시 편집도 운영 시연 화면에서 확인했다. 남은 일은 여러 실제 계정의 지연 재기, 표·도식이 든 AURA 절을
다시 불러오기 없이 열린 화면에 넣기, 여러 앱 프로세스가 같은 DB를 쓸 때 1초 주기로 건너가는 알림 지연 줄이기다.

### 6.3.4 모델 교체

실제 도입 때 더 큰 모델이나 파인튜닝한 판으로 바꿀 수 있도록 모델 이름·문맥 길이·생각 끄기 인자를 코드가 아닌 연결 설정에 두었고, 문맥
한도는 서버가 알려 주는 값을 쓰며, 작업 메모와 최근 대화의 몫도 한도에 대한 비율로 정했다. 교체 때는 운영 설정을 그대로 둔 채 후보 모델을 운영 모델과 같은 데이터로 나란히 잰다(검색·답·종류 판정과 ADR-0069의 네 묶음). 문맥이 큰 모델에서 절 맡기기가 덜 필요해지는지도 같은 시나리오로
잰다.

### 6.3.5 그 밖의 과제

- 한글 완성본을 한글 프로그램에서 직접 열어 확인하고, 예산표·명단표의 행 순서 대응을 넣는다.
- 용어를 모르고 상황으로 묻는 규정 질의를 위해 구현해 둔 질의 확장의 운영 모델을 정한다.
- 계획↔실적 짝의 엄격 지표(33.3%)를 올리고, 사업별 목표 대비 실적 화면과 결과보고서 초안을 잇는다.
- 같은 부서 안 동료 문서 검토 의견, 그래프의 사업 별칭·연관 관계를 열람 범위로 거를지 정한다.
- 열람 등급 값 체계, 보관·삭제 범위, 외부 전송 결정 6건을 학교 기준에 맞춰 확정한다.

요컨대 AURA는 사람이 검수하는 초안을 내는 경로와 안전장치를 갖추었고, 품질은 자동 시험지 수준에서 확인됐다. 실제 담당자의 문서와 질문으로 잰 품질,
사람 평가, 더 큰 모델로의 학습 적용은 파일럿과 다음 단계에서 확인한다.
