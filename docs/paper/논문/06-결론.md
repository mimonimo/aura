# 6. 결론

AURA는 행정 문서를 학교 밖으로 보내지 않고도 근거를 갖춘 초안을 만들 수 있음을 자동 시험 수준에서 확인했다. 남은 일은 실제 담당자의 문서와 질문으로
품질을 다시 측정하고, 검증한 학습 절차를 더 큰 모델에 적용하는 것이다.

## 6.1 연구 요약 및 기여점

본 연구의 기여는 1.2에서 제시한 네 기술, 곧 문서 데이터화, GraphRAG, 문서 작업 에이전트, 칸 단위 공동 편집을 교내 장비만으로 하나의 서비스로 묶고
각각의 효과를 측정한 데 있다. 생성·임베딩·리랭커 모델을 모두 교내에서 운영하고 운영 서버, 서빙 장비 두 대, 학습 장비로 역할을 나누었으며,
네 기술 모두 「판단은 모델, 실행은 코드」라는 같은 구조 위에 있다.

문서 데이터화에서는 교내 문서 약 3만 5천 건을 형식에 맞는 경로(글자층 직독, MinerU[21]·27B 판독, kordoc[27])로 읽고 표·개인정보·조각·서류 종류·사업·판본을
정리해 색인과 지식 그래프로 구축하였다. 판독 경로는 실물 문서 비교로 정했으며, 스캔 판독의 어절 F1은 27B가 0.839로 가장 높았다(MinerU 0.690).

GraphRAG에서는 27B가 질문을 온톨로지 용어로 해석하고 코드가 그래프에서 검색 범위를 정한 뒤 어휘 검색과 의미 검색을 RRF[37]로 결합하였다.
같은 시험지에서 그래프 단계만 바꾸어 측정한 결과, 절 질문(73문)에서 정답 문서가 상위 5건에 든 비율은 전문 검색 18%, 그래프 64%, 27B 질문 해석을
더한 구성 70%였다. 관계 질문(75문)은 전문 검색 13%에서 27B 질문 해석을 더한 구성 45%로 올랐고([표 5-3] 회차), 이후 계획서와 실적보고서를 짝으로
함께 담도록 보정하자 보정 실험의 기준선 46.7%에서 58.7%가 되었다.

문서 작업 에이전트는 양식을 고르고 절마다 작성한 뒤 원본 한글 서식 그대로 완성본을 만든다. 약점이던 고쳐 쓰기는 사례별 규칙을 덧대지 않고, 고쳐 쓰기
전용 도구를 두고 하위 절을 [개요] → [본문] → 자기 점검 순서로 쓰게 하며 문단 끝에 근거 출처를 적게 하는 방식으로 개선하였다. 그 결과 「더 구체적으로」
요청의 반영이 1/3에서 3/3으로 늘었고, 지어낸 숫자는 개선 전후 모두 0건이었다.

칸 단위 공동 편집은 기안기가 공동 편집 API를 제공하지 않는 조건에서 모든 문단을 칸으로 감싸 칸마다 편집권을 주는 방식으로 구현하였다. 한 화면에서
입력한 글자가 다른 화면에 나타나기까지의 지연은 중앙값 221ms였고 사라진 글자는 없었으며, AURA 에이전트도 사람과 같은 경로로 한 문서에 작성한다.

이와 함께 측정이 잘못된 수치를 내는 경로 세 가지를 찾아 절차로 막았다. 서빙 장비 설정 없이 실행된 측정에서 모델이 CPU용으로 대체된 경우, 색인
모델과 질의 모델이 어긋난 경우, SFT 어댑터가 서빙 모델에 적용되지 않은 경우다. 모델 교체 기준과 정답 로그확률 확인은 다음 모델을 도입할 때 쓸
비교 절차로 정리하였다.

## 6.2 결과 평가 및 한계점

5장의 결과는 근거 기반 답과 초안이라는 목표를 시험지 수준에서 달성했음을 보여 주지만, 시험지 대부분이 합성 질의이거나 그래프에서 자동으로 뽑은
질문이어서 실제 담당자 질문에서의 성능은 아직 모른다. 영역별 결과와 한계는 다음과 같다.

검색과 답 생성에서, 규정 검색 운영 구성은 합성 질의 표본 300건(10-18 회차)에서 R@1 0.740, R@5 0.857을 기록했다. 모델 교체 기준 v2 시험(답 30문)에서는
오류, 빈 답, 표시되지 않은 근거 밖 숫자가 모두 0건이었고, 근거에 정답 문서가 포함된 비율은 90%, 답 전체 시간 중앙값은 16.6초였다. 다만 GraphRAG의
이점은 시험지가 그래프에서 나왔다는 점 때문에 과대평가되었을 수 있으므로, 6.3.1의 골드셋으로 다시 확인해야 한다.

문서 처리에서, 반입 충실도는 표 평문화, 쪽 번호, 판본, 서류 종류 항목에서 개선을 측정하였다. 그러나 서류 종류와 사업 판정은 규칙과의 일치율만 있고
사람 정답 대비 정확도는 측정하지 않았다. 처리에 실패한 111건(암호·손상)은 읽지 못하며, 표 칸 배경색 같은 시각 서식은 보존하지 못한다.

문서 작성에서, 짧은 서식(예산 변경·출장 보고·기안문)은 끝까지 채웠고 지어낸 숫자는 모든 측정에서 0건이었다. 긴 사업계획서는 절 맡기기로 끝까지 작성한
판이 나왔지만, 절을 맡길지에 대한 판단이 회차마다 달라지고 시간이 3~4배 든다. 시나리오 평가는 판마다 3회이고 채점이 같은 27B의 자기 평가이므로
판 비교에만 쓴다. 행을 늘린 서식 표가 쪽 아래로 넘치던 문제는 해결하였다. 완성본 서식을 위해 기관 서식 프로필과 서식 대조 도구를 추가했으나,
기준 문서의 모양에 가깝게 맞추는 작업은 아직 진행 중이다.

파인튜닝은 더 큰 모델에 적용하기 위한 실험으로 수행하였으며, Writer 27B에서 학습 절차와 데이터를 검증하였다. 교내 실문서 학습쌍 4,434쌍으로 LoRA[17] SFT를
수행하자 시험 문항 220개의 chrF가 27.9에서 36.6으로 오르고, 질문에 없는 숫자가 든 답의 비율이 4.1%에서 0%로 줄었다. 사실이 아니라 근거를 모아 답을
구성하는 방식만 학습해도, 학습한 형식의 요청에서는 정확성과 형식이 함께 나아졌다. 한편 학습쌍이 한 가지 형식뿐이어서 에이전트 단계의 JSON 요청에도
학습한 형식으로 답했고, 그 결과 문서 작성 시나리오에서 작업본을 만들지 못했다(2/2 → 0/2). 더 큰 모델에서는 플랫폼의 요청 형식을 학습 데이터에 포함해
이를 보완한다. 현재 서비스에서는 기반 모델인 27B가 RAG와 GraphRAG 근거로 답한다.

공동 편집에서, 칸 단위 공동 편집은 헤드리스 크롬 세 창 측정에서 글자 지연 중앙값 221ms, 손실 글자 0자를 기록했고, 제목과 표 칸의 수정 내용과 서식,
AURA가 작성한 절이 다시 불러오기 없이 열린 화면에 반영된다. 실제 기안기에서 세 창이 Enter를 섞어 빠르게 동시 입력한 시험과 AURA가 다른 절을 쓰는
동안의 동시 입력 시험에서도 글자 누락, 문단 겹침, 사본 밀림은 없었다. 다만 한 칸은 먼저 잡은 사람만 편집할 수 있고, 표·그림·용지처럼
칸에 담기지 않는 수정은 한 사람씩 문서 전체를 저장한 뒤 다른 화면이 새 판을 받는다.
또한 칸 위치 측정은 공개 API가 아닌 기안기 내부 구조에 의존하므로 제품 버전이 바뀌면 칸 표시가 어긋날 수 있다.

운영과 제도에서, 열람 등급 체계, 개인정보의 부서 검토, 보관·삭제 범위, 외부 전송에 관한 남은 결정 6건은 학교의 확인이 필요하다. 부서 드라이브는 각
부서 총괄 책임자의 실제 연결이 남아 있다. 개인정보 탐지는 정규식과 항목 이름 같은 문맥 단서에 의존하므로 단서 없이 적힌 이름이나 주소를 놓칠 수 있고,
그래서 더 큰 모델용 학습 데이터 반출에는 사람 검수를 더한다. 설치·운영 묶음(deploy/)을 이용하면 다른 기관도 플랫폼을 설치하고 자체 LLM 서버, 사용자,
원본 폴더를 관리 화면에서 연결할 수 있으나, 설치부터 백업·복구·업데이트까지의 검증은 빈 Ubuntu 컨테이너에서만 수행하였다.

## 6.3 향후 연구 방향

다음 단계는 실제 담당자의 문서와 질문으로 다시 측정하는 데서 시작한다. 그 위에서 학습 절차를 더 큰 모델에 옮기고, 큰 문서의 공동 편집과 모델 교체를 다듬는다.

### 6.3.1 파일럿 운영과 실사용 평가

파일럿에서는 최근 3~5년의 유사 유형 사업계획서 20~30건과 그에 대응하는 결과보고서로 범위를 한정하고, 실제 공고 한 건을 처음부터
끝까지 처리한다. 출처가 붙은 초안과 배점 반영 보고서를 만들고, 담당자가 고친 분량과 이유를 기록한다. 같은 기간에 담당자가 직접 작성한 질의로 검색
골드셋(200~500문항, 검수자 2인 판정과 일치율 기록)을 구축해 합성 시험지보다 현실에 가까운 성능을 측정한다. 생성 결과는 모델을 가린 사람 평가(문체·논리
5점 척도)로 평가하고, 언어 모델 판정[72]은 보조 지표로만 사용한다. 서류 종류와 사업 판정도 표본을 사람이 판정해 정확도를 측정한다.

### 6.3.2 더 큰 모델의 SFT

27B로 검증한 학습 절차와 데이터(교내 실문서 학습쌍, 개인정보 반출 검사, 사업 단위 학습·검증·시험 분리)를 더 큰 모델에 적용해 운영 모델로 쓰는 것이
목표다. 더 큰 모델용 절차에서는 사람 검수를 더한다(이번 4,434쌍은 자동 생성분이다). 27B 실험에서 드러난 에이전트 단계의 JSON 형식 문제를 막기 위해,
학습 데이터에는 플랫폼이 실제로 모델에 보내는 요청 형식의 예시를 대부분 자동으로 생성해 추가한다. 절차는 다음과 같다.

1. 운영과 분리된 시험 DB에서 공개 문서와 가상 사업으로 문서 작업 시나리오를 실행하며, 에이전트 단계 JSON, 작업 메모 갱신, 채팅 답, 절 작성,
   고쳐 쓰기 요청의 메시지(시스템 지시·도구 목록·대화)를 LLM 클라이언트에서 기록한다.
2. 형식 검사 통과, 시나리오 채점 점수, 자료에 없는 숫자의 부재를 자동으로 점검해 이를 통과한 답만 남긴다.
3. 절 본문은 이번 학습쌍(4,434쌍)의 좋은 답을 실제 절 작성 요청 형식에 넣어, 정답에 가까운 내용, 적절한 길이, 지어낸 숫자 0건이라는 장점을 유지한다.
4. 사람 검토는 요청 종류마다 수십 건의 표본으로 수행한다.

학습 전후 비교에서는 먼저 정답 로그확률로 학습 결과가 반영되었는지 확인한 뒤, 시험 문항의 chrF·ROUGE-L·항목 점수, 맥락 이해 30문항, 문서 작성 시나리오를
같은 조건으로 비교한다.

### 6.3.3 대용량 문서 공동 편집

행정 서식에는 100~400쪽에 이르는 문서도 있다. 451쪽 문서까지 칸 목록 읽기, 칸 위치 측정, 파일 쓰기의 지연을 측정하고 바뀐 부분만 주고받는 방식으로
지연을 줄였으며(5.5절), 실제 기안기의 세 창 동시 입력도 확인하였다. 남은 과제는 여러 실제
계정에서의 지연 측정, 표나 도식이 포함된 AURA 절을 다시 불러오기 없이 열린 화면에 반영하는 기능, 여러 앱 프로세스가 같은 DB를 사용할 때 1초 주기로
전달되는 알림의 지연 단축이다.

### 6.3.4 모델 교체

실제 도입 때 더 큰 모델이나 파인튜닝한 모델로 바꿀 수 있도록 모델 이름, 문맥 길이, 생각 모드 끄기 인자를 코드가 아닌 연결 설정에 두었다. 문맥
한도는 서버가 알려 주는 값을 사용하며, 작업 메모와 최근 대화가 차지하는 분량도 한도에 대한 비율로 정하였다. 교체할 때는 운영 설정을 그대로 둔 채
후보 모델과 운영 모델을 같은 데이터로 나란히 측정한다. 문맥 길이가 큰 모델에서 절 맡기기의 필요성이 줄어드는지도 같은 시나리오로 측정한다.

### 6.3.5 기타 과제

한글 완성본을 한글 프로그램에서 직접 열어 확인하고, 예산표와 명단표의 행 순서 대응 기능을 추가한다. 용어를 모른 채 상황으로 묻는 규정 질의를 위해
구현해 둔 질의 확장 기능에 쓸 운영 모델을 정한다. 계획서와 실적보고서 짝의 엄격 지표(33.3%)를 높이고, 사업별 목표 대비 실적 화면을 결과보고서 초안
작성과 연결한다. 같은 부서 동료의 문서 검토 의견과 그래프의 사업 별칭·연관 관계를 열람 범위에 따라 제한할지 결정한다. 열람 등급 체계, 보관·삭제 범위,
외부 전송에 관한 결정 6건도 학교 기준에 맞춰 확정한다.

AURA는 사람이 검수하는 초안을 만드는 경로와 안전장치를 갖추었고, 그 품질은 자동 시험지 수준에서 확인되었다. 실제 담당자의 문서와 질문으로 측정한 품질,
