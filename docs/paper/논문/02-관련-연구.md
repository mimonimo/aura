# 2. 관련 연구

이 장에서는 AURA 를 구성하는 기술을 영역별로 소개한다. 영역은 생성 모델과 서빙(2.1), 모델 학습(2.2), 문서 읽기와 변환(2.3), 검색(2.4),
지식 표현(2.5), 개인정보 보호(2.6), 에이전트(2.7), 문서 작성과 공동 편집(2.8), 웹 플랫폼(2.9)이다. 기술마다 무엇인지, 왜 골랐는지,
AURA 에서 어떻게 쓰는지를 차례로 적는다. 수치는 본 프로젝트의 측정 기록에서 가져온 것이며, 측정 방법과 상세 결과는 5장에서 다룬다.

## 2.1 생성 모델과 서빙

### 2.1.1 Qwen3.8-27B

Qwen 은 알리바바의 Qwen 팀이 공개하는 오픈웨이트 언어모델 계열이다[2]. AURA 의 생성 모델은 Qwen3.8-27B 이다[3]. 27B 는 매개변수가 약 270억 개라는 뜻이고,
모든 매개변수가 매 토큰 계산에 참여하는 dense 구조다. 이 모델은 이미지 입력을 받는 멀티모달 모델이고 긴 문맥을 다룬다.

선택 이유는 네 가지다. 첫째, 이미지 입력이 되므로 스캔 문서와 사진 판독을 별도 모델 없이 맡길 수 있다. 서빙 장비가 두 대뿐이라 모델을 여럿 띄울 메모리가
없기 때문에, 대화 답·문서 작업·반입 검토·이미지 판독·질문 해석·서류 종류 판정을 한 모델이 맡는 것이 유리하다. 실제로 판독용 소형 모델을 시험했을 때는
없는 문장을 지어내고 줄을 반복해 쓰지 않았다. 둘째, dense 구조는 LoRA 학습(2.2.1)과 vLLM 어댑터 서빙(2.1.2)이 검증된 경로다. 셋째, NVIDIA 가 젯슨용
NVFP4 양자화 판을 공식 배포한다[4](2.1.3). 넷째, Apache 2.0 라이선스라 학습본에 다른 이름을 붙이거나 표시 의무를 지는 조건이 없다.

국내 모델과도 비교했다. EXAONE 4.0 32B[6]는 글만 입력받아 판독을 맡길 수 없고 라이선스가 연구·교육 목적 한정이다. HyperCLOVA X SEED Think 32B[7]는 이미지 입력을
받지만 서비스에 제공사 표시를 하고 학습본 이름 앞에 제공사 이름을 붙여야 하는 조건이 있으며 젯슨용 공식 양자화 판이 없다. 한국어 지식을 묻는 벤치마크
KMMLU[8]에서는 국내 모델이 앞선다(EXAONE 4.0 32B 75.2, HyperCLOVA X 32B 71.3, 같은 Qwen 계열의 Qwen3-VL 32B 47.4, Qwen3.8-27B 자체 수치는 확인하지 못함).
그러나 AURA 는 규정·실적 같은 지식을 모델이 외우지 않고 검색으로 넣어 주는 구조이므로, 모델에 요구되는 것은 주어진 문서를 읽고 형식에 맞춰 쓰는 능력이다.
이 격차가 결과에 직접 오지 않는다고 판단해 Qwen3.8-27B 를 택했다.

초기 서빙 검증(9월 1주)은 같은 계열의 MoE(전문가 혼합) 모델 Qwen3.5-35B-A3B[5]로 수행했다. MoE 는 전체 매개변수 가운데 일부(이 모델은 약 3B)만
토큰마다 계산에 참여해 같은 크기의 dense 모델보다 빠르다. 당시 검증 장비에서 첫 토큰 87ms, 초당 30.8 토큰을 확인했다. 이후 이미지 입력과 학습 경로를 이유로
생성 모델을 Qwen3.8-27B 로 바꾸었다.

AURA 에서 이 모델은 용도별 연결(답, 반입 검토, 이미지 판독, 업무 도우미)로 호출된다. Qwen 계열은 답 전에 스스로 따져 보는 출력(생각 모드)이 기본으로 켜져 있는데,
끄지 않은 호출이 출력 한도를 생각에 다 써 값 없이 실패한 일이 있어 교내 호출은 생각 모드를 기본으로 끈다. 답 쓰기에서 켜 본 비교는 7배 느리고 채점이 나빠졌다.

### 2.1.2 vLLM

vLLM 은 대규모 언어모델 추론 서빙 엔진이다[9]. 주의(attention) 계산에 쓰는 키·값 캐시를 운영체제의 가상 메모리처럼 고정 크기 블록으로 나눠 관리하는
PagedAttention 기법[10]으로 메모리 낭비를 줄이고 여러 요청을 묶어 처리한다. OpenAI 호환 HTTP API 를 제공하므로 클라이언트 코드는 서버 종류에 덜 묶인다.

선택 이유는 세 가지다. 학습본 LoRA 어댑터를 기본 모델 위에 얹어 서빙할 수 있고, 동시 요청을 처리하며, 양자화 정밀도(NVFP4·FP8·bf16)를 고를 수 있다.
또한 JSON 스키마로 출력 형식을 강제하는 구조화 출력[50]을 지원해, 에이전트 단계 출력이나 질문 해석 결과를 형식 오류 없이 받을 수 있다.

AURA 는 서빙 엔진을 vLLM 하나로 통일했다. 초기 검증 장비(aarch64 + Blackwell)에서는 릴리스 이미지가 GPU 아키텍처를 지원하지 않아 실패했고 nightly 이미지로
동작을 확인했다. 움직이는 태그 대신 이미지 다이제스트로 판을 고정해 같은 서빙 환경을 재현한다. 문맥 한도는 서버가 `/v1/models` 로 알려 주는 값을 먼저 쓰고,
모델 이름·문맥 길이·생각 모드 인자는 코드에 넣지 않고 연결 설정에 둔다. 더 큰 모델로 바꿀 때 코드 수정 없이 설정만 바꾸기 위해서다.

### 2.1.3 NVIDIA Jetson AGX Thor 와 NVFP4 양자화

Jetson AGX Thor 는 NVIDIA 의 임베디드·엣지용 컴퓨팅 장비로, CPU 와 GPU 가 하나의 통합 메모리(본 장비 122GB)를 함께 쓴다[11]. AURA 는 이 장비 두 대를 서빙에 쓴다.
한 대(토르 02)는 대화 답과 문서 작성처럼 사람이 기다리는 일을, 다른 한 대(토르 03)는 반입 검토·이미지 판독 같은 배치 일과 임베딩·리랭커 서비스를 맡는다.

양자화는 모델 가중치를 더 적은 비트로 표현해 메모리와 계산량을 줄이는 기법이다. NVFP4 는 NVIDIA 가 Blackwell 세대 GPU 를 위해 제시한 4비트 부동소수점 형식으로,
작은 블록마다 배율 값을 따로 두어 4비트로도 정밀도 손실을 줄인다[12]. 젯슨 토르처럼 메모리 대역폭이 속도를 정하는 장비에서는 가중치를 줄이는 것이 곧 속도다.

원본 bf16 판은 요청 하나에 초당 2~5 토큰이라 실사용이 어려웠다. NVFP4 판으로 바꾸자 초당 10.4~10.9 토큰이 나왔고 판독 5쪽은 128초에서 29초로 줄었으며,
같은 입력으로 비교한 검토·판독 내용은 같았다. 정밀도는 NVFP4, FP8, bf16 순으로 우선하되, 원본과 같은 입력으로 검토와 판독을 비교하고 초안의 수치를 대조해
손실이 허용 범위 안일 때만 쓴다는 채택 조건을 두었다.

### 2.1.4 다음 토큰 예측 층을 이용한 추측 디코딩

추측 디코딩(speculative decoding)은 가벼운 예측기가 다음 토큰 몇 개를 미리 짐작하고 본 모델이 한 번에 검증해 맞은 만큼 받아들이는 기법이다[13].
검증을 본 모델이 하므로 출력 분포는 그대로이고, 맞힌 만큼 빨라진다. 여러 토큰 예측(multi-token prediction, MTP)[14] 층을 함께 학습한 모델은 그 층을
예측기로 쓸 수 있다.

AURA 는 Qwen3.8-27B 에 든 MTP 층으로 추측 디코딩을 켰다. 작은 층이 토큰 두 개를 미리 짐작하고 본 모델이 검증한다. 생성 속도는 검토 쪽에서 초당 10.6 토큰에서
23.8 토큰으로, 답 쪽에서 약 12 토큰에서 24.6 토큰으로 올랐다. 이때 GPU 메모리 비율을 너무 높게 잡아 같은 장비의 임베딩·리랭커와 메모리를 다투다
검토가 약 25분 멈춘 일이 있어, 비율은 같은 장비의 다른 서비스를 고려해 정한다.

## 2.2 모델 학습

### 2.2.1 LoRA 와 SFT

지도 미세조정(Supervised Fine-Tuning, SFT)은 입력과 바라는 출력의 쌍으로 사전학습된 모델을 추가 학습하는 방법이다. LoRA(Low-Rank Adaptation)[15]는 원래 가중치를
고정하고, 각 층에 작은 저랭크 행렬 두 개를 더해 그것만 학습한다. 학습할 매개변수가 크게 줄어 메모리가 적게 들고, 학습 결과가 작은 어댑터 파일로 남아
기본 모델 위에 얹거나 합칠 수 있다.

AURA 는 학습 장비(DGX)에서 Hugging Face 의 PEFT[16]와 TRL[17] 라이브러리로 bf16 LoRA SFT 를 한다. 학습 문맥은 16,384 토큰이다. 운영에 넣을 때는 어댑터를
기본 모델에 합친 뒤 운영과 같은 NVFP4 로 다시 양자화한다.

학습의 범위는 좁게 정했다. 사업의 사실과 수치는 해마다 바뀌는데 모델이 외운 값은 바뀌지 않고, 내부 원문을 학습에 넣으면 개인정보가 모델에 남는다.
그래서 실문서의 사실은 검색과 지식 그래프로 공급하고, 파인튜닝은 「질문을 보고 무엇을 어디서 찾아 어떤 근거로 답을 구성할지」라는 문맥 구성 추론과
문서 구조에만 쓴다. 첫 SFT 학습셋은 학습 4,434건, 검증 346건, 시험 220건이다. 이 학습본을 오픈 모델과 같은 시험으로 비교한 결과는 5장에서 다룬다.

### 2.2.2 Label Studio

Label Studio 는 오픈소스 데이터 주석 도구다[18]. 웹 화면에서 작업 묶음을 만들고 사람이 항목별로 판정·수정한 결과를 내보낼 수 있다.

AURA 는 학습 데이터의 사람 검수에 Label Studio 를 쓴다. 자동 검사(근거 기록 유무, 근거가 그 턴에 글자 그대로 보이는지, 숫자가 근거에 있는지, 중복)를 통과한
학습 후보를 검수자가 근거·구조·맥락·개인정보 네 항목으로 확인하고 채택·수정·폐기한다. 네 항목이 모두 확인된 것만 승인본이 된다. 자동 생성물을 정답으로
간주하지 않기 위한 절차다.

## 2.3 문서 읽기와 변환

### 2.3.1 MinerU

MinerU 는 OpenDataLab 이 공개한 문서 구조 추출 도구다[19][20]. PDF 에서 제목·문단·표·그림·수식의 배치를 검출하고 읽기 순서를 정하며, 글자층이 없는 스캔본은
OCR 로 읽는다. 표는 병합 셀을 포함한 HTML 로 낸다.

AURA 는 9월 초 문서 파서들을 같은 실물 문서로 비교해 MinerU 를 기본으로 정했다. 비교 대상 가운데 dots.ocr 는 고유명사 오독과 영어 환각이 있었고, docling[21]은
스캔 판독 대결(어절 F1)에서 0.334 로 MinerU 0.690 에 크게 뒤져 스캔 경로에서 뺐다. 같은 대결에서 Qwen3.8-27B 의 이미지 판독은 0.839 로 가장 높았지만,
대량 처리에서는 처리량 때문에 MinerU 를 기준으로 두고 짧은 스캔 문서와 사진에만 27B 판독을 쓴다. 디지털 PDF 에서도 표·2단·읽기 순서 같은 구조는 MinerU 로 잡고,
그 위에 원본 글자를 좌표로 덮어쓴다.

[그림 2-8] MinerU 로고(출처: MinerU 공식 저장소(opendatalab/MinerU)) (그림 docs/images/logos/f2-08-mineru.png)

### 2.3.2 PDF 글자층 직독과 보조 OCR

디지털 PDF 는 글자와 그 좌표가 파일 안에 들어 있다. 이것을 OCR 로 다시 읽으면 멀쩡한 글자까지 오인식한다. 실제로 한 OCR 엔진으로 전부 읽었을 때
「기초과학」이 「기추과하」로 바뀐 일이 있었다. 그래서 AURA 는 PDFium[22] 으로 원본 글자층을 글자 좌표째 읽는다. 고루 뽑은 여섯 쪽의 쪽당 글자 수가 충분하고
깨진 글자 비율이 0.15 미만이면 디지털 PDF 로 보고 직독하며, 그렇지 않으면 스캔본으로 보고 OCR 경로로 보낸다.

화면의 원본 복원 보기는 원본 쪽 그림을 배경에 두고 그 위에 투명한 글자층을 얹는다. 디지털 PDF 는 글자 좌표를 그대로, 스캔본은 MinerU 의 줄 좌표를 쓴다.
사진은 27B 이미지 판독, MinerU OCR, Tesseract[23] 순서로 시도한다.

[그림 2-9] 원본 복원 보기 화면 — 원본 쪽 위의 투명 글자층 (그림 docs/images/figures-1025/f2-09-original-text-layer.jpg)

### 2.3.3 한글 문서 형식과 kordoc

한글(HWP)은 한글과컴퓨터의 문서 형식으로, 국내 공공기관과 대학 행정의 기본 형식이다. 옛 HWP 5 형식은 이진 복합 파일이고, HWPX 는 XML 문서를 ZIP 으로 묶은
개방형 형식(OWPML, KS X 6101)이다[24]. 교내 서식 대부분이 이 두 형식이다.

HWPX 는 AURA 가 자체 OWPML 파서로 읽는다. 표준 라이브러리만으로 ZIP 과 XML 을 풀어 문단·표·글상자·머리말까지 구조로 읽는다. 옛 HWP 는 kordoc[25] 을 1순위로 쓴다.
kordoc 은 한글(HWP 3/5·HWPX)·PDF·XLSX·DOCX 를 자체 파서로 읽어 마크다운·JSON 으로 내는 MIT 라이선스 도구다. 비교 측정에서 옛 HWP 30MB 파일을 1초에 읽었고
(기존 pyhwp[26] 경로 3분) 글자 양이 같았으며 중첩·병합 표를 보존했다. AURA 는 kordoc 을 판 고정한 포크로 보관하고, 실패하면 pyhwp 경로로 물러난다.
kordoc 의 출력은 AURA 의 내부 문서 구조(문단·제목·표 좌표·그림)로 옮기고, 그 뒤의 개인정보 처리·조각 나누기·색인은 AURA 의 것을 그대로 쓴다.

한글 완성본을 낼 때도 HWPX 의 구조를 이용한다. 구역 XML 을 다시 직렬화하지 않고 원본 바이트를 그대로 둔 채 절 제목 문단 뒤에 문단·표·그림 XML 을 끼워 넣고,
ZIP 항목 순서와 압축 방식은 유지한 채 바뀐 항목만 다시 쓴다(서식 보존 채우기). 변환기로 새로 만든 한글 파일은 표 테두리·칸 폭·글꼴이 원래 서식과 달라
제출용으로 쓸 수 없기 때문이다. 한글 프로그램을 원격 조작하는 방식도 시험했지만 윈도우 장비가 필요하고 불안정해 버렸다.

## 2.4 검색

### 2.4.1 검색 증강 생성

검색 증강 생성(RAG)은 질문과 관련된 문서 조각을 먼저 검색하고, 그 조각을 언어모델의 입력에 넣어 답을 생성하는 방식이다[1]. 모델이 학습하지 않은 최신 정보나
기관 내부 정보로 답할 수 있고, 답의 근거를 출처로 보일 수 있다.

AURA 의 검색은 두 색인과 하나의 그래프로 이뤄진다. 규정 색인은 교내 규정·지침을 조문 단위로, 사업 문서 색인은 사업 문서 조각을 담는다. 두 색인을 합치지 않는 것은
규정 질문에 사업 문서 조각이, 사업 질문에 규정이 섞이지 않게 하려는 것이다. 검색 조건에는 질문한 사람의 열람 권한이 SQL 조건으로 들어간다. 답을 만든 뒤에
거르면 모델이 이미 권한 밖 자료를 읽은 뒤이기 때문이다.

[그림 2-13] RAG 개념도 — 검색, 근거 묶기, 생성 (그림 docs/images/diagrams/c2-13-rag.png)

### 2.4.2 KURE 임베딩과 대조 학습

임베딩 모델은 문장을 고정 길이 벡터로 바꿔 뜻이 가까운 문장이 가까운 벡터가 되게 한다. KURE-v1 은 고려대학교 NLP&AI 연구실이 다국어 임베딩 모델 BGE-M3[30]를
한국어 데이터로 추가 학습해 공개한 모델이다[29]. 1,024차원 벡터를 내고 MIT 라이선스이며, 한국어 검색 벤치마크에서 상위권이었다.

KURE-v1 은 일반 문장에는 좋지만 「교원업적평가」, 「차년도 사업비 이월」 같은 교내 용어와 규정 문체에는 약했다. 그래서 AURA 는 KURE-v1 을 바탕으로 교내 문서에 맞춘
임베딩 학습본(Embed v2)을 만들었다. 규정 조각마다 생성 모델로 합성 질의를 세 형식(실무형, 공고 요구사항형, 키워드형)으로 만들고, 운영 검색이 실제로 올린 후보 가운데
정답이 아닌 조각을 어려운 오답으로 쓴다. 손실은 정답 쌍을 가깝게, 배치 안 오답과 어려운 오답을 멀게 하는 대조 학습 손실 InfoNCE[31](온도 0.05)이다.
채택 기준은 임베딩 단독 지표가 아니라 운영 하이브리드 검색 위에서 정답 후보가 실제로 더 많이 올라오는지다. 첫 학습본(v1)은 단독 지표만 오르고 운영 경로에서
이득이 없어 버렸고, 두 번째 학습본(v2)을 채택했다. 공개 KURE-v2(다중 벡터)도 측정했으나 운영 경로에서 이득이 없어 채택하지 않았다.

### 2.4.3 bge-reranker-v2-m3 리랭커

리랭커는 질문과 후보 조각을 한 쌍씩 함께 읽어 관련도 점수를 매기는 교차 인코더(cross-encoder)다. 질문과 조각을 따로 벡터로 만드는 임베딩보다 느리지만 더 정확하므로,
검색이 올린 소수의 후보를 다시 줄 세우는 데 쓴다. bge-reranker-v2-m3 는 BAAI 가 공개한 다국어 리랭커로, BGE-M3 와 같은 계열이고 Apache 2.0 라이선스다[32].

AURA 는 운영 하이브리드가 실제로 올린 후보 목록에 대해 정답 쪽 확률을 높이는 목록 단위 학습으로 리랭커 학습본(Rerank v1)을 만들었다. 문서 단위 홀드아웃에서
R@1 이 0.649 에서 0.711 로, MRR 이 0.751 에서 0.790 으로 올라 채택했다. 서빙 장비 GPU 로 옮기자 질의당 3.75초가 0.07초가 되었고, 그 덕에 재정렬 후보를 10개에서
20개로 늘렸다. 리랭커는 규정 검색에만 쓴다. 사업 문서 검색에서는 그래프 절 축과 문서당 조각 수 제한과 겹쳐 오히려 손해라 꺼 두었다. 생성 모델로 후보를
다시 매기는 방식도 비교했으나 덜 정확하고 53배 느렸다.

### 2.4.4 Kiwi 형태소 분석과 어휘 검색

한국어는 조사와 어미가 붙어 어절 단위로는 낱말이 맞지 않는다. 어휘 검색을 하려면 형태소 분석으로 낱말을 뽑아야 한다. Kiwi 는 C++ 로 구현된 한국어 형태소 분석기로
파이썬 바인딩을 제공하고 사용자 사전을 지원한다[33]. 조사 시점에 활발히 유지되는 사실상 유일한 선택지였다.

AURA 의 어휘 축은 Kiwi 로 명사와 두 글자 이상 영문 약칭을 뽑고, 띄어 쓴 복합 명사를 붙이며, 드문 낱말에 무게를 주는 IDF 로 점수를 낸다. 이는 BM25[34] 계열의
고전적 어휘 검색과 같은 발상이다. 색인과 질의가 같은 낱말 함수를 쓰고, 사업 문서 쪽은 낱말을 미리 뽑아 PostgreSQL 전문 색인(GIN)에 둔다.

### 2.4.5 RRF 하이브리드 검색

하이브리드 검색은 어휘 검색과 의미 검색의 결과를 섞는다. 두 검색의 점수는 척도가 달라 그대로 더할 수 없으므로 순위로 섞는다. RRF(Reciprocal Rank Fusion)[35]는
문서 d 의 융합 점수를 각 검색 결과에서의 순위 r 로 1/(k + r) 을 구해 더한 값으로 정한다. 점수 보정 없이도 안정적이고 구현이 단순하다.

AURA 는 k=60 으로 두 축의 순위를 섞고, 어휘 축에 0.4, 의미 축에 1.0 의 가중을 준다. 가중 스윕에서 0.2~0.5 가 고원이었고, 학습 문서를 뺀 질의로 다시 재도
후보 진입률이 가중 0~0.6 에서 같아 0.4 를 유지했다. 동가중(1.0) 대비 MRR 이 0.045 높았다. 사업 문서 쪽은 어휘 1위 조각이 섞은 순위에서 밀리지 않게 지킨다.
행정 질문에는 사업 약칭·규정 이름처럼 글자 그대로 맞아야 하는 말과 「학생이 휴학하려면」처럼 뜻으로 찾아야 하는 말이 함께 있어, 한 축만으로는 어느 한쪽을 놓친다.

### 2.4.6 PostgreSQL 과 pgvector

PostgreSQL 은 오픈소스 관계형 데이터베이스다[38]. pgvector 는 PostgreSQL 에 벡터 자료형과 근접 이웃 검색 색인을 더하는 확장이다[36]. 근사 검색 색인으로 HNSW[37]를
지원하는데, HNSW 는 벡터를 여러 층의 근접 그래프로 이어 두고 위층에서 아래층으로 내려가며 가까운 이웃을 찾는다.

별도 벡터 데이터베이스 대신 pgvector 를 고른 것은 문서 정보·권한·부서·서류 종류 조건을 벡터 검색과 같은 SQL 안에서 걸 수 있고, 조인·트랜잭션·백업이 한 시스템으로
일원화되기 때문이다. AURA 는 사업 문서 조각 벡터 1,586,051개(10월 18일 운영)를 halfvec 1,024차원 HNSW 색인에 둔다. 운영 서버 메모리에 벡터 배열을 올리던 방식에서
pgvector 로 옮기자 같은 고정 질문 80문에서 정답 문서 적중이 0.688 에서 0.675 로 1문 차이였고, 검색 시간은 3.49초에서 1.85초로 줄었으며, 운영 서버 메모리에서
5GB 넘는 배열이 빠졌다. 근사 검색이라 정확 계산 대비 recall@10 은 0.915 였다. 지식 그래프의 노드와 관계도 같은 PostgreSQL 에 표로 둔다.

## 2.5 지식 표현

### 2.5.1 온톨로지와 지식 그래프

온톨로지는 한 분야의 개념(클래스)과 개념 사이의 관계, 그리고 지켜야 할 제약을 명시적으로 정의한 것이다. 지식 그래프는 온톨로지에 따라 실제 대상(노드)과
관계(간선)를 이은 데이터다. GraphRAG[39]는 문서 조각의 유사도만이 아니라 그래프 구조를 함께 써서 검색 범위를 정하거나 근거를 모으는 RAG 방식을 가리킨다.

AURA 가 온톨로지를 쓰는 이유는 두 가지다. 문서가 수만 건이면 사업·연차·서류 종류를 먼저 좁히고 그 안에서 찾아야 하고, 「계획 대비 실적」이나 「앞 단계 사업」처럼
문서 사이 관계를 묻는 질문은 관계가 데이터로 있어야 답할 수 있다. AURA 의 노드 종류는 여덟(사업 묶음, 사업, 기관, 연차, 문서, 절, 단위과제, 성과지표)이고,
관계는 포함, 계획↔실적, 평가, 앞·뒤 단계, 편입, 연관, 주관 부처·전담기관, 성과지표 측정 등이다. 관계마다 근거(문서·절 위치나 외부 출처 URL)를 달고,
근거를 댈 수 없는 관계는 만들지 않는다. 2026-10-25 기준 노드 415,686개, 관계 583,062개이고, 사업 노드는 136개(10월 18일 집계)다.

질문은 생성 모델이 온톨로지의 말(사업 번호, 연도, 차수, 서류 종류, 따라갈 관계)로 읽어 형식이 강제된 JSON 으로 내고, 그래프 탐색은 코드가 결정적으로 한다.
같은 시험지에서 절 질문의 정답 문서가 상위 5건 안에 든 비율은 전문 검색 18%, 그래프(이름 맞추기) 64%, 그래프와 모델의 질문 해석 70% 였다.

### 2.5.2 OWL·RDF 와 SHACL

RDF 는 「주어-서술어-목적어」 세 값으로 정보를 표현하는 W3C 표준 데이터 모델이고[41], OWL 은 RDF 위에서 클래스·속성·제약을 정의하는 온톨로지 언어다[40].
SHACL 은 RDF 그래프가 지켜야 할 모양(shape)을 정의하고 검사하는 W3C 표준이다[42].

AURA 는 그래프 자체는 PostgreSQL 표에 두되, 표준 층으로 온톨로지 설계도를 rdflib[43]로 OWL·RDF 로 내보내고 pySHACL[44]로 SHACL 규칙을 검사한다.
규칙은 「연차는 사업 하나에만 속하고 연도는 1990~2035」, 「문서의 서류 종류는 하나까지이고 사업·연차에 속하거나 기관 업무 문서」, 「관계는 기준 다섯
(구조, 분류, 식별자 일치, 추출, 유사도) 가운데 하나에 근거 하나 이상」 등이다. 그래프를 다시 지을 때마다 검사가 돌고, 측정 시점의 위반은 0건이었다.
설계도는 그래프 탐색 화면에서 내려받아 Protégé[45] 같은 온톨로지 편집 도구로 열 수 있다.

## 2.6 개인정보 보호

### 2.6.1 Presidio

Presidio 는 Microsoft 가 시작한 오픈소스 개인정보 탐지·비식별화 프레임워크다[47]. 정규식·체크섬·개체명 인식을 조합한 인식기(recognizer)로 개인정보를 찾고,
찾은 대상을 가리거나 바꾼다. 사용자 정의 인식기를 끼워 넣는 구조가 공식 사용 방식이다.

AURA 는 Presidio 위에 한국형 패턴 인식기 8종을 얹었다. 주민등록번호와 사업자번호는 체크섬으로 검증하고, 계좌·학번·생년월일·성명은 「계좌번호:」, 「성명」 같은
이름표 문맥이 있을 때만 잡는다. 표에서는 옆 칸의 직위 문맥으로 성명을 한 번 더 가린다.

가림의 범위는 쓰는 곳에 따라 나눴다. 교내 담당자가 업무로 보는 원문을 모두 가리면 일을 할 수 없고, 학습 데이터나 밖으로 나가는 글은 반드시 가려야 한다.
그래서 내부 열람의 가림은 관리자 설정으로 켜고 끄고, 학습 반출은 이 설정과 상관없이 별도 사본에서 전체 탐지와 사람 검수를 거친다. 밖으로 나가는 글에는
고위험 형식(주민번호·이메일·휴대전화·카드번호)을 언제나 한 번 더 검사하고, 가림에 실패하면 내보내지 않는다. 배포 점검의 전체 잔여 검사(10월 9일)에서 문서 41,764건·
조각 1,973,998개 가운데 가렸어야 할 잔여는 0건이었다. 다만 이 검사는 정규식 기반이라 이름표 없는 이름·주소를 놓칠 수 있으므로 완전 제거의 증명은 아니다.

## 2.7 에이전트

### 2.7.1 도구 사용 에이전트와 구조화 출력

언어모델 에이전트는 모델이 상황을 보고 다음 행동(도구 호출)을 고르고, 도구 결과를 다시 보고 다음 행동을 고르는 과정을 되풀이해 과제를 푼다.
ReAct[48]는 추론과 행동을 번갈아 내게 하는 대표적인 방식이다.

AURA 의 문서 작업 에이전트는 매 단계 상태(요청, 최근 대화, 프로젝트 문서 목록, 작업본의 절 목록과 빈 절, 받지 못한 값, 지금까지의 단계)를 보고
`{생각, 도구, 인자}` 를 JSON 으로 고른다. 도구는 근거 찾기, 문서 읽기, 절 쓰기·다시 쓰기, 검토, 한글 내보내기, 묻기, 마무리 등 17가지다. 요청 글을 낱말 규칙으로
해석하면 형식이 조금만 달라도 틀린 일을 하므로, 무엇을 할지는 모델이 판단하고 코드는 판단을 안전하게 실행한다. 코드가 지키는 관문은 단계 수 상한,
되돌리기 어려운 도구는 담당자 요청 글에 그 뜻이 있을 때만 실행, 도구 결과 안의 글이 지시를 흉내 내지 못하게 하는 자료 울타리, 열람 범위와 수치 근거 대조다.
출력 형식은 vLLM 의 구조화 출력[50]으로 강제하고, 서버가 스키마 강제를 거절하면 JSON 지시와 파싱으로 물러난다.

[그림 2-23] 에이전트 실행 흐름 — 상태, 도구 선택, 관문, 실행, 기록 (그림 docs/images/diagrams/c2-23-agent.png)

### 2.7.2 단계 추론과 대화 기억

단계 추론(chain-of-thought)[49]은 모델이 답 전에 중간 단계를 글로 써 내려가게 해 복잡한 문제의 정확도를 높이는 방법이다. AURA 는 답 앞에
[1단계: 질문 파악] → [2단계: 근거 확인] → [3단계: 답 구성] 의 짧은 단계 추론을 두고, 화면에는 답만 보이며 추론은 「생각 과정」으로 펼쳐 볼 수 있다.
이 형식은 학습 데이터의 구조 단계 문답과 같다.

긴 대화에서 앞의 내용을 잃지 않도록 작업 메모를 둔다. 답이 끝나면 배경에서 「지금 목표 / 확정된 것 / 진행 상황 / 남은 일」을 갱신하고, 요청에는 메모와 최근 대화
원문을 문맥 한도의 일정 비율(최근 대화 30%, 메모 6%)만큼 넣는다. 개수가 아니라 비율로 정해 모델을 바꾸면 저절로 맞는다. 긴 서식은 메인 에이전트가 필요할 때
같은 모델을 깨끗한 문맥으로 다시 불러 절 하나를 맡기는 방식(서브 에이전트)을 쓴다.

## 2.8 문서 작성과 공동 편집

### 2.8.1 한컴 웹 한글 기안기

한컴 웹 한글 기안기(WebHwpCtrl)는 한글과컴퓨터가 제공하는 웹 브라우저용 한글 문서 편집기다[51]. 별도 프로그램 설치 없이 브라우저에서 HWP·HWPX 문서를 열고
편집하며, 자바스크립트 API 로 필드(누름틀) 읽기·쓰기, 커서 이동, 동작 실행을 제어할 수 있다. AURA 는 13.82.0.208 판을 교내 서버에 두고 쓴다.

선택 이유는 교내 행정 서식이 한글이기 때문이다. 한글 서식을 다른 형식으로 바꿔 편집하면 표와 쪽 배치가 달라진다. 기안기에서 원본을 그대로 열면 담당자는
익숙한 한글 화면에서 고치고, AURA 에이전트가 서버에서 hwpx 의 절 누름틀 뒤에 본문을 넣으면 열린 기안기들이 그 새 판을 다시 불러온다(4장). 기안기에 이미 있는 기능(편집 용지, 쪽 번호, 머리말, 표 편집 등)은
AURA 화면에 다시 만들지 않고 기안기의 동작 실행으로 쓴다. 이를 위해 공개 API 메서드 103개와 실제 등록된 동작 467개를 조사해 사람과 에이전트가 쓸 수 있는
기능 표를 만들었다.

[그림 2-25] 한컴 웹 한글 기안기 화면 — AURA 에이전트(27B)가 절을 쓰는 동안 세 사람이 같은 작업본을 연 모습(시연 계정) (그림 docs/images/figures-1025/f2-25-aura-writing-editor.jpg)

### 2.8.2 공동 편집 기법과 칸 단위 편집권

여러 사람이 같은 문서를 동시에 고치는 공동 편집에는 대표적으로 두 기법이 있다. 연산 변환(Operational Transformation, OT)[52]은 동시에 일어난 편집 연산을 서로의 결과에
맞게 변환해 모든 사본이 같은 결과에 이르게 한다. CRDT(Conflict-free Replicated Data Type)[53]는 병합 순서와 상관없이 같은 결과가 나오도록 설계한 자료구조를 쓴다.
두 기법 모두 문서 내부 모델에 글자 단위로 접근할 수 있어야 한다.

웹 기안기의 공개 API 에는 문서가 바뀌었다는 사건이 없고 문서 내부 모델에 닿을 수 없어 OT·CRDT 를 쓸 수 없다. 쓸 수 있는 것은 필드 API, 필드의 「양식 모드에서 편집 가능」
속성, 양식 보호 모드, 커서 저장·되돌리기다. 그래서 AURA 는 네 안을 비교한 끝에 칸 단위 비관적 임대(lease)를 골랐다. 칸을 처음 고칠 때 그 칸의 편집권을 잡고,
칸 글 전체를 판 번호와 함께 보내며, 서버의 기록을 정답으로 삼는다. 같은 칸을 둘이 동시에 쓰지 않으므로 병합이 필요 없고 공개 API 만으로 된다. 판 번호가 어긋난
변경은 버리지 않고 충돌 사본으로 남긴다. AURA 에이전트도 같은 길로 칸을 쓰는 참여자이며, 사람이 쥔 칸은 쓰지 않는다. 헤드리스 브라우저 세 창으로 잰
한 글자당 다른 화면까지의 지연은 중앙값 221ms, 최대 302ms 였고 잃은 글자는 없었다.

### 2.8.3 SSE

SSE(Server-Sent Events)는 웹 서버가 하나의 HTTP 연결로 브라우저에 사건을 계속 밀어 보내는 표준이다[54]. 브라우저는 EventSource 객체로 받고, 연결이 끊기면
마지막으로 받은 사건 번호(Last-Event-ID)를 붙여 자동으로 다시 연결한다. 서버에서 브라우저 한 방향이고 일반 HTTP 위에서 동작한다.

AURA 의 공동 편집은 밀어 주기를 SSE 로, 변경 보내기를 일반 HTTP POST 로 한다. 양방향 통신 라이브러리(예: Socket.IO)나 별도 협업 프레임워크는 새 의존성과 빌드
단계를 요구하는데, AURA 의 화면은 빌드 없는 정적 자바스크립트다. SSE 는 FastAPI 서버 그대로 쓸 수 있고 끊긴 뒤 이어 받기가 표준에 들어 있어 이 구조에 맞는다.

[그림 2-27] SSE 알림 흐름 — 칸 변경 POST 와 사건 밀어 주기 (그림 docs/images/diagrams/c2-27-sse.png)

### 2.8.4 구글 독스·드라이브 연동

구글 드라이브 API[56]는 드라이브의 파일 목록·내려받기·내보내기를, 구글 독스 API[55]는 문서의 구조 읽기(documents.get)와 원자적 일괄 갱신(documents.batchUpdate)을
제공한다. 인증은 OAuth 2.0[57]으로, 사용자가 허용한 범위 안에서만 접근한다.

AURA 는 담당자 문서 일부가 구글 드라이브에 있어 드라이브를 읽기 전용 문서 원천으로 붙였다. 가져온 문서는 업로드와 같은 처리 경로(부서·등급·개인정보·조각·색인)를
탄다. 또한 구글 독스를 작업본으로 열어 에이전트가 API 로 같은 문서를 읽고 고친다. 독스에 쓰는 것은 교내 내용이 구글로 나가는 외부 전송이므로, 담당자 본인의
학교 계정으로만 연결하고, 넣는 글은 개인정보 검사를 한 번 더 거치며, 모든 쓰기를 감사 기록에 남긴다. 구글 클라이언트 라이브러리를 들이지 않고 HTTP 로 REST 를
직접 불러 의존성을 늘리지 않았다. 사용자는 작업 편집기로 한글 기안기와 구글 독스 가운데 하나를 고른다.

## 2.9 웹 플랫폼

### 2.9.1 FastAPI 와 Jinja2

FastAPI 는 파이썬 타입 힌트를 바탕으로 요청 검증과 API 문서를 자동으로 만드는 비동기 웹 프레임워크다[58]. Jinja2 는 파이썬 템플릿 엔진이다[59].

AURA 는 FastAPI 위에서 Jinja2 템플릿을 서버에서 그리고, 화면마다 가벼운 자바스크립트 파일(채팅 작업 공간, 문서 작업 공간, 드라이브 둘러보기, 공동 편집 등)만 붙인다.
별도 프런트엔드 빌드가 없어 배포가 코드 반영과 재시작으로 끝나고, 인터넷이 막힌 교내 서버에 설치할 것이 적다. 답 생성처럼 오래 걸리는 일은 뒤에서 돌리고,
화면은 진행 상태를 몇 초 간격으로 물어 단계와 근거 개수만 받는다. 모델의 내부 추론이나 원문은 진행 상태에 싣지 않는다.
