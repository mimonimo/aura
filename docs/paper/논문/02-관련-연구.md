# 2. 관련 연구

이 장은 AURA를 이루는 기술을 생성 모델과 서빙(2.1), 모델 학습(2.2), 문서 읽기와 변환(2.3), 검색(2.4), 지식 표현(2.5), 개인정보 보호(2.6),
에이전트(2.7), 문서 작성과 공동 편집(2.8), 웹 플랫폼(2.9)으로 나눠, 기술마다 무엇인지, 왜 골랐는지, 어떻게 쓰는지를 적는다.
수치는 본 프로젝트의 측정 기록에서 가져왔으며 측정 방법은 5장에서 다룬다.

## 2.1 생성 모델과 서빙

### 2.1.1 Qwen3.8-27B

Qwen은 알리바바 Qwen 팀이 공개하는 오픈웨이트 언어모델 계열이다[2]. Qwen3.8-27B는 매개변수 약 270억 개가 매 토큰 계산에 모두 참여하는
dense 구조이며, 이미지 입력과 최대 262,144토큰의 문맥을 다룬다[3].

채택한 이유는 네 가지다. 첫째, 스캔 문서와 사진 판독까지 한 모델로 맡길 수 있다. 서빙 장비 두 대에는 모델을 여럿 띄울 메모리가 없고,
시험한 소형 판독 모델은 없는 문장을 지어내고 같은 줄을 반복했다. 둘째, dense 구조라 LoRA 학습(2.2.1)과 vLLM 어댑터 서빙(2.1.2)이 검증되어 있다.
셋째, NVIDIA가 젯슨용 NVFP4 양자화 판을 공식 배포한다[4]. 넷째, Apache 2.0 라이선스라 학습본 이름·표시 의무가 없다. 국내 모델 EXAONE 4.0 32B[6]와
HyperCLOVA X SEED Think 32B[7]는 한국어 지식 벤치마크 KMMLU[8]에서 앞서지만 이미지 입력, 라이선스, 젯슨용 양자화 판 가운데 하나씩이 맞지 않았다.
AURA는 지식을 검색으로 넣어 주므로 모델에는 주어진 문서를 읽고 형식에 맞춰 쓰는 능력이 더 중요하다고 보았다. 초기 서빙 검증은 같은 계열의
MoE 모델 Qwen3.5-35B-A3B[5]로 했다.

AURA 에서는 이 모델 하나가 대화 답, 문서 작업 에이전트, 업무 도우미, 반입 검토, 이미지 판독, 질문 읽기, 서류 종류·사업 판정을 모두 맡는다.
코드는 모델 이름이 아니라 용도(답, 반입 검토, 이미지 판독, 업무 도우미 등)로 호출하고, 용도마다 서버·모델 이름·생각 끄기 인자·구조화 출력 방식·
동시 요청 상한을 연결 설정에 둔다. 더 큰 모델로 바꿀 때는 이 설정만 고친다. Qwen 계열은 답 전에 스스로 따져 보는 생각 모드가 기본으로 켜져
있어, 끄지 않은 호출은 출력 한도를 생각에 다 쓰고 빈 값으로 실패한다. 그래서 클라이언트가 교내 호출의 생각 모드를 기본으로 끈다. 답 쓰기에서
켜 보니 7배 느렸고 채점도 나빠졌다. 판정·답 기록에는 실제로 답한 모델 이름을 함께 남긴다.

### 2.1.2 vLLM

vLLM은 대규모 언어모델 추론 서빙 엔진이다[9]. 주의(attention) 계산의 키·값 캐시를 고정 크기 블록으로 나눠 관리하는 PagedAttention[10]으로
메모리 낭비를 줄이고 여러 요청을 묶어 처리하며, OpenAI 호환 HTTP API를 제공한다.

LoRA 어댑터 서빙, 동시 요청 처리, 양자화 정밀도(NVFP4·FP8·bf16) 선택, JSON 스키마로 출력 형식을 강제하는 구조화 출력[50]을 한 엔진에서
할 수 있어 골랐다.

서빙 장비마다 vLLM 컨테이너 하나로 Writer 27B NVFP4를 「zzaimy-writer」라는 서빙 이름으로 띄우고, 앱은 OpenAI 호환 주소(/v1)로 잇는다.
서빙 문맥은 모델 최대치인 262,144토큰이며, 앱은 서버가 `/v1/models` 로 알려 주는 문맥 한도를 먼저 쓴다. 젯슨에는 NVIDIA 젯슨용 이미지를,
일반 GPU 서버에는 공식 이미지를 쓰고, 판은 태그가 아닌 이미지 다이제스트로 고정한다. 포트는 내부망 주소에만 열고 접근 키를 건다.
에이전트 단계 출력과 질문 해석은 구조화 출력으로 받고, 서버가 스키마 강제를 받지 않으면 JSON으로 답하라고 지시한 뒤 결과를 파싱한다. 컨테이너는 정상 종료로
내린다. 강제로 지우면 젯슨의 GPU 메모리가 돌아오지 않아 재부팅이 필요할 수 있다.

### 2.1.3 NVIDIA Jetson AGX Thor와 NVFP4 양자화

Jetson AGX Thor는 NVIDIA의 임베디드·엣지용 컴퓨팅 장비로, CPU와 GPU가 통합 메모리(본 장비 122GB)를 함께 쓴다[11]. 양자화는 가중치를 더 적은
비트로 표현해 메모리와 계산량을 줄이는 기법이고, NVFP4는 NVIDIA가 Blackwell 세대 GPU 용으로 제시한 4비트 부동소수점 형식으로 작은 블록마다
배율 값을 따로 두어 정밀도 손실을 줄인다[12].

젯슨 토르는 메모리 대역폭이 생성 속도를 정하고 FP4·FP8 연산을 하드웨어로 가속하므로 가중치가 작을수록 빠르다. 원본 bf16판은 요청 하나에
초당 2~5토큰이라 쓸 수 없었고, NVFP4판은 초당 10.4~10.9토큰에 같은 입력의 검토·판독 내용이 원본과 같았다.

두 대에 같은 판을 올리고 일을 장비로 나눈다. 토르 02는 대화 답·문서 작업·업무 도우미처럼 사람이 기다리는 일을, 토르 03은 반입 검토·이미지
판독·질문 읽기·판정 같은 배치 일과 임베딩·리랭커 서비스를 맡는다. 그래서 수만 건의 반입 검토가 도는 동안에도 대화 답이 밀리지 않는다.
정밀도는 NVFP4, FP8, bf16 순으로 우선하되 같은 입력의 검토·판독과 초안 수치를 원본과 대조해 같을 때만 쓴다. 큰 가중치 파일을 받은 직후에는
페이지 캐시가 통합 메모리를 차지해 엔진이 뜨지 못하므로 캐시를 비우고 띄운다.

### 2.1.4 다음 토큰 예측 층을 이용한 추측 디코딩

추측 디코딩(speculative decoding)은 가벼운 예측기가 다음 토큰 몇 개를 미리 짐작하고 본 모델이 한 번에 검증해 맞은 만큼 받아들이는 기법이다[13].
여러 토큰 예측(multi-token prediction, MTP)[14] 층을 함께 학습한 모델은 그 층을 예측기로 쓸 수 있다.

검증을 본 모델이 하므로 출력 분포가 바뀌지 않고, 별도 예측 모델 없이 모델 안의 층을 쓰므로 메모리도 거의 늘지 않는다.

Qwen3.8-27B에 든 MTP 층이 토큰 두 개를 짐작하게 했다. 생성 속도는 검토 쪽이 초당 10.6토큰에서 23.8 토큰으로, 답 쪽이 약 12토큰에서 24.6 토큰으로
올랐다. GPU 메모리 비율은 같은 장비의 임베딩·리랭커가 쓰는 몫을 뺀 여유 안에서 정해야 한다. 시작 시점의 빈 메모리보다 크게 잡았을 때 엔진이
뜨지 못해 검토가 약 25분 멈췄고, 그 뒤 켜는 스크립트와 되돌리는 스크립트를 함께 두었다.

## 2.2 모델 학습

### 2.2.1 LoRA와 SFT

지도 미세조정(Supervised Fine-Tuning, SFT)은 입력과 바라는 출력의 쌍으로 사전학습 모델을 추가 학습하는 방법이다. LoRA(Low-Rank Adaptation)[15]는
원래 가중치를 고정하고 각 층에 더한 작은 저랭크 행렬 두 개만 학습한다.

메모리가 적게 들어 27B 모델을 학습 장비 한 대에서 학습할 수 있고, 결과가 작은 어댑터 파일로 남아 기본 모델에 얹거나 합치기 쉽다.

학습 장비(DGX)에서 Hugging Face의 PEFT[16]와 TRL[17]로 bf16 LoRA SFT를 한다(r32, 2에폭, 학습 문맥 16,384토큰). 서빙에 넣을 때는 어댑터를 기본 모델에
합친 뒤 운영과 같은 NVFP4로 다시 양자화해 후보 서빙 이름으로 올린다. 어댑터를 vLLM에 직접 얹으면 어댑터의 층 이름이 서빙 모델 구조와 맞지
않을 때 오류 없이 붙지 않으므로, 생성 비교 전에 정답의 로그확률로 학습이 들어갔는지 먼저 확인한다. 학습 범위는 좁다. 사업의 사실과 수치는
해마다 바뀌고 내부 원문을 학습하면 개인정보가 모델에 남으므로, 사실은 검색과 지식 그래프로 공급하고 학습은 「무엇을 어디서 찾아 어떤 근거로
답을 구성할지」라는 문맥 구성 추론과 문서 구조에만 쓴다. 이 절차와 데이터는 더 큰 모델에 적용하기 위해 Writer 27B로 먼저 검증했다(학습 4,434건,
검증 346건, 시험 220건). 학습한 형식의 요청에서는 정답 겹침이 올랐고, 에이전트 단계 요청의 JSON 형식은 학습 데이터에 넣어야 한다는 보완점이
드러났다(5.4.5절).

### 2.2.2 Label Studio

Label Studio는 사람이 웹 화면에서 항목별로 판정·수정한 결과를 내보내는 오픈소스 데이터 주석 도구다[18].

교내 장비에 설치할 수 있고 판정 화면을 항목에 맞게 꾸밀 수 있어 골랐다.

학습 장비에 두고 학습 데이터 사람 검수에 쓴다. 자동 검사(근거 기록 유무, 근거가 그 턴에 글자 그대로 있는지, 숫자가 근거에 있는지, 중복)를
통과한 후보를 검수자가 근거·구조·맥락·개인정보 네 항목으로 확인해 채택·수정·폐기한다. 자동 생성물을 정답으로 간주하지 않도록 네 항목이 모두
확인된 것만 승인본으로 삼는다. 검수자는 플랫폼의 문답 검수 권한으로 들어가고, 운영 서버에는 학습셋의 이름·상태·건수만 목록으로 들어온다.

## 2.3 문서 읽기와 변환

### 2.3.1 MinerU

MinerU는 OpenDataLab이 공개한 문서 구조 추출 도구다[19][20]. PDF에서 제목·문단·표·그림·수식의 배치를 검출하고 읽기 순서를 정하며, 글자층이
없는 스캔본은 OCR로 읽는다. 표는 병합 셀을 포함한 HTML로 낸다.

같은 실물 문서로 파서를 비교해 골랐다. 스캔 판독 어절 F1은 MinerU 0.690, docling[21] 0.334 였고, dots.ocr는 고유명사를 잘못 읽고 영어 문장을
지어냈다. 27B 이미지 판독은 0.839로 가장 높지만 쪽당 165초라 대량 처리에는 맞지 않는다.

대량 스캔 판독은 학습 장비 GPU에서 MinerU로 배치 처리하고(쪽당 약 7.6초), 짧은 스캔 문서와 사진은 27B 판독을 먼저 쓴다. 디지털 PDF도
표·2단·읽기 순서는 MinerU로 잡되 글자는 원본 글자층으로 덮어쓴다. 글자층이 있는 문서를 스캔으로 다루면 멀쩡한 글자까지 오인식하므로,
읽기 전에 글자층을 먼저 감지해 경로를 나눈다(2.3.2).

### 2.3.2 PDF 글자층 직독과 보조 OCR

디지털 PDF는 글자와 좌표가 파일 안에 들어 있다. PDFium[22]은 이 글자층을 좌표째 읽는 PDF 엔진이다.

OCR로 다시 읽으면 멀쩡한 글자까지 오인식하지만(「기초과학」→「기추과하」), 직독은 원본 글자를 그대로 얻고 빠르다.

고루 뽑은 여섯 쪽의 쪽당 글자 수가 충분하고 깨진 글자 비율이 0.15 미만이면 직독하고, 아니면 스캔본으로 보고 OCR 경로로 보낸다. 화면의 원본
복원 보기는 원본 쪽 그림을 배경에 두고 투명한 글자층을 얹는다. 디지털 PDF는 글자 좌표를, 스캔본은 MinerU의 줄 좌표를 쓴다. 사진은 27B 이미지
판독, MinerU OCR, Tesseract[23] 순서로 시도한다.

### 2.3.3 한글 문서 형식과 kordoc

한글(HWP)은 국내 공공기관과 대학 행정의 기본 문서 형식이다. 옛 HWP 5 형식은 이진 복합 파일이고, HWPX는 XML 문서를 ZIP으로 묶은 개방형
형식(OWPML, KS X 6101)이다[24]. kordoc[25]은 한글(HWP 3/5·HWPX)·PDF·XLSX·DOCX를 자체 파서로 읽어 마크다운·JSON으로 내는 MIT 라이선스 도구다.

교내 서식 대부분이 이 두 형식이다. kordoc은 옛 HWP 30MB 파일을 1초에 읽었고(기존 pyhwp[26] 경로 3분) 글자 양이 같았으며 중첩·병합 표를 보존했다.

HWPX는 자체 OWPML 파서가 표준 라이브러리만으로 ZIP과 XML을 풀어 문단·표·글상자·머리말까지 구조로 읽는다. 옛 HWP는 kordoc을 1순위로 쓰고
실패하면 pyhwp 경로로 다시 읽으며, 판을 고정한 포크를 보관해 폐쇄망에서도 같은 결과를 낸다. 출력은 AURA 내부 문서 구조(문단·제목·표 좌표·그림)로
옮기고, 개인정보 처리·조각 나누기·색인은 AURA의 것을 쓴다. 한글 완성본은 구역 XML을 다시 직렬화하지 않고 원본 바이트를 둔 채 절 제목 문단
뒤에 문단·표·그림 XML을 끼워 넣으며, ZIP 항목 순서와 압축 방식을 유지하고 바뀐 항목만 다시 쓴다(서식 보존 채우기). 변환기로 새로 만든 파일은
표 테두리·칸 폭·글꼴이 원래 서식과 달라 제출할 수 없기 때문이다. 글꼴 이름은 언어별 목록을 구분해 읽어야 엉뚱한 글꼴이 들어가지 않는다.
한글 프로그램을 COM으로 조작하는 방식은 담당자 PC 마다 설치가 필요해 폐기했다.

## 2.4 검색

### 2.4.1 검색 증강 생성

검색 증강 생성(RAG)은 질문과 관련된 문서 조각을 먼저 검색하고, 그 조각을 언어모델 입력에 넣어 답을 생성하는 방식이다[1].

학습하지 않은 최신·내부 자료로 답하고 근거를 출처로 보일 수 있다. 계획서의 수치는 근거가 있어야 하므로 이 성질이 필요했다.

검색은 두 색인과 그래프 하나로 이뤄진다. 규정 색인은 교내 규정·지침을 조문 단위로, 사업 문서 색인은 사업 문서 조각을 담으며, 규정 질문과 사업
질문의 결과가 섞이지 않게 둘을 나눴다. 사업 문서는 지식 그래프(2.5.1)로 범위를 먼저 좁힌다. 열람 권한은 검색 단계의 SQL 조건으로 건다. 답을
만든 뒤 거르면 모델이 이미 권한 밖 자료를 읽은 뒤이기 때문이다. 모델에 건넨 근거 목록이 그대로 화면의 출처가 되고, 답의 숫자는 그 근거와
코드가 대조한다.

[그림 2-13] RAG 개념도: 검색, 근거 묶기, 생성 (그림 docs/images/diagrams/c2-13-rag.png)

### 2.4.2 KURE 임베딩과 대조 학습

임베딩 모델은 뜻이 가까운 문장이 가까운 고정 길이 벡터가 되게 바꾼다. KURE-v1은 고려대학교 NLP&AI 연구실이 다국어 임베딩 모델 BGE-M3[30]를
한국어 데이터로 추가 학습해 공개한 모델로[29], 1,024차원 벡터를 내고 MIT 라이선스다.

한국어 검색 벤치마크에서 상위권이었고 교내 GPU에서 서비스할 수 있는 크기다. 다만 「교원업적평가」, 「차년도 사업비 이월」 같은 교내 용어와 규정
문체에 약해 학습본을 만들었다.

학습본(Embed v2)은 규정 조각마다 27B로 합성 질의를 세 형식(실무형, 공고 요구사항형, 키워드형)으로 만들고, 운영 검색이 올린 후보 가운데 정답이
아닌 조각을 어려운 오답으로 써서, 정답 쌍을 가깝게 하고 배치 안 오답과 어려운 오답을 멀게 하는 InfoNCE[31](온도 0.05)로 학습했다. 채택 기준은
단독 지표가 아니라 운영 하이브리드 검색에서 정답이 후보에 더 많이 드는지이며, 첫 학습본은 단독 지표만 올라 버렸다. 서비스는 토르 03의 임베딩
서버가 맡고, 앱은 관리 화면의 서버 설정에 그 주소와 접근 키를 넣는다. 색인과 질의는 반드시 같은 모델이어야 하므로 임베딩 모델을 바꾸면 전체를
다시 색인한다. 교내망 보안 장비가 긴 숫자열이 든 요청을 끊어 9자리 이상 숫자열은 가려 보내며, 서빙 장비가 응답하지 않으면 규정 검색은 운영
서버 CPU에서 같은 모델을 돌려 대신한다.

[그림 2-14] KURE 로고(출처: KURE 공식 저장소(nlpai-lab/KURE)) (그림 docs/images/logos/f2-14-kure.png)

### 2.4.3 bge-reranker-v2-m3 리랭커

리랭커는 질문과 후보 조각을 한 쌍씩 함께 읽어 관련도 점수를 매기는 교차 인코더(cross-encoder)다. bge-reranker-v2-m3는 BAAI가 공개한 다국어
리랭커로, BGE-M3와 같은 계열이고 Apache 2.0 라이선스다[32].

임베딩보다 느리지만 정확하다. 27B 생성 모델로 후보를 다시 매기는 방식보다도 정확했고 53배 빨랐다.

운영 하이브리드가 실제로 올린 후보 목록에서 정답 확률을 높이는 목록 단위 학습으로 학습본(Rerank v1)을 만들었다. 문서 단위 홀드아웃에서 R@1이
0.649에서 0.711로 올랐다. 토르 03 GPU의 리랭커 서버로 옮기자 질의당 3.75초가 0.07초가 되어 재정렬 후보를 20개로 늘렸고, 점수가 하한 아래인
후보는 근거에서 뺀다. 리랭커는 규정 검색에만 쓴다. 사업 문서 검색에서는 그래프 절 축과 문서당 조각 수 제한과 겹쳐 오히려 손해라 껐다.

### 2.4.4 Kiwi 형태소 분석과 어휘 검색

한국어는 조사와 어미가 붙어 어휘 검색에 형태소 분석이 필요하다. Kiwi는 C++ 로 구현된 한국어 형태소 분석기로 파이썬 바인딩과 사용자 사전을
제공한다[33].

조사 시점에 꾸준히 관리되는 한국어 형태소 분석기가 이것뿐이었고, 사용자 사전으로 교내 용어를 더할 수 있다.

Kiwi로 명사와 두 글자 이상 영문 약칭을 뽑고, 띄어 쓴 복합 명사를 붙이며, 드문 낱말에 무게를 주는 IDF로 점수를 낸다. BM25[34] 계열 어휘 검색과
같은 발상이다. 색인과 질의가 같은 낱말 함수를 쓰고, 사업 문서 쪽은 낱말을 미리 뽑아 PostgreSQL 전문 색인(GIN)에 둔다.

### 2.4.5 RRF 하이브리드 검색

하이브리드 검색은 어휘 검색과 의미 검색의 결과를 섞는다. RRF(Reciprocal Rank Fusion)[35]는 문서 d의 융합 점수를 각 검색 결과에서의 순위 r에 대한
1/(k + r)의 합으로 정한다.

두 점수는 척도가 달라 순위로 섞어야 하고, RRF는 점수 보정 없이 단순하다. 행정 질문에는 사업 약칭·규정 이름처럼 글자 그대로 맞아야 하는 말과
「학생이 휴학하려면」처럼 뜻으로 찾을 말이 섞여 한 축만으로는 한쪽을 놓친다.

k=60으로 두 축의 순위를 섞고 어휘 축에 0.4, 의미 축에 1.0의 가중을 준다. 가중은 0.2~0.5에서 결과가 평평했고 학습 문서를 뺀 질의로 다시 재도
같아 0.4를 유지했다. 사업 문서 쪽은 어휘 1위 조각이 섞은 순위에서 밀리지 않게 지킨다. 융합 순위의 상위 20개가 리랭커 후보가 된다.

### 2.4.6 PostgreSQL과 pgvector

PostgreSQL은 오픈소스 관계형 데이터베이스다[38]. pgvector는 여기에 벡터 자료형과 근접 이웃 검색 색인을 더하는 확장으로[36], 여러 층의 근접
그래프를 위에서 아래로 내려가며 가까운 이웃을 찾는 근사 검색 색인 HNSW[37]를 지원한다.

별도 벡터 데이터베이스를 두지 않고 권한·부서·서류 종류 조건을 벡터 검색과 같은 SQL에 걸며, 조인·트랜잭션·백업을 한 시스템에서 처리할 수 있다.

사업 문서 조각 벡터 약 156만 개를 halfvec 1,024차원 HNSW 색인에 둔다. 운영 서버 메모리의 벡터 배열에서 옮기자 정답 문서 적중은 거의 같고
검색 시간은 3.49초에서 1.85초로 줄었으며 메모리에서 5GB 넘는 배열이 빠졌다. 근사 검색의 정확 계산 대비 recall@10은 0.915 다. 문서·조각·권한과
지식 그래프의 노드·관계도 같은 PostgreSQL에 표로 두어, 백업은 앱 스키마 덤프 하나로 끝난다.

## 2.5 지식 표현

### 2.5.1 온톨로지와 지식 그래프

온톨로지는 한 분야의 개념(클래스)과 관계, 제약을 명시적으로 정의한 것이고, 지식 그래프는 온톨로지에 따라 실제 대상(노드)과 관계(간선)를 이은
데이터다. GraphRAG[39]는 조각 유사도와 함께 그래프 구조로 검색 범위를 정하거나 근거를 모으는 RAG 방식이다.

문서가 수만 건이면 사업·연차·서류 종류를 먼저 좁혀야 하고, 「계획 대비 실적」이나 「앞 단계 사업」처럼 문서 사이 관계를 묻는 질문은 관계가
데이터로 있어야 답할 수 있다.

노드는 여덟 종류(사업 묶음, 사업, 기관, 연차, 문서, 절, 단위과제, 성과지표)이고, 관계는 포함, 계획↔실적, 평가, 앞·뒤 단계, 편입, 연관, 주관 부처·
전담기관, 성과지표 측정 등이다. 관계마다 근거(문서·절 위치나 외부 출처 URL)를 달고, 근거 없는 관계는 만들지 않는다. 사업 이름 변경이나 같은
사업인지의 판단은 외부 검색으로 확인한 출처를 근거로 둔다. 그래프는 PostgreSQL의 노드·관계 표에 두고, 입력(문서·조각·종류·사업 장부 등)의
지문이 바뀌면 주기 작업이 다시 짓는다. 질문이 오면 27B가 질문을 온톨로지의 말(사업 번호, 연도, 차수, 서류 종류, 따라갈 관계)로 읽어 구조화
출력 JSON으로 내고, 그래프 탐색은 코드가 결정적으로 한다. 절 질문의 정답 문서가 상위 5건에 든 비율은 전문 검색 18%, 그래프 64%, 그래프와
모델의 질문 해석 70%였다.

[그림 2-19] AURA 온톨로지: 노드 여덟 종류와 관계 (그림 docs/images/diagrams/c2-19-ontology.png)

### 2.5.2 OWL·RDF와 SHACL

RDF는 「주어-서술어-목적어」 세 값으로 정보를 표현하는 W3C 표준 데이터 모델이고[41], OWL은 RDF 위에서 클래스·속성·제약을 정의하는 온톨로지
언어다[40]. SHACL은 RDF 그래프가 지켜야 할 모양(shape)을 정의·검사하는 W3C 표준이다[42].

온톨로지를 표준 형식으로 내보내면 외부 도구로 열람·검사할 수 있고, 규칙을 데이터로 적어 그래프를 지을 때마다 자동으로 검사할 수 있다.

그래프 자체는 PostgreSQL 표에 두고, 온톨로지 설계도만 rdflib[43]로 OWL·RDF로 내보내 pySHACL[44]로 검사한다. 규칙은 「연차는 사업 하나에만 속하고
연도는 1990~2035」, 「문서의 서류 종류는 하나까지이고 사업·연차에 속하거나 기관 업무 문서」, 「관계는 기준 다섯(구조, 분류, 식별자 일치, 추출,
유사도) 가운데 하나에 근거 하나 이상」 등이다. 검사는 그래프를 다시 지을 때마다 돌고 위반은 0건이었다. 설계도는 그래프 탐색 화면에서 내려받아
Protégé[45] 같은 편집 도구로 열 수 있다.

### 2.5.3 Cytoscape.js

Cytoscape.js는 웹 브라우저에서 그래프를 그리고 다루는 자바스크립트 라이브러리다[46].

빌드 없이 정적 스크립트로 붙일 수 있어 AURA의 화면 구성(2.9)에 맞는다.

그래프 탐색 화면은 Cytoscape.js와 fcose 배치 확장으로 사업 중심 그래프와 온톨로지 보기를 그리고, 노드를 고르면 이웃을 펼쳐 관계와 근거를 보인다.

## 2.6 개인정보 보호

### 2.6.1 Presidio

Presidio는 Microsoft가 시작한 오픈소스 개인정보 탐지·비식별화 프레임워크다[47]. 정규식·체크섬·개체명 인식을 조합한 인식기(recognizer)로
개인정보를 찾아 가리거나 바꾼다.

교내 장비에 설치할 수 있고, 사용자 정의 인식기를 끼워 한국형 개인정보를 다룰 수 있다.

Presidio 위에 한국형 패턴 인식기 8종을 얹었다. 주민등록번호와 사업자번호는 체크섬으로 검증하고, 계좌·학번·생년월일·성명은 「계좌번호:」, 「성명」
같은 이름표 문맥이 있을 때만 잡는다. 표에서는 옆 칸의 직위 문맥으로 성명을 한 번 더 가린다. 가림 범위는 쓰는 곳에 따라 다르다. 담당자가 업무로
보는 원문을 모두 가리면 일을 할 수 없으므로 내부 열람 가림은 관리자 설정으로 켜고 끄며, 학습 반출은 설정과 상관없이 별도 사본에서 전체 탐지와
사람 검수를 거친다. 밖으로 나가는 글은 고위험 형식(주민번호·이메일·휴대전화·카드번호)을 늘 한 번 더 검사하고, 가림에 실패하면 내보내지 않는다.
전체 문서와 조각을 다시 검사했을 때 가렸어야 할 잔여는 0건이었으나, 정규식 기반이라 이름표 없는 이름·주소를 놓칠 수 있어 완전 제거의 증명은 아니다.

## 2.7 에이전트

### 2.7.1 도구 사용 에이전트와 구조화 출력

언어모델 에이전트는 상황과 도구 결과를 보고 다음 행동(도구 호출)을 고르기를 되풀이해 과제를 푼다. ReAct[48]는 추론과 행동을 번갈아 내게 하는
대표 방식이다.

낱말 규칙으로 요청을 해석하면 표현이 조금만 달라도 엉뚱한 일을 한다. 판단을 모델에 맡기고 코드는 그 판단을 안전하게 실행하게 하려고 이 방식을 골랐다.

문서 작업 에이전트는 매 단계 상태(요청, 최근 대화, 프로젝트 문서 목록, 작업본의 절 목록과 빈 절, 받지 못한 값, 지금까지의 단계)를 보고
`{생각, 도구, 인자}` 를 JSON으로 고른다. 출력 형식은 vLLM의 구조화 출력[50]으로 강제한다. 한글 기안기 작업의 도구는 근거 찾기, 문서 읽기,
양식 찾기·만들기, 절 쓰기, 칸 채우기, 표 서식, 절 맡기기·고쳐 쓰기, 값 기억, 묻기, 마무리 등 19가지다. 코드의 관문은 단계 수 상한, 되돌리기 어려운
도구는 담당자 요청 글에 그 뜻이 있을 때만 실행, 도구 결과 안의 글이 지시를 흉내 내지 못하게 하는 자료 울타리, 아무것도 바꾸지 못하는 쓰기의
한도, 열람 범위와 수치 근거 대조다. 단계마다 상태·선택·결과를 기록해 실패 원인을 찾고 이후 학습 재료로 쓴다.

[그림 2-23] 에이전트 실행 흐름: 상태, 도구 선택, 관문, 실행, 기록 (그림 docs/images/diagrams/c2-23-agent.png)

### 2.7.2 단계 추론과 대화 기억

단계 추론(chain-of-thought)[49]은 모델이 답 전에 중간 단계를 글로 써 내려가게 해 복잡한 문제의 정확도를 높이는 방법이다.

생각 모드를 켜면 느리고 채점도 나빴으므로(2.1.1), 길이를 통제한 짧은 단계 추론을 답 앞에 두는 쪽을 골랐다.

답 앞에 [1단계: 질문 파악] → [2단계: 근거 확인] → [3단계: 답 구성]을 두고, 화면에는 답만 보이되 추론은 「생각 과정」으로 펼쳐 볼 수 있다. 학습 데이터의
구조 단계 문답과 같은 형식이다. 긴 대화를 위해 작업 메모를 둔다. 답이 끝나면 배경에서 「지금 목표 / 확정된 것 / 진행 상황 / 남은 일」을 갱신하고,
요청에는 메모와 최근 대화 원문을 문맥 한도의 일정 비율(메모 6%, 최근 대화 30%)만큼 넣는다. 개수가 아니라 비율이라 문맥이 긴 모델로 바꾸면
저절로 맞는다. 긴 서식은 메인 에이전트가 같은 모델을 깨끗한 문맥으로 다시 불러 절을 맡긴다(서브 에이전트).

## 2.8 문서 작성과 공동 편집

### 2.8.1 한컴 웹 한글 기안기

한컴 웹 한글 기안기(WebHwpCtrl)는 한글과컴퓨터의 웹 브라우저용 한글 문서 편집기다[51]. 프로그램 설치 없이 브라우저에서 HWP·HWPX 문서를 열어
편집하며, 자바스크립트 API로 필드(누름틀) 읽기·쓰기, 커서 이동, 동작 실행을 제어한다.

교내 행정 서식이 한글이고, 다른 형식으로 바꿔 편집하면 표와 쪽 배치가 달라진다. 원본을 그대로 열면 담당자는 익숙한 한글 화면에서 고친다.

13.82.0.208판을 운영 서버 안에 설치하고, 사용자는 AURA의 로그인과 열람 범위 확인을 거친 프록시로만 닿는다. AURA 에이전트가 쓴 절도 사람과 같은
칸 경로로 열린 기안기들에 흘러 들어간다(4장). 기안기에 있는 기능(편집 용지, 쪽 번호, 머리말, 표 편집 등)은 다시 만들지 않고 동작 실행으로 쓴다.
이를 위해 공개 API 메서드 103개와 등록된 동작 467개를 조사해 기능 표를 만들었다. 주의할 점은 표 배치다. 기안기는 「글자처럼 취급」한 표를 쪽에서
나누지 못하므로, 행이 많거나 쪽 본문 절반보다 높은 표는 셀 단위로 나누고 본문과 함께 흐르게 바꾼다.

### 2.8.2 공동 편집 기법과 칸 단위 편집권

여러 사람이 같은 문서를 동시에 고치는 공동 편집의 대표 기법은 둘이다. 연산 변환(Operational Transformation, OT)[52]은 동시에 일어난 편집 연산을 서로의
결과에 맞게 변환하고, CRDT(Conflict-free Replicated Data Type)[53]는 병합 순서와 상관없이 같은 결과가 나오도록 설계한 자료구조를 쓴다. 둘 다 문서
내부 모델에 글자 단위로 접근해야 한다.

웹 기안기의 공개 API에는 문서 변경 사건이 없고 문서 내부 모델에 닿을 수 없어 OT·CRDT를 쓸 수 없다. 쓸 수 있는 것은 필드 API, 커서 저장·되돌리기,
칸을 서식째 꺼내고 넣는 블록 입출력이다. 그래서 네 안을 비교해 칸 단위 비관적 임대(lease)를 골랐다.

문서를 열 때 제목·표 칸까지 모든 글 문단을 칸으로 감싸 주소로 쓰고, 칸을 처음 고칠 때 편집권을 잡고, 바뀐 부분만 판 번호와 함께 보내며, 서버
기록을 정답으로 삼는다. 같은 칸을 둘이 동시에 쓰지 않아 병합이 필요 없다. 판 번호가 어긋난 변경은 버리지 않고 충돌 사본으로 남긴다. 표·용지처럼
칸에 담기지 않는 고침은 한 사람씩 문서 전체를 저장하고 다른 화면이 새 판을 받는다. 긴 절은 줄바꿈을 칸 안 줄 나눔이 아닌 문단으로 넣고, 받은 칸은
짧은 조각으로 나눠 넣어 큰 문서에서도 입력이 멈추지 않게 했다. AURA 에이전트도 같은 경로로 칸을 쓰는 참여자이며, 사람이 쥔 칸은 쓰지 않는다.
헤드리스 브라우저 세 창으로 잰 한 글자당 다른 화면까지의 지연은 중앙값 221ms 였고 잃은 글자는 없었다.

### 2.8.3 SSE

SSE(Server-Sent Events)는 웹 서버가 HTTP 연결 하나로 브라우저에 사건을 계속 밀어 보내는 표준이다[54]. 브라우저는 EventSource 객체로 받고, 연결이
끊기면 마지막으로 받은 사건 번호(Last-Event-ID)를 붙여 자동으로 다시 연결한다.

Socket.IO 같은 양방향 라이브러리나 협업 프레임워크는 새 의존성과 빌드 단계가 필요하지만, SSE는 빌드 없는 정적 자바스크립트 화면과 FastAPI에서
그대로 쓰고 끊긴 뒤 이어 받기가 표준에 들어 있다.

공동 편집은 밀어 주기를 SSE로, 변경 보내기를 일반 HTTP POST로 한다. 앱 프로세스가 여럿이면 프로세스 사이 알림은 같은 DB를 1초 주기로 읽어
건넨다. 망이 끊긴 뒤 반쯤 열린 연결을 잡기 위해 서버가 주기적으로 빈 알림을 보내고, 화면은 일정 시간 소식이 없으면 다시 붙는다.

### 2.8.4 구글 독스·드라이브 연동

구글 드라이브 API[56]는 파일 목록·내려받기·내보내기를, 구글 독스 API[55]는 문서 구조 읽기(documents.get)와 원자적 일괄 갱신(documents.batchUpdate)을
제공한다. 인증은 OAuth 2.0[57]으로, 사용자가 허용한 범위 안에서만 접근한다.

담당자 문서 일부가 구글 드라이브에 있어 읽기 전용 원천으로 붙였다. 한글 기안기가 주 작업 편집기이고 구글 독스는 고를 수 있는 보조 편집기다.

가져온 문서는 업로드와 같은 처리 경로(부서·등급·개인정보·조각·색인)를 탄다. 구글 독스를 작업본으로 열면 에이전트가 API로 같은 문서를 읽고
고친다. 독스에 쓰는 것은 외부 전송이므로 사용자마다 본인의 학교 계정으로만 연결하고, 부서 드라이브는 그 부서 총괄 책임자가 부서 공용 학교 계정으로
연결한다. 넣는 글은 개인정보 검사를 한 번 더 거치고 모든 쓰기를 감사 기록에 남긴다. 구글 클라이언트 라이브러리 없이 REST를 직접 부른다.

## 2.9 웹 플랫폼

### 2.9.1 FastAPI와 Jinja2

FastAPI는 파이썬 타입 힌트로 요청 검증과 API 문서를 자동 생성하는 비동기 웹 프레임워크다[58]. Jinja2는 파이썬 템플릿 엔진이다[59].

프런트엔드 빌드 단계가 없어 배포가 코드 반영과 재시작으로 끝나고, 인터넷이 막힌 교내 서버에 설치할 것이 적다.

FastAPI에서 Jinja2 템플릿을 서버 쪽에서 그리고, 화면마다 가벼운 자바스크립트 파일(채팅 작업 공간, 문서 작업 공간, 드라이브 둘러보기, 공동 편집
등)만 붙인다. 답 생성처럼 오래 걸리는 일은 뒤에서 돌리고, 화면은 몇 초마다 진행 상태를 물어 단계와 근거 개수만 받는다. 모델의 내부 추론이나
원문은 진행 상태에 싣지 않는다. 설치는 설치 묶음(deploy/)의 스크립트 한 번으로 파이썬 환경·PostgreSQL·서비스·주기 작업까지 갖추고, 폐쇄망에는
미리 만든 묶음으로 설치한다. 업데이트는 진행 중 요청이 끝나길 기다려 재시작하고, 새 판이 뜨지 않으면 앞 판으로 되돌린다.
