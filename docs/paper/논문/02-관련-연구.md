# 2. 관련 기술

이 장은 AURA에 사용한 기술과 각 기술을 선택한 이유를 설명한다. 선택 기준은 두 가지다. 교내 장비에 설치해 문서를 외부로 보내지 않고 사용할 수 있어야 하며,
같은 평가에서 대안보다 나은 결과를 보여야 한다. 기술은 생성 모델과 서빙(2.1절), 모델 학습(2.2절), 문서 읽기와 변환(2.3절), 검색(2.4절), 지식 표현(2.5절),
개인정보 보호(2.6절), 에이전트(2.7절), 문서 작성과 공동 편집(2.8절), 웹 플랫폼(2.9절)으로 나누어 개요, 채택 이유, AURA에서의 적용 순으로 기술하고,
2.10에서 선행 접근과 AURA의 차이를 정리한다. 수치는 본 프로젝트의 측정 기록에서 가져왔으며 측정 방법은 5장에서 다룬다.

## 2.1 생성 모델과 서빙

여러 모델을 함께 올릴 메모리가 없는 장비에서는 한 모델이 판독·판정·작성을 모두 담당하면서도 실사용이 가능한 속도를 확보해야 한다.
AURA는 생성 모델 하나를 양자화와 추측 디코딩으로 가속해 서빙 장비 두 대에 같은 버전으로 올렸다.

### 2.1.1 Qwen3.8-27B

Qwen은 알리바바 Qwen 팀이 공개하는 오픈웨이트 언어모델 계열이다[3]. Qwen3.8-27B는 매개변수 약 270억 개가 매 토큰 계산에 모두 참여하는
dense 구조이며[^c2-dense], 이미지 입력과 최대 262,144토큰의 컨텍스트(context)[^c2-ctx]를 다룬다[4]. 같은 계열에는 토큰마다 일부 매개변수만 계산하는 MoE 모델도 있으나,
본 프로젝트는 판독과 작성 품질, 학습 도구의 성숙도를 고려해 dense 모델을 기본으로 삼았다.

[^c2-ctx]: 컨텍스트는 모델이 한 번의 호출에서 읽는 입력 전체(지시, 대화, 근거)다. 컨텍스트 길이는 그 최대 토큰 수다.

[^c2-dense]: dense 구조는 모든 매개변수가 매 토큰 계산에 참여하는 구조다. MoE(Mixture of Experts) 구조는 여러 전문가 층 가운데 토큰마다 일부만 선택해 계산하므로 계산량은 적지만, 전체 가중치는 메모리에 올려 두어야 한다.

이 모델을 선택한 가장 큰 이유는 스캔 문서와 사진 판독까지 한 모델로 처리한다는 점이다. 서빙 장비 두 대에는 여러 모델을 함께 올릴 메모리가 없고,
시험한 소형 판독 모델은 없는 문장을 지어내거나 같은 줄을 반복했다. 그 밖에 dense 구조여서 LoRA 학습(2.2절)과 vLLM 어댑터 서빙(2.1.2절)이 검증되어 있고,
NVIDIA가 젯슨용 NVFP4 양자화 모델을 공식 배포하고[5], Apache 2.0 라이선스여서 학습한 모델에 이름 표시 의무가 없다. 국내 모델 EXAONE 4.0 32B[6]와
HyperCLOVA X SEED Think 32B[7]는 한국어 지식 벤치마크 KMMLU[8]에서 앞서지만, 이미지 입력, 라이선스, 젯슨용 양자화 모델 가운데 한 가지씩 조건이 맞지 않았다.
AURA는 지식을 검색으로 공급하므로, 모델에는 지식의 양보다 주어진 문서를 읽고 형식에 맞춰 작성하는 능력이 더 중요하다고 판단했다. 초기 서빙 검증은 같은 계열의
MoE 모델 Qwen3.5-35B-A3B[9]로 수행했다.

AURA에서는 이 모델 하나가 대화 응답, 문서 작업 에이전트, 업무 도우미, 수집 검토, 이미지 판독, 질문 해석, 서류 종류·사업 판정을 모두 담당한다.
코드는 용도 이름으로 모델을 호출하며, 용도별 서버·모델 이름·추론 모드 인자·구조화 출력 방식·동시 요청 상한은 연결 설정에 둔다(3.6.2절).
따라서 더 큰 모델로 교체할 때는 설정만 바꾸면 된다. Qwen 계열은 추론 모드(thinking mode)[^c2-think]가 기본으로 켜져 있으므로, 클라이언트에서
추론 모드를 기본으로 끈다. 끄지 않았을 때 생긴 문제와 속도·채점 비교는 3.6.1절에서 다룬다.

[^c2-think]: 추론 모드는 모델이 최종 답을 출력하기 전에 추론 과정을 별도 구간에 먼저 생성하는 동작 방식이다. 추론 구간도 출력 토큰 한도에 포함된다.

### 2.1.2 vLLM

vLLM은 대규모 언어모델 추론 서빙 엔진이다[10]. 언어모델은 토큰을 하나씩 생성하면서 앞선 토큰들의 주의(attention) 키·값 벡터를 캐시에
보관한다. 요청마다 최대 길이만큼 연속된 메모리를 미리 잡으면 실제로 사용하지 않는 공간이 많이 남는다. vLLM의 PagedAttention[11]은 운영체제의
가상 메모리 페이징처럼 이 캐시를 고정 크기 블록으로 나누어 필요할 때마다 할당한다. 그 결과 메모리 낭비가 줄고, 남은 메모리로 더 많은 요청을
동시에 처리한다. vLLM은 생성 도중에도 새 요청을 배치에 넣어 함께 처리하며, OpenAI 호환 HTTP API를 제공한다.

LoRA 어댑터 서빙, 동시 요청 처리, 양자화 정밀도(NVFP4·FP8·bf16) 선택, 구조화 출력[^c2-so]을 하나의 엔진에서 지원하므로 채택했다[12]. 특히
구조화 출력은 에이전트가 선택한 도구와 인자를 코드가 그대로 실행하는 AURA의 구조(2.7절)에 필수적이다.

[^c2-so]: 구조화 출력은 생성 단계에서 주어진 JSON 스키마에 맞지 않는 토큰을 후보에서 제외해, 출력이 항상 스키마를 따르게 하는 기능이다.

각 서빙 장비에는 vLLM 컨테이너 하나로 Writer 27B NVFP4를 실행하고, 앱은 OpenAI 호환 API(/v1)로 접속한다.
서빙 컨텍스트 길이는 모델 최대치인 262,144토큰이다. 젯슨에는 NVIDIA의 젯슨용 컨테이너 이미지를, 일반 GPU 서버에는 공식 이미지를 사용하며,
버전은 태그가 아닌 이미지 다이제스트로 고정한다. 포트는 내부망에만 열고 접근 키를 요구한다. 에이전트 단계 출력과 질문 해석 결과는
구조화 출력으로 받으며, 서버가 스키마 강제를 지원하지 않으면 JSON 형식을 지시한 뒤 결과를 파싱한다.

### 2.1.3 NVFP4 양자화와 MTP 추측 디코딩

Jetson AGX Thor는 NVIDIA의 임베디드·엣지용 컴퓨팅 장비로, CPU와 GPU가 통합 메모리(본 장비 122GB)를 공유한다[13]. 양자화는 가중치를 더 적은
비트로 표현해 메모리와 계산량을 줄이는 기법이고, NVFP4는 NVIDIA가 Blackwell 세대 GPU 용으로 제시한 4비트 부동소수점 형식으로 작은 블록마다
배율 값을 따로 두어 정밀도 손실을 줄인다[14].

토큰 하나를 생성할 때마다 가중치 전체를 메모리에서 읽어야 하므로, 요청 하나의 생성 속도는 연산 성능보다 메모리 대역폭에 좌우된다.
가중치를 16비트(bf16)에서 4비트로 줄이면 한 번에 읽을 양이 약 4분의 1로 줄어든다. 젯슨 토르는 FP4·FP8 연산도 하드웨어로 가속하므로,
가중치가 작을수록 빠르다. 원본 bf16 모델은 요청 하나당
초당 2.4~4.5토큰으로 실사용이 어려웠으나, NVFP4 모델은 초당 10.4~10.8토큰을 생성하면서도 같은 입력의 검토·판독 결과가 원본과 같았다(3.6.1절 [표 3-8]).

두 장비에는 같은 모델을 올리고, 사용자가 결과를 기다리는 대화형 작업과 배치 작업을 장비별로 나눈다(3.1.1절 [표 3-1]). 정밀도는 NVFP4, FP8, bf16 순으로 우선하되, 같은 입력의 검토·판독과 초안 수치가 원본과 일치할 때만 채택한다.

[그림 2-3] NVIDIA 로고 (그림 docs/images/logos/f2-03-nvidia.png)

생성 속도를 더 높이기 위해 MTP 추측 디코딩도 함께 적용한다. MTP(multi-token prediction, 여러 토큰 예측)[15]는 다음 토큰과 그 뒤에 이어질 토큰 몇 개를 함께 예측하는 층을 본 모델과 같이 학습하는
방식이다. 이렇게 학습된 MTP 층은 추론 시 추측 디코딩의 예측기 역할을 한다. 추측 디코딩(speculative decoding)은 가벼운 예측기가 다음 토큰
몇 개를 먼저 제안하고, 본 모델이 이를 한 번에 검증해 맞은 만큼 받아들이는 기법이다[16]. [그림 2-4]는 이 과정을 나타낸다.

[그림 2-4] 추측 디코딩 개념도 (그림 docs/images/diagrams/c2-04-speculative.png)

[그림 2-4]에서 MTP 예측 층은 지금까지의 문맥 뒤에 올 토큰 두 개를 먼저 제안한다(①). 본 모델은 제안된 두 자리를 한 번의
계산(순전파, forward pass)으로 함께 확인하여(②), 맞은 토큰은 그대로 받아들이고 처음 틀린 자리에는 자신이 계산한 토큰을 넣는다(③).
받아들인 토큰은 문맥에 덧붙고 같은 과정을 되풀이한다. 예측이 맞을수록 한 번의 계산으로 여러 토큰을 얻으며, 최종 토큰은 언제나 본 모델이
정하므로 출력 분포는 바뀌지 않는다. 예측기가 모델 내부의 층이어서 메모리 사용량이 거의 늘지 않고, 별도의 소형 예측 모델을 두는 방식과 달리
두 모델의 어휘와 버전을 맞출 필요도 없다.

Qwen3.8-27B에 포함된 MTP 층으로 토큰 두 개를 미리 예측하게 했다. 생성 속도는 수집 검토에서 초당 10.6토큰에서 23.8토큰으로, 대화 응답에서
약 12토큰에서 24.6토큰으로 올랐다([표 3-8]). GPU 메모리 할당 비율은 같은 장비의 임베딩·리랭커가 사용하는 메모리를 제외한 범위에서 정한다.

## 2.2 모델 학습

AURA에서 학습은 사실을 암기시키는 수단이 아니라 교내 문서에 맞춰 검색하고 작성하는 능력을 높이는 수단이다. 따라서 적은 메모리로 큰 모델을 학습할 수 있는
LoRA를 사용하고, 학습 데이터는 교내 장비 안에서 생성하고 검사한다.

지도 미세조정(Supervised Fine-Tuning, SFT)은 입력과 바라는 출력의 쌍으로 사전학습 모델을 추가 학습하는 방법이다. LoRA(Low-Rank Adaptation)[17]는
원래 가중치를 고정하고 각 층에 더한 작은 저랭크 행렬 두 개만 학습한다. 가중치 행렬 W(d×k)를 직접 고치는 대신 변화량을 B(d×r)와 A(r×k)의
곱으로 나타내며, 랭크 r은 d와 k보다 훨씬 작다. [그림 2-5]는 이 구조를 나타낸다.

[그림 2-5] LoRA 구조 (그림 docs/images/diagrams/c2-05-lora.png)

입력은 고정된 W와 학습되는 BA를 나란히 지나 더해지며, 학습이 끝나면 BA를 W에 더해 하나의 모델로 병합할 수 있다. 학습할 매개변수가 전체의
일부에 불과하므로 메모리 사용량이 적고, 27B 모델도 학습 장비 한 대에서 학습한다. 전체 미세조정과 달리 결과가 작은 어댑터 파일로 남아,
기본 모델에 결합하거나 병합하기도 쉽다.

학습 장비(DGX)에서 Hugging Face의 PEFT[18]와 TRL[19]로 bf16 LoRA SFT를 수행한다(랭크 32, 2에폭, 학습 컨텍스트 길이 16,384토큰). 서빙에 반영할 때는 어댑터를
기본 모델에 병합한 뒤 운영과 같은 NVFP4로 다시 양자화하여 후보 서빙 이름으로 올린다. 어댑터의 층 이름이 서빙 모델 구조와 맞지 않으면 vLLM이
오류 없이 어댑터를 적용하지 않으므로, 생성 결과를 비교하기 전에 정답의 로그확률로 학습 반영 여부를 먼저 확인한다.

학습 범위는 의도적으로 한정하였다. 사업의 사실과 수치는 해마다 바뀌고, 내부 원문을 학습하면 개인정보가 모델에 남는다. 따라서 사실은 검색과
지식 그래프로 공급하고, 학습은 무엇을 어디서 찾아 어떤 근거로 답을 구성할지 정하는 컨텍스트 구성 추론과 문서 구조에만 적용한다. 이 절차와 데이터는
더 큰 모델에 적용하기에 앞서 Writer 27B로 검증했다(학습 4,434건, 검증 346건, 평가 220건). 학습한 형식의 요청에서는 정답과의 겹침이 늘었고,
에이전트 단계 요청의 JSON 형식도 학습 데이터에 포함해야 한다는 보완점이 드러났다(5.4.3절).

[그림 2-6] Hugging Face 로고 (그림 docs/images/logos/f2-06-huggingface.png)

학습 데이터의 사람 검수에는 Label Studio를 사용한다. Label Studio는 사람이 웹 화면에서 항목별로 판정·수정한 결과를 내보낼 수 있는 오픈소스 데이터 주석 도구다[20].
교내 장비에 설치할 수 있고 판정 화면을 검수 항목에 맞게 구성할 수 있어 채택했다.

AURA는 Label Studio를 학습 장비에 설치해 학습 데이터 검수 화면으로 구성했다. 자동 검사(근거 기록 유무, 근거가 해당 대화 턴에 그대로 있는지, 숫자가 근거에 있는지,
중복 여부)를 통과한 후보를 검수자가 근거·구조·맥락·개인정보 네 항목으로 확인해 채택·수정·폐기하는 절차다. 이번 27B 실험에 사용한 4,434쌍은 자동 검사만 거친
자동 생성 데이터이며, 사람 검수는 더 큰 모델용 학습 데이터 절차에 더한다(6.3.2절). 운영 서버에는 학습 데이터셋의 이름·상태·건수만 목록으로 전달된다.

[그림 2-7] Label Studio 로고 (그림 docs/images/logos/f2-07-label-studio.png)

## 2.3 문서 읽기와 변환

모든 문서를 하나의 OCR로 읽으면 정상적인 글자까지 잘못 인식하므로, 문서는 형식마다 가장 정확한 경로로 읽는다. 텍스트 레이어가 있는 PDF는
OCR 없이 텍스트 레이어를 추출하고, 스캔본만 판독(OCR)하며, 한글 문서는 전용 파서로 표 구조까지 읽는다.

### 2.3.1 MinerU와 PDF 텍스트 레이어 추출

MinerU는 OpenDataLab이 공개한 문서 구조 추출 도구다[21][22]. 먼저 배치 분석 모델이 쪽 이미지에서 제목·문단·표·그림·수식 영역을 검출하고
읽기 순서를 정한다. 이어서 영역 종류마다 표 인식, 수식 인식, OCR 모델을 적용해 내용을 읽고, 결과를 마크다운으로 합친다. 표는 병합 셀을
포함한 HTML로 출력한다. 글자를 한 줄씩 읽는 일반 OCR과 달리 쪽의 구조를 먼저 파악하므로, 2단 배치와 표가 많은 행정 문서에 적합하다.

같은 실물 문서로 파서를 비교해 선정하였다. 스캔 판독의 어절 F1은 MinerU 0.690, docling[23] 0.334였고, dots.ocr[24]은 고유명사를 잘못 읽고 영어 문장을
지어냈다. 27B 이미지 판독은 0.839로 가장 높지만 쪽당 165초가 걸려 대량 처리에는 적합하지 않다.

대량 스캔 판독은 학습 장비 GPU에서 MinerU로 배치 처리하고(쪽당 약 7.6초), 짧은 스캔 문서와 사진은 27B 판독을 우선 사용한다. 디지털 PDF도
표·2단 배치·읽기 순서는 MinerU로 분석하되 글자는 원본 텍스트 레이어의 것으로 대체한다. 이를 위해 읽기 전에 텍스트 레이어 유무를 먼저 판별해 처리 경로를 나눈다.

[그림 2-8] MinerU 로고 (그림 docs/images/logos/f2-08-mineru.png)

디지털 PDF는 파일 안에 글자와 그 좌표를 담은 텍스트 레이어를 포함한다. PDFium[25]은 이 텍스트 레이어를 좌표와 함께 읽는 PDF 엔진이다.
OCR로 다시 읽으면 정상 글자까지 오인식하지만(「기초과학」→「기추과하」), 텍스트 레이어 추출은 원본 글자를 그대로, 그리고 빠르게 얻는다.

문서 전체에서 고르게 표본으로 뽑은 여섯 쪽의 쪽당 글자 수가 충분하고 깨진 글자 비율이 0.15 미만이면 텍스트 레이어를 추출하고, 그렇지 않으면 스캔본으로 판단해
OCR 경로로 보낸다. 사진은 27B 이미지 판독, MinerU OCR, Tesseract[26] 순서로 시도한다. 화면의 원본 복원 보기는 원본 쪽 이미지를 배경에 두고 그 위에 투명한
텍스트 레이어를 겹치는 방식이며, 디지털 PDF는 글자 좌표를, 스캔본은 MinerU의 줄 좌표를 사용한다. [그림 2-9]는 원본 복원 보기 화면이다.

[그림 2-9] 원본 복원 보기 화면 (그림 docs/images/figures-1027/f2-09-original-text-layer.jpg)

사용자는 원본과 같은 모습의 쪽에서 글자를 선택하고 검색하며, 추출된 글자가 원본의 위치와 맞는지도 직접 확인할 수 있다.

### 2.3.2 kordoc과 LibreOffice

한글(HWP)은 국내 공공기관과 대학 행정의 기본 문서 형식이다. 옛 HWP 5 형식은 이진 복합 파일이고, HWPX는 XML 문서를 ZIP으로 묶은 개방형
형식(OWPML[^c2-owpml], KS X 6101)이다[27]. kordoc[28]은 한글(HWP 3/5·HWPX)·PDF·XLSX·DOCX를 자체 파서로 읽어 마크다운·JSON으로 출력하는 MIT 라이선스 도구다.

[^c2-owpml]: OWPML(Open Word-Processor Markup Language)은 HWPX 문서의 본문·서식·그림을 XML로 기술하는 규격이다. 본문은 구역(section) 단위의 XML 파일로 나뉘어 ZIP 안에 저장된다.

교내 서식은 대부분 이 두 형식이다. kordoc은 30MB 크기의 옛 HWP 파일을 1초 만에 읽었고(기존 pyhwp[29] 경로는 3분), 추출한 글자 양이 같았으며
중첩·병합 표도 보존하여 채택하였다.

HWPX는 자체 OWPML 파서가 표준 라이브러리만으로 ZIP과 XML을 해석해 문단·표·글상자·머리말까지 구조로 읽는다. 옛 HWP는 kordoc을 우선 사용하고
실패하면 pyhwp 경로로 다시 읽으며, 버전을 고정한 포크를 보관해 폐쇄망에서도 같은 결과를 얻는다. 읽은 결과는 AURA 내부 문서 구조(문단·제목·
표 좌표·그림)로 변환하고, 개인정보 처리·청크 분할·색인은 AURA의 처리기를 사용한다.

변환기로 새로 만든 파일은 표 테두리·셀 너비·글꼴이 원래 서식과 달라 제출용으로 사용할 수 없다. 따라서 한글 완성본을 만들 때는 구역 XML을
다시 직렬화하지 않고, 원본 바이트를 유지한 채 절 제목 문단 뒤에 문단·표·그림 XML을 삽입한다. ZIP 항목 순서와 압축 방식도 유지하고
바뀐 항목만 다시 쓴다(서식 보존 채우기). [그림 2-10]은 HWPX 파일의 구성과 서식 보존 채우기가 내용을 삽입하는 위치를 나타낸다.

[그림 2-10] HWPX 파일 구조 (그림 docs/images/diagrams/c2-11-hwpx.png)

구역 XML 가운데 절 제목 문단 뒤만 바뀌고 나머지 항목은 원본 그대로 남으므로, 한글에서 열었을 때 원래 서식이 유지된다. 한글 프로그램을 COM으로
조작하는 방식도 검토했으나 담당자 PC마다 프로그램 설치가 필요해 제외했다.

[그림 2-11] 한컴오피스 한글 로고 (그림 docs/images/logos/f2-10-hancom-hangul.png)

LibreOffice[30]는 명령줄에서 문서 형식을 바꿀 수 있는 오픈소스 오피스 프로그램이다. python-docx·openpyxl·python-pptx[31]는 DOCX·XLSX·PPTX를
읽는 파이썬 라이브러리다.
LibreOffice는 옛 형식 변환과 열람용 PDF 생성을 서버에 설치한 프로그램 하나로 해결할 수 있어 채택하였다.

DOCX·XLSX는 kordoc으로 먼저 읽고 실패하면 python-docx·openpyxl로, PPTX는 python-pptx로 읽는다. 엑셀이 아닌 문서에서 쪽당 글자 수가 60자
미만이면 그림 위주 문서로 판단해 MinerU로 다시 읽는다. XLS·DOC·PPT 같은 옛 형식과 HWP 3은 LibreOffice로 새 형식으로 변환한 뒤 같은 경로로
처리한다. 한글·오피스 원본을 화면에서 볼 수 있도록 열람용 PDF도 LibreOffice로 생성한다.

[그림 2-12] LibreOffice 로고 (그림 docs/images/logos/f2-12-libreoffice.png)

## 2.4 검색

AURA의 검색은 글자가 그대로 일치하는 문서를 찾는 어휘 검색과 뜻이 가까운 문서를 찾는 의미 검색을 함께 사용하고, 교내 문서로 학습한 모델로 순위를 조정한다.
행정 질문에는 사업 약칭·규정 이름처럼 글자가 일치해야 하는 표현과 「학생이 휴학하려면」처럼 상황으로 묻는 표현이 섞여 있어 어느 한쪽만으로는 정답을 놓친다.

### 2.4.1 검색 증강 생성(RAG)

검색 증강 생성(RAG)은 질문과 관련된 문서 청크(chunk)를 먼저 검색하고, 그 청크를 언어모델 입력에 넣어 답을 생성하는 방식이다[1]. [그림 2-13]은
그 처리 과정을 나타낸다.

[그림 2-13] RAG 개념도 (그림 docs/images/diagrams/c2-13-rag.png)

문서는 미리 청크로 나누어 색인해 두고, 질문이 들어오면 관련 청크를 찾아 근거로 구성한 뒤 질문과 함께 모델에 전달한다. 모델은 매개변수에
저장된 지식 대신 전달된 근거에 기대어 답하므로, 학습하지 않은 최신 자료나 내부 자료로도 답할 수 있고 근거를 출처로 제시한다. 내부
자료를 모델에 직접 학습시키는 방식과 비교하면, 자료가 바뀔 때 색인만 갱신하면 되고 열람 권한도 검색 단계에서 적용된다. 계획서의
수치에는 근거가 필요하므로 이 특성이 중요했다.

검색은 두 개의 색인과 하나의 그래프로 구성된다. 규정 색인은 교내 규정·지침을 조문 단위로, 사업 문서 색인은 사업 문서 청크를 담으며, 규정 질문과
사업 질문의 결과가 섞이지 않도록 둘을 분리했다. 사업 문서는 지식 그래프(2.5절)로 검색 범위를 먼저 좁힌다. 답을 생성한 뒤에 걸러 내면
모델이 이미 권한 밖 자료를 읽은 뒤이므로, 열람 권한은 검색 단계의 SQL 조건으로 적용한다. 모델에 전달한 근거 목록이 그대로 화면의 출처가 되며,
답에 포함된 숫자는 코드가 그 근거와 대조한다.

### 2.4.2 KURE 임베딩과 bge-reranker 리랭커

임베딩 모델은 문장을 고정 길이 벡터로 바꾸되, 뜻이 가까운 문장일수록 가까운 벡터가 되도록 한다. 질문과 문서 청크를 각각 따로 벡터로 바꾸는 이중 인코더(bi-encoder)
구조이므로, 문서 청크의 벡터는 미리 계산해 두고 질의 시에는 질문 하나만 벡터로 바꾸어 가까운 벡터를 찾는다. 단어가 달라도 뜻이 가까우면 찾을
수 있다는 점이 어휘 검색(2.4.3절)과 다르다. KURE-v1은 고려대학교 NLP&AI 연구실이 다국어 임베딩 모델 BGE-M3[32]를
한국어 데이터로 추가 학습해 공개한 모델로[33], 1,024차원 벡터를 출력하며 MIT 라이선스다.

KURE-v1은 한국어 검색 벤치마크에서 상위권이었고 교내 GPU에서 서비스할 수 있는 크기다. 다만 「교원업적평가」, 「차년도 사업비 이월」 같은 교내 용어와 규정
문체에 약해 추가 학습을 진행하였다.

학습 모델(Embed v2)은 규정 청크마다 27B로 세 유형(실무형, 공고 요구사항형, 키워드형)의 합성 질의를 생성하고, 운영 검색이 상위에 올린 후보 가운데
정답이 아닌 청크를 어려운 오답(hard negative)으로 사용했다. 학습 목표는 정답 쌍을 가깝게, 배치 내 오답과 어려운 오답을 멀게 하는 InfoNCE[^c2-infonce]
(온도 0.05)다[34]. 첫 학습 모델(Embed v1)은 시험 학습 결과가 기반 모델보다 낮아 배포하지 않았고(5.3.1절), 지금은 임베딩 단독 지표 대신 운영 하이브리드
검색에서 정답이 후보에 더 많이 포함되는지를 채택 기준으로 삼은 Embed v2를 운영한다. 색인과 질의는 반드시 같은 모델로 임베딩해야 하므로, 임베딩 모델을 바꾸면 전체를 다시 색인한다. 서비스는 토르 03의
임베딩 서버가 담당하며, 서빙 장비가 응답하지 않으면 규정 검색은 운영 서버 CPU에서 같은 모델을 실행해 대신한다.

[^c2-infonce]: InfoNCE는 정답 쌍의 유사도를 여러 오답의 유사도와 함께 소프트맥스로 비교해 정답 쌍의 확률을 높이는 대조 손실 함수다. 온도는 유사도 분포를 얼마나 날카롭게 만들지 정하는 값이다.

[그림 2-14] KURE 로고 (그림 docs/images/logos/f2-14-kure.png)

리랭커는 질문과 후보 청크를 한 쌍씩 함께 읽어 관련도 점수를 매기는 교차 인코더(cross-encoder)다. bge-reranker-v2-m3는 BAAI가 공개한 다국어
리랭커로, BGE-M3와 같은 계열이고 Apache 2.0 라이선스다[35].

이중 인코더는 질문과 청크를 따로 벡터로 만들기 때문에 두 글 사이의 세부 대응을 반영하지 못한다. 교차 인코더는 질문과 청크를 하나의 입력으로
이어 붙여 모든 단어 사이의 주의를 계산하므로 더 정확하지만, 후보마다 모델을 한 번씩 실행해야 하므로 느리다. 따라서 임베딩·어휘 검색으로 후보를
먼저 줄이고, 상위 후보에만 리랭커를 적용한다. 27B 생성 모델로 후보 순위를 다시 매기는 방식과 비교하면 리랭커가 더 정확했고 53배 빨랐다.

운영 하이브리드 검색이 실제로 상위에 올린 후보 목록에서 정답의 확률을 높이는 목록 단위(listwise) 학습으로 학습 모델(Rerank v1)을 구축했다. 문서 단위
홀드아웃에서 R@1[^c2-r1]이 0.649에서 0.711로 올랐다. 토르 03 GPU의 리랭커 서버로 옮기자 질의당 처리 시간이 3.75초에서 0.07초로 줄어 재정렬 후보를
20개로 늘렸고, 점수가 하한보다 낮은 후보는 근거에서 제외한다. 사업 문서 검색에서는 그래프 기반 절 검색 및
문서당 청크 수 제한과 효과가 겹쳐 오히려 성능이 떨어졌으므로, 리랭커는 규정 검색에만 사용한다.

[^c2-r1]: R@1(Recall@1)은 정답이 1위 후보에 오른 질의의 비율이다. 문서 단위 홀드아웃은 학습에 사용한 문서를 평가에서 통째로 제외하는 평가 방식이다.

[그림 2-15] BAAI BGE 로고 (그림 docs/images/logos/f2-15-bge.png)

### 2.4.3 Kiwi·RRF 하이브리드 검색과 pgvector

한국어는 조사와 어미가 결합하므로 어휘 검색에 형태소 분석이 필요하다. Kiwi는 C++로 구현된 한국어 형태소 분석기로 파이썬 바인딩과 사용자 사전을
제공한다[36].
조사한 한국어 형태소 분석기 가운데 꾸준히 유지보수되던 것은 Kiwi뿐이었으며, 교내 용어는 사용자 사전으로 추가한다.

Kiwi로 명사와 두 글자 이상의 영문 약칭을 추출하고 띄어 쓴 복합 명사를 결합한 뒤, 드문 단어에 가중치를 주는 IDF[^c2-idf]로 점수를 계산한다. 이는
BM25[37] 계열 어휘 검색과 같은 원리다. 색인과 질의는 같은 단어 추출 함수를 사용하고, 사업 문서는 단어를 미리 추출해 PostgreSQL 전문
색인(GIN)[^c2-gin]에 저장한다. 어휘 검색은 사업 약칭이나 규정 이름처럼 글자 그대로 일치해야 하는 질의에서 임베딩 검색보다 강하다.

[^c2-idf]: IDF(Inverse Document Frequency)는 단어가 등장하는 문서가 적을수록 큰 값을 주는 가중치다. 「사업」처럼 흔한 단어보다 드문 고유 용어가 점수에 더 크게 기여한다.

[^c2-gin]: GIN(Generalized Inverted Index)은 단어마다 그 단어를 포함한 행의 목록을 저장하는 역색인으로, 단어 포함 여부를 빠르게 찾는다.

[그림 2-16] Kiwi 로고 (그림 docs/images/logos/f2-16-kiwi.png)

하이브리드 검색은 어휘 검색과 의미 검색의 결과를 섞는다. RRF(Reciprocal Rank Fusion)[38]는 문서 d의 융합 점수를 각 검색 결과에서의 순위 r에 대한
1/(k + r)의 합으로 정한다. 상수 k는 상위 몇 개 순위가 점수를 독차지하지 않도록 완화하는 값이다. AURA는 검색 결과마다 가중치 w를 곱해
w/(k + r)을 더하는 가중 RRF를 사용한다.

두 검색의 점수는 척도가 달라 점수를 그대로 더할 수 없다. 점수를 정규화해 합치는 방식은 질의마다 점수 분포가 달라 보정이 필요하지만, RRF는
순위만 사용하므로 별도 보정이 필요 없다.

k=60으로 두 검색의 순위를 결합하고, 어휘 검색에 0.4, 의미 검색에 1.0의 가중치를 준다. 가중치는 0.2~0.5 범위에서 결과 차이가 거의 없었고,
학습 문서를 제외한 질의로 다시 측정해도 같아 0.4를 유지했다. 사업 문서 검색에서는 어휘 검색 1위 청크가 융합 순위에서 밀려나지 않도록 보정한다.
융합 순위 상위 20개가 리랭커의 후보가 된다. [그림 2-17]은 이 검색 흐름을 나타낸다.

[그림 2-17] RRF 하이브리드 검색 흐름 (그림 docs/images/diagrams/c2-17-hybrid.png)

어휘 검색과 의미 검색이 각각 산출한 순위를 RRF로 합쳐 후보를 정하고, 규정 검색에서는 그 상위 후보를 리랭커가 다시 정렬해 최종 근거를 선택한다.

검색 색인은 PostgreSQL에 둔다. PostgreSQL은 오픈소스 관계형 데이터베이스다[39]. pgvector는 여기에 벡터 자료형과 근접 이웃 검색 색인을 더하는 확장으로[40], 근사 검색 색인
HNSW[41]를 지원한다. HNSW는 벡터들을 서로 가까운 것끼리 연결하는 그래프를 여러 층으로 만든다. 위층은 듬성듬성하게, 아래층은 촘촘하게 연결되어
있어, 검색은 위층에서 대략적인 위치를 찾은 뒤 아래층으로 내려가며 가까운 이웃을 좁혀 간다. 모든 벡터와 거리를 계산하는 정확 검색보다 훨씬
빠르며, 대신 일부 이웃을 놓칠 수 있다.
pgvector를 사용하면 별도 벡터 데이터베이스 없이 권한·부서·서류 종류 조건을 벡터 검색과 같은 SQL에 적용하고, 조인·트랜잭션·백업도 한 시스템에서 처리한다.

사업 문서 청크 벡터 약 156만 개를 halfvec[^c2-halfvec] 1,024차원 HNSW 색인에 저장한다. 운영 서버 메모리에 벡터 배열을 올려 검색하는 방식과
비교하면 정답 문서 적중은 거의 같고, 검색 시간은 3.49초에서 1.85초로 짧으며, 5GB가 넘는 배열을 메모리에 둘 필요가 없다. 정확 계산 대비 근사 검색의
recall@10은 0.915로, 정확 검색의 상위 10개 가운데 평균 91.5%를 근사 검색도 찾았다. 문서·청크·권한과 지식 그래프의 노드·관계도 같은
PostgreSQL에 표로 저장하므로 백업은 앱 스키마 덤프 하나로 끝난다.

[^c2-halfvec]: halfvec은 벡터의 각 값을 16비트 부동소수점으로 저장하는 pgvector 자료형으로, 32비트 저장보다 크기가 절반이다.

## 2.5 지식 그래프와 온톨로지

수만 건의 사업 문서에서 해당 사업과 연도의 문서를 찾으려면 문서 사이의 관계가 데이터로 저장되어 있어야 한다. AURA는 사업·연차·문서·절을 연결하는
온톨로지를 정의하고, 그에 따라 만든 지식 그래프로 검색 범위를 먼저 좁힌다.

온톨로지는 한 분야의 개념(클래스)과 관계, 제약을 명시적으로 정의한 것이고, 지식 그래프는 온톨로지에 따라 실제 대상(노드)과 관계(간선)를 연결한
데이터다. GraphRAG[42]는 청크 유사도와 함께 그래프 구조로 검색 범위를 정하거나 근거를 모으는 RAG 방식이다.

「계획 대비 실적」이나 「앞 단계 사업」처럼 문서 사이의 관계를
묻는 질문은 그 관계가 데이터로 존재해야 답할 수 있다. 청크 유사도만 사용하는 일반 RAG는 비슷한 단어가 많은 다른 사업이나 다른 연도의 문서를
함께 가져오기 쉽다. [그림 2-19]는 AURA의 온톨로지를 나타낸다.

[그림 2-19] AURA 온톨로지 구조 (그림 docs/images/diagrams/c2-19-ontology.png)

노드는 여덟 종류(사업군, 사업, 기관, 연차, 문서, 절, 단위과제, 성과지표)이고, 관계는 포함, 계획↔실적, 평가, 앞·뒤 단계, 편입, 연관, 주관 부처·
전담기관, 성과지표 측정 등이다. 관계마다 근거(문서·절 위치 또는 외부 출처 URL)를 기록하며, 근거 없는 관계는 만들지 않는다. 사업 이름 변경이나
사업 동일성 판단은 외부 검색으로 확인한 출처를 근거로 둔다. 그래프는 PostgreSQL의 노드·관계 표에 저장하고, 입력(문서·청크·서류 종류·사업 대장 등)의
지문이 바뀌면 주기 작업이 다시 구축한다. 질문이 들어오면 27B가 질문을 온톨로지의 용어(사업 번호, 연도, 차수, 서류 종류, 따라갈 관계)로 해석해
구조화 출력 JSON으로 반환하고, 그래프 탐색은 코드가 결정적으로 수행한다. 절 질문에서 정답 문서가 상위 5건에 포함된 비율은 전문 검색 18%, 그래프 64%,
그래프와 모델의 질문 해석을 함께 사용한 경우 70%였다.

온톨로지는 표준 형식으로도 내보낸다. RDF는 「주어-서술어-목적어」 세 값으로 정보를 표현하는 W3C 표준 데이터 모델이고[43], OWL은 RDF 위에서 클래스·속성·제약을 정의하는 온톨로지
언어다[44]. SHACL은 RDF 그래프가 지켜야 할 모양(shape)을 정의·검사하는 W3C 표준이다[45].
온톨로지를 표준 형식으로 내보내면 외부 도구로 열람·검사할 수 있고, 데이터로 기술한 규칙으로 그래프를 구축할 때마다 자동 검사도 가능하다.

그래프 자체는 PostgreSQL 표에 두고, 온톨로지 정의만 rdflib[46]로 OWL·RDF 형식으로 내보내 pySHACL[47]로 검사한다. 규칙의 예로는 「연차는 하나의
사업에만 속하고 연도는 1990~2035 범위에 있다」, 「문서의 서류 종류는 최대 하나이며, 문서는 사업·연차에 속하거나 기관 업무 문서다」, 「모든 관계는
다섯 기준(구조, 분류, 식별자 일치, 추출, 유사도) 가운데 하나에 해당하고 근거를 하나 이상 가진다」가 있다. 검사는 그래프를 다시 구축할 때마다
수행되며 위반은 0건이었다. 내보낸 온톨로지는 Protégé[48] 같은 편집 도구로 열 수 있다.

[그림 2-20] W3C 시맨틱 웹 로고 (그림 docs/images/logos/f2-20-w3c-semantic-web.png)

그래프 시각화에는 Cytoscape.js를 사용한다. Cytoscape.js는 웹 브라우저에서 그래프를 그리고 다루는 자바스크립트 라이브러리다[49].
빌드 과정 없이 정적 스크립트로 포함할 수 있어 AURA의 화면 구성 방식(2.9절)에 맞는다.

그래프 탐색 화면은 Cytoscape.js와 fcose 배치 확장으로 사업 중심 그래프와 온톨로지를 그리며, 노드를 선택하면 이웃 노드를 펼쳐 관계와 근거를 보여 준다.

[그림 2-21] Cytoscape.js 로고 (그림 docs/images/logos/f2-21-cytoscape-js.png)

## 2.6 개인정보 보호

개인정보는 교내에서 동작하는 탐지기로 처리하고, 외부로 나가는 글은 한 번 더 검사한다. 상용 탐지 서비스는 문서를 외부로 보내야 하므로 사용할 수 없다(3.1.1절).

Presidio는 Microsoft가 시작한 오픈소스 개인정보 탐지·비식별화 프레임워크다[50]. 정규식·체크섬·개체명 인식을 조합한 인식기(recognizer)로
개인정보를 찾아 마스킹하거나 다른 값으로 바꾼다. 각 인식기는 후보 문자열과 신뢰 점수를 출력하고, 주변 문맥에 「성명」 같은 단서 단어가 있으면 점수를 높인다.
교내 장비에 설치할 수 있고, 사용자 정의 인식기를 추가해 한국형 개인정보를 처리할 수 있어 채택하였다.

AURA는 Presidio에 한국형 패턴 인식기 8종을 추가하였다. 주민등록번호와 사업자번호는 체크섬[^c2-checksum]으로 검증하고, 계좌번호·학번·생년월일·성명은
「계좌번호:」, 「성명」 같은 표지 문구가 앞에 있을 때만 탐지한다. 표 안의 성명은 옆 셀에 직위가 적혀 있는 경우 한 번 더 찾아 마스킹한다.

마스킹 범위는 용도에 따라 달리 적용한다. 담당자가 업무에 쓰는 원문까지 모두 마스킹하면 업무를 처리할 수 없으므로, 내부 열람용 마스킹은 관리자가
설정에서 켜고 끈다. 학습용으로 반출하는 자료는 이 설정과 관계없이 별도 사본을 만들어 전체 탐지를 다시 수행하고, 담당자가 직접 확인한 뒤에만 내보낸다.
외부 서비스로 보내는 글은 주민등록번호·이메일·휴대전화·카드번호를 한 번 더 검사하며, 마스킹에 실패하면 전송하지 않는다.

수집한 전체 문서와 청크를 다시 검사한 결과 남아 있는 개인정보는 0건이었다. 다만 탐지가 정규식과 표지 문구에 의존하므로, 표지 문구 없이 적힌
이름이나 주소는 찾지 못할 수 있다. 따라서 0건이라는 결과만으로 개인정보가 모두 제거되었다고 단정할 수는 없다.

[^c2-checksum]: 체크섬은 번호의 마지막 자리를 앞자리를 이용해 정해진 산식으로 계산해 두는 검증 방식이다. 형식만 같은 임의의 숫자열을 걸러 내 오탐을 줄인다.

[그림 2-22] Presidio 로고 (그림 docs/images/logos/f2-22-presidio.png)

## 2.7 에이전트

문서 작업은 요청마다 순서가 달라 정해진 파이프라인으로는 처리할 수 없다. AURA는 모델이 매 단계 도구를 선택하고 코드가 그 선택을 검사해 실행하는
도구 사용 에이전트를 사용한다.

언어모델 에이전트는 상황과 도구 결과를 바탕으로 다음 행동(도구 호출)을 선택하는 과정을 반복해 과제를 해결한다. ReAct[51]는 추론과 행동을 번갈아 생성하게 하는
대표적인 방식이다. 모델이 매 단계 추론을 적고 도구 하나를 선택하면, 실행기가 도구를 실행해 결과를 다음 단계의 입력으로 전달한다. 이 과정은 모델이
마무리를 선택하거나 단계 한도에 이를 때까지 반복된다.

키워드 규칙으로 요청을 해석하면 표현이 조금만 달라도 잘못된 작업을 수행하고, 정해진 순서로만 도는 파이프라인은 요청마다 다른 작업 순서를
따라가지 못한다. 판단은 모델이 담당하고 코드는 그 판단을 안전하게 실행하도록 하기 위해 이 방식을 채택하였다. [그림 2-23]은 AURA 문서 작업
에이전트의 실행 흐름이다.

[그림 2-23] 에이전트 실행 흐름 (그림 docs/images/diagrams/c2-23-agent.png)

모델이 상태를 보고 도구를 선택하면, 코드 검증을 통과한 경우에만 도구가 실행되고 그 결과와 함께 단계 기록이 남는다.

문서 작업 에이전트는 매 단계의 상태(요청, 최근 대화, 프로젝트 문서 목록, 작업 문서의 절 목록과 빈 절, 아직 받지 못한 값, 지금까지의 단계)를 보고
`{생각, 도구, 인자}` 를 JSON으로 선택한다. 출력 형식은 vLLM의 구조화 출력[12]으로 강제한다. 도구는 근거 찾기, 문서 읽기,
양식 찾기·만들기, 절 쓰기, 입력란 채우기, 표 서식, 절 위임·재작성, 값 기억, 사용자에게 묻기, 마무리 등이며 일곱 그룹으로 나뉜다(4.6절 [표 4-10]). 코드는 여러 검증 단계를 둔다.
단계 수에 상한을 두고, 되돌리기 어려운 도구는 담당자의 요청 글에 그 의도가 드러날 때만 실행한다. 도구 결과 안의 글이 지시처럼 작동하지 않도록
자료 영역을 구분하고, 문서를 바꾸지 못한 쓰기 시도에는 한도를 둔다. 또한 열람 범위와 수치 근거를 대조한다. 단계마다 상태·선택·결과를 기록해
실패 원인 분석과 이후 학습 재료로 활용한다.

에이전트의 답 품질과 긴 대화 유지를 위해서는 단계 추론과 작업 메모를 사용한다. 단계 추론(chain-of-thought)[52]은 모델이 답변 전에 중간 추론 단계를 서술하게 하여 복잡한 문제의 정확도를 높이는 방법이다.
생성 모델에 내장된 추론 모드(thinking mode)는 답변 전에 긴 추론 과정을 생성한다. 측정 당시에는 서빙 컨텍스트 길이를
16,384토큰으로 두었는데, 추론 모드를 켜면 추론 과정이 이 한도 안에서 답변에 쓸 토큰을 먼저 차지한다. 그 결과 답변 시간이 평균 7배 길어지고
블라인드 채점 점수도 낮아졌으며, 출력 한도를 추론에 모두 써 값 없이 끝나는 호출도 있었다(5.4.1절). 이에 AURA는 추론 모드를 끄고,
길이를 제한한 짧은 단계 추론을 답변 앞에 두는 방식을 사용한다. 현재 서빙 컨텍스트 길이는 262,144토큰으로 늘었으므로, 이 설정에서 추론 모드를
다시 비교할 예정이다.

답 앞에는 학습 데이터의 구조 단계 문답과 같은 형식으로 [1단계: 질문 파악] → [2단계: 근거 확인] → [3단계: 답 구성]을 두며, 화면에는 답만 표시하고
추론은 「생각 과정」[^c2-cot]으로 펼쳐 볼 수 있게 했다. 긴 대화를 위해서는 작업 메모를 둔다. 답이 끝나면 배경에서 「지금 목표 / 확정된 것 / 진행 상황 /
남은 일」을 갱신하고, 다음 요청에는 메모와 최근 대화 원문을 컨텍스트 길이의 일정 비율(메모 6%, 최근 대화 30%)만큼 포함한다(3.6.2절). 긴 서식은 메인 에이전트가 같은 모델을 새 컨텍스트로 다시 호출해 절 작성을 위임한다(서브 에이전트). 답변 화면에서 단계 추론과 컨텍스트 사용량이 표시되는 모습은 4.5절의 [그림 4-8]과 같다.

[^c2-cot]: 생각 과정은 답 앞에 적은 단계 추론 글을 화면에서 부르는 이름이다. 2.1.1의 추론 모드와 달리 길이를 통제한 짧은 글이며, 사용자가 펼쳐 볼 때만 보인다.

## 2.8 문서 작성과 공동 편집

담당자는 원본 한글 서식을 유지한 채 익숙한 한글 화면에서 문서를 수정할 수 있어야 한다. 이를 위해 웹 한글 기안기를 편집기로 사용하고, 기안기가 공동 편집 기능을
제공하지 않으므로 영역 단위 편집권으로 동시 편집을 구현하였다.

### 2.8.1 한컴 웹 한글 기안기

한컴 웹 한글 기안기(WebHwpCtrl)는 한글과컴퓨터의 웹 브라우저용 한글 문서 편집기다[53]. 프로그램 설치 없이 브라우저에서 HWP·HWPX 문서를 열어
편집하며, 자바스크립트 API로 필드(누름틀) 읽기·쓰기, 커서 이동, 동작 실행을 제어한다.
교내 행정 서식이 한글 형식이고, 다른 형식으로 바꿔 편집하면 표와 쪽 배치가 달라진다. 원본을 그대로 열면 담당자는 익숙한 한글 화면에서 문서를 수정한다.

AURA는 기안기 13.82.0.208 버전을 운영 서버 안에 설치하고, 사용자는 AURA의 로그인과 열람 범위 확인을 거친 프록시를 통해서만 접근한다. AURA 에이전트가 작성한 절도
사람의 편집과 같은 편집 영역 경로를 거쳐 열려 있는 모든 기안기에 반영된다(4.7절). 기안기에 이미 있는 기능(편집 용지, 쪽 번호, 머리말, 표 편집 등)은 다시
구현하지 않고 동작 실행으로 호출한다. 이를 위해 공개 API 메서드 103개와 등록된 동작 467개를 조사해 기능 목록을 정리했다. 표 배치에는 주의가
필요하다. 기안기는 「글자처럼 취급」으로 설정된 표를 쪽 경계에서 나누지 못하므로, 행이 많거나 쪽 본문 높이의 절반을 넘는 표는 셀 단위로 나뉘고
본문과 함께 흐르도록 속성을 바꾼다. [그림 2-24]는 기안기에서 에이전트와 사람이 같은 작업 문서를 함께 연 화면이다.

[그림 2-24] 한컴 웹 한글 기안기 화면 (그림 docs/images/figures-1025/f2-25-aura-writing-editor.jpg)

에이전트가 작성한 절이 세 사람의 화면에 동시에 나타나며, 사용자는 익숙한 한글 편집 화면을 그대로 사용한다.

### 2.8.2 공동 편집 기법과 SSE

여러 사람이 같은 문서를 동시에 고치는 공동 편집의 대표 기법은 둘이다. 연산 변환(Operational Transformation, OT)[54]은 동시에 일어난 편집 연산을 서로의
결과에 맞게 변환하고, CRDT(Conflict-free Replicated Data Type)[55]는 병합 순서와 상관없이 같은 결과가 나오도록 설계한 자료구조를 사용한다. 둘 다 문서
내부 모델에 글자 단위로 접근해야 한다.

웹 기안기의 공개 API에는 문서 변경 이벤트가 없고 문서 내부 모델에도 접근할 수 없어 OT·CRDT를 적용할 수 없다. 사용할 수 있는 것은 필드 API,
커서 저장·복원, 편집 영역의 내용을 서식과 함께 읽고 삽입하는 블록 입출력뿐이다. 이에 네 가지 방안을 비교해(4.7절) 영역 단위 비관적 편집 잠금(lease)[^c2-lease] 방식을 선택하였다.

[^c2-lease]: 비관적 방식은 충돌이 일어난 뒤 병합하는 대신 미리 편집권을 한 사람에게만 주어 충돌을 막는 방식이다. 편집 잠금은 일정 시간이 지나면 저절로 풀리는 편집권이므로, 사용자의 연결이 끊겨도 편집 영역이 영구히 잠기지 않는다.

문서를 열 때 제목과 표 셀을 포함한 모든 글 문단을 편집 영역(필드)으로 감싸 주소로 사용한다. 사용자는 편집 영역을 처음 수정할 때 편집권을 얻고, 바뀐 부분만
버전 번호와 함께 서버로 보내며, 서버 기록을 기준으로 삼는다. 같은 편집 영역을 두 사람이 동시에 수정하지 않으므로 병합이 필요 없다. 버전 번호가 맞지 않는
변경은 버리지 않고 충돌 사본[^c2-conflict]으로 보관한다. 표나 용지 설정처럼 편집 영역에 담기지 않는 수정은 한 사람씩 문서 전체를 저장하고, 다른 화면은 새 버전을
받는다. AURA 에이전트도 같은 경로로 편집 영역에 작성하는 참여자이며, 사람이 편집권을 보유한 편집 영역에는 작성하지 않는다. [그림 2-25]는 이 구조를 나타낸다.

[^c2-conflict]: 충돌 사본은 다른 사람이 먼저 바꾼 편집 영역에 늦게 도착한 변경을 덮어쓰지 않고 따로 보관한 사본이다. 사용자가 나중에 확인해 반영할 수 있다.

[그림 2-25] 영역 단위 공동 편집 구조 (캡처 있음: docs/images/diagrams/03-hwp-coedit.png)

각 화면의 어댑터가 기안기 API로 편집 영역의 변경을 읽어 공동 편집 층에 넘기고, 서버는 편집권과 버전 번호를 확인해 반영한 뒤 다른 화면에 알린다.
헤드리스 브라우저 세 창으로 측정한 결과, 한 글자 입력이 다른 화면에 반영되기까지의 지연은 중앙값 221ms였고 유실된 글자는 없었다. 실제 기안기에서
세 창이 Enter를 섞어 빠르게 동시 입력한 실험과 AURA가 다른 절을 작성하는 동안 입력한 실험에서도 글자 누락이나 문단 겹침은 없었다.

변경 알림은 SSE로 전송한다. SSE(Server-Sent Events)는 웹 서버가 HTTP 연결 하나로 브라우저로 이벤트를 지속적으로 전송하는 표준이다[56]. 브라우저는 EventSource 객체로 받고, 연결이
끊기면 마지막으로 받은 이벤트 번호(Last-Event-ID)를 붙여 자동으로 다시 연결한다.

Socket.IO 같은 양방향 라이브러리나 협업 프레임워크는 새 의존성과 빌드 단계가 필요하다. 반면 SSE는 빌드 없는 정적 자바스크립트 화면과 FastAPI에서
그대로 사용할 수 있고, 연결이 끊긴 뒤 이어서 수신하는 기능이 표준에 포함되어 있다.

공동 편집에서 서버의 알림 전송은 SSE로, 클라이언트의 변경 전송은 일반 HTTP POST로 처리한다. [그림 2-26]은 이 알림 흐름을 나타낸다.

[그림 2-26] SSE 알림 흐름 (그림 docs/images/diagrams/c2-27-sse.png)

한 화면이 편집 영역의 변경을 POST로 보내면 서버가 이를 기록하고, SSE 연결을 열어 둔 다른 화면들에 변경 이벤트를 전송한다. 앱 프로세스가 여러 개이면
프로세스 사이의 알림은 같은 DB를 1초 주기로 읽어 전달한다. 네트워크가 끊긴 뒤 반쯤 열린 채 남은 연결을 감지하기 위해 서버는 주기적으로
빈 알림을 보내고, 화면은 일정 시간 알림이 없으면 다시 연결한다.

### 2.8.3 Google Docs·Drive API

구글 드라이브 API[57]는 파일 목록·내려받기·내보내기를, 구글 독스 API[58]는 문서 구조 읽기(documents.get)와 원자적 일괄 갱신(documents.batchUpdate)을
제공한다. 인증은 OAuth 2.0[59]으로, 사용자가 허용한 범위 안에서만 접근한다.
담당자 문서의 일부가 구글 드라이브에 있어 드라이브를 읽기 전용 자료원으로 연결했다. 주 편집기는 한글 기안기이고, 구글 독스는 선택할 수 있는 보조 편집기다.

가져온 문서는 업로드와 같은 처리 경로(부서·등급·개인정보·청크·색인)를 거친다. 구글 독스를 작업 문서로 열면 에이전트가 API로 같은 문서를 읽고
수정한다. 독스에 작성하는 것은 외부 전송에 해당하므로 학교 계정으로만 연결하며(3.5.3절), 독스에 입력하는 글은 개인정보 검사를 한 번 더 거치고, 모든 쓰기는 감사 기록에 남긴다. [그림 2-27]은 부서 폴더와
구글 드라이브의 파일을 한 창에서 선택하는 파일 가져오기 창이다.

[그림 2-27] 파일 가져오기 창 (그림 docs/images/figures-1022/f05-file-finder.jpg)

## 2.9 웹 플랫폼

웹 화면은 인터넷이 막힌 교내 서버에 설치할 구성 요소를 줄이고 배포를 단순하게 하도록, 빌드 단계 없이 서버에서 그리는 구성으로 만들었다.

FastAPI는 파이썬 타입 힌트로 요청 검증과 API 문서를 자동 생성하는 비동기 웹 프레임워크다[60]. Jinja2는 파이썬 템플릿 엔진이다[61].
두 도구를 함께 사용하면 프런트엔드 빌드 단계 없이 배포가 코드 반영과 재시작으로 끝나므로 채택하였다.

FastAPI에서 Jinja2 템플릿으로 화면을 서버에서 렌더링하고, 화면마다 가벼운 자바스크립트 파일(채팅 작업 공간, 문서 작업 공간, 드라이브 탐색, 공동
편집 등)만 추가한다. 답 생성처럼 오래 걸리는 작업은 배경에서 실행하고, 화면은 몇 초마다 진행 상태를 조회해 단계와 근거 개수만 받는다. 모델의
내부 추론이나 원문은 진행 상태에 포함하지 않는다. 업데이트 시에는 진행 중인 요청이 끝나기를 기다려 재시작하고, 새 버전이 기동하지 않으면
이전 버전으로 되돌린다.

## 2.10 기존 연구와의 비교

AURA가 기존 접근과 다른 점은 문서를 학교 밖으로 보내지 않으면서, 검색 범위를 사업 구조로 좁히고, 원본 한글 서식을 지킨 채 사람과 에이전트가
한 문서를 함께 편집한다는 데 있다. 개별 기술은 대부분 공개된 것이지만, 행정 문서 업무에 필요한 이 조건들을 한 시스템에서 함께 만족시키는 접근은
아래 세 범주의 선행 접근에서 찾기 어렵다. 비교는 특정 기관의 사례 단위가 아닌 접근 방식의 범주 단위로 한다.

상용 클라우드 사무 AI는 문서 요약, 초안 작성, 공동 편집을 하나의 서비스로 제공하지만, 문서와 질문이 서비스 제공자의 서버로 전송된다. 개인정보와
기관 내부 정보가 든 행정 문서에는 이 전제가 맞지 않는다(1.1.2절). 또한 한글(HWP·HWPX) 원본은 대개 다른 형식으로 바꾸어야 다룰 수 있어, 제출용 서식의 표와 쪽
배치가 달라질 수 있다.

일반적인 청크 유사도 RAG[1]는 문서를 청크로 나누어 질문과 비슷한 청크를 찾는다. 사업 이름이 단계마다 바뀌고 같은 서식이 해마다 반복되는 행정
문서에서는 단어가 비슷한 다른 사업이나 다른 연도의 청크가 함께 검색되기 쉽고, 「계획 대비 실적」처럼 문서 사이의 관계를 묻는 질문에는 답할
근거가 없다. AURA는 같은 하이브리드 검색을 사용하되, 그 앞에서 지식 그래프로 사업·연차·서류 종류를 먼저 정한다.

GraphRAG[42]는 문서에서 개체와 관계를 뽑아 그래프를 만들고, 그래프를 묶은 커뮤니티마다 요약을 만들어 문서 집합 전체에 대한 질문에 답하는 데 초점을 둔다.
AURA의 그래프는 요약이 아니라 검색 범위를 정하는 데 사용한다. 사업 > 연차 > 문서 > 절이라는 행정 업무의 구조를 온톨로지로 미리 정하고,
관계마다 문서 위치나 외부 출처를 근거로 기록하며, 27B가 질문을 이 온톨로지의 용어로 해석하면 코드가 그래프를 따라가 범위를 정한다. 선행 접근과의 차이는 [표 2-1]과 같다.

| 비교 항목 | 상용 클라우드 사무 AI | 청크 유사도 RAG[1] | GraphRAG[42] | AURA |
|---|---|---|---|---|
| 문서와 모델의 위치 | 서비스 제공자 서버 | 구성에 따라 다름 | 구성에 따라 다름 | 교내 장비 |
| 검색 범위를 정하는 방법 | 서비스 내부 방식 | 질문과 청크의 유사도 | 자동 추출한 개체 그래프와 커뮤니티 요약 | 사업·연차 온톨로지로 범위를 좁힌 뒤 하이브리드 검색 |
| 그래프의 목적 | 해당 없음 | 해당 없음 | 문서 집합 전체의 요약 | 검색 범위 제한과 문서 사이 관계 질문 |
| 한글 원본 서식 | 대개 다른 형식으로 변환 | 다루지 않음 | 다루지 않음 | 원본 HWPX에 바뀐 XML만 삽입해 보존 |
| 공동 편집과 에이전트 | 서비스 고유 방식 | 다루지 않음 | 다루지 않음 | 사람과 에이전트가 같은 영역 단위 편집권으로 한 문서를 공동 작성 |

[표 2-1] 선행 접근과 AURA의 차이

이 차이는 행정 문서 업무의 조건에서 비롯된다. 문서를 외부로 보낼 수 없으므로 모델을 교내에 두었고, 같은 사업의 비슷한 문서가 많으므로 사업 구조로
범위를 좁혔으며, 제출 서류가 한글 서식이므로 원본을 보존하고 그 위에서 사람과 에이전트가 함께 작성하도록 하였다. 범위 제한의 효과는 5.3.2에서 같은 평가 데이터셋으로 측정한다.
