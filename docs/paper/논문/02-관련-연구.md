# 2. 관련 연구

이 장은 AURA를 이루는 기술을 생성 모델과 서빙(2.1), 모델 학습(2.2), 문서 읽기와 변환(2.3), 검색(2.4), 지식 표현(2.5), 개인정보 보호(2.6),
에이전트(2.7), 문서 작성과 공동 편집(2.8), 웹 플랫폼(2.9)으로 나누어, 각 기술의 개요와 채택 이유, AURA에서의 적용 방식을 기술한다.
수치는 본 프로젝트의 측정 기록에서 가져왔으며 측정 방법은 5장에서 다룬다.

## 2.1 생성 모델과 서빙

### 2.1.1 Qwen3.8-27B

Qwen은 알리바바 Qwen 팀이 공개하는 오픈웨이트 언어모델 계열이다[2]. Qwen3.8-27B는 매개변수 약 270억 개가 매 토큰 계산에 모두 참여하는
dense 구조이며[^dense], 이미지 입력과 최대 262,144토큰의 문맥을 다룬다[3]. 같은 계열에는 토큰마다 일부 매개변수만 계산하는 MoE 모델도 있으나,
본 프로젝트는 판독과 작성 품질, 학습 도구의 성숙도를 고려해 dense 모델을 기본으로 삼았다.

[^dense]: dense 구조는 모든 매개변수가 매 토큰 계산에 참여하는 구조다. MoE(Mixture of Experts) 구조는 여러 전문가 층 가운데 토큰마다 일부만 골라 계산하므로 계산량은 적지만, 전체 가중치는 메모리에 올려 두어야 한다.

채택한 이유는 네 가지다. 첫째, 스캔 문서와 사진 판독까지 한 모델로 처리할 수 있다. 서빙 장비 두 대에는 여러 모델을 함께 올릴 메모리가 없고,
시험한 소형 판독 모델은 없는 문장을 지어내거나 같은 줄을 반복했다. 둘째, dense 구조여서 LoRA 학습(2.2.1)과 vLLM 어댑터 서빙(2.1.2)이 검증되어 있다.
셋째, NVIDIA가 젯슨용 NVFP4 양자화 모델을 공식 배포한다[4]. 넷째, Apache 2.0 라이선스여서 학습한 모델에 대한 이름 표시 의무가 없다. 국내 모델 EXAONE 4.0 32B[6]와
HyperCLOVA X SEED Think 32B[7]는 한국어 지식 벤치마크 KMMLU[8]에서 앞서지만, 이미지 입력, 라이선스, 젯슨용 양자화 모델 가운데 한 가지씩 조건이 맞지 않았다.
AURA는 지식을 검색으로 공급하므로, 모델에는 지식의 양보다 주어진 문서를 읽고 형식에 맞춰 쓰는 능력이 더 중요하다고 판단했다. 초기 서빙 검증은 같은 계열의
MoE 모델 Qwen3.5-35B-A3B[5]로 수행했다.

AURA에서는 이 모델 하나가 대화 응답, 문서 작업 에이전트, 업무 도우미, 반입 검토, 이미지 판독, 질문 해석, 서류 종류·사업 판정을 모두 담당한다.
코드는 모델 이름이 아니라 용도로 모델을 호출하며, 용도별 서버·모델 이름·생각 모드 인자·구조화 출력 방식·동시 요청 상한은 연결 설정에 둔다(3.6.3).
따라서 더 큰 모델로 교체할 때는 설정만 바꾸면 된다. Qwen 계열은 생각 모드[^think]가 기본으로 켜져 있어, 이를 끄지 않으면 출력 한도를 추론에
모두 소모하고 빈 값을 반환한다. 이 때문에 클라이언트에서 생각 모드를 기본으로 끈다. 응답 생성에 생각 모드를 켜 본 결과 속도는 7배 느려지고
채점 결과도 나빠졌다.

[^think]: 생각 모드는 모델이 최종 답을 내기 전에 추론 과정을 별도 구간에 먼저 생성하는 동작 방식이다. 추론 구간도 출력 토큰 한도에 포함된다.

### 2.1.2 vLLM

vLLM은 대규모 언어모델 추론 서빙 엔진이다[9]. 언어모델은 토큰을 하나씩 생성하면서 앞선 토큰들의 주의(attention) 키·값 벡터를 캐시에
보관한다. 요청마다 최대 길이만큼 연속된 메모리를 미리 잡으면 실제로 쓰지 않는 공간이 많이 남는다. vLLM의 PagedAttention[10]은 운영체제의
가상 메모리 페이징처럼 이 캐시를 고정 크기 블록으로 나누어 필요할 때마다 할당한다. 그 결과 메모리 낭비가 줄고, 남은 메모리로 더 많은 요청을
동시에 처리할 수 있다. vLLM은 생성 도중에도 새 요청을 배치에 넣어 함께 처리하며, OpenAI 호환 HTTP API를 제공한다.

LoRA 어댑터 서빙, 동시 요청 처리, 양자화 정밀도(NVFP4·FP8·bf16) 선택, 구조화 출력[50][^so]을 하나의 엔진에서 지원하므로 채택했다. 특히
구조화 출력은 에이전트가 고른 도구와 인자를 코드가 그대로 실행하는 AURA의 구조(2.7.1)에 필수적이다.

[^so]: 구조화 출력은 생성 단계에서 주어진 JSON 스키마에 맞지 않는 토큰을 후보에서 제외해, 출력이 항상 스키마를 따르게 하는 기능이다.

각 서빙 장비에는 vLLM 컨테이너 하나로 Writer 27B NVFP4를 띄우고, 앱은 OpenAI 호환 API(/v1)로 접속한다.
서빙 문맥 길이는 모델 최대치인 262,144토큰이다. 젯슨에는 NVIDIA의 젯슨용 컨테이너 이미지를, 일반 GPU 서버에는 공식 이미지를 사용하며,
버전은 태그가 아닌 이미지 다이제스트로 고정한다. 포트는 내부망에만 열고 접근 키를 요구한다. 에이전트 단계 출력과 질문 해석 결과는
구조화 출력으로 받으며, 서버가 스키마 강제를 지원하지 않으면 JSON 형식을 지시한 뒤 결과를 파싱한다.

### 2.1.3 NVIDIA Jetson AGX Thor와 NVFP4 양자화

Jetson AGX Thor는 NVIDIA의 임베디드·엣지용 컴퓨팅 장비로, CPU와 GPU가 통합 메모리(본 장비 122GB)를 함께 쓴다[11]. 양자화는 가중치를 더 적은
비트로 표현해 메모리와 계산량을 줄이는 기법이고, NVFP4는 NVIDIA가 Blackwell 세대 GPU 용으로 제시한 4비트 부동소수점 형식으로 작은 블록마다
배율 값을 따로 두어 정밀도 손실을 줄인다[12].

토큰 하나를 생성할 때마다 가중치 전체를 메모리에서 읽어야 하므로, 요청 하나의 생성 속도는 연산 성능보다 메모리 대역폭에 좌우된다.
가중치를 16비트(bf16)에서 4비트로 줄이면 한 번에 읽을 양이 약 4분의 1로 줄어든다. 젯슨 토르는 FP4·FP8 연산도 하드웨어로 가속하므로,
가중치가 작을수록 빠르다. 원본 bf16 모델은 요청 하나당
초당 2~5토큰으로 실사용이 어려웠고, NVFP4 모델은 초당 10.4~10.9토큰을 내면서 같은 입력에 대한 검토·판독 결과가 원본과 같았다.

두 장비에 같은 모델을 올리고 작업 성격에 따라 장비를 나눈다. 토르 02는 대화 응답·문서 작업·업무 도우미처럼 사용자가 결과를 기다리는 작업을,
토르 03은 반입 검토·이미지 판독·질문 해석·판정 같은 배치 작업과 임베딩·리랭커 서비스를 담당한다. 이로써 수만 건의 반입 검토가 진행되는
동안에도 대화 응답이 지연되지 않는다. 정밀도는 NVFP4, FP8, bf16 순으로 우선하되, 같은 입력에 대한 검토·판독과 초안 수치가 원본과 일치할 때만 채택한다.

### 2.1.4 다음 토큰 예측 층을 이용한 추측 디코딩

추측 디코딩(speculative decoding)은 가벼운 예측기가 다음 토큰 몇 개를 미리 짐작하고 본 모델이 한 번에 검증해 맞은 만큼 받아들이는 기법이다[13].
여러 토큰 예측(multi-token prediction, MTP)[14] 층을 함께 학습한 모델은 그 층을 예측기로 쓸 수 있다. [그림 2-4]는 이 과정을 나타낸다.

[그림 2-4] 추측 디코딩 개념도: 예측 층의 짐작과 본 모델의 검증 (그림 docs/images/diagrams/c2-04-speculative.png)

예측 층이 다음 토큰 후보를 제안하면 본 모델은 한 번의 순전파로 후보 전체를 검증하고, 처음 어긋난 위치 앞까지만 받아들인다. 예측이 맞을수록
한 번의 계산으로 여러 토큰을 얻게 된다. 검증을 본 모델이 수행하므로 출력 분포가 바뀌지 않고, 별도 예측 모델 없이 모델 내부의 층을 사용하므로
메모리 사용량도 거의 늘지 않는다. 별도의 소형 예측 모델을 두는 방식과 비교하면 두 모델의 어휘와 버전을 맞출 필요가 없다는 장점도 있다.

Qwen3.8-27B에 포함된 MTP 층으로 토큰 두 개를 미리 예측하게 했다. 생성 속도는 반입 검토에서 초당 10.6토큰에서 23.8토큰으로, 대화 응답에서
약 12토큰에서 24.6토큰으로 올랐다. 다만 GPU 메모리 할당 비율은 같은 장비의 임베딩·리랭커가 쓰는 메모리를 제외한 범위에서 정해야 한다.
기동 시점의 여유 메모리보다 크게 잡았을 때 엔진이 뜨지 못해 검토가 약 25분 중단된 일이 있었다.

## 2.2 모델 학습

### 2.2.1 LoRA와 SFT

지도 미세조정(Supervised Fine-Tuning, SFT)은 입력과 바라는 출력의 쌍으로 사전학습 모델을 추가 학습하는 방법이다. LoRA(Low-Rank Adaptation)[15]는
원래 가중치를 고정하고 각 층에 더한 작은 저랭크 행렬 두 개만 학습한다. 가중치 행렬 W(d×k)를 직접 고치는 대신 변화량을 B(d×r)와 A(r×k)의
곱으로 나타내며, 랭크 r은 d와 k보다 훨씬 작다. [그림 2-5]는 이 구조를 나타낸다.

[그림 2-5] LoRA 구조 개념도: 고정 가중치와 저랭크 행렬 두 개 (그림 docs/images/diagrams/c2-05-lora.png)

입력은 고정된 W와 학습되는 BA를 나란히 지나 더해지며, 학습이 끝나면 BA를 W에 더해 하나의 모델로 병합할 수 있다. 학습할 매개변수가 전체의
일부에 불과하므로 메모리 사용량이 적어 27B 모델을 학습 장비 한 대에서 학습할 수 있다. 전체 미세조정과 달리 결과가 작은 어댑터 파일로 남아,
기본 모델에 결합하거나 병합하기도 쉽다.

학습 장비(DGX)에서 Hugging Face의 PEFT[16]와 TRL[17]로 bf16 LoRA SFT를 수행한다(랭크 32, 2에폭, 학습 문맥 16,384토큰). 서빙에 반영할 때는 어댑터를
기본 모델에 병합한 뒤 운영과 같은 NVFP4로 다시 양자화하여 후보 서빙 이름으로 올린다. 어댑터의 층 이름이 서빙 모델 구조와 맞지 않으면 vLLM이
오류 없이 어댑터를 적용하지 않으므로, 생성 결과를 비교하기 전에 정답의 로그확률로 학습 반영 여부를 먼저 확인한다.

학습 범위는 의도적으로 좁혔다. 사업의 사실과 수치는 해마다 바뀌고, 내부 원문을 학습하면 개인정보가 모델에 남는다. 따라서 사실은 검색과
지식 그래프로 공급하고, 학습은 무엇을 어디서 찾아 어떤 근거로 답을 구성할지 정하는 문맥 구성 추론과 문서 구조에만 적용한다. 이 절차와 데이터는
더 큰 모델에 적용하기에 앞서 Writer 27B로 검증했다(학습 4,434건, 검증 346건, 시험 220건). 학습한 형식의 요청에서는 정답과의 겹침이 늘었고,
에이전트 단계 요청의 JSON 형식도 학습 데이터에 포함해야 한다는 보완점이 드러났다(5.4.5절).

### 2.2.2 Label Studio

Label Studio는 사람이 웹 화면에서 항목별로 판정·수정한 결과를 내보내는 오픈소스 데이터 주석 도구다[18].
교내 장비에 설치할 수 있고 판정 화면을 검수 항목에 맞게 구성할 수 있어 채택했다.

학습 장비에 설치해 학습 데이터의 사람 검수에 사용한다. 자동 검사(근거 기록 유무, 근거가 해당 대화 턴에 그대로 있는지, 숫자가 근거에 있는지,
중복 여부)를 통과한 후보를 검수자가 근거·구조·맥락·개인정보 네 항목으로 확인해 채택·수정·폐기한다. 자동 생성물을 그대로 정답으로 삼지 않도록,
네 항목이 모두 확인된 데이터만 승인한다. 운영 서버에는 학습셋의 이름·상태·건수만 목록으로 전달된다.

## 2.3 문서 읽기와 변환

### 2.3.1 MinerU

MinerU는 OpenDataLab이 공개한 문서 구조 추출 도구다[19][20]. 먼저 배치 분석 모델이 쪽 이미지에서 제목·문단·표·그림·수식 영역을 검출하고
읽기 순서를 정한다. 이어서 영역 종류마다 표 인식, 수식 인식, OCR 모델을 적용해 내용을 읽고, 결과를 마크다운으로 합친다. 표는 병합 셀을
포함한 HTML로 낸다. 글자를 한 줄씩 읽는 일반 OCR과 달리 쪽의 구조를 먼저 파악하므로, 2단 배치와 표가 많은 행정 문서에 적합하다.

같은 실물 문서로 파서를 비교해 선정했다. 스캔 판독의 어절 F1은 MinerU 0.690, docling[21] 0.334였고, dots.ocr는 고유명사를 잘못 읽고 영어 문장을
지어냈다. 27B 이미지 판독은 0.839로 가장 높지만 쪽당 165초가 걸려 대량 처리에는 적합하지 않다.

대량 스캔 판독은 학습 장비 GPU에서 MinerU로 배치 처리하고(쪽당 약 7.6초), 짧은 스캔 문서와 사진은 27B 판독을 우선 사용한다. 디지털 PDF도
표·2단 배치·읽기 순서는 MinerU로 분석하되 글자는 원본 글자층의 것으로 대체한다. 글자층이 있는 문서를 스캔본처럼 처리하면 정상 글자까지
오인식하므로, 읽기 전에 글자층 유무를 먼저 판별해 처리 경로를 나눈다(2.3.2).

### 2.3.2 PDF 글자층 직독과 보조 OCR

디지털 PDF는 글자와 좌표가 파일 안에 들어 있다. PDFium[22]은 이 글자층을 좌표째 읽는 PDF 엔진이다.
OCR로 다시 읽으면 정상 글자까지 오인식하지만(「기초과학」→「기추과하」), 직독은 원본 글자를 그대로, 그리고 빠르게 얻는다.

문서 전체에서 고르게 추출한 여섯 쪽의 쪽당 글자 수가 충분하고 깨진 글자 비율이 0.15 미만이면 직독하고, 그렇지 않으면 스캔본으로 보고 OCR 경로로
보낸다. 사진은 27B 이미지 판독, MinerU OCR, Tesseract[23] 순서로 시도한다. 화면의 원본 복원 보기는 원본 쪽 이미지를 배경에 두고 그 위에 투명한
글자층을 얹는 방식이며, 디지털 PDF는 글자 좌표를, 스캔본은 MinerU의 줄 좌표를 사용한다. [그림 2-9]는 원본 복원 보기 화면이다.

[그림 2-9] 원본 복원 보기 화면: 원본 쪽 위의 투명 글자층 (그림 docs/images/figures-1027/f2-09-original-text-layer.jpg)

사용자는 원본과 같은 모습의 쪽에서 글자를 선택하고 검색할 수 있으며, 추출된 글자가 원본의 위치와 맞는지도 직접 확인할 수 있다.

### 2.3.3 한글 문서 형식과 kordoc

한글(HWP)은 국내 공공기관과 대학 행정의 기본 문서 형식이다. 옛 HWP 5 형식은 이진 복합 파일이고, HWPX는 XML 문서를 ZIP으로 묶은 개방형
형식(OWPML[^owpml], KS X 6101)이다[24]. kordoc[25]은 한글(HWP 3/5·HWPX)·PDF·XLSX·DOCX를 자체 파서로 읽어 마크다운·JSON으로 내는 MIT 라이선스 도구다.

[^owpml]: OWPML(Open Word-Processor Markup Language)은 HWPX 문서의 본문·서식·그림을 XML로 기술하는 규격이다. 본문은 구역(section) 단위의 XML 파일로 나뉘어 ZIP 안에 저장된다.

교내 서식 대부분이 이 두 형식이다. kordoc은 30MB 크기의 옛 HWP 파일을 1초 만에 읽었고(기존 pyhwp[26] 경로는 3분), 추출한 글자 양이 같았으며
중첩·병합 표도 보존했다.

HWPX는 자체 OWPML 파서가 표준 라이브러리만으로 ZIP과 XML을 해석해 문단·표·글상자·머리말까지 구조로 읽는다. 옛 HWP는 kordoc을 우선 사용하고
실패하면 pyhwp 경로로 다시 읽으며, 버전을 고정한 포크를 보관해 폐쇄망에서도 같은 결과를 얻는다. 읽은 결과는 AURA 내부 문서 구조(문단·제목·
표 좌표·그림)로 변환하고, 개인정보 처리·조각 나누기·색인은 AURA의 처리기를 사용한다.

한글 완성본을 만들 때는 구역 XML을 다시 직렬화하지 않고, 원본 바이트를 유지한 채 절 제목 문단 뒤에 문단·표·그림 XML을 삽입한다. ZIP 항목
순서와 압축 방식도 유지하고 바뀐 항목만 다시 쓴다(서식 보존 채우기). 변환기로 새로 만든 파일은 표 테두리·칸 폭·글꼴이 원래 서식과 달라
제출용으로 쓸 수 없기 때문이다. [그림 2-10]은 HWPX 파일의 구성과 서식 보존 채우기가 내용을 삽입하는 위치를 나타낸다.

[그림 2-10] HWPX 파일 구조: ZIP 안의 구역 XML과 서식 보존 채우기 위치 (그림 docs/images/diagrams/c2-11-hwpx.png)

구역 XML 가운데 절 제목 문단 뒤만 바뀌고 나머지 항목은 원본 그대로 남으므로, 한글에서 열었을 때 원래 서식이 유지된다. 한글 프로그램을 COM으로
조작하는 방식도 검토했으나 담당자 PC마다 프로그램 설치가 필요해 제외했다.

### 2.3.4 LibreOffice와 오피스 문서 라이브러리

LibreOffice[27]는 명령줄에서 문서 형식을 바꿀 수 있는 오픈소스 오피스 프로그램이다. python-docx·openpyxl·python-pptx[28]는 DOCX·XLSX·PPTX를
읽는 파이썬 라이브러리다.
옛 형식 변환과 열람용 PDF 생성을 서버에 설치한 프로그램 하나로 해결할 수 있어 채택했다.

## 2.4 검색

### 2.4.1 검색 증강 생성

검색 증강 생성(RAG)은 질문과 관련된 문서 조각을 먼저 검색하고, 그 조각을 언어모델 입력에 넣어 답을 생성하는 방식이다[1]. [그림 2-13]은
그 처리 과정을 나타낸다.

[그림 2-13] RAG 개념도: 검색, 근거 묶기, 생성 (그림 docs/images/diagrams/c2-13-rag.png)

문서는 미리 조각으로 나누어 색인해 두고, 질문이 들어오면 관련 조각을 찾아 근거로 묶은 뒤 질문과 함께 모델에 전달한다. 모델은 매개변수에
저장된 지식 대신 전달된 근거에 기대어 답하므로, 학습하지 않은 최신 자료나 내부 자료로도 답할 수 있고 근거를 출처로 제시할 수 있다. 내부
자료를 모델에 직접 학습시키는 방식과 비교하면, 자료가 바뀔 때 색인만 갱신하면 되고 열람 권한도 검색 단계에서 적용할 수 있다. 계획서의
수치에는 근거가 필요하므로 이 특성이 중요했다.

검색은 두 개의 색인과 하나의 그래프로 구성된다. 규정 색인은 교내 규정·지침을 조문 단위로, 사업 문서 색인은 사업 문서 조각을 담으며, 규정 질문과
사업 질문의 결과가 섞이지 않도록 둘을 분리했다. 사업 문서는 지식 그래프(2.5.1)로 검색 범위를 먼저 좁힌다. 열람 권한은 검색 단계의 SQL 조건으로
적용한다. 답을 생성한 뒤에 걸러 내면 모델이 이미 권한 밖 자료를 읽은 상태이기 때문이다. 모델에 전달한 근거 목록이 그대로 화면의 출처가 되며,
답에 포함된 숫자는 코드가 그 근거와 대조한다.

### 2.4.2 KURE 임베딩과 대조 학습

임베딩 모델은 뜻이 가까운 문장이 가까운 고정 길이 벡터가 되게 바꾼다. 질문과 문서 조각을 각각 따로 벡터로 바꾸는 이중 인코더(bi-encoder)
구조이므로, 문서 조각의 벡터는 미리 계산해 두고 질의 시에는 질문 하나만 벡터로 바꾸어 가까운 벡터를 찾는다. 낱말이 달라도 뜻이 가까우면 찾을
수 있다는 점이 어휘 검색(2.4.4)과 다르다. KURE-v1은 고려대학교 NLP&AI 연구실이 다국어 임베딩 모델 BGE-M3[30]를
한국어 데이터로 추가 학습해 공개한 모델로[29], 1,024차원 벡터를 내고 MIT 라이선스다.

한국어 검색 벤치마크에서 상위권이었고 교내 GPU에서 서비스할 수 있는 크기다. 다만 「교원업적평가」, 「차년도 사업비 이월」 같은 교내 용어와 규정
문체에 약해 추가 학습을 진행했다.

학습본(Embed v2)은 규정 조각마다 27B로 세 유형(실무형, 공고 요구사항형, 키워드형)의 합성 질의를 만들고, 운영 검색이 상위에 올린 후보 가운데
정답이 아닌 조각을 어려운 오답(hard negative)으로 사용했다. 학습 목표는 정답 쌍을 가깝게, 배치 내 오답과 어려운 오답을 멀게 하는 InfoNCE[31][^infonce]
(온도 0.05)다. 채택 기준은 임베딩 단독 지표가 아니라 운영 하이브리드 검색에서 정답이 후보에 더 많이 포함되는지로 정했다. 첫 학습본은 단독
지표만 올랐기 때문이다. 색인과 질의는 반드시 같은 모델로 임베딩해야 하므로, 임베딩 모델을 바꾸면 전체를 다시 색인한다. 서비스는 토르 03의
임베딩 서버가 담당하며, 서빙 장비가 응답하지 않으면 규정 검색은 운영 서버 CPU에서 같은 모델을 실행해 대신한다.

[^infonce]: InfoNCE는 정답 쌍의 유사도를 여러 오답의 유사도와 함께 소프트맥스로 비교해 정답 쌍의 확률을 높이는 대조 손실 함수다. 온도는 유사도 분포를 얼마나 날카롭게 만들지 정하는 값이다.

### 2.4.3 bge-reranker-v2-m3 리랭커

리랭커는 질문과 후보 조각을 한 쌍씩 함께 읽어 관련도 점수를 매기는 교차 인코더(cross-encoder)다. bge-reranker-v2-m3는 BAAI가 공개한 다국어
리랭커로, BGE-M3와 같은 계열이고 Apache 2.0 라이선스다[32].

이중 인코더는 질문과 조각을 따로 벡터로 만들기 때문에 두 글 사이의 세부 대응을 보지 못한다. 교차 인코더는 질문과 조각을 하나의 입력으로
이어 붙여 모든 낱말 사이의 주의를 계산하므로 더 정확하지만, 후보마다 모델을 한 번씩 실행해야 해 느리다. 그래서 임베딩·어휘 검색으로 후보를
먼저 줄이고, 상위 후보에만 리랭커를 적용한다. 27B 생성 모델로 후보 순위를 다시 매기는 방식과 비교하면 리랭커가 더 정확했고 53배 빨랐다.

운영 하이브리드 검색이 실제로 올린 후보 목록에서 정답의 확률을 높이는 목록 단위(listwise) 학습으로 학습본(Rerank v1)을 만들었다. 문서 단위
홀드아웃에서 R@1[^r1]이 0.649에서 0.711로 올랐다. 토르 03 GPU의 리랭커 서버로 옮기자 질의당 처리 시간이 3.75초에서 0.07초로 줄어 재정렬 후보를
20개로 늘렸고, 점수가 하한보다 낮은 후보는 근거에서 제외한다. 리랭커는 규정 검색에만 사용한다. 사업 문서 검색에서는 그래프 기반 절 검색 및
문서당 조각 수 제한과 효과가 겹쳐 오히려 성능이 떨어졌기 때문이다.

[^r1]: R@1(Recall@1)은 정답이 1위 후보에 오른 질의의 비율이다. 문서 단위 홀드아웃은 학습에 쓴 문서를 평가에서 통째로 제외하는 평가 방식이다.

### 2.4.4 Kiwi 형태소 분석과 어휘 검색

한국어는 조사와 어미가 결합하므로 어휘 검색에 형태소 분석이 필요하다. Kiwi는 C++로 구현된 한국어 형태소 분석기로 파이썬 바인딩과 사용자 사전을
제공한다[33].
조사 시점에 꾸준히 유지보수되던 한국어 형태소 분석기가 Kiwi뿐이었고, 사용자 사전으로 교내 용어를 추가할 수 있다.

Kiwi로 명사와 두 글자 이상의 영문 약칭을 추출하고, 띄어 쓴 복합 명사를 결합하며, 드문 낱말에 가중치를 주는 IDF[^idf]로 점수를 계산한다. 이는
BM25[34] 계열 어휘 검색과 같은 원리다. 색인과 질의는 같은 낱말 추출 함수를 사용하고, 사업 문서는 낱말을 미리 추출해 PostgreSQL 전문
색인(GIN)[^gin]에 저장한다. 어휘 검색은 사업 약칭이나 규정 이름처럼 글자 그대로 일치해야 하는 질의에서 임베딩 검색보다 강하다.

[^idf]: IDF(Inverse Document Frequency)는 낱말이 등장하는 문서가 적을수록 큰 값을 주는 가중치다. 「사업」처럼 흔한 낱말보다 드문 고유 용어가 점수에 더 크게 기여한다.

[^gin]: GIN(Generalized Inverted Index)은 낱말마다 그 낱말을 포함한 행의 목록을 저장하는 역색인으로, 낱말 포함 여부를 빠르게 찾는다.

[그림 2-16] Kiwi 로고(출처: Kiwi 공식 저장소(bab2min/Kiwi)) (그림 docs/images/logos/f2-16-kiwi.png)

### 2.4.5 RRF 하이브리드 검색

하이브리드 검색은 어휘 검색과 의미 검색의 결과를 섞는다. RRF(Reciprocal Rank Fusion)[35]는 문서 d의 융합 점수를 각 검색 결과에서의 순위 r에 대한
1/(k + r)의 합으로 정한다. 상수 k는 상위 몇 개 순위가 점수를 독차지하지 않도록 완화하는 값이다. AURA는 검색 결과마다 가중치 w를 곱해
w/(k + r)을 더하는 가중 RRF를 사용한다.

두 검색의 점수는 척도가 달라 점수를 그대로 더할 수 없다. 점수를 정규화해 합치는 방식은 질의마다 점수 분포가 달라 보정이 필요하지만, RRF는
순위만 사용하므로 별도 보정 없이 적용할 수 있다. 행정 질문에는 사업 약칭·규정 이름처럼 글자
그대로 일치해야 하는 표현과 「학생이 휴학하려면」처럼 의미로 찾아야 하는 표현이 섞여 있어, 한 가지 검색만으로는 어느 한쪽을 놓친다.

k=60으로 두 검색의 순위를 결합하고, 어휘 검색에 0.4, 의미 검색에 1.0의 가중치를 준다. 가중치는 0.2~0.5 범위에서 결과 차이가 거의 없었고,
학습 문서를 제외한 질의로 다시 측정해도 같아 0.4를 유지했다. 사업 문서 검색에서는 어휘 검색 1위 조각이 융합 순위에서 밀려나지 않도록 보정한다.
융합 순위 상위 20개가 리랭커의 후보가 된다. [그림 2-17]은 이 검색 흐름을 나타낸다.

[그림 2-17] RRF 하이브리드 검색 흐름: 어휘 축·의미 축·순위 융합·리랭커 (그림 docs/images/diagrams/c2-17-hybrid.png)

어휘 검색과 의미 검색이 각각 낸 순위를 RRF로 합쳐 후보를 정하고, 규정 검색에서는 그 상위 후보를 리랭커가 다시 정렬해 최종 근거를 고른다.

### 2.4.6 PostgreSQL과 pgvector

PostgreSQL은 오픈소스 관계형 데이터베이스다[38]. pgvector는 여기에 벡터 자료형과 근접 이웃 검색 색인을 더하는 확장으로[36], 근사 검색 색인
HNSW[37]를 지원한다. HNSW는 벡터들을 서로 가까운 것끼리 잇는 그래프를 여러 층으로 만든다. 위층은 듬성듬성하게, 아래층은 촘촘하게 이어져
있어, 검색은 위층에서 대략적인 위치를 찾은 뒤 아래층으로 내려가며 가까운 이웃을 좁혀 간다. 모든 벡터와 거리를 계산하는 정확 검색보다 훨씬
빠르며, 대신 일부 이웃을 놓칠 수 있다.
별도 벡터 데이터베이스 없이 권한·부서·서류 종류 조건을 벡터 검색과 같은 SQL에 걸 수 있고, 조인·트랜잭션·백업을 한 시스템에서 처리할 수 있다.

사업 문서 조각 벡터 약 156만 개를 halfvec[^halfvec] 1,024차원 HNSW 색인에 저장한다. 이전에는 운영 서버 메모리의 벡터 배열로 검색했는데, 이를 옮긴 결과
정답 문서 적중은 거의 같으면서 검색 시간은 3.49초에서 1.85초로 줄었고 5GB가 넘는 배열이 메모리에서 빠졌다. 정확 계산 대비 근사 검색의
recall@10은 0.915다. 즉 정확 검색의 상위 10개 가운데 평균 91.5%를 근사 검색도 찾았다. 문서·조각·권한과 지식 그래프의 노드·관계도 같은
PostgreSQL에 표로 저장하므로 백업은 앱 스키마 덤프 하나로 끝난다.

[^halfvec]: halfvec은 벡터의 각 값을 16비트 부동소수점으로 저장하는 pgvector 자료형으로, 32비트 저장보다 크기가 절반이다.

## 2.5 지식 표현

### 2.5.1 온톨로지와 지식 그래프

온톨로지는 한 분야의 개념(클래스)과 관계, 제약을 명시적으로 정의한 것이고, 지식 그래프는 온톨로지에 따라 실제 대상(노드)과 관계(간선)를 이은
데이터다. GraphRAG[39]는 조각 유사도와 함께 그래프 구조로 검색 범위를 정하거나 근거를 모으는 RAG 방식이다.

문서가 수만 건에 이르면 사업·연차·서류 종류로 범위를 먼저 좁혀야 한다. 또한 「계획 대비 실적」이나 「앞 단계 사업」처럼 문서 사이의 관계를
묻는 질문은 그 관계가 데이터로 존재해야 답할 수 있다. 조각 유사도만 쓰는 일반 RAG는 비슷한 낱말이 많은 다른 사업이나 다른 연도의 문서를
함께 가져오기 쉽다. [그림 2-19]는 AURA의 온톨로지를 나타낸다.

[그림 2-19] AURA 온톨로지: 노드 여덟 종류와 관계 (그림 docs/images/diagrams/c2-19-ontology.png)

노드는 여덟 종류(사업 묶음, 사업, 기관, 연차, 문서, 절, 단위과제, 성과지표)이고, 관계는 포함, 계획↔실적, 평가, 앞·뒤 단계, 편입, 연관, 주관 부처·
전담기관, 성과지표 측정 등이다. 관계마다 근거(문서·절 위치 또는 외부 출처 URL)를 기록하며, 근거 없는 관계는 만들지 않는다. 사업 이름 변경이나
사업 동일성 판단은 외부 검색으로 확인한 출처를 근거로 둔다. 그래프는 PostgreSQL의 노드·관계 표에 저장하고, 입력(문서·조각·서류 종류·사업 장부 등)의
지문이 바뀌면 주기 작업이 다시 구축한다. 질문이 들어오면 27B가 질문을 온톨로지의 용어(사업 번호, 연도, 차수, 서류 종류, 따라갈 관계)로 해석해
구조화 출력 JSON으로 내고, 그래프 탐색은 코드가 결정적으로 수행한다. 절 질문에서 정답 문서가 상위 5건에 포함된 비율은 전문 검색 18%, 그래프 64%,
그래프와 모델의 질문 해석을 함께 쓴 경우 70%였다.

### 2.5.2 OWL·RDF와 SHACL

RDF는 「주어-서술어-목적어」 세 값으로 정보를 표현하는 W3C 표준 데이터 모델이고[41], OWL은 RDF 위에서 클래스·속성·제약을 정의하는 온톨로지
언어다[40]. SHACL은 RDF 그래프가 지켜야 할 모양(shape)을 정의·검사하는 W3C 표준이다[42].
온톨로지를 표준 형식으로 내보내면 외부 도구로 열람·검사할 수 있고, 규칙을 데이터로 기술해 그래프를 구축할 때마다 자동으로 검사할 수 있다.

그래프 자체는 PostgreSQL 표에 두고, 온톨로지 정의만 rdflib[43]로 OWL·RDF 형식으로 내보내 pySHACL[44]로 검사한다. 규칙의 예로는 「연차는 하나의
사업에만 속하고 연도는 1990~2035 범위에 있다」, 「문서의 서류 종류는 최대 하나이며, 문서는 사업·연차에 속하거나 기관 업무 문서다」, 「모든 관계는
다섯 기준(구조, 분류, 식별자 일치, 추출, 유사도) 가운데 하나에 해당하고 근거를 하나 이상 가진다」가 있다. 검사는 그래프를 다시 구축할 때마다
수행되며 위반은 0건이었다. 내보낸 온톨로지는 Protégé[45] 같은 편집 도구로 열 수 있다.

## 2.6 개인정보 보호

### 2.6.1 Presidio

Presidio는 Microsoft가 시작한 오픈소스 개인정보 탐지·비식별화 프레임워크다[47]. 정규식·체크섬·개체명 인식을 조합한 인식기(recognizer)로
개인정보를 찾아 가리거나 바꾼다. 각 인식기는 후보 문자열과 신뢰 점수를 내고, 주변 문맥에 「성명」 같은 단서 낱말이 있으면 점수를 높인다.
교내 장비에 설치할 수 있고, 사용자 정의 인식기를 추가해 한국형 개인정보를 처리할 수 있다. 상용 클라우드의 개인정보 탐지 서비스는 문서를
외부로 보내야 하므로 AURA의 전제(3.1.1)와 맞지 않는다.

Presidio 위에 한국형 패턴 인식기 8종을 추가했다. 주민등록번호와 사업자번호는 체크섬[^checksum]으로 검증하고, 계좌번호·학번·생년월일·성명은 「계좌번호:」,
「성명」 같은 표지 문맥이 있을 때만 탐지한다. 표에서는 인접 칸의 직위 문맥을 이용해 성명을 한 번 더 가린다. 가림 범위는 용도에 따라 다르다.
담당자가 업무로 보는 원문을 모두 가리면 업무를 할 수 없으므로 내부 열람용 가림은 관리자 설정으로 켜고 끄며, 학습용 반출은 설정과 관계없이
별도 사본에서 전체 탐지와 사람 검수를 거친다. 외부로 나가는 글은 고위험 형식(주민등록번호·이메일·휴대전화·카드번호)을 항상 한 번 더 검사하고,
가림에 실패하면 내보내지 않는다. 전체 문서와 조각을 다시 검사했을 때 가려야 할 잔여는 0건이었다. 그러나 정규식 기반이어서 표지 문맥이 없는
이름·주소를 놓칠 수 있으므로, 이 결과가 완전한 제거를 증명하지는 않는다.

[^checksum]: 체크섬은 번호의 마지막 자리를 앞자리들로부터 정해진 산식으로 계산해 두는 검증 방식이다. 형식만 같은 임의의 숫자열을 걸러 내 오탐을 줄인다.

## 2.7 에이전트

### 2.7.1 도구 사용 에이전트와 구조화 출력

언어모델 에이전트는 상황과 도구 결과를 보고 다음 행동(도구 호출)을 고르기를 되풀이해 과제를 푼다. ReAct[48]는 추론과 행동을 번갈아 내게 하는
대표 방식이다. 모델이 매 단계 생각을 적고 도구 하나를 고르면, 실행기가 도구를 실행해 결과를 다음 단계의 입력으로 돌려준다. 이 과정은 모델이
마무리를 선택하거나 단계 한도에 이를 때까지 반복된다.

낱말 규칙으로 요청을 해석하면 표현이 조금만 달라도 잘못된 작업을 수행하고, 정해진 순서로만 도는 파이프라인은 요청마다 다른 작업 순서를
따라가지 못한다. 판단은 모델에 맡기고 코드는 그 판단을 안전하게 실행하도록 하기 위해 이 방식을 채택했다. [그림 2-23]은 AURA 문서 작업
에이전트의 실행 흐름이다.

[그림 2-23] 에이전트 실행 흐름: 상태, 도구 선택, 관문, 실행, 기록 (그림 docs/images/diagrams/c2-23-agent.png)

모델이 상태를 보고 도구를 고르면, 코드의 관문을 통과한 경우에만 도구가 실행되고 그 결과와 함께 단계 기록이 남는다.

문서 작업 에이전트는 매 단계의 상태(요청, 최근 대화, 프로젝트 문서 목록, 작업본의 절 목록과 빈 절, 아직 받지 못한 값, 지금까지의 단계)를 보고
`{생각, 도구, 인자}` 를 JSON으로 선택한다. 출력 형식은 vLLM의 구조화 출력[50]으로 강제한다. 한글 기안기 작업용 도구는 근거 찾기, 문서 읽기,
양식 찾기·만들기, 절 쓰기, 칸 채우기, 표 서식, 절 위임·고쳐 쓰기, 값 기억, 사용자에게 묻기, 마무리 등 19가지다. 코드는 여러 관문을 둔다.
단계 수에 상한을 두고, 되돌리기 어려운 도구는 담당자의 요청 글에 그 의도가 드러날 때만 실행한다. 도구 결과 안의 글이 지시처럼 작동하지 않도록
자료 영역을 구분하고, 문서를 바꾸지 못한 쓰기 시도에는 한도를 둔다. 또한 열람 범위와 수치 근거를 대조한다. 단계마다 상태·선택·결과를 기록해
실패 원인 분석과 이후 학습 재료로 활용한다.

### 2.7.2 단계 추론과 대화 기억

단계 추론(chain-of-thought)[49]은 모델이 답 전에 중간 단계를 글로 써 내려가게 해 복잡한 문제의 정확도를 높이는 방법이다.
생각 모드를 켜면 느리고 채점 결과도 나빴으므로(2.1.1), 길이를 통제한 짧은 단계 추론을 답 앞에 두는 방식을 택했다.

답 앞에 [1단계: 질문 파악] → [2단계: 근거 확인] → [3단계: 답 구성]을 두며, 화면에는 답만 표시하고 추론은 「생각 과정」으로 펼쳐 볼 수 있게 했다.
이는 학습 데이터의 구조 단계 문답과 같은 형식이다. 긴 대화를 위해서는 작업 메모를 둔다. 답이 끝나면 배경에서 「지금 목표 / 확정된 것 / 진행 상황 /
남은 일」을 갱신하고, 다음 요청에는 메모와 최근 대화 원문을 문맥 한도의 일정 비율(메모 6%, 최근 대화 30%)만큼 넣는다. 개수가 아니라 비율로 정했으므로
문맥이 긴 모델로 바꾸면 자동으로 맞춰진다. 긴 서식은 메인 에이전트가 같은 모델을 새 문맥으로 다시 호출해 절 작성을 맡긴다(서브 에이전트). 답 화면에서 단계 추론과 문맥 사용량이 표시되는 모습은 4.5절의 [그림 4-8]과 같다.

## 2.8 문서 작성과 공동 편집

### 2.8.1 한컴 웹 한글 기안기

한컴 웹 한글 기안기(WebHwpCtrl)는 한글과컴퓨터의 웹 브라우저용 한글 문서 편집기다[51]. 프로그램 설치 없이 브라우저에서 HWP·HWPX 문서를 열어
편집하며, 자바스크립트 API로 필드(누름틀) 읽기·쓰기, 커서 이동, 동작 실행을 제어한다.
교내 행정 서식이 한글 형식이고, 다른 형식으로 바꿔 편집하면 표와 쪽 배치가 달라진다. 원본을 그대로 열면 담당자는 익숙한 한글 화면에서 문서를 수정할 수 있다.

13.82.0.208 버전을 운영 서버 안에 설치하고, 사용자는 AURA의 로그인과 열람 범위 확인을 거친 프록시를 통해서만 접근한다. AURA 에이전트가 쓴 절도
사람의 편집과 같은 칸 경로를 거쳐 열려 있는 모든 기안기에 반영된다(4장). 기안기에 이미 있는 기능(편집 용지, 쪽 번호, 머리말, 표 편집 등)은 다시
구현하지 않고 동작 실행으로 호출한다. 이를 위해 공개 API 메서드 103개와 등록된 동작 467개를 조사해 기능 목록을 정리했다. 표 배치에는 주의가
필요하다. 기안기는 「글자처럼 취급」으로 설정된 표를 쪽 경계에서 나누지 못하므로, 행이 많거나 쪽 본문 높이의 절반을 넘는 표는 셀 단위로 나뉘고
본문과 함께 흐르도록 속성을 바꾼다. [그림 2-24]는 기안기에서 에이전트와 사람이 같은 작업본을 함께 연 화면이다.

[그림 2-24] 한컴 웹 한글 기안기 화면: AURA 에이전트(27B)가 절을 쓰는 동안 세 사람이 같은 작업본을 연 모습(시연 계정) (그림 docs/images/figures-1025/f2-25-aura-writing-editor.jpg)

에이전트가 쓴 절이 세 사람의 화면에 동시에 나타나며, 사용자는 익숙한 한글 편집 화면을 그대로 사용한다.

### 2.8.2 공동 편집 기법과 칸 단위 편집권

여러 사람이 같은 문서를 동시에 고치는 공동 편집의 대표 기법은 둘이다. 연산 변환(Operational Transformation, OT)[52]은 동시에 일어난 편집 연산을 서로의
결과에 맞게 변환하고, CRDT(Conflict-free Replicated Data Type)[53]는 병합 순서와 상관없이 같은 결과가 나오도록 설계한 자료구조를 쓴다. 둘 다 문서
내부 모델에 글자 단위로 접근해야 한다.

웹 기안기의 공개 API에는 문서 변경 이벤트가 없고 문서 내부 모델에도 접근할 수 없어 OT·CRDT를 적용할 수 없다. 사용할 수 있는 것은 필드 API,
커서 저장·복원, 칸 내용을 서식째 꺼내고 넣는 블록 입출력뿐이다. 이에 네 가지 방안을 비교해 칸 단위 비관적 임대(lease)[^lease] 방식을 선택했다.

[^lease]: 비관적 방식은 충돌이 일어난 뒤 병합하는 대신 미리 편집권을 한 사람에게만 주어 충돌을 막는 방식이다. 임대는 일정 시간이 지나면 저절로 풀리는 편집권으로, 사용자가 연결을 잃어도 칸이 영구히 잠기지 않는다.

문서를 열 때 제목과 표 칸을 포함한 모든 글 문단을 칸(필드)으로 감싸 주소로 사용한다. 사용자가 칸을 처음 고칠 때 편집권을 얻고, 바뀐 부분만
버전 번호와 함께 서버로 보내며, 서버 기록을 기준으로 삼는다. 같은 칸을 두 사람이 동시에 쓰지 않으므로 병합이 필요 없다. 버전 번호가 맞지 않는
변경은 버리지 않고 충돌 사본으로 보관한다. 표나 용지 설정처럼 칸에 담기지 않는 수정은 한 사람씩 문서 전체를 저장하고, 다른 화면은 새 버전을
받는다. AURA 에이전트도 같은 경로로 칸을 쓰는 참여자이며, 사람이 편집권을 가진 칸에는 쓰지 않는다. [그림 2-25]는 이 구조를 나타낸다.

[그림 2-25] 칸 단위 공동 편집 구조: 어댑터, 공동 편집 층, 서버 (캡처 있음: docs/images/diagrams/03-hwp-coedit.png)

각 화면의 어댑터가 기안기 API로 칸 변경을 읽어 공동 편집 층에 넘기고, 서버는 편집권과 버전 번호를 확인해 반영한 뒤 다른 화면에 알린다.
헤드리스 브라우저 세 창으로 측정한 결과, 한 글자 입력이 다른 화면에 반영되기까지의 지연은 중앙값 221ms였고 유실된 글자는 없었다.

### 2.8.3 SSE

SSE(Server-Sent Events)는 웹 서버가 HTTP 연결 하나로 브라우저에 사건을 계속 밀어 보내는 표준이다[54]. 브라우저는 EventSource 객체로 받고, 연결이
끊기면 마지막으로 받은 사건 번호(Last-Event-ID)를 붙여 자동으로 다시 연결한다.

Socket.IO 같은 양방향 라이브러리나 협업 프레임워크는 새 의존성과 빌드 단계가 필요하다. 반면 SSE는 빌드 없는 정적 자바스크립트 화면과 FastAPI에서
그대로 쓸 수 있고, 연결이 끊긴 뒤 이어 받는 기능이 표준에 포함되어 있다.

공동 편집에서 서버의 알림 전송은 SSE로, 클라이언트의 변경 전송은 일반 HTTP POST로 처리한다. [그림 2-26]은 이 알림 흐름을 나타낸다.

[그림 2-26] SSE 알림 흐름: 칸 변경 POST와 사건 밀어 주기 (그림 docs/images/diagrams/c2-27-sse.png)

한 화면이 칸 변경을 POST로 보내면 서버가 이를 기록하고, SSE 연결을 열어 둔 다른 화면들에 변경 사건을 보낸다. 앱 프로세스가 여러 개이면
프로세스 사이의 알림은 같은 DB를 1초 주기로 읽어 전달한다. 네트워크가 끊긴 뒤 반쯤 열린 채 남은 연결을 감지하기 위해 서버는 주기적으로
빈 알림을 보내고, 화면은 일정 시간 알림이 없으면 다시 연결한다.

### 2.8.4 구글 독스·드라이브 연동

구글 드라이브 API[56]는 파일 목록·내려받기·내보내기를, 구글 독스 API[55]는 문서 구조 읽기(documents.get)와 원자적 일괄 갱신(documents.batchUpdate)을
제공한다. 인증은 OAuth 2.0[57]으로, 사용자가 허용한 범위 안에서만 접근한다.
담당자 문서의 일부가 구글 드라이브에 있어 읽기 전용 자료원으로 연결했다. 주 편집기는 한글 기안기이고, 구글 독스는 선택할 수 있는 보조 편집기다.

가져온 문서는 업로드와 같은 처리 경로(부서·등급·개인정보·조각·색인)를 거친다. 구글 독스를 작업본으로 열면 에이전트가 API로 같은 문서를 읽고
수정한다. 독스에 쓰는 것은 외부 전송에 해당하므로 사용자마다 본인의 학교 계정으로만 연결하고, 부서 드라이브는 해당 부서의 총괄 책임자가 부서
공용 학교 계정으로 연결한다. 독스에 넣는 글은 개인정보 검사를 한 번 더 거치고, 모든 쓰기는 감사 기록에 남긴다. [그림 2-27]은 부서 폴더와
구글 드라이브의 파일을 한 창에서 고르는 파일 가져오기 창이다.

[그림 2-27] 파일 가져오기 창: 부서 폴더와 구글 드라이브 (그림 docs/images/figures-1022/f05-file-finder.jpg)

어느 위치에서 고른 파일이든 같은 반입 처리기를 거치므로, 가져온 경로에 따라 검색 결과가 달라지지 않는다.

## 2.9 웹 플랫폼

### 2.9.1 FastAPI와 Jinja2

FastAPI는 파이썬 타입 힌트로 요청 검증과 API 문서를 자동 생성하는 비동기 웹 프레임워크다[58]. Jinja2는 파이썬 템플릿 엔진이다[59].
프런트엔드 빌드 단계가 없어 배포가 코드 반영과 재시작으로 끝나고, 인터넷이 차단된 교내 서버에 설치할 구성 요소가 적다.

FastAPI에서 Jinja2 템플릿으로 화면을 서버에서 렌더링하고, 화면마다 가벼운 자바스크립트 파일(채팅 작업 공간, 문서 작업 공간, 드라이브 탐색, 공동
편집 등)만 붙인다. 답 생성처럼 오래 걸리는 작업은 배경에서 실행하고, 화면은 몇 초마다 진행 상태를 조회해 단계와 근거 개수만 받는다. 모델의
내부 추론이나 원문은 진행 상태에 포함하지 않는다. 업데이트 시에는 진행 중인 요청이 끝나기를 기다려 재시작하고, 새 버전이 기동하지 않으면
이전 버전으로 되돌린다.
