# 1. 서론

대학 행정 문서는 양이 많고 형식이 제각각이며 개인정보를 담고 있어, 상용 클라우드 AI로는 처리할 수 없다. 본 프로젝트는 이 문제를 교내 장비만으로
해결하는 문서 처리 플랫폼 AURA를 구현하고, 문서를 읽는 단계부터 공동 편집까지 각 단계의 효과를 같은 평가 데이터셋으로 측정하였다.

## 1.1 프로젝트 배경 및 목적

행정 문서 업무를 돕는 도구에는 많은 문서에서 필요한 자료를 찾는 능력과 근거에 충실한 정확성이 함께 필요하다. 그러나 문서를 외부로 보낼 수 없다는 조건 때문에
지금까지는 이 일을 사람이 직접 처리해 왔다. AURA는 두 요구를 교내 장비 안에서 충족하는 것을 목적으로 한다.

### 1.1.1 대학 행정 문서 업무의 현황

대학 행정 업무의 상당 부분은 국고 재정지원사업의 공고문·사업계획서·실적보고서·평가 자료, 교내 규정, 공문과 서식을 다루는 일이다.
영남이공대학교 행정 부서도 공고 분석과 계획서 작성, 채용·입학 서류 검토, 규정 확인을 되풀이한다.

이 업무를 어렵게 만드는 요인은 문서의 양, 이름의 변화, 형식의 다양성이다. 본 프로젝트에서 수집한 교내 문서만 약 3만 5천 건이며, 대부분이 86개 국고사업에
속한다. 담당자는 새 계획서를 작성할 때 지난 자료를 파일 서버 폴더에서 일일이 찾아 읽는다. 같은 사업이 단계마다 이름을 바꾸고(LINC+ → LINC 3.0 → RISE 등)
같은 서식도 해마다 조금씩 다른 버전[^c1-version]으로 들어오므로, 사업 이름이나 파일명만으로는 원하는 문서를 찾기 어렵다. 디지털 PDF, 스캔본, 사진,
한글(HWP·HWPX), 오피스 문서가 섞여 있어 문서를 읽는 단계부터 정확도가 떨어진다.

[^c1-version]: 버전은 같은 문서나 서식의 연도별·수정 차수별 사본을 말한다. AURA는 같은 문서의 여러 버전을 하나의 버전 그룹으로 관리한다.

계획서에는 기관의 실제 실적 수치가 들어가므로, 근거 없는 수치는 허위 기재가 되어 사업 평가에서 불이익으로 이어질 수 있다.
따라서 문서 작성 도구는 속도보다 근거의 정확성을 우선해야 한다.

### 1.1.2 교내 구축이 필요한 이유

대규모 언어모델(Large Language Model, LLM)과 검색 증강 생성[^c1-rag](Retrieval-Augmented Generation, RAG)[1]은 문서를 요약하고 근거를 찾아 답하는 데
실용적인 수준에 이르렀다. 그러나 행정 문서에는 개인정보와 기관 내부 정보가 들어 있어 외부 서비스에 보내면 개인정보 보호 법령[2]과 기관 보안 원칙에
어긋난다. 따라서 행정 문서에 언어모델을 활용하려면 모델을 교내에서 운영해야 한다.

[^c1-rag]: RAG는 질문과 관련된 문서의 일부를 먼저 찾아 언어모델 입력에 넣고, 모델이 그 근거에 기대어 답하게 하는 방식이다. 원리는 2.4.1에서 설명한다.

가중치가 공개된 오픈웨이트 모델을 교내 장비에서 서빙하면 문서를 외부로 내보내지 않고도 같은 작업을 수행할 수 있다.
본 프로젝트는 이러한 온프레미스(on-premise) 구성을 전제로 한다.

### 1.1.3 프로젝트 목적

본 프로젝트의 목적은 교내 장비만으로 행정 문서를 읽고, 찾고, 쓰고, 함께 고치는 플랫폼 AURA를 설계하고 구현하는 것이다.
AURA는 학교 원본 문서를 형식에 관계없이 읽어 검색용 청크(chunk)[^c1-chunk]로 나누고 사업·연차·서류 종류별로 정리한다. 질문한 사람의 열람 권한 안에서
근거 문서를 찾아 출처와 함께 답하고, 근거에 없는 수치는 따로 표시한다. 담당자가 요청하면 양식에 맞춰 초안을 작성하고 원본 한글 서식을 유지한 완성본을 생성하며,
여러 담당자와 에이전트가 하나의 한글 문서를 브라우저에서 동시에 편집할 수 있게 한다.

[^c1-chunk]: 청크는 검색 단위로 잘라 낸 문서의 일부다. AURA는 절 경계를 넘지 않게 문서를 나누고, 청크마다 원본 위치와 쪽 번호를 기록한다.

AURA가 산출하는 결과는 사람이 검수하는 초안이다. 시스템은 근거를 갖춘 초안과 검토 의견을 제시하고, 제출 여부는 담당자가 결정한다.
초안 속 수치가 근거 자료에 있는지, 예산 계산이 맞는지는 언어모델의 판단에 맡기지 않고 코드로 구현한 검증기가 확인한다.

## 1.2 핵심 내용

본 프로젝트의 기여는 네 가지 기술을 상용 클라우드 없이 교내 장비만으로 하나의 서비스로 묶고, 각 기술의 효과를 같은 평가 데이터셋(benchmark)[^c1-bench]으로
측정한 데 있다. 네 기술은 다음과 같다.

[^c1-bench]: 평가 데이터셋은 질문과 정답 문서(또는 정답 답안)를 미리 정해 둔 평가 문항의 집합이다. 같은 평가 데이터셋으로 구성만 바꾸어 측정해야 개선 폭을 비교할 수 있다.

- 문서 데이터화: 형식이 제각각인 교내 문서를 표 구조를 보존하고 개인정보를 처리하면서 검색 가능한 청크로 바꾼다.
- GraphRAG: 사업·연차·문서·절을 연결하는 지식 그래프[^c1-kg]로 검색 범위를 먼저 좁힌 뒤 어휘 검색과 의미 검색을 결합한다.
- 문서 작업 에이전트: 생성 모델이 도구를 선택해 양식에 맞춰 초안을 작성하고, 원본 한글 서식을 보존한 완성본을 생성한다.
- 영역 단위 공동 편집: 여러 사람과 에이전트가 웹 한글 기안기에서 한 문서를 편집 영역(필드, field)[^c1-field] 단위로 나누어 동시에 편집한다.

[^c1-kg]: 지식 그래프는 사업·연차·문서 같은 대상을 노드로, 그 사이의 관계를 간선으로 저장한 데이터다. 노드와 관계의 종류와 제약을 정한 설계도를 온톨로지(ontology)라 한다(2.5절).

[^c1-field]: 편집 영역은 한글 문서 안에서 이름으로 찾아 읽고 쓸 수 있는 입력 영역(한글의 누름틀)이다. AURA는 모든 문단을 편집 영역으로 감싸 편집 단위로 사용한다(2.8.2절).

생성 모델은 Qwen3.8-27B(이하 Writer 27B)[^c1-writer] 하나다. AURA는 교내 장비 네 대 위에 이 생성 모델과 검색 모델 둘, 지식 그래프, 문서 작업 에이전트,
웹 한글 공동 편집을 구성한 시스템이며, 영역별로 채택한 구성과 구현 방법은 [표 1-1]과 같다.

[^c1-writer]: Writer 27B는 문서 작성과 판단을 담당하는 생성 모델의 서빙 이름이다. 코드는 모델을 이름 대신 용도로 호출하므로, 다른 모델로 바꾸어도 이름 체계는 유지된다.

| 구분 | 채택한 구성 | 구현 방법 |
|---|---|---|
| 생성 모델과 서빙 | Qwen3.8-27B(dense, 멀티모달) 하나, vLLM, NVFP4, MTP 추측 디코딩 | 젯슨 토르 두 대에 같은 모델 탑재, 대화형 작업과 배치 작업을 장비별로 분담. 모델을 이름 대신 용도로 호출하여 연결 설정만 바꾸면 교체 가능 |
| 문서 데이터화 | PDF 텍스트 레이어 추출, MinerU·27B 판독(OCR), 자체 HWPX 파서·kordoc, Presidio | 형식별 최적 읽기 경로 선택, 표 병합 셀 보존. 개인정보 마스킹 뒤 절 경계를 넘지 않는 청크 분할, 서류 종류·사업은 27B 판정 |
| 근거 검색 | Kiwi 어휘 검색, Embed v2(KURE-v1 기반 학습 모델) 임베딩, RRF, Rerank v1(bge-reranker-v2-m3 기반 학습 모델), pgvector | 어휘 검색과 의미 검색의 순위 융합, 규정은 리랭커로 재정렬. 열람 권한은 검색 SQL 조건으로 적용 |
| 지식 그래프 | 사업 > 연차 > 문서 > 절 온톨로지, OWL·SHACL 검사 | 관계별 근거를 기록해 PostgreSQL 테이블에 저장. 질문의 온톨로지 용어 해석은 27B, 그래프 탐색은 코드 담당 |
| 답변과 검증 | 제공한 근거만 인용, 수치 검증기·배점 반영 점검·예산 검산 | 출처는 모델에 제공한 근거 목록에서만 생성, 근거에 없는 수치는 코드 대조로 표시 |
| 문서 작업 에이전트 | 도구 사용 에이전트(구조화 출력), 절 단위 위임, 서식 보존 채우기 | 단계별 도구 선택은 27B(JSON), 실행 전 검사는 코드 담당. 원본 한글 서식은 바뀐 XML만 끼워 넣어 보존 |
| 공동 편집 | 한컴 웹 한글 기안기, 영역 단위 편집권, SSE | 모든 문단을 편집 영역으로 감싸 영역별 편집권 부여, 바뀐 부분만 송수신. 에이전트도 같은 경로로 작성 |
| 도메인 특화 학습 | 검색 모델 대조·목록 학습, Writer LoRA SFT | 학습한 검색 모델은 운영에 사용. 생성 모델은 더 큰 모델에 적용할 SFT 절차와 데이터를 27B로 검증 |
| 설치와 운영 | 설치·운영 패키지, 웹 초기 설정 | 앱 서버와 모델 서버를 스크립트 한 번으로 설치, 연결·원본 폴더·사용자는 관리 화면에서 설정 |

[표 1-1] AURA의 핵심 내용

각 영역은 수집(ingestion)[^c1-ingest]에서 검색, 답변 생성, 문서 작성, 공동 편집으로 이어지는 하나의 처리 흐름을 이루며, 모두 같은 생성 모델과 같은
검색 기반을 공유한다. 설계는 두 가지 원칙을 따른다.

[^c1-ingest]: 수집은 원본 파일을 읽어 텍스트·표로 바꾸고 개인정보 처리, 청크 분할, 서류 종류·사업 판정, 색인까지 마치는 과정 전체를 말한다.

하나는 판단은 모델이 하고 실행은 코드가 하도록 역할을 나누는 것이다. 질문 해석, 서류 종류와 사업 판정, 도구와 양식 선택처럼 문장의 뜻을 알아야
하는 판단은 27B가 담당한다. 키워드 규칙은 표현이 조금만 달라져도 오작동하므로 이러한 판단에는 쓰지 않았다. 코드는 모델의 판단을 실행하면서
권한, 수치 근거, 되돌리기 어려운 작업을 검사하고 기록한다. 다른 하나는 지식은 검색으로 공급하고 학습은 능력을 기르는 데에만 사용하는 것이다.
해마다 바뀌는 사업의 사실과 수치는 검색과 지식 그래프로 공급하고, 학습은 검색 모델이 교내 용어에 적응하는 일과 생성 모델이 근거를 모아 답을
구성하는 능력에만 적용한다.

이 구성이 사용자에게 드러나는 모습은 [그림 1-1]과 같다. 담당자는 왼쪽 대화 창에서 요청하고, 에이전트가 근거를 찾아 오른쪽 한글 작업 문서에 직접 작성한다.

## 1.3 기대 효과

AURA를 사용하면 근거 문서를 빠르게 찾을 수 있고, 근거 없는 숫자가 문서에 들어갈 위험이 줄어들며, 문서를 학교 밖으로 보내지 않고도 언어모델을
활용할 수 있다. 아래 수치는 모두 3~5장의 측정 결과에서 가져왔다.

업무 효율 면에서, 담당자는 폴더를 일일이 찾지 않고 질문만으로 근거 문서와 해당 대목을 찾는다. GraphRAG 비교 실험(절 질문 73문항)에서 정답 문서가
상위 5건 안에 든 비율은 단순 전문 검색의 18%에서 그래프 범위 제한과 27B의 질문 해석을 더한 구성의 70%로 올랐다. 모델 교체 기준 v2 실험(답변 30문항)에서
답변 하나의 생성 시간 중앙값은 16.6초였다. 계획서도 공고와 지난 자료를 근거로 절 단위 초안을 작성할 수 있으므로, 공고 분석부터 초안 작성까지의 시간도
줄어들 것으로 기대한다.

신뢰성 면에서, 모든 답변에는 출처가 표시된다. 4.5절 [표 4-8]의 답변 개선 실험에서 근거에 없는 수치가 포함된 답변은 10건 가운데 2건에서 0건으로 줄었다.
수치 대조와 예산 검산을 코드가 수행하므로 계획서에 잘못된 값을 적을 위험도 줄어든다.

보안 면에서, 생성·임베딩·리랭커 모델이 모두 교내 장비에서 동작하므로 상용 클라우드 AI로 문서를 보내는 경로가 없다. 코드에서 외부로 나갈 수 있는
경로 31개는 목록으로 관리하며, 이 경로로 나가는 내용은 전송 전에 개인정보 포함 여부를 검사한다. 자세한 내용은 3.1.2절에서 설명한다.

모델 개선 면에서, 교내 문서에 맞춘 학습의 효과를 같은 평가 데이터셋으로 확인하였다. 학습한 리랭커(Rerank v1)는 학습에 사용하지 않은 12개 문서에서 R@1(정답이 1위 후보에 오른 질의의 비율)을
0.649에서 0.711로 올려 운영에 채택했다. 생성 모델은 더 큰 모델에 적용하기 위한 실험으로 Writer 27B에서 학습 절차와 데이터를 검증했다.
교내 실제 문서로 구성한 학습 데이터 4,434쌍으로 SFT를 수행한 결과 평가 문항의 chrF(정답 답안과의 글자 단위 겹침 점수)가 27.9에서 36.6으로 올랐다. 다만 학습 데이터가 한 가지 형식뿐이어서 에이전트 단계의
JSON 요청에도 학습한 형식으로 답하는 문제가 드러났으므로, 더 큰 모델에서는 플랫폼의 요청 형식까지 학습 데이터에 포함하고 같은 비교 도구로 측정한다.

## 1.4 시스템 구성

AURA는 교내 장비 네 대로 구성된다. 운영 서버(학과 가상 서버, GPU 없음)가 웹 서비스, 데이터베이스, 검색, 지식 그래프, 문서 수집을 담당하고,
서빙 장비 두 대(NVIDIA Jetson AGX Thor)가 생성 모델과 검색 모델을 서빙하며, 학습 장비(NVIDIA DGX)가 학교 원본 보관과 대량 처리, 모델 학습을 담당한다.
학교 원본은 부서 원본 보관 PC(사업별 폴더)에서 학습 장비로 복사해 두고, 운영 서버에는 처리 결과(텍스트·청크·임베딩·그래프)만 두어 원본이 이동하는
범위를 최소화하였다. 교직원은 브라우저로 운영 서버에 접속해 업무 화면과 웹 한글 기안기를 사용한다. 구글 드라이브와 구글 문서는 계정을 연결한
사용자만 사용하는 보조 경로다. 장비와 연결 관계는 [그림 1-2]와 같다.

[그림 1-2] 전체 프로젝트 구조 (그림 docs/images/diagrams/01-system.png)

학교 원본 파일의 목록은 원본 대장에 동기화된다. 문서는 형식에 맞는 방법으로 읽은 뒤 표를 정리하고 개인정보를 처리하여 청크로 나눈다. 문서마다
서류 종류와 사업을 판정해 버전 그룹으로 정리한 뒤, 청크를 어휘·벡터 색인과 지식 그래프에 저장한다. 질문이 들어오면 생성 모델이 질문을 해석하고, 그래프로 검색 범위를 정한 뒤
하이브리드 검색으로 근거를 모아 답을 생성한다. 답에 포함된 숫자는 근거와 대조한 뒤 출처와 함께 화면에 표시한다. 문서 작성에서는 같은 검색 기반 위에서 에이전트가 양식을
선택하고 절마다 작성하며, 마지막에 원본 한글 서식에 내용을 채운다. 자세한 구조는 3장에서 설명한다. 화면별 사용 방법은 부록의 사용 설명서에 정리하였다.
