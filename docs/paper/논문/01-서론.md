# 1. 서론

## 1.1 프로젝트 배경 및 목적

### 1.1.1 대학 행정 문서 업무의 현황

대학 행정은 문서로 움직인다. 국고 재정지원사업의 공고문·사업계획서·실적보고서·평가 자료, 교내 규정과 지침, 공문과 각종 서식이 그 대상이다.
영남이공대학교 행정 부서도 국고사업 공고 분석과 계획서 작성, 채용·입학 서류 검토, 규정 확인처럼 문서를 읽고 정리하는 반복 업무를 수행한다.

이 업무는 세 가지 이유로 어렵다. 첫째, 문서의 양이 많고 흩어져 있다. 한 사업만 해도 연차마다 계획서와 실적보고서가 수십 건씩 쌓이고,
담당자는 새 계획서를 쓸 때 지난 자료를 파일 서버의 폴더에서 일일이 찾아 읽어야 한다. 본 프로젝트에서 교내 원본 문서를 장부로 정리한 결과
원본 파일은 167,146건(중복 제외 130,046건)이었다. 둘째, 같은 사업이 단계마다 이름을 바꾸고(LINC+ → LINC 3.0 → RISE 등) 같은 서식이 해마다
조금씩 다른 판본으로 들어오기 때문에, 이름이나 파일명만으로는 필요한 문서를 찾기 어렵다. 셋째, 문서의 형태가 제각각이다. 디지털 PDF,
스캔본, 사진, 한글(HWP·HWPX), 오피스 문서가 섞여 있어 읽어 들이는 단계에서부터 정확도가 떨어진다.

계획서에는 기관의 실제 실적 수치가 들어간다. 근거가 없는 수치가 들어가면 허위 기재가 되어 사업 평가에 불이익이 생길 수 있다. 따라서
문서 작성을 돕는 도구는 글을 빨리 쓰는 것보다 근거를 정확히 짚는 것이 더 중요하다.

### 1.1.2 상용 AI 서비스를 쓸 수 없는 이유

최근 대규모 언어모델(LLM)과 검색 증강 생성(Retrieval-Augmented Generation, RAG)[1] 기술은 문서를 읽고 요약하며 근거를 찾아 답하는 일을
상당한 수준으로 해낸다. 그러나 행정 문서에는 개인정보와 기관 내부 정보가 들어 있다. 이 문서를 외부 클라우드 AI 서비스에 올리는 것은
개인정보 보호 법령[60]과 기관 보안 원칙에 맞지 않는다. 그 결과 문서 업무의 자동화가 사실상 이루어지지 못하고 있다.

이 제약을 풀려면 모델과 데이터가 모두 교내에 있어야 한다. 공개된 가중치를 내려받아 쓸 수 있는 오픈웨이트 모델을 교내 장비에서 서빙하면
문서를 외부로 내보내지 않고도 같은 일을 할 수 있다. 본 프로젝트는 이 온프레미스(on-premise) 구성을 전제로 한다.

### 1.1.3 프로젝트 목적

본 프로젝트의 목적은 교내 장비만으로 동작하는 행정 문서 처리 플랫폼 AURA 를 설계하고 구현하는 것이다. AURA 는 다음 네 가지를 한다.

- 학교 원본 문서를 형식에 상관없이 읽어 검색할 수 있는 조각으로 바꾸고, 사업·연차·서류 종류로 정리한다.
- 질문을 받으면 질문한 사람의 열람 권한 안에서 근거 문서를 찾아 출처와 함께 답한다. 근거에 없는 숫자는 따로 표시한다.
- 담당자의 요청에 따라 양식에 맞춰 문서 초안을 쓰고, 원본 한글 서식을 그대로 살린 완성본을 낸다.
- 질문 해석, 서류 종류와 사업 판정, 작업 도구 선택 같은 판단은 오픈웨이트 모델이 하고, 프로그램 코드는 실행·검증·기록을 맡는다.

AURA 의 산출물은 사람이 검수하는 초안이다. 시스템은 제출용 완성본을 대신 만드는 것이 아니라 근거를 갖춘 초안과 검토 의견을 내고,
최종 판단은 담당자가 내린다. 이 전제는 설계 전반에 걸쳐 유지된다. 예를 들어 초안 속 수치가 근거 자료에 실제로 있는지, 예산 계산이 맞는지는
언어모델이 아니라 결정론적 검증기가 확인한다.

## 1.2 핵심내용

본 프로젝트는 두 개의 축으로 진행했다. 축 A 는 문서 반입부터 초안 작성까지의 전 경로를 실제 행정에 쓸 수 있는 수준으로 만드는 실용 시스템이고,
축 B 는 오픈웨이트 모델을 교내 문서 도메인에 맞게 개선하고 그 개선 폭을 수치로 확인하는 도메인 특화 모델 개발이다. 두 축은 다음 다섯 가지 핵심
내용으로 구체화된다.

| 구분 | 내용 | 주요 기술 |
|---|---|---|
| 문서 데이터화 | 디지털 PDF·스캔본·사진·한글·오피스 문서를 표 구조까지 보존해 읽고, 개인정보를 탐지하며, 절 단위 조각으로 나눈다 | MinerU, PDF 글자층 직독, kordoc·자체 HWPX 파서, Presidio |
| 근거 검색 | 어휘 검색과 의미 검색을 섞고, 리랭커로 다시 정렬하며, 지식 그래프로 검색 범위를 먼저 좁힌다 | Kiwi, Embed v2(KURE-v1 학습본), RRF, Rerank v1(bge-reranker-v2-m3 학습본), pgvector, 온톨로지(OWL·SHACL) |
| 근거 기반 답과 검증 | 모델에 건넨 근거로만 출처를 만들고, 근거에 없는 숫자를 기계적으로 대조해 표시한다 | Qwen3.8-27B, 수치 검증기·배점 반영 점검·예산 검산 |
| 문서 작업 에이전트와 공동 편집 | 에이전트가 양식을 고르고 절마다 근거를 찾아 쓰며, 사람과 AURA 가 웹 한글 기안기에서 같은 문서를 칸 단위로 함께 고친다 | 도구 사용 에이전트, 한컴 웹 한글 기안기, SSE, 구글 독스·드라이브 API |
| 도메인 특화 모델 | 검색 모델 둘(임베딩·리랭커)을 교내 문서로 학습해 운영에 쓰고, 생성 모델의 SFT 학습본을 오픈 모델과 같은 시험으로 비교한다 | 대조 학습, LoRA SFT, vLLM, NVFP4 양자화 |

[표 1-1] AURA 의 핵심 내용

첫째, 문서 데이터화는 형식마다 가장 정확한 읽기 경로를 고른다. 글자층이 멀쩡한 디지털 PDF 는 원본 글자를 좌표째 읽고, 스캔본은 OCR 로 읽으며,
한글 문서는 전용 파서로 읽는다. 행정 문서의 핵심 값(예산·성과지표·일정)은 대부분 표에 있으므로 병합 셀을 포함한 표 구조를 보존한다.
10월 18일 운영 기준으로 라이브러리 문서 35,469건, 문서 조각 1,848,580개, 규정 조각 9,595개가 이 과정을 거쳐 검색 대상이 되었다.

둘째, 근거 검색은 「무엇을 찾을지」를 먼저 정한다. 행정 질문에는 사업 약칭·규정 이름·숫자처럼 글자 그대로 맞아야 하는 말과, 뜻으로 찾아야 하는 말이
섞여 있다. 그래서 어휘 검색과 의미 검색을 순위 융합(RRF)으로 섞는다. 또한 문서가 수만 건일 때 조각 유사도만으로는 「LINC 3.0 2차년도 실적보고서의
취업 성과」 같은 질문을 풀기 어렵다. 이를 위해 사업 > 연차 > 문서 > 절의 구조와 계획↔실적, 앞·뒤 단계 같은 관계를 온톨로지로 정하고 지식 그래프를
만들었다. 질문은 생성 모델이 온톨로지의 말(사업·연도·차수·서류 종류·관계)로 읽고, 그래프 탐색은 코드가 결정적으로 수행한다.

셋째, 근거 기반 답은 지어낸 숫자를 막는 데 초점을 둔다. 답의 출처는 모델에 실제로 건넨 근거 목록에서만 만들고, 답에 든 숫자 가운데 근거에 없는 것은
「(근거 확인 필요)」로 표시한다.

넷째, 문서 작업 에이전트는 담당자의 요청(「작년 실적보고서 참고해서 추진 배경 절 써 줘」, 「한글 파일로 내보내 줘」)을 받아 필요한 도구를 스스로 골라
실행한다. 되돌리기 어려운 작업은 담당자의 요청에 그 뜻이 있을 때만 실행되도록 코드가 관문을 둔다. 작성한 문서는 웹 한글 기안기에서 열리며,
여러 사람과 AURA 가 서로 다른 칸을 동시에 고칠 수 있다.

다섯째, 도메인 특화 모델은 「지식은 검색으로, 능력은 학습으로」라는 원칙을 따른다. 사업의 사실과 수치는 해마다 바뀌므로 모델에 외우게 하지 않고
검색과 지식 그래프로 공급한다. 학습은 검색 모델의 교내 용어 적응과, 생성 모델이 근거를 모아 형식에 맞게 구성하는 능력에만 쓴다.

## 1.3 기대효과

본 프로젝트의 기대효과는 업무 효율, 신뢰성, 보안, 학술의 네 측면으로 정리된다.

업무 효율 측면에서, 담당자는 폴더를 뒤지는 대신 질문 한 번으로 근거 문서와 해당 대목을 찾을 수 있다. 같은 시험지에서 질문의 절에 해당하는 정답 문서가
상위 5건 안에 든 비율은 단순 전문 검색 18%에서 그래프 범위와 모델의 질문 해석을 더한 방식 70%로 올랐다. 답 하나에 걸리는 시간은 처음 기준 134초에서
중앙값 16.6초로 줄었다. 계획서 작성에서는 공고와 지난 자료를 근거로 절 단위 초안이 나오므로, 공고 분석부터 초안까지 걸리는 시간이 단축될 것으로 기대된다.

신뢰성 측면에서, 모든 답에 출처가 붙고 근거에 없는 숫자는 기계적으로 표시된다. 근거 밖 숫자가 표시 없이 들어간 답은 측정 표본에서 2/10 에서 0/10 으로
줄었다. 수치·예산 검증이 자동화되므로 계획서의 오기재 위험이 줄어들 것으로 기대된다.

보안 측면에서, 생성·임베딩·리랭커 모델이 모두 교내 장비에서 동작하고 상용 클라우드 AI 로 가는 경로가 없다. 외부로 나갈 수 있는 경로는 목록으로 관리하고
관문을 둔다. 문서를 외부로 내보내지 않는 행정 AI 의 교내 실사용 선례가 될 수 있다.

학술 측면에서, 오픈웨이트 모델을 교내 문서 도메인에 맞춘 개선 폭을 같은 시험으로 측정한 기록을 남긴다. 검색 리랭커 학습본은 문서 단위 홀드아웃에서
R@1 을 0.649 에서 0.711 로 올려 운영에 채택했다. 생성 모델의 SFT 학습본은 학습 형식 안의 지표는 좋아졌으나 플랫폼의 문서 작업 에이전트가 동작하지
않아 채택하지 않는 쪽으로 판단했는데, 이러한 부정 결과도 평가 절차와 함께 기록했다. 5장에서 이 수치들을 다시 다룬다.

## 1.4 프로젝트 구성

### 1.4.1 전체 프로젝트 구조

AURA 는 네 종류의 교내 장비로 구성된다. 운영 서버(학과 가상 서버, GPU 없음)가 웹 서비스·데이터베이스·검색·지식 그래프·문서 반입 처리를 맡고,
서빙 장비 두 대(NVIDIA Jetson AGX Thor)가 생성 모델과 검색 모델을 서빙하며, 학습 장비(NVIDIA DGX)가 학교 원본 보관과 대량 처리, 모델 학습을 맡는다.
학교 원본은 학습 장비에 두고 운영 서버에는 처리본(글·조각·임베딩·그래프)만 둔다.

[그림 1-2] 전체 프로젝트 구조 — 장비 네 종과 데이터 흐름 (캡처 있음: docs/images/diagrams/01-system.png)

데이터는 다음 순서로 흐른다. 학교 원본은 원본 장부로 동기화되고, 형식별 읽기·표 정리·개인정보 처리를 거쳐 조각으로 나뉜다. 조각은 서류 종류와
사업이 판정되고 판본으로 묶인 뒤 어휘·벡터 색인과 지식 그래프에 들어간다. 질문이 들어오면 생성 모델이 질문을 읽고, 그래프로 범위를 정한 뒤
하이브리드 검색으로 근거를 모아 답을 만든다. 답의 숫자는 근거와 대조되어 출처와 함께 화면에 나온다. 문서 작성은 같은 검색 위에서 에이전트가 양식을
고르고 절마다 쓰며, 끝에 원본 한글 서식으로 채운다. 3장에서 이 구조를 자세히 설명한다.

| 팀원 2 | 문서 데이터화, RAG, 학습 데이터 구축과 파인튜닝 |
| 팀원 3 | 교내 문서·규정 수집 |

[표 1-2] 팀 구성과 역할

플랫폼 쪽(웹 서비스, 검색, 지식 그래프, 에이전트, 문서 편집, 서빙 연결)과 데이터·학습 쪽(학습 데이터 생성·검수, 생성 모델 SFT)은 장비 경계에 맞춰 나뉜다.
데이터·학습 쪽은 학습 장비에서 학습셋을 만들고 승인하며, 운영 서버에는 학습셋의 이름·상태·건수 같은 목록 정보만 들어온다.

### 1.4.3 추진 일정

프로젝트는 9월부터 11월까지 13주로 계획했고 12월 초 발표회로 마무리한다. 주차별 계획은 [표 1-3] 과 같다.

| 주차 | 기간 | 내용 |
|---|---|---|
| 1~2주 | 9/1~9/14 | 장비 검증, 파서 비교 선정, 설계 문서 작성, 운영 서버 이전 |
| 3~5주 | 9/15~10/5 | 교내 문서·규정 반입과 파싱, 평가셋 구축, 검색 모델 학습본 채택, 서빙 장비 2대 구성 |
| 6~8주 | 10/6~10/26 | 실문서 반입과 지식 그래프, 생성 모델 베이스라인 측정, 문서 작업 에이전트 |
| 9~10주 | 10/27~11/9 | 생성 파이프라인과 검증기 고도화, 실물 문서 파일럿 |
| 11~12주 | 11/10~11/23 | 모델 추가 학습과 개선 폭 측정 |
| 13주 | 11/24~11/30 | 평가 정리, 논문 작성, 발표 준비 |

[표 1-3] 추진 일정

일정의 원칙은 「베이스라인을 먼저 측정한 뒤에 학습한다」이다. 학습 전 기준을 먼저 재야 개선 폭을 입증할 수 있기 때문이다.

### 1.4.4 논문의 구성

본 논문의 구성은 다음과 같다. 2장에서는 AURA 에 쓰인 기술을 영역별로 소개한다. 3장에서는 장비 환경 구축과 시스템 아키텍처를 설명한다. 4장에서는 문서 처리,
검색과 지식 그래프, 답 생성과 검증, 문서 작업 에이전트, 한글 문서 작성과 공동 편집, 학습 데이터 구축을 기능별로 다룬다. 5장에서는 측정 결과와 시연 화면을
제시한다. 6장에서는 연구를 요약하고 한계와 향후 과제를 정리한다.
