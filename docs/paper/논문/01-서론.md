# 1. 서론

## 1.1 프로젝트 배경 및 목적

### 1.1.1 대학 행정 문서 업무의 현황

대학 행정 업무의 상당 부분은 국고 재정지원사업의 공고문·사업계획서·실적보고서·평가 자료, 교내 규정, 공문과 서식을 다루는 일이다.
영남이공대학교 행정 부서도 공고 분석과 계획서 작성, 채용·입학 서류 검토, 규정 확인을 되풀이한다.

이 업무가 어려운 이유는 세 가지다. 첫째, 문서가 많고 흩어져 있다. 담당자는 새 계획서를 쓸 때 지난 자료를 파일 서버 폴더에서 일일이 찾아 읽는다.
본 프로젝트에서 수집한 교내 문서만 약 3만 5천 건이며, 대부분이 86개 국고사업에 속한다.
둘째, 같은 사업이 단계마다 이름을 바꾸고(LINC+ → LINC 3.0 → RISE 등) 같은 서식도 해마다 조금씩 다른 판본으로 들어오므로,
사업 이름이나 파일명만으로는 원하는 문서를 찾기 어렵다. 셋째, 문서 형식이 제각각이다. 디지털 PDF, 스캔본, 사진, 한글(HWP·HWPX), 오피스 문서가 섞여 있어
문서를 읽어 들이는 단계부터 정확도가 떨어진다.

계획서에는 기관의 실제 실적 수치가 들어간다. 근거 없는 수치는 허위 기재가 되어 사업 평가에서 불이익으로 이어질 수 있다.
따라서 문서 작성 도구는 속도보다 근거의 정확성을 우선해야 한다.

### 1.1.2 상용 AI 서비스를 쓸 수 없는 이유

대규모 언어모델(LLM)과 검색 증강 생성(Retrieval-Augmented Generation, RAG)[1]은 문서를 요약하고 근거를 찾아 답하는 데 실용적인 수준에 이르렀다.
그러나 행정 문서에는 개인정보와 기관 내부 정보가 들어 있어, 외부 클라우드 AI 서비스에 올리면 개인정보 보호 법령[60]과 기관 보안 원칙에 어긋난다.
이 때문에 행정 문서 업무는 여전히 대부분 사람이 직접 처리한다.

가중치가 공개된 오픈웨이트 모델을 교내 장비에서 서빙하면 문서를 외부로 내보내지 않고도 같은 일을 할 수 있다.
본 프로젝트는 이러한 온프레미스(on-premise) 구성을 전제로 한다.

### 1.1.3 프로젝트 목적

본 프로젝트의 목적은 교내 장비만으로 동작하는 행정 문서 처리 플랫폼 AURA를 설계하고 구현하는 것이다. AURA의 기능은 네 가지다.
첫째, 학교 원본 문서를 형식에 관계없이 읽어 검색용 조각으로 바꾸고 사업·연차·서류 종류별로 정리한다.
둘째, 질문한 사람의 열람 권한 안에서 근거 문서를 찾아 출처와 함께 답하고, 근거에 없는 숫자는 따로 표시한다.
셋째, 담당자의 요청에 따라 양식에 맞춰 초안을 쓰고, 원본 한글 서식을 그대로 유지한 완성본을 만든다.
넷째, 여러 담당자가 하나의 한글 문서를 브라우저에서 동시에 편집하고, 에이전트도 같은 문서에 함께 작성한다.

AURA의 산출물은 사람이 검수하는 초안이다. 시스템은 근거를 갖춘 초안과 검토 의견을 제시하고, 제출 여부는 담당자가 결정한다.
초안 속 수치가 근거 자료에 있는지, 예산 계산이 맞는지는 언어모델이 아니라 코드로 구현한 검증기가 확인한다.

## 1.2 핵심내용

본 프로젝트의 핵심 기술은 네 가지다. 첫째, 형식이 제각각인 교내 문서를 표 구조와 개인정보 처리를 유지하며 검색 가능한 조각으로 바꾸는 문서 데이터화 경로다.
둘째, 사업·연차·문서·절을 잇는 온톨로지 지식 그래프로 검색 범위를 좁힌 뒤 어휘 검색과 의미 검색을 결합하는 GraphRAG다. 셋째, 27B 모델이 도구를 골라
양식에 맞춰 초안을 쓰고 원본 한글 서식을 보존해 완성본을 만드는 문서 작업 에이전트다. 넷째, 여러 사람과 에이전트가 웹 한글 기안기에서 한 문서를 칸 단위로
동시에 편집하는 공동 편집이다. 이 기술들을 상용 클라우드 없이 교내 장비만으로 하나의 서비스로 묶고, 각 단계의 효과를 같은 시험지로 측정한 것이 본 프로젝트의 기여다.

AURA는 교내 장비 네 대 위에 생성 모델 하나, 검색 모델 둘, 지식 그래프, 문서 작업 에이전트, 웹 한글 공동 편집을 구성한 시스템이다.
영역별로 채택한 구성과 구현 방법은 [표 1-1]과 같다.

| 구분 | 채택한 구성 | 구현 방법 |
|---|---|---|
| 생성 모델과 서빙 | Qwen3.8-27B(dense, 멀티모달) 하나, vLLM, NVFP4, MTP 추측 디코딩 | 젯슨 토르 두 대에 같은 모델을 올리고 대화형 작업과 배치 작업을 장비별로 나눈다. 모델은 이름이 아닌 용도로 호출하므로 연결 설정만 바꾸면 교체할 수 있다. |

[표 1-1] AURA의 핵심 내용

이 표의 각 영역은 반입에서 검색, 답 생성, 문서 작성, 공동 편집으로 이어지는 하나의 처리 흐름을 이루며, 모든 영역이 같은 생성 모델과 같은 검색 기반을 공유한다.
설계 원칙은 두 가지다. 첫째는 「판단은 모델, 실행은 코드」다. 질문 해석, 서류 종류와 사업 판정, 도구와 양식 선택처럼 문장의 의미를 이해해야
하는 판단은 27B가 맡는다. 코드는 그 판단을 실행하면서 권한, 수치 근거, 되돌리기 어려운 작업을 검사하고 기록한다. 키워드 규칙은 표현이 조금만
달라져도 오작동하기 때문이다. 둘째는 「지식은 검색으로, 능력은 학습으로」다. 해마다 바뀌는 사업의 사실과 수치는 검색과 지식 그래프로 공급하고,
학습은 검색 모델의 교내 용어 적응과 생성 모델의 근거 구성 능력에만 사용한다. 이러한 구성이 사용자에게 드러나는 모습은 [그림 1-1]과 같다.
담당자는 왼쪽 대화 창에서 요청하고, 에이전트가 근거를 찾아 오른쪽 한글 작업본에 직접 작성한다.

## 1.3 기대효과

기대효과는 업무 효율, 신뢰성, 보안, 모델 개선의 네 측면으로 나누어 볼 수 있다.

첫째, 업무 효율이 높아진다. 담당자는 폴더를 뒤지지 않고 질문만으로 근거 문서와 해당 대목을 찾는다. 같은 시험지에서 절 질문의 정답 문서가
상위 5건 안에 든 비율은 단순 전문 검색의 18%에서 그래프 범위 제한과 모델의 질문 해석을 더한 방식의 70%로 올랐다. 답 하나에 걸리는 시간은
중앙값 134초에서 16.6초로 줄었다. 계획서는 공고와 지난 자료를 근거로 절 단위 초안이 만들어지므로 공고 분석부터 초안 작성까지의 시간도 줄어들 것으로 기대한다.

둘째, 신뢰성이 높아진다. 모든 답에는 출처가 붙는다. 근거 밖 숫자가 표시 없이 들어간 답은 측정 표본에서 2/10에서 0/10으로 줄었다.
수치 대조와 예산 검산을 코드가 수행하므로 계획서에 잘못된 값을 적을 위험도 줄어든다.

셋째, 보안이 유지된다. 생성·임베딩·리랭커 모델이 모두 교내 장비에서 동작하며 상용 클라우드 AI로 가는 경로가 없다. 외부로 나갈 수 있는 경로 31개는
목록으로 관리하고 각 경로에서 전송 전 검사를 거친다.

넷째, 교내 문서에 맞춘 모델 개선 폭을 같은 시험으로 확인했다. 검색 리랭커 학습본은 문서 단위 홀드아웃 12건에서
R@1을 0.649에서 0.711로 올려 운영에 채택했다. 생성 모델은 더 큰 모델에 적용하기 위한 실험으로 Writer 27B에서 학습 절차와 데이터를 검증했다.
교내 실문서 학습쌍 4,434쌍으로 SFT를 수행하자 시험 문항의 chrF가 27.9에서 36.6으로 올랐다. 다만 학습쌍이 한 가지 형식뿐이어서 에이전트 단계의 JSON
요청에도 학습한 형식으로 답하는 문제가 드러났다. 더 큰 모델에서는 플랫폼의 요청 형식까지 학습 데이터에 넣고 같은 비교 도구로 측정한다. 이 수치는 5장에서 다시 다룬다.

## 1.4 프로젝트 구성

### 1.4.1 전체 프로젝트 구조

AURA는 교내 장비 네 대로 구성된다. 운영 서버(학과 가상 서버, GPU 없음)가 웹 서비스·데이터베이스·검색·지식 그래프·문서 반입을 맡고,
서빙 장비 두 대(NVIDIA Jetson AGX Thor)가 생성 모델과 검색 모델을 서빙하며, 학습 장비(NVIDIA DGX)가 학교 원본 보관과 대량 처리, 모델 학습을 맡는다.
학교 원본은 부서 원본 보관 PC(사업별 폴더)에서 학습 장비로 복사해 두고, 운영 서버에는 처리 결과(텍스트·조각·임베딩·그래프)만 둔다.
교직원은 브라우저로 운영 서버에 접속해 업무 화면과 웹 한글 기안기를 사용한다. 구글 드라이브와 구글 문서는 계정을 연결한 사용자만 쓰는 보조 경로다.
장비와 연결 관계는 [그림 1-2]와 같으며, 원본 문서는 학습 장비에 두고 운영 서버에는 처리 결과만 두어 원본의 이동 범위를 최소화하였다.

[그림 1-2] 전체 프로젝트 구조: 교내 장비와 연결 (그림 docs/images/diagrams/01-system.png)

학교 원본은 원본 장부로 동기화되고, 형식별 읽기·표 정리·개인정보 처리를 거쳐 조각으로 나뉜다. 각 조각은 서류 종류와
사업을 판정받고 판본별로 묶인 뒤 어휘·벡터 색인과 지식 그래프에 저장된다. 질문이 들어오면 생성 모델이 질문을 해석하고, 그래프로 검색 범위를 정한 뒤
하이브리드 검색으로 근거를 모아 답을 생성한다. 답의 숫자는 근거와 대조된 뒤 출처와 함께 화면에 표시된다. 문서 작성에서는 같은 검색 기반 위에서 에이전트가 양식을
고르고 절마다 작성하며, 마지막에 원본 한글 서식에 내용을 채운다. 자세한 구조는 3장에서 설명한다.

### 1.4.2 팀 구성과 역할

팀 이름은 AURA이고 4명으로 구성된다. 역할 분담은 [표 1-2]와 같다.

| 구성원 | 역할 |
|---|---|
| 서원준(팀장) | 프로젝트 총괄, 플랫폼 개발, 모델 서빙, 문서 작업 에이전트 |
| 형예진 | 문서 데이터화, RAG, 학습 데이터 구축과 파인튜닝 |
| 은수인 | 교내 문서·규정 수집 |
| 짜투바카테베 | 교내 문서·규정 수집 |

[표 1-2] 팀 구성과 역할

업무는 장비 경계에 맞춰 플랫폼(웹 서비스, 검색, 지식 그래프, 에이전트, 문서 편집, 서빙 연결)과 데이터·학습(학습 데이터 생성·검수, 생성 모델 SFT)으로 나누었다.
학습셋은 학습 장비에서 만들고 승인하며, 운영 서버에는 학습셋의 이름·상태·건수 같은 목록 정보만 전달된다.

### 1.4.3 추진 일정

프로젝트는 9월부터 11월까지 13주로 계획했고 12월 초 발표회로 마무리한다. 주차별 계획은 [표 1-3]과 같다.

| 주차 | 기간 | 내용 |
|---|---|---|
| 1~2주 | 9/1~9/14 | 장비 검증, 파서 비교 선정, 설계 문서 작성, 운영 서버 이전 |
| 3~5주 | 9/15~10/5 | 교내 문서·규정 반입과 파싱, 평가셋 구축, 검색 모델 학습본 채택, 서빙 장비 2대 구성 |

[표 1-3] 추진 일정

일정은 베이스라인을 먼저 측정한 뒤 학습한다는 원칙을 따랐다. 학습 전 기준이 있어야 개선 폭을 입증할 수 있기 때문이다.

### 1.4.4 논문의 구성

본 논문의 구성은 다음과 같다. 2장은 AURA에 쓰인 기술을 영역별로 소개하고, 3장은 장비 환경 구축과 시스템 아키텍처를 설명한다. 4장은 문서 처리,
검색과 지식 그래프, 답 생성과 검증, 문서 작업 에이전트, 한글 문서 작성과 공동 편집, 학습 데이터 구축을 기능별로 다룬다. 5장은 측정 결과와 시연 화면을
제시하고, 6장은 연구를 요약하며 한계와 향후 과제를 정리한다.
