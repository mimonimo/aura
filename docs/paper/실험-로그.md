정리 2026-09-15: 출처 없는 수치를 미확인 처리했다(09-02 Embed 1차 리허설의 홀드아웃 R@1 .436→.487과 구 코퍼스 602조각, 09-03 검색 재측정의 질의 2,478건·R@1 .583·R@10 .871, 리랭커 GPU 10쌍 0.2초, 실사고 문서 103쪽). 09-04 검색 기준선 정본 행을 추가하고 가중 스윕의 개선폭을 스윕 표 값으로 정정했다. 09-07 이후의 OCR 벤치·PaddleOCR-VL 대결·한글 에이전트·파일럿 코퍼스 인제스트·학습된 연관 판정(ADR-0015)·조각 재분할·리랭커 길이 조정 행을 추가했다. 사고 기록에 VM CPU 포화·오프라인 로더·합성 질의 세트 유실을 더했다.

1차 색인이다. 각 행의 수치 정본은 판정 칸에 적은 리포트(docs/ 아래)이며,

## 실패·사고 기록 (방법론의 재료)

- 학습 SIGKILL 원인 규명 2건: (1) 통합메모리에서 트레이너 CUDA 초기화 OOM
  → CUDA_VISIBLE_DEVICES= 로 CPU 강제, (2) 학습 중 동시 GPU 작업(MinerU·별도
  서빙)이 커널 OOM 킬 유발 → 학습 단독 점유 규칙 확립. 메모리 스파이크는
  MALLOC_ARENA_MAX=2·max_seq 512·batch 8로 완화(dev-changelog 09-02). 스텝
  시간 개선폭은 미확인
- 코퍼스 재구성 시 파생물 연쇄 무효화: 합성 질의 세트(chunk_id 기준)와
  임베딩 npz가 함께 무효 — "재구성 → 51 → 52 → 53" 체인 순서를 규칙화
- 디지털 PDF OCR 오판 실사고: MinerU auto가 디지털 문서를 OCR로 읽어
  "기초과학→기추과하" — 텍스트 레이어 감지 라우팅으로 원천 차단(ADR-0007)
- 운영 VM CPU 포화 실사고(09-08): PaddleOCR-VL 배치에 전체 코어 할당 → 약
  6시간 SSH·웹 응답 지연 — 무거운 작업은 코어 절반·낮은 우선순위·순차 처리
  규칙(HANDOFF §5)
- 오프라인 서버의 모델 로더 함정: 아웃바운드가 막힌 VM에서 허브 갱신 확인에
  멈춤 → 로더에 HF 오프라인 기본값(ADR-0015)
- 합성 질의 세트 유실: Spark → VM 이관 시 세트가 옮겨지지 않아 09-14 재분할
  후 검색 재측정이 막힘 → LLM 연결 후 51 재생성(HANDOFF §4)

## OCR·복원 실험 (축 A 방법론)

- 복원 뷰 3안 비교(실물 렌더 검증): 블록 bbox 재구성(잘림·중복·왜곡 발생)
  → 글자 좌표 직독(pdfium charbox — 원리적 무오차, 단 표 괘선·서식 미표현)
  → 원본 렌더 배경 + 투명 텍스트 레이어(구글 OCR PDF 방식)로 확정.
  디지털=좌표 직독, 스캔=MinerU 줄 좌표(신뢰도≥0.5), 사진=보정 스캔+OCR 줄
  (ADR-0007)
- 표 복원: 디지털 PDF는 괘선 좌표와 글자층을 직접 읽어 병합·열 폭·텍스트를
  원본대로 복원(괘선 직독). 실물 공고문에서 OCR 오인식("직계존속정"보")이
  사라지고 원본과 같은 칸 비율로 복원됨을 확인(weekly/2026-09-08-w2)
- LLM 오타 교정의 게이트·범위 확장: 본문만 → 표 셀 포함, 라벨 기준 →
  실제 OCR 발생 기준. 행정 용어 사전 프롬프트로 맥락 없는 셀 교정률 개선
  ("주민등특번호→주민등록번호", "등의여부→동의여부" 실측 교정)
