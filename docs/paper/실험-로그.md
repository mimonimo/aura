# 실험 로그

축 B(도메인 특화)와 파이프라인 판정 실험의 시계열 기록이다. 논문의 표와 방법론 절이 여기서
출발한다. 수치의 정본은 각 행의 판정 칸에 적은 측정 기록이며, 기록이 없는 값은 확인하지 않은
것으로 남긴다. 실패한 실험도 그대로 둔다. 논문 원재료는 이 로그를 인용하고 수치를 따로 두지
않는다.

## 2. 실패와 사고의 기록

방법론의 재료가 되는 실패들이다.

학습이 두 번 강제 종료됐다. 한 번은 통합 메모리 장비에서 학습 프로그램이 GPU를 초기화하다 메모리가
모자랐고, 한 번은 학습 중에 돌던 다른 GPU 작업이 커널의 메모리 회수를 불렀다. 앞의 문제는 학습을
CPU로 강제해 피했고 뒤의 문제는 학습이 장비를 단독으로 쓰는 규칙으로 막았다. 메모리 스파이크는
할당 영역과 시퀀스 길이, 배치를 줄여 완화했다.

코퍼스를 다시 구성하면 조각 번호에 묶인 합성 질의 세트와 임베딩 파일이 함께 무효가 된다. 재구성
뒤에는 질의 생성, 임베딩, 측정을 이 순서로 다시 돌리는 규칙을 두었다.

디지털 PDF를 OCR로 읽는 오판이 있었다. MinerU가 글자층이 있는 문서를 스캔으로 다뤄 "기초과학"을
"기추과하"로 읽었다. 글자층을 먼저 감지해 경로를 나누는 것으로 원천에서 막았다.

9월 8일에는 운영 서버의 CPU가 포화됐다. OCR 배치에 코어를 전부 할당해 여섯 시간 동안 접속과
웹 응답이 늦어졌다. 무거운 작업은 코어의 절반만 쓰고 우선순위를 낮춰 차례로 돌리는 규칙을 두었다.

외부 인터넷이 막힌 서버에서 모델 적재기가 허브의 갱신을 확인하려다 멈췄다. 적재기의 기본값을
오프라인으로 바꿨다.

합성 질의 세트가 Spark에서 운영 서버로 옮겨지지 않아 9월 14일 재분할 뒤의 재측정이 막혔다. 언어
모델을 연결한 9월 20일에 다시 만들었다.

9월 21일에는 측정이 세 번 무효가 됐다. 서빙 장비 설정을 읽지 않고 띄운 측정이 리랭커와 질의
임베딩을 CPU 베이스 모델로 조용히 물러나게 했고, 운영 구성 행이 실제보다 0.1 낮게 나왔다. 이후
보고서는 어느 리랭커가 답했는지와 폴백 수를 항상 적고, 서빙 장비가 아니면 운영 구성이라 부르지
않는다.

같은 날 젯슨에서 GPU 메모리 함정을 둘 겪었다. 큰 파일을 받은 뒤 페이지 캐시가 GPU 메모리를 막아
vLLM이 죽었고, 컨테이너를 강제로 끝내자 GPU 메모리 88GB가 돌아오지 않아 재부팅이 필요했다. 서빙
교체는 정상 종료를 기다리도록 바꿨다.

## 3. OCR과 복원 실험

복원 뷰는 세 가지 안을 실물 렌더로 견줘 정했다. 블록 좌표를 다시 배치하는 방식은 잘림과 중복,
왜곡이 생겼다. 글자 좌표를 직접 읽는 방식은 원리상 오차가 없지만 표의 괘선과 서식을 표현하지
못했다. 결국 원본 렌더를 배경으로 두고 그 위에 투명한 글자층을 얹는 방식으로 확정했다. 디지털
PDF는 좌표를 직접 읽고, 스캔은 MinerU의 줄 좌표를, 사진은 보정한 스캔에 OCR 줄을 쓴다.

표는 디지털 PDF의 괘선 좌표와 글자층을 직접 읽어 병합, 열 폭, 글자를 원본대로 복원한다. 실물
공고문에서 OCR 오인식이 사라지고 원본과 같은 칸 비율로 복원되는 것을 확인했다.

언어 모델의 오타 교정은 본문에서 표 셀까지 넓혔고, 판정 기준을 라벨에서 실제 OCR 발생으로
바꿨다. 행정 용어 사전을 프롬프트에 넣자 맥락 없는 셀의 교정률이 올랐다. "주민등특번호"가
"주민등록번호"로, "등의여부"가 "동의여부"로 고쳐졌다.

근거: ADR-0007, docs/weekly/2026-09-08-w2.md.

## 4. 검색 모델 학습과 채택 (9월 20일)

리랭커 학습본 ZZAIMY-Rerank v1은 운영 하이브리드가 실제로 올린 후보 20개에서 목록 단위로 학습했다.
문서 단위 홀드아웃 12건에서 R@1이 0.649에서 0.711로 올랐다. 서빙 장비 GPU로 옮기자 질의당 시간이
3.75초에서 0.07초로 줄었다. 근거 하한은 모델마다 다시 잰다.

임베딩 학습본 ZZAIMY-Embed v2는 후보 진입률로 판정해 채택했고 색인과 질의 임베딩을 같은 모델로
묶어 서빙한다. 리랭커가 싸진 덕에 후보 수를 10개에서 20개로 늘렸다. 30개는 더 낫지 않았다.

용어를 모르고 상황으로 묻는 질의의 22.7%는 두 검색 축 모두 상위 20에 넣지 못한다. 이 몫은
리랭커나 후보 수로는 줄지 않는다.

근거: ADR-0020, ADR-0021, docs/model-cards.

## 5. 문서함 재반입과 측정의 유효성 (9월 21일)

문서함을 비우고 원본에서 다시 반입했다. 문서 194건(규정 8, 교내 113, 국고 공개 68, 외부 공고 5),
기준 조각 4,254개다. 처음에는 교내 문서를 잘못된 갈래로 넣고 국고 공개 문서 폴더가 목록에 없어
조각이 300개뿐이었다.

이름 규칙을 반입 단계로 옮겼다. 파일 이름이 무엇이든 본문 제목으로 이름을 정하고 같은 제목은
부제나 접수번호로 구분한다. 표 줄, 공고번호 줄, 발신처 줄, 마크다운 표시는 제목이 되지 않는다.
실제 반입 경로로 자가 점검했다.

유효한 측정은 질의 1,026건과 표본 300건으로 어휘 R@1 0.430, 임베딩 0.691, 하이브리드 0.671, 운영
구성 0.763, 운영 R@10 0.927이었다. 같은 표본에서 리랭커가 하이브리드를 0.680에서 0.763으로 올렸고
서빙 장비 응답 300건에 폴백은 없었다.

공개 수집 문서 73건을 마스킹 대상으로 바꿔 다시 처리하자 잔여 개인정보가 208건에서 0건이 됐다.
"박사 학위"의 "박사"를 성명으로 잡던 오탐도 없앴다.

근거: data/platform/eval/retrieval-latest.json, docs/HANDOFF.md 4절.

## 6. 이미지 판독 모델과 서빙 정밀도 (9월 21~22일)

글자층의 65.7%가 깨진 36쪽 스캔 매뉴얼로 판독 모델을 비교했다. 계획에 없던 소형 모델은 5쪽을
21초에 읽었지만 없는 문장을 지어내고 줄을 반복했다. Qwen3.8-27B 원본은 128초가 걸렸지만 원문을
그대로 읽었다. 계획대로 27B로 통일하고 소형 모델은 뺐다.

27B 원본은 젯슨에서 동시 세 요청의 생성 합이 초당 14토큰, 요청당 5토큰 남짓이었다. 검토 한 건에
3분, 판독 한 쪽에 1~2분이 걸렸다. 두 토르로 역할을 나누고 정밀도 우선순위를 FP4, FP8, bf16 순으로
정했다.

NVFP4 판은 젯슨 기본 빌드에서 양자화된 출력층을 읽지 못해 실패했고 Qwen3.8 전용 빌드로 올라갔다.
요청 하나에 초당 10.4토큰이다. FP8 판은 기본 빌드에서 실패했다. 9월 22일에는 토르 02도 NVFP4로
바꿔 두 서빙 서버가 같은 판을 쓴다(초당 10.9토큰).

호출 제한 시간 180초는 27B 판독에 짧아 한 쪽이 2분을 넘기면 판독이 꺼졌다. 판독과 검토의 제한을
600초로 늘렸다. 검토 의견의 생성 상한을 1,024에서 2,048토큰으로 올리고 상한에 걸리면 이어 쓰게
하자 잘린 검토가 193건 중 84건에서 0건이 됐다.

근거: ADR-0023.

## 7. KURE-v2 다중 벡터 경로와 조각 잡음 (9월 22일)

공개 KURE-v2는 조각당 벡터 하나가 아니라 토큰마다 128차원 벡터를 내는 모델이다. 인코딩을 옮겨
토르 03에 색인(조각 4,284개, 토큰 84만 6천 개, 780MB, 33초)과 MaxSim 서비스(질의당 50~70ms)를
만들고 운영과 같은 질의 1,023건으로 쟀다. 단독 R@1 0.682(운영 임베딩 0.692), 후보 진입률 0.919

## 8. 반입 충실도 — 표 평문, 쪽 번호, 판본, 서류 갈래, 깨진 판독 (9월 22일)

글자층 직독은 쪽별 본문을 유지해 조각마다 쪽 번호를 붙인다. 제목 정규화 열쇠(family)로 같은 제목을 묶고 본문
겹침 0.95 이상이면 같은 내용으로 거절하며, 그 아래면 판본으로 잇는다(가장 가까운 판본 쌍이 0.90이라 오판하지
않는다). 붙임 앞머리 모양과 사업 이름 앞글자로 같은 공고의 묶음을 잡아 머리 문서에 잇는다. 서류 갈래는 제목의
낱말, 없으면 본문 생김새(조문 머리, 결재란, 빈칸 표시, 신청 기간)로 정하고 확신이 없으면 비운다. 비전 판독
결과는 표를 행 평문으로 풀어 본문에 넣는다. 깨진 게시물은 27B 비전으로 다시 읽었다(한 건에 4~5분).

없는 문서는 10건에서 2건(앞서 30쪽만 비전으로 읽은 문서 1건, 글자 없는 사진 1건)으로, 한자 잡음 문서는 9건에서

### 9.1 계획↔실적 짝 개선

진단. 시험지의 짝은 그래프의 문서 짝(plans_reports) 가운데 하나를 무작위로 고른 것인데, 문서 짝은 같은 사업·연차의 계획서 ×
실적보고서를 모두 잇는다(예: 한 연차 계획서 45건 × 실적보고서 6건 = 270쌍). 질문의 절 제목을 가진 같은 연차 계획서가 평균 십여 건이고
실적보고서도 여러 건이라, 정답 두 문서가 후보에 없거나 순위에서 밀린 것이 아니라 같은 짝 가운데 다른 판본이 걸린 경우가 대부분이었다.
그래서 엄격 지표(시험지 두 문서)와 함께 짝 성립(질문의 절을 가진 같은 연차 계획서 하나 + 그 짝 실적보고서 하나)을 따로 잰다.
실패의 실제 원인은 두 가지였다. B 는 관계를 읽지 않아 짝을 담지 않았고, C 는 근거 문서마다 「첫 짝」 만 담아 모든 계획서가 같은
실적보고서 하나를 가리켰다(실적 쪽 적중 25% 고정).

바꾼 것. 물은 갈래가 관계의 양 끝(계획서·실적보고서)이면 모델 읽기 없이도 그 관계를 따른다(graph/retrieve.KIND_RELATIONS, 새 낱말 규칙 없음).
근거 문서마다 아직 근거에 없는 짝 가운데 검색 순위가 앞선 것(순위에 없으면 짝 문서들 안에서 다시 찾은 순위)을 담아 짝이 서로 다른
문서로 고르게 들어간다(grant_search._cover_relations). 담는 짝 수 상한(3)은 그대로다.

검색만 쟀다(답변 생성 없음, 재순위 꺼짐, 같은 시험지 graphrag_rel_set). 절 질문과 앞뒤 단계·평가 질문에서 바뀐 결과는 새 경로가
작동하지 않은 질문들이라 회차 잡음(±4pt)이다. C 의 절 질문은 다시 재지 않았다 — 바뀐 코드는 관계를 따를 때만 작동한다.
남은 한계: 「계획 대비 실적」 처럼 계획 갈래 낱말이 없는 질문은 B 에서 여전히 짝을 따르지 않는다(27B 읽기 C 가 필요하다).
엄격 지표의 계획 쪽은 같은 절을 가진 판본 가운데 어느 것이 정답인지 질문으로 가릴 수 없어 더 오르기 어렵다.

## 13. 질문에 문서 이름을 넣으면 — 묶어 적은 이름 읽기 (10월 15일)

계기: 12절 채점에서 운영 답의 만점이 6/24 에 그쳤다. 절 질문 시험지(scripts/173 rag_probe_set, 80문)는 「<사업> <연도> 계획서의
「절 제목」」 꼴이라, 같은 제목의 절을 가진 문서가 여럿이면(단위과제·협약반마다 같은 서식, 80문 가운데 57문) 질문이 문서 하나를
가리키지 못한다. 그래서 같은 시험지에 문서 이름을 넣은 질문(q_named — 갈래 낱말 자리에 「문서 이름」)을 더하고 검색만 쟀다
(173 --reader, 27B 질문 읽기 켬 = 운영과 같음).

| | 정답 문서가 상위 5 안 | 같은 절을 가진 문서 가운데 하나가 상위 5 안 |
|---|---|---|
| 원래 질문(고치기 전) | 61.3% | 90.0% |
| 문서 이름 넣은 질문(고치기 전) | 53.8% | 76.3% |
| 문서 이름 넣은 질문(고친 뒤) | 70.0% | 85.0% |
| 원래 질문(고친 뒤) | 55.0% | 92.5% |

고치기 전에는 문서 이름을 넣으면 오히려 나빠졌다. 질문에 묶어 적은 이름은 모두 절 이름으로 보았고(「인테리어디자인과」 를 절
제목으로 찾음), 묶은 이름 속 낱말까지 질문의 연차·갈래로 읽었다(문서 이름 속 「2차년도」 가 연도와 맞부딪혀 0건, 절 이름 「사업
실적(기타)」 의 「실적」 이 갈래를 실적보고서로).

고친 것(graph/retrieve.scope, app/grant_search):
- 묶어 적은 이름이 그 사업의 전체 공개 문서 이름(문서함 이름 — 반입 때 본문 제목으로 바꾼 것)이면 그 문서로 좁히고 절 이름으로 쓰지
  않는다. 걸리는 문서가 없거나 20건을 넘으면 문서 이름이 아니다. 같은 이름이 범위 안 공개 문서의 절 제목이기도 하면 절 이름으로
  읽는다(「사업 예산집행 계획」 은 계획서의 절이자 같은 이름의 붙임 문서다). 낱말 규칙 없이 문서함·그래프에 있는 이름으로만 가른다.
- 연차·갈래 낱말은 묶어 적은 이름 밖에서만 읽는다.
- 공개가 아닌 문서는 이름·절 제목 맞추기에 쓰지 않는다 — 이 단계는 묻는 사람을 모르므로 그런 문서가 있는지가 검색 단계 글로
  새지 않게(보안 검토 두 번 지적, 반영).

원래 질문의 정답 문서 비율이 61% → 55% 로 움직인 것은 이 변경 때문이 아니다. 갈린 문항을 하나씩 보니 질문 읽기·범위는 그대로였고,
그사이 27B 갈래 판정·앞뒤 단계 배정으로 그래프가 바뀌었으며(사업 문서 11,927 → 11,911건), 같은 제목의 절을 가진 문서가 12건을
넘으면 그래프 절 축(section_hits)이 그 가운데 어느 12건을 앞에 둘지가 DB 순서라 정답 문서가 드나든다. 같은 절 문서 기준으로는
90% → 92.5% 로 그대로다.

이어서 같은 제목의 절이 12건을 넘으면 어휘·임베딩 순위가 높은 문서의 절부터 앞에 두게 했다(DB 순서 대신). 원래 질문 정답 문서
55.0% → 57.5%, 이름 넣은 질문 70.0% → 68.8% — 한두 문항이라 잡음 안이다. 순서를 우연에 맡기지 않는다는 뜻으로 두었다.
이 작업 중 보안 검토가 그래프 절 축 조각이 열람 권한을 거치지 않는 것을 찾았다(이 변경 전부터 있던 것 — 색인 경로에서 남의 비공개
문서의 같은 제목 절이 근거에 들 수 있었다). 어휘·임베딩 축과 같은 조건(permitted)으로 거르게 고쳤다.

근거: VM data/eval/rag_probe_named1015.json · rag_probe_named1015--named.json(세 번째 측정), 시험지 rag_probe_set.json(q_named 추가).

## 15. 근거 밖 숫자 표시와 답 꼴 정리 (10월 17일)

물음. 기준 측정에서 답 10개 가운데 2개에 근거에 없는 숫자가 있었고, 답 하나가 평균 약 1,200 토큰이라 생성에 105초가 걸렸다.
답을 내기 전 마지막 점검과 답의 꼴을 바꾸면 둘 다 줄어드는가.

바꾼 것. 첫째, 답을 내보내기 전에 수치 검증기(verify.numbers.flag_unsupported)가 답의 숫자를 모델에 실제로 건넨 근거 글과 대조하고, 근거에 없는 숫자는 지우지 않고
그 자리에 「(근거 확인 필요)」를 붙이며 답 끝에 안내를 단다. 측정에서는 이렇게 표시한 숫자를 몰래 섞인 숫자로 세지 않는다.
둘째, 답 꼴 지시를 「핵심 먼저, 요점 5개 이내, 600자 안팎, 근거 표·문단을 옮겨 적지 않기」로 바꿨다. 원문은 출처 패널의
「문서에서 보기」가 대신 보인다.

결과. 추측 디코딩(16절)과 함께 적용한 뒤 195 를 다시 돌렸다(검색 단계는 바꾸지 않음).

|---|---|---|
| 근거 밖 수치가 있는 답(표시 안 한 것) | 2/10 | 0/10 |
| 정답 사실 재현율 | 0.036 | 0.047 |
| 근거에 정답 문서 | 0.8 | 0.7 (세 번 잰 값 0.5 · 0.8 · 0.7) |

## 16. 서빙 추측 디코딩(MTP) 적용 (10월 17일)

출력 분포는 바뀌지 않고, 맞힌 만큼 한 번에 여러 토큰이 나온다. 먼저 검토·판독 담당 장비에 켜고 같은 시험 문장 3개로 쟀다.

## 18. 사업 분류 파일 단위 27B 재판정 (10월 18일)

물음. 사업 분류는 폴더 단위 판정과 파일 이름 뽑기로 해 왔다. 그런데 폴더 단위 「사업 아님」 판정이 그 폴더에 섞인 사업 문서까지
기관 일반 업무로 보내고, 파일 이름 뽑기는 「3차년도 지방보조사업」 같은 일반어를 사업 묶음으로 세웠다. 이런 원본을 27B 가 파일
하나씩 보고 다시 정하면 얼마나 바뀌는가.

방법. scripts/196_program_rejudge.py. 코드는 다시 볼 후보만 고른다 — 사업 장부의 이름·별칭이 제목이나 본문에 나오는데 「사업 아님」으로
간 원본, 사업 이름이 아닌 묶음에 든 원본. 27B(검토 연결)가 제목·폴더·본문 첫머리와 사업 장부의 사업 목록을 보고
`{"label", "confidence", "reason"}` JSON 하나로 답한다. 답은 장부에 있는 이름, 「사업 아님」, 「모름」 가운데 하나다. 장부에 없는 이름이거나
「모름」·확신 낮음이면 적지 않는다. 판정은 같은 검토 장부에 파일 단위 줄로 덧붙이고 원본 장부 맞추기와 그래프가 폴더 판정보다 먼저 쓴다.
네 건씩 동시에 판정하고 한 건마다 바로 적어 중간에 멈춰도 남게 했다. 줄마다 판정한 모델 정보를 남긴다.

| 결과 | 건수 |
|---|---|
| 다시 판정한 원본 | 1,034 |
| 사업으로 옮김 | 734 |
| 그대로 | 259 |
| 버림 | 34 |
| 실패 | 7 |

판단. 반영. 10-18 운영 기준으로 사업 장부는 96개(교내 재정지원사업 현황 엑셀에 있는 66개, 공개 출처로 확인한 옛 사업 등 30개), 지식그래프의
사업 노드는 136개다. 「버림」 34건이 어떤 판정 갈래인지는 운영 집계에 세부가 없어 미확인이고, 판정의 정확도는 표본 대조를 하지 않아 미측정이다.
근거: scripts/196_program_rejudge.py, 10-18 운영 집계(저장소 밖).
