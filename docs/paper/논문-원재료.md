# 논문 원재료

국문 논문의 본문을 이 문서만 보고 쓸 수 있도록 핵심을 모았다. 수치는 저장소의 측정 기록과
결정 기록에 있는 실측치만 쓰고, 리허설이나 확인하지 못한 값은 그렇게 적는다. 실험의 시계열은
실험 로그가 정본이며 여기서는 되풀이하지 않는다. 각 절 끝의 "근거" 줄이 출처다.

제목 후보: 온프레미스 sLLM 기반 대학 행정문서 처리 플랫폼의 설계와 도메인 특화 개선

## 1. 연구 목표

대학 행정문서, 곧 국고사업 계획서와 채용·입학 서류를 교외로 내보내지 않고 처리하는 온프레미스
AI 플랫폼을 만드는 것이 목표다. 주장은 두 축이다. 축 A는 문서 반입에서 추출, 검색, 검토와 작성에
이르는 전 경로를 실제 행정에 쓸 수 있는 수준으로 구현하는 것이고, 축 B는 오픈웨이트 모델을 교내
문서에 맞게 특화해 베이스라인 대비 개선폭을 수치로 입증하는 것이다.

제약은 개인정보다. 문서에 개인정보와 기관 내부 정보가 들어 있어 외부 API를 쓸 수 없다. 장비는
운영 서버, 서빙 서버, 학습 서버로 나뉜다. 운영 서버는 학과 ESXi 가상서버로 GPU가 없고 웹, 검색,
OCR, 문서 관리를 맡는다. 서빙은 젯슨 AGX 토르 두 대가 맡는데, 토르 02는 대화와 초안 작성처럼
사람이 기다리는 일을, 토르 03은 반입 검토와 이미지 판독 같은 배치 작업과 임베딩·리랭커 서비스를
맡는다. 학습은 DGX가 전담한다. 9월 첫 주의 초기 검증은 별도의 DGX Spark 한 대에서 했고 지금은
쓰지 않는다.

시스템의 위치는 "70% 초안과 사람 검수"다. 완성본을 만드는 기계가 아니라 근거를 갖춘 초안과 검토
의견을 내고, 판단은 담당자가 한다.

근거: ADR-0023, docs/HANDOFF.md 1절, docs/env-report.md.

## 2. 시스템 구성

### 서빙

서빙 엔진은 vLLM이다. 초기 검증에서는 MoE 모델(Qwen3.5-35B-A3B)이 같은 조건의 dense 4B보다
빨라 대역폭이 제약인 장비에서 MoE가 유리함을 확인했다. 그러나 2주차 미팅에서 생성 모델을
Qwen3.8-27B로 정하면서 dense 모델로 옮겼다. 이 모델은 이미지 입력이 되는 멀티모달이라 스캔 문서
판독까지 한 모델이 맡는다.

젯슨에서 27B 원본(bf16)은 요청 하나에 초당 2~5토큰이라 실사용이 어려웠다. NVIDIA가 배포한 NVFP4
양자화 판으로 바꾸자 같은 입력에서 초당 10토큰 남짓이 나왔고, 판독과 검토가 서너 배 빨라졌으며
내용은 같았다. 양자화 판은 젯슨 기본 빌드가 아니라 Qwen3.8 전용 빌드가 필요했고, FP8 판은 그
빌드에서도 뜨지 않아 보류했다. 이미지 판독, 반입 검토, 초안, 대화가 모두 이 한 모델로 돈다.

근거: ADR-0004, ADR-0023, 실험 로그 6절.

### 플랫폼

FastAPI와 SQLite, 서버사이드 템플릿으로 만들었다. 업무 영역(국고사업, 채용, 입학, 일반) 아래
프로젝트(사업, 공고, 학년도 단위)가 있고 그 아래 문서의 접수, 검토, 판정, 초안이 놓인다. 담당자
계정과 개발자 계정이 분리돼 있다. 운영 서버에서 자동으로 시작하고 모델 캐시를 오프라인으로
두어 외부 인터넷 없이 자립한다.

추출 결과는 하나의 데이터 계약을 따른다. 제목, 문단, 표, 그림을 읽기 순서대로 담는 조각 표와
그림 파일 표가 그것이며, 화면 렌더링과 내보내기, 후속 검색과 작성이 모두 이 계약을 읽는다.

근거: ADR-0007, docs/HANDOFF.md 1절.

### 지식 그래프

기준 문서, 접수 문서, 프로젝트를 노드로 두고 근거, 소속, 조문 참조, 의미 유사를 간선으로 잇는
경량 온톨로지다. 문서 사이의 연관은 임베딩 유사도가 주 신호이고, 개체가 하나만 겹쳐도 잇던
규칙 기반 연관은 제거했다. 사업, 부서, 연도, 실적 같은 개체 계층은 2단계로 진행 중이다.

근거: ADR-0009, ADR-0010, ADR-0015.

### 외부 참조 관문과 한글 산출

외부 AI에 질의할 때는 개인정보와 기관 식별자를 걷어내고 위험을 판정한 뒤 승인 큐를 거쳐 보내며
감사 기록을 남긴다. 실제 전송은 키를 등록하기 전까지 꺼져 있다. 한글 문서는 한글 프로그램을
COM으로 조작하는 에이전트가 만들며, 서버의 지시가 실제 한글 화면에 반영되는 왕복을 실장비에서
확인했다. 초안은 docx, pdf, md, hwpx 네 형식으로 내보낸다.

근거: ADR-0008, ADR-0019, ADR-0014.

### 데이터 공방

검토 의견, 초안, 대화 기록을 학습 형식(JSONL)으로 바꾼다. 출력의 수치가 입력 근거에 있는 쌍만
통과시키며 Label Studio와 연동된다.

### 규모

2026년 9월 22일 기준으로 자동 테스트 555건이 통과하고 결정 기록은 25건이다. 운영 서버의 문서는
194건(규정 8, 교내 113, 국고 공개 68, 외부 공고 5)이고 기준 조각은 3,503개다. 조각 수는 9월 22일
절 단위 재분할 뒤의 값이며, 9월 14일의 기준선은 1,211개였다.

근거: docs/HANDOFF.md 4절, docs/dev-now.md.

## 3. 방법

### 3.1 문서 추출

스캔, 사진, 손글씨, 표가 섞인 문서에서 기존 OCR은 글자를 잘못 읽고 구조를 잃는다. 입력의 종류에
따라 경로를 나눴다. 사진과 짧은 PDF는 서빙 중인 멀티모달 모델이 전사한다. 표는 병합 셀과 머리글을
살린 HTML로, 강조는 굵게로 쓰도록 지시하고, 문서 영역은 사각형 검출과 원근 보정으로 자동으로
자르며 직인은 색을 분리해 따로 뽑는다. 판독 모델은 토르 03의 27B이고 서빙이 없으면 MinerU로
물러난다. 글자층이 있는 PDF라도 한자 잡음이 15%를 넘으면 스캔본으로 보고 판독한다.

긴 PDF는 디지털이면 MinerU로 구조를 뽑고 원본 글자층을 덧씌워 OCR 오인식을 원천에서 막는다.
스캔이면 MinerU OCR 뒤에 언어 모델이 보수적으로 오타를 고치는데, 배치 구분자 검증과 길이 가드로
환각을 막는다. 복원 뷰는 원본 렌더 위에 투명한 글자층을 얹는 방식이며 디지털 PDF는 글자 좌표를
직접 읽고 표는 괘선을 직접 읽는다. HWP와 HWPX는 전용 파서를 쓴다.

결과로, PaddleOCR이 깨뜨린 손글씨 표를 멀티모달 판독이 표 구조와 값까지 복원했다. 디지털 PDF를
스캔처럼 처리했을 때 MinerU의 어절 F1은 0.74에서 0.84 사이였다. 도전자로 시험한 MinerU
hybrid-engine과 dots.ocr은 오독과 환각으로 보류했고, PaddleOCR-VL은 CPU에서 측정하지 못했다.
스캔 문제집의 오타 교정 건수와 장식 아이콘 필터의 전후 건수는 원 로그가 없어 확인하지 못했다.

근거: ADR-0007, docs/ocr-cer-bench.md, docs/ocr-duel.md, 실험 로그 1절과 3절.

### 3.2 검색

규정 질의에서 부분 문자열 검색은 재현율이 낮다. 어휘 검색과 임베딩 검색을 함께 쓴다. 어휘 축은
Kiwi로 명사를 뽑고 교내 용어 사전을 더해 IDF와 희귀 명사 우선으로 순위를 매기며, 임베딩 축과
RRF로 융합한다(어휘 가중 0.4, 임베딩 1.0). 융합 상위 20개를 리랭커가 다시 정렬한다. 운영 모델은
학습본인 ZZAIMY-Embed v2와 ZZAIMY-Rerank v1이며 토르 03의 서비스로 돈다.

초기 기준선은 2026년 9월 4일, 조각 1,236개와 합성 질의 2,595건으로 쟀다. 한 번에 맞히는 비율(R@1)은
어휘 0.338, 임베딩 0.611, 하이브리드 0.595였고 MRR@10은 각각 0.413, 0.700, 0.692였다. 어휘 가중은
0.2에서 0.5 사이가 고원이라 기본값 0.4를 두었다. 리랭커는 표본 300건에서 R@1을 0.490에서 0.623으로
올렸다.

재반입 뒤인 9월 21일 측정에서는 조각 4,254개와 질의 1,026건으로 어휘 0.430, 임베딩 0.691,
하이브리드 0.671, 리랭커까지 거친 운영 구성 0.763을 얻었고 운영 구성의 R@10은 0.927이었다. 9월
22일 절 단위로 다시 나눈 뒤에는 조각 3,503개에서 운영 구성 R@1 0.723, R@10 0.907, MRR 0.782다.
조각이 커진 만큼 합성 질의 기준 값은 조금 내려갔지만 조각 하나가 절 하나를 온전히 담는다.

해석은 이렇다. 합성 질의로 자기 문서를 찾는 측정이라 절대치는 낙관적이고 방식 간 비교에만 쓴다.
임베딩 단독과 하이브리드는 동급이며 뚜렷한 개선은 리랭커에서 나온다. 용어를 모르고 상황으로 묻는
질의의 22.7%는 두 축 모두 상위 20에 넣지 못해 리랭커로는 넘을 수 없는 천장이다. 사람이 쓴
골드셋 측정은 아직이다.

측정에는 규율이 하나 있다. 서빙 장비 설정을 읽지 않고 띄운 측정은 리랭커와 질의 임베딩이 CPU
베이스 모델로 조용히 물러나 거짓 수치를 낸다. 9월 21일 세 번의 측정이 그렇게 무효가 됐고, 이후
보고서는 어느 리랭커가 답했는지와 폴백 수를 항상 적는다.

근거: docs/retrieval-baseline-mini.md, docs/retrieval-weight-sweep.md, docs/rerank-baseline.md,
data/platform/eval/retrieval-latest.json, 실험 로그 4절과 5절.

### 3.3 도메인 특화 학습

규정 조각마다 언어 모델로 합성 질의를 세 종류(실무형, 공고 요구사항형, 키워드형) 만들고, 문서
단위로 홀드아웃을 나눈 뒤 베이스라인을 재고 학습해 같은 홀드아웃에서 다시 잰다. 채택은 운영
하이브리드 위에서 개선이 있을 때만 한다.

첫 리허설(9월 3일, CPU)은 학습 쌍 2,253개와 홀드아웃 96질의로 했는데 R@1이 0.271에서 0.219로
내려가 배포하지 않았다. 홀드아웃이 편성표 문서 7건에 치우친 것이 한 원인이다. 이 리허설의 성과는
생성, 측정, 학습, 평가, 보고로 이어지는 사이클을 자동으로 완주한 것이다.

9월 20일에는 토르 03 GPU로 두 학습본을 채택했다. 리랭커 v1은 운영 하이브리드가 실제로 올린 후보
20개로 목록 단위 학습을 했고 문서 단위 홀드아웃 12건에서 R@1이 0.649에서 0.711로, MRR이 0.751에서
0.790으로 올랐다. 임베딩 v2는 후보 진입률로 판정해 채택했고 색인과 질의 임베딩을 같은 모델로
묶어 서빙한다. 임베딩 v1은 단독 지표만 오르고 운영 하이브리드에서 이득이 없어 채택하지 않았는데,
"운영 경로 위의 개선"이라는 채택 기준이 작동한 사례다. 생성 모델로 후보를 다시 매기는 방식은
568M 리랭커보다 덜 정확하고 53배 느려 쓰지 않는다. 공개 KURE-v2를 다중 벡터 검색으로 별도 색인해
같은 질의로 쟀을 때는 학습 전 모델인데도 학습본에 근접했지만 운영 경로에서 이득이 없어 채택하지
않았다.

통합 메모리 장비에서 서빙과 CPU 학습을 동시에 돌리면 메모리 스파이크로 학습이 강제 종료됐다.
서빙을 잠시 멈추고 메모리 할당과 시퀀스 길이, 배치를 줄여 해결했다.

생성 모델과 추출 모델의 학습은 교내 실물 문서를 받은 뒤 베이스라인을 재고 DGX에서 SFT, 이어서
DPO로 진행한다. DPO의 선호쌍은 담당자의 판정과 재작성 이력에서 나온다. 학습본은 bf16으로 병합해
NVFP4로 양자화한 뒤 두 토르로 자동으로 옮긴다.

근거: docs/embed-v0-report.md, docs/model-cards, ADR-0020, ADR-0021, ADR-0025, docs/llm-rerank-eval.md.

### 3.4 개인정보 보호

접수 문서는 파싱 직후 주민번호, 전화, 이메일, 계좌, 사업자번호, 성명 여섯 가지를 가린 뒤에만
저장하고 모델에 전달한다. 탐지는 Presidio에 한국형 인식기를 더했고 주민번호와 사업자번호는
체크섬으로 검증한다. 규정과 공고 같은 기준 문서는 판단 근거이므로 원문을 유지한다. 마스킹은
색인 앞 단계에 두어 사후 재구축 비용을 피한다. 점검 화면은 마스킹 기록, 알려진 정답 자가 점검,
색인 본문 잔여 스캔을 제공하며 외부 참조는 관문을 통해서만 나간다.

근거: ADR-0006, ADR-0008.

### 3.5 검토와 작성

검토는 업무 영역별 프롬프트를 쓴다. 채용은 서열화를 금지하고 사실만 정리하며 입학은 기준과
대조한다. 프로젝트 지침과 연결된 공고를 우선 근거로 넣는다. 승인, 재검토, 반려의 판정이 피드백
루프가 되고 이것이 DPO 선호쌍의 원천이다.

국고사업 초안은 공고에서 뼈대를 뽑고 섹션별로 생성한 뒤 수치 대조, 배점 커버리지, 예산 검산을
거친다. 통짜 생성은 하지 않는다. 섹션의 재료는 섹션 질의와 접수 자료 조각의 임베딩 유사도 상위
여섯 개다. 담당자 의견을 반영한 재작성 루프가 있고 한글 산출은 COM 에이전트가 한다. 생성된 수치는
인출한 근거에 있어야 하며 없으면 "근거 없음"으로 표시한다. 학습 데이터 정제기와 데이터 공방도
같은 기준을 쓴다.

근거: ADR-0014, ADR-0015.

### 3.6 연관과 반영 판정을 학습된 표현으로

세 곳에서 규칙이 문제였다. 그래프는 개체 하나만 겹쳐도 문서를 이었고, 초안 재료는 문서 앞 여섯
조각으로 고정돼 있었으며, 배점 커버리지는 키워드 포함만 봤다. 규칙과 역할 사전으로 고치려는
시도는 모두 사례 짜맞추기로 흘렀다.

세 곳 모두 임베딩의 의미 유사도로 판정을 통일했다. 커버리지는 절대 임계값 대신 돋보임 규칙을
쓴다. 항목별 최고 문단의 유사도가 문단 평균보다 0.10 이상 높고 0.40 이상이며 문단이 넷 이상일 때
반영된 것으로 본다. 임베딩 함수는 주입식이라 모델이 없으면 규칙 동작으로 내려간다.

9월 14일 측정에서 그래프는 동의 절차 문서끼리 0.862, 장학 사업끼리 0.842와 0.865, 산학협력단
규정끼리 0.905로 묶였고 절차와 사업은 엮이지 않았다. 개체 기반 유사도는 절차와 사업을 0.703으로
잘못 이었다. 커버리지는 절대 임계 0.62가 전부를 누락으로 찍었고 돋보임 규칙은 합성 표본 55점 중
45점을 맞혔다. 크로스인코더는 0.50 근처에 몰려 판별하지 못했다. 돋보임 폭 0.10은 합성 문단
기준이라 실제 초안과 공고로 다시 보정해야 한다.

근거: ADR-0015.

## 4. 기여

첫째, 외부 반출이 불가능한 제약에서 CPU 운영 서버와 서빙 GPU 두 대, 학습 GPU 한 대의 구성으로
추출, 검색, 검토, 작성의 전 경로를 구현하고 각 단계의 설계 선택을 실측으로 정당화했다. 서빙
정밀도로 FP4를 택한 것, 하이브리드에 리랭커를 얹은 것, 입력별로 OCR 경로를 나눈 것이 그 예다.

둘째, 서빙 중인 범용 멀티모달 모델을 OCR의 보완재로 쓰는 경로 분기다. 손글씨와 직인처럼 전통
OCR이 못 다루는 영역을 별도 모델 없이 처리한다.

셋째, 규칙과 키워드 대신 학습된 임베딩으로 문서 연관, 초안 재료, 배점 반영을 한 가지 잣대로
판정하는 설계다. 도메인 임베딩을 학습하면 세 곳이 함께 좋아지는 구조다.

넷째, 검색 학습본의 채택 기준을 "운영 경로 위의 개선"으로 두고 리랭커와 임베딩을 채택한 절차다.
단독 지표만 오른 판을 걸러낸 사례가 포함된다.

다섯째, 수치 무결성 체계다. 검증기, 학습 데이터 정제기, 데이터 공방이 같은 기준을 공유하고 학습
사이클이 자동화돼 재현할 수 있다.

여섯째, 온프레미스 운영의 실측 보고다. 통합 메모리 장비에서 서빙과 학습을 동시에 돌릴 때의 한계,
젯슨의 페이지 캐시가 GPU 메모리를 막는 함정, 양자화 판의 빌드 의존성, CPU 전용 서버에서의 OCR
한계, 오프라인 모델 적재의 함정과 해법을 기록했다.

## 5. 한계와 향후

검색 학습본의 홀드아웃은 문서 12에서 21건, 상황 질문 14건 규모라 상황 질문의 개선폭은 표본 오차
안이다. 실물 골드셋과 층화 분할로 다시 재야 한다. 생성 모델과 추출 모델의 특화 학습은 아직
시작하지 않았고 지금 서빙하는 27B는 학습 전 베이스다. 검색 절대치는 합성 질의 기준이며 상황 질의의
22.7%는 두 축 모두 놓친다. 커버리지 돋보임 폭은 실제 초안으로 재보정해야 한다. 긴 스캔 PDF는
MinerU 품질에 의존하고 표 셀의 배경색 같은 시각 서식은 보존하지 못한다. MinerU의 GPU 판독 백엔드는
젯슨 빌드에서 출력이 무너져 보류했다. 검색 색인은 임베딩 사전 계산 방식이며 벡터 DB 도입은 미결이다.
