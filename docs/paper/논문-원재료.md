# 논문 원재료 정리

정리 2026-09-15: Writer 베이스를 Qwen3.8-27B(2주차 미팅 확정)로, 장비를 운영 가상서버(CPU)+GPU 서버(DGX, 확보 대기) 구성으로 갱신했다. 검색·리랭커 수치를 정본 리포트(retrieval-baseline-mini·retrieval-weight-sweep·rerank-baseline, 2026-09-04, 합성 질의)와 일치시키고, Embed 학습은 리허설(홀드아웃 96질의, 베이스 미달)로 정정했다. 출처 없는 수치(692조각 시점 검색치 0.588/0.761/0.780/0.840, 정제 효과 +3.2%p, Embed +5.1%p·홀드아웃 39질의·학습 쌍 1,749, 테스트 128건, 문서 31건/602조각, 스텝 33s→10s, OCR 교정 76곳/잔존 2곳, 아이콘 크롭 20건→1건, 사용자 사전 27어)는 삭제하거나 미확인으로 바꿨다. 실험별 설정·결과·판정의 시계열은 실험-로그.md를 정본으로 두고 여기서는 인용만 한다. ADR-0015(학습된 연관 판정)·ADR-0014(한글 에이전트)·ADR-0008(외부 참조 관문)·ADR-0009(지식 그래프)를 반영했다.

국문 논문 작성 시 이 문서만 보고 본문을 구성할 수 있도록 핵심만 적는다.
수치는 docs/ 아래 리포트·ADR·인수인계 문서에 있는 실측치만 쓰고, 리허설·
미확인은 그렇게 표기한다. 실험의 시계열(설정·결과·판정)은 `실험-로그.md`가
정본이며 여기서는 반복하지 않는다.

제목 후보: 온프레미스 sLLM 기반 대학 행정문서 처리 플랫폼의 설계와 도메인 특화 개선

## 1. 연구 목표

- 대학 행정문서(국고사업·채용·입학)를 교외 반출 없이 처리하는 온프레미스 AI 플랫폼 구축
- 핵심 주장 두 축
  - 축 A: 문서 반입→추출→검색→검토·작성에 이르는 전 경로의 실사용 수준 구현
  - 축 B: 오픈웨이트 모델의 도메인 특화 개선(베이스라인 대비 개선폭을 수치로 입증)
- 제약: 개인정보 문서라 외부 API 사용 불가. 장비는 운영 서버(학과 ESXi
  가상서버, CPU, GPU 없음, 상시 가동)와 GPU 서버(DGX, 생성·학습 — 확보 대기)의
  2단 구성. 초기 검증(2026-09-01~07)은 DGX Spark 1대(aarch64, GB10, compute
  capability 12.1, 메모리 119.7GiB — env-report)에서 했고 현재는 사용하지
  않는다(HANDOFF §1)
- 시스템의 위치: 70% 초안 + 사람 검수 전제. 완성본 생성기가 아니다

## 2. 시스템 구성 (무엇을 만들었나)

- 서빙: vLLM. 초기 검증(Spark, ADR-0004)에서 nightly 이미지(다이제스트 고정) +
  Qwen3.5-35B-A3B(MoE, bf16)로 첫 토큰 87ms·30.8 tok/s를 실측했고, 같은 조건의
  dense 4B(Qwen3-4B, 47ms·23.0 tok/s)보다 빨라 대역폭 제약 장비에서 MoE가
  유리함을 확인했다. v0.11.0 릴리스는 sm_121a ptxas 미지원, FP8은 cutlass
  오류로 nightly bf16 확정. Writer 베이스는 2주차 미팅(2026-09-08)에서
  Qwen3.8-27B(dense, 멀티모달)로 확정됐고 DGX 확보 후 서빙·베이스라인 측정
  예정(미측정)
- 플랫폼: FastAPI + SQLite + 서버사이드 템플릿. 업무 영역(국고사업·채용·입학·
  일반) → 프로젝트(사업·공고·학년도 단위) → 문서 접수·검토·판정·초안의 계층
  구조. 담당자·개발자 계정 분리. 운영 서버에서 systemd 자동시작, 오프라인
  모델 캐시로 자립 동작(HANDOFF §1)
- 데이터 계약: doc_chunks(제목/문단/표JSON/그림, 읽기 순서)·doc_assets(그림 파일)
  — 렌더링, CSV·MD 내보내기, 후속 검색·작성이 전부 이 계약을 읽는다(ADR-0007)
- 지식 그래프: 기준 문서·접수 문서·프로젝트를 노드로, 근거·소속·조문 참조·
  임베딩 유사를 간선으로 잇는 구조 그래프(ADR-0009, 경량 온톨로지 v1).
  문서↔문서 연관은 임베딩 유사 간선이 주 신호이고 개체 공출현·규칙 기반
  연관은 제거했다(ADR-0015). 개체(사업·부서·연도·실적) 추출은 2단계 진행 중
- 외부 참조 관문(이그레스 게이트웨이, ADR-0008): 외부 AI 질의 시 PII·기관
  식별자 세척 → 위험 판정 → 승인 큐 → 감사 기록. 실전송은 아웃바운드 개방·
  API 키 확보 전까지 비활성
- 한글(HWP) 산출: 한글 COM 에이전트 + Markdown IR(ADR-0014). 서버 지시 → 실제
  한글 화면 반영 왕복을 실장비에서 검증(2026-09-08). 초안 내보내기는
  docx·pdf·md·hwpx 4형식
- 데이터 공방(/dev/data): 검토 의견·초안·대화 기록을 학습 형식(JSONL)으로
  변환하되 출력 수치가 입력 근거에 있는 쌍만 통과. Label Studio 연동
- 규모: 자동 테스트 210건 통과(2026-09-08 주간 보고), ADR 15건(0001~0015),
  운영 VM 문서 44건·청크 3,767(HANDOFF §2), 규정 조각 1,211개(2026-09-14
  재분할 후)

## 3. 방법론 — 기술별 (무엇을 어떻게 발전시켰나)

### 3.1 문서 추출 (OCR)
- 문제: 스캔·사진·손글씨·표 혼재 문서에서 기존 OCR(PaddleOCR 계열)의 오인식·구조 손실
- 방법 (입력별 경로 분기, ADR-0007):
  - 사진·4쪽 이하 PDF → 서빙 중인 VLM으로 전사. 표는 HTML(병합 셀·머리글)로,
    강조는 굵게로 지시. 문서 영역은 OpenCV 사각형 검출→원근 보정으로 자동
    크롭. 직인은 색 분리로 별도 추출. LLM 서빙이 없으면 MinerU로 폴백(현재
    운영 VM은 GPU가 없어 이 경로는 DGX 연결 후 활성)
  - 5쪽 이상 PDF → 디지털이면 MinerU 구조 추출 + 원본 텍스트 레이어 오버레이
    (OCR 오인식 원천 차단), 스캔이면 MinerU OCR + LLM 보수적 오타 교정(배치
    구분자 검증·길이 가드로 환각 차단)
  - 복원 뷰는 원본 렌더 배경 + 투명 텍스트 레이어. 디지털 PDF는 글자 좌표
    직독(pdfium charbox), 표는 괘선 직독
  - HWP/HWPX·텍스트는 전용 파서(.hwp 리더, ADR-0014)
- 결과 (실측, 상세는 실험-로그):
  - PaddleOCR이 깨뜨린 손글씨 표를 비전 판독이 표 구조·값까지 복원(ADR-0007)
  - 스캔 문제집 12쪽에 LLM 보수적 오타 교정 적용(ADR-0007). 교정·잔존 건수는
    미확인(원 로그 없음)
  - 장식 아이콘(120px 미만·중복) 필터, 문서당 그림 20장 상한(ADR-0007). 필터
    전후 건수는 미확인
  - MinerU 정량: 디지털 PDF 렌더를 스캔처럼 처리한 어절 F1 0.74~0.84(문서 5건,
    운영 VM CPU — ocr-cer-bench)
  - 도전자 대결: MinerU hybrid-engine·dots.ocr는 오독·환각으로 보류, PaddleOCR-VL은
    CPU에서 측정 불가(GPU 확보 후 재개)

### 3.2 검색 (RAG)
- 문제: 규정 질의에서 부분문자열 검색의 낮은 재현율
- 방법: Kiwi 명사 추출(+교내 용어 사용자 사전 26어, regulations.py) + IDF +
  희귀명사 우선의 어휘 검색과 KURE-v1 임베딩 검색을 RRF(어휘 w_a 0.4, 임베딩
  1.0)로 융합하고, bge-reranker-v2-m3 리랭커(쌍 길이 256)로 상위를 재정렬.
  단계별 실측으로 채택
- 결과 (합성 질의 2,595건, 조각 1,236개, 2026-09-04 — retrieval-baseline-mini):
  R@1 어휘 0.338 → 임베딩 0.611 / 하이브리드(임베딩 우세) 0.595, MRR@10 0.413 /
  0.700 / 0.692, 하이브리드 R@10 0.877(동가중 0.879). 가중 스윕은 w_a 0.2~0.5
  고원(MRR 0.692~0.693, 최적 0.3), 동가중 0.647(retrieval-weight-sweep)
- 리랭커 (표본 300건 — rerank-baseline): 하이브리드 R@1 0.490 → 0.623, R@5
  0.813 → 0.850, MRR 0.623 → 0.716. 속도는 운영 VM CPU에서 쌍 길이 256으로
  9.2s → 4.6s/질의, top-1 일치 1.00(HANDOFF §4)
- 해석: 합성 질의 자가 검색이라 절대치는 낙관적이며 방식 간 비교용. 이
  세트에서는 임베딩 단독이 하이브리드보다 R@1·MRR에서 근소하게 앞선다 —
  하이브리드는 브리프 설계(dense + sparse 이중 벡터화)에 따른 구성이고,
  뚜렷한 개선폭은 리랭커에서 나온다. 사람 작성 골드셋(200~500문항, eval-plan)
  측정 전
- 코퍼스 정제(웹 수집 노이즈 제거) 전후 비교치는 미확인 — 원 측정 기록이 남아
  있지 않다
- 2026-09-14 조각 재분할(1,236→1,211) 후 재측정 없음 — 합성 질의 세트가 VM
  이관 시 유실돼 LLM 연결 후 재생성 필요(HANDOFF §4)

### 3.3 도메인 특화 학습 (축 B 리허설)
- 방법: 규정 조각에서 LLM으로 합성 질의 3종(실무형·공고 요구사항형·키워드형,
  model-plan) 생성 → 문서 단위 홀드아웃 분리 → 베이스라인 측정 → KURE-v1 MNR
  대조학습 → 동일 홀드아웃 재측정
- 결과 (embed-v0-report, 2026-09-03): 학습 쌍 2,253, 홀드아웃 96질의(편성표
  문서 7건 — 유형 편중). 베이스 R@1 0.271 / R@10 0.802 / MRR 0.429 → v0.0
  0.219 / 0.833 / 0.387. 베이스 미달로 미배포. 09-02 1차 리허설의 수치는
  리포트가 덮어써져 미확인. 이번 검증의 성과는 사이클(생성→측정→학습→평가→
  리포트) 자동 완주
- 운영 발견: 통합메모리 장비에서 서빙(vLLM)과 CPU 학습 동시 수행 시 메모리
  스파이크로 학습이 반복 강제종료 — 서빙 일시 정지 + MALLOC_ARENA_MAX=2 +
  max_seq 512 + batch 8로 해결(dev-changelog 09-02). 스텝 시간 개선폭은 미확인.
  논문의 온프레미스 운영 절에 쓸 것
- 계획: DGX 확보 → Qwen3.8-27B 서빙 → 베이스라인 측정 → QLoRA SFT → DPO(2주차
  미팅에서 부활, 선호쌍 = 담당자 판정·재작성 이력). 베이스라인 측정 전
  파인튜닝 금지(절대 규칙)

### 3.4 개인정보 보호 설계
- 원칙: 인풋 문서는 파싱 직후 6종(주민·전화·이메일·계좌·사업자·성명, Presidio +
  한국형 인식기, 주민·사업자는 체크섬 검증) 마스킹 후에만 저장·LLM 전달. 기준
  문서(규정·공고)는 판단 근거이므로 원문 유지(ADR-0006). 마스킹은 인덱싱 이전
  단계에 배치(사후 재구축 비용 회피)
- 점검: PII 점검 화면(/dev/pii)이 마스킹 기록(유형·건수)·알려진 정답 자가
  점검·색인 본문 잔여 스캔을 제공. 외부 참조는 이그레스 게이트웨이(ADR-0008)로만

### 3.5 검토·작성 파이프라인
- 검토: 업무 영역별 프롬프트(채용은 서열화 금지·사실 정리, 입학은 기준 대조) +
  프로젝트 지침·연결 공고를 우선 근거로 주입. 판정(승인·재검토·반려) 피드백
  루프 — DPO 선호쌍의 원천
- 작성(국고사업): 공고 스키마 추출 → 섹션별 생성(통짜 생성 금지) → 수치 대조·
  배점 커버리지·예산 검산. 섹션 재료는 섹션 질의와 접수 자료 조각의 임베딩
  코사인 상위 6개(후보 40조각, ADR-0015). 담당자 의견 반영 재작성 루프. 한글
  산출은 COM 에이전트(ADR-0014)
- 수치 무결성: 생성 수치는 인출 근거에 존재해야 함(검증기) — 근거 없으면
  "(근거 없음)". 학습 데이터 정제기·데이터 공방도 같은 기준

### 3.6 연관·반영 판정의 학습된 표현 전환 (ADR-0015)
- 문제: 그래프는 개체 하나만 겹쳐도 연결(동의 절차 문서가 장학 사업계획과
  연관으로 표시), 초안 재료는 문서 앞 6조각 고정, 배점 커버리지는 키워드
  문자열 포함만 판정. 규칙·역할 사전으로 고치려는 시도는 모두 사례 짜맞추기로
  흘렀다
- 방법: 세 곳 모두 KURE-v1 임베딩의 의미 유사를 판정 근거로 통일. 커버리지는
  절대 임계값 대신 돋보임 규칙(항목별 최고 문단 코사인 − 문단 평균 ≥ 0.10,
  최고 ≥ 0.40, 문단 4개 이상). 임베딩 함수는 주입식이라 모델이 없으면 규칙
  동작으로 내려간다
- 결과 (운영 VM, KURE-v1 CPU, 2026-09-14): 그래프에서 동의 절차끼리 .862, 장학
  사업끼리 .842/.865, IACF 규정끼리 .905로 묶이고 절차↔사업은 안 엮임(개체
  코사인은 .703으로 오결합). 커버리지 절대 임계 0.62는 전부 누락으로 찍었고,
  돋보임 규칙으로 합성 표본 0/55점 → 45/55점. 크로스인코더는 시그모이드
  .500~.534로 판별 불가
- 한계: 돋보임 폭 0.10은 합성 문단 표본 기준 — 실제 초안·공고 쌍에서 재보정
  필요. 판단 품질이 임베딩 모델에 묶이므로 ZZAIMY-Embed 완성 시 세 곳이 함께
  좋아진다

## 4. 기여점 (논문 주장으로 쓸 것)

1. 외부 반출 불가 제약에서 CPU 운영 서버 + GPU 서버 2단 구성으로 추출→검색→
   검토·작성 전 경로를 구현하고, 실측치로 각 단계 설계 선택을 정당화(MoE 서빙
   실측, 하이브리드 + 리랭커, 입력별 OCR 경로)
2. 서빙 중인 범용 VLM을 OCR 보완재로 쓰는 입력별 경로 분기 — 손글씨·직인 등
   전통 OCR 한계 영역을 추가 모델 없이 처리
3. 규칙·키워드 짜맞추기 대신 학습된 임베딩으로 문서 연관·초안 재료·배점 반영을
   일관되게 판정하는 설계와 실측 근거(ADR-0015) — 도메인 임베딩 파인튜닝이 세
   곳을 동시에 개선하는 구조
4. 수치 무결성 체계: 검증기·학습 데이터 정제기·데이터 공방이 같은 기준(출력
   수치 ⊂ 입력 근거)을 공유하고, 학습 사이클(생성→측정→학습→평가→리포트)을
   자동화한 재현 가능한 절차
5. 온프레미스 운영 실측 보고: 통합메모리 장비의 서빙·학습 동시 수행 한계, CPU
   전용 서버에서 VLM OCR 불가, 오프라인 모델 로딩 함정과 해법

## 5. 한계·향후 (정직하게 쓸 것)

- Embed 리허설은 베이스 미달(부정 결과, 홀드아웃 편중) — 실데이터 파일럿·
  골드셋·층화 분할로 재측정
- Writer·Extract·Rerank 특화 학습은 미착수(GPU 서버 대기, 베이스라인 측정이 먼저)
- 검색 절대치는 합성 질의 자가 검색 — 골드셋 측정 전이며, 09-14 재분할 이후
  재측정 없음
- 커버리지 돋보임 폭은 합성 표본 기준 — 실제 초안으로 재보정 필요
- 5쪽 초과 스캔 PDF는 MinerU 품질 의존, 표 셀 원문 교체·셀 배경색 등 시각
  서식 미보존(ADR-0007)
- 비전 판독 경로는 LLM 서빙 전제 — 현재 운영 VM에서 비활성
- 검색은 임베딩 사전계산 방식 — 벡터DB(Qdrant vs pgvector) 확정·이관 미결
