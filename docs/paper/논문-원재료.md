# 논문 원재료 — AURA 구현 설명서

이 문서는 AURA 가 지금(2026-10-23) 어떻게 만들어져 있는지를 처리 순서대로 설명한다. 절마다 무엇을 하는지, 왜 그렇게 했는지,
어떻게 구현했는지, 잰 값이 있으면 무엇인지를 차례로 적는다. 수치는 저장소의 측정 기록과 결정 기록(ADR), 그리고 운영에서 직접 잰
값만 쓰고 괄호 안에 출처를 적는다. 문서·조각·그래프 규모는 10-18 운영 값이고, 그 뒤에 잰 값은 날짜를 함께 적는다. 재지 않은 것은 「미측정」, 확인하지 못한 것은 「미확인」으로 둔다. 실험의 시간 순서와 실패 기록은
실험 로그(docs/paper/실험-로그.md)가 정본이고, 여기서는 결론만 가져온다.

제목 후보: 온프레미스 sLLM 기반 대학 행정문서 처리 플랫폼의 설계와 구현 — 문서 반입, 온톨로지 기반 GraphRAG, 문서 작업 에이전트

## 1. 개요

### 1.1 문제

대학 행정은 국고 재정지원사업의 계획서·실적보고서·평가 자료, 규정과 지침, 공문과 서식 같은 문서로 돌아간다. 한 사업만 해도 연차마다
계획서·실적보고서가 수십 건씩 쌓이고, 사업 이름이 단계마다 바뀌며(LINC+ → LINC 3.0 → RISE 등), 같은 서식이 해마다 조금씩 다른 판으로
들어온다. 담당자는 새 계획서를 쓸 때 지난 자료를 폴더에서 일일이 찾아 읽어야 한다. 이 문서들에는 개인정보와 기관 내부 정보가 들어
있어 상용 클라우드 AI 에 보낼 수 없다.

### 1.2 목표

교외로 문서를 내보내지 않고, 교내 장비만으로 다음을 하는 플랫폼을 만든다.

- 학교 원본 문서를 형식에 상관없이 읽어 검색할 수 있는 조각으로 바꾸고, 사업·연차·서류 갈래로 정리한다.
- 질문하면 열람 권한 안의 근거 문서를 찾아 출처와 함께 답한다. 근거에 없는 숫자는 표시한다.
- 담당자의 요청에 따라 양식대로 문서 초안을 쓰고, 원본 한글 서식 그대로 완성본을 낸다.
- 위의 판단(질문 읽기, 갈래·사업 판정, 도구 고르기)은 오픈웨이트 모델이 하고, 코드는 실행·관문·기록을 맡는다.

시스템의 자리는 사람이 검수하는 초안이다. 완성본을 대신 만드는 기계가 아니라 근거를 갖춘 초안과 검토 의견을 내고, 판단은 담당자가 한다.

### 1.3 장비 구성

| 장비 | 맡는 일 |
|---|---|
| 운영 서버(가상 서버, GPU 없음, 메모리 64GB) | 웹 서비스, PostgreSQL(pgvector), 검색, 지식그래프, 문서 반입 처리, 주기 작업 |
| 서빙 장비 1(젯슨 AGX 토르) | 생성 모델 27B — 대화 답, 문서 작업 에이전트, 업무 도우미처럼 사람이 기다리는 일 |
| 서빙 장비 2(젯슨 AGX 토르) | 생성 모델 27B — 반입 검토, 이미지 판독, 갈래·사업 판정 같은 배치 일. 임베딩·리랭커 서비스 |
| 학습 장비(DGX) | 학교 원본 보관, 대량 처리(스캔 판독, 일괄 판정), 학습 데이터 생성·승인, 파인튜닝 |

원본은 학습 장비에 두고 운영 서버에는 처리본(글·조각·임베딩·그래프)과 보기용 캐시만 둔다(ADR-0047·0049). 운영 서버는 학습 장비를
읽기 전용으로만 본다.

### 1.4 데이터 흐름 한 줄

학교 원본 → 원본 장부 동기화 → 형식별 읽기·표 정리·개인정보 처리 → 조각 나누기 → 서류 갈래·사업 판정 → 판본 묶기 →
색인(어휘 + 벡터)과 지식그래프 → 질문 읽기(27B) → 그래프 범위 + 하이브리드 검색 → 근거 묶기 → 답 생성(27B) → 근거 밖 숫자 표시 → 출처와 함께 화면.

문서 작성은 같은 검색 위에서 에이전트가 양식을 고르고 절마다 쓰며, 끝에 원본 한글 서식으로 채운다.

## 2. 문서 처리

문서 처리는 학교 원본을 「검색과 그래프가 읽을 수 있는 처리본」으로 바꾸는 단계다. 들어오는 길(학교 원본 동기화, 라이브러리 업로드,
채팅 첨부, 구글 드라이브 가져오기)이 여럿이지만 모두 같은 처리기(`app/pipeline.py` DocumentProcessor)를 거친다(ADR-0049). 길마다 처리가
다르면 같은 문서가 길에 따라 다르게 검색되기 때문이다.

### 2.1 원본 반입과 동기화

무엇을. 학교 원본은 학습 장비의 사업별 폴더에 계속 들어온다. 이것을 운영 서버가 놓치지 않고 따라가야 한다.

어떻게. 두 장부를 둔다.

- 원본 장부(`archive_files` 표, `app/archive.py`): 원본 파일 하나가 한 줄이다. 경로, 크기, 수정 시각, 확장자, 사업, 처리 상태, 서류 갈래,
  연도·차수, 중복 대상(dup_of), 등록된 문서 번호를 담는다. 파일 내용은 담지 않는다. 화면의 「원본 보관소」(`/archive`)가 이 장부다.
- 라이브러리 문서(`documents` 표): 처리를 마친 문서다. 조각·벡터·그래프는 모두 이 문서 번호에 붙는다.

동기화는 주기 작업으로 돈다. 운영 서버는 1분 주기로 업로드 원본·새 조각 색인·그래프 표시를 맞추고, 10분 주기로 학습 장비 원본 목록을
훑어 장부를 차이(새로·바뀜·옮김·없어짐)로 갱신한다(scripts/170, 잠금으로 겹쳐 돌지 않음). 접속은 읽기 전용 키 하나로, 서버 쪽에서 읽기
전용 rsync 로 묶여 있다. 학습 장비는 매분 원본 보관소가 바뀌었는지만 보고, 바뀌었을 때(그리고 한 시간에 한 번) 전체 목록과 새·바뀐 원본의 가벼운 처리(scripts/165·167)를 한다. 목록이 바뀌면 운영 서버가 그 도장을 1분 안에 받아 장부 동기화를 바로 돌린다(10-18 — 주기 대기 대신 바뀌면 바로). 원본 한 건을 화면에서 열면
그때 읽기 전용으로 받아 크기·시각이 장부와 같은지 대조한다(`app/archive_original.py`).

같은 파일 찾기는 이름·크기가 같은 묶음 안에서만 sha256 지문을 내어 비교한다(`archive_dups.py`). 모든 파일의 지문을 내는 비용을 줄이려는
것이다. 확장자가 없거나 틀린 파일은 파일 머리로 실제 형식을 본다.

처리를 마친 문서는 `documents/반입/<연도>/<유형>/<접수번호> <제목>/` 폴더에 원본을 두고 모든 파일을 파일 장부(`files` 표)에 적는다
(ADR-0030, `app/storage.py`). DB 가 원본 정보이고 디스크 폴더는 사람이 찾기 쉽게 하는 배치다. 학습 장비에만 원본이 있는 문서는 이 폴더
대신 학습 장비 경로를 가리킨다.

규모(10-18 운영): 원본 장부 167,146건(중복 제외 130,046), 라이브러리 문서 35,469건(사업 문서 35,119).

### 2.2 형식별 읽기

무엇을. PDF(디지털·스캔), 한글(hwp·hwpx), 워드·엑셀·파워포인트, 옛 오피스 형식, 사진이 섞여 들어온다. 형식마다 가장 정확한 읽기 길을 고른다.

왜. 한 OCR 엔진으로 전부 읽으면 글자층이 멀쩡한 디지털 PDF 까지 오인식한다(실제 사고: 「기초과학」 → 「기추과하」, 실험 로그 2절).
반대로 스캔본을 글자층으로 읽으면 깨진 한자만 남는다.

어떻게(`app/pipeline.py`, `ingest/parsers/`).

| 입력 | 읽는 길 | 판단 기준 |
|---|---|---|
| 디지털 PDF | 원본 글자층을 글자 좌표(pdfium charbox)째 읽는다. 구조(표·2단·읽기 순서)는 MinerU 로 잡고 그 위에 원본 글자를 좌표로 덮어쓴다 | 고루 뽑은 6쪽의 쪽당 글자가 충분하고 깨진 글자(한자 잡음) 비율이 0.15 미만 |
| 아주 긴 디지털 PDF(60쪽 이상) | 글자층 직독 | 표본 6쪽 120자 이상, 전체 200자 이상 |
| 스캔 PDF | 짧은 문서는 27B 이미지 판독(최대 30쪽), 기본은 MinerU(auto) | 쪽당 글자 200자 미만이거나 깨진 글자 비율 0.15 이상 |
| 사진 | 27B 이미지 판독 → MinerU OCR → tesseract 순 | 사진·게시물은 유형과 상관없이 판독 모델이 먼저 |
| hwp | kordoc 1순위(판 고정), 실패하면 pyhwp | ADR-0033 |
| hwpx | 자체 OWPML 파서(표준 라이브러리만) | 표·글상자·머리말까지 구조로 읽음 |
| docx·xlsx·pptx | kordoc, 실패하면 python-docx·openpyxl / python-pptx | 글이 너무 적으면(쪽당 60자 미만) MinerU 로 다시 |
| 옛 형식(xls·doc·ppt·hwp3 등) | LibreOffice 로 새 형식으로 바꾼 뒤 위 길 | — |

27B 이미지 판독은 표를 병합 셀(rowspan·colspan)이 살아 있는 HTML 표로, 제목을 머리말로 쓰도록 지시한다. 흘린 손글씨는 「(판독 불가)」로
적게 해 지어내지 않게 한다. 대량 스캔 판독은 학습 장비에서 MinerU 로 했다(ADR-0007).

화면의 원본 복원 보기는 원본 쪽 그림을 배경에 두고 그 위에 투명한 글자층을 얹는다. 디지털 PDF 는 글자 좌표를 그대로, 스캔본은 MinerU 의
줄 좌표를 쓴다. 블록을 다시 배치하는 방식은 잘림·중복이 생겨 버렸다(실험 로그 3절).

결과. 스캔 판독 대결(어절 F1)에서 27B 이미지 판독 0.839, MinerU 0.690, docling 0.334 로 docling 을 스캔 경로에서 뺐다(ADR-0050, scripts/171).
대량 처리 기준은 처리량 때문에 MinerU 로 둔다. MinerU 판독 문서 6,503건 가운데 손상 신호 창이 10% 이상인 문서는 57건이었고 대부분
한두 쪽짜리 사업자등록증·견적서였다(dev-now, 10-15). 처리 실패 111건은 암호 문서·손상 파일이다.

### 2.3 표 처리

무엇을. 행정 문서의 핵심 값(예산, 성과지표, 일정)은 대부분 표에 있다. 표를 화면에서는 원래 모양대로, 검색과 모델 입력에서는 읽을 수 있는
평문으로 둔다.

어떻게. 표 조각은 칸마다 `[행, 열, 행 병합, 열 병합, 머리칸 여부, 글]` 로 저장한다. 화면은 이것을 병합이 살아 있는 HTML 표로 그린다.
검색·인용용 평문은 행마다 칸을 「 | 」로 잇는데, 가로 병합은 첫 칸에만 한 번 쓰고, 세로 병합 때문에 새 글 없이 되풀이만 하는 행은 내지
않는다(`app/render.py`, ADR-0027). 병합 셀을 칸마다 채우던 처음 방식은 「예비군대대 | 예비군대대 | 예비군대대 …」 같은 줄을 만들어 검색 잡음이
됐다. 이 규칙으로 표 조각 2,743개 가운데 1,444개의 평문이 바뀌고 글자 수가 811,240 에서 517,902 로 줄었다(실험 로그 8절). 긴 표는 행 단위로
약 700자씩 묶고 머리 행을 붙인다. 디지털 PDF 의 표는 괘선 좌표와 글자층을 직접 읽어 칸 비율까지 원본대로 복원한다.

성과지표는 표 칸 격자에서 「성과지표」 칸을 찾고 칸 이름으로 기준·목표·실적·달성률을 읽어 값을 그대로 꺼낸다(`graph/indicators.py`).
모델이 값을 만들지 않는다.

### 2.4 개인정보 처리

무엇을. 문서 속 주민등록번호·전화·이메일·계좌·사업자번호·학번·생년월일·성명을 찾아 가린다.

왜. 같은 원문이라도 쓰는 곳에 따라 위험이 다르다. 교내 담당자가 업무로 보는 원문을 모두 가리면 일을 할 수 없고, 학습 데이터나 밖으로
나가는 글은 반드시 가려야 한다. 그래서 내부 열람과 학습 반출을 서로 다른 관문으로 나눴다(ADR-0044).

어떻게(`ingest/pii.py`, `app/privacy_policy.py`).

- 탐지는 Presidio 위에 한국형 패턴 인식기 8종을 얹었다. 주민등록번호와 사업자번호는 체크섬으로 검증하고, 계좌·학번·생년월일·성명은 「계좌번호:」
  「성명」 같은 이름표 문맥이 있을 때만 잡는다. 표에서는 옆 칸 직위 문맥으로 성명을 한 번 더 가린다.
- 내부 반입·첨부·답의 가림은 관리자 설정으로 켜고 끄며 항목별로 고른다. 기본은 꺼짐이다. 규정·공고 같은 기준 문서는 판단 근거이므로
  원문을 유지한다(ADR-0006).
- 학습 후보는 이 설정과 상관없이 별도 사본에서 전체 탐지를 하고 사람 검수를 통과해야 반출된다(6절).
- 밖으로 나가는 글과 수집 자료에는 고위험 꼴(주민번호·이메일·휴대전화·카드번호 정규식)을 언제나 한 번 더 쓴다. 가림에 실패하면 내보내지
  않는다(fail-closed, 7절).

결과. 배포 점검의 전체 잔여 검사(10-09)에서 문서 41,764건·조각 1,973,998개 가운데 가렸어야 할 잔여 0(dev-now). 이 검사는 정규식 기반이라
이름표 없는 이름·주소를 놓칠 수 있으므로 완전 제거의 증명이 아니다(ADR-0044).

### 2.5 조각 나누기

무엇을. 문서를 검색 단위인 조각으로 나눈다.

왜. 조각이 너무 작으면 문맥이 끊기고, 너무 크면 엉뚱한 대목까지 근거로 들어간다. 행정 문서는 절 구조가 분명하므로 절을 넘지 않게 자르는
것이 인용과 화면 가독성에 낫다(ADR-0048).

어떻게. 사업 문서는 파서가 낸 블록(제목·문단·표·그림 글)을 하나씩 조각으로 만든다(본문 최대 2,000자, 문서당 최대 2,000조각). 조각마다 쪽
번호를 붙이고, 소속 절의 제목 경로는 앞선 제목 줄의 번호 꼴로 읽어 붙인다(`app/chunk_path.py`). 규정 문서는 「제N조」가 셋 이상이면 조문
단위로, 아니면 장·번호 표제에서 끊는다(`app/regulations.py`). 공통 규칙은 셋이다. 실질 글자 40자 미만 조각은 다음 조각과 합치고, 1,400자를
넘으면 줄이나 문장 단위로 나누며, 표제 없는 블록은 직전 표제를 물려받는다. 마지막 관문은 실질 20자 미만 같은 잡음 조각을 뺀다.

결과. 규모(10-18 운영): 문서 조각 1,848,580개, 규정 조각 9,595개.

### 2.6 서류 갈래 판정

무엇을. 문서마다 공고·양식·계획서·결과보고서·규정·협약서·증빙 같은 서류 갈래(19개, `app/doc_routing.py` KINDS)를 붙인다.

왜. 갈래는 검색 범위(「2024년 실적보고서」), 그래프의 계획↔실적 짝, 검색에서 빼야 할 지출 증빙을 가르는 기준이다. 처음에는 제목 낱말 규칙으로
정했는데, 「주간업무보고」를 결과보고서로, 견적서를 계획서로 보는 식의 오판이 많았고 규칙을 덧대면 사례 짜맞추기가 된다.

어떻게(`app/kind_read.py`). 27B 에게 갈래 목록과 갈래별 한 줄 설명, 제목, 폴더, 본문 앞 1,500자를 주고 `{kind, why}` JSON 하나를 받는다. 목록
밖 답이나 형식 오류는 버리고 규칙 판정이 남는다. 검색에서 빠지는 갈래(증빙)가 나오면 본문 2,500자를 다시 보여 주고 한 번 더 확인하며
(judge), 아니라고 하면 그 갈래를 빼고 다시 고른다. 본문이 200자 미만이면 제목만 보고 문서를 검색에서 빼지 않도록 규칙과 엇갈리는 증빙 판정을
받지 않는다. 지시를 고치면 지시 판 번호를 올려 옛 판정을 다시 본다. 학교 원본 3만여 건은 학습 장비에서 일괄 판정했고(scripts/191), 10-18 부터 새 문서는 운영 서버가 받는 즉시 반입 검토와 같은 27B(토르 03)로 판정한다 — 학습 장비에 상주 27B 를 두지 않아 학습과 메모리를 다투지 않는다.
판정 결과는 운영 서버가 백업 뒤 반영한다(scripts/192, 되돌리기 있음). 판정 줄마다 판정한 모델 정보를 남긴다.

결과. 표본 300건에서 규칙과 다른 판정 대부분이 27B 쪽이 맞았다(견적서·세금계산서 → 증빙, 교과과정표 → 교육과정). 전체 판정 29,444건(10-16,
약 96%), 규칙과 다른 판정 11,823건(dev-now). 모델 교체 기준 측정에서 표본 50건의 규칙 일치 0.92, 규칙이 비운 문서를 채운 비율 0.96(8절).

### 2.7 사업 분류

무엇을. 문서마다 어느 재정지원사업(예: LINC 3.0, RISE, 전문대학 혁신지원)의 문서인지 정한다. 사업 분류는 라이브러리의 사업별 목록, 검색의
사업 범위, 그래프의 사업 노드, 학습 데이터의 사업 단위 분리가 모두 같이 쓴다.

왜. 사업마다 주기·문서 꼴·기준이 달라 한 사업의 자료가 다른 사업 답에 섞이면 틀린 답이 된다. 폴더 이름만으로는 부족하다. 한 폴더에 여러 사업
자료가 섞여 있고, 사업 이름이 단계마다 바뀌며, 파일 이름에는 「3차년도 지방보조사업」 같은 일반어가 들어 있다.

어떻게. 기준은 사업 장부(`kg_external.json`, `app/program_names.py`)다. 장부에는 사업마다 정식 이름, 다른 이름, 기간, 주관 부처·전담기관, 앞뒤
단계 관계와 그 출처가 들어 있다. 교내 재정지원사업 현황 엑셀에서 사업명·세부과제·지원기관·기간·부서를 읽어 장부를 보강하고(scripts/186,
책임자 이름은 읽지 않음), 사업의 동일성과 이름 변경은 외부 검색으로 출처를 확인해 적는다. 장부를 바꾸기 전에는 사본을 남긴다.

분류는 세 층이다(`graph/programs.py` apply_reviews). 규칙(폴더 경로·제목·본문 앞부분의 장부 이름)이 먼저 정하고, 규칙이 못 정한 폴더는 폴더
단위 판정을 받으며, 파일 단위 판정이 있으면 그것이 가장 앞선다. 파일 단위 판정은 27B 가 한다(scripts/196). 코드는 다시 볼 후보만 고른다 —
장부 사업 이름이 제목·본문에 나오는데 「사업 아님」으로 간 원본, 사업 이름이 아닌 묶음에 든 원본. 27B 는 제목·폴더·본문 1,500자와 장부
사업 목록을 보고 장부의 이름, 「사업 아님」, 「모름」 가운데 하나를 근거 한 문장과 함께 고른다. 장부에 없는 이름, 「모름」, 확신 낮음은 적지 않는다.

결과(10-18 운영). 사업 장부 96개(교내 엑셀에 있는 66개, 공개 출처로 확인한 옛 사업 등 30개), 그래프 사업 노드 136개. 파일 단위 재판정
1,034건 가운데 사업으로 옮김 734, 그대로 259, 버림 34, 실패 7(실험 로그 18절). 사업 미분류 경고는 108 에서 16 으로 줄었다(dev-now).
재판정의 정확도는 표본 대조를 하지 않아 미측정이다.

### 2.8 판본·중복 묶기

무엇을. 해마다 조금씩 다른 판으로 들어오는 같은 서식·규정, 이름만 다른 같은 파일을 묶는다.

왜. 바이트 해시로는 한 글자만 달라도 다른 파일이 된다. 묶지 않으면 검색 상위가 같은 문서의 판들로 채워지고, 옛 판 조문이 근거로 인용된다.

어떻게(`app/doc_family.py`, `app/grant_search.py`). 제목에서 붙임 번호·괄호·공백을 뗀 열쇠로 묶음 후보를 찾고, 본문을 8자 조각 집합으로 견준다.
겹침 0.95 이상이면 같은 내용으로 보고 받지 않으며, 그 아래면 판본으로 잇는다(가장 가까운 실제 판본 쌍이 0.90 이라 오판하지 않는다, 실험 로그
8절). 검색 때는 같은 묶음에서 개정일, 없으면 원본 수정 시각이 가장 늦은 판만 남기고, 옛 판 조각이 걸리면 최신 판의 같은 글로 바꾼다
(`_newest_in_family`, `_promote_revisions`). 옛 판은 지우지 않아 연도를 지정한 질문에는 쓰인다.

### 2.9 쓸모없는 문서 정리

무엇을. 검색·그래프에 잡음만 더하는 문서(지출·계약 증빙, 같은 본문 중복, 빈 문서, 도면, 개인 제출물)를 라이브러리에서 정리한다.

어떻게(scripts/187, `app/archive_cleanup.py`). 기준은 판정된 갈래(증빙·도면·개인 제출물), 같은 사업 안 본문 지문 일치(사본·백업 경로가 아닌
최신 것을 남김), 본문 100자 미만(양식 제외)이다. 지우기 전에 문서 행과 딸린 조각·그림·색인·연결을 모두 백업 파일에 남기고, 원본은 지우지 않고
원본 보관소의 정리함으로 옮긴다. 되돌리기를 하면 문서를 되살리고 벡터를 다시 만든다. 학교 원본에서 새로 들어오는 증빙은 동기화 때마다
정리함으로 옮긴다.

결과(10-18 운영). 정리 697건 — 증빙 304, 중복 32, 빈 문서 9, 도면 31, 개인 제출물 321. 백업 있음.

### 2.10 문서 이름

파일 이름(「최종_수정본(2).hwp」) 대신 본문 제목으로 이름을 정한다(`app/doc_naming.py`). 순서는 공문의 「제목:」 줄, 본문 제목 줄, 모델이 짚은
본문 제목 줄(본문에 있는 줄만 받음), 군더더기를 걷은 파일 이름, 「갈래 · 사업 연도」 꼴이다. 본문 제목이 파일 이름의 연도·차수·기관 같은 구별
정보를 잃으면 쓰지 않는다. 사람 이름은 제목에서 뺀다. 이름은 질문에 문서 이름을 넣었을 때 그 문서로 좁히는 데에도 쓰인다(3.6).

## 3. 검색과 지식

검색은 두 색인과 하나의 그래프로 이뤄진다. 규정 색인은 교내 규정·지침을 조문 단위로, 사업 문서 색인은 사업 문서 조각을 담는다. 문서 계열을
하나의 색인으로 합치지 않는 것은 규정 질문에 사업 문서 조각이, 사업 질문에 규정이 섞이지 않게 하려는 것이다. 지식그래프는 사업 > 연차 > 문서 > 절
구조로 검색 범위를 좁힌다.

### 3.1 임베딩 — ZZAIMY-Embed v2

무엇을. 질문과 조각을 같은 벡터 공간(1,024차원)에 놓아 낱말이 달라도 뜻이 가까우면 찾게 한다.

왜 학습했나. 공개 한국어 임베딩 KURE-v1 은 일반 문장에는 좋지만 「교원업적평가」「차년도 사업비 이월」 같은 교내 용어와 규정 문체에는 약했다.

어떻게(scripts/108). 규정 조각마다 27B 로 합성 질의를 세 꼴(실무형, 공고 요구사항형, 키워드형)로 만들고, 문서 단위로 20%를 홀드아웃으로 뗐다.
어려운 오답은 운영 하이브리드가 실제로 올린 후보 상위 20 가운데 정답이 아닌 조각 최대 6개다. 손실은 배치 안 오답과 어려운 오답을 함께 쓰는
대조학습(InfoNCE, 온도 0.05), 2에폭, 서빙 장비 GPU 에서 약 20분이다. 채택 기준은 단독 지표가 아니라 운영 하이브리드 위에서 후보 진입률이 오르는지다.
v1 은 단독 지표만 오르고 운영 경로에서 이득이 없어 버렸고 v2 를 채택했다(ADR-0021).

서빙. 서빙 장비 2 의 임베딩 서비스가 색인과 질의를 같은 모델로 만든다. 색인과 질의의 모델이 다르면 공간이 어긋나므로 색인에 모델 이름을 적고
대조한다. 교내망 보안 장비가 긴 숫자열이 든 요청을 끊어서 9자리 이상 숫자열은 가린 뒤 보낸다(`embed_search.transport_mask`). 서비스가 응답하지
않으면 규정 검색은 운영 서버 CPU 모델로, 사업 문서 검색은 어휘 축만으로 물러난다.

결과. 규정 검색(합성 질의 1,026건, 9-21) 임베딩 단독 R@1 0.691, 어휘 0.430(실험 로그 5절). 공개 KURE-v2(다중 벡터)는 학습 전인데도 근접했지만
운영 경로에서 이득이 없어 채택하지 않았다(ADR-0025).

### 3.2 리랭커 — ZZAIMY-Rerank v1

무엇을. 검색이 올린 후보 20개를 질문과 한 쌍씩 읽어 다시 줄 세운다(교차 인코더, bge-reranker-v2-m3 기반).

어떻게(scripts/104). 운영 하이브리드가 실제로 올린 후보 목록 전체에 대해 정답 쪽 확률을 높이는 목록 단위 학습을 했다. 서빙 장비 GPU 로 옮겨
질의당 3.75초에서 0.07초가 됐고, 그 덕에 후보를 10개에서 20개로 늘렸다. 1위 점수의 0.25배 아래 꼬리는 근거에서 뺀다.

어디에 쓰나. 규정 검색에만 쓴다. 사업 문서 검색에서는 그래프 절 축·문서당 2개 규칙과 겹쳐 오히려 손해라 꺼 두었다(dev-now 10-05, 코드 기본 꺼짐).

결과. 문서 단위 홀드아웃 12건에서 R@1 0.649 → 0.711, MRR 0.751 → 0.790(ADR-0020). 규정 검색 운영 구성(하이브리드 + 리랭커) R@1 0.763(9-21),
학습 문서를 뺀 질의 22,084건 재측정에서 리랭커 뒤 R@1 0.707(실험 로그 10절). 생성 모델로 후보를 다시 매기는 방식은 덜 정확하고 53배 느려 쓰지 않는다.

### 3.3 하이브리드 검색

무엇을. 어휘 검색(낱말이 그대로 겹치는 조각)과 의미 검색(뜻이 가까운 조각)을 섞는다.

왜. 행정 질문에는 사업 약칭·규정 이름·숫자처럼 글자 그대로 맞아야 하는 말과, 「학생이 휴학하려면」처럼 뜻으로 찾아야 하는 말이 함께 있다.
한 축만으로는 어느 한쪽을 놓친다.

어떻게.

- 어휘 축: Kiwi 형태소 분석으로 명사와 두 글자 이상 영문 약칭을 뽑고, 띄어 쓴 복합 명사를 붙이며, 드문 낱말에 무게를 주는 IDF 로 점수를 낸다.
  색인과 질의가 같은 낱말 함수를 쓴다(`app/grant_lex.py` lex_terms). 사업 문서 쪽은 낱말을 미리 뽑아 PostgreSQL 전문 색인(GIN)에 둔다.
- 의미 축: 사업 문서 조각 벡터는 PostgreSQL pgvector 의 HNSW 색인(halfvec 1,024차원)에 있다(ADR-0057). 권한·부서·갈래 조건을 같은 SQL 에서 건다.
- 섞기: 두 축의 순위를 RRF(k=60)로 섞는다. 어휘 가중 0.4, 의미 1.0 이다. 가중 0.2~0.5 가 고원이었고, 학습 문서를 뺀 질의로 다시 재도 후보 진입률이
  가중 0~0.6 에서 같아 0.4 를 유지했다(실험 로그 1·10절). 사업 문서 쪽은 어휘 1위 조각이 섞은 순위에서 밀리지 않게 지킨다.
- 뒤처리(사업 문서): 판본 최종본만 남기기, 문서당 조각 2개, 상위 5개. 규정 검색과 사업 문서 검색은 서로 기대지 않으므로 동시에 돌린다.

결과. pgvector 로 옮기자 같은 고정 질문 80문에서 정답 문서 적중 0.688 → 0.675(80문 중 1문 차), 검색 시간 3.49 → 1.85초, 운영 서버 메모리에서
5GB 넘는 배열이 빠졌다. 근사 검색이라 정확 계산 대비 recall@10 0.915(ADR-0057). 사업 문서 벡터 1,586,051개(10-18 운영).

### 3.5 온톨로지

무엇을. 검색이 「무엇을 찾을지」를 알 수 있도록 행정 문서 세계의 개념과 관계를 정해 둔다.

왜. 문서가 수만 건이면 「LINC 3.0 2차년도 실적보고서의 취업 성과」 같은 질문을 조각 유사도만으로는 풀기 어렵다. 사업·연차·갈래를 먼저 좁히고
그 안에서 찾아야 한다. 또 「계획 대비 실적」「앞 단계 사업」처럼 문서 사이 관계를 묻는 질문은 관계가 데이터로 있어야 답할 수 있다(ADR-0047).

어떻게. 노드 종류는 여덟이다 — 사업 묶음, 사업, 기관, 연차, 문서, 절, 단위과제, 성과지표. 문서는 서류 갈래를 하위 분류로 갖고, 어느 사업에도
속하지 않는 기관 업무 문서는 따로 둔다(ADR-0048·0055). 관계는 포함(contains), 계획↔실적(plans_reports), 평가함(evaluates), 앞·뒤 단계(succeeded_by),
편입(integrated_into), 연관(related), 주관 부처·전담기관(supervised_by·managed_by), 성과지표 측정 등이다.

관계마다 기준과 근거를 단다. 기준은 다섯 가지(구조, 분류, 식별자 일치, 추출, 유사도) 가운데 하나이고, 근거는 문서·절 위치나 외부 출처 URL 이다.
근거를 댈 수 없는 관계는 만들지 않는다. 사업 사이 관계와 기관은 외부 확인 장부에서만 가져온다.

표준 층으로 온톨로지 설계도를 OWL·RDF(rdflib)로 내보내고 SHACL(pySHACL) 규칙으로 검사한다(ADR-0056, `graph/shapes.ttl`). 규칙은 「연차는 사업 하나에만
속하고 연도는 1990~2035」, 「문서의 갈래는 하나까지이고 사업·연차에 속하거나 기관 업무 문서」, 「관계는 기준 다섯 중 하나에 근거 하나 이상」 등이다.
그래프를 다시 지을 때마다 검사가 돈다. 설계도는 그래프 탐색 화면에서 내려받아 Protégé 같은 도구로 열 수 있다.

결과. SHACL 위반 0(10-09 측정 c14~c15, dev-now). 사업 미분류 경고 6,899 → 141(10-09) → 16(dev-now 진행 중인 일).

### 3.6 지식그래프

무엇을. 온톨로지대로 실제 문서를 이은 그래프다.

어떻게(scripts/157, `graph/programs.py`·`sections.py`·`units.py`, 저장 `graph/kg_store.py`). 그래프는 요청 때마다 만들지 않고 PostgreSQL 의 노드 표
(`kg_nodes`)와 관계 표(`kg_edges`)에 둔다. 문서·조각이 바뀌면 최대 15분에 한 번, 갈래만 바뀌면 최대 한 시간에 한 번 다시 짓는다.

- 사업 → 연차 → 문서: 2.7 의 사업 분류와 문서 연도·차수로 잇는다. 연차를 모르는 문서는 연차에 넣지 않는다.
- 문서 → 절: 처리본의 제목 경로로 절 트리를 만든다. 같은 사업 안에서 같은 제목 절이 되풀이되는 묶음은 단위과제 노드로 묶는다.
- 계획↔실적: 같은 사업·연차의 계획서와 실적보고서를 잇고, 절끼리는 제목 맥락과 본문 유사도로 짝짓는다. 「차년도 계획」 절은 빼고, 연차가
  맞지 않으면 잇지 않는다.
- 사업 사이: 외부 확인 장부의 앞뒤 단계·편입·묶음. 「연관」만 같은 문서가 함께 다룬 비율로 만든다.

결과. 노드 415,834개, 관계 583,557개, 사업 노드 136개(10-18 운영). 짝 판정 정밀도 95~96%, 놓친 비율 0%(dev-now).

### 3.7 GraphRAG — 27B 가 질문을 읽고 그래프를 따라 찾기

무엇을. 질문을 온톨로지의 말(사업, 연도, 차수, 갈래, 관계)로 읽어 그래프에서 범위를 정한 뒤, 그 안에서만 하이브리드 검색을 한다.

왜. 처음에는 사업 이름 맞추기와 「N차년도」·갈래 낱말 정규식으로 질문을 읽었다. 이 방식은 「계획 대비 실적」을 계획 갈래로만 보고, 앞 단계 사업을
물어도 질문에 적힌 사업만 봤다. 질문 꼴마다 정규식을 덧대는 대신 질문의 뜻은 모델이 읽고, 그래프 탐색은 코드가 결정적으로 하게 했다(ADR-0063).

어떻게.

1. 질문 읽기(`graph/question_read.py`): 27B 에게 질문, 질문과 겹치는 사업 후보 목록(번호), 관계 7종을 주고 형식이 강제된 JSON 을 받는다 — 사업 번호,
   연도, 차수, 갈래(계획·실적·평가), 따라갈 관계. 사업은 목록에 있는 것만 받는다(지어낸 사업 이름 차단). 온도 0, 출력 120토큰, 같은 질문은 10분 기억한다.
2. 범위 정하기(`graph/retrieve.py` scope): 이름 맞추기를 먼저 하고 모델 읽기로 관계·둘째 사업·빈 연도와 갈래를 보탠다. 연도를 물으면 연도를 모르는 문서는
   뺀다. 관계를 따라 범위를 넓힌다(계획↔실적 짝, 평가 문서, 앞·뒤 단계, 편입 사업). 질문에 「」로 묶어 적은 이름이 그 사업의 문서 이름이면 그 문서로
   좁히고, 절 제목이면 그 절로 좁힌다(실험 로그 13절).
3. 찾기(`app/grant_search.py`): 범위 안에서 그래프 절 축(묶어 적은 절 제목과 같은 절의 조각)을 앞에 두고, 어휘·의미 축을 RRF 로 섞는다. 관계를 물은
   질문은 관계 양쪽 문서에서 한 조각씩 근거에 담는다. 그래프 절 축 조각도 열람 권한을 다시 거른다.
4. 모델 읽기에 실패하면 이름 맞추기로 물러난다. 운영에서는 켜 두었다(dev-now).

결과(실험 로그 9절, 10-14). 같은 시험지에서 절 질문 정답 문서 상위 5 비율 풀텍스트 RAG 18% → 그래프(이름 맞추기) 64% → 27B 읽기 70%. 관계 질문은
13% · 9% · 45% 로 27B 읽기가 있어야 풀텍스트를 넘는다. 답 근거에 정답 문서 31% · 53% · 75%. 이어 계획↔실적 짝 담기를 고쳐 관계 질문 전체
46.7% → 58.7%(9.1절). 지금 기준(시험지 v2, 136문)은 정답 문서@k 0.89, 같은 판 0.993, 같은 사업 1.0(8절).

### 3.8 열람 범위 — 권한별 RAG 공간

무엇을. 누가 묻느냐에 따라 검색 후보 자체를 다르게 한다.

왜. 답을 만든 뒤에 거르면 모델이 이미 남의 부서 자료를 읽은 뒤다. 그래서 권한은 검색 단계의 SQL 조건으로 건다.

어떻게.

- 문서마다 부서와 열람 등급(전체 공개·부서 제한·담당자 한정)을 반입 때 붙인다. 판정 규칙은 `app/access_policy.py` 한 곳(visible, 같은 뜻의 SQL 조건
  doc_sql, 보는 사람 viewer)에 두고, 라이브러리·폴더·문서 화면·검색·지식그래프·원본 장부·채팅 근거가 모두 이것을 쓴다(노트 2026-10-15-access-control).
- RAG 공간은 색인을 복제하지 않고 같은 색인 위의 검색 조건으로 얹는다(ADR-0053). 학생 공간은 학생 공개로 지정한 학사 규정만, 부서 공간은 그 부서와 공통
  사업 문서, 관리자는 전부다. 계정마다 다른 부서 자료를 더 열어 줄 수 있다.
- 질문이 범위 밖 부서를 가리키면 답 머리에 「그 부서 자료는 열람 권한이 없다」고 알리고 감사 기록에 남긴다. 안내에는 부서 이름만 싣고, 그 부서 문서의
  제목·건수·있고 없음은 말하지 않는다.
- 모르는 역할은 가장 좁은 학생 범위로 본다. 다섯 합성 계정으로 화면 판정과 SQL 판정, 채팅 근거가 어긋나지 않는지 테스트가 본다
  (`tests/test_access_matrix.py`).

### 4.2 Writer 27B 서빙

어떻게. vLLM 으로 서빙 장비 두 대에 같은 판을 띄운다(문맥 16,384 토큰). 원본 bf16 은 요청 하나에 초당 2~5 토큰이라 실사용이 어려웠고, NVFP4 양자화
판으로 바꾸자 초당 10.4~10.9 토큰, 판독 5쪽 128초 → 29초, 내용은 같았다(ADR-0023). 이어 모델 안에 든 다음 토큰 예측 층(MTP)으로 추측 디코딩을 켰다.
작은 층이 토큰 두 개를 미리 짐작하고 본 모델이 검증해 받아들이므로 출력은 그대로이고 맞힌 만큼 빨라진다. 생성 속도는 10.6 → 23.8 토큰/초(검토 쪽),
약 12 → 24.6 토큰/초(답 쪽)가 됐다(실험 로그 16절).

생각 모드. Qwen 계열은 답 전에 혼자 따져 보는 출력(생각 모드)이 기본으로 켜져 있다. 끄지 않은 호출이 출력 한도를 생각에 다 써 값 없이 실패한 일이 있어
(정체 읽기 713건 값 0), 클라이언트가 교내 호출의 생각 모드를 기본으로 끈다. 답 쓰기에서 켜 본 비교는 7배 느리고 채점이 나빠져(나빠짐 12 · 나아짐 0) 끈 채
둔다(실험 로그 12절).

### 4.3 연결 설정과 모델 교체 대비

무엇을. 모델 호출은 「용도」로 한다 — 답(answer), 반입 검토(review), 이미지 판독(vision), 업무 도우미(helper). 용도마다 어느 서버의 어느 모델을 쓸지는
개발 화면의 연결 설정에서 정한다(`generate/llm_connections.py`).

왜. 실제 도입 때는 더 큰 모델이나 파인튜닝한 판으로 바뀐다. 모델 이름, 문맥 길이, 생각 끄기 인자를 코드에 박아 두면 교체가 코드 수정이 된다.

어떻게(노트 2026-10-15-model-swap).

- 문맥 한도는 서버가 알려 주는 값(`/v1/models` 의 max_model_len)을 먼저 쓰고, 없을 때만 설정값을 쓴다.
- 생각 끄기·켜기 인자, 구조화 출력 방식은 연결마다 설정으로 둔다. 서버가 JSON 스키마 강제를 거절하면 JSON 지시 + 파싱으로 물러난다.
- 지정 서버가 응답하지 않으면 같은 모델을 내는 다른 교내 연결로 넘긴다. 외부로는 넘기지 않는다.
- 모델이 만든 결과(갈래 판정, 에이전트 걸음, 절 작성, 질문 읽기 등)에는 서버가 알려 주는 실제 모델 정보를 남긴다. 서버 주소와 가중치 경로는 남기지 않는다.
- 교체 점검 스크립트(scripts/195)가 후보 모델을 운영 설정을 바꾸지 않고 같은 데이터 상태에서 운영 모델과 나란히 잰다(검색·답·갈래 판정). 채택은 이 표로 한다.

### 4.4 답 흐름

대화 화면에서 질문 하나가 답이 되기까지는 다음 순서다(`app/main.py` → `app/responder.py`).

1. 입력 정리: 전각 문자를 반각으로 바꾼다.
2. 권한 점검(`app/access_guard.py`): 특정인의 개인정보를 묻는 질문은 모델을 부르지 않고 막는다. 지시를 바꾸려는 꼴의 질문과 범위 밖 부서 질문은 감사 기록에
   남긴다. 이 계정의 RAG 공간으로 검색 범위를 정한다.
3. 문서 작업 에이전트가 먼저 받아 도구를 고른다(4.5). 모델에 닿지 못했을 때만 낱말 규칙 경로로 물러난다.
4. 검색: 규정 검색과 사업 문서 검색(질문 읽기 + 그래프 범위 + 하이브리드)을 동시에 돌린다. 프로젝트 대화면 그 프로젝트에 올린 문서가 먼저 온다.
5. 근거 묶기: 교내 규정 묶음, 사업 문서 묶음을 따로 표시해 건넨다. 규정 근거가 약하고 사업 문서 근거가 있으면 규정 묶음은 뺀다. 근거가 없거나 약하면 그렇다고
   알리는 안내를 붙인다.
6. 문맥 맞추기(`app/llm_budget.py`): 첨부 → 오래된 대화 → 출력 상한 → 검색 근거 순으로 줄여 문맥 한도에 맞춘다. 다 줄여도 넘으면 보내지 않는다.
7. 생성: 답 꼴 지시는 「첫머리 1~3문장 답, 근거 요점 5개 이내, 표·문단 옮겨 적지 않기, 600자 안팎」이다. 원문은 출처 패널이 보인다. 화면에 흘려 보이고,
   출력 한도에서 끊기면 한 번 이어 쓴다.
8. 근거 밖 숫자 표시(4.7): 답의 숫자 가운데 모델에 실제로 건넨 근거에 없는 것에 「(근거 확인 필요)」를 붙이고 끝에 안내한다.
9. 출처: 화면의 출처는 모델에 실제로 건넨 근거 목록에서만 만든다. 출처를 누르면 오른쪽 패널에서 그 대목을 연다.
10. 기록: 답마다 실행 기록(answer_runs)과 담당자의 도움됨·아쉬움 평가를 남긴다.

답 모드는 셋이다(ADR-0038). 기본은 위의 문서 근거 답이다. 외부 검색 모드는 질문 글만 웹 검색에 보내고(구글·네이버 검색 키가 있으면 그것, 없으면 DuckDuckGo)
가져온 쪽 글을 근거로 27B 가 출처 번호를 달아 답한다. 질문에 개인정보가 있으면 보내지 않는다. 27B 자체 답 모드는 검색 없이 모델 지식으로만 답하고
출처 없음을 밝힌다. 학생 계정은 기본 모드만 쓴다.

결과(기준 v2, 10-17). 답 30문에서 오류·빈 답 0, 표시 안 된 근거 밖 숫자 0, 근거에 정답 문서 0.9, 답 전체 시간 중앙값 16.6초(처음 기준 134초).

### 4.5 문서 작업 에이전트

무엇을. 대화 화면의 요청(「작년 실적보고서 참고해서 추진 배경 절 써 줘」, 「이 표 채워 줘」, 「한글 파일로 내보내 줘」)을 처리하는 에이전트다
(`app/doc_agent.py`).

왜. 요청 글을 낱말 규칙으로 해석하면 꼴이 조금만 달라도 틀린 일을 한다. 무엇을 할지는 모델이 판단하고, 코드는 판단을 안전하게 실행하는 쪽이 낫다.

어떻게. 27B 가 매 걸음 상태(요청, 최근 대화, 프로젝트 문서 목록, 작업본의 절 목록과 빈 절, 받지 못한 값, 지금까지 한 걸음)를 보고
`{생각, 도구, 인자}` 를 고른다. 도구는 17가지다 — 근거 찾기(프로젝트·라이브러리·기준 문서·규정), 찾은 문서 이어 읽기, 절 읽기, 문서 만들기, 프로젝트 문서 열기,
문서 읽기, 값 기억, 자료로 값 채우기, 절 쓰기·다시 쓰기, 검토, 편집, 안내 상자 지우기, 한글 내보내기, 작업본 새로 만들기, 답하기, 묻기, 마무리.
코드는 고른 인자로 해당 함수를 바로 부른다.

코드가 지키는 관문은 다음과 같다.

- 걸음은 14번, 문서 쓰기는 4번까지. 같은 걸음이 세 번 잇달으면 멈춘다. 한도에 닿았는데 찾은 근거가 있으면 답하기만 고를 수 있는 마지막 걸음을 준다.
- 되돌리기 어려운 도구(편집, 다시 쓰기, 한글 내보내기, 작업본 새로 만들기)는 담당자 요청 글에 그 뜻이 부정 없이 있을 때만 돈다. 모델이 낸 인자로 이 관문을
  건너뛸 수 없다.
- 상태·도구 결과는 자료 울타리 안에만 넣고, 자료 속 울타리 기호는 전각으로 바꿔 문서 속 글이 지시를 흉내 내지 못하게 한다.
- 열람 범위, 수치 근거 대조, 양식 모양은 코드가 지킨다.
- 낱말 규칙 경로로 물러나는 것은 모델에 닿지 못했거나 형식 오류가 두 번 났을 때뿐이다.

절을 쓰기 전에 27B 가 필요한 정보와 찾을 곳·검색어를 정하고 코드가 찾아 준다(`app/context_plan.py`). 양식은 프로젝트의 작성 서식, 대화에서 정한 목차,
공통 양식 5종 가운데 27B 가 고른다(`app/form_choice.py`, ADR-0060). 절 작성은 구글 독스 작업본에 편집 계획(JSON 스키마 강제: 넣기·바꾸기·표·칸 채우기·도식 등)으로
적용하고, 근거에 없는 숫자는 ○○ 로 가린다. 받지 못한 값은 사실(자료에서 찾을 값)과 결정(담당자가 정할 값)으로 나누고, 사실 값은 프로젝트 문서에 글자 그대로
있을 때만 출처와 함께 확인 전 제안으로 보인다. 절을 못 채운 까닭(담당자 문서 필요, 재료 없음, 재료 불일치, 일부만)은 기록에 남겨 다음 안내와 학습 재료로 쓴다.
걸음 기록(doc_agent_episodes)은 컨텍스트 구성 리즈닝 학습의 재료다.

### 4.6 업무 도우미

무엇을. 채팅 화면 밖 모든 화면의 오른쪽 아래에 떠 있는 창이다. 플랫폼 사용법을 안내하고 화면에서 하는 일(학생 공개 지정, 규정 후보 등록, 부서 만들기,
프로젝트 만들고 첫 요청 보내기, 에이전트 대화로 넘기기)을 대신 제안한다(`app/platform_helper.py`, 노트 platform-helper).

어떻게. 에이전트와 같은 걸음 구조(걸음 8번까지)에 도구만 다르다 — 화면 안내 찾기, 내 대상 목록 보기, 동작 제안, 화면 열기, 마무리. 동작은 바로 실행하지 않고
[실행] 단추로 제안하며, 누르면 서버가 대화 주인·계정 역할·대상을 다시 확인한 뒤 화면 단추와 같은 함수로 실행한다. 두 번 눌러도 한 번만 돈다. 화면 위
커서가 같은 일을 하는 화면 요소를 가리켜 보인다. 화면 안내 자료는 화면마다 한 항목이고, 적어 둔 단추 이름·자리가 템플릿에 실제로 있는지 테스트가 확인한다.
사업 문서 내용 질문은 에이전트 대화로 넘긴다.

### 4.7 수치 검증기

무엇을. 모델이 쓴 숫자가 근거에 있는지 기계적으로 대조한다(`verify/numbers.py`). 모델에게 판단을 맡기지 않는다.

어떻게. 답과 근거에서 숫자를 뽑아 표면형(쉼표 제거)과 정준값(조·억·만·천 단위 환산, 「3억 5천만」 합산, 「1만 1799명」 → 11,799)으로 함께 견준다. 목록 번호,
연도, 전화·날짜·코드 꼴, 단위 없는 10 이하 숫자는 대조에서 뺀다. 답에는 「300명(근거 확인 필요)」처럼 표시하고, 문서 편집에서는 「○○명」으로 가린다.
같은 금액을 단위만 바꿔 쓴 값도 같은 값으로 본다(ADR-0068) — 숫자 바로 뒤 괄호의 금액 단위(「500(백만원)」)나 글의 「(단위: 백만원)」 선언을 읽어
환산하므로 5억 = 500,000,000원 = 500백만원 = 백만원 단위 표의 500 이다. 우회를 막으려고 환산은 금액끼리만, 같은 덩이에서 가장 가까운 단위 선언 하나만 쓰고,
셈 단위(명·건·% 등)가 붙은 숫자와 표 칸 밖 숫자에는 쪽 단위 선언을 적용하지 않는다. 정말 없는 값(700(백만원), 4,500명)은 그대로 잡는다.
학습 데이터 정제도 같은 함수를 써서 학습과 서빙이 같은 기준으로 숫자를 판정한다. 배점 반영 점검(`verify/coverage.py`)은 항목별 최고 문단 유사도가 평균보다 0.10
이상 높고 0.40 이상일 때 반영으로 보고, 예산 검산(`verify/budget.py`)은 정수 원 단위로 단가×수량을 다시 계산한다. 예산 계산에는 모델을 쓰지 않는다.

결과. 근거 밖 숫자가 있는 답 2/10 → 0/10(실험 로그 15절). 배점 반영 판정은 합성 표본에서 키워드만 0/55 → 45/55(ADR-0015).

### 4.7a 대화 기억·단계 추론·서브 에이전트(ADR-0065)

무엇을. 긴 대화에서도 담당자가 알려 준 값·정한 방향을 잃지 않고(작업 메모), 답 앞에 짧게 단계별로 생각하며(CoT), 긴 문서는 필요할 때만 일을 나눠 맡긴다(서브 에이전트).

왜. 요청마다 최근 대화 몇 개만 넣으면 그 밖의 대화가 사라진다. 모델마다 문맥 한도가 달라(지금 16,384 토큰, 도입 때 더 큰 모델) 개수로 자르는 방식은 맞지 않는다.
한 문맥에서 대화·검색·단계 기록·긴 본문을 다 다루면 절 41개 서식은 한 요청에 17절에서 멈췄다.

어떻게.
- 작업 메모(`app/chat_memory.py`): 답이 끝나면 배경에서 「앞 메모 + 그 뒤 대화 → 새 메모」 — 지금 목표/확정된 것/진행 상황/남은 일·물어볼 것. 요청에는 메모 + 최근 대화
  원문(문맥 한도의 30%), 메모 상한은 한도의 6%. 비율이라 모델을 바꾸면 저절로 맞는다.
- 단계 추론: [1단계: 질문 파악] → [2단계: 근거 확인] → [3단계: 답 구성] → [답]. 학습 데이터(구조 단계 문답)와 같은 꼴. 화면엔 답만, 추론은 「생각 과정」 으로 펼쳐 본다.
- 서브 에이전트(제안): 같은 27B 를 다른 역할·깨끗한 문맥으로 한 번 더 부르는 것. 기본은 메인이 CoT 로 직접 처리하고, 빈 절이 많거나 절 하나가 길거나 남은 문맥이
  모자랄 때만 메인이 지시서를 써서 「절 맡기기」. 맡길지는 에이전트가 판단하고 코드는 관문만 둔다. 서브는 동시에 돌 수 있어 시간도 준다.
- 핵심 위험은 문맥 누락(서브가 지시서에 없는 것을 모름)과 문맥 관리(여러 서브 결과를 메모·개요에 맞게 유지) — 지시서 필수 항목, 「확인 필요」 반환, 짧은 보고를
  메모에 접기, 끝에 전체 정비로 막고 일관성 지표로 잰다.

결과. 실제 27B 3턴(임시 DB): 첫 질문 「AI 교육 쪽으로 뭔가 사업」 → 메모의 지금 목표 「2027년 1학년 대상 AI 교육 사업계획서 작성 및 목차 구성」, 확정된 것에 대상·예산
5천만원·기간 원문 그대로. 답에 단계 글 섞임 0, 가장 큰 호출 5,400~7,900/16,384 토큰.

서브 맡기기 구현과 비교(ADR-0065 결과 절). 한글 기안기 경로의 도구 delegate_section — 메인은 절 이름·요지·형식·분량만, 지시서의 필수 항목(메모 목표·확정 값, 문서 개요,
앞 절 요지, 담당자 원문 인용)은 코드가 채우고, 서브는 그 절의 작성방법·압축한 근거만 보고 쓰며 모르는 값은 「확인 필요」 로 돌려준다. 쓰기는 메인과 같은 관문(예시 글자,
근거에 없는 수치, 길이)을 지난다. 근거는 문장 단위로 ZZAIMY-Rerank 압축(숫자·날짜·고유명사 문장 우선, 리랭커가 없으면 원문). 실제 27B(한도 16,384)·임시 DB 실측:
- 실서식 사업계획서(절 47): 항상 직접(off) 두 번 모두 절 0/47(큰 칸 5개만 쓰거나 같은 찾기를 되풀이하다 멈춤, 가장 큰 호출 16,277~16,342). 필요할 때 맡기기(auto) 1차는
  22번 맡겨 절 21/47, 지어낸 숫자 0, 앞뒤 절 어긋남 0, 확인 필요 36건, 서브 근거 123,182→80,985 토큰(−34%), 735초. auto 2차는 한 번만 맡겨 1/47(155초).
- 공통 양식 사업계획서(절 36, 가상 사업 개요): auto 2차는 11번 맡겨 절 20/36·표 19·도식 1, off 2·3차는 형식 오류로 0~1/36(3차는 큰 칸 19곳). auto 3차는 맡기지 않고 2/36.
- 짧은 문서(예산 변경·기안문·출장 보고)는 auto 에서도 맡기지 않았고 결과가 off 와 같았다.
맡긴 판은 긴 서식을 끝까지 쓰는 쪽으로 크게 나아지지만, 맡길지 고르는 판단이 판마다 흔들려 평균 효과는 표본을 더 모아야 말할 수 있다. 시간은 맡긴 판이 3~4배다.

### 4.7b 양식 만들기와 여러 턴 시나리오 평가(ADR-0067)

무엇을. 문서함·공통 양식·공고 서식 가운데 목적에 맞는 양식이 없으면 Writer(27B)가 양식부터 설계하고, 코드는 공통 양식과 같은 빌더로 한글(hwpx) 작업본을 만든다.
그리고 두루뭉술한 시작부터 디자인 바꾸기까지 이어지는 대화를 한 묶음으로 잰다.

어떻게.
- 설계는 깨끗한 문맥의 같은 모델이 JSON 으로 낸다(제목·표지·요약 표 칸·절 단계와 제목·작성방법·분량·표 열 머리와 표 갈래·도식 자리). 재료는 작업 메모의 목표·확정 값,
  담당자 인용, 공고의 작성·평가 항목, 목적이 비슷한 실물 양식 2~3개의 구조(절 제목·표 머리·안내 요지·칸 라벨 — 값은 넣지 않음), 실물 양식에서 갈래별로 센 흔한 절(입력 지문이
  바뀌면 다시 만드는 파생 결과물). 설계 뒤 점검표로 한 번 자기 검토한다.
- 코드는 관문(빈 제목·절 0개·중복·단계 건너뛰기·긴 안내·안내 글 꼴 제목·칸 라벨 꼴)을 두고, 번호를 학교 서식 꼴(1. → 가. → 1))로 매기고, 위 절의 쓸 자리를 빼고,
  자가 점검을 지난 파일만 작업본으로 연다. 모델 이름·문맥 길이는 쓰지 않고 몫은 문맥 한도 비율로 정한다.
- 평가(scripts/202): 임시 DB·실제 27B 로 11턴(시작 → 대상·예산 → 기간·양식 → 절 쓰기 → 계속 → 고쳐 쓰기 둘 → 디자인 넷), 문서함에 양식이 있는 판과 없는 판.
  디자인 반영은 작업본 XML 값(방향·여백·머리줄 음영·쪽 번호)을 요청 전 값과 견줘 센다. 글 품질은 review 연결 27B 가 기준표로 채점(같은 모델의 자기 평가 한계 — 판·회차 비교용).
  양식 만들기 묶음은 목적 여덟 가지 × 「참고 없음 / 참고 / 참고+검토」 직접 설계와 에이전트 대화 한 턴.

### 4.7c 고쳐 쓰기·개요·자기 점검(ADR-0068)

무엇을. 4.7b 시나리오에서 남은 약점 — 고쳐 쓰기 반영 1/6, 작업 메모 목표 흔들림, 채점 구체성 2.3~3.7·근거 2.0~3.0, 긴 서식에서 차례로만 맡겨 31~39분,
단위만 바꾼 값을 지어낸 숫자로 잡음 — 을 사례 규칙 없이 일반 메커니즘으로 고친다. 판단은 27B, 코드는 도구·관문·기록이라는 원칙(4.5)은 그대로다.

어떻게.
- 고쳐 쓰기 도구 hwp_revise(`app/delegate.Reviser`): 서브 호출 둘. 첫째는 지시의 뜻을 점검표 JSON(의도·길이 늘림/줄임/그대로·표·도식·더할 항목·뺄 항목·문체·검색어 0~3)으로,
  둘째는 지금 글·지시·점검표·그 절의 작성방법·점검표 검색어로 찾은 근거를 깨끗한 문맥으로 주고 절 전체를 다시 받는다. 코드는 셀 수 있는 것만 본다 — 바뀌었나,
  길이 방향(늘림 1.15배·줄임 0.9배), 표·도식 유무, 더할 항목 낱말, 본문 관문. 어기면 까닭을 붙여 한 번 다시 청한다.
- 서브 절 쓰기: 서브가 검색어 2~3개를 먼저 내고 코드가 절 제목+요지와 그 검색어마다 찾아 번호·쪽을 붙인 근거로 모은다. 같은 호출 안에서 [개요] → [본문]을 쓰고
  근거 문서에서 온 문장 끝에 짧은 출처 꼬리 「(출처: 문서 이름 N쪽)」 를 단다. 쓴 뒤 기준표(구체성·근거·작성방법·개요 반영)로 한 번 자기 점검하고, 고친 글이
  관문을 못 지나거나 처음 글의 절반보다 짧으면 처음 글을 쓴다.
- 작업 메모 맨 앞의 「최종 결과물」 한 줄을 담당자가 바꾸자고 하지 않으면 지킨다(코드 관문 keep_final, 「미정」 줄은 구체화를 받는다).
- 여러 절 동시 맡기기: delegate_section 의 sections 목록. 연결 설정의 동시 상한(없으면 2, 합 4까지) 안에서 모델 호출만 동시에, 찾기와 파일 쓰기는 차례로.
- 본문이 표를 들고 오면 같은 절의 양식 빈 표를 지운다(결과 문서에서 본문 표 밑에 빈 표가 겹쳐 남던 것).
- 설정 넷(ZZAIMY_DRAFT_QUALITY·ZZAIMY_REVISE·ZZAIMY_DELEGATE_PARALLEL·ZZAIMY_MEMO_GOAL_LOCK)을 끄면 이전 흐름 그대로이며, 평가는 그 판(202 --old)과 견준다.

### 4.7d 오픈 모델과 SFT 학습 모델 비교(ADR-0069)

무엇을. 아스트라가 학습한 Writer SFT(LoRA r32, BF16 바탕, 2에폭, 4,434쌍)를 운영에 넣을지, 모델만 바꾸고 나머지(질문·플랫폼 코드·생성 설정·채점 모델)는
그대로 둔 채 같은 시험으로 오픈 모델(Qwen3.8-27B NVFP4)과 비교한다. 운영에 넣을 꼴은 어댑터를 합친 뒤 운영과 같은 NVFP4 로 다시 줄인 병합본이다.

어떻게.
- 시험 문항 220개(학습셋에서 떼어 둔 test, 규정·제도 문서 156 · 사업 자료 활용 64, 첫 질문 61 · 이어지는 질문 159): 학습 꼴 그대로 생성(온도 0.2, 최대 2,048토큰, 생각 끔).
  채점 모델(토르 03 운영 Writer)이 두 답 중 나은 쪽을 순서를 바꿔 두 번 고르고, 답 하나씩 여섯 항목(지시 충실·맥락 이해·형식·근거 충실·문체·완결성)을 1~5점으로 매긴다.
  정답은 채점 모델에 보여 주지 않는다. 코드가 세는 지표는 정답 겹침(chrF·ROUGE-L), 질문에 없는 숫자, 표·정답 형식, 잘림, 길이, 시간.
- 맥락 이해 30문항(가상 값): 여러 번 주고받은 값 이어 쓰기, 약 1.16만 토큰 공개 자료 속 사실 찾기, 자료에 없는 칸을 「확인 필요」 로 두기 — 코드 채점.

- 이 어댑터 대상은 같은 모델을 두 번 돌린 대조군이 됐다. 둘 중 나은 답 고르기 220문항에서 이김 49 · 비김 129 · 짐 42, 점수 0.516(95% 구간 0.475~0.559) —
  채점 모델이 같은 모델끼리도 41% 문항에서 한쪽을 골랐고 두 순서 판정이 23% 엇갈렸다. 병합본의 차이는 이 잡음 폭을 넘을 때만 차이로 읽는다.
- 병합본을 운영 옆에 따로 띄우는 것은 메모리 부족으로 실패해 운영 서버를 바꾼 뒤 같은 시험을 돌렸다. 결과 파일을 비교 대상 이름으로 남겨 교체 뒤에도 섞이지 않는다.
- 항목 점수와 맥락 이해는 두 모델 모두 거의 만점이라 위쪽이 막혀 있다.
- 첫 질문에서 오픈 모델 답은 정답보다 2.4~3.6배 길고, 정답 형식(「근거 설명: … 답변: …」)은 하나도 따르지 않았다. 이 형식은 시스템 지시에 없고 학습셋에만 있는 꼴이라,
  SFT 가 배우면 정답 겹침은 오르지만 플랫폼이 실제로 보내는 요청에서는 쓰이지 않는 꼴을 끼워 넣을 수 있다(협업 기록 claude.md 「아스트라에게 — Writer SFT 비교」).

### 4.8 한글 완성본 채우기

무엇을. 독스 작업본에서 쓴 내용을 원본 한글(hwpx) 서식 그대로 채워 제출용 완성본을 낸다(「한글 파일로 내보내 줘」, ADR-0035).

왜. 행정 서식은 표 테두리·칸 폭·글꼴이 정해져 있어 변환기로 새로 만든 한글 파일은 제출용으로 쓸 수 없다. 한글 프로그램을 원격 조작하던 방식은 윈도우 장비가
필요하고 불안정해 버렸다(ADR-0034).

어떻게(`ingest/hwpx_fill.py`). hwpx 는 XML 을 담은 ZIP 이다. 구역 XML 을 다시 직렬화하지 않고 원본 바이트를 그대로 둔 채 절 제목 문단(또는 그 뒤 【작성방법】 상자)
뒤에 문단·표·그림 XML 을 끼워 넣는다. 서식에 이미 있는 표는 칸 위치로 대응해 값만 써 넣고, 새 표는 문서에서 가장 많이 쓰는 실선 테두리를 물려받는다. ZIP 항목
순서와 압축 방식은 유지하고 바뀐 항목만 다시 쓴다. 끝에 ZIP 규약·XML 형식·참조 무결성·표 격자를 자가 점검한다. 원본이 hwpx 가 아니면 공통 양식 문서는 docx 로 낸다.

결과. 64쪽 서식이 64쪽 완성본으로 나왔다(dev-now 09-28). 그림·표 칸 채움은 LibreOffice 렌더로 확인했고, 한글 프로그램에서 직접 열어 보는 확인은 남았다.

### 5.5 한글 문서함과 양식 정리

무엇을. 부서 디렉터리 꼴의 한글 문서함에서 부서 문서를 함께 고치고, 지난 문서에서 모은 한글 양식을 쓸 수 있게 갈라 둔다.

어떻게.
- 자리: `documents/기안기/<부서>/…`. 부서마다 저장 전 판(.판)과 휴지통(.휴지통)을 두고, 사람마다 「내 폴더」(뿌리 이름 「~아이디」 — 부서 이름은 ~ 로 시작하지 않아
  겹치지 않는다)가 처음 열 때 생긴다. 즐겨찾기·최근 폴더는 사람마다 설정 하나에 두고, 보여 줄 때마다 지금 쓸 수 있는 부서·있는 폴더만 남긴다.
- 폴더 이름을 바꾸면 안의 문서 장부 경로와 즐겨찾기·최근 폴더를 함께 고친다. 경로 앞부분으로 찾는 SQL LIKE 는 `_`·`%` 를 이스케이프해 다른 폴더의 경로를 바꾸지 않는다.
- 양식 정리(`app/past_forms.py` 판정 하나, 정리 scripts/208 plan·apply·restore, 새 양식 등록 scripts/200 register 도 같은 판정): 어디서나 쓸 빈 양식은
  「공통/공통 양식/<목적>」, 특정 사업 양식은 「공통/지난 사업 문서/<사업>/<목적>」(양식이 3개 이하인 사업은 목적 폴더 없이), 개인 서류·채워진 제출본·한 번 쓴 기록·
  깨짐·빈 파일·중복은 휴지통으로. 규칙은 특정 파일·사업을 적지 않고 장부(사업 이름·별칭), 제목 낱말, 본문에서 기계로 잰 값(빈 칸 비율·개인 정보 꼴·양식 예시 글자 수)만
  보며 잰 값과 문턱은 계획 파일에 남는다. apply 는 계획의 지문(경로·sha256)이 지금과 같을 때만 돌고 바뀔 줄·설정·파일을 먼저 백업한다.

결과. 10-23 정리: 공통 양식 232 · 지난 사업 문서 489 · 휴지통 522. 정리 백업은 1주 지켜본 뒤 지운다.

## 6. 학습 데이터와 파인튜닝

### 6.1 방향

실문서의 사실과 수치는 모델에 외우게 하지 않고 검색(RAG)과 지식그래프로 공급한다. 파인튜닝은 「질문을 보고 무엇을 어디서 찾아 어떤 근거로 답을 구성할지」라는
컨텍스트 구성 리즈닝에만 쓴다(ADR-0047). 사업 자료는 해마다 바뀌는데 외운 값은 바뀌지 않고, 내부 원문을 학습에 넣으면 개인정보가 모델에 남기 때문이다.
SFT 데이터는 규정·발전계획 묶음과 사업 구조·검색 활용 묶음 두 갈래로 나눈다(ADR-0052). 실적·예산 사실 문답은 뺀다.

### 6.2 학습쌍 만드는 법

- 실문서 절 작성쌍(scripts/152, ADR-0039): 양식(작성 서식)과 완성본 한 쌍에서 절마다, 입력은 서빙 프롬프트와 같은 꼴(작성 방법, 근거 조각, 사실 목록, 양식 표
  격자), 출력은 편집 계획 JSON 으로 만든다. 출력 숫자가 입력 근거에 없으면 그 쌍을 버린다.
- 문서 구조 단계 문답(scripts/153, ADR-0040): 사업명 → 개요 → 목차 → 요구 항목 → 뼈대로 이어지는 단계 문답.
- 근거 기반 연결 대화: 사업·연차·문서·절 경로(program_id, node_path)와 근거 위치를 유지한 2~6턴 대화. 후속 질문은 앞 대화와 함께 둔다.
- 운영 기록: 에이전트 걸음, 질문 읽기, 양식 고르기, 절 작성, 못 채운 까닭 기록이 리즈닝 학습 재료로 쌓인다. 수집 자료 화면이 이것을 가린 사본으로 묶는다(7.5).

### 6.3 검수와 승인

자동 검사 통과와 사람 승인을 분리한다(ADR-0044, `dataset/quality_gate.py`).

1. 자동 검사: 사업 경로·근거 기록이 있는지, 근거가 그 턴에 글자 그대로 보이는지, 숫자가 근거에 있는지(수치 검증기), 대화 순서, 중복.
2. 사람 검수: Label Studio 에서 근거·구조·맥락·개인정보 네 항목을 확인하고 채택·수정·폐기한다. 네 항목이 모두 확인된 채택·수정만 승인본이다.
3. 개인정보: 학습 사본은 내부 가림 설정과 상관없이 전체 탐지로 가리고, 가림을 다시 해도 바뀌지 않는 파일만 반출한다(fail-closed).
4. 묶음 검사: 여러 파일을 합칠 때 사업 단위 학습·검증·시험 분리와 중복을 전체에서 다시 본다.

학습셋은 학습 장비에서 만들고 승인하며 원문은 학습 장비 밖으로 나가지 않는다. 운영 서버의 데이터·학습 화면에는 이름·상태·건수·지문·승인 범위만 담은 목록이
1분마다 들어온다(scripts/197). 최근 학습셋 파일은 개발자 계정만 내려받고 표본을 볼 수 있다(10-18).

### 6.4 writer-v1 학습셋

10-17 학습 장비에서 AI 검토로 승인했다가, 10-18 최종 의미 점검에서 고치지 못한 답 결함이 나와 보류했다. 같은 날 결함을 고친 판(v6)을 다시 점검해(경고 34건은 유지 이유 기록, 미처리 0) 첫 SFT 실험 범위로 승인했다. 학습 4,434 · 검증 346 · 시험 220건이고, 대화 1,214건과 출처 묶음 155개에서 만들었다(docs/progress.json). 학습 전 측정으로
베이스 27B 를 시험 세트 30건에 재어 25건이 통과했다. 30건의 문항 구성과 통과 기준은 학습 장비 쪽 기록에 있어 저장소에서는 미확인이다.

학습은 아직 시작 전이다. 지금 서비스의 모든 답은 학습하지 않은 베이스 27B 가 RAG·GraphRAG 근거로 만든다.

### 6.5 다음 단계

학습 장비(DGX)에서 TRL·PEFT 학습 스크립트로 bf16 LoRA SFT 를 돌리고(문맥 16,384 토큰), 같은 시험 세트와 모델 교체 기준 v2(scripts/195)로 학습 전후를 한 표에서 견준다. 학습본은 서빙 장비에 다른
서빙 이름으로 올려 후보로 재고, 나빠지지 않을 때만 용도를 옮긴다. 선호 학습(DPO)은 10-20 범위에서 뺐다. 담당자의 판정·재작성 이력은 다음 학습 재료로 쌓는다.

## 7. 개인정보·권한·운영

### 7.1 온프레미스

모든 모델(생성·임베딩·리랭커)이 교내 장비에서 돈다. 상용 클라우드 AI 연결 경로는 없다. 예전에 설계했던 외부 AI 참조 경로는 제거했다(ADR-0043·0061). 모델
캐시를 오프라인으로 두어 외부 서비스 없이 뜬다.

### 7.2 외부 전송 관문

밖으로 나갈 수 있는 길을 목록화해 통제했다(노트 2026-10-15-egress-audit, 31개 경로). 지금 밖으로 나가는 것은 외부 검색 모드의 질문 글(개인정보가 있으면 차단),
구글 독스 작업본(담당자 학교 계정, 넣는 글은 개인정보 검사와 감사 기록), 외부 GPU 서버 연결을 쓸 때의 요청이다. 외부 GPU 서버 연결은 문서 작업 기본 연결로만,
개인정보 검토 확인을 받은 뒤 지정할 수 있고, 요청의 개인정보를 되돌릴 수 있는 토큰으로 바꿔 보낸 뒤 답에서 원값으로 되돌린다. 가릴 수 없거나 그림이 들어 있으면
보내지 않는다(`generate/outbound.py`). 반입 검토·판독은 외부로 넘기지 않는다. 남은 결정 6건(외부 GPU 연결 존치 등)은 학교 확인 대기다.

### 7.3 열람 등급

3.8 의 규칙이 화면과 검색에 함께 걸린다. 바꾸는 권한은 열람과 따로 둔다 — 문서를 지우거나 고치는 요청은 올린 사람과 관리자만, 프로젝트는 담당자와 관리자만
바꾼다. 구글 계정은 본인 연결과 부서 공용만 쓴다. 부서 드라이브는 그 부서 총괄 책임자가 부서 공용 학교 계정으로 연결하고 관리자는 확인만 하며, 그 계정 토큰은
부서 폴더 안 문서를 만들고 다룰 때만 쓴다(`gdrive_files.doc_account_for`, 부서는 계정 표의 소속에서 읽는다). 드라이브 찾기·가져오기·쓸 계정 목록은 본인 계정만 받아,
부서 계정으로 아무 폴더나 둘러볼 수 없다. 연결을 거절해도 허용 state 를 써 버리고, 연결에 실패한 토큰은 지운다. 작업 문서는 같은 부서 동료에게 문서마다 보기 권한으로 공유하되, 그 대화의 근거 문서를 동료도 모두 볼 수 있을 때만
준다. 열람 등급 값 체계는 학교 기준이 확정되면 바꾼다.

### 7.4 감사 기록

권한 밖 시도·개인정보 요청·지시 흉내 질문(access_audit), 구글 문서 쓰기(gdocs_audit), 도우미 실행(platform_actions), 답 실행 기록(answer_runs), 에이전트 걸음 기록을
남긴다. 감사 기록에는 질문 앞부분만 남기고 원문 전체는 남기지 않는다.

### 7.5 수집 자료 가린 사본

대화·답 실행·평가·에이전트 걸음 같은 운영 기록을 학습 재료로 쓰려면 밖으로 꺼내야 한다. 수집 자료 화면(`/dev/collect`, `app/collect.py`, 관리자만)은 기간·항목별로
묶음을 내려받게 하는데, 묶음은 늘 가린 사본이다. 글은 개인정보 탐지와 고위험 꼴로 가리고 가림에 실패한 글은 통째로 「[가림 실패]」로 바꾼다. 사람 칸은 서버 비밀값으로
만든 가명으로 바꾸고, 대화 단위로 학습·평가를 나누며 평가 세트와 같은 질문은 뺀다.

### 7.6 운영

운영 서버 메모리가 64GB 라 그래프 전체나 색인 전체를 읽는 무거운 작업은 하나씩 돌리고 주기 작업에 메모리 상한을 둔다. 서빙 장비의 GPU 메모리 비율은 같은 장비의
임베딩·리랭커·파일 캐시를 고려해 정한다(MTP 적용 때 비율을 너무 높게 잡아 검토가 약 25분 멈춘 일이 있다, 실험 로그 16절). 데이터를 바꾸는 운영 작업은 백업을 먼저
하고 되돌리기 명령을 함께 둔다. 시험은 운영 설정이 아닌 시험 DB 에서 한다. 서버를 옮길 때 무엇을 옮길지는 이관 목록 도구(scripts/209 report·pack, docs/ops/migration.md)의 규칙표 한 곳에서 정한다 — 경로마다 옮김·비밀값·다시 만듦·옮기지 않음·학습(학습 장비 담당) 갈래를 붙이고, 어느 규칙에도 안 걸린 경로는 「규칙 없음」 으로 드러내 조용히 빠지는 것이 없게 한다. 비밀값은 내용을 읽지 않고 경로만 적어 따로 옮기며, 운영 DB 는 pg_dump 로 옮긴다. VM 에서의 첫 실행은 남았다. 자동 테스트 2,492건이 통과한다(10-23, 건너뜀 1).

## 9. 한계와 남은 일

- 파인튜닝: Writer SFT(writer-v1)는 DGX 에서 학습 중이다(체크포인트 110에서 이어 학습). 학습 효과는 아직 재지 않았다. Extract 전용 학습은 시작하지 않았다.
- 평가 표본: 답 시험지 30문, 검색 시험지 136문은 그래프에서 자동으로 뽑은 질문이다. 실제 사용자 질문으로 만든 골드셋 측정은 아직이다. 정답 사실 재현율은 상대 지표다.
- 규정 검색: 용어를 모르고 상황으로 묻는 질의의 일부(9-20 측정 22.7%)는 두 축 모두 상위 20 에 넣지 못한다. 질의 확장은 구현돼 있으나 운영 모델 지정이 결정 전이다.
- 판정 정확도: 서류 갈래는 규칙과의 일치율만 쟀고 사람 정답 대비 정확도는 미측정이다. 사업 파일 단위 재판정의 정확도도 미측정이다.
- 문서 처리: 긴 스캔 PDF 는 MinerU 품질에 의존하고, 표 셀 배경색 같은 시각 서식은 보존하지 못한다. 처리 실패 111건(암호·손상)은 읽지 못한다.
- 한글 완성본: 한글 프로그램에서 직접 열어 확인하는 일, 예산표·명단표의 행 순서 대응이 남았다.
- 권한: 작업 권한 등급(ADR-0066)은 들어갔으나 같은 부서 안 동료 문서 검토 의견, 그래프 사업 별칭·연관 관계를 범위로 거를지가 결정 전이다.
  부서 드라이브는 각 부서 총괄 책임자의 실제 연결이 남았다.
- 문서 작성 평가: 시나리오 평가(4.7b·4.7c)는 판마다 3회이고 채점이 같은 27B 의 자기 평가라 판 비교에만 쓴다. 목표 유지와 「표로」 고쳐 쓰기는 고친 잣대로 다시 재야 한다. 열람 등급 값 체계와 개인정보 부서 검토, 보관·삭제 범위는
  학교 확인이 필요하다.
- 외부 전송: 남은 결정 6건이 학교 확인 대기다.
- 개인정보 탐지는 정규식·이름표 문맥 기반이라 이름표 없는 이름·주소를 놓칠 수 있어, 학습 반출에는 사람 검수를 함께 요구한다.
