# 품질 체계 — 추출·표·OCR 문제를 구조로 막는다

사용자 방침(2026-09-08): "문서를 고치는 게 중요한 게 아니라, 저런 식으로 안 되게끔
해야 한다. 체계를 명확하게 잡으라." 이 문서가 그 체계다. 개별 문서의 수리는
검증 수단일 뿐 목표가 아니며, 모든 품질 문제는 발생 계층을 찾아 그 계층에서
차단한다.

## 다섯 계층

문제 하나가 보고되면 아래 순서로 처리한다. 어느 계층에서 막았는지를 항상
명시한다.

1. 원천 차단 (파이프라인)
   문제가 생기는 처리 경로 자체를 바꾼다. 특정 문서에 맞춘 예외 규칙은
   금지한다(하드코딩 금지 원칙). 같은 부류의 모든 입력에 적용되는 일반
   메커니즘만 허용된다.
   예: 디지털 PDF 표의 규격 불일치 → 괘선 직독 추출(lattice.py)로 경로 교체.
   OCR 근사 대신 원본의 벡터 선·글자층을 직접 읽으므로 오타와 구조 왜곡이
   원천적으로 발생하지 않는다.

2. 자기 검증 (인제스트 게이트)
   파이프라인이 자기 산출물을 스스로 의심한다. 확신이 낮은 결과는 조용히
   저장하지 않고 표시를 남긴다.
   현재: 디지털 PDF 여부 판별(글자층 검사), 낮은 확신 OCR 줄 표시(재판독
   대상), 파싱 방식·표 개수를 parse_note로 기록.
   예정: 표 추출 신뢰도(괘선 격자와 셀 텍스트 정합), 글자층-추출 텍스트
   대조 비율.

3. 회귀 잠금 (테스트)
   고친 문제는 반드시 테스트로 잠근다. 같은 결함이 재발하면 배포 전에
   테스트가 먼저 잡는다. 테스트 없는 수정은 완료가 아니다.
   예: 격자·병합·열 폭·셀 텍스트 테스트 9건(test_lattice.py), 세척·분류
   안전 계약 테스트(test_egress.py).

4. 지표 추적 (평가 하네스)
   개선폭은 수치로 남긴다. 어절 F1(OCR), 표 구조 보존(파서 bake-off 기준),
   Recall@k·MRR(검색). 수치 없는 "좋아진 것 같다"는 기록으로 인정하지
   않는다. 이 기록이 논문 방법론의 원재료다.

5. 신고 루프 (운영)
   담당자가 화면에서 발견한 문제를 한 번의 조작으로 남긴다(문서 화면의
   추출 문제 신고). /dev 백로그에 유형별로 집계되고, 처리 시 위 1~4 계층
   중 어디서 막았는지를 남긴다. 실문서가 쌓일수록 이 루프가 개선 우선순위를
   정한다.

## 운영 규칙

- 문제 보고를 받으면: 재현 → 발생 계층 진단 → 해당 계층에서 수정 → 테스트
  잠금 → 지표 기록 → (설계 변경이면) ADR.
- 인프라·스크립트 결함도 같은 체계를 따른다. 사람이 조심해서 피하는 방식은
  차단이 아니다 — 스크립트·설정에 박는다.
  예: 재색인이 허브 접속을 재시도하며 허비 → 스크립트에 오프라인 강제
  (HF_HUB_OFFLINE), 코어 절반·nice 강제, flock 동시 실행 방지.
- 테스트용 문서로 발견한 문제도 실문서와 똑같이 다룬다. 테스트 문서는
  문제를 미리 드러내라고 넣는 것이다.

|---|---|---|
| 스캔본 표 인식 (괘선이 그림 속) | 1 원천 차단 | GPU 확보 후 비전 모델 경로 |
