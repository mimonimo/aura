## 1. 전체 데이터 흐름

두 개의 파이프라인이 있고, 교차점은 저장 계층뿐이다.

**구축 파이프라인 (배치)** — 문서를 자산으로 바꾼다:

```
PDF/HWP 입수 → 파싱(표 구조 보존) → PII 마스킹 → 계열 분류·메타데이터 부여
  ├─ (전 계열) 청킹 → 이중 벡터화(dense + Kiwi sparse) → 벡터 인덱스 적재
  └─ (③ 결과보고서만) 구조화 추출 → 원문 대조 검증 → 사람 검수 → 실적 카드 DB
```

**생성 루프 (대화형)** — 공고에서 초안까지 (브리프 6장 그대로 채택):

```
공고 파싱→정형 스키마 → 방향 입력 → 섹션별 루프[근거 인출→생성→수치 검증]
  → 배점 대조 검증 → 예산표 생성(LLM 금지) → 출처 주석 초안 출력
```

파이프라인 순서는 **타입으로 강제한다**. 구현 완료된 첫 사례가
`src/zzaimy/ingest/pii.py`의 `RawDocument`/`MaskedDocument` 분리다 —
마스킹을 거치지 않은 문서는 인덱싱 함수의 시그니처를 통과할 수 없다.
이 패턴을 각 단계 경계(파싱 전/후, 검증 전/후)에 동일 적용한다.

## 2. 문서 4계열 처리 경로 분리 (브리프 5.6)

구현: `src/zzaimy/ingest/schema.py` (TASK-06 완료).

| 계열 | 경로 | 인덱스 |
|---|---|---|
| ① 공고·지침 | 파싱 → 마스킹 → 공고 스키마 추출 대상 | 별도 컬렉션 `announcements` |
| ② 사업계획서 | 파싱 → 마스킹 → 청킹·벡터화 (+ Writer 학습 데이터 원천) | `proposals` |
| ③ 결과보고서 | 파싱 → 마스킹 → 벡터화 **+ 실적 카드 추출** | `reports` + 실적 카드 DB |
| ④ 지출 문서 | **분류 즉시 격리** — 파이프라인 밖 (절대 규칙 10) | 없음 |

계열은 규칙 기반 분류기(파일명 키워드)로 1차 판정하고, 판정 불가(None)는
사람이 지정한다. 추측으로 채우지 않는다.

## 3. 실적 카드 DB 스키마 — 최우선 구축 대상

저장소: **PostgreSQL** (출처 참조 무결성을 FK로 강제). 브리프 6장 필드에
출처·검수 이력을 더한다.

```sql
CREATE TABLE achievement_cards (
  card_id       BIGSERIAL PRIMARY KEY,
  business_name TEXT NOT NULL,        -- 사업명
  year          INT  NOT NULL,
  budget_krw    BIGINT,               -- 예산규모 (원 단위 정수)
  participants  INT,                  -- 참여인원
  metric_name   TEXT,                 -- 정량성과 항목명
  metric_value  NUMERIC,              -- 정량성과 값
  metric_unit   TEXT,
  department    TEXT,                 -- 소관부서
  equipment     TEXT[],               -- 활용장비
  source_doc_id TEXT NOT NULL,        -- 출처 문서 (메타데이터 doc_id)
  source_page   INT  NOT NULL,        -- 출처 페이지
  source_span   INT4RANGE,            -- 원문 문자 오프셋 (대조 검증용)
  review_status TEXT NOT NULL DEFAULT 'pending',  -- pending|approved|rejected
  reviewed_by   TEXT,                 -- 검수자 (직책 표기 — 성명 아님)
  extracted_by  TEXT NOT NULL         -- 교사모델|ZZAIMY-Extract 버전
);
```

- **모든 수치 필드는 출처(문서+페이지+오프셋) 없이 삽입 불가** — NOT NULL로 강제.
- `review_status='approved'`만 생성 루프의 인출 대상이다.
- 검수 완료 카드가 곧 ZZAIMY-Extract 학습 데이터가 된다 (UC-5 겸용).

## 4. 섹션별 생성 파이프라인 (통짜 생성 금지, 브리프 5.4)

```
공고 스키마(목차·평가지표·배점·분량)에서 섹션 목록 생성
for 섹션 in 목차:
    근거 = 실적카드DB.조회(승인분, 메타필터) + 하이브리드검색(섹션 요구사항)
    초안 = Writer(섹션 요구사항 + 평가지표 + 근거 + 방향성)     # 근거는 입력으로만
    검증 = 수치대조(초안 수치 ⊆ 근거 수치)
    if 검증 실패: 해당 수치를 빈칸 + "근거 없음" 표시로 치환    # 지어내지 않는다
전체 조립 → 배점 대조 검증 → 예산표(결정론) → 출처 주석 부착
```

공고 스키마 추출은 vLLM **xgrammar** 스키마 강제로 형식을 보장하고,
추출값의 원문 대조(문자열 매칭)로 내용을 보장한다 — 형식·내용 이중 보증.

## 5. 검증기 3종 — 시스템의 차별화 지점

| 검증기 | 방식 | 원칙 |
|---|---|---|
| 수치 대조 | 초안에서 수치·고유 실적명 기계 추출 → 인출 근거 집합과 대조 | **결정론적**. LLM 판단 배제 |
| 배점 커버리지 | 공고 스키마의 배점 항목별로 초안 반영 여부 체크 → 누락 리포트 | 항목 매칭은 규칙 + 임베딩 유사도 보조, 최종 판단은 리포트로 사람에게 |
| 예산 계산 | 단가 DB + 산식 로직으로 예산표 생성·검산 | **LLM 절대 금지** (절대 규칙 5) |

검증기의 인터페이스는 TASK-08 수직 슬라이스에서 먼저 고정한다 —
나중에 끼워 넣기 어려운 지점이기 때문이다.

## 6. 검색 계층

- 하이브리드: dense(ZZAIMY-Embed) + sparse(Kiwi 형태소 → BM25 계열) → RRF 융합 → 리랭킹(ZZAIMY-Rerank)
- 메타데이터 필터: 연도·계열·사업명·**열람 등급** — 필터가 강한 질의가 지배적이므로
  필터 인식 인덱스가 요구사항이다.

**벡터 스토어 — 상태: 미결 (질문 #8)**

| 안 | 장점 | 단점 |
|---|---|---|
| Qdrant (2-스토어) | dense+sparse 네이티브 하이브리드, 필터 인식 HNSW, 단일 바이너리 | 실적 카드 DB(PostgreSQL)와 이원화 |
| pgvector (1-스토어) | 실적 카드와 한 DB — 출처 FK 무결성, 운영 단일화 | sparse 하이브리드 직접 구현 필요 |

운영 인력의 DB 경험(#8) 답변으로 확정한다. 그 전 구현은 저장소 추상 인터페이스
뒤에서 진행해 교체 비용을 낮춘다.

## 7. 열람 등급 필터링 (TASK-06에서 확정한 구조)

절대 규칙 4: **열람 등급 필터링은 검색 단계에 있다.** 구현 구조는 다음과 같다.

- 모든 문서 메타데이터(`src/zzaimy/ingest/schema.py`의 `BaseDocMeta`)는
  `access_level` 필드를 갖는다. 값은 문자열 enum(`AccessLevel`)이라
  벡터DB의 메타데이터 필터(Qdrant payload filter / pgvector WHERE 절)에
  **변환 없이 그대로** 쓸 수 있다.
- 인덱싱 시 청크마다 이 값이 페이로드로 함께 적재된다. 검색 쿼리는
  `access_level ∈ {사용자 허용 등급}` 필터를 항상 동반하며, 필터를 빼먹은
  검색이 없도록 retrieve 계층의 공개 API가 사용자 등급을 필수 인자로 받는다.
- **미분류 문서의 기본값은 가장 보수적인 `restricted`다.**
- 값 체계 자체는 **미해결 질문 #7** 확정 후 교체한다. 필드·필터 경로가 이미
  있으므로 값 교체는 재인덱싱 없이 가능하다. 필드 추가를 미뤘다면 전체
  재인덱싱이었다.

## 9. 에이전트 계층과 검수 대시보드 — 상태: 제안 (ADR-0002)

실사용 전환(capstone-plan §1.1)을 위해 두 계층을 설계에 포함한다.
**구현 우선순위는 파이프라인·모델 → 수직 슬라이스 → UI 순**이며, 브리프에
명시되지 않은 산출물 추가이므로 ADR-0002로 제안하고 승인을 받는다.

- **에이전트 계층**: 생성 루프(§4)와 구축 파이프라인(§1)의 오케스트레이션.
  SFTP 반입 감시 → 인제스트 자동 트리거, 섹션 루프 실행, 검증 실패 시 재시도·
  에스컬레이션. 각 에이전트는 파이프라인 단계의 얇은 래퍼로, 로직은 라이브러리
  계층(src/zzaimy)에 남긴다 — 에이전트 프레임워크 종속을 피한다.
- **검수 대시보드**: UC-1(초안 생성·검토), UC-3(짜임새 점검), UC-5(실적 카드 검수)의
  화면. "70% 초안 + 사람 검수" 경고를 UI에 명문화한다(capstone-plan §1.1-3).
  수직 슬라이스(CLI) 위에 얇게 얹는다.

## 10. 도메인 중립 공통 계층 — 상태: 제안 (ADR-0003)

캡스톤의 상위 목표는 "행정업무 자동화를 위한 YNC LLM"이며 국고사업은 첫
적용 도메인이다. 두 번째 후보(채용 서류 검토)를 위해 **인제스트 공통 계층**
(파싱·PII 마스킹·분류·열람 등급)은 국고사업 전용 가정을 넣지 않고 설계한다.
이미 그렇게 구현돼 있다 — 파서 인터페이스·PII recognizer·AccessLevel은 문서
도메인과 무관하다. 국고사업 고유 로직(실적 카드, 배점 검증, 예산)은 도메인
모듈로 격리한다. **이번 학기 구현 범위는 국고사업뿐이다.**
