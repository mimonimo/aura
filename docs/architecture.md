# 시스템 설계

> 지금 구조의 정본이다(마지막 정리 2026-10-25). 착수 단계(2026-09-01)에 쓴 설계 판단의 근거는 그대로 두고, 구현이 달라진 곳은 각 절에 `현황:`으로 적는다.
> 문서 작성은 9장(에이전트)·10.2(웹 한글 기안기 공동 편집)·10.3(27B 가 문서에 쓰는 길)이 지금 모습이다. 결정의 이유는 결정 기록(ADR)에 있다.
> 운영 구성은 [프로젝트 브리프](../PROJECT_BRIEF.md) 4·6장과 [인수인계](HANDOFF.md)를 따른다.
> 근거: [조사 요약](../research/00-summary.md), [시스템 개관 조사](../research/02-system-overview.md), 1~2주차 측정.

현재 구성의 큰 줄기는 다음과 같다. 운영 DB는 PostgreSQL이고, 내부 문서의 개인정보 마스킹은 선택 설정(기본 꺼짐)이다.
원본 보관과 일괄 처리는 DGX가, 실시간 서비스는 운영 서버와 두 대의 젯슨 토르가 맡는다. 사업별 문서·절 그래프는
확장 중이며, 관계의 의미 정확성과 원문 전체 커버리지는 따로 검증한다(ADR-0047·0048).

## 1. 전체 데이터 흐름

파이프라인은 둘이고, 만나는 곳은 저장 계층뿐이다.

구축 파이프라인(배치)은 문서를 검색 가능한 자산으로 바꾼다.

```
PDF/HWP 입수 → 파싱(표 구조 보존) → 처리 정책 적용 → 계열·사업·권한 메타데이터 부여
  ├─ (전 계열) 청킹 → 이중 색인(dense + Kiwi sparse) → 인덱스 적재
  └─ (③ 결과보고서만) 구조화 추출 → 원문 대조 검증 → 사람 검수 → 실적 카드 DB
```

생성 흐름(대화형)은 공고에서 초안까지 간다. 브리프 6장을 그대로 따른다.

```
공고 파싱 → 정형 스키마 → 방향 입력 → 절 단위 반복[근거 인출 → 생성 → 수치 검증]
  → 배점 대조 검증 → 예산표 생성(LLM 미사용) → 출처 주석이 붙은 초안
```

내부 문서의 일괄 마스킹은 필수 관문이 아니다(ADR-0044). 내부 마스킹 설정, 문서 접근 권한, 학습 사본의
검수·반출 관문은 서로 독립이다. 초기 설계의 RawDocument/MaskedDocument 타입 분리는 플랫폼 전체에 마스킹을
강제한다는 뜻으로 쓰이지 않는다.

## 2. 문서 4계열 처리 경로 분리 (브리프 5.6)

구현: `src/zzaimy/ingest/schema.py`.

| 계열 | 경로 | 인덱스 |
|---|---|---|
| ① 공고·지침 | 파싱 → 마스킹 → 공고 스키마 추출 대상 | 별도 컬렉션 `announcements` |
| ② 사업계획서 | 파싱 → 마스킹 → 청킹·벡터화 (+ Writer 학습 데이터 원천) | `proposals` |
| ③ 결과보고서 | 파싱 → 마스킹 → 벡터화 + 실적 카드 추출 | `reports` + 실적 카드 DB |
| ④ 지출 문서 | 분류 즉시 파이프라인 밖으로 격리 (절대 규칙 11) | 없음 |

계열은 규칙 기반 분류기로 1차 판정하고, 판정하지 못한 문서는 사람이 지정한다. 추측으로 채우지 않는다.

현황: 기준 문서와 접수 문서는 PostgreSQL 테이블 `regulation_chunks`·`doc_chunks`로 구분한다. 위 표의
필수 마스킹과 컬렉션 구성은 초기 설계다. 내부 마스킹은 설정을 따르고, 학습 후보는 `/dev/train`에서 따로 검수한다.

## 3. 실적 카드 DB 스키마

저장소는 PostgreSQL이며 출처 참조 무결성을 외래 키로 강제한다. 브리프 6장 필드에 출처·검수 이력을 더한다.

```sql
CREATE TABLE achievement_cards (
  card_id       BIGSERIAL PRIMARY KEY,
  business_name TEXT NOT NULL,        -- 사업명
  year          INT  NOT NULL,
  budget_krw    BIGINT,               -- 예산 규모 (원 단위 정수)
  participants  INT,                  -- 참여 인원
  metric_name   TEXT,                 -- 정량 성과 항목명
  metric_value  NUMERIC,              -- 정량 성과 값
  metric_unit   TEXT,
  department    TEXT,                 -- 소관 부서
  equipment     TEXT[],               -- 활용 장비
  source_doc_id TEXT NOT NULL,        -- 출처 문서 (메타데이터 doc_id)
  source_page   INT  NOT NULL,        -- 출처 쪽
  source_span   INT4RANGE,            -- 원문 문자 오프셋 (대조 검증용)
  review_status TEXT NOT NULL DEFAULT 'pending',  -- pending|approved|rejected
  reviewed_by   TEXT,                 -- 검수자 (직책 표기, 성명 아님)
  extracted_by  TEXT NOT NULL         -- 교사 모델 | ZZAIMY-Extract 버전
);
```

- 모든 수치 필드는 출처(문서·쪽·오프셋) 없이 넣을 수 없다.
- `review_status='approved'`인 카드만 생성 흐름의 인출 대상이다.
- 검수가 끝난 카드는 그대로 ZZAIMY-Extract 학습 데이터가 된다.

현황: 위 스키마는 목표 설계다. 실문서 처리와 사업별 구조화가 진행 중이며, 초안 재료는 권한 있는 원문 조각과
검증된 근거에서 인출한다.

## 4. 절 단위 생성 (브리프 5.4)

```
공고 스키마(목차·평가지표·배점·분량)에서 절 목록 생성
for 절 in 목차:
    근거 = 실적카드DB.조회(승인분, 메타필터) + 하이브리드검색(절 요구사항)
    초안 = Writer(절 요구사항 + 평가지표 + 근거 + 방향)     # 근거는 입력으로만
    검증 = 수치대조(초안 수치 ⊆ 근거 수치)
    if 검증 실패: 해당 수치를 빈칸 + "근거 없음" 표시로 바꾼다  # 지어내지 않는다
전체 조립 → 배점 대조 검증 → 예산표(결정론) → 출처 주석 부착
```

공고 스키마 추출은 vLLM의 구조화 출력(xgrammar)으로 형식을 보장하고, 추출값을 원문과 문자열로 대조해 내용을
보장한다.

현황: 위 순서는 착수 때 그림이다. 지금은 27B 문서 작업 에이전트가 양식을 고르고(ADR-0060), 절마다 근거를 찾아 개요 → 본문 →
자기 점검 순으로 쓴다(ADR-0068). 숫자 대조는 아래 검증기를 그대로 쓰는 관문이다. 어떤 길로 문서 파일에 들어가는지는 10.3.

## 5. 검증기 3종

| 검증기 | 방식 | 원칙 |
|---|---|---|
| 수치 대조 | 초안에서 수치·고유 실적명을 기계 추출해 인출 근거와 대조. 같은 금액을 단위만 바꿔 쓴 값(5억 = 500(백만원) = 「(단위: 백만원)」 표의 500)은 같은 값으로 본다(ADR-0068 — 금액끼리만, 가장 가까운 단위 선언 하나만) | 결정론적. LLM 판단을 쓰지 않는다 |
| 배점 커버리지 | 공고 스키마의 배점 항목별로 초안 반영 여부를 확인하고 누락을 보고 | 규칙과 임베딩 유사도로 매칭하고, 최종 판단은 사람이 한다 |
| 예산 계산 | 단가 표와 산식으로 예산표를 만들고 검산 | LLM을 쓰지 않는다 (절대 규칙 5) |

구현: `src/zzaimy/verify/` (`numbers.py`, `coverage.py`, `budget.py`). 검증기 인터페이스는 수직 슬라이스 단계에서
먼저 고정했다. 나중에 끼워 넣기 어려운 지점이기 때문이다.

## 6. 검색 계층

- 하이브리드: dense(ZZAIMY-Embed)와 sparse(Kiwi 형태소 기반 어휘 검색)를 RRF로 합치고, 규정 후보는 ZZAIMY-Rerank로 재정렬한다.
- 메타데이터 필터: 연도·계열·사업명·열람 등급. 필터가 강한 질의가 많으므로 필터를 인식하는 인덱스가 필요하다.

그래프 검색(`graph/retrieve.py`)은 질의에 명시된 연도·차년도·문서 갈래에 맞는 근거만 돌려준다. 맞는 자료가 없으면
다른 연차나 갈래로 넓히지 않고, 연도가 불분명한 문서는 연도를 지정한 질의의 근거에서 뺀다.

사업 문서 본문의 어휘 색인(`app/grant_lex.py`)은 색인과 질의가 같은 낱말 함수 `lex_terms` 를 쓴다. Kiwi 명사와 두 글자 이상
영문 약칭을 소문자로 모으고, 띄어 쓴 복합 명사는 붙이며, 전각 문자는 먼저 정리한다(`responder.normalize_input`). 그래서 한 낱말 질의도 본문 대목이
찾힌다. 규칙이 바뀌면 동기화가 판 번호를 보고 옛 판으로 뽑은 줄을 다시 뽑는다.

모든 모델 호출(답변, 에이전트 걸음, 편집 계획)은 보내기 전에 문맥 한도에 맞춘다(`app/llm_budget.py`). 한도는 서빙 서버의
`/v1/models` 가 알려 주는 `max_model_len` 이고, 읽지 못하면 설정값(`ZZAIMY_WRITER_CONTEXT`)을 쓴다. 첨부·연결 문서와 오래된
대화부터 줄이고 요청 글과 에이전트가 찾은 근거는 맨 뒤에 줄인다. 다 줄여도 넘으면 모델을 부르지 않는다. 표시하는 출처는
모델에 실제로 전달한 근거 목록에서만 만든다.

벡터 저장소 초기 비교:

| 안 | 장점 | 단점 |
|---|---|---|
| Qdrant (저장소 2개) | dense+sparse 하이브리드 내장, 필터 인식 HNSW, 단일 바이너리 | 실적 카드 DB(PostgreSQL)와 이원화 |
| pgvector (저장소 1개) | 실적 카드와 한 DB, 출처 외래 키 무결성, 운영 단일화 | sparse 하이브리드를 직접 구현 |

현황: 운영 PostgreSQL의 pgvector를 쓴다(ADR-0057). 사업 문서 조각의 의미 검색은 `grant_vec` 표와 HNSW 색인에서 하고,
권한·RAG 공간·범위 필터를 같은 SQL에서 적용한다. 색인과 질의 임베딩은 같은 학습본(ZZAIMY-Embed v2)이어야 하고
(ADR-0021), 리랭킹은 토르 03의 ZZAIMY-Rerank v1 서비스가 맡는다(ADR-0020).

## 7. 열람 권한

절대 규칙 4에 따라 열람 등급 필터는 검색 단계에 둔다.

- 문서 메타데이터(`ingest/schema.py`의 `BaseDocMeta`)는 `access_level` 필드를 갖는다. 값이 문자열 enum이라 SQL WHERE 절에
  그대로 쓸 수 있다.
- 반입할 때 문서마다 부서와 열람 등급(전체 공개, 부서 제한, 담당자 한정)을 붙인다(`app/access_policy.py`).
  규정·공고·지침은 전체 공개, 그 밖의 접수 문서는 부서 제한이 기본이다.
- 검색 범위는 RAG 공간으로 정한다(`app/rag_spaces.py`, ADR-0053). 학생 계정은 학생 공개로 지정한 학사 규정만, 부서
  교직원은 그 부서의 사업 문서와 공통·부서 규정을 검색한다. 채팅 검색과 머리말 검색(`/search`)의 본문 대목·규정 조각이
  같은 공간 범위를 쓴다. 라이브러리의 판본 묶음은 캐시 없이 요청마다 열람 범위 안에서 계산한다.
- 열람 등급 값 체계는 학교 기준이 확정되면 바꾼다. 필드와 필터 경로가 이미 있어 값 교체에 재색인이 필요 없다.
- 작업 권한은 열람과 따로 교직원 등급으로 나눈다(`app/grades.py`, ADR-0066) — 일반·행정 담당자·사업 책임자·총괄 책임자와 관리자(최대 2명).
  권한 판단은 소속 부서 등급만 보고, 겸직 등급은 그 부서 안에서만 쓴다. 부서 단위는 두 단계(총괄 책임자 = 처·단, 사업 책임자·행정 담당자 = 팀·센터)이며
  조직도(`app/org_routes.py`)에서 관리자와 맡은 처·단의 총괄 책임자만 고치고, 고치는 검사·쓰기·되돌리기는 공용 잠금 하나 안에서 한다.
- 부서 드라이브(`app/dept_drive_routes.py`, `ingest/dept_drive.py`)는 부서 총괄 책임자가 부서 공용 학교 계정으로 연결한다. 그 계정 토큰은 부서 폴더 안
  문서를 만들고 다룰 때만 쓰고(`gdrive_files.doc_account_for`), 드라이브 찾기·가져오기·쓸 계정 목록은 본인 계정만 받는다. 관리자는 연결 상태를 확인만 한다.

그래프 조회도 문서 화면과 같은 가시성 정책을 따른다. 노드 생성·사업 분석·유사도 비교 전에 문서 범위를 좁히고,
일반 사용자에게는 본인 프로젝트만 포함한다. 사업 그래프(`/graph/program`)는 허용된 문서·절과 상위 사업·연차·분류만
남기고, 양 끝 노드가 모두 보이는 관계만 표시한다. 접근할 수 없거나 없는 사업은 404로 응답한다. 부서 선택값은 보기
필터일 뿐 권한을 넓히지 않는다.

대화의 진행 상태는 `/chat/{id}/status` 폴링으로 전달한다. 단계 이름과 근거 개수만 알리고, 모델의 내부 추론·프롬프트·
원문은 포함하지 않는다. 대화 소유자만 조회할 수 있다.

## 8. 서빙·실행 환경

- 서빙: vLLM. 젯슨 토르 2대에 Writer 27B NVFP4를 올리고(`scripts/126_serve_writer.sh`), 토르 03에 임베딩·리랭커
  서비스를 둔다(ADR-0023). 초기 검증에 쓴 DGX Spark 구성(ADR-0004)은 쓰지 않는다.
- 학습: TRL·PEFT(LoRA)와 sentence-transformers를 별도 가상환경(`.venv-train`)에서 쓴다(ADR-0001). Writer 학습은 DGX 학습 스크립트
  (`scripts/83_sft_writer_qlora.py`, 승인 기록·해시 관문)로 하고 진행은 TensorBoard 로 본다. LLaMA Board 는 10-18 걷어냈다.
  검색 모델은 토르 03 GPU에서 학습했다(2에폭 20분).
- 파싱: 디지털 PDF 글자층 직독, MinerU(스캔 PDF 구조·OCR), Writer 이미지 판독(그림·사진), tesseract(사진의 마지막 대안),
  kordoc(한글·docx·xlsx), python-docx·openpyxl·python-pptx, LibreOffice(옛 오피스 형식 변환)
  (ADR-0007·0016·0033·0050·0051). Docling은 처리 경로에서 쓰지 않는다.
- 일괄 처리: 문서 단위로 나눈다. 반입은 두 건씩 동시에 처리한다(파싱은 운영 서버 CPU, 검토는 토르 03).

## 9. 에이전트 계층과 검수 화면 (ADR-0002)

착수 단계에는 두 계층을 설계에 포함했다.

- 에이전트 계층: 생성 흐름(4절)과 구축 파이프라인(1절)을 조율한다. 각 에이전트는 파이프라인 단계를 감싸는 얇은 층이고,
  로직은 라이브러리 계층(`src/zzaimy`)에 둔다. 특정 에이전트 프레임워크에 묶이지 않는다.
- 검수 화면: 초안 생성·검토, 배점 반영 점검, 실적 카드 검수 화면. 초안은 사람이 검수해 완성한다는 원칙을 화면에 표시한다.

현황: 문서 작성 쪽은 Writer가 도구를 고르고 코드가 실행하는 문서 작업 에이전트(`app/doc_agent.py`)로 구현했다.

- Writer는 매 걸음 상태(요청, 최근 대화, 프로젝트 문서 목록, 작업본의 절 목록과 빈 절, 받지 못한 값, 지금까지 한 걸음)를 보고
  도구 하나와 그 인자를 고른다. 도구는 근거 찾기, 찾은 문서 이어 읽기, 절 읽기, 문서 만들기, 프로젝트 문서 열기, 그림 쪽 판독, 절 쓰기·다시 쓰기,
  검토, 편집, 한글 내보내기, 작업본 새로 만들기, 안내 상자 지우기, 값 기억, 자료로 값 채우기, 답하기, 묻기, 마무리다.
  코드는 요청 글을 낱말 규칙으로 다시 해석하지 않고 고른 인자로 해당 함수를 바로 부른다.
- 절을 쓰기 전 필요한 정보와 검색어는 Writer가 정하고(`app/context_plan.py`), 문서 양식은 Writer가 후보 안에서 고른다
  (`app/form_choice.py`, ADR-0060).
- 열람 범위, 수치 근거 대조, 양식 모양, 품질 검사, 걸음·쓰기 횟수 상한, 같은 걸음 되풀이 멈춤은 코드가 지킨다. 되돌리기
  어려운 도구는 담당자 요청 글에 그 뜻이 있을 때만 실행하고, 이 관문은 모델이 낸 인자로 건너뛸 수 없다. 걸음 한도에 닿았을 때
  찾은 근거가 있으면 답하기 도구만 고를 수 있는 마지막 걸음을 한 번 더 주고, 문서를 바꾸는 도구는 한도 뒤에 돌지 않는다.
- 찾은 문서 이어 읽기는 이번 요청의 검색 결과에 있던 문서만, 열람 범위를 다시 확인한 뒤 검색과 같은 조각 글로 읽는다.
- 상태·걸음 기록·도구 결과는 자료 울타리 안에만 넣고, 자료 속 울타리 기호와 머리말은 전각으로 바꿔 흉내 낼 수 없게 한다.
- 받지 못한 값은 사실(자료에서 찾을 값)과 결정(담당자가 정할 값)으로 나눈다. 사실 값은 이 프로젝트 문서의 검색 결과에
  글자 그대로 있을 때만 출처와 함께 확인 전 제안으로 남기고, 담당자가 확인해야 담당자 값이 된다.
- 낱말 규칙 경로로 물러나는 것은 모델에 닿지 못했거나 형식 오류가 두 번 났을 때뿐이다. 도구 실패는 모델에 돌려주어
  다시 고르게 한다.
- 걸음 기록(`doc_agent_episodes.jsonl`)은 컨텍스트 구성 추론 학습의 재료로 남긴다.

자세한 도구 표와 관문은 [문서 작업 흐름](document-work-flow.md) 3절에 있다.

## 10. 도메인 중립 공통 계층 (ADR-0003)

국고사업은 첫 적용 도메인이다. 채용 서류 검토 같은 다음 도메인을 위해 인제스트 공통 계층(파싱·개인정보 인식·분류·
열람 등급)에는 국고사업 전용 가정을 넣지 않는다. 파서 인터페이스, 개인정보 인식기, `AccessLevel`은 문서 도메인과
무관하게 구현돼 있다. 실적 카드, 배점 검증, 예산 같은 국고사업 고유 로직은 도메인 모듈로 분리한다.

## 10.2 웹 한글 기안기 공동 편집 (ADR-0070, 10-24)

한글 문서함의 같은 문서를 여러 사람과 AURA 가 칸(누름틀) 단위로 함께 고친다. 처리 방식별로 사용자가 보는 것·뒤의 일·걸리는 시간은 개발자 화면 「처리 흐름 › 공동 편집 처리 방식」 표(app/process_flow.COEDIT)가 정본이다. 기안기 공개 API 에 문서 바뀜 사건이 없어 글자 단위 병합 대신
칸 임대 + 칸 글 전체 전송 + 서버 정답으로 짰다. 자세한 동작과 측정은 ADR-0070, 논문 원재료 5.6.

| 층 | 모듈 | 맡는 일 |
|---|---|---|
| 어댑터 | static/webhwp-wrapper.js | 기안기 API 를 부르는 유일한 곳(칸 읽기·쓰기, 편집 가능 켜기·끄기, 커서 저장·되돌리기, 칸 자리 재기, 입력·한글 조합 사건) |
| 공동 편집 층 | static/webhwp-collab.js · webhwp-collab.css | 임대, 보낼 줄(IndexedDB 에도)·받을 줄, 판 번호, 지문 대조, 충돌 사본, 머리줄 아바타·칸 표시·누름 막 |
| 화면 | templates/hwp_edit.html | 두 층을 잇기만 한다 |
| 경로 | app/webhwp_coedit_routes.py · webhwp_routes.py | /hwp/{id}/coedit · events(SSE) · ops · lease · leave · conflicts, presence |
| 서버 정답 | app/webhwp_coedit.py | 표 일곱(webhwp_field_locks · webhwp_field_state · webhwp_field_ops · webhwp_field_edits · webhwp_conflicts · webhwp_events · webhwp_presence), 문서별 쓰기 줄 세우기, 파일 써 넣기 |
| 파일 | app/webhwp_write.py · webhwp.py | set_fields 로 hwpx 필드에 쓰고 save(앞 판은 .판/) |

```
[창 A] 키·조합 사건 → 어댑터가 칸 글 읽기(조합 중엔 안 읽음)
   → 공동 편집 층: 첫 고침에 POST /lease, 300ms 마다 POST /ops {client, seq, base, 칸 글}
                                       │
[서버] 문서별 잠금 안에서: 같은 (client, seq) 면 같은 답 / base 어긋남·남의 임대면 충돌 사본
       → webhwp_field_state 판 번호 올림 → webhwp_events 에 알림 → 3초 뒤(최대 20초) hwpx 써 넣기
                                       │ SSE /events
[창 B] 판 번호가 앞선 글만, 입력이 300ms 멈추고 조합 중이 아닐 때 PutFieldText → 커서·스크롤 되돌림
       0.25초마다 칸 자리 다시 셈(기안기 커서 모델) → 옅은 바탕·색 커서·이름 깃발·누름 막
```

칸 밖 고침(본문·표 행·용지)은 구조 잠금을 쥔 한 사람이 문서 전체를 저장하고, 서버가 칸 글 표를 덮어 써 다른 사람의 칸 글을 지킨다.

칸 글이 어디에 있다가 파일로 가는지: 화면에서 친 글은 먼저 운영 DB(PostgreSQL)의 `webhwp_field_state` 에 칸마다 판 번호와 함께 남는다.
임시 저장소가 아니라 영구 표이고, 사람 사이의 정답이다. 마지막 고침 3초 뒤(계속 고치면 20초마다) 서버가 문서별 잠금 안에서
hwpx 의 그 누름틀 범위(fieldBegin ~ fieldEnd) 안 글만 바꿔 써 넣는다(`overlay` → `set_fields`). 글자는 그 칸의 원래 문단·글자 모양을
이어받으므로 양식 서식이 그대로이고, 앞 판은 `.판/` 폴더에 남는다. 내려받기·미리 보기·27B 읽기는 모두 이 hwpx 를 본다.
시간 값은 설정 표 `coedit:<키>` → `ZZAIMY_COEDIT_<키>` → 기본값 순으로 읽는다. 창 번호는 로그인한 사람과 묶어 남의 변경을 막는다.

## 10.3 27B 가 문서에 쓰는 길 (ADR-0060·0065·0068, 10-25)

채팅·업무 도우미·시연의 「AURA로 쓰기」는 모두 같은 길로 간다(`main._schedule_answer` → `_run_doc_agent`). 27B 는 vLLM 의 OpenAI 호환
API 로 불리고, 걸음마다 `{생각, 도구, 인자}` JSON 하나를 낸다. 코드는 그 도구를 실행하고 결과를 다음 걸음에 돌려준다(`doc_agent.run`,
걸음 한도 14·문서 바꾸는 도구 4번). 무엇을 쓸지·어느 절을 쓸지·무엇을 더 찾을지는 27B 가 정하고, 코드는 도구·관문·기록만 맡는다.

| 단계 | 하는 곳 | 내용 |
|---|---|---|
| 양식 고르기·만들기 | `webhwp_agent.forms` · `form_create` | 공통 양식(코드로 만든 `양식:*`)과 실물 양식 가운데 고르고, 맞는 것이 없으면 실물을 참고해 설계(ADR-0067) |
| 근거 찾기 | 검색 도구(RAG·그래프 단계) | 절의 작성방법을 읽고 필요한 근거를 찾는다 |
| 관문 | `webhwp_agent.gate` → `check_body` | 근거에 없는 숫자, 남은 양식 예시 글자(○○·000), 문맥 한도를 넘는 긴 본문을 거절하고 이유를 27B 에 돌려준다 |
| 쓰기 | `webhwp_agent.write` → `webhwp_write.write_section` | hwpx 의 그 절 누름틀 뒤에 문단·표를 넣는다. 사람이 그 칸을 쥐고 있으면 쓰지 않는다 |
| 꾸밈 | `webhwp_dress` | `> ` 줄은 참고 상자, `<표> 제목` 줄은 표 캡션 스타일, 표 번호는 문서 차례대로 다시 매김 |
| 알림 | `webhwp_coedit.put` · 활동 기록 | 쓴 글을 칸 글 표에도 올려 다른 창이 다시 읽고, 머리줄에 「AURA · 맡긴 사람」 으로 보인다 |

절 하나를 쓸 때 문서 파일을 직접 고치므로(사람의 칸 글처럼 DB 를 거쳐 써 넣지 않는다), 열려 있는 창은 그 절을 다시 불러온다.
절 조각만 창에 밀어 넣는 방식은 구조가 깨져 걷어냈다(ADR-0070 기록).
