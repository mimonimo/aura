# 구글 드라이브 원천 — 1단계(읽기 전용) 설정과 2단계 설계

작성 2026-09-22. 사용자 요청: 구글 드라이브의 문서를 플랫폼으로 끌어오고, 나중에는 구글 독스를 웹 화면 안에서
에이전트와 함께 작업하고 싶다.

## 1단계에서 되는 것

드라이브 폴더 하나를 원천으로 등록하면 공유 폴더(NAS)와 같은 방식으로 문서를 가져온다. 드라이브에는 아무것도
쓰지 않는다. 목록을 읽고 파일을 내려받는다. 구글 독스는 docx, 시트는 xlsx, 프레젠테이션은 pdf로 내보내기 받아
이름 뒤에 그 확장자를 붙인다. 그림·폼·사이트 같은 구글 형식은 문서가 아니라서 건너뛴다. 가져온 파일은 업로드와
같은 처리(부서·등급, 마스킹, 조각, 색인)를 받고, 같은 파일은 다시 들이지 않는다.

코드: `src/zzaimy/ingest/gdrive.py`(백엔드·OAuth), `nas_sync.BACKENDS["gdrive"]`, 경로 `/dev/gdrive/*`.
검증: `tests/test_gdrive.py`(가짜 드라이브 API — 구글에는 아무것도 보내지 않는다).

## 관리자가 한 번 해야 하는 것 (OAuth 클라이언트)

플랫폼이 담당자 대신 드라이브를 읽으려면 구글에 "이 앱"을 등록해야 한다. 계정을 만들거나 로그인하는 일은 사람이 한다.

1. https://console.cloud.google.com 에서 프로젝트를 하나 만든다(이름은 아무거나, 예: zzaimy).
2. "API 및 서비스 → 라이브러리"에서 Google Drive API 를 사용 설정한다.
3. "OAuth 동의 화면"을 만든다. 학교 워크스페이스 계정이면 사용자 유형 내부(Internal)를 고른다. 외부(External)면
   테스트 사용자에 담당자 이메일을 넣는다(테스트 상태에서는 갱신 토큰이 7일 뒤 만료되므로 내부 또는 게시 상태가 맞다).
   범위는 `https://www.googleapis.com/auth/drive.readonly` 하나다.
4. "사용자 인증 정보 → OAuth 클라이언트 ID → 웹 애플리케이션"을 만들고, 승인된 리디렉션 URI에 플랫폼 주소 +
   `/dev/gdrive/callback` 을 넣는다. 정확한 값은 /dev/nas 화면의 구글 드라이브 칸에 표시된다(플랫폼 공개 주소가
   프록시 뒤에 있으면 `.env.local` 의 `ZZAIMY_PUBLIC_URL` 로 맞춘다).
5. 나온 클라이언트 ID·비밀을 /dev/nas 화면의 구글 드라이브 칸에 넣는다. 서버의 `data/platform/gdrive_oauth.json`(0600)에만
   저장되고 화면에는 앞 12자만 보인다.

담당자는 같은 화면에서 "구글 계정 허용"을 눌러 자기 계정으로 한 번 허용한다. 갱신 토큰은 `gdrive_tokens.json`(0600)에
계정별로 남고, 허용 지우기를 누르면 서버 쪽 토큰이 지워진다(구글 쪽 접근 권한은 구글 계정 설정에서 따로 지운다).
그 다음 원천 등록에서 방식 "구글 드라이브", 경로에 폴더 주소(…/folders/ID) 또는 폴더 ID, 계정에 허용한 이메일을 고른다.

## 제약

- 학교 워크스페이스가 외부 앱 접근을 막아 두었으면 관리자 승인이 필요하다. 이 부분은 학교 확인 사항이다.
- 운영 VM에서 googleapis.com 으로 나가는 통신은 열려 있다(2026-09-22 확인). 막히면 이 기능은 조용히 실패하고 원천의
  마지막 실행 사유에 남는다.
- 드라이브의 공유 문서함(공유 드라이브)도 읽는다(supportsAllDrives). 파일 크기는 구글 형식 문서에는 없어 0으로 잡히고,
  변경 감지는 수정 시각으로 한다.

## 2단계 설계 — 구글 독스를 화면 안에서, 에이전트와 함께

원하는 모습은 왼쪽에 구글 독스 편집기, 오른쪽에 에이전트다. 편집기는 iframe 으로 띄운다(`https://docs.google.com/document/d/<ID>/edit`).
담당자가 그 브라우저에서 구글에 로그인돼 있어야 하고, 서드파티 쿠키를 막는 브라우저(사파리 기본값)에서는 iframe 안
로그인이 되지 않는다. 우리 화면은 iframe 안의 내용을 읽을 수 없다(다른 출처). 그래서 에이전트는 화면이 아니라
구글 독스 API로 같은 문서를 읽고(`documents.get`) 고친다(`documents.batchUpdate`). 편집기는 실시간 동기화라
API로 넣은 글이 iframe 에 바로 보인다.

에이전트가 할 수 있는 것과 없는 것:
- 문서 전체 본문·제목 구조를 읽어 근거 검색·검토·초안 생성의 재료로 쓴다.
- 지정한 제목 아래에 글을 넣거나, 특정 문장을 바꾸거나, 표를 넣는다. 커서 위치는 알 수 없으므로 "어디에"는 담당자가
  고른다(제목 목록에서 선택).
- 제안을 직접 쓰지 않고 댓글로 남기는 방식은 드라이브 API 의 댓글(위치 지정 없음)로 가능하다.
- 독스의 "제안 모드"로 넣는 것은 API 가 지원하지 않는다.

필요한 것: 허용 범위에 `documents` 와 `drive.file`(또는 drive)을 더해 다시 허용받기, 문서 작업 화면 하나(iframe + 에이전트
패널, 아스트라), 에이전트 도구 두 개(문서 읽기·삽입), 그리고 규칙 하나. 교내 문서나 검색 근거를 구글 문서에 쓰는
것은 외부 전송이므로 외부 AI 참조 관리와 같은 승인·기록을 거친다. 이 규칙은 ADR 로 먼저 정한 뒤 만든다.
규모는 3~5일이다.
