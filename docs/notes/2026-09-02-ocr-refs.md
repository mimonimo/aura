# OCR 조사 — 엔진 후보·스캔 전처리·고도화 레퍼런스 (2026-09-02)

착수 단계에 따로 적었던 OCR 조사 세 편(엔진 후보, 스캔 전처리·복원, 문서이해 고도화 레퍼런스)을 한 문서로 묶었다.
판정은 그때 것이다. 이후 실측 결정은 ADR-0007(추출 표준), ADR-0050·0051(docling 제외)과 [OCR 엔진 대결](../ocr-duel.md)을 따른다.

## 1. 한국어 OCR 엔진 후보

스캔 행정문서 OCR 인식률·구조 품질을 올릴 엔진 후보 조사와 판정.
현 스택: MinerU 3.4.5 pipeline 백엔드(PP-OCR 계열, 줄 좌표 활용) + Qwen3.5 비전 판독.

전제: 한국어 공개 수치가 있는 후보가 드물다. 어떤 판정이든 실물 30~50p
표본 대조(진행 중인 bake-off 틀) 후 ADR로 확정한다.

### 절대 규칙 관련 주의

end-to-end VLM 계열(dots.ocr, DeepSeek-OCR)은 저품질 스캔에서 텍스트를
그럴듯하게 지어내는 환각 위험이 전통 파이프라인보다 높다. VLM 백엔드를
도입하면 원문 대조 검증을 OCR 출력에도 적용한다 (수치는 인출하고 생성하지
않는다 — 브리프 절대 규칙 1과 동일한 정신).

## 2. 스캔 전처리·복원 후보

OCR 인식률을 올리기 위한 전처리 오픈소스 조사 결과와 판정.
현재 체인은 OpenCV 원근 보정 + CLAHE + 언샤프뿐이다. 조사 상세 출처는 말미.

공통 전제: 효과 수치는 전부 영어·중국어 벤치마크 기준이고 한글 행정문서
실측은 없다. 도입 판정이 나더라도 실물 표본 A/B 후 ADR로 확정한다.
sm_121 실동작도 전 후보 미확인 — 스모크 테스트가 선행돼야 한다.

### 판정

| 후보 | 역할 | 판정 | 근거 |
|---|---|---|---|
| DocRes (CVPR 2024, MIT) | 그림자·조명·디블러·dewarping·이진화 통합 복원 | 도입 후보 1순위 | 단일 모델·CLI 추론으로 폰카 그림자/조명 불균일을 해결. 지금 체인이 못 하는 영역 |

### 안전 원칙

생성형 복원(SR·diffusion)은 글자·숫자를 바꿔칠 수 있다. 절대 규칙 1(수치는
인출)과 같은 정신으로, 전처리 전/후 OCR 결과의 수치 diff 검사를 파이프라인에
넣은 뒤에만 생성형 복원을 통과시킨다.

### 실측 근거 (참고)

- PreP-OCR(ACL 2025): 이미지 복원만으로 Tesseract CER 5.87%→1.99%,
  파이프라인 전체 CER 63.9~70.3% 감소 (영어권 실물 13,831쪽)
- UVDoc: MS-SSIM 0.785 (DocTr 0.697, DocGeoNet 0.706)

## 3. OCR·문서이해 고도화 레퍼런스

온프레미스 제약(DGX Spark, 외부 API 불가) 기준으로 선별했다.

### 즉시 도입 가치 상위 3
1. Kiwi 오타 교정·띄어쓰기 복원을 OCR 후처리에 재사용 (이미 의존성 보유, 비용 최소)
2. PP-StructureV3/SLANeXt 표 구조 모델을 MinerU pipeline backend에 결합
   (같은 PaddleOCR 생태계 — 예산표·배점표 인식 강화, 절대 규칙 1·5와 직결)
3. OpenCV 전처리 표준화: CLAHE 대비 정규화 + 그림자 마스크 + minAreaRect deskew

### 이미 반영된 것 (2026-09-02)
- 문서 영역 원근 보정(OpenCV), 직인 색 분리 크롭, LLM 오타 교정(보수적),
  비전 판독(사진·4쪽 이하 PDF), 장식 아이콘 필터, 다운스케일

### 검증 필요 (파일럿 bake-off 대상)
- olmOCR-2 / Surya OCR 2 / GOT-OCR2 / Qwen3-VL 한국어 실측 — 전부 미확인,
  기존 파서 bake-off(TASK-04)와 같은 방식으로 30~50p 표본 대조 권장
- MinerU VLM backend는 중국어 위주 → 한국어는 pipeline backend 유지가 맞음(확인됨)
- AI-Hub 공공행정문서 OCR(90만 장): 비상업 연구 한정, 지자체·외교 도메인.
  PII 스크리닝 전 인덱싱 금지(절대 규칙 3)

### 프롬프트·해상도 관행
- Qwen3-VL 계열은 동적 타일링 지원 — 과도한 축소보다 2000px급 유지가 유리
- 표/본문/직인 영역 분리 후 태스크별 프롬프트가 검증 추적에 유리 (환각 억제)
- 페이지 경계를 넘는 표는 인접 페이지 컨텍스트 포함 필요 (예산표 대응)

### 외부 레퍼런스 검토 (2026-09-02)

|---|---|---|---|

| Upstage OCR 라벨링 인터뷰 | 라벨링 기준 설계·품질 관리·특화 모델 구축 실무 | **프로세스 도입** (도구 아님) | 아래 세 가지를 실데이터 파일럿 계획에 반영한다 |

Upstage 인터뷰에서 가져올 세 가지:
1. 일반+특화 병행 — 범용 추출(현 파이프라인)을 유지하고, 자주 오는 서식(공고문·
   신청서)만 특화 처리를 얹는다. 전면 교체 금지
2. 하드케이스 마이닝 루프 — 초기 모델로 대량 처리 → 어려운 케이스만 골라 라벨링 →
   재학습. 우리 플랫폼의 판정(승인·반려)·담당자 의견이 곧 이 라벨링 채널이다.
   담당자가 고친 부분이 학습 데이터가 되며, 별도 라벨링 도구 없이 운영 중에 모은다
3. 실수 방지형 입력 설계 — 라벨(판정·의견)을 받는 UI가 데이터 품질을 정한다.
   판정 3버튼·의견 텍스트 같은 제약된 입력을 유지하고 자유 형식을 늘리지 않는다
