# 서빙 엔진 검토 — vLLM과 Ollama

2026-09-22

서빙 장비를 토르 두 대로 나누던 날, 굳이 vLLM을 쓰지 않고 Ollama로 서빙하면 되지 않느냐는 물음이
있었다. 두 엔진을 우리 장비에서 실제로 써 본 결과와, vLLM 하나로 통일한 이유를 정리한다.

## 두 엔진의 성격

vLLM은 서버용 추론 엔진이다. 여러 사람의 요청을 한데 묶어 GPU를 채우고, OpenAI와 같은 규격의
API를 낸다. 모델은 허깅페이스에 올라온 원본과 양자화 판을 그대로 읽는다. 학습으로 얻은 LoRA
어댑터를 서빙 중에 붙여 쓸 수 있고, NVIDIA가 젯슨용 컨테이너를 모델별로 배포한다.

Ollama는 개인 컴퓨터에서 모델을 받아 바로 돌려 보는 실행기다. 편의성이 핵심이며 모델은 GGUF라는
변환 형식으로 받는다. 요청은 기본적으로 하나씩 처리하고, 학습본을 쓰려면 병합해서 GGUF로 다시
만들어야 한다. 젯슨용 패키지는 있지만 새 모델 지원이 늦다.

## 우리 장비에서 겪은 것

토르에 깔린 Ollama는 Qwen3.8을 읽지 못했다. 이 모델을 Ollama로 올리려면 GGUF로 바꾼 다른 판을
받아야 하는데, 그 판은 NVIDIA가 젯슨의 FP4 가속으로 검증한 판이 아니다.

Ollama는 문맥 길이를 모델 태그의 기본값인 26만 토큰으로 잡아 호출마다 메모리를 크게 요구했고,
모델이 계속 올라갔다 내려갔다 하면서 호출이 시간 초과됐다. 문맥을 줄인 설정 파일을 따로 만들자
같은 8천 자 요약이 113초에서 5초로 줄었다. 서버로 쓰려면 이런 손질이 모델마다 필요하다.

vLLM은 젯슨용 공식 컨테이너로 27B 원본과 NVFP4 양자화 판을 올렸다. 양자화 판은 요청 하나에
초당 10토큰 남짓으로 원본의 서너 배 속도가 나왔고, 같은 입력에서 내용이 같았다. 다만 양자화 판은
기본 빌드가 아니라 Qwen3.8 전용 빌드가 필요했고 FP8 판은 그 빌드에서도 뜨지 않았다. vLLM이라고
아무 판이나 되는 것은 아니다.

DGX의 Ollama로 27B 4비트 판을 돌리면 요청 하나에 초당 19토큰이 나왔다. 장비가 달라 직접 비교는
어렵고, 학습 전용 장비를 서빙에 쓰는 것은 계획과 맞지 않아 임시로만 썼다.

## vLLM으로 통일한 이유

첫째, 학습본을 그대로 올린다. DGX에서 LoRA로 학습한 모델을 vLLM은 어댑터째 붙이거나 병합본을
양자화해 올리면 된다. Ollama는 GGUF 변환이 한 단계 더 들어가고 그 과정에서 정밀도가 바뀐다.

둘째, 동시 요청을 견딘다. 검토 배치와 대화를 두 장비로 나눴어도 한 장비 안에서 요청은 겹친다.
요청을 묶어 처리하지 않으면 대기가 줄줄이 생긴다. 원본 판으로 잰 실측에서는 동시 세 요청의 생성
속도 합이 초당 14토큰에 그쳤다.

셋째, API 규격이 하나다. 플랫폼은 답변, 검토, 판독, 질의 확장을 모두 같은 규격으로 부른다. 장비마다
엔진이 다르면 코드가 갈라진다. 실제로 Ollama는 생각 끄기 인자를 무시해 따로 처리를 넣어야 했다.

넷째, 젯슨의 FP4 가속을 쓰는 검증된 경로가 vLLM 컨테이너다.

## Ollama가 맞는 자리

개인 컴퓨터에서 모델을 빨리 시험할 때, 또는 사용자가 한 명이고 학습본 교체가 없는 작은 서비스에는
Ollama가 낫다. 학습본을 계속 바꾸고 여러 사람이 동시에 쓰는 교내 서비스에는 맞지 않는다. 토르의
Ollama는 용도에서 빠졌다.
