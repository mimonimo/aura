# 기술 검토 — 서빙 엔진: vLLM 과 Ollama

작성 2026-09-22. 9/21 서빙 장비를 나누며 "Ollama 로 그냥 서빙하면 되지 않나"는 물음이 있었다. 두 엔진을
같은 장비(젯슨 AGX 토르, DGX)에서 실제로 써 본 결과와, 우리가 vLLM 하나로 통일한 이유를 적는다(ADR-0023).

## 1. 두 엔진이 무엇인가

| | vLLM | Ollama |
|---|---|---|
| 성격 | 서버용 추론 엔진 — 요청을 묶어(batching) GPU 를 채우고 OpenAI 규격 API 를 낸다 | 개인 PC 용 실행기 — 모델을 받아 바로 돌리는 편의성이 핵심 |
| 모델 형식 | HF 원본(safetensors)·양자화(FP8·NVFP4·AWQ 등) 그대로 | GGUF(llama.cpp 계열) 변환본 |
| 동시 요청 | 연속 배칭 — 여러 요청을 한 번에 처리 | 기본은 순차, 병렬은 제한적 |
| LoRA 학습본 | 어댑터를 서빙 중에 붙여 쓸 수 있음 | 병합해서 GGUF 로 다시 만들어야 함 |
| 젯슨 지원 | NVIDIA 가 젯슨용 컨테이너를 공식 배포(모델별 빌드) | 패키지는 있으나 최신 모델 지원이 늦음 |

## 2. 우리 장비에서 실제로 겪은 것

- 토르의 Ollama(0.32.6)는 Qwen3.8 을 아예 읽지 못했다(모델 형식 미지원, 갱신에는 sudo 필요). 27B 를
  Ollama 로 올리려면 GGUF 로 바꾼 다른 판을 받아야 하고, 그 판은 NVIDIA 가 젯슨 FP4 로 검증한 판이 아니다.
- Ollama 는 문맥 크기를 모델 태그의 기본값(262K)으로 잡아 호출마다 메모리를 크게 요구했고 모델이 계속
  올라갔다 내려갔다 해 호출이 시간 초과됐다. 문맥을 줄인 Modelfile 을 따로 만들어야 8천 자 요약이
  113초 → 5.2초가 됐다(HANDOFF §1). 서버용으로 쓰려면 이런 손질이 모델마다 필요하다.
- vLLM 은 젯슨용 공식 컨테이너로 27B 원본(bf16)과 NVFP4 판을 올렸고, NVFP4 는 요청당 10.4~10.9 토큰/초로
  bf16 의 3~4배, 내용 동일(ADR-0023 표). 다만 양자화 판은 기본 빌드(vLLM 0.19)가 아니라 Qwen3.8 전용
  빌드가 필요했고, FP8 은 그 빌드에서도 실패했다 — vLLM 도 "아무 판이나" 되는 것은 아니다.
- DGX 의 Ollama(27B 4bit)는 요청당 18.8 토큰/초로 빨랐지만 장비가 다르고(DGX 대역폭), 학습 전용 장비를
  서빙에 쓰는 것은 계획 위반이라 임시로만 썼다(9/21 14~17시, 이후 연결 삭제).

## 3. 결정 — vLLM 하나로 통일한 이유

1. 학습본을 그대로 올린다. DGX 에서 LoRA 로 학습한 Writer 를 vLLM 은 어댑터째 또는 병합본을 NVFP4 로
   양자화해 올린다(ADR-0023 §3). Ollama 는 GGUF 변환이 한 단계 더 들어가고 그 변환에서 정밀도가 바뀐다.
2. 동시 요청. 반입 검토(배치)와 대화(사람이 기다림)를 두 토르로 나눴어도 각 장비 안에서는 여러 요청이
   겹친다. 연속 배칭이 없으면 대기가 줄줄이 생긴다(bf16 실측: 동시 3요청 합계 14 토큰/초).
3. 하나의 API 규격. 플랫폼은 OpenAI 규격 하나로 답변·검토·판독·질의 확장을 부른다. 장비마다 엔진이
   다르면 "DGX 는 이거, 토르는 저거" 식 뒤죽박죽이 되고, 생각 끄기 같은 인자도 엔진마다 달라 코드가
   갈라진다(실제로 Ollama 는 vLLM 식 인자를 무시해 별도 처리를 넣어야 했다).
4. 젯슨 정밀도. FP4 하드웨어 가속을 쓰는 검증된 경로가 vLLM 컨테이너다.

## 4. Ollama 가 맞는 자리

개인 PC 에서 모델을 빨리 시험해 볼 때, 또는 사용자가 한 명이고 학습본 교체가 없는 작은 서비스. 우리처럼
학습본을 계속 바꾸고 여러 사람이 동시에 쓰는 교내 서비스에는 맞지 않는다. 토르의 Ollama 는 서빙 실험용
흔적(`zzaimy-answer`·`zzaimy-review`)만 남아 있고 용도에서 빠졌다.

관련: ADR-0004(초기 서빙 스택), ADR-0023(두 토르 분담·정밀도), HANDOFF §1, configs/serving.yaml.
