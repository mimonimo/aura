# AI 읽기 표/레이아웃 원본 불일치 — 원인 진단

작성 2026-09-08. 사용자 지적(문서 104·105 "연계교육과정 편성표", MinerU 파싱)
세 증상을 코드 조사 + 실데이터 렌더로 진단했다. 이 문서는 조사·보고이며 수정은
합의 후. 캡처: `scratchpad/tbl_render.png`(현재), `scratchpad/tbl_mid.png`(개선안).

## 방법

- 렌더 경로 코드 읽기: `render.py`(table_html·chunk_blocks·layout_pages),
  `parsers/html_table.py`(HTML 표 파서), `parsers/mineru.py`(MinerU 경로).
- 실데이터 확인: VM에서 문서 104·105 표 조각의 셀 구조를 조회.
- 실제 병합 표(문서105 chunk 5735, 11x4, 병합 4)를 실 CSS로 렌더해 눈으로 대조.

## 증상 1 — 세로 병합이 안 살아 보인다 → **렌더 버그 아님, CSS 표현 문제**

결론: 데이터·렌더는 정확하다. 병합은 구조적으로 살아 있고, 화면에서 "안
살아 보이는" 건 세로 정렬 때문이다.

근거.
- 데이터: 문서105 표의 "C프로그래밍1" 셀은 `[row=3, col=0, rowspan=2, colspan=1,
  header=0, "C프로그래밍1"]`. **rowspan=2가 정확히 들어 있다.** 커버된 (row4,col0)은
  셀 목록에 없다(표준 HTML 모델). 빈칸 0.
- 파서(html_table.py): `_occupied` 집합으로 rowspan/colspan 점유 좌표를 추적하고
  커버된 칸을 건너뛴다. placeholder 빈 셀을 만들지 않는다 — 올바르다.
- 렌더(table_html): 각 행의 셀을 열 순으로 `rowspan/colspan` 속성과 함께 낸다.
  합성 입력 검증에서 정상 병합은 `<td rowspan="2">`로, 병합 실패(빈칸) 입력만
  "아랫행 빈 칸"으로 나온다. 실데이터는 전자다.
- 실 렌더 확인: 병합 셀이 2행 높이 한 칸으로 정확히 그려진다(오른쪽 열은 2개
  행). 다만 `table.extract td { vertical-align: top }`이라 텍스트가 칸 위쪽에
  붙어 아래 절반이 비어 보인다 — 이것이 "첫 행에만 값, 아랫행 빈 칸"의 정체다.

해법(합의 시): `table.extract th, table.extract td`의 `vertical-align: top`을
`middle`로. before/after 캡처로 확인했고, middle이면 병합 셀 텍스트가 두 행
중앙에 놓여 원본 편성표처럼 "한 칸이 두 행을 덮는" 게 명확해진다. 한 줄 변경,
저위험. 위치는 `base.html`의 `.extract` CSS(공용 파일이라 소유자와 조율 필요)
또는 render.py에서 병합 셀에 인라인 정렬을 부여하는 방식.

## 증상 2 — 표 비율(열 폭·전체 폭)이 원본과 다르다 → **기하 정보 부재 (부분 수정 가능)**

결론: MinerU 경로 표에는 열 폭(col_w)이 없어 내용 기준 자동 폭으로 그려진다.
원본의 고정 비율과 어긋난다. 렌더 버그가 아니라 입력에 기하 정보가 없다.

근거.
- 문서 104·105의 모든 표 조각이 `col_w=False`. 렌더의 col_w 분기(고정 레이아웃)
  는 col_w가 있을 때만 탄다.
- 괘선 직독(`lattice.py`, 디지털 PDF 전용)은 실제 괘선 위치에서 col_w를 만든다.
  하지만 이 문서들은 스캔/이미지라 MinerU 경로로 가고, MinerU는 표를 HTML
  (`table_body`)로만 내보내 **셀 좌표(bbox)가 없다** — `mineru.py`는 표 전체
  bbox만 잡고 셀 단위 폭 정보는 받지 않는다.

해법 후보(우선순위).
- (a) MinerU middle.json이 셀 단위 bbox를 내는지 **확인 필요**. 낸다면
  `mineru.py`에서 셀 x좌표로 열 경계를 추정해 col_w를 계산할 수 있다(중간 난이도).
- (b) 셀 bbox가 없으면, 표 구조를 좌표까지 읽는 비전 모델(GPU 후속)이 필요하다.
현재 코드만으로는 스캔 표의 원본 비율 복원이 불가하며, (a) 가능 여부가 갈림길이다.

## 증상 3 — 제목 박스(테두리 틀) 유실 → **레이아웃 충실도 한계 (후속)**

원본의 테두리 사각형(제목 틀)은 표가 아닌 레이아웃 요소다. "AI 읽기"는
읽기 순서 흐름 렌더(chunk_blocks)라 독립 테두리 틀을 재현하지 않는다.
bbox 기반 원본 배치 복원(layout_pages)은 디지털 PDF용이고 이 스캔 요소엔
약하다. 원본 틀까지 살리려면 배치 복원 경로 확장이나 비전 접근이 필요하다
(빠른 흐름-렌더 수정 대상 아님).

## AI 읽기가 쓰는 렌더 경로

"AI 읽기"(doc.html의 viewFlow)는 `chunk_blocks`(읽기 순서 흐름)를 쓴다 —
표 조각마다 `table_html` 호출. `layout_pages`(bbox 배치)는 디지털 PDF 원본
배치 복원용 별도 경로다. 따라서 AI 읽기 표는 기하 정보 없이 자동 폭·흐름 배치다.

## 경계 요약 (어디까지 렌더 버그, 어디부터 스캔 한계)

| 증상 | 판정 | 조치 |
|---|---|---|
| 1 병합 안 살아 보임 | 렌더 버그 아님 — CSS 세로정렬 | `vertical-align: middle` 한 줄(저위험, 즉시) |
| 2 비율·열 폭 불일치 | 입력에 기하 부재(MinerU 스캔) | MinerU 셀 bbox 확인 → 있으면 col_w 계산, 없으면 비전 후속 |
| 3 제목 틀 유실 | 레이아웃 충실도 한계 | 배치 복원 확장/비전 후속(빠른 수정 아님) |

렌더·파서 자체에는 버그가 없다. 증상 1은 표현 한 줄로 즉시 개선되고, 2·3은
스캔 표의 기하·레이아웃 정보 부족이 근본이라 MinerU 셀 좌표 확보 여부와
GPU 비전 후속에 달려 있다.
