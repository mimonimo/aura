# kordoc 조사 — 서식 보존 작성에 흡수할 기술 (2026-09-30)

한글 완성본(ADR-0035, `ingest/hwpx_fill.py`)을 더 원본답게 만들려고 kordoc 4.15.7 의 쓰기·편집 쪽을 다시 봤다.
규칙은 그대로다. kordoc 의 흐름을 들이지 않고 원리만 가져오며, 채택은 대조 수치로 좁게 한다. 문서별 정답을 코드에 넣지 않는다.

조사 방법

- README 1,392줄 전부(변경 내역 포함)를 읽었다.
- dist 의 소스맵(`*.js.map`)에 TypeScript 원문이 들어 있어 거기서 `roundtrip/`·`form/`·`hwpx/`·`validate.ts` 를 복원해 읽었다.
- VM `/tmp/kordoc-survey/` 에 557 작성서식(ver5) 원본.hwpx 사본을 두고 patch·validate·generate·profile·render 를 돌렸다. 끝나고 지웠다. 저장소와 문서함은 건드리지 않았다.

## 2. 기술별 동작

### 2.1 patch — 소스맵 끼워 넣기 (`roundtrip/patcher.ts`·`source-map.ts`)

- 구역 XML 을 DOM 으로 다시 쓰지 않고 정규식 토크나이저로 문단·셀·`hp:t` 의 글자 위치를 기록한 뒤 그 위치만 바꾼다. 우리 hwpx_fill 이 이미 이 원리다.
- 원본 마크다운 유닛과 편집 유닛을 정렬해 바뀐 것만 고친다. 추가·삭제·순서 변경은 건너뛰고 사유를 남긴다.
- 문단 글 바꾸기는 첫 `hp:t` 에 새 글을 넣고 나머지 `hp:t` 를 비운다. run 과 charPr 는 그대로다. 원래 글의 앞뒤 공백(들여쓰기)을 새 글에 다시 입힌다.
- 부호 run 보존(`markerRunSplices`): 첫 `hp:t` 가 "부호 + `<hp:tab/>`" 꼴이면 부호 run 은 두고 뒤 글만 바꾼다. 문단 전체를 다시 쓰면 탭이 공백이 되어 내어쓰기 정렬이 깨지기 때문이다.
- 글이 바뀐 구역은 `linesegarray` 를 전부 지운다(일부만 지우면 한컴이 여전히 변조 경고). 우리와 같다.
- 끝나면 패치본을 다시 읽어 편집 마크다운과 견준 잔차(`verification`)를 낸다.
- 4.15.7 에서도 블록 추가는 안 된다. 실측: 1.1 절 【작성방법】 뒤에 "□ …"·"○ …" 두 문단을 더한 편집은 "블록 추가는 미지원 (v1)" 두 건으로 건너뛰었다. ADR-0035 의 판단이 여전히 맞다.

### 2.2 표 행 추가·삭제 (`roundtrip/table-rows.ts`)

- 행 정렬로 유지·삭제·삽입을 가른다. 새 행은 이웃 유지 행의 `<hp:tr>` 을 통째로 복제하고 셀 글만 바꾼다. 머리 행(0행)은 본으로 쓰지 않고 다음 자료 행을 우선한다.
- 같이 고치는 것: 표 `rowCnt`, 뒤따르는 행의 `cellAddr rowAddr`, 표 `hp:sz height`(더한 행 높이만큼), 복제 조각 안 `linesegarray` 제거.
- 막는 조건: 세로 병합이 삽입·삭제 자리를 가로지름, 본 행에 중첩표·그림·필드가 있음, 본 행이 격자를 다 덮지 않음, 새 행의 칸 수·가로 병합이 본 행과 다름, `cellAddr` 표기가 섞임, `rowCnt` 가 실제 행 수와 다름.
- 실측(557 서식 사본):
  - 표지 4열 표에 행 하나 추가 → 적용, validate 통과.
  - 비목별 집행 계획 표의 "합 계" 아래에 행 추가 → 적용. 새 행은 합계 행의 칸별 borderFill(244·245·246)·paraPr·charPr·칸 여백을 그대로 가졌고 `rowCnt` 24→25, 표 높이 39984→41366 이 맞게 바뀌었다.
  - 같은 표의 "장학금" 묶음(세로 병합 3행) 안에 행 추가 → "행 삽입 위치가 세로 병합 내부 — 미지원" 으로 건너뜀. 예산표는 이 꼴이 흔하다.

### 2.3 문단을 표로 (`roundtrip/table-insert.ts`)

- 새 표 id 는 문서 전체 숫자 id 최댓값 다음. header 의 `borderFills` 에 실선 하나를 덧붙이고 `itemCnt` 를 올린다. 우리 hwpx_fill 이 이미 흡수한 부분이다.
- 표 폭은 44000 고정 균등 분할, 셀 문단·글자 모양은 id 0, 바깥 문단만 원래 문단의 paraPr 를 잇는다. 서식의 표 모양은 따르지 않는다. 이 점은 우리가 이미 더 낫다(본문 표의 실선 borderFill 승계, 작업본 열 비율).

### 2.4 양식 채우기 (`form/filler-hwpx.ts`·`click-here.ts`·`match.ts`)

- 순서: 누름틀(CLICK_HERE) 이름 정확 매칭 → 칸 안 패턴(체크박스 □→☑, "(   )" 빈칸, "(한자：)" 주석) → 라벨|값 이웃 칸 → 첫 행이 전부 라벨인 표의 열 매칭 → 표 밖 "라벨: 값".
- 값의 `\n` 은 새 문단이 아니라 문단 안 강제 줄바꿈(`<hp:lineBreak/>`)으로 넣는다.
- 값에 배열을 주면 같은 라벨의 등장 순서대로 하나씩 쓴다. `--require-unique` 는 한 키가 두 곳 이상 맞으면 거부한다.
- 우리 일(절 본문)과는 다르지만 신청서·기입란 표에는 그대로 쓸 수 있는 규칙들이다.

### 2.5 그림 넣기 (`form/seal.ts`·`hwpx/gen-image.ts`)

- `BinData/imageN.ext` 는 기존 BinData 번호와 manifest id 둘 다 피해서 고른다. manifest 에 `isEmbeded="1"` 로 등재. 우리와 같다.
- 확장자와 매직 바이트가 맞는지 본다(JPEG 은 `FF D8 FF` 세 바이트). 우리는 두 바이트만 본다.
- 96dpi 픽셀 = 75 HWPUNIT, 본문 폭을 넘으면 비례 축소. 우리와 같다.

### 2.6 마크다운 → 새 HWPX (`hwpx/gen-*.ts`·`style-registry.ts`)

- 스타일 등록기: 원하는 문단·글자 모양을 사양(정렬·왼쪽 여백·내어쓰기·줄 간격·autoTab …)으로 요청하면 같은 사양은 같은 id, 없으면 새 id 를 header 에 덧붙인다. 손으로 id 를 셈하다 한 칸 밀리는 사고를 막으려고 만든 것이라 한다.
- 개조식 부호: 부호 run 을 "부호 + `<hp:tab>`" 으로 쓰고, paraPr 는 `indent = -(부호 폭 + 1타)`·내어쓰기용 자동 탭(tabPr `autoTabLeft="1"`)과 짝을 짓는다. 둘째 줄이 첫 줄 내용 시작과 맞는다.
- 표: 머리 행 음영(#DFE6F7)·굵게·아래 이중선, 라벨 열 음영, 비고·근거 열은 좁게(25% 이내)·내용 열은 넓게.
- 실측: 우리 절 본문 꼴의 짧은 마크다운(소제목 둘, 2단계 목록, 3열 표, 출처 줄)을 `--preset 보고서` 로 만들었다. validate 통과, kordoc 렌더로 보면 장 띠·□/○ 위계·머리 행 음영 표·※ 출처 줄이 공문서답게 나온다. 다만 '~다' 종결을 문체 경고로 잡고 □ 두 줄 꺾임을 경고한다(보고서 문체 강제).
- 판단: 품질은 좋지만 서식을 새로 만드는 것이라 "공고 서식 그대로" 라는 우리 제출 조건에 맞지 않는다. 최종본 경로로 쓰지 않는다. 흡수할 것은 부호·내어쓰기 원리와 스타일 등록기다.

### 2.7 표 서식 프로필 (`hwpx/extract-profile.ts`·`gen-profile.ts`)

- 원본 표마다 칸별 borderFill 정의(테두리 종류·굵기·색, 채움색), 열 실폭, 칸 첫 run 의 charPr(글꼴 이름 포함)를 뽑는다. 병합 칸 폭은 알려진 열을 뺀 나머지를 나눠 채운다.
- 적용 때는 새 문서 header 에 새 id 로 다시 등록하고(재매핑) 표 대응은 행·열 수 일치 + 첫 칸 글 앵커(없으면 첫 행 지문, 그것도 없으면 순번)로 한다. 앵커가 다르면 적용하지 않는다(서식 없음이 틀린 서식보다 안전).
- 실측: 557 서식에서 표 90개를 뽑았다. 우리 새 표에 입히면 앵커가 달라 아무것도 적용되지 않았다. 표 단위 복제는 새 표에 맞지 않고, 역할(머리 행·라벨 열·본문 칸)별로 모아 쓰는 쪽이 우리에게 맞다.

### 2.8 구조 검증 (`validate.ts`)

- 보는 것: ZIP 인지, `mimetype` 이 첫 항목이고 내용이 `application/hwp+zip` 인지, 필수 파일, `.xml/.hpf/.rdf` 웰폼드, header `secCnt` = 실제 구역 수, manifest href 실존.
- 안 보는 것: 본문이 가리키는 paraPr·charPr·borderFill·style id 가 header 에 있는지, `itemCnt` 가 실제 개수와 맞는지, `binaryItemIDRef` 가 manifest 에 있는지, 표 `rowCnt`·격자 덮개가 맞는지. 우리가 새 id 를 만들수록 이쪽이 사고 지점이다.
- 조사용으로 이 네 가지를 보는 짧은 점검을 만들어 원본·우리 완성본(9/29 15:44)·kordoc 행 추가본·kordoc 생성본에 돌렸다. 넷 다 문제 0건(우리 완성본 참조 paraPr 2,788·charPr 3,106·borderFill 1,984). 지금은 깨끗하다는 뜻이고, 앞으로 모양을 새로 등록하기 시작하면 이 점검이 회귀 방지선이 된다.

### 2.9 그 밖의 작은 원리

- ZIP 부분 교체(`zip-patch.ts`): 중앙 디렉터리를 직접 읽어 바뀐 항목의 로컬 레코드만 다시 쓰고 나머지는 압축된 바이트를 그대로 복사한다. 우리는 안 바뀐 항목도 다시 압축한다(CRC 는 같고 압축 바이트는 다를 수 있다). 한글이 여는 데는 차이가 없어 급하지 않다.
- 글 이스케이프(`escapeXmlText`): XML 1.0 에서 금지된 C0 제어문자(\t \n \r 제외)를 지운다. 문서가 안 열리는 손상을 막는 한 줄이다.
- splice 적용(`applySplices`): 시작 위치로 정렬해 한 번에 잇고 겹치면 오류로 멈춘다. 우리는 뒤에서부터 잘라 붙이며 겹침을 검사하지 않는다.

### 2.10 render 를 미리보기로 쓸 수 있나

- 우리 완성본(바뀐 구역만 줄 배치 캐시가 없는 섞인 문서)을 렌더하면 "조판 캐시 없는 문단 텍스트 생략" 경고와 함께 64쪽 문서가 53쪽으로 나오고 넣은 글이 빠진다.
- 캐시를 전부 지운 사본은 reflow 로 56쪽이 되지만 18쪽이 도형만 남는 등 실서식 문서에서는 쓸 수 없었다.
- 판단: 미리보기는 지금처럼 우리 변환기 → LibreOffice PDF 로 둔다. kordoc render 는 kordoc 이 만든 단순 문서 확인용 정도다.

## 3. 우리 hwpx_fill 의 현재 상태

이미 하는 것

- 바이트 보존 끼워 넣기, 바뀐 구역만 줄 배치 캐시 제거, ZIP 항목 순서·압축 방식 유지.
- 새 표 id = 문서 최댓값 다음, 본문 표가 가장 많이 쓰는 네 변 실선 borderFill 승계, 없으면 실선 하나 등록(itemCnt 갱신).
- 작업본 표 열 너비 비율, 병합 서식 표 칸을 x 위치로 맞춰 원래 칸에 써 넣기.
- 서식에 이미 있는 글·표는 다시 넣지 않고 지나가기, 소제목 접기, 중복 보고.
- 그림: BinData 새 항목, manifest 등재, 글자처럼 취급하는 그림 문단, 본문 폭 안으로 축소.
- 【작성방법】 상자 빼기(제출본).

빠진 것(이번 조사에서 확인)

- 새 문단은 전부 바탕글(이 서식에서 paraPr 1·charPr 16, 10pt). 서식에는 본문 자리의 "◦" 소항목 문단(paraPr 91·charPr 126, 12pt 굵게, 왼쪽 800)과 음수 내어쓰기 문단(paraPr 202·92·93)이 있는데 쓰지 않는다. 접힌 소제목('1) 강점(S)')도 바탕글 본문으로 들어간다.
- 새 표는 모든 칸이 한 borderFill·바탕글 글자다. 서식에서 【작성방법】 상자를 뺀 2행 이상 최상위 표 30개 중 23개가 머리 행 음영(#E0E5FA·#E6EEF7·#DFE6F7 등)을 쓰고, 20개는 음영과 굵은 글자를 함께 쓰며, 19개는 둘째 행 첫 칸(라벨 열)도 음영이다. 새 표만 맨 표라 눈에 띈다.
- 서식 표와 작업본 표의 행 수가 다르면 칸 대응을 포기하고 새 표로 넣는다(`_map_cells` 가 행 수 일치를 요구). 사업비 집행 계획처럼 "행 추가 가능" 이라고 적힌 표가 바로 이 경우다.
- 채운 뒤 스스로 하는 점검이 없다. kordoc validate 는 수동으로 한 번 돌렸을 뿐이다.
- 글 이스케이프가 `xml.sax.saxutils.escape` 뿐이라 금지 제어문자를 거르지 않는다. 구글 독스 API 는 문단 안 줄 바꿈(Shift+Enter)을 `\u000b` 로 주는데(API 문서 기준, 우리 작업본에서 실제로 나오는지는 미확인), `gdocs.section_bodies` 도 hwpx_fill 도 이를 따로 다루지 않는다. 들어가면 한글이 문서를 못 연다.
- `section_bodies` 가 독스 글머리 목록(bullet·nestingLevel)을 버린다. 작업본에서 목록 기능으로 쓴 개조식은 부호와 단계가 사라진 평문으로 온다.

## 4. 개선 목록(우선순위 순)

크기는 대략의 코드 줄 수다. 검증은 모두 `tests/test_hwpx_fill.py` 에 사례를 더하고, 557 서식 실측(쪽 수·표 수·넣은 절 자리)과 kordoc validate 를 다시 돌리는 것을 기본으로 한다. 한글 프로그램에서 여는 확인은 여전히 담당자 PC 몫이다(미확인).

### 1) 글자 안전 — 금지 제어문자 제거와 `\u000b` 처리

- 무엇: 새 글을 XML 에 넣기 전에 C0 제어문자(\t \n \r 제외)를 지우고, `\u000b` 는 줄 나눔으로 바꾼다. 본문이면 새 문단, 칸이면 새 문단(지금 칸 규칙과 같게).
- 왜: 한 글자만 섞여도 구역 XML 이 깨져 문서 전체가 안 열린다. 가장 싸고 피해가 가장 큰 구멍이다.
- 어떻게: `paragraph_xml`·칸 채우기·`table_xml` 이 쓰는 이스케이프를 한 함수(`_xml_text`)로 모은다. `section_bodies` 의 `_para_text` 결과에서 `\u000b` 를 `\n` 으로 바꾸는 것을 함께 한다.
- 검증: `\x0b`·`\x01` 이 든 작업본 글로 채운 뒤 구역 XML 을 파서로 읽어 웰폼드인지, 그 글이 두 문단으로 들어갔는지 본다.
- 크기: 20줄 안팎.

### 2) 채운 뒤 자가 점검 — 참조 무결성과 재파싱 대조

- 무엇: 저장 직후 (a) ZIP 규약(mimetype 첫 항목·무압축·내용), 바뀐 항목 웰폼드, secCnt, manifest href — kordoc validate 와 같은 항목, (b) kordoc 이 안 보는 것 — 본문의 paraPr·charPr·borderFill·style id 가 header 에 있는지, 각 목록 itemCnt = 실제 개수, binaryItemIDRef 가 manifest 에 있는지, 표마다 `rowCnt` = 실제 행 수이고 칸 덮개(colSpan×rowSpan 합) = rowCnt×colCnt 인지, (c) 우리 hwpx 리더로 다시 읽어 넣은 글·표가 각 절 제목 뒤에 순서대로 있는지 대조.
- 왜: 앞으로 3)~6)에서 header 에 모양을 새로 등록하고 표 행을 늘리면 id·개수·격자가 어긋날 수 있다. kordoc 의 patch 도 끝에 재파싱 검증을 한다. 화면 수치는 기계 산출물에서만이라는 규칙과도 맞는다.
- 어떻게: `hwpx_fill.check(out) -> list[str]` 를 두고 `fill()` 보고에 `checks` 로 싣는다. 문제가 있으면 채팅 답에 "점검 실패"로 알리고 파일은 보관하되 제출본 표시를 하지 않는다. 조사 때 쓴 점검(80줄)이 거의 그대로 쓸 수 있다.
- 검증: 원본·현재 완성본은 0건이어야 한다(조사 때 확인). 일부러 없는 charPr id·틀린 rowCnt 를 넣은 사본에서 잡히는지 본다.
- 크기: 100~150줄.

### 3) 서식 표 행 늘리기 — 행 복제, 세로 병합 묶음 안 포함

- 무엇: 작업본 표가 서식 표보다 행이 많으면 새 표로 떨어뜨리지 말고 서식 표에 행을 복제해 넣은 뒤 칸에 쓴다.
- 왜: 사업비·성과지표처럼 "행 추가·삭제 가능" 이라고 안내된 표가 가장 자주 늘어난다. 지금은 원래 표가 빈 채 남고 아래에 맨 새 표가 붙는다.
- 어떻게: kordoc `table-rows.ts` 원리 — 본 행 `<hp:tr>` 복제, 셀 글만 교체, 복제 조각의 linesegarray 제거, 뒤 행 `rowAddr` +1, `rowCnt` 갱신, 표 `hp:sz height` 에 행 높이 더하기. 여기에 kordoc 이 막아 둔 경우 하나를 더한다: 삽입 자리가 세로 병합 묶음 안이면 그 병합 칸(묶음 머리)의 `rowSpan` 을 1 올리고 `cellSz height` 에 행 높이를 더하며, 본 행은 같은 묶음 안의 병합 칸이 없는 행(묶음 둘째 행 이후)에서 고른다. 행 대응은 지금의 x 위치 대응을 행 단위로 쓰고, 작업본에만 있는 행을 "삽입" 으로 본다(행 글 정렬, 소계·합계 같은 행은 글로 맞춘다 — 특정 표 이름이 아니라 같은 글 행끼리의 정렬).
- 막는 조건은 kordoc 그대로 둔다: 본 행에 중첩표·그림·필드, 칸 수·가로 병합 불일치, cellAddr 표기 혼재, rowCnt 불일치. 막히면 지금처럼 새 표로 넣고 보고한다.
- 검증: 비목별 집행 계획 표의 장학금 묶음에 두 행을 더하는 작업본으로 채워 rowCnt·rowSpan·격자 덮개(2의 점검)·LibreOffice PDF 에서 묶음 칸이 늘어난 모양을 본다. 병합 없는 표 끝 행 추가, 머리 행만 있는 표도 사례로.
- 크기: 200~250줄.

### 4) 새 표에 서식 표의 역할별 모양 승계

- 무엇: 새 표를 만들 때 서식 본문 표들에서 역할별 모양을 모아 쓴다 — 머리 행 칸(borderFill·첫 run charPr·문단 paraPr·세로 정렬), 첫 열 라벨 칸, 본문 칸, 셀 여백, 표 바깥 여백.
- 왜: 서식 표 대부분이 머리 행 음영·굵은 글자를 쓰는데 새 표만 맨 표라 한눈에 이질적이다. 칸 글자도 바탕글 10pt 가 아니라 서식 표 칸 글자(대개 표 안 글자 스타일)여야 한다.
- 어떻게: 지금 `_table_template` 의 "가장 많이 쓰는 실선 borderFill" 을 역할별 최빈값으로 넓힌다. 같은 구역(없으면 문서 전체)의 【작성방법】 상자를 뺀 2행 이상 표에서 0행 칸 = 머리, 1행 이후 0열 칸 = 라벨, 나머지 = 본문으로 세고, 머리와 본문의 borderFill 이 같으면 음영이 없는 서식으로 본다. 라벨 열 모양은 작업본 표 첫 열이 글자만 있고 나머지가 수치·긴 글일 때만 쓴다(판정은 일반 규칙). kordoc profile 처럼 표 단위로 복제하지 않는다 — 우리 새 표는 서식 표와 모양이 달라 앵커가 맞지 않는다(2.7 실측).
- 검증: 557 서식에서 새 표 머리 행이 서식 최빈 머리 borderFill(채움색 있음)·굵은 charPr 를 갖는지, 표가 하나도 없는 서식에서는 지금처럼 실선 하나로 떨어지는지.
- 크기: 80~120줄.

### 5) 새 문단 모양 승계 — 부호별, 쓰기 자리, 제목 단계

- 무엇: 새 문단의 paraPr·charPr·styleIDRef 를 다음 순서로 고른다. (a) 글이 부호(□ ○ ◦ ㅇ - ㆍ ※ 1) 가. ① 등)로 시작하면 서식의 최상위 본문 문단(상자·표 밖) 중 같은 부호로 시작하는 문단의 최빈 모양, (b) 부호가 없으면 절 제목(또는 상자) 바로 뒤의 빈 문단, 곧 서식이 남겨 둔 쓰기 자리의 모양, (c) 둘 다 없으면 지금처럼 바탕글. 접힌 소제목은 부모 절 제목보다 한 단계 아래 제목 문단(예: 1.1 → 1.1.1 이 쓰는 모양)을 쓰고, 그 단계가 서식에 없으면 (a)~(c).
- 왜: 제목은 13pt 인데 본문이 10pt 바탕글이고 ◦ 소항목도 바탕글이라 서식 작성자가 의도한 위계가 사라진다. 작업본의 ◦ 는 서식의 ◦ 문단 모양을 따라야 한다.
- 주의: 서식의 ◦ 문단은 굵은 소제목일 수 있다(이 서식이 그렇다). 부호 문단 모양을 빌릴 때 그 문단 글이 짧고(한 줄) 굵으면 소제목으로 보고, 긴 본문 문장에는 (b)를 쓴다. 쓰기 자리 문단은 새 글을 넣은 뒤 남기지 않고 첫 새 문단이 그 자리를 대신하게 할지 판단이 필요하다(빈 줄 하나가 남는 것이 서식 관행인지 확인 뒤).
- 어떻게: `_Section` 을 만들 때 최상위 문단마다 (부호, paraPr, charPr, style, 글 길이, 굵기)를 모아 표를 만든다. 굵기는 header charPr 에 `<hh:bold` 가 있는지로 본다. 부호 목록은 section_context·gongmun 쪽과 공유한다.
- 검증: 557 서식 성과지표 절(section4)에 "◦ …" 긴 문장을 넣어 paraPr 91 계열이 아닌 본문 모양이, "◦ 추진 전략" 같은 짧은 줄은 91·126 이 붙는지. 제목 모양 사다리는 1.1 아래 접힌 소제목이 paraPr 149·style 4 를 받는지.
- 크기: 100~150줄.

### 6) 개조식 내어쓰기 — 모양 등록기

- 무엇: 부호 문단의 둘째 줄이 첫 줄 내용 시작에 맞도록 내어쓰기 문단 모양을 쓴다. 서식에 맞는 모양(같은 부호, 음수 intent)이 있으면 그것, 없으면 기준 모양(5의 결과)을 복제해 `intent = -(부호 폭 + 1타)`, 필요하면 `left` 를 더한 새 paraPr 를 header 에 등록하고, 부호 뒤는 공백 대신 `<hp:tab/>` 을 쓴다(tabPr 는 서식의 `autoTabLeft="1"` 항목, 이 서식은 id 1).
- 왜: 지금 부호 문단이 두 줄로 넘어가면 둘째 줄이 부호 아래로 들어가 공문서 모양이 흐트러진다.
- 어떻게: kordoc style-registry 원리 — 사양 → 같은 사양이면 같은 id, 없으면 문서 최댓값 다음 id 로 덧붙이고 `paraProperties itemCnt` 를 올린다. 주의할 한 가지: 한컴 paraPr 여백은 `hp:switch` 안 `hp:case`(HwpUnitChar)와 `hp:default` 두 벌이 있고 값이 다르다(이 서식 paraPr 202 는 case -1993, default -3986). 둘 다 같은 비율로 바꿔야 한다. 부호 폭은 글자 크기 기준 근사(한글 1em, 부호류 1em)로 충분하다 — 한컴이 탭 폭을 조판 때 다시 계산한다.
- 선행 조건: 작업본에서 부호가 글로 들어와야 한다. `section_bodies` 가 독스 글머리 목록을 버리므로, 목록 문단은 `nestingLevel` 과 글리프를 받아 부호 글로 바꾸는 일이 먼저다(단계별 부호는 서식 최빈 부호 순서에서, 없으면 □ ○ - ㆍ).
- 검증: 두 줄 넘는 "□ …" 문단을 넣고 우리 변환기 → LibreOffice PDF 에서 둘째 줄 시작 x 가 첫 줄 내용 x 와 같은지(글자 좌표 직독). header itemCnt·참조는 2의 점검으로.
- 크기: 120~180줄(등록기 60, 부호·탭 40, section_bodies 글머리 40).

### 7) 칸 채우기 세부

- 원래 칸 글의 앞뒤 공백(들여쓰기)을 새 글에 다시 입힌다(kordoc `buildParagraphSplices`).
- 칸에 쓰는 새 문단이 여럿일 때 원래 칸의 두 번째 이후 문단 모양도 차례로 쓰고(지금은 첫 문단 모양만 반복), 넘치면 마지막 모양을 반복한다.
- 신청서형 칸(□ 선택지, "(   )" 빈칸)은 작업본 칸 글이 선택지와 같은 글자 집합이면 통째로 바꾸지 말고 체크 표시만 옮긴다 — kordoc fill 의 칸 안 패턴 규칙. 표지·신청서 표에 해당.
- 크기: 60~100줄. 우선순위는 낮다.

### 8) 그림 소소한 것

- JPEG 판정을 `FF D8 FF` 세 바이트로. splice 겹침을 검사해 겹치면 멈추고 보고(kordoc `applySplices`). 각 10줄 안팎.

### 들이지 않는 것

- kordoc patch 로 절 본문을 넣는 것: 4.15.7 도 블록 추가가 안 된다(실측).
- kordoc generate 를 최종본으로: 서식을 새로 만든다. 원본 서식 보존이 아니다.
- kordoc render 를 완성본 미리보기로: 섞인 캐시 문서에서 글이 빠지고 쪽 수가 틀린다(실측).
- 표 서식 프로필 통째 적용: 앵커가 맞지 않아 새 표에는 적용되지 않는다(실측). 역할별 승계(4)로 대신한다.

## 5. 마크다운 → HWPX(generate) 에 대한 답

- 된다. `kordoc generate x.md --preset 보고서|계획서|개조식|기안문 …` 과 `markdownToHwpx`. 표(병합 포함 HTML 표)·수식·차트·그림 실데이터·항목부호 8단계·내어쓰기·표지·목차·결재란까지 낸다.
- 해 본 결과: 짧은 절 본문을 보고서 프리셋으로 만들면 validate 를 통과하고 kordoc 렌더로 볼 때 공문서 위계가 잘 선다. 글꼴·크기·색은 프리셋 값(실결재 실측)이고 공고 서식의 것이 아니다. 한글 프로그램에서 연 모양은 미확인.
- 쓸 자리: 공고가 서식을 주지 않는 내부 보고서·결과 보고서 초안을 한글로 낼 때 후보가 될 수 있다. 채택하려면 ADR 과 대조 수치(우리 변환기 출력과 쪽·표·글자 대조)가 먼저다.
