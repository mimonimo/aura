# 문서 작업 흐름 — 문서 세트에서 작성·합본까지

실물 문서 세트가 들어와서 담당자와 에이전트가 함께 쓰고, 결과가 다시 플랫폼 문서함으로 돌아오기까지의 체계다.
10-21 부터 문서 작성의 주 경로는 웹 한글 기안기(한글 문서함 `/hwp`, 원본 hwpx 를 브라우저에서 바로 편집)이고, 구글 독스는 보조 경로다.
아래 절 가운데 날짜가 그 전인 독스 작업본 설명은 보조 경로의 기록이다. 2026-09-24 실물 세트(AID 전환 중점 전문대학 지원사업 7건)로 확인한 것을 기준으로 적었고, 결정의 근거는
ADR-0027~0032, 작업 규율은 `docs/context/working-notes.md`(2026-09-24 절)에 있다. 현황은 `docs/dev-now.md`가 우선한다.

## 1. 들어오는 길

### 프로젝트와 참조 자료의 구분 (2026-10-03)

프로젝트는 진행 중인 업무와 과거 자료의 보관 묶음으로 구분한다.
DGX의 과거 사업 문서는 프로젝트 단위로 분류해 보관하고 RAG·온톨로지·지식그래프에서 활용한다.
보관 프로젝트는 기본 사이드바에서 제외하되 권한 범위 안에서 검색·열람할 수 있다.
반입·재동기화는 보관 상태를 유지하며 진행 중인 업무 목록에 자동 노출하지 않는다.
담당자의 실제 업무(예: 2026년 ○○ 지원사업)는 활성 프로젝트로 관리한다.
담당자의 프로젝트 생성 동작 또는 새 업무 생성 의사가 있는 채팅을 시작점으로,
관련 사업과 과거 문서를 검색하고 선택한 자료를 참조 연결한다. 단순 검색이나 첨부는 생성 의사가 아니다.
참조 연결은 원본 소유권·사업 분류·열람 권한을 변경하지 않는다.
보관 처리는 삭제가 아니다. 기존 프로젝트 묶음·문서 연결·대화·작업본을 보존한다.
신규 업무의 `지침·기준` 탭에서 관련 보관 프로젝트를 검색·열람하고 필요한 자료를 참조 연결한다.
후보에는 사업·수행 연도/연차·관련 이유를 표시한다. 근거 없는 연관은 확정하지 않으며,
과거 실적 자료를 새 업무의 의무 평가 기준으로 자동 적용하지 않는다. 참조를 위해 보관 해제할 필요는 없다.

구현 상태(2026-10-04): 지침·기준에서 `/projects/archived?for_project=…`로 진입해
상태·사업단·수행 연도별 검색 후 보관 사업을 참조 연결한다. 검색 UI 개선은 로컬 검증 단계다.
자동 보관 묶음은 `archive_source=dgx`로 구분하며 기존 묶음의 출처는 2026-10-04 배포에서
이관했다. 소유자·이름·보관 상태만으로 자동 생성이라 추정하지 않는다.

지난 사업 후보(`project_refs.candidates`)는 프로젝트 이름만이 아니라 프로젝트에 이은 기준 문서 제목과 문서에서 읽은 사업명을
낱말(형태소 명사·영문 약칭)로 견주고, 사업명을 읽지 못했으면 첨부 문서 제목도 쓴다. 자기 자신과 이미 이은 묶음은 뺀다.

### 처음 만들 때의 자동 연결

문서는 세 길로 들어온다. 어느 길이든 DB `documents` 가 원본 대장이고 파일은 `data/platform/documents/` 아래 정해진
자리(ADR-0030)에 놓인다.

- 새 채팅에 문서 두 건 이상을 던진다 — 프로젝트가 생긴다. 이름은 공고·기본계획 이름에서 붙임 번호·서류 낱말·연도 표기의
  '+'·'_' 를 정리한 것이다(`_title_from_bundle`, `storage.title_of`).
- 프로젝트 화면의 접수(파일 하나든 여럿이든 `POST /project/{id}/bundle`).
- 첫 화면의 "문서 묶음으로 프로젝트 만들기"(`POST /projects/bundle`).

묶음은 파일 이름의 서류 갈래(`doc_routing.guess_kind`, 제목의 맨 뒤 낱말이 갈래)로 둘로 나뉜다.

- 기준 문서: 공고·기본계획·지침·매뉴얼·심사 기준. `doc_type=regulation` 으로 문서함에 등록되고 기준 조각(`regulation_chunks`)이
  만들어져 검색·검토·초안의 근거가 되며 프로젝트 기준(`project_criteria`)에 이어진다.
- 접수 문서: 양식·계획서·결과보고서·현황표·발표자료. 프로젝트의 sector 유형으로 들어가 조각(`doc_chunks`)만 만든다.

같은 사업의 지난 기준 문서(연도만 다른 공고·기본계획)는 이름 낱말이 7할 이상 겹치면 자동으로 프로젝트 기준에 이어진다
(`_link_past_materials`). 같은 내용의 문서는 거절되고 원본을 `version_of` 에 남긴다(ADR-0027).

반입 뒤 분류에서 공고·지침·기준 갈래로 정해진 문서는 그 문서가 속한 프로젝트의 기준 문서로 이어진다
(`project_documents.link_criteria_kind`). 담당자가 만든 진행 중 프로젝트에, 담당자가 직접 올리거나 그 대화에 첨부한 문서만
잇는다. 보관 묶음·원본 보관소 자동 묶음과 원본 보관소에서 옮겨 온 문서(dgx://)는 잇지 않는다. 규칙이 생기기 전에 올린 문서는
`scripts/182_criteria_kind_backfill.py` 가 같은 함수로 소급 연결한다(기본은 미리보기, 프로젝트 소유자 열람 범위 확인).
다른 문서에 기준을 추천할 때는 같은 프로젝트이거나 같은 사업(정체의 사업 이름 열쇠가 같음)이라는 근거가 있을 때만 한다
(`regulations.criteria_link_evidence`).

라이브러리에서는 기준 문서와 접수 문서가 한 목록이다(ADR-0062). 「기준」 칩은 서류 갈래가 공고·지침·규정·심사 기준·
기본계획이거나 규정 색인에 든 문서를, 「작성·결과」 칩은 그 밖을 보인다(`library.use_sql`). 규정 색인에 든 문서는 「기준」
꼬리표를 단다. 규정 색인에 넣는 길은 「기준」 칩의 「기준 등록」(`/criteria/upload`) 하나이고, 이미 등록된 문서의 갈래를
규정으로 바꾸는 동작은 없다 — 사업 문서 검색 색인·가림·열람 범위가 갈래를 따라 바뀌기 때문이다. 옛 `/criteria` 주소는
`/?type=all&use=criteria` 로 넘어간다. 업무 탭 줄은 문서가 있는 업무가 둘 이상일 때만 보인다.

문서 이름은 `app/doc_naming.py` 한 곳에서 정한다. 본문 제목이 모양 검사를 통과하고 파일 이름의 구별 정보(연도·차수·지역·
기관·약어·사업·갈래)를 지키면 그것을, 아니면 군더더기를 걷어 낸 파일 이름을, 둘 다 빈약하면 「서류 갈래 · 사업 연도」 꼴의
대체 이름을 쓴다. 공문은 「수신」 칸 뒤의 「제목」 칸이 이름이다(표로 판독돼 칸이 한 줄에 붙어도, 앞의 수신 값 「내부결재」 는 떼고).
서류 갈래 낱말이 없어도 받지만 나머지 모양 검사와 겹침 규칙은 같다. 화면 이름에는 구분 말이나 접수번호를 붙이지 않는다 — 같은 제목은 문서함이 판본으로 묶고 접수번호는 따로
보인다. 올라온 파일 이름은 `identity.original_filename` 에 남는다. 규칙을 바꾸면 `scripts/124_refresh_names.py` 로 다시 매긴다
(미리보기·대응표 → `--apply` 백업 뒤 적용 → `--restore`). 담당자가 직접 붙인 이름은 건너뛴다.

### 프로젝트 만들기 한 곳 (2026-10-09)

프로젝트는 첫 화면의 프로젝트 만들기 창 하나에서 만든다(`POST /projects/bundle`). 파일은 있어도 없어도 되고, 있으면 묶음 접수로
판독·색인까지 하고 검토 의견·정체 읽기는 묶음의 모든 문서를 읽은 뒤로 미룬다(`defer_review`). 그래서 받은 문서는 바로 작성 재료로 쓰인다.
묶음은 한 건씩 판독한다 — 동시 처리는 젯슨 27B 처리량이 늘지 않고 MinerU 가 CPU 를 다퉈 더 느렸다(ADR-0058).

### 프로젝트 문서의 세 갈래 (2026-10-10)

대화 문서함 패널, 프로젝트 화면의 문서 목록, 지침·기준 탭은 같은 목록(`app/project_documents.py` 의 `collect`)을 본다.

- 사용자 첨부 문서: 프로젝트에 올린 문서와 대화에 첨부한 문서.
- 참고 문서: 문서함의 기존 문서를 끌어온 것. 에이전트가 답·편집·절 작성의 근거로 불러온 문서(`chat_sources`, 약한 근거 제외)와
  작업 원본으로 이은 문서이며 「에이전트가 불러옴」 처럼 온 길을 함께 적는다. 최근 것부터 40건까지.
- 규정·지침: 프로젝트에 연결된 기준 문서와 프로젝트에 올린 기준 문서. 검토 전이거나 다른 업무 영역의 기준도 보인다.

프로젝트 대화면 그 프로젝트의 모든 대화를 모아 어느 화면에서 봐도 같고, 프로젝트 없는 대화는 그 대화만 본다.
열람 권한을 통과한 문서만 담는다. 대화 문서함은 새로고침 버튼과 답이 끝날 때마다 목록을 다시 읽는다.
대화 문서함 맨 위의 작업 문서(함께 편집하는 Google Docs)는 세 갈래와 별도로 둔다.

## 2. 보는 길

플랫폼 문서 화면은 추출 조각(글·표 평문·그림)을 보여 준다. 원본 서식 그대로 보려면 구글 열람본이다(`/doc/{id}/view`,
문서함 패널 `/api/doc/{id}/google`). 열람본은 담당자가 열 때 한 번 만들어 `doc_google:<id>` 에 기억한다.
원본 형식(미리보기 종류·MIME·변환기)은 표시 이름이 아니라 실제 원본 확장자로 고른다(`storage.original_ext`·`original_name`).
반입 뒤 표시 이름은 확장자 없는 본문 제목이기 때문이다.

| 원본 | 열람본 | 만드는 쪽 |
|---|---|---|
| docx·xlsx·pptx | 독스·시트·슬라이드 | 구글 변환 |
| pdf·그림 | 드라이브 미리보기 | 그대로 올림 |
| hwpx | 독스 | `ingest/hwpx_docx.py` (글자·문단·표·글상자·그림·쪽 설정을 docx 로) |
| hwp | 독스 | `ingest/hwp5_docx.py` (pyhwp 구조 XML → hwpx 와 같은 변환기로 docx). 안 되면 `hwp_html.py`(pyhwp HTML) |

구글이 바꿀 수 있는 것은 구글에 맡기는 것이 원칙이다. 한글(hwp·hwpx)은 구글 드라이브가 가져오기 형식으로 받지 않는다
(2026-09-24 실측: 원본 hwpx 를 어떤 MIME 으로 올려도 400). 한컴독스는 공개 API 가 없어 연동할 수 없고 서버용 변환 SDK 는
별도 라이선스라 범위 밖이다. 그래서 한글만 우리가 docx·HTML 로 풀고 마지막 변환은 구글이 한다.

한컴 쪽 대안도 봤다(2026-09-24). Hancom Data Loader 는 클라우드 전용·쪽당 과금 API 라 교내 문서를 밖으로 못 내는 우리
원칙과 맞지 않고, 출력 구조(요소·좌표·쪽·마크다운)는 우리 조각(kind·page_no·bbox)과 같은 꼴이라 참고만 한다. HWP SDK 는
상용 문의형이고 Word 용 한글 변환기는 윈도우 전용이다. 옛 .hwp 는 pyhwp 의 구조 XML(hwp5proc xml, 30MB 문서에 7.5분,
캐시)을 읽어 우리 변환기에 넣는 것이 가장 원본에 가깝다 — 실측 사업계획서 95쪽: 표 124(중첩 41)·그림 27·글상자 19 모두 옮겨짐.

변환 품질은 문서 하나가 아니라 묶음으로 잰다. `scripts/145_hwp_convert_check.py` 가 문서함의 한글 문서 전부를 변환해 원본과
글자·표·그림 수를 대조하고 워드 구조 오류(붙은 표, 속성 순서, 글 든 가는 열, 너비 0)를 FAIL 로 낸다. 독스에서 어떻게 보이는지는
드라이브 PDF 내보내기(10MB 한도, 그림은 1600px 로 줄임)로 확인한다. 워드·독스는 붙어 있는 두 표를 한 표로 합치므로 표 사이에는
반드시 문단을 둔다.

한글 변환은 담당자가 열거나 "이 문서로 작업하자" 할 때만 한다. 미리 돌리지 않는다. 변환 품질은 원본 양식과 가장 비슷하게가
목표이고 독스에서 실물을 보며 다듬는다(작성서식 62쪽 기준 빈 쪽 6 → 1, 평가편람 0).

## 3. 쓰는 길

지금 흐름(10-25): 담당자가 한글 문서함에서 공통 양식(코드로 만든 15종) 사본이나 학교 실물 서식을 열고, 채팅으로 AURA 에게 절을 맡긴다.
27B 문서 작업 에이전트가 양식 고르기 → 근거 찾기 → 개요·본문·자기 점검을 거쳐 그 hwpx 의 절 자리에 바로 쓰고, 열린 기안기는 새 판을 불러온다.
수치 관문(근거에 없는 숫자 거절)·양식 예시 글자 거절은 쓰기 도구 앞에서 돈다. 자세한 구조는 `docs/architecture.md` 10.3.

### 공통 양식과 절 작성 에이전트 (2026-10-09, ADR-0058)

작성 서식이 없는 사업이나 새 문서는 독스 공통 양식 5종(사업계획서·실적보고서·단위 프로그램 실시계획서·결과보고서·회의록,
`ingest/gdocs_templates.py`, scripts/180)을 바탕으로 쓴다. 절마다 「작성 지침 — 」 문단에 쓸 내용·근거 위치·실문서 같은 절의
분량 중앙값을 적었다. 처음의 「병합 없는 8열 이하 표」는 2026-10-10 실제 서식 모양(2단 머리행·병합 칸·서식 격자·합계 행)으로
바뀌었다(ADR-0059). 양식의 모양과 구조는 코드 규칙으로 지키고 27B 는 내용만 쓴다.

어떤 양식으로 쓸지는 Writer 가 고른다(2026-10-11, ADR-0060, `app/form_choice.py`). 코드는 후보(프로젝트 작성 서식, 대화에서 정한
목차, 공통 양식 5종)만 모으고, 고름이 후보 밖이거나 실패하면 규칙(목차 지칭 → 목차, 맞는 서식 → 서식, 서류 갈래 → 공통 양식)으로
물러난다. 쓰고 난 뒤의 품질 관문(본문 폭을 넘는 표, 잇달아 반복된 줄)은 `ingest/doc_quality.py` 가 문서 구조에서 재고 고친다.

대화의 요청은 안전 관문(개인정보 요청·권한 범위·주입 의심)을 지난 뒤 문서 작업 에이전트(`app/doc_agent.py`)가 받는다.
Writer 가 매 걸음 상태(프로젝트 문서 제목, 연결 문서의 절 목록과 빈 절, 받지 못한 값, 최근 대화)를 보고 도구 하나를 고르며,
요청의 갈래와 대상(어느 절, 어느 문서, 어떤 값)은 모델이 정한다. 코드는 고른 대상을 그대로 받아 실행하고, 요청 글을 낱말 규칙으로
다시 해석하지 않는다.

편집 도구(hwp_page_setup ~ hwp_undo)는 서버가 파일을 직접 고친다 — 기안기가 열려 있지 않아도 되고, 고치기 전 판을 남기며, 고친 결과가
자가 점검(hwpx_fill.check: ZIP·웰폼드·참조 id·itemCnt·표 격자)을 통과할 때만 저장한다(실패하면 파일은 그대로). 열린 편집 화면은 AURA 의
저장을 보고 다시 불러온다. hwp_live 의 동작은 기안기(13.82)에서 하나씩 실행해 결과를 확인한 것만 허용하며, 파일 열기·저장·인쇄·
끼워 넣기 파일·하이퍼링크·대화 상자는 없다(되돌리기는 기안기 API 로 듣지 않아 판으로 되돌린다). 기안기가 열려 있으면(실행기 2 가 살아 있으면)
hwp_page_setup·hwp_page_number·hwp_header_footer 는 파일 대신 기안기 동작(PageSetup·PageNumPos·HeaderFooter)으로 해 화면이 다시 불러오지 않는다.

작업 메모(app/chat_memory) 맨 앞에는 「최종 결과물」 한 줄(문서 이름·용도·대상·마감)을 따로 둔다(ADR-0068). 담당자가 바꾸자는 말을 하지 않으면
지난 줄을 지키고(지금 단계 이름으로 바뀌는 것을 막는 코드 관문 keep_final), 「미정」 이 든 막연한 줄은 더 구체적인 줄로 바뀌는 것을 받는다.
이 줄은 서브 지시서와 양식 설계 재료에도 실린다. 고쳐 쓰기·개요·자기 점검·여러 절 동시 맡기기는 설정 넷(ZZAIMY_DRAFT_QUALITY·ZZAIMY_REVISE·
ZZAIMY_DELEGATE_PARALLEL·ZZAIMY_MEMO_GOAL_LOCK)으로 끄고 켜며, 시나리오 평가(scripts/202 --old)가 끈 판과 견준다.

되돌리기 어려운 도구(다시 쓰기·편집·안내 상자·내보내기·작업본)는 담당자 요청 글에 그 뜻이 있을 때만 돈다. 문서를 바꿔 잇거나
판독하는 도구는 담당자 요청 글이 그 문서 제목과 흔한 갈래 낱말이 아닌 네 글자 이상을 함께 가질 때만 돈다(`_mentions_document`).
프로젝트 문서 목록과 양식 후보는 대화 주인의 열람 범위 안의 것만 보인다. 걸음과 쓰기 횟수에 한도가 있고,
도구 결과는 자료로만 모델에 돌려준다. 모든 걸음은 `doc_agent_episodes.jsonl` 에 남겨 리즈닝 학습 재료로 쓴다.
절을 쓰기 전에는 Writer 가 필요한 정보와 찾을 곳·검색어를 정하고 코드가 그대로 검색한다(`app/context_plan.py`).

답과 글에 쓰는 사실은 그 요청에서 search 로 찾은 결과에 있는 것만 쓴다. 상태의 최근 대화는 맥락일 뿐 근거가 아니어서, 앞 대화에서
본 사실을 쓰려면 다시 찾는다. 찾기 전에 사실 질문에 답하려 하면 한 번 먼저 찾게 하고(`SEARCH_FIRST`), 검색 결과 머리에는 검색어의
명사가 결과에 있었는지(「검색어 일치」)를 붙여 모델이 다른 표현으로 다시 찾을지 정하게 한다. 답변기(`responder`)도 앞 대화를
수치·날짜의 근거로 쓰지 않는다. 검색 결과는 조각마다 앞부분만 보이므로, 맞는 문서를 찾았는데 표·목록이 잘렸으면 검색어를 바꾸기보다
read_found 로 그 문서를 이어 읽는다(결과 머리에 문서 번호와 「잘린 결과가 있다」 단서를 붙인다).

걸음 한도에 닿았을 때 이번 요청에서 근거를 찾았으면 마지막 걸음을 한 번 더 준다. 이 걸음에서는 문서를 바꾸지 않는 답하기
도구(answer_question)만 고를 수 있고, 질문이 아니거나 근거가 모자라다고 판단하면 모델이 stop 을 낸다. 그 걸음이 형식 오류이거나
stop 이면 전처럼 한도 안내(찾은 자료를 밝히고 문서는 바꾸지 않았다는 글)로 끝난다. 쓰기 한도와 되풀이 멈춤은 그대로다.

모든 모델 호출(에이전트 걸음, 답변, 편집 계획)은 보내기 전에 서빙 모델의 문맥 한도 안에 맞춘다(`app/llm_budget.py`). 한도는
서버의 `/v1/models` 가 알려 주는 `max_model_len` 을 연결마다 한 번 읽고, 못 읽으면 설정값(`ZZAIMY_WRITER_CONTEXT`, 16384)을 쓴다.
토큰 수는 글자 갈래별 비율로 넉넉히 어림하고 vLLM `/tokenize` 가 되면 실측으로 보정한다. 줄이는 차례는 첨부·연결 문서 →
오래된 대화 → 출력 상한(바닥까지) → 검색 근거 → 에이전트가 찾은 근거이고, 요청 글은 줄이지 않는다. 다 줄여도 넘으면 보내지 않는다.
에이전트 걸음에서는 오래된 결과 글 → 오래된 걸음 → 상태 글 뒤쪽 → 최근 결과 글 차례로 줄이며, 최근 세 걸음과
「지금까지 한 걸음」 기록(도구·인자·결과 한 줄)은 늘 싣는다. 같은 걸음을 다시 고르면 그때 결과를 다시 보여 주고, 두 번째부터는
고를 수 있는 다음 걸음을 알리며, 잇달아 세 번이면 찾은 자료를 밝히고 멈춘다(대비 경로로 가지 않는다). 거절된 걸음(관문·검증
거절, 두 번 실패)을 같은 인자로 다시 고르는 것도 되풀이로 세고 그때 거절 까닭을 다시 보여 준다. 값 채우기에서 값이 결과 글에
그대로 없으면 그 출처 결과 글에서 그대로 뗀 후보(물은 이름의 낱말이 든 줄, 날짜·기간·수량 꼴)를 자료로 돌려준다.
받지 못한 값에는 갈래가 있다 — 사실(자료에 있을 수 있는 값)과 결정(담당자가 정할 목표·계획). ask_user 가 값을 만들 때 모델이
갈래를 붙이고, 갈래가 없는 옛 값은 모델이 걸음 JSON 의 ask_kinds 로 한 번 정한다. 사실 값만 찾고, 결정 값만 겨누는 검색은 막는다.
검색 결과에 받지 못한 사실 값의 글이 보이면 결과 머리에 알려 바로 resolve_from_evidence 로 남기게 하고, 한 값을 세 번 찾아도
결과에 그 값의 글이 없으면 이번 요청에서는 「자료에서 못 찾음」으로 두고 더 찾지 않는다. 단계 한도에 닿아 끝나도 이번에 찾은 값,
못 찾은 값, 남은 값을 정리해 알린다.
기준 문서 찾기(search source=criteria)는 기준 문서가 규정 색인에 있든 사업 문서 색인에 있든 그 문서 id 안에서 찾고, 못 찾으면
그렇게 말하며 source=project 를 권한다.
상태·걸음 기록·도구 결과(검색 조각·절 글·오류 글)는 모두 자료 울타리(<<< >>>) 안에만 들어가고, 자료 속 울타리 기호와 우리
머리말은 전각으로 바꿔 흉내 낼 수 없게 한다. 코드가 쓴 안내는 울타리 밖 [안내] 줄로 나눈다. 걸음 기록에는 결과 글 대신 길이와
출처 제목만 적고, 담당자에게 보이는 실패 안내에는 오류 글을 옮기지 않는다. 관문(동의·먼저 찾기)은 담당자 글로만 정하며 모델이 낸
인자로 건너뛸 수 없다.

낱말 규칙 경로(판독·문서 지목·초안·연결 문서 명령)로 물러나는 것은 모델에 닿지 못했거나(연결·서버 오류) 형식 오류가 두 번 났을
때뿐이다. 도구가 실패하면 그 결과를 모델에 돌려주어 다시 하거나 다른 걸음을 고르게 하고, 끝내 못 하면 무엇이 실패했고 문서는
바꾸지 않았다고 담당자에게 알린다. 물러난 경로도 문서를 만들거나 고치는 갈래는 담당자 글에 그 뜻이 있을 때만 간다 — 에이전트
도구와 편집 계획(이름 바꾸기·옮기기)의 동의 관문과 같은 패턴이며, 「고치지 말고」 처럼 부정한 말이 있으면 다른 낱말이 있어도
고치지 않는다. 질문이면 답만 한다.
이 경로는 장애 대비이며, 갈래와 쓸 절만 낱말 규칙(`drafting.target_sections` 등)으로 정하고 실행은 에이전트 도구와 같은 함수를 쓴다.

쓸 절은 Writer 가 상태의 절 목록에서 고른다. 물러난 경로에서는 비어 있는 절 앞쪽부터, 요약 절은 마지막, 이미 다룬 절은 건너뛰고, 「「제목」 절 써 줘」 처럼 집어 말하면 그 절이다. 재료는 그 절의 작성 지침,
문서 전체 규칙, 기준 문서, 프로젝트 문서, 문서함의 사업 문서 RAG(보는 사람의 열람 범위 안, 실적보고서면 같은 연차 계획서도)다.
넣은 글의 수치와 출처는 재료와 대조하고, 근거에 없는 수치는 문서에 넣기 전 「○○」로 가려 확인할 값으로 알린다(절대 규칙 1, `verify.numbers.mask_unsupported`). 모르는 운영 방침은 지어내지 않고
「(확인 필요)」 로 두고 묻는다. 검토를 받으면 「검토 의견 반영해 다시 쓰기」 로 같은 절을 다시 쓴다.

내보내기는 쓴 바탕을 따른다. 한글 서식 변환본은 원본 hwpx 에 채우고(아래), 공통 양식 문서와 원본이 .hwp 인 서식은
작성 지침 문단을 뺀 Word 로 낸다. 새로 내보내면 같은 이름의 옛 판은 드라이브 휴지통으로 간다.

절을 비우거나 덜 채우면 그 까닭을 원인 갈래(담당자 자료 필요·재료 없음·재료 불일치·일부 비움)로 남긴다(`app/fill_gaps.py`,
`data/platform/fill_gaps.jsonl`). 답 끝에 무엇을 올리면 이어 쓰는지 한 줄로 알리고, 같은 절을 다시 쓸 때 지난 까닭을 재료 맨 앞에 둔다.
보고서 절은 계획서의 짝 절(추진과제·성과지표·사업비 …)을 그래프 절로 찾아 재료로 쓰고, 「1. (추진 과제 1) ○○○○」 같은 자리 표시 제목은
쓴 뒤 이름만 따로 물어 같은 번호로 채운다.

`tests/test_agent_docs.py` 가 코드와 맞는지 확인하며, 도구를 더하거나 빼면 이 문서도 같이 고쳐야 테스트가 통과한다.

- 절 쓰기 전 정보 계획: `app/context_plan.py`

### 원본 기반 작성 양식

작성 양식은 해당 사업·연도의 원본 서식을 기준으로 한다. 목차만 모은 문서나 표의 일부 행만
남긴 요약본은 편집용 양식으로 게시하지 않는다. 기존 `162`·`172` 산출물의 Drive 게시 경로
(`169`)는 차단한다. 이미 저장된 문서나 원본은 자동 삭제하지 않는다.

`scripts/stage_source_templates.py`는 선택한 DGX HWP·HWPX를 별도 검증 폴더에 복사하고
직접 DOCX로 변환한다. 원본 해시·출처·표 구조를 기록하며 변환 실패를 본문 재조립으로
대체하지 않는다. 이 단계의 결과는 검수 전 작업본이며 공통 양식이 아니다.

표 변환은 병합 셀의 테두리·지정 배경색과 명시된 쪽 분할 제한을 보존한다.
페이지 수가 원본과 같다는 보장은 없으며, 제목 행의 범위를 모르면 반복 행을 임의로 지정하지 않는다.

게시 전에는 사업·연도·문서 종류, 예시와 실제 입력란, 표 병합·단위·작성 지침을 확인한다.
Google Docs 사본에서 입력·수정·비우기를 시험하고 화면과 구조를 대조한 뒤 게시한다.
과거 작성 사례의 예산·성과·담당자 정보는 새 양식의 기본값으로 옮기지 않는다.

작성은 원본 서식을 건드리지 않는다. 담당자가 프로젝트 문서를 지목해 작업하자고 하면(에이전트의 open_project_document, 모델이
없을 때는 `_project_doc_named`) 그 문서의 독스 변환본을 복제해
「제목 작업본 YYYY-MM-DD」 를 프로젝트 드라이브 폴더 `작성/` 에 만들고 대화에 잇는다(`_link_existing_document`,
문서함의 "이 문서로 작업" 버튼 `POST /api/chat/{sid}/work-on/{doc_id}`). 언제든 새 복제본으로 다시 시작할 수 있다.

이어진 뒤의 명령은 곧 문서 편집이다(`gdocs_agent`, ADR-0029). 에이전트는 문서의 절 구조를 읽고(탭 문서·표·번호 문단까지,
`gdocs.outline`) 편집 계획(insert·replace·style·bold·table·rename·move)을 세워 적용한다.

- 근거: 기준 조각(`find_relevant`) + 프로젝트 접수 문서 조각(`_project_evidence`, 지목한 문서만·작업본의 원본 서식은 제외).
  합본·지난 계획서의 그림 쪽은 글이 없으므로 요청 시 판독해 조각을 더한다(`read_image_pages`, 12쪽씩. 긴 판독은
  `scripts/143_read_image_pages.py` 로 서비스 밖에서).
- 넣는 자리: 절이 작성방법 상자(표)로 끝나면 표 뒤에 본문 모양으로.
- 가림: 주민번호·계좌·사업자번호만(`scrub_for_writing`). 기관·담당자 이름·업무 연락처는 남긴다. 모르는 값은 ○○○·빈칸.
- 이름 바꾸기·옮기기는 담당자가 말했을 때만. 질문에는 문서를 만들지 않는다.
- 최종 한글본: "한글 파일로 내보내 줘" 가 작업본의 절 본문(글·표)을 원본 hwpx 서식에 서식 보존으로 넣어(`ingest/hwpx_fill.py`,
  ADR-0035) `생성/` 에 보관하고 프로젝트 드라이브 `작성/` 에 올린다. 서식 표는 같은 절 안에서 같은 모양의 표를 찾아 채운다. "안내 상자 없이"·"제출본" 이면 【작성방법】 상자를 뺀다.
  원본이 .hwp 면 hwpx 로 저장한 서식을 반입하라고 안내한다.

## 4. 제안하는 길

무조건 돌리지 않고 알림처럼 다음 일을 내민다(`_project_suggestions`).

- 프로젝트 화면 "다음 작업 제안": 양식이 있으면 "그 양식으로 작성 시작", 글자 없는 그림 쪽이 있는 접수 문서가 있으면
  "그림 쪽 판독". 누르면 그 질문으로 새 대화가 열린다.
- 편집 명령에 근거가 없으면 답 끝에 판독을 제안한다.
- 새 채팅으로 프로젝트가 생기면 첫 답에 기준·접수 건수와 이어진 지난 자료를 알린다.

## 5. 여러 사람과 함께 쓰기

웹 한글 기안기에서 같은 문서를 여러 사람과 AURA 가 칸(누름틀) 단위로 함께 고친다(ADR-0070). 같은 칸은 먼저 고친 한 사람만,
다른 칸은 동시에 고치고, 칸 글은 서버 DB 를 거쳐 0.2~0.3초 안에 다른 창으로 간 뒤 몇 초 안에 hwpx 에 써 넣는다. 처리 방식별로
사용자가 보는 것과 뒤에서 일어나는 일은 개발자 화면 「처리 흐름 › 공동 편집 처리 방식」. 남은 설계는 다음이다(독스 시절의 합본 구상).

- 절 단위 담당 지정과 진행 표시(누가 어느 절을 썼는가는 독스 수정 기록과 `gdocs_audit.jsonl` 로 잇는다).
- 부서별 작업본을 하나로 합치는 합본 명령(절 순서는 원본 양식의 목차를 따른다).
- 합본 결과를 플랫폼 문서함에 생성 문서로 되돌리기(`documents/생성/`, ADR-0030) — 검토·판정·한글 산출(ADR-0035)로 이어진다.

## 6. 지키는 것

- 시험용 프로젝트·문서는 실물과 섞지 않고 끝나면 지운다.
- 지적된 항목은 회귀 테스트로 남긴다: `tests/test_project_bundle.py`, `test_gdocs.py`, `test_scrub_for_writing.py`,
  `test_hwpx_docx.py`, `test_hwp_html.py`.
- 교내 문서는 학교 워크스페이스 드라이브까지만. 외부 공유는 하지 않는다.
- 배포 재시작으로 끊긴 대화는 시작 때 안내를 붙여 잠기지 않게 한다.
