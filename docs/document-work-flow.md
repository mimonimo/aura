# 문서 작업 흐름 — 문서 세트에서 작성·합본까지

실물 문서 세트가 들어와서 담당자와 에이전트가 구글 독스에서 함께 쓰고, 결과가 다시 플랫폼 문서함으로 돌아오기까지의
체계다. 2026-09-24 실물 세트(AID 전환 중점 전문대학 지원사업 7건)로 확인한 것을 기준으로 적었고, 결정의 근거는
ADR-0027~0032, 작업 규율은 `docs/context/working-notes.md`(2026-09-24 절)에 있다. 현황은 `docs/dev-now.md`가 우선한다.

## 1. 들어오는 길

문서는 세 길로 들어온다. 어느 길이든 DB `documents` 가 원본 대장이고 파일은 `data/platform/documents/` 아래 정해진
자리(ADR-0030)에 놓인다.

- 새 채팅에 문서 두 건 이상을 던진다 — 프로젝트가 생긴다. 이름은 공고·기본계획 이름에서 붙임 번호·서류 낱말·연도 표기의
  '+'·'_' 를 정리한 것이다(`_title_from_bundle`, `storage.title_of`).
- 프로젝트 화면의 접수(파일 하나든 여럿이든 `POST /project/{id}/bundle`).
- 첫 화면의 "문서 묶음으로 프로젝트 만들기"(`POST /projects/bundle`).

묶음은 파일 이름의 서류 갈래(`doc_routing.guess_kind`, 제목의 맨 뒤 낱말이 갈래)로 둘로 나뉜다.

- 기준 문서: 공고·기본계획·지침·매뉴얼·심사 기준. `doc_type=regulation` 으로 문서함에 등록되고 기준 조각(`regulation_chunks`)이
  만들어져 검색·검토·초안의 근거가 되며 프로젝트 기준(`project_criteria`)에 이어진다.
- 접수 문서: 양식·계획서·결과보고서·현황표·발표자료. 프로젝트의 sector 유형으로 들어가 조각(`doc_chunks`)만 만든다.

같은 사업의 지난 기준 문서(연도만 다른 공고·기본계획)는 이름 낱말이 7할 이상 겹치면 자동으로 프로젝트 기준에 이어진다
(`_link_past_materials`). 같은 내용의 문서는 거절되고 원본을 `version_of` 에 남긴다(ADR-0027).

## 2. 보는 길

플랫폼 문서 화면은 추출 조각(글·표 평문·그림)을 보여 준다. 원본 서식 그대로 보려면 구글 열람본이다(`/doc/{id}/view`,
문서함 패널 `/api/doc/{id}/google`). 열람본은 담당자가 열 때 한 번 만들어 `doc_google:<id>` 에 기억한다.

| 원본 | 열람본 | 만드는 쪽 |
|---|---|---|
| docx·xlsx·pptx | 독스·시트·슬라이드 | 구글 변환 |
| pdf·그림 | 드라이브 미리보기 | 그대로 올림 |
| hwpx | 독스 | `ingest/hwpx_docx.py` (글자·문단·표·글상자·그림·쪽 설정을 docx 로) |
| hwp | 독스 | `ingest/hwp_html.py` (pyhwp HTML 을 한 파일로 → 구글이 독스로) |

구글이 바꿀 수 있는 것은 구글에 맡기는 것이 원칙이다. 한글(hwp·hwpx)은 구글 드라이브가 가져오기 형식으로 받지 않는다
(2026-09-24 실측: 원본 hwpx 를 어떤 MIME 으로 올려도 400). 한컴독스는 공개 API 가 없어 연동할 수 없고 서버용 변환 SDK 는
별도 라이선스라 범위 밖이다. 그래서 한글만 우리가 docx·HTML 로 풀고 마지막 변환은 구글이 한다.

한글 변환은 담당자가 열거나 "이 문서로 작업하자" 할 때만 한다. 미리 돌리지 않는다. 변환 품질은 원본 양식과 가장 비슷하게가
목표이고 독스에서 실물을 보며 다듬는다(작성서식 62쪽 기준 빈 쪽 6 → 1, 평가편람 0).

## 3. 쓰는 길

작성은 원본 서식을 건드리지 않는다. 담당자가 프로젝트 문서를 지목해 작업하자고 하면(`_project_doc_named` — 짧게 불러도
한 문서에만 있는 낱말이면 그 문서, 서로 다른 문서를 가리키면 되묻는다) 그 문서의 독스 변환본을 복제해
「제목 작업본 YYYY-MM-DD」 를 프로젝트 드라이브 폴더 `작성/` 에 만들고 대화에 잇는다(`_link_existing_document`,
문서함의 "이 문서로 작업" 버튼 `POST /api/chat/{sid}/work-on/{doc_id}`). 언제든 새 복제본으로 다시 시작할 수 있다.

이어진 뒤의 명령은 곧 문서 편집이다(`gdocs_agent`, ADR-0029). 에이전트는 문서의 절 구조를 읽고(탭 문서·표·번호 문단까지,
`gdocs.outline`) 편집 계획(insert·replace·style·bold·table·rename·move)을 세워 적용한다.

- 근거: 기준 조각(`find_relevant`) + 프로젝트 접수 문서 조각(`_project_evidence`, 지목한 문서만·작업본의 원본 서식은 제외).
  합본·지난 계획서의 그림 쪽은 글이 없으므로 요청 시 판독해 조각을 더한다(`read_image_pages`, 12쪽씩. 긴 판독은
  `scripts/143_read_image_pages.py` 로 서비스 밖에서).
- 넣는 자리: 절이 작성방법 상자(표)로 끝나면 표 뒤에 본문 모양으로.
- 가림: 주민번호·계좌·사업자번호만(`scrub_for_writing`). 기관·담당자 이름·업무 연락처는 남긴다. 모르는 값은 ○○○·빈칸.
- 이름 바꾸기·옮기기는 담당자가 말했을 때만. 질문에는 문서를 만들지 않는다.

## 4. 제안하는 길

무조건 돌리지 않고 알림처럼 다음 일을 내민다(`_project_suggestions`).

- 프로젝트 화면 "다음 작업 제안": 양식이 있으면 "그 양식으로 작성 시작", 글자 없는 그림 쪽이 있는 접수 문서가 있으면
  "그림 쪽 판독". 누르면 그 질문으로 새 대화가 열린다.
- 편집 명령에 근거가 없으면 답 끝에 판독을 제안한다.
- 새 채팅으로 프로젝트가 생기면 첫 답에 기준·접수 건수와 이어진 지난 자료를 알린다.

## 5. 여러 사람과 합본 (설계 중)

부서별로 절을 나눠 쓰고 합본해 검토하는 일이 많다. 독스는 공동 편집이 되므로 작업본 하나를 여러 사람이 같이 쓰는 것이
기본이다. 남은 설계는 다음이다.

- 절 단위 담당 지정과 진행 표시(누가 어느 절을 썼는가는 독스 수정 기록과 `gdocs_audit.jsonl` 로 잇는다).
- 부서별 작업본을 하나로 합치는 합본 명령(절 순서는 원본 양식의 목차를 따른다).
- 합본 결과를 플랫폼 문서함에 생성 문서로 되돌리기(`documents/생성/`, ADR-0030) — 검토·판정·한글 산출(ADR-0014)로 이어진다.

## 6. 지키는 것

- 시험용 프로젝트·문서는 실물과 섞지 않고 끝나면 지운다.
- 지적된 항목은 회귀 테스트로 남긴다: `tests/test_project_bundle.py`, `test_gdocs.py`, `test_scrub_for_writing.py`,
  `test_hwpx_docx.py`, `test_hwp_html.py`.
- 교내 문서는 학교 워크스페이스 드라이브까지만. 외부 공유는 하지 않는다.
- 배포 재시작으로 끊긴 대화는 시작 때 안내를 붙여 잠기지 않게 한다.
