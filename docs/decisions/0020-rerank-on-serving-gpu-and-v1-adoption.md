# 0020. 리랭커를 서빙 GPU 로 옮기고 학습본(ZZAIMY-Rerank v1)을 운영에 쓴다

- 상태: 확정
- 날짜: 2026-09-20
- 관련: `PROJECT_BRIEF.md` 축 B, `docs/model-plan.md` §ZZAIMY-Rerank, `docs/llm-rerank-eval.md`,
  절대규칙 2(베이스라인 먼저)

## 맥락

리랭커(bge-reranker-v2-m3)는 운영 VM CPU 에서 돌고 있었다. 질의당 3.75초라 쌍 길이를
256토큰으로 줄이고 쌍 텍스트에서 문서 이름을 뺀 상태였는데, 그 설정에서는 **정확한 질문의
순위가 오히려 나빠졌다**(하이브리드 R@1 0.647 → 리랭커 0.640). 리랭커를 켜고도 손해를 보는
구성이라, 파인튜닝을 시작하기 전에 베이스라인 자체를 바로잡아야 했다.

## 선택지

| 안 | 장점 | 단점 |
|---|---|---|
| A. VM CPU 유지, 256토큰 | 장비 추가 없음 | 정확한 질문에서 손해. 질의당 3.75초로 대화 흐름을 끊는다 |
| B. VM CPU, 512토큰 | 순위는 좋아진다 | 질의당 9.2초(실측). 운영 불가 |
| C. 토르 GPU 서비스로 분리 | 512토큰에서 질의당 0.07초 | 서비스 하나를 더 관리해야 한다. 죽으면 폴백 필요 |
| D. 서빙 장비의 생성 모델(LLM)로 리랭킹 | 별 서비스 없이 기존 Ollama 사용 | 27B 판정자가 568M 교차인코더보다 못하고 53배 느리다(실측) |

## 결정

C 를 택했다. 리랭커를 토르 GPU 의 단일 용도 서비스로 올리고(`scripts/102`, 포트 8013),
VM 은 `ZZAIMY_RERANK_URL` 로 점수만 물어본다. 서비스가 죽으면 VM CPU 경로로 물러난다.
같은 자리에 학습본을 올려 갈아탄다(`scripts/104` 학습 → 8015 → 운영 지정).
질의 임베딩도 같은 이유로 토르로 옮겼다(`scripts/103`, 8014).

## 근거

같은 후보·같은 질의 표본에서 짝지어 측정했다(질의 150건, 조각 4,003).

| 구성 | 정확한 질문 R@1 / MRR | 상황 질문 R@1 / MRR | 질의당 |
|---|---|---|---|
| 하이브리드(리랭크 없음) | 0.647 / 0.715 | 0.407 / 0.509 | 0.30초 |
| 리랭커 256토큰·제목 없음(옛 운영) | 0.640 / 0.701 | 0.473 / 0.550 | 3.75초(CPU) |
| 리랭커 512토큰·제목 포함(GPU) | 0.667 / 0.720 | 0.467 / 0.547 | 0.07초 |
| LLM 판정자 Qwen3.8-27B(DGX) | 0.750 / 0.776 *(표본 60)* | — | 7.98초 |
| 교차인코더 GPU, 같은 표본 60 | 0.767 / 0.782 | — | 0.15초 |

학습본(ZZAIMY-Rerank v1, `scripts/104`: 목록 단위 소프트맥스, 후보 안의 정답을 1위로, 2에폭)은
학습에 쓰지 않은 문서의 질의로만 검증했다(홀드아웃 12문서, `scripts/106`).

| 홀드아웃 | 하이브리드 | 베이스 | 학습본 |
|---|---|---|---|
| 정확한 질문(114건) R@1 / MRR | 0.544 / 0.678 | 0.649 / 0.751 | 0.711 / 0.790 |
| 상황 질문(14건) R@1 / MRR | 0.357 / 0.512 | 0.429 / 0.559 | 0.500 / 0.631 |

근거 하한(RERANK_MIN)은 모델마다 다시 잰다(`scripts/105`). 베이스·GPU 구성 0.271,
학습본 0.005(학습본은 점수가 또렷해 정답 중앙 1.000, 무관 질의 최대 0.000). 운영에서는
`.env.local` 의 `ZZAIMY_RERANK_MIN` 으로 지정하고, 지금 값은 모델 학습 화면에 표시한다.

## 결과와 되돌리기 비용

- 되돌리기: `.env.local` 에서 `ZZAIMY_RERANK_URL`·`ZZAIMY_RERANK_MIN` 을 지우면 VM CPU 경로로
  돌아간다(재색인 불필요). 베이스 모델은 8013 에 그대로 돌고 있어 A/B 도 가능하다.
- 잠기는 것: 리랭커 성능 주장은 이제 GPU 서빙을 전제한다. 서빙 장비가 없는 환경에서는
  옛 수치(CPU·256토큰)로 되돌아가고, 그 구성은 정확한 질문에서 이득이 없다.
- 하한은 모델에 딸린 값이다. 모델을 바꾸고 하한을 안 고치면 근거 표시가 틀어진다 —
  그래서 화면에 하한을 함께 적어 둔다.
