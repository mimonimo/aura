# ADR-0047: 실문서는 온톨로지·지식그래프로 RAG 에, 파인튜닝은 컨텍스트 구성 리즈닝만

상태: 채택(방향) · 날짜: 2026-10-01 · 관련: ADR-0009·0010(온톨로지 v1·v2), ADR-0015(학습된 연관), ADR-0044(학습 반출 보호), 절대 규칙 1·4·6·8

## 맥락

교내 실문서 약 1.5TB(사업별 폴더: LINC3.0·앵커·산단·RISE …)를 DGX(211.170.162.110)에 받고 있다. 운영 VM 은 남은 공간 427GB 라
원본을 다 반입할 수 없다(반입 시 원본의 약 4.5배). 교수님 방향(2026-10-01): "실제 데이터는 온톨로지/지식그래프 작업해서 RAG 로 다 빼고
리즈닝을 파인튜닝함으로써 최적의 컨텍스트를 구성하도록." 사용자: 에이전트는 사용자 입력이 들어오면 리즈닝 과정을 진행한다.

## 결정

1. 보관·처리는 DGX: 원본은 DGX 에 둔다. 글·구조 추출(우리 한글·PDF 변환기), 목차 노드, 표, 개인정보 탐지 기록을 DGX 에서 만들어
   문서마다 "처리본"(구조화된 글 JSON)을 낸다. 처리는 한 번, 결과는 아래 넷이 함께 쓴다.
2. 문서함은 색인만(참조 반입): VM 에는 문서 정보·처리본 조각·임베딩·그래프만 둔다. 열람·원문·독스 변환이 원본을 요구할 때 DGX 에서
   가져온다(읽기 전용 계정·SSH 키). ADR-0030 의 "원본은 문서함" 원칙을 이 갈래에 한해 바꾼다 — 별도 ADR 로 구현 때 확정.
3. 온톨로지 v3: 사업 → 연차(차수) → 문서(계획서·실적보고서·예산·지침·공고) → 목차 노드(절) → 성과지표·예산 항목·조직·규정 조항.
   관계: 계획서↔실적보고서 대응, 지표 목표값↔실적값, 절↔근거 문서, 판본(doc_family). 규모 때문에 그래프를 매번 다시 만들지 않고
   PostgreSQL 에 노드·관계를 저장한다(ADR-0009 의 "규모가 커지면" 조건).
4. 지식그래프 추출: 결정론 1차(번호·제목·표 구조·연도) 뒤 Writer 27B 2차. 수치는 원문 인출만(규칙 1), 모든 노드·관계는 근거 위치를 단다.
5. RAG: 처리본 조각을 문서 계열별 색인으로(규칙 6), 열람 등급 필터는 검색 단계(규칙 4), 임베딩 Embed v2. 그래프 탐색 결과로 후보를
   좁힌 뒤 조각 검색.
6. 에이전트 리즈닝 루프(입력마다): 질문 파악(사업·연차·문서·노드) → 그래프 탐색 → 근거 검색 → 컨텍스트 구성(넣을 것·뺄 것) →
   생성 → 근거 대조. 도구는 그래프 질의·조각 검색·문서 열람.
7. 파인튜닝은 이 리즈닝만(규칙 8): 학습 데이터 = 실문서에서 만든 리즈닝 기록 — 질문, 단계별 판단(노드 id·근거 id 인용, 고른 이유),
   고른 근거, 답. 형식은 서빙 때 도구 호출과 같게. 생성·검수·반출은 아스트라(ADR-0044 관문 그대로), 그래프·RAG·루프는 Claude.
   아스트라 근거 기록(program_id·node_path·evidence_records)과 온톨로지 id 를 같은 키로 맞춘다.

## 순서

파일럿: LINC3.0 계획서·보고서 모음으로 1~7 을 끝까지 한 번(목록 → 처리본 → 참조 반입 → 그래프 → 리즈닝 루프 → 리즈닝 기록 후보).
그 뒤 사업 단위로 넓힌다. 전체 반입·처리는 VM CPU 로 몇 주 걸리므로 DGX GPU 처리와 단계 반입이 전제다.

## 남은 판단

- DGX 읽기 전용 연동 계정 만들기(sudo — 사용자).
- 참조 반입의 열람 캐시 상한, 백업·삭제 범위(보관 노트 갱신).
- 리즈닝 기록의 단계 표기(아스트라 단계 문답 형식과 통일).
