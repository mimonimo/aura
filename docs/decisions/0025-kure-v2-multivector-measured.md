# 0025. KURE-v2 다중 벡터 검색을 같은 질의로 재고 채택하지 않는다 (ADR-0022의 조건 이행)

- 상태: 확정
- 날짜: 2026-09-22
- 관련: ADR-0022(보류 조건), ADR-0021(Embed v2), ADR-0020(Rerank v1)

## 배경

ADR-0022는 공개 KURE-v2가 다중 벡터 모델이라 바꾼다면 같은 질의 세트에서 후보 진입률과 R@1을
운영과 나란히 재고 색인 크기와 질의 시간을 적는다는 조건으로 보류했다. 사용자가 이 조건을
이행하라고 했다.

## 무엇을 만들었나

PyLate의 인코딩을 pylate 없이 옮겨 색인을 만들었다. 젯슨 컨테이너에 pylate를 깔면
sentence-transformers가 통째로 바뀌기 때문이다. 질의는 `<cls> [Q] … <sep>` 뒤에 마스크 토큰으로
64토큰까지 확장하고, 문서는 `<cls> [D] … <sep>`에 구두점 토큰을 뺀 뒤 Dense 3층을 거쳐 토큰별
128차원으로 정규화한다. 조각 4,284개가 토큰 84만 6천 개, fp16으로 780MB가 됐고 토르 03 GPU에서
33초가 걸렸다. 서비스는 색인 전체를 GPU에 두고 질의 토큰과 조각 토큰의 MaxSim으로 순위를 낸다.
질의당 50~70ms, 컨테이너 메모리 1.8GB다. 측정 도구에는 대안 조밀 축이 있으면 단독, 어휘 융합,
같은 표본의 리랭커 행과 후보 진입률을 운영 행과 나란히 내는 기능을 넣었다.

## 결과

2026년 9월 22일 01시 30분, 조각 4,284개, 합성 질의 1,023건, 리랭커 표본 300건, 운영 설정으로 쟀다.

| 방식 | R@1 | R@5 | R@10 | MRR@10 | 후보 진입률 R@20 |
|---|---|---|---|---|---|
| 임베딩 운영 (ZZAIMY-Embed v2, 학습본) | 0.692 | 0.865 | 0.900 | 0.765 | |
| 다중 벡터 (KURE-v2, 공개, 학습 전) | 0.682 | 0.844 | 0.891 | 0.749 | |
| 하이브리드 어휘+Embed v2 (운영) | 0.673 | 0.861 | 0.901 | 0.749 | 0.935 |
| 하이브리드 어휘+KURE-v2 | 0.634 | 0.820 | 0.884 | 0.713 | 0.919 |
| 운영 구성 어휘+Embed v2+리랭커 (표본 300) | 0.737 | 0.857 | 0.900 | 0.792 | |
| 어휘+KURE-v2+리랭커 (같은 표본) | 0.743 | 0.857 | 0.903 | 0.796 | |

## 결정

채택하지 않는다. 운영은 Embed v2 그대로다. 학습하지 않은 공개 모델이 우리 학습본에 근접한 것은
인상적이지만, 운영 경로에서는 후보 진입률이 낮고 어휘와의 융합이 더 나빠지며 리랭커까지 거친
최종 값의 차이는 300건 중 2건으로 표본 오차 안이다. ADR-0021의 채택 기준인 운영 경로 위의 개선을
만족하지 않는다.

경로는 비교용으로 남긴다. 다시 볼 조건은 둘이다. 교내 실물 문서와 골드셋으로 재측정할 때, 그리고
KURE-v2를 우리 자료로 학습해 학습본끼리 견줄 때다. 그 전까지 서비스는 내려도 되고 색인은 33초면
다시 만든다.

## 주의

같은 날 운영 구성 행이 전날보다 낮게 나온 것은 표본이 아니라 코퍼스 차이다. 문서 하나를 다시
처리해 조각이 4,254개에서 4,284개로 늘었는데 색인은 4,254개 그대로여서 30조각이 색인에 없었다.
재분할 뒤 전부 다시 색인했다. 다중 벡터 색인은 조각당 벡터 하나보다 12배 크므로 조각이 수만 개가
되면 GPU 상주 대신 후보 재정렬로만 쓰는 구조가 된다.
