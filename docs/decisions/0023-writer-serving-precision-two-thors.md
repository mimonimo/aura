# 0023. ③Writer 서빙 — 두 토르 분담, 정밀도는 FP4 > FP8 > bf16, 채택은 측정으로

- 상태: 확정 (사용자 결정 2026-09-21: "토르 02 가 메인으로 문서 작성, 03 이 나머지·임베딩")
- 날짜: 2026-09-21
- 관련: 0004(서빙 스택 vLLM bf16) · 0020 · 0021 · 0022

## 배경

Qwen3.8-27B 를 토르 02 한 대(bf16, vLLM)에 올려 문서 작업·반입 검토·이미지 판독을 다 맡기니 요청이
줄을 서고 요청당 ~5 토큰/초(동시 3요청 합계 14)였다. 답 1개 100초, 검토 1건 3분, 판독 1쪽 1~2분.
젯슨 토르는 메모리 대역폭이 속도를 정하므로 무게를 줄이는 것이 곧 속도다. 토르는 FP8·FP4 를 하드웨어로 가속한다.

## 결정

1. **분담**: 토르 02 = 대화·초안(사람이 기다리는 일). 토르 03 = 반입 검토·이미지 판독(배치) + 임베딩·리랭커 서비스.
   같은 판을 두 대에 올린다. DGX 는 학습 전용(서빙 안 함). 스택은 vLLM 하나로 통일(파인튜닝 어댑터 서빙·동시 처리·정밀도).
2. **정밀도 우선순위**: NVFP4(요청당 ~4배) > FP8(~2배) > bf16(바닥). 채택 조건은 같다 — bf16 과 같은 입력으로
   검토·판독 대결과 초안 수치 대조를 재서 손실이 허용 안이면 쓴다.
3. **학습본 이관**: DGX 에서 bf16 학습·병합 → 채택된 판으로 양자화(ModelOpt) → `116_ship_and_serve.sh writer` 로 두 토르에.

## 실측(2026-09-21)

- NVFP4(`nvidia/Qwen3.8-27B-NVFP4`): 기본 젯슨 vLLM 빌드(0.19.0)는 양자화된 lm_head 를 못 받아 실패.
  Qwen3.8 전용 빌드(`ghcr.io/nvidia-ai-iot/vllm:qwen3.8-next-jetson-thor`)로는 적재·워밍업 통과, 요청 1개 10.4 토큰/초.
- FP8(`Qwen/Qwen3.8-27B-FP8`): 0.19.0 빌드에서 KV 캐시 시험 실행의 cuBLAS 실패(캐시 비워도, eager 도 같음).
- 젯슨은 큰 파일을 받은 뒤 페이지 캐시가 CUDA 메모리를 막는다 → 서빙 전 root 로 `sync; sysctl vm.drop_caches=3`.
- DGX Ollama 27B(4bit)는 요청당 18.8 토큰/초 — 처리량이 급할 때의 임시 넘침용으로만 썼고 분리한다.
