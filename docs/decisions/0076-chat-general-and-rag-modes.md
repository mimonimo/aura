# 0076. 대화 입력줄의 답변 방식은 「일반」·「RAG」 둘로, 인터넷 검색은 일반 답에서 모델이 권할 때 한 번 눌러서

- **상태**: 확정
- **날짜**: 2026-10-27
- **관련**: ADR-0038(외부 검색 모드 — 이 결정이 0항의 고르는 자리를 대체한다), ADR-0053(RAG 공간), ADR-0063(그래프 단계), `app/answer_pref.py`, `app/chat_routes.py`(chat_send·/api/chat/answer-mode), `app/web_search.py`(answer_from_model), `app/retrieval_compare.py`, `app/effort.py`(답변 깊이)

## 맥락

- 대화 입력줄에 답변 방식 고르기(문서 작업·기본 대화·웹 검색)와, 관리자에게만 보이는 검색 방식 실험 고르기(온톨로지+RAG·풀텍스트 RAG·27B 읽기)가 나란히 있었다. 담당자에게는 고를 것이 많고 이름이 어려웠으며, 실험 고르기는 일하는 화면에 둘 것이 아니었다.
- 담당자가 실제로 가르는 것은 둘이다. 일반 업무 질문(모델이 바로 답하면 되는 것)과 문서 작업·문서 처리(내 계정에 연결된 RAG 를 근거로).
- 웹 검색은 따로 켜는 모드보다, 모델이 스스로 답하기 어렵다고 볼 때 권하는 편이 자연스럽다.

## 결정

1. 입력줄에는 「일반」·「RAG」 토글 하나를 둔다(학생은 학사 RAG 하나라 토글이 없다). 폼 값은 그대로 `web` 칸 — RAG = "", 일반 = "model".
2. 처음 값: 그 대화에서 마지막으로 쓴 방식, 없으면 프로젝트 대화·첨부·연결 문서가 있으면 RAG, 아니면 계정이 마지막으로 고른 방식(처음은 RAG). 고른 방식은 계정마다 서버에 기억한다(설정 `chat_mode_pref:<계정>`). 파일을 붙이면 그 질문은 RAG 로 간다(일반 답은 파일을 읽지 않는다).
3. 일반 = 27B 자체 지식 답(ADR-0038 의 모델 지식 길). 모델은 답 끝에 `[인터넷 확인: 필요|불필요]` 표시를 달고, 코드는 그 표시만 읽는다(질문 낱말로 정하지 않는다). 「필요」 면 답 끝에 「인터넷에서 찾아볼까요?」 와 선택지 「인터넷에서 찾아보기」 를 붙인다. 누르면 같은 질문을 웹 검색 길(`web=1`, ADR-0038 제공자: 구글·네이버 키, 없으면 DuckDuckGo)로 다시 묻는다. 작업 패널의 「외부 검색 모드(웹)」 체크는 뺐다(같은 기능 두 곳 금지).
4. RAG = 지금의 문서 근거 길. 범위는 계정의 RAG 공간(`rag_spaces.search_scope`). 토글 옆 범위 단추로 쓸 RAG(공통·소속 부서·받은 부서)를 골라 좁힐 수 있다. 고를 수 있는 것은 search_scope 결과의 사업 문서 부서(grant_depts, 관리자는 공통+알려진 부서)이고, 저장·답 만들기 때마다 그 집합과 겹치는 것만 남긴다. 범위 밖 값만 오면 사업 문서를 쓰지 않는 쪽으로 닫는다(넓히지 않는다). 공통 규정은 규정 검색이 늘 넣는다.
5. 대화의 질문 머리에 방식을 짧게 보인다 — 「RAG」(좁혔으면 「RAG · 공통·기획처」)·「일반」·「인터넷 검색」.
6. 검색 방식 실험(풀텍스트 RAG·온톨로지+RAG·27B 질문 읽기)은 입력줄에서 뺐다. `[실험 · …]` 표시줄도 없다. 실험 모드 자체(`grant_search.graph_mode`)는 그대로 두고, 질문 하나를 세 방식으로 나란히 돌리는 관리자 도구 `POST /dev/quality/retrieval-compare`(app/retrieval_compare.py, 검색만·답 생성 없음)를 둔다. 시험지 전체 측정은 scripts/188 그대로.

7. 답변 깊이(10-27 덧붙임) — 입력줄의 방식 토글 옆에 깊이 단추 하나, 단계는 둘만 둔다(사용자: 「그냥 두단계로… 너무 세세하게는 필요 없을 것 같고」). 「빠르게」(기본)는 27B 생각을 끄고(지금까지와 같음) 맡긴 절의 자기 점검을 건너뛴다. 문맥(작업 몫)은 두 단계가 같다 — 한도 그대로(사용자 10-27 「컨텍스트는 둘다 똑같지?」, 묶어야 하면 ZZAIMY_EFFORT_FAST_CONTEXT). 「꼼꼼하게」는 답·에이전트·도우미 호출에 생각을 켜고 출력 한도에 생각 몫(기본 8,192 토큰, 문맥 한도 안에서만)을 더하며, 작업 몫은 문맥 한도(256K) 그대로, 자기 점검을 하고 걸음 한도를 1.5배로 둔다. 단계 → 설정 표는 `app/effort.py` 한 곳이고, 값은 요청마다 contextvar 로 나른다 — 정하는 곳은 대화 답(`main._answer_task`, 질문에 남긴 `chat_msg_effort:<메시지>`)과 도우미(`chat_routes._helper_task`, 계정 값), 읽는 곳은 client(생각 켜기 인자는 연결 설정 think_extra — 모델 이름 없음)·work_len·delegate 자기 점검·doc_agent 걸음·answer_think 다섯 곳. 값을 정하지 않은 호출(반입·배치·측정)은 바뀌지 않는다. 계정 값은 같은 설정(`chat_mode_pref:<계정>` 의 effort)에, 같은 주소(`POST /api/chat/answer-mode` 의 effort)로 저장한다. 기본이 아닌 깊이로 보낸 질문만 머리에 「· 꼼꼼하게」 를 붙인다. 학생에게는 단추가 없다(늘 빠르게). 숫자는 환경변수(ZZAIMY_EFFORT_FAST_CONTEXT·ZZAIMY_EFFORT_THINK_TOKENS·ZZAIMY_ANSWER_THINK_TIMEOUT)로 바꾼다.

8. 10-27~10-30 덧붙임(운영에서 본 것을 고침).
   - 깊이 기본값은 「꼼꼼하게」(생각 켬)로 바꿨다(사용자 10-27 「생각모드가 기본이고, 간단한 거 물을 때는 끄는 건」). 「빠르게」 는 생각을 끄고
     답 앞 단계 추론(responder.COT_RULE)도 붙이지 않는다 — 27B 가 단계 머리·「[답]」 을 빼먹으면 단계 생각 글이 답 앞에 그대로 나왔다(10-30).
   - 일반·인터넷 답도 RAG 답과 같은 대화 맥락(작업 메모 + 최근 대화)과 플랫폼 줄(서빙 모델 이름·문맥 길이)을 넣는다. 질문 한 줄만 보내
     「K 로 바꾸면 그럼?」 같은 이어진 질문의 앞 내용을 몰랐고, 이 플랫폼 모델을 물으면 「확실하지 않다」 고 했다(web_search._context_messages).
   - 인터넷 검색어는 27B 가 이어진 질문을 풀어 만들되 담당자가 직접 쓴 말의 낱말만 쓴다. 답·작업 메모·교내 문서 글이 섞이면 질문 그대로
     보내고, 기관 이름은 저절로 넣지 않는다 — 밖으로 나가는 것은 담당자가 쓴 말뿐이라는 이 결정의 원칙 그대로(보안 점검, web_search._only_user_words).
   - 첨부에서 읽은 글은 문맥의 25%까지만 질문 맥락에 넣는다(넘치면 앞부분 + 줄였다는 표시). 사진 한 장의 판독 글이 418K 토큰으로 문맥을
     넘겨 답이 멈췄다(main._fit_attachment).
   - 회귀 시험: `scripts/219_mode_eval.py` — 같은 질문을 모드·깊이별로 운영 데이터에 보내 답·시간을 잰다(10-30 기준: RAG 빠르게 30~50초,
     꼼꼼하게 약 110초, 일반 3~8초, 인터넷 약 14초).

## 결과

- 담당자는 두 가지만 고른다. 웹 검색은 모델이 필요하다고 본 답에서만 한 번 눌러 쓴다 — 밖으로 나가는 것은 여전히 질문 글뿐이다.
- 품질·성능 화면에 「검색 방식 비교」 입력(질문 → 세 방식 결과 표)을 붙이면 실험을 화면에서 다시 돌릴 수 있다(화면 고리는 아직).
- 시험: tests/test_chat_answer_mode.py(토글 기억·일반은 검색 안 돎·제안 선택지가 웹 길·RAG 범위 좁히기만·고르기 없어짐·비교 도구), tests/test_answer_effort.py(깊이 계정 기억·학생 단추 없음·질문의 깊이가 답 호출의 생각 인자와 작업 몫에 닿음·정하지 않으면 그대로·생각 몫은 문맥 한도 안·자기 점검·걸음 한도).
