# 0065. 대화 기억은 작업 메모로, 답은 단계 추론으로, 긴 문서는 필요할 때만 서브 에이전트에 맡긴다

- **상태**: 제안(작업 메모·단계 추론은 운영 반영, 서브 맡기기는 비교 실험 뒤 기본값 결정)
- **날짜**: 2026-10-22
- **관련**: ADR-0040(구조 단계 문답 CoT 학습셋), ADR-0060(양식은 Writer 가 고르고 품질 관문은 코드), 리즈닝 파인튜닝 방향(10-01)

## 맥락

- 대화 기록을 요청마다 최근 몇 개만 넣어(답변기 6개, 문서 에이전트 7개·300자) 그 밖의 대화 — 담당자가 알려 준 값, 정한 방향, 만든 문서 —
  가 사라졌다. 처음엔 두루뭉술한 요청이 대화를 거치며 분명한 목표로 모여야 하는데 그 과정이 남지 않았다.
- 모델마다 문맥 한도가 다르다(지금 27B 서빙 16,384 토큰, 실제 도입 때 더 큰 모델). 개수로 자르면 모델을 바꿔도 맞지 않는다.
- 답변 생성은 추론 없이 바로 답을 썼다. 학습 데이터(구조 단계 문답)는 「[N단계: …] 추론 + [답]」 꼴이라 서빙과 학습의 꼴이 달랐다.
- 문서 에이전트가 한 문맥에서 대화 상태·검색 결과·걸음 기록·긴 본문을 다 다뤄, 절 41개짜리 사업계획서 서식은 한 요청에 17절에서 멈췄다(scripts/201).

## 결정

1. **작업 메모**(app/chat_memory.py): 대화마다 하나, 답이 끝나면 배경(review 연결)에서 「앞 메모 + 그 뒤 대화 → 새 메모」 로 고친다.
   갈래는 넷 — 지금 목표 / 확정된 것 / 진행 상황 / 남은 일·물어볼 것. 요청에는 메모 + 최근 대화 원문(모델 문맥 한도의 30%)을 넣는다.
   메모 길이 상한은 한도의 6%. 비율이라 모델을 바꾸면 저절로 맞는다. 메모는 맥락일 뿐 근거가 아니다(수치는 검색 근거에서만, 절대 규칙 1).
2. **단계 추론(CoT)**: 답변기는 [1단계: 질문 파악] → [2단계: 근거 확인] → [3단계: 답 구성] → [답] 꼴로 쓴다(ZZAIMY_ANSWER_COT, 기본 켬).
   화면엔 답만, 추론은 메시지별로 저장해 「생각 과정」 으로 펼쳐 본다. 문서 에이전트의 걸음별 생각도 같은 자리에 「[N단계: 도구] 생각」 으로 남긴다.
3. **문맥 사용 표시**: 답마다 모델 호출 수, 가장 큰 호출의 입력+출력 / 한도, 보낸 입력 합, 줄였는지를 기록해 입력창 아래에 보인다.
4. **필요할 때만 서브 에이전트(제안)**: 같은 27B 를 다른 역할·깨끗한 문맥으로 한 번 더 부르는 것.
   - 기본은 메인이 CoT 로 직접 처리(질문 답, 칸 몇 개, 짧은 절, 서식 고치기).
   - 「절 맡기기」 도구: 메인이 지시서(절 이름·요지·확정 값·형식·분량 + 문서 개요 + 앞 절 요지 + 담당자 원문 인용)를 쓰면 서브가 그 절의 양식 칸·작성방법·
     평가 기준·지난 해 같은 절·근거만 보고 쓴다. 여러 절은 동시에(토르 03 위주, 동시 2~4개). 서브는 모르는 값을 비우고 「확인 필요」 로 돌려준다.
   - 맡길지는 에이전트가 판단한다. 상태 글에 남은 문맥 %, 빈 절 수와 절별 분량, 남은 걸음을 보여 준다. 코드는 관문만 — 남은 문맥이 모자란데
     긴 본문을 직접 쓰려 하면 거절하고 맡기기를 안내한다.
   - 서브가 맡는 양은 문맥 한도에서 계산한다(16K 는 절 하나, 큰 모델은 장 단위로 묶음). 메인·서브에 다른 모델을 쓸 수 있게 역할별 연결로 연다.
   - 품질: 메인이 돌아온 절을 근거·수치 대조, 분량, 요지 반영으로 검토하고 모자라면 다시 맡긴다. 끝에 전체 정비(용어·숫자·표현) 한 번.

## 핵심 위험 — 문맥 누락과 문맥 관리

서브 호출은 문맥을 나눠 쓰는 방법(문맥 격리)이다. 따질 문제는 두 가지다.
- **문맥 누락**: 서브가 대화를 직접 보지 않으므로, 메인이 지시서에 빠뜨린 것은 서브가 모른다(담당자의 미묘한 뜻, 다른 절과의 관계, 확정 값).
  막는 법 — 지시서 필수 항목(작업 메모의 목표·확정 값, 문서 개요, 앞 절 요지, 담당자 원문 인용)을 코드가 채워 넣고, 서브는 모르는 값을 지어내지 않고
  「확인 필요」 로 돌려준다. 측정 — 서브 결과에서 확정 값이 빠지거나 틀린 수, 「확인 필요」 수.
- **문맥 관리**: 메인이 여러 서브의 결과를 받아 작업 메모·문서 개요를 계속 맞게 유지해야 한다(같은 값이 절마다 다르게 적히지 않게, 바뀐 결정이 이미 쓴 절에
  반영되게). 막는 법 — 서브 보고를 짧은 꼴(쓴 절·쓴 값·비운 칸)로 받아 메모에 접고, 결정이 바뀌면 영향받는 절을 메인이 다시 맡긴다. 끝에 전체 정비.
  측정 — 앞뒤 절 일관성(같은 값이 다르게 적힌 곳 수), 바뀐 결정이 반영되지 않은 절 수.

## 결과와 확인

- 작업 메모 실측(10-22, 실제 27B, 임시 DB 3턴): 첫 질문 「AI 교육 쪽으로 뭔가 사업」 → 3턴 뒤 메모의 지금 목표 「2027년 1학년 대상 AI 교육
  사업계획서 작성 및 목차 구성」, 확정된 것에 대상·예산 5천만원·기간 원문 그대로. 답에 단계 글 섞임 0건, 생각 과정 3턴 모두 저장.
  가장 큰 호출 5,400~7,900 / 16,384 토큰.
- 서브 맡기기는 바꾸기 전에 같은 요청 묶음(사업계획서·예산변경·기안문·출장보고, scripts/201)으로 「항상 직접」 과 「필요할 때 맡기기」 를 견준다.
  지표: 쓴 절 수, 사실 반영, 지어낸 숫자, 절별 분량, 작성방법 반영, 앞뒤 절 일관성(같은 값이 다르게 적힌 곳 수), 걸린 시간. 결과 문서를 기안기로 나란히
  보여 담당자 판단을 받은 뒤 기본값을 정한다. 설정으로 켜고 끈다.
- 남은 확인: 운영 대화에서 메모 품질, 단계 추론이 더하는 시간(어림 출력 약 200토큰 ≈ 15~20초).
