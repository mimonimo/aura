# 0070. 웹 한글 기안기 실시간 공동 편집은 칸(누름틀) 단위 임대와 서버 정답으로

- **상태**: 확정(칸 글 주고받기·임대·구조 잠금). 절 서식째 주고받기(M3)는 시험 기능 — 설정으로만 켠다
- **날짜**: 2026-10-24
- **관련**: `app/webhwp_coedit.py`·`webhwp_coedit_routes.py`, `static/webhwp-wrapper.js`·`webhwp-collab.js`·`webhwp-collab.css`, `templates/hwp_edit.html`, ADR-0035(한글 완성본 채우기)

## 맥락

한글 기안기 문서를 여러 사람이 같이 연다. 그전에는 문서 전체 편집 잠금 하나와, 2초마다 커서 칸 글을 설정 JSON 한 줄에 읽고 고쳐 쓰는
칸 공유였다. 실측한 문제: 기다리는 사람의 편집기가 실제로는 입력을 받아 그 글이 다시 열면 사라졌다, 기다리는 사람의 같이 보기 표시·칸 글이
서버에 가지 않았다, 동시에 쓰면 설정 JSON 이 덮여 칸 글이 빠졌다, 잠금 안내에 이름 대신 계정 아이디가 나왔다.

기안기(한컴 WebHwpCtrl 13.82.0.208) 공개 API 는 문서 바뀜 사건이 없고(마우스·스크롤 정도), 문서 내부 모델에 닿을 수 없어 OT·CRDT 는 쓸 수 없다.
쓸 수 있는 것은 필드 API(GetFieldList·GetFieldText·PutFieldText·GetCurFieldName·MoveToField), 필드 속성(ModifyFieldProperties — 「양식 모드에서 편집 가능」),
EditMode(2 = 양식 보호), GetPos/SetPos, GetTextFile/SetTextFile(JSON 블록)이다. 실브라우저로 확인한 것(10-24):
- EditMode 2 에서 편집 가능 속성을 끈 칸은 입력이 들어가지 않고, 필드 밖 입력도 막힌다. PutFieldText 는 잠긴 칸에도 쓰이고 커서를 옮기지 않는다.
- 한글 조합 중에 기안기에 무엇이든 물으면(GetCurFieldName·GetFieldText·ModifyFieldProperties) 조합이 끊겨 자모가 따로 박힌다(「ㄱ기김」).
- 커서를 다른 칸으로 옮겼다가 같은 작업 단위 안에서 SetPos 로 되돌리면 화면 이동 없이 그 칸의 커서 자리를 잴 수 있다.
- GetTextFile('JSON','saveblock') → SetTextFile(…,'insertfile') 로 절 칸의 굵게·기울임·문단 나눔이 그대로 옮겨진다(필드 수 그대로).

## 선택지

| 안 | 장점 | 단점 |
|---|---|---|
| A. 문서 전체 잠금만 | 단순 | 한 사람만 쓴다 |
| B. 칸 단위 비관적 임대 + 칸 글 전체 전송 + 서버 정답 | 공개 API 로 된다, 같은 칸 동시 편집이 없어 병합이 필요 없다 | 칸 밖 고침은 따로(구조 잠금), 서식은 글만(서식째는 시험) |
| C. 기안기 내부 모델에 OT/CRDT | 구글 문서와 같은 글자 단위 | 공개 API 밖, 제품 판이 바뀌면 깨진다 |
| D. Socket.IO·React 협업 페이지 | 재연결·방 기능 기본 | 새 의존성·빌드 단계, 앱은 빌드 없는 정적 JS |

## 결정

B. 서버는 FastAPI 그대로, 밀어 주기는 SSE(EventSource), 변경은 fetch POST. 화면은 빌드 없는 정적 JS 세 겹이다.

1. 어댑터(`static/webhwp-wrapper.js`) — 기안기 API 를 부르는 곳은 여기 하나. 칸 읽기·쓰기, 칸 편집 가능 켜기·끄기, 양식 모드, 커서 저장·되돌리기,
   칸 자리 재기, 입력·조합 사건, 절 서식째 꺼내기·넣기, 명령 실행기(`webhwp-agent-runner.js`)가 쓰는 읽기·찾기·그림 넣기.
2. 공동 편집 층(`static/webhwp-collab.js`) — 동기화 엔진(임대, 보낼 줄·받을 줄, 판 번호, 알림 흐름, 지문 대조, 충돌 사본)과 화면(머리줄 아바타,
   남이 쥔 칸의 색 테두리·이름표, 안내 띠, 충돌 사본 창). 편집 화면(`hwp_edit.html`)은 이 둘을 잇기만 한다.
3. 서버(`app/webhwp_coedit.py`) — 표 일곱: 칸 임대(webhwp_field_locks, 구조 잠금은 필드 이름 빈 값), 칸 글(webhwp_field_state, 판 번호·써 넣은 판),
   받은 변경(webhwp_field_ops, (client, seq) 한 번만), 고친 기록(webhwp_field_edits), 충돌 사본(webhwp_conflicts), 알림 줄(webhwp_events), 같이 보는 사람(webhwp_presence).
   한 문서의 쓰기는 묶음 안에서 줄을 세운다(SQLite BEGIN IMMEDIATE, PostgreSQL pg_advisory_xact_lock).

동작 규칙:
- 커서가 든 칸의 임대를 잡는다. 아무도 안 쥔 칸은 바로 쓸 수 있게 두고 임대는 뒤따라 잡는다(첫 글자를 잃지 않게). 남이 쥔 칸만 편집 가능을 끈다.
- 임대는 활동(입력·커서·스크롤)으로 늘어난다. 다른 칸으로 옮기면 유예 뒤 풀리고(돌아오면 그대로), 다른 사람이 기다리면 입력 없음 시간이 짧아지고
  쥔 사람에게 「넘겨주기」 안내가 뜬다. 풀리기 1분 전 「계속 쓰기」 안내. 시간 값은 모두 설정(설정 표 coedit:<키> → 환경 변수 ZZAIMY_COEDIT_<키> → 기본값):
  lease 300초, lease_contended 120초, grace 30초, warn 60초, throttle_ms 300, pause_ms 300, commit_delay 3초, commit_max 20초, hash_check 30초, presence_ttl 30초, aura_ttl 20초, rich 0.
- 보내기: 입력 중에도 300ms 마다 칸 글 전체를 seq·base 와 함께. 보낼 줄은 IndexedDB 에도 두고 서버 답을 받아야 지운다. 끊기면 다시 이어질 때 보낸다.
  한글 조합 중에는 칸 글을 읽지 않는다(조합이 끝나면 보낸다).
- 서버: 같은 (client, seq) 는 같은 답. base 가 지금 판과 다르고 그 사이 판을 다른 창이 썼거나, 남이 임대를 쥔 칸이면 반영하지 않고 충돌 사본으로 남긴다 —
  버리지 않는다. 받은 글은 표에 남기는 순간이 「저장됨」이고, commit_delay 뒤(이어지면 commit_max 안에) 한글 파일 필드에 써 넣는다
  (webhwp_write.set_fields → webhwp.save, 앞 판은 .판/). 파일 열기·내려받기·드라이브 올리기는 아직 안 들어간 칸 글을 먼저 써 넣는다.
- 받기: 판 번호가 앞선 것만, 내가 300ms 입력을 멈추고 조합 중이 아닐 때 넣고 커서·스크롤을 되돌린다. 30초마다 칸 글 지문(CRC32)을 서버와 맞춘다.
- 임대 놓기 순서: 보낼 것을 다 보내 답을 받고 → 한글 파일에 써 넣고 → 알리고 → 지운다.
- 칸 밖 고치기(구조 잠금): 본문·표 행·용지처럼 칸이 아닌 고침은 「⋯ → 칸 밖 고치기」로 구조 잠금을 쥔 사람만, 그 사람이 문서 전체를 저장한다.
  저장할 때 서버가 칸 글 표를 덮어 써 다른 사람의 칸 글이 남는다. 다른 화면은 「문서 저장」 알림을 받아 입력이 멈추면 새 판을 열고 커서로 돌아간다.
- 필드가 없는 문서는 예전처럼 문서 전체 잠금 — 쥔 사람만 고치고, 기다리는 사람의 편집기는 읽기 전용(ReadOnlyMode)이다. 쥔 사람이 저장하면 새 판을 받고, 풀리면 이어서 잡는다.
- AURA 에이전트도 참여자다: 칸 값은 같은 길(임대 확인·판 번호·알림)로 쓰고 바로 놓는다. 사람이 쥔 칸은 쓰지 않고 알린다. 절 본문 쓰기는 사람이 그 절 칸을 쥐었으면 쓰지 않는다.
  AURA 명령(편집 용지·표 등)은 구조 잠금을 잠깐 잡고 실행한다. 「AURA 작성 중」 표시는 마지막 쓰기 뒤 aura_ttl 초.
- 권한은 편집 화면과 같다(교직원·관리자, 열 수 있는 부서의 파일, 학생 막음, 잠긴 공통 양식은 관리자만 고침).
- 기안기에 이미 있는 찾기·찾아 바꾸기·편집 용지는 따로 만들지 않는다(우리 페이지 설정 창과 찾기 메뉴를 뺐다). Ctrl/⌘+F·Ctrl+H(맥 ⌘⇧H)는 기안기 창을 연다.

## 근거

로컬 앱 + 운영 VM 기안기 서버(터널), 헤드리스 크롬 세 사용자(가짜 계정), 한글 조합은 자모 단계(ㄱ→기→김)로 흉내(10-24):
- A 확정 → B 화면: 한 글자씩 21회 중앙값 221ms, 90% 299ms, 최대 302ms, 잃은 글자 0. 이어 치기 마지막 글자 62~203ms.
- 남이 쥔 칸에 B 가 친 글자는 들어가지 않음. 다른 칸 동시 입력 서로 보임(3~265ms).
- 임대 넘기기: A 가 다른 칸으로 옮긴 뒤 유예(시험 설정 3초) 지나 B 가 잡음 3.1~3.8초.
- B 오프라인 중 입력 → 「오프라인 — 연결되면 저장」, 다시 이어진 뒤 A 화면까지 19~40ms.
- 다른 프로세스에서 AURA 가 칸을 씀 → A 화면 863ms(프로세스 사이는 1초 주기 읽기), 머리줄에 AURA 아바타.
- 칸 밖 고치기 저장 → B 새 판 389~499ms, B 의 칸 글 그대로. 새로 열어 다섯 칸 모두 정확히 일치, 파일(hwpx)에도 들어감, 충돌 0.
- 필드 없는 문서: 기다리는 사람 입력이 막힘, 같이 보는 사람에 나옴, 쥔 사람 저장 2.2초 뒤 받음, 쥔 사람이 닫으면 0.2초 뒤 이어 잡음.
- 절 서식째(rich=1): 굵게·기울임·두 문단이 B 쪽 칸 JSON 과 같음(식별자·날짜 빼고 일치). 서버 써 넣기는 글만이다.

## 결과와 되돌리기 비용

- 칸 단위라 한 칸을 둘이 동시에 쓰지 못한다(먼저 잡은 사람). 칸 밖 고침은 한 사람씩이다.
- 서버가 한글 파일에 써 넣는 칸 글은 글만이다(줄바꿈은 칸 안 줄 나눔). 칸 안 서식은 문서 전체 저장(칸 밖 고치기·필드 없는 문서) 때만 파일에 남는다.
  그래서 서식째 주고받기는 시험 기능으로 두고 기본은 끈다.
- 남이 쥔 칸 자리는 기안기 내부 커서 모델(HwpApp.hwpCaret·HwpApp.hxe.CalcCaretPos — 공개 API 밖)로 잰다(아래 「사용 중 고침」). 제품 판이 바뀌어 이 내부가 없어지면 어댑터가 null 을 돌려 칸 표시만 빠지고(틀린 자리를 그리지 않는다) 머리줄 아바타·편집은 그대로다.
- 여러 앱 프로세스가 같은 DB 를 쓰면 알림은 1초 주기로 건너간다(같은 프로세스는 바로). 프로세스를 여럿 띄울 때 지연이 늘어난다.
- 되돌리기: 편집 화면이 /ops·/events 를 안 쓰면 예전처럼 문서 전체 잠금으로 돌아간다(표는 남아도 무해). 예전 /live·/presence·/state 경로는 새 표 위에서 그대로 돈다.

## 보안 점검(10-24)

- 창 번호(client)는 화면이 지어 보내는 값이라 표 안에서는 로그인한 사람과 묶는다(ckey). 남의 창 번호와 seq 를 먼저 차지해 그 사람의 변경을 막거나, 남의 창 번호로 판 번호 검사를 건너뛰거나, 같이 보는 사람 줄을 바꾸고 빼는 일을 막았다.
- 상한: 요청 본문 4MB, 문서마다 새 칸 줄 2,000개, 사람·문서마다 충돌 사본 200개, 사람·문서마다 알림 흐름 8개, 활동 알림 칸 목록 500개.

## 사용 중 고침(10-24, 세 창 실사용에서 나온 문제)

- 임대가 쌓였다: 칸을 누르기만 해도 임대를 잡고, 옮겨도 유예(30초) 동안 남아 한 사람이 칸 일곱 개를 쥔 것처럼 보였다. 이제 임대는 칸을 처음 고칠 때 잡고,
  다른 칸으로 옮기면 보낼 것을 보낸 뒤 바로 놓는다. 서버도 한 창에 한 칸만 둔다(새 칸을 잡으면 그 창의 다른 칸을 놓는다). 변경(op)만으로는 임대를 만들지 않는다
  (남은 변경이 옛 칸 임대를 되살리지 않게). 창을 닫으면 그 창의 칸은 바로 풀린다. 누르기만 한 사람은 옅은 세로줄(보는 중)로만 보인다.
- 이름표가 엉뚱한 자리·글 위에 그려졌다: 화면 커서(HWP_CURSOR_VIEW)는 그리기 차례에 늦게 옮겨지고 가려진·초점 없는 창에서는 더 늦어, 그것으로 잰 자리가
  다른 칸·빈 줄을 가리켰다. 이제 커서 모델에서 쪽 좌표를 같은 작업 단위 안에서 읽고(커서·스크롤은 그대로) 화면 좌표는 0.25초마다 다시 셈한다(스크롤·확대·창 크기).
  한 줄 칸은 테두리, 여러 줄 칸은 왼쪽 세로 막대, 이름표는 쪽 왼쪽 여백(글이 없는 곳)에 둔다 — 여백이 좁으면 머리 글자 동그라미.
- 내 이름표가 내 창에 보였다: 같은 사람의 다른 창이 쥔 칸이었다. 임대에 창 번호를 실어 내 이 창이 쥔 칸은 표시하지 않고, 내 다른 창은 「이름(다른 창)」으로 보이며 이 창에서는 막는다.
- 막힘이 남았다: 「쉬는 동안 풀렸습니다」 안내가 닫히지 않고 다시 잡지도 않았다. 이제 풀리면 안내 없이 다음 고침에 다시 잡고, 안내 띠는 짧은 말로 저절로 닫힌다.
- AURA 작성 표시가 사람이 쥔 칸에도 떴다: 칸 값 쓰기에서 표시를 쓰기 앞에 남겼다. 이제 실제로 쓴 칸에만.
- 공통 양식은 칸 공동 편집으로 누구도(관리자도) 고치지 않는다 — 관리자가 고칠 때는 문서 전체 잠금으로만(시험 글이 양식에 남는 길을 막음).
- 실측(헤드리스 세 창 1440·1000·570px + 같은 사람 둘째 창): 누르기만 → 임대 0, 고치기 → 다른 창 이름표 48~60ms, 칸 옮겨 고치기 → 이름표 하나로 30~46ms,
  누르고 떠나기 → 임대 0, 창 닫기 → 바로 풀림, 이름표 오른쪽 끝이 칸 왼쪽보다 147px 왼쪽(글 위 아님), 재기 전후 커서·스크롤 같음, 상자와 실제 커서 차 3px 안,
  글자당 지연 중앙값 204~216ms·잃은 글자 0.

## 사용 중 고침 2 (10-24 오후, 사용자 화면 시험)

- 칸 자리 재기는 커서를 칸에 넣었다 빼는 일이라, 빈 칸(누름틀 안내 글이 지워진다)과 누르거나 치는 중(막 누른 자리를 되돌려 입력이 남의 칸으로 가서 막혔다)에는 하지 않는다. 남의 커서만 있는 칸(보는 중)은 문서 위에 그리지 않고 머리줄 목록에만 둔다.
- 표시는 구글 독스 꼴로: 남이 쓰는 칸은 옅은 색 바탕(한 줄)·왼쪽 옅은 막대(여러 줄), 칸 끝에 색 커서, 커서 위에 이름 깃발. 「(다른 창)」 꼬리는 뺐다.
- 공동 편집 중에는 「AURA 따라가기」(내 커서를 AURA 칸으로 옮기고 내 커서 자리에 AURA 표를 그림)를 끈다 — 내가 쓴 글을 가렸다. AURA 칸은 같은 깃발로 보인다.
- 머리줄: 다른 사람 동그라미 4개까지 + 「+N」, 맨 끝 「나」 동그라미. 올리거나 「+N」 을 누르면 같이 있는 사람 목록(어느 칸에서 쓰는 중/보는 중, 누르면 그 칸으로).
- 같이 있는 사람: 알림은 칸이 바뀔 때만 가서 가만히 있는 사람이 30초 뒤 사라졌다 — 몇 초마다 보내는 presence 의 답으로 서버가 아는 사람 모두를 돌려준다.
- (같은 날 녹화 시험 뒤) 남이 쓰는 칸 위에 투명 막을 두어 누르면 「○○ 님이 쓰는 중」 안내만 띄운다 — 기안기가 막힌 칸을 누르면 커서를 앞 칸으로 돌려놓아 친 글이 엉뚱한 칸에 들어갔다.
- 이름표는 글 위가 아니라 커서가 있는 줄 높이의 종이 여백(커서에 가까운 쪽)에. 여러 줄 칸 표시가 화면 머리줄 `.bar` 꾸밈을 물려받아 형광펜처럼 보이던 것(클래스 이름 겹침)을 고쳤다.
- 「쓰는 중」 은 임대로 판단(알림이 늦어도 맞게), AURA 는 시킨 사람에게 딸려 「AURA · 이름」 으로 보인다(aura 알림에 by).
- 보기만 한 창이 「불러오는 중」 에 머물던 것 — 칸 공동 편집으로 열리면 「저장됨」.
- 같이 있는 사람 목록 꼬리는 「쓰는 중 · 칸 이름」 을 짧게 자르고 전체는 풀이말로.
- 남이 쥔 칸의 자리를 아직 모르면(글이 막 들어옴) 1초마다 다시 잰다 — 자리를 모르는 동안 누름 막이 없어 친 글이 앞 칸으로 샜다(3분할 시연).

## 큰 문서 대응(10-24 밤, 53·163·451쪽 합성 문서 실측)

가장 큰 공통 양식(사업계획서, 절 36·칸 57·표 64)을 1·2·6번 이어 붙인 시험 문서(53쪽 필드 157 · 163쪽 314 · 451쪽 942, 그림 66, 지어낸 글)를
세 창(브라우저 따로)과 다른 프로세스 AURA 로 잰 결과, 작은 칸은 451쪽에서도 글자당 중앙값 98~117ms·잃은 글자 0이었지만 긴 절(17k~50k자)에서
아래 문제가 나왔다. 고친 차례대로 적는다.

### 1. 필드 값의 줄바꿈은 진짜 문단 나눔으로

- 원인: 서버 써 넣기(`webhwp_write.set_fields`)가 줄바꿈을 한 문단 안 줄 나눔(`<hp:lineBreak/>`)으로 썼는데, 기안기 GetFieldText 는 줄 나눔을
  돌려주지 않는다(17,000자·줄 나눔 44개 절 → 16,956자, 줄바꿈 0). 그래서 그 칸을 한 글자 고치면 줄이 모두 붙은 글이 서버로 가고, 써 넣기 뒤
  파일의 줄 나눔 44개가 0개가 됐다. 받는 화면의 쪽 수도 53 → 52 로 바뀌었다.
- 긴 절이 한 문단이 되면 양식 모드(EditMode 2)에서 기안기가 한 글자마다 그 문단을 다시 배치한다(CPU 프로파일, 6글자): 17k자 한 문단 글자당
  258ms, 451쪽 50k자 한 문단 1.3초, 같은 50k자를 문단으로 나누면 60ms. 일반 모드는 한 문단 17k자도 60ms 안팎이다.
- 고침: `set_fields` 는 여러 줄 값을 필드가 든 문단과 같은 모양(문단·글자 모양, 쪽 나눔 없음)의 새 문단으로 나눈다 — 필드가 여러 문단에
  걸친다(기안기 PutFieldText 의 `\r\n` 과 같은 꼴, 942칸 문서에서 그대로 열리고 GetFieldText 가 `\r\n` 으로 돌려줌을 확인). 글 상한(50,000자)은 이 길에서 뺐다.
  예전 판의 필드 안 줄 나눔은 `normalize_breaks` 가 문단 나눔으로 바꾸고(값은 그대로), 파일을 열거나 내려받을 때(`webhwp_coedit.fresh`)
  한 번 돈다 — 바꾸기 전 판은 `.판/` 에 남기고 「문서 저장」(AURA)을 알려 열린 화면이 새 판을 연다. 잠긴 공통 양식·hwp 는 손대지 않는다.
- 같이 고침: 알림 흐름이 화면이 이미 본 알림(앞 20개)을 열 때마다 다시 보내 제 줄 나눔 정리 「문서 저장」 을 받고 한 번 더 열었다 — 본 번호 이하는 다시 보내지 않는다.
- 남은 한계: 사람이 Shift+Enter 로 넣은 줄 나눔은 여전히 GetFieldText 에 안 보여 다른 화면에는 붙어서 간다(다음 열기 때 파일 쪽은 문단으로 정리된다).

### 2. 칸 글 50,000자 상한을 걷고, 넘으면 자르지 않고 거절

- 원인: 편집 화면(`norm` 의 `slice(0, 50000)`), 서버 `norm`, 써 넣기(`clean_text`) 세 곳이 50,000자에서 잘랐다. 451쪽 문서의 50,000자 절 끝에
  친 15자는 그 창 밖으로 나가지 않았고(다른 창 50,000자, 친 창 50,027자), 절 처음에 치면 모두의 화면과 파일에서 절 끝 글이 잘렸다.
- 고침: 한 칸 상한 1,000,000자(`webhwp_fields.TEXT_MAX`·`webhwp_coedit.TEXT_MAX`, 화면은 서버 설정 `field_max`), 한 문서 칸 글 합계 상한
  8,000,000자(`DOC_TEXT_MAX`), 요청 본문 상한 8MB. 넘는 고침은 자르지 않는다 — 서버는 `too_long`·`too_big` 으로 거절하고, 화면은 보내기 전에
  「○○ 칸은 N자까지」 를 알린다(넘는 동안 저장되지 않음을 숨기지 않는다).

### 3. 칸 글 전체 대신 바뀐 부분을 주고받기

- 원인: 300ms 마다 칸 글 전체를 보내고(5만 자 칸이면 한 글자에 약 150KB), 서버는 알림·고친 기록에 전체를 남기고, 받는 화면은 PutFieldText 로
  칸 전체를 다시 썼다. 받는 쪽 비용이 칸의 문단 수·뒤쪽 쪽 수만큼 커져 451쪽 문서의 여러 문단 5만 자 칸은 한 번에 3.7초, AURA 가 2만 자 절 하나를
  쓰면 9.8초 화면이 멈췄다. 35k자 칸을 1분(변경 200개) 치면 고친 기록·알림 줄이 각각 17MB 쌓였다.
- 고침: 보내기는 서버가 아는 판의 글과 지금 글의 앞뒤 같은 부분을 뺀 {at, del, ins, base, fp}(자리는 글자 — 코드 포인트). 서버는 그 판 글에
  넣어 보고 지문(CRC32)이 맞을 때만 받고, 판이 어긋나거나·남이 쥐었거나·지문이 다르면 「delta」 로 돌려보낸다(답을 기록하지 않음) — 화면이 그 칸만
  전체 글로 다시 보내 기존 규칙(판 번호·충돌 사본)을 탄다. 아직 표에 없는 칸은 파일의 지금 값이 바탕이다. 알림(SSE)도 바뀐 부분과 지문만 싣고,
  받는 화면은 판이 이어지면 받을 글을 만들어 지문을 맞춰 본 뒤 그 자리만 고친다(SetPos+InsertText, SelectText+Delete, 줄바꿈은 BreakPara —
  451쪽 5만 자 칸 넣기 4.7ms·지우기 3.3ms). 판이 끊기거나 지문이 다르면 그 칸 글만 다시 받고(`/coedit?field=…`), 고친 뒤 글이 안 맞으면 통째 쓰기로
  돌아간다. 대리 쌍·탭이 든 글은 자리 셈을 믿을 수 없어 통째 쓰기. 남이 쥔 칸은 양식 모드에서 잠겨 문단 나누기·지우기가 듣지 않아(글 넣기는 든다)
  고치는 동안만 편집 가능을 켠다. 고친 기록은 바뀐 부분만, 처음·전체 글 고침·50판마다 스냅숏(`history` 가 되살림).
- 53쪽 확인: 한 글자 보내기 135바이트(앞 17KB), 받는 쪽 알림 10개 1.6KB(앞 256KB/15개), 통째 쓰기 0번·긴 작업 0, 줄바꿈·지우기 포함 두 창 글 일치.

### 4. 커서는 든 칸 기준으로 되돌리고, 남의 고침 뒤에는 되돌리기를 잠근다

- 커서 저장이 문서 처음부터 센 문단 번호여서 위쪽 칸의 문단 수가 바뀌면 다른 칸·칸 밖으로 갔다. 이제 커서가 든 칸 처음에서 센 자리로 저장하고
  그 칸 처음(MoveToField)에서 다시 센다. 커서가 보이던 화면 높이를 지키도록 세로 스크롤을 맞춘다(스크롤 값 75 = 화면 1px, 실측). 칸 자리 재기처럼
  같은 작업 단위 안에서 바로 되돌릴 때는 문단 번호 그대로.
- 받은 고침은 기안기 되돌리기 기록에 들어가 내 ⌘Z 가 남의 글을 지웠다(실측). 남의 고침을 넣은 뒤 Undo·Redo 를 잠그고(LockCommand — 리본 단추도
  같이), 내가 고치면 푼다. 내 고침을 되돌린 뒤 한 번 더 누르면 남의 고침에 닿을 수 있다 — 그 칸은 남이 쥔 칸이라 서버로 가지 않고 30초 지문 대조가 되돌린다.

### 5. 써 넣기(hwpx) 가볍게

- 원인: 써 넣기 한 번이 파일 전체를 다시 풀고(필드마다 `xml[start:]` 를 잘라 닫는 자리를 찾아 942칸·5MB 절에서 0.35초), 모든 칸 글을 다시 견주고,
  임대를 놓을 때는 그 요청 안에서 기다렸다(451쪽 0.45~1.3초).
- 고침: 닫는 필드 자리는 절 xml 하나에 한 번만 훑는다(필드 값 풀기 348ms → 19ms, 칸 하나 써 넣기 643ms → 162~225ms, 451쪽). 파일 필드 값은
  파일 수정 시각·크기로 캐시하고 써 넣은 값으로 이어 둔다(밖에서 문서 전체 저장으로 바뀌면 다시 푼다). 써 넣기는 아직 안 들어간 칸만 본다.
  임대를 놓을 때는 써 넣기를 바로 뒤로 넘기고 돌아온다 — 파일을 읽는 쪽(열기·내려받기·AURA)은 `fresh` 가 먼저 써 넣으므로 순서는 같다.

### 6. 받은 칸은 나눠 넣고, AURA 는 절마다 따로 흘려 쓴다

- 원인: 받은 칸을 한 작업에서 모두 넣어, AURA 가 216절을 한꺼번에 쓰면 451쪽 문서의 받는 화면이 31~74초 한 번에 멈췄다.
- 고침: 한 번에 30ms 만 넣고 쉰다(입력이 생기면 입력이 멈출 때까지 미룬다). 보이는 칸(화면이 자리를 아는 칸 중 화면 근처)부터, 그다음 내 커서 칸에서
  가까운 칸 차례. 전체 글로 온 고침도 내 글과 견줘 바뀐 부분으로 넣는다 — 다만 칸 대부분을 바꾸는 2만 자 아래 칸은 통째 쓰기가 더 싸다
  (451쪽 3,000자 칸: 통째 180ms, 지우고 넣기 211~250ms). 줄바꿈 든 글은 InsertText 한 번(`\r\n` 이 문단 나눔)으로 넣는다.
- 서버 쪽 참여자: `put` 은 지금 판(없으면 파일 값)과 견줘 바뀐 부분으로 보낸다. `SectionStream` 은 절 하나를 그 절만의 AURA 창 번호 임대로 잡고
  쓴 데까지를 바뀐 부분으로 흘려 보낸 뒤 놓는다. `put_sections` 는 여러 절을 절마다 따로 임대해 문단 하나씩 돌아가며 쓴다(사람이 쥔 절은 건너뜀).
- 예전 칸 공유 경로(`live_since`)는 알림에 글 전체를 기대해, 알림 읽기(`events_since`)가 기본으로 바뀐 부분 알림에 지금 글을 채운다. 알림 흐름(SSE)만 채우지 않는다.

### 7. 칸 자리는 기억해 두고 한 번에 한 칸, 같이 있는 사람에 쪽 번호

- 칸 자리 재기는 남이 쥔 칸을 모두, 화면 밖까지 4초마다 커서로 찔러 봤다(451쪽·20칸 46~65ms). 이제 칸마다 자리를 기억하고, 처음 보는 칸(내 커서 칸에서
  가까운 칸부터)이나 화면 근처 칸 가운데 바뀌었을 수 있는 칸(그 칸이나 앞쪽 칸 글이 바뀜·4초 지남)만 250ms 마다 한 칸씩 잰다.
- 같이 있는 사람은 기안기 KeyIndicator 로 안 쪽 번호를 함께 보낸다(재기 없이). 머리줄 풀이말·목록이 「이름 · N쪽 · 절 쓰는 중」, 누르면 그 칸으로.

### 8. 갑자기 닫힌 내 옛 창의 칸은 새 창이 이어받는다

- 창이 닫힘 알림 없이 사라지면(탭 강제 종료·잠자기) 그 창의 임대가 남아, 같은 사람의 새 창도 「내 다른 창」 으로 보고 5분 동안 그 칸을 못 썼다(시험 중 15자가 안 들어감).
  presence 답과 처음 상태에 그 사람의 살아 있는 창 번호(`windows`)를 실어, 그 창이 살아 있지 않으면 새 창이 처음 고칠 때 이어받는다.

### 9. 열 때 덜 하기

- 서버에 없는 칸 글을 칸마다 읽던 것(942칸 0.32초)을 한 번에 읽고, 처음에는 칸을 편집 가능으로 보고 남이 쥔 칸에만 속성을 쓴다(0.5초 덜).
  기안기 Open 자체(451쪽 4.8~10초)는 기안기 서버 변환·배치라 우리 밖이다.

### 11. 서버 참여자의 서식째 조각(hwpx)

- AURA·논문 작성기가 `put_rich` 로 칸 글과 hwpx 조각(`{"fmt": "hwpx", "b64": …}`)을 함께 보내면, 열린 편집 화면은 그 칸에 SetTextFile(HWPX, insertfile)로
  넣는다(표·꾸밈 스타일째, 다시 넣으면 바뀜 — ADR-0072 실측, 53쪽 문서에서 2.7초 안에 들어가고 30초 대조 뒤에도 그대로). 조각을 넣은 칸은 화면 글이
  서버 글과 조금 달라도(표 안 글은 GetFieldText 에 안 나옴) 지문 대조가 글만 다시 써 서식을 지우지 않게, 그 칸을 다음에 글로 고칠 때까지 대조에서 뺀다.
  남이 쥔 칸은 넣는 동안만 잠금을 푼다.
- 남은 일: 써 넣기(hwpx 파일)는 아직 글만이라, 다시 열면 그 칸 서식은 사라진다(문서 전체 저장 때만 남는다). 조각의 문단·글자·테두리 모양을 대상 파일 머리(header)에
  합쳐 칸 안에 문단·표로 넣는 일은 따로 한다.

### 12. 긴 절을 칸 여럿으로(양식 설계)

- 양식의 절 아래 제목(가.·1) 단계)마다 이미 칸이 따로 생긴다(사업계획서 양식 절 칸 36개). 제목 없이 수십 쪽을 한 칸에 쓰는 절은 한 사람만 쥘 수 있어,

### 보안 점검 2(큰 문서 대응 뒤)

- 서식째 조각: 사람 화면이 `/ops` 로 보낸 hwpx 조각은 받지 않는다(`rich_denied`) — 받으면 다른 사람 화면에 아무 조각이나 넣게 된다. 서버 참여자(`put_rich`)의
  조각도 검사한다: 넣을 수 있는 부분은 문서 머리·절·미리보기·그림(png·jpg·gif·bmp)뿐, 절 안에 OLE·동영상·양식 개체·하이퍼링크·외부 주소(href·src)가 있으면
  거절(`rich_bad`), 조각 안 누름틀은 떼어 낸다(칸 안에 칸·다른 칸 이름이 생기지 않게). 알림에는 서버가 검사한 조각만 `trusted` 로 실리고, 화면은 그 표시가 있거나
  서버 칸 상태에서 온 조각만, 그 알림의 칸에만 넣는다.
- 기안기 JSON 블록(시험 기능)은 설정이 켜져 있고 그 칸 임대를 쥔 창이 보낸 것만 남긴다 — 아니면 글만 받는다.
- 바뀐 부분: 서버는 남이 쥔 칸·판 어긋남·자리/길이가 글 밖·지문 다름을 모두 거절(`delta`)하고, 화면은 받은 바뀐 부분의 자리·길이가 글 밖이거나 지문이 다르면
  넣지 않고 그 칸 글을 다시 받는다. 받은 칸 이름이 이 문서의 칸이 아니면 넣지 않는다(예전과 같음).
- 화면 글: 이름표·목록·안내 띠는 모두 textContent 로 넣는다(innerHTML 은 비우기에만).

### 보안 점검 3(해석 차이·권한)

- 조각 검사를 문자열 훑기에서 진짜 XML 해석으로 바꿨다(`sanitize_fragment`). 문자열 훑기는 기안기가 읽는 XML 과 어긋날 수 있었다 — 다른 이름공간 접두어
  (`zz:fieldBegin`), 글자 참조(`&#104;ttp`), CDATA, 대소문자, 주석으로 가른 태그, 같은 이름 두 번, 경로 넘기. 이제:
  ZIP 부분은 이름을 정확히 허용한 것만(대소문자·같은 이름 두 번·`..` 거절), XML 은 expat 으로 먼저 읽어 DTD·개체 선언을 거절하고 ElementTree 로 읽은 나무에서
  이름공간을 뺀 요소 이름으로 막힌 개체(필드·OLE·동영상·양식 개체·하이퍼링크·스크립트·글맵시·차트)를 거절, 속성 값은 풀린 값으로 주소(href·src 와 http·javascript·data 등)를
  거절(한컴·OPF·DC·W3C 이름공간 표시와 조각 안 부분 이름만 허용), 누름틀은 나무에서 뗀다. 보내는 조각은 검사한 나무를 다시 써서 만든다 — 검사한 것과 보내는 것이 같다
  (원래 이름공간 선언은 맨 위 요소에 되살린다 — 없으면 기안기가 조각을 받지 않았다, 실측). 그림은 확장자와 파일 머리가 맞아야 하고, mimetype 은 hwpx 여야 한다.
  논문 작성기 조각(`paper_hwp.fragment`)은 그대로 지난다.
- 창 번호·칸 이름은 `clean_client`·`clean_field` 한 곳에서 가른다. 예전에는 경로마다 `[:80]`·`[:200]` 으로 잘라 넘겼다 — 자르지 않고, 창 번호는 1~80자에 공백·제어 문자
  (표 안 열쇠 구분자 `\x1f` 포함) 없음, 칸 이름은 1~200자에 제어 문자 없음, 맞지 않으면 400(서버 안에서는 bad). `ckey` 도 구분자가 든 사람·창 번호를 받지 않는다.
- `put_rich` 는 서버 안 함수로만 부른다 — 이 길로 들어오는 경로(route)는 없다(시험이 지킨다). 사람 화면의 `/ops` 로 온 hwpx 조각은 앞 점검대로 `rich_denied`.
- 메뉴 말 고침(10-24): 「칸 밖 고치기」 → 「문서 틀 고치기(제목·표·용지)」, 「충돌로 따로 둔 내 글」 → 「겹쳐서 따로 남긴 내 글」, 드라이브 「최종본」·목차 「논문」 꼬리 뺌, 아래 안내 「자동 저장 · 여럿이 함께 편집」.
- 편집 화면(10-24): 넓은 화면에서 처음 배율이 「폭 맞춤」 125~200%로 너무 커서, 110% 를 넘으면 100% 로 연다. 사람이 바꾼 배율은 이 브라우저에 기억해 다음에도. 「⋯」 메뉴는 편집기(틀) 안을 누르거나 초점이 틀로 넘어가면 닫힌다.
- 편집 화면(10-25): 큰 문서는 기안기 서버가 바쁠 때 20초 안에 안 뜰 수 있어(논문 158쪽), 20초에는 「불러오는 중 — 오래 걸림」만 띄우고 실패 표시는 90초가 지나도 안 뜰 때만. 새 판을 다시 불러와도 보던 배율 그대로(폭 맞춤으로 커지지 않게).
- 시도하고 접은 것(10-25): 서식째 쓴 절을 저장 알림(전체 다시 불러오기) 대신 그 칸의 hwpx 조각으로 보내기. 절 쓰기(webhwp_write.write_section)는 첫 문단만 칸 안에 두고 표·상자·나머지 문단은 칸 뒤 문단으로 넣어서, 칸 조각만 바꾸면 화면(칸 안에 다 들어감)과 파일(칸 뒤)의 구조가 갈라진다. 하려면 칸 뒤 문단까지 화면에서 지우고 넣는 구조 고치기가 같이 있어야 한다.
- 기다리는 사람 알림(10-25): 남이 쥔 칸에 커서가 들어오기만 해서는(사람 목록에서 그 자리로 옮기기 포함) 쥔 사람에게 「쓰려고 기다려요」 를 보내지 않는다. 그 칸에서 글을 치려 할 때(글자·지우기·줄바꿈 키)만 알린다.
- 배율 기억 고침(10-25): 큰 문서는 다 열린 뒤 편집기가 스스로 폭 맞춤(202%)으로 다시 키웠고, 그 값을 사람이 고른 배율로 잘못 기억했다. 이제 퍼센트로 바꾼 배율만 기억하고, 처음 2분 안의 편집기 폭 맞춤은 되돌린다. 저장 키를 바꿔(aura-hwp-zoom2) 잘못 기억된 값을 버린다.
- AURA 이름표(10-25): 작성 기록(webhwp_activity)에 시킨 사람을 남겨, 편집 화면을 새로 열거나 다시 맞춘 뒤에도 「AURA · 이름」(예전엔 「AURA · AURA」).
- 편집기 정적 파일 캐시(10-25): 기안기 서버가 모든 파일을 no-cache 로 보내 문서를 열 때마다 wasm 13MB·앱 스크립트 5MB 를 다시 받았다(느린 연결에서 논문 문서 열기가 90초를 넘김). 우리 프록시(/webhwpctrl/)가 js·css·wasm·글꼴·그림만 「private, max-age=86400」 으로 바꿔 보낸다. 문서·API 응답은 기안기 서버 헤더 그대로.
  같은 날 덧붙임: 크롬이 수식 wasm(13MB)은 캐시에 두지 않아, 큰 js·css·wasm·svg 는 gzip 으로 보낸다(wasm 13MB → 7MB, 압축본은 경로·ETag 마다 메모리에 한 번, 80MB 넘으면 비움). 잰 값: 시연 문서 열기 17초(정적 파일 캐시 뒤), 논문 171쪽은 첫 열기 40초·두 번째 33초.
- 장문 동시 편집 시험(10-25, 운영 시연 화면, 63쪽 사업계획서 양식 · 절 293): 세 계정이 5·37·58쪽의 서로 다른 절을 동시에 써도 세 칸 모두 같은 글, 한 칸에서 친 글이 다른 두 칸에 약 100ms. 사람 목록에 쪽 번호가 보인다. 좁은 칸에서 편집기 문서 영역이 29px 넓어 트랙패드로 위아래를 밀면 옆으로 흔들렸다 — 넘침이 64px 이하면 가로 스크롤을 막는다(확대해서 넓으면 그대로).

## 덧붙임 (2026-10-25) — 죽은 알림 연결 알아채기

시연에서 AURA 가 절을 써 「문서 저장」 알림이 나갔는데 열린 세 창 모두 새 판을 불러오지 않았다. 직전에 망이 잠깐 끊겼고, 알림 연결이
반쯤 열린 채 남아 EventSource 가 오류도 내지 않았다. 서버의 연결 유지 신호가 주석 줄(`: beat`)이라 화면 스크립트가 볼 수 없었던 탓이다.
이제 서버는 조용한 동안 15초마다 이름 붙은 `beat` 알림을 보내고, 화면은 45초 동안 아무 알림도 받지 못하면 새로 붙어 서버 정답을 다시 맞춘다
(놓친 알림은 마지막 번호 뒤부터 다시 온다). 그 사이 창은 옛 판을 보여 주므로, 구조 잠금을 쥔 창이 문서 전체를 저장하면 AURA 가 칸 뒤에 넣은 문단을
덮을 수 있었다 — 같은 고침이 이 틈을 45초 안으로 줄인다.

## 덧붙임 (2026-10-25) — 표 정리 주기

칸 글 표(webhwp_field_state)는 칸마다 한 줄인 지금의 정답이라 문서가 있는 동안 둔다 — 문서가 늘어도 「문서 수 × 칸 수」 줄만 늘고 고친 횟수만큼 쌓이지 않는다.
쌓이기만 하는 표는 기간을 둔다: 알림 30분, 칸 변경 묶음(같은 요청 두 번 막기) 7일, 고친 기록·충돌 사본 30일, 같이 보는 사람 하루.
문서를 휴지통으로 보내 장부에서 빠지면 그 문서의 줄은 모든 공동 편집 표에서 지운다(`webhwp_coedit.prune`, 알림을 낼 때 5분에 한 번).
운영 10-25 크기: 칸 글 237줄 · 변경 묶음 1,743 · 고친 기록 988 · 알림 752 — 모두 합쳐 약 2.5MB.

## 덧붙임 (2026-10-25) — 필드 갈래 「입력:」 과 코드로 짠 양식의 절 필드

- 필드 이름 갈래에 「입력:<라벨>」 을 더했다. 날짜·서명·결재·달성률처럼 사람이 정하는 칸이다. 공동 편집 경로(칸 글 표·임대·알림)는 칸 필드와 같고,
  에이전트 칸 채우기(`webhwp_agent.fill`)만 담당자에게 물어 받은 값(`from_user`)일 때 넣는다. `webhwp_write.fields` 의 kind 는 「입력」.

## 덧붙임 (2026-10-26) — AURA 가 쓴 글도 필드 안에

공동 편집 시연에서 사용자 지적: 「빨간거 없으면 수정도 안되고」. AURA 가 절을 쓰면(webhwp_write.write_section) 첫 줄만 절 필드 안에 들고
나머지 문단·표는 필드 문단 뒤, 필드 밖에 붙었다. 기안기는 양식 모드로 돌아 필드 밖 글은 구조 잠금을 쥐어야 고칠 수 있어, 사람이 AURA 글을
고치지 못했다.
- 이제 글 줄은 모두 절 필드 안의 문단으로 넣는다(누름틀은 여러 문단에 걸칠 수 있다 — 칸 글 써 넣기와 같은 꼴). 줄마다 단계 들여쓰기·내어쓰기
  문단 모양은 그대로다.
- 표·도식은 필드 밖에 둔다. 칸 글 동기화는 필드 글을 GetFieldText/PutFieldText 로 통째 읽고 쓰므로 표가 필드 안에 있으면 지워진다.
  표 뒤에 오는 글은 표 바로 뒤에 새로 만든 이어 쓰기 필드에 넣는다. 이름은 「이어:」 + 절 필드 이름 + 「 (n)」(n 은 2부터, 예 「이어:절:1. 변경 사유 (2)」).
  「절:」 로 시작하지 않으므로 절 목록·빈 절 세기·논문 목차는 그대로이고, webhwp_write.section_of 로 어느 절의 것인지 안다. fields() 는
  이어 쓰기 필드를 따로 내지 않고 그 글을 절 글 뒤에 잇는다. field_values() 에는 그대로 나온다(공동 편집이 칸마다 견준다).
- 다시 쓰기는 절 필드 안을 비우고, 그 절의 이어 쓰기 필드를 문단째 떼고, 앞서 넣은 표 문단(written)을 지운 뒤 새로 쓴다.
- 칸 글 표: 쓰고 저장한 뒤 절 필드와 이어 쓰기 필드의 파일 값을 칸 글 표에 넣고(webhwp_agent.write, paper_hwp.write_batch), 이번에 없어진
  이어 쓰기 필드의 줄은 지운다(webhwp_coedit.forget). 다시 불러온 화면의 칸 글이 표와 같아 30초 지문 대조가 서로 덮지 않는다.
- 사람이 그 절에서 한 줄을 고치면 써 넣기(set_fields)가 필드 글을 다시 쓰는데, 예전에는 모든 줄이 첫 문단 모양을 받아 들여쓰기가 지워졌다.
  이제 옛 줄과 견줘 같은(또는 고친) 줄은 제 문단 모양을, 새로 끼운 줄은 바로 앞 줄의 모양을 잇는다.

## 덧붙임 (2026-10-26 오후 2) — 일반 편집 모드: 칸을 넘는 선택·서식째 복사

사용자: 「복붙해서 서식까지 다 가져가고 싶은데 칸 안에 든 건 복사해도 텍스트뿐이고, 칸 범위 밖은 드래그도 못 하네」. 편집기를 양식 모드(EditMode 2)로
돌려 선택이 칸 경계를 넘지 못하고 복사가 글만 됐다. 문서 전체를 칸으로 감쌌으므로(위 덧붙임) 일반 편집 모드(EditMode 1)로 바꾼다 — 운영 설정
coedit:form_mode=1 이면 예전 양식 모드.
- 양식 모드가 막아 주던 것을 공동 편집 층이 대신 막는다(guardKey, 고치는 키에만): 남이 쓰는 칸에서 치면 막고 그 칸 이름표를 흔든다(임대 요청),
  칸 처음의 Backspace·칸 끝의 Delete 는 칸 표시를 지우므로 막는다. 줄 끝·문단 앞을 눌러 칸 바깥(칸 끝 표시 뒤)에 선 커서는 누르거나 화살표를 뗀
  순간 같은 문단의 칸 안으로 옮긴다(snapIntoField — 고르는 중에는 옮기지 않음). 한글 조합 첫 키(Process)는 막지 않으므로 이 옮기기가 먼저다.
- 여러 칸에 걸친 고침(선택이 칸을 넘음)·칸 바깥 고침·칸째 붙여넣기는 막지 않는다 — 편집기가 그대로 하고, 화면이 곧바로 문서 틀 잠금을 잡아 2초 뒤
  문서 전체를 저장하고 잠금을 놓는다(autoStruct). 서버는 구조 저장 때 새로 생긴 칸 밖 문단을 칸으로 감싸고, 같은 이름 칸(칸째 복사)은 뒤의 것을
  새 「문단:n」 으로 바꾼다(webhwp_fields.wrap_rest, 저장 답의 wrapped). 감싼 것이 있으면 저장한 화면도 새 판으로 다시 연다. 다른 화면은 「문서
  저장」 알림으로 새 판을 받는다 — 이런 고침만 문서 전체 길이고, 칸 안 고침·서식은 칸 길 그대로다.
- 칸째 붙여넣기 알아채기: 칸을 넘어 고른 범위를 복사하면 칸 표시까지 함께 붙어 같은 이름 칸이 겹친다(운영 실측 — 칸 19개가 24개, 겹침 5개, 다른 화면에는
  글만 가고 서식째 블록은 관문이 막음). 서식 손놀림(붙여넣기 Ctrl/⌘+V·툴바 붙이기 포함) 뒤 0.7초에 칸 목록부터 보고, 수가 바뀌었거나 겹치면 서식째 보내기
  대신 구조 고침으로 돌린다(화면이 잠금 → 전체 저장 → 서버가 겹친 칸 이름을 고치고 새 문단을 감쌈 → 모든 화면 새 판).
- 운영 실측: 세 화면 모두 EditMode 1 로 열림, 칸을 넘는 드래그 선택 됨, 붙여 넣은 글이 붙인 화면에서 서식째(소제목 꼴·주황 기울임·노란 형광).
- 구조 저장이 붙여넣기를 되돌리던 것(운영 실측): 서버가 문서 전체 저장을 받을 때 모든 칸을 DB 칸 글로 덮어(남의 동시 고침을 지키려는 장치),
  붙여 넣은 칸도 DB 의 옛 글로 되돌렸다(칸 표시가 든 칸은 서식 보존 길을 못 타 통째로). 이제 저장한 사람이 마지막으로 쓴 칸은 덮지 않고

  겹친 이름은 다른 칸 안에 들어간 복사본 쪽을 새 이름으로 바꿔 원래 자리의 「절:2」 가 그 이름을 지킨다.
- 칸 안의 칸 설정값을 글로 읽던 것(운영 실측): 칸째 붙여넣기로 칸 안에 칸이 들면 서버의 칸 글 읽기(field_values·fields·_frag_text)가 안쪽 칸의
