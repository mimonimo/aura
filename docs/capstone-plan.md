### 1.1 "실사용"이 추가하는 요구 — 캡스톤 범위에 원래 없던 것

발표로 끝나는 프로토타입과 행정에 실제로 들어가는 시스템은 요구사항이 다르다.
아래 세 가지는 나중에 붙이기 어렵거나 불가능하므로 **지금 설계에 심어야 한다.**

1. **접근권한 설계 (미해결 질문 #7).** 원안에서도 "나중에 붙이기 매우 어려움"으로
   경고된 항목인데(브리프 9장), 실사용이면 발표 직후부터 여러 부서가 쓰기 시작한다.
   문서별 열람 등급을 **검색 단계에서 필터링**하는 구조를 W2까지 확정한다.
2. **운영 인수인계.** 캡스톤 팀은 해산하지만 시스템은 남는다. 원안 §9의 "담당 인력 이탈"
   위험이 캡스톤에서는 확정된 사건이다. 12월 이후 유지보수 주체를 정하고,
   그 전제인 문서화·재현 절차를 W1부터 누적한다(브리프 12장 "문서화 우선").
3. **책임 경계의 명시.** 브리프 2장의 "70% 초안 · 사람 검수 전제"를
   발표 자료와 사용자 문서 양쪽에 명문화한다. 근거 없는 수치가 계획서에 들어가면
   허위 기재로 **사업 취소·환수·제재 사유**가 된다(5.3). 실사용 전환 시
   이 경고가 시스템 UI 안에도 있어야 한다.

### 1.2 발표회용 데모 데이터

공개 발표에서 실제 국고사업 문서를 화면에 띄우게 된다.
**비식별화를 통과한 데모 세트를 별도로 준비**하고, 어떤 사업·연도를 쓸지 W2에 확정한다.
Presidio 파이프라인 산출물을 그대로 쓰되, 발표 전 육안 검수를 한 번 더 거친다.

원안 대비: P1~P5 = 30주 → **13주**. 산술적으로 43% 압축이며, 단순 가속으로는 불가능하다.
아래 §3의 삭감 없이는 일정이 성립하지 않는다.

## 2. 압축의 원칙 — 무엇을 지키고 무엇을 버리는가

**절대 지키는 것 (브리프 11장 금지사항 + 논문 성립 요건)**

1. **★게이트 — P3 베이스라인 측정 후에만 학습 시작.** 순서를 바꾸면 축 B의 개선폭을
   주장할 수 없고, 그 순간 논문의 기여가 사라진다. 일정이 밀려도 이 순서만은 고정한다.
2. **평가셋 우선 (5.5).** 논문의 실험 섹션 전체가 여기 의존한다.
3. **수치는 인출, 생성 금지 (5.3).** 파이프라인 구조 수준 강제.
4. **PII 스크리닝은 인덱싱 이전.** 사후 조치 = 벡터DB 전체 재구축.
5. **파일럿 우선.** 계획서 20~30건 + 대응 결과보고서. 수만 장 전체로 시작하지 않는다.

**버리는 것 (범위 축소 — 논문에는 "향후 과제"로 기재)**

| 항목 | 원안 | 처리 | 근거 |
|---|---|---|---|
| 선호 최적화(DPO) | P5 후반 | **제외** | `research/51` 전제인 학생 8명 2회 집중 투입이 13주에 안 들어감. SFT까지가 상한 |
| 학생 검수 인력 | 2회 집중 (P2~P3, P5) | **1회로 축소** (W3~W6) | 실적 카드·평가셋 검수에만 투입 |
| P6 그래프 A/B | 조건부 2~4주 | **제외** | 원안에서도 조건부. `01-C` 결론이 이미 "미도입" |
| P7 전체 확장 | 8주 | **제외** | 파일럿 범위 유지 |
| ④ 지출 문서 계열 | P7 편입 | **제외** | 브리프 11장이 초기 범위 포함을 금지 |
| 운영 서버 사양 산정 | 산출물 11번 | **약식** | P2~P5 실측 로그 기반 1~2p 부록으로 대체 |

**모델 4종은 유지한다.** 축 B가 논문의 본체이고, Embed/Rerank/Extract는 학습 비용이
낮다(소형 모델·대조학습·증류). 비용이 큰 것은 Writer(35B MoE QLoRA) 하나뿐이다.

## 3. 주차별 계획

### W1~W2 (9/1~9/14) — P1 설계 + 환경 + 파서 확정

원안 P1(2주) + P2 앞부분을 겹친다. 설계 문서는 P0 리서치가 이미 결론을 좁혀 놨으므로
새 판단이 아니라 확정 기록에 가깝다.

- `docs/architecture.md` · `model-plan.md` · `eval-plan.md` · `pilot-plan.md` · `risks.md`
- **DGX Spark 환경 구축** — vLLM 검증 이미지 태그 고정, LLaMA-Factory/Unsloth 스모크 테스트
  (aarch64 + sm_121 빌드 이슈는 `00-summary` 위험 2번 — 여기서 터지면 조기에 알아야 한다)
- **파서 bake-off** — MinerU 3.x ↔ Docling, 실물 결과보고서 30~50p 대조. 표 구조 보존이 판정 기준
- 병행: 개인정보 검토 착수, 벡터 스토어 확정(Qdrant vs pgvector)

**완료 판정**: 설계 5종 승인 + 파서 확정 + 학습·서빙 스택 실동작 확인

### W3~W5 (9/15~10/5) — P2 파싱 + 평가셋

- 파일럿 문서 파싱 → PII 마스킹(Presidio + 한국형 recognizer 6종) → 계열 분류·메타데이터
- 청킹(섹션·표 인지) → 이중 벡터화(dense + Kiwi sparse) → 인덱스 적재
- **평가셋 v1 구축** — 검색 IR 평가셋 + 생성 평가셋. 학생 검수 인력 투입 구간
- 합성 질의 생성(Embed 학습 데이터) 병행 — 파싱만 끝나면 만들 수 있으므로 미리 쌓는다

**완료 판정**: 파일럿 문서 인덱싱 완료 + 평가셋 v1 확정
**최대 위험 구간**. 파싱 품질이 전 영역의 상류이고(위험 1번), 평가셋 구축이 실작업의 90%다.

### W6~W8 (10/6~10/26) — P3 검색 + 실적 카드 DB + ★베이스라인

- 하이브리드 검색(RRF) + 리랭킹 파이프라인
- **실적 카드 DB** — 구조화 추출(xgrammar 형식 보장 + 원문 대조 내용 보장) → 사람 검수
- **★베이스라인 측정** — KURE-v1 / bge-reranker-v2-m3 베이스 그대로의 Recall@k·MRR·nDCG
- W8 베이스라인 확정 즉시 **ZZAIMY-Embed 학습 착수** (게이트 통과했으므로 순서 위반 아님)

**완료 판정**: 베이스라인 리포트 확정 — 이후 모든 개선폭 주장의 비교 기준

### W9~W10 (10/27~11/9) — P4 생성 + 검증기

- 공고 스키마 추출 → 섹션별 생성 루프(통짜 생성 금지)
- **검증기 3종** — 수치 대조(생성 수치 ⊆ 인출 근거) · 배점 커버리지 · 예산 계산(LLM 금지)
- 실공고 1건 end-to-end 초안 생성
- 병행: Embed/Rerank 학습 계속, Extract 증류 착수

**완료 판정**: 출처 주석 달린 초안 1건 + 배점 커버리지 보고서

### W11~W12 (11/10~11/23) — P5 모델 트랙

- `ZZAIMY-Embed` / `ZZAIMY-Rerank` — 개선폭 측정 (W8부터 돌린 것의 마무리)
- `ZZAIMY-Extract` — 필드 F1 · 처리량 배수
- `ZZAIMY-Writer` — QLoRA 섹션 SFT. **출력 수치 ⊆ 입력 근거 정제 후 학습**
- 모델 카드 4종 + 평가 보고서

**완료 판정**: 베이스 대비 개선폭이 재현 가능하게 측정됨

### W13 (11/24~11/30) — 마감

- 최종 측정 정리, 논문 탈고, 발표 자료
