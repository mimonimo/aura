# 협업 방식 — 명세와 구현의 분리

> 명세(브리프·리서치): 교수님 / `mrgrit/zzaimy`
> 구현: 본 저장소 (포크)

## 1. 원칙

**포크에서 업스트림 파일을 수정하지 않는다.**

| 파일 | 소유 | 포크에서 |
|---|---|---|
| `PROJECT_BRIEF.md` | 교수님 | 읽기 전용 |
| `research/**` | 교수님 | 읽기 전용 |
| `docs/business-plan.md` | 교수님 | 읽기 전용 |
| `docs/capstone-plan.md`, `docs/decisions/**`, `src/**`, `configs/**`, `scripts/**`, `tests/**` | 구현자 | 자유 |

이걸 지키는 한 업스트림 병합은 항상 충돌 없이 통과한다.
한 번이라도 어기면 이후 모든 동기화에서 손으로 충돌을 풀어야 하고,
"모든 판단의 기준 문서"가 두 갈래로 갈라진다.

P1 설계 문서 5종(`architecture.md` 등)의 소유권은 별도 합의가 필요하다.
브리프 9장은 이를 프로젝트 산출물로 규정하므로, **작성은 구현자가 하되
승인은 교수님이** 하는 형태를 기본으로 제안한다.

## 2. 업스트림 동기화

```bash
git remote add upstream https://github.com/mrgrit/zzaimy.git   # 최초 1회
git fetch upstream
git merge upstream/main
```

주 1회 정기적으로. 브리프가 갱신되면 `docs/decisions/`의 기존 결정 중
전제가 무너진 것이 없는지 확인한다.

## 3. 되돌려 보내는 채널 — 구현이 명세에 알려야 할 것

브리프 0장은 추측으로 채우지 말고 질문하라고, 12장은 갈리는 지점을
임의 결정하지 말고 선택지를 제시하라고 지시한다. 조용히 우회하지 않는다.

| 상황 | 방법 |
|---|---|
| 미해결 질문의 답이 필요함 | 업스트림 Issue — `research/99-open-questions.md`의 번호 인용 |
| 실증 결과가 리서치 추천을 뒤집음 (예: bake-off) | ADR 작성 → 업스트림에 PR 또는 Issue로 근거 제출 |
| 명세대로는 13주에 안 들어감 | ADR에 `상태: 제안` → 주간 동기화에서 승인 |
| 구현 중 발견한 명세의 빈틈 | Issue. 브리프 수정은 교수님이 판단 |

**리서치 문서를 포크에서 고쳐서 반영하지 않는다.** 근거를 들고 업스트림에 올린다.

## 4. 보고 주기

- **주 1회 동기화** — 진행 상황, `상태: 제안`인 ADR, 막힌 지점
- **Phase 게이트** — 브리프 12장의 공식 승인 지점. 13주 압축안에서도 유지한다
  - P1 종료: 설계 5종 승인
  - **P3 종료: 베이스라인 리포트 확정 (★ 순서 변경 불가)**
  - P5 종료: 모델 카드·평가 보고서 4종

주간 동기화는 진행 공유, Phase 게이트는 승인. 둘을 섞지 않는다.

## 5. 브랜치

```
main            항상 동작하는 상태
feat/<범위>     예: feat/parser-bakeoff, feat/eval-harness
```

`main`을 깨진 상태로 두지 않는다. 발표 시연이 `main`에서 나가야 한다.

## 6. 커밋에서 절대 하지 않을 것

- 실제 국고사업 문서·파싱 결과·실적 카드 커밋 (`.gitignore`로 차단돼 있으나 `git add` 전 `git status` 확인)
- 업스트림 파일 수정
- 근거 없이 브리프의 금지사항(11장)을 우회하는 구현
