세션 로컬 메모리를 저장소로 옮긴 것. 현재 인프라 상태는 `docs/HANDOFF.md`,

(비밀번호 등 실제 비밀은 여기 없음 — 별도 전달.)

## 사용자·협업 방식

- 구축·시운영·의사결정은 전부 사용자(학생) 단독. 교수님은 초기 개념 제시까지(ADR-0005, PR 승인 생략).
- 사용자는 git/PR·SFT 같은 용어에 익숙하지 않음 — 설명은 비유 중심으로 쉽게, 명령은 복붙 가능한 한 줄로.
- 확신 없으면 추측으로 채우지 말고 질문. 판단 갈리면 선택지+트레이드오프 제시. 검증 안 된 건 "미확인"으로.

## 제품 철학·우선순위

- 가치 = "에이전트가 업무를 이해해서, 사람이 일일이 검토하지 않아도 되게 의사결정을 돕고 귀찮은 일을 줄이는 것". 전결·결재 워크플로 재현은 하지 않는다(기존 포털에 이미 있음).
- 우선순위: ① 에이전트+대시보드를 빨리 가동 ② 실문서 넣고 돌리며 점진 강화 ③ 파인튜닝은 시스템이 돈 뒤. 완성도 검증에 매몰되지 말 것.
- 주 사용자 = 교직원(행정 담당자). 학생 규정 질문도 담당자의 민원·서류 처리 관점(절차·확인사항·근거)으로 답한다.
- 고도화 방향(사용자 당부): 멀티 에이전트 협업(검토/규정/초안), 지식그래프 점진 도입(doc_chunks에 기반 준비됨).

## 작업 안전 규율 (반복 사고에서 나온 것)

- **템플릿은 문자열 패치(sed/replace) 금지** — 조용한 미적용·과잉삭제 사고 반복. Edit/Write로 고치고 div 균형·핵심 셀렉터 존재를 검증.
- **base.html의 `{% block head %}`는 기본 `<style>` 뒤에** 있어야 페이지 CSS가 이긴다(이 순서 결함으로 반나절 헤맴).
- **UI 변경은 배포 전 눈으로 확인** — 헤드리스 크롬 캡처(스크립트 있으면) 후 Read로 직접 확인. 안 보고 배포 금지.
- **하드코딩·억지 짜맞추기 금지** — 사용자가 알려준 특정 오타·사례를 규칙에 넣지 말 것. 일반 메커니즘(모델 교체·학습·전처리·일반 교정)으로만 성능 개선.
- **가용 자원 꽉 채우지 말 것** — CPU/메모리 무거운 작업은 코어 절반·낮은 우선순위, 순차 처리.

## 데이터 원칙

- **기준(규정·지침·공고) 문서는 PII 마스킹하지 않는다** — 판단 근거라 원문 유지. 마스킹은 개인식별 가능한 인풋 문서에만.
- **외부 수집 자료의 자리(2026-09-21 갱신)**: 교내 실물 문서가 들어오기 전 개발 단계에서는 공개 국고사업 문서를 기준 문서로
  쓴다(사용자 지시: 재반입 대상 = 웹의 국고사업 문서 + 영남이공대 서류). 이 분량은 `owner=corpus` 로 표시하며 마스킹 대상이다
  (기준 문서 마스킹 제외의 예외). 나중에는 교내 문서·사용자가 올린 문서로 바뀐다 — 수집 스크립트는 개발용이다.
- 웹 수집 .txt는 보일러플레이트(메뉴 노이즈) 제거 후 등록. 홍보·소개성 페이지는 기준 저장소 제외.

## 2026-09-21 에 굳은 규칙

- **모델은 계획 문서의 4종만**(Embed·Rerank·Writer 27B·Extract 4B). gemma 같은 문서 밖 모델을 편의로 끼워 넣지 않는다.
  서빙 스택은 vLLM 하나, 토르 02 = 대화·초안, 토르 03 = 검토·판독·검색, DGX = 학습 전용(ADR-0023).
- **측정·배치는 `.env.local` 을 읽고 띄운다.** 안 읽으면 서빙 장비 대신 CPU 베이스로 조용히 떨어져 수치가 거짓이 된다.
  보고서의 "리랭커: 서빙 장비 … 응답 N · 폴백 M" 줄을 확인한다.
- **젯슨은 큰 파일을 받은 뒤 캐시를 비우고 서빙한다**(root `sync; sysctl vm.drop_caches=3`). CUDA 가용은 `free` 가 아니라
  `torch.cuda.mem_get_info()` 로 본다.
- **root 가 필요하면 우회하지 말고 명령을 사용자에게 준다.** 별도 포트에 몰래 띄우는 식의 우회는 하지 않는다.
- **새 기능·규칙을 넣으면 문서를 그 자리에서 최신화하고 기존 검증(테스트·스모크·PII·반입·서빙·측정)을 전부 다시 돌린다.**
  소급이 필요한 규칙(이름 등)은 실제 반입 경로로 자가 점검(scripts/125)해 저절로 되는지 본다.
- **깃허브가 정본.** 맥 → VM rsync 로 밀어 넣지 않는다(트리가 더러워져 pull 이 막힌다). 배포는 커밋·푸시 → VM pull.
- VM·토르가 한꺼번에 안 닿으면 사용자 VPN 미연결 — 기다렸다 재시도. 긴 작업은 setsid 로 띄우고 재시도 루프를 둔다.

## 2026-09-24 에 굳은 규칙 — 실물 문서 세트와 구글 독스 작업

- 문서 세트(공고·기본계획·지침·양식·계획서·표)는 프로젝트 하나로 묶는다. 공고·기본계획·지침·심사 기준은 VM 문서함에
  기준 문서로 등록해(기준 조각·프로젝트 연결) 검색·검토·분석에 쓰고, 양식·계획서·표는 접수 문서로 둔다. 나중에는
  새 채팅에 던지면 프로젝트가 생기고 지난 자료(같은 사업의 지난 판본·기준)가 자동으로 이어져야 한다.
- 한글(hwp·hwpx)은 구글 독스로 바꿔 여러 사람과 에이전트가 같이 작업한다. 변환은 무조건 미리 돌리지 않고 담당자가
  그 문서를 열거나 "이 문서로 작업하자"고 할 때만 한다. 엑셀·PPT·PDF 는 우리 변환기를 거치지 않는다(구글이 바꾸거나
  그대로 미리보기). 한글 에이전트(COM)는 지금 우선순위가 아니다.
- 변환 품질은 원본 양식과 가장 비슷하게 — 표 테두리·바탕색·병합·열 너비·글자 크기·정렬·그림까지(hwpx_docx.py).
  독스에서 실물로 보고 다듬는 일을 계속한다. 소스마다 다르다: hwpx 는 우리 변환기, hwp 는 pyhwp HTML 경로.
- 문서를 작성할 때는 원본 서식은 그대로 두고 복제본(작업본 YYYY-MM-DD)을 만들어 그 복제본에 쓴다. 언제든 다시
  작성할 수 있어야 한다. 어떤 문서를 고칠지 분명해야 한다 — 이름이 비슷한 후보가 여럿이면 되묻고, 문서함에서
  골라 "이 문서로 작업"도 된다.
- 질문에는 드라이브 문서를 만들지 않는다. 이름 바꾸기·옮기기는 담당자가 말했을 때만(모델이 '자기소개서'로 개명한 사례).
- 문서에 써 넣는 글에서 기관명·총장·담당자 이름·업무 전화·전자우편은 가리지 않는다(신청서·공문에 적어야 하는 정보).
  주민번호·계좌·사업자번호만 가린다. 담당자나 값을 모르면 ○○○·빈칸 그대로 두고 무엇이 비었는지 말한다.
- 문서 작성 확인은 몇 줄 넣는 시험이 아니라 양식 복제본에 절 단위로 제대로 채우는 실행으로 한다.
- 여러 사람이 나눠 쓰고 합본하는 경우가 많다(부서별 절 작성 → 합본 → 검토). 독스 공동 편집과 합본 흐름을 설계에 둔다.
- 교내 문서도 학교 워크스페이스 드라이브까지는 올린다(공개가 아니다). 외부 공유는 하지 않는다.
- 지적된 항목은 그때그때 회귀 테스트(tests/test_project_bundle.py·test_gdocs.py·test_scrub_for_writing.py·test_hwpx_docx.py)로
  남겨 다시 생기지 않게 한다.
- 지시 없이 스스로 점검한다: 문서 작업 흐름은 `scripts/144_flow_selfcheck.py --project N` 로 9항목(반입·갈래·기준 조각·색인·검색·재료·
  구글·제안·대화)을 돌려 WARN·FAIL 을 먼저 없앤 뒤 보고한다. 새 기준 문서가 들어오면 재색인(96)까지 한 묶음이다.
