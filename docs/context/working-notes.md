# 작업 원칙 — 제품 방향·문서 규칙·운영 주의

현재 인프라 상태는 `docs/HANDOFF.md`, 작업 지침은 `CLAUDE.md`, 판단 기준은 `PROJECT_BRIEF.md` 에 있다.
이 문서는 그 사이에 쌓인 원칙과 주의사항을 모은다. 비밀값은 여기 두지 않는다.

## 제품 방향

- 가치는 업무 맥락을 이해해 의사결정을 돕고 반복 작업을 줄이는 데 있다. 전결·결재 흐름은 기존 포털에 있으므로 재현하지 않는다.
- 순서는 에이전트와 대시보드 가동 → 실문서를 넣어 돌리며 점진 강화 → 시스템이 돈 뒤 파인튜닝이다.
- 주 사용자는 행정 담당자다. 학생 규정 질문도 담당자의 민원·서류 처리 관점(절차·확인사항·근거)으로 답한다.
- 근본 목적은 로컬 Writer 27B 가 문서 맥락 파악부터 새 사업 초안까지 해내는 것이다. 정답(합본)을 코드에 넣어 문서를 찍어 내는
  스크립트는 만들지 않는다. 구조는 코드가 보여 주고 판단은 모델이 한다.
- 실전 흐름: 문서 검토 → 문서함에서 과거 사업 찾기 → 맥락 생성 → 양식대로 초안 → 사람과 에이전트가 고도화 → 합본.
  초안은 에이전트 대화에서, 개별 문서 화면은 검토용이다.
- 외부 사례(kordoc 등)는 흐름을 베끼지 않고 원리와 기술만 흡수한다. 협업은 독스, 최종 산출은 원본 한글 서식(ADR-0035).
- 폐쇄망은 인터넷 차단이 아니라 중요 정보가 밖으로 나가지 않게 통제한다는 뜻이다.

## 유즈케이스

1. 국고사업 계획서 지원(주 트랙, PROJECT_BRIEF).
2. 채용 서류 검토(확장 — 접수 서류를 로컬 모델로 검토 의견 생성).

문서 작성 루프는 공고(연결 기준) → 입력 서류 → 초안 → 담당자 의견 → 재작성이다. 프로젝트는 사업·공고·학년도·학과 단위로 만들어
입력과 검토를 묶는다.

## 문서·말투 규칙

- README·설계·기획서는 담백한 서술형으로 쓴다. 이모지 상태표, 굵게 남발, 슬로건, 조문체, 과한 표·목록을 피한다.
- 화면 문구는 짧은 명사형(「판정 대기 3」). 대시보드 서술은 격식 있는 자연문.
- 화면에 내보내는 「제목」 뒤 조사는 받침대로 붙여 쓴다(`korean_text.quote`·`josa`, 옛 답변은 `particles` 필터). 길이로 자를 때는
  `korean_text.clip` 으로 문장·낱말 경계에서 자른다(낱말 중간에서 끊지 않는다).
- 채팅 문서 패널은 답이 올 때마다 편집기를 다시 불러오지 않는다. 구글 편집기는 API 로 넣은 글을 바로 받는다(ADR-0029).
  다시 불러오는 것은 담당자가 위치 이동을 고를 때뿐이고, 그동안 「…위치로 이동하는 중」 덮개를 iframe 의 load 까지 둔다.

## 화면 디자인 (교내 LMS 계열)

- 다크네이비 탑바 `#16223A`, 네이비 `#1B3B75`, 포인트블루 `#497BFB`, 배경 `#F2F6F9`.
- 라운드 카드 16px, 필터 필(활성 진초록). 기존 계열 모양을 유지한다.
- 화면 숫자는 `app/metrics.py` 의 지표 이름·정의를 쓴다(`metric_label`·`metric_tip`). 다른 집합을 세면 다른 이름으로 — 같은 이름에 다른 숫자가 나오지 않게.
- 개발 화면 이름은 `app/dev_nav.py` 표 하나에서(사이드바·머리·탭 제목). 업무 목록은 `app/work_areas.py`.
- 되돌리기 어렵거나 오래 걸리는 동작의 폼에는 `data-confirm="무엇이 바뀌는지"` 를 단다(공용 확인은 `workspace-navigation.js`, 자체 확인창이 있으면 `data-own-confirm`).

## 코드 작업 주의

- 기존 흐름을 활용해 작고 명확하게 고친다. 불필요한 추상화·설정·중복 구현을 더하지 않는다.
- 템플릿은 문자열 치환(sed)으로 고치지 않는다. 조용히 안 먹거나 과하게 지워진다. 고친 뒤 div 균형과 핵심 셀렉터를 확인한다.
- `base.html` 의 `{% block head %}` 는 기본 `<style>` 뒤에 있어야 페이지 CSS 가 이긴다.
- 화면 변경은 배포 전에 헤드리스 캡처로 직접 확인한다.
- 화면 인라인 스크립트는 즉시 실행 함수(`(function () { … })()`)나 모듈로 감싼다. 맨 바깥 `var status` 같은 선언은
  브라우저 전역(window.status)과 부딪혀 스크립트가 멈춘다. `tests/test_page_scripts.py` 가 전역 이름 충돌을 잡는다.
- 확인창은 폼마다 `onsubmit="return confirm(…)"` 로 따로 두지 않고 위의 `data-confirm` 공용 규칙을 쓴다.
- 특정 사례·오타를 규칙에 넣지 않는다. 성능은 일반 메커니즘(모델 교체·학습·전처리·일반 교정)으로만 올린다.
- 무거운 작업은 코어 절반·낮은 우선순위로 하나씩 돌린다.

## 데이터 원칙

- 내부 마스킹은 기본 꺼짐이며 설정을 따른다(ADR-0044). 기준 문서 원문과 접근 권한은 보존한다. 학습 사본의 개인정보 검수·승인은
  별도이며 내부 설정으로 끄지 않는다.
- 교내 실물이 들어오기 전 개발 단계에서는 공개 국고사업 문서를 기준 문서로 쓴다. 이 분량은 `owner=corpus` 로 표시하고 마스킹
  대상이다. 수집 스크립트는 개발용이다.
- 웹 수집 .txt 는 메뉴 같은 반복 문구를 지운 뒤 등록한다. 홍보·소개성 페이지는 기준 저장소에서 뺀다.
- 문서함에는 실문서만 둔다. 한글은 반입 때 PDF 로 바꿔 문서 화면 본문에 보인다. 대학명·총장 등 기관 정보는 규정·문서함에서
  가져오고, 없으면 비우고 설정으로 보정한다.

## OCR 복원 뷰

- 디지털 PDF 배치 복원은 `src/zzaimy/app/pdf_lines.py` 가 pdfium 글자 상자로 좌표를 직접 읽는다. MinerU 블록 상자 근사는 경계 잘림
  때문에 쓰지 않는다.
- 같은 줄 조각을 병합하지 않는다(2단 목차가 뒤엉킨다). 스캔·사진은 OCR 경로(VLM/MinerU)로.
- 문서 뷰어는 원본/AI 읽기 2탭이다.

## 모델·서빙·측정

- 모델은 계획 문서의 4종(Embed·Rerank·Writer 27B·Extract)만 쓴다. Extract 는 Writer 27B 를 공유한다. 서빙은 vLLM 하나,
  토르 02 는 대화·초안, 토르 03 은 검토·판독·검색, DGX 는 원본 보관·일괄 처리·학습을 맡는다(ADR-0023).
- 측정·배치는 `.env.local` 을 읽고 띄운다. 안 읽으면 CPU 로 떨어져 수치가 틀린다. 보고서의 「리랭커: 서빙 장비 … 응답 N · 폴백 M」
  줄로 확인한다.
- 젯슨은 큰 파일을 받은 뒤 페이지 캐시를 비우고 서빙한다. CUDA 가용량은 `torch.cuda.mem_get_info()` 로 본다.
- 깃허브가 정본이다. 배포는 커밋·푸시 → VM pull 이며, rsync 로 밀어 넣지 않는다.
- 새 기능·규칙을 넣으면 문서를 바로 고치고 기존 검증(테스트·스모크·PII·반입·서빙·측정)을 다시 돌린다. 소급이 필요한 규칙은
  실제 반입 경로로 자가 점검(scripts/125)한다.

## 문서 세트와 구글 독스 작업

한글 COM 에이전트는 ADR-0034 로 폐기됐고, 최신 경로는 `document-work-flow.md` 를 따른다.

- 문서 세트(공고·기본계획·지침·양식·계획서·표)는 프로젝트 하나로 묶는다. 공고·기본계획·지침·심사 기준은 기준 문서로, 양식·계획서·표는
  접수 문서로 둔다. 같은 사업의 지난 판본과 기준은 자동으로 이어진다.
- 한글은 담당자가 그 문서로 작업하자고 할 때만 독스로 바꾼다. 엑셀·PPT·PDF 는 구글이 바꾸거나 그대로 미리본다.
- 변환은 원본 양식과 가장 가깝게(표 테두리·바탕색·병합·열 너비·글자 크기·정렬·그림, `hwpx_docx.py`).
- 작성은 원본을 두고 복제본(작업본 YYYY-MM-DD)에 한다. 고칠 문서가 분명하지 않으면 되묻는다.
- 질문에는 드라이브 문서를 만들지 않는다. 이름 바꾸기·옮기기는 담당자가 요청할 때만 한다.
- 문서에 쓰는 글에서 기관명·총장·담당자 이름·업무 연락처는 가리지 않는다. 주민번호·계좌·사업자번호만 가린다. 모르는 값은
  ○○○·빈칸으로 두고 무엇이 비었는지 알린다.
- 부서별 절 작성 → 합본 → 검토 흐름을 설계에 둔다. 교내 문서는 학교 워크스페이스 드라이브까지만 올리고 외부 공유하지 않는다.
- 문서 작업 흐름은 `scripts/144_flow_selfcheck.py --project N` 의 9항목(반입·갈래·기준 조각·색인·검색·재료·구글·제안·대화)으로
  점검한다. 새 기준 문서가 들어오면 재색인(96)까지 한 묶음이다.
- 테스트는 실제 구글 토큰·운영 데이터에 닿지 않는다(`tests/conftest.py` 가 `ZZAIMY_DATA_DIR` 을 임시 폴더로). 시험용 드라이브 업로드는
  만들면 지운다.
- 긴 판독은 서비스 재시작에 끊기므로 scripts/143 으로 서비스 밖에서 돌린다. `pkill -f` 패턴은 앞을 고정해 자기 ssh 명령줄과 겹치지
  않게 한다.
