   정답은 사람이 붙이지 않아도 되게, 조각 자신에서 유도하는 방식을 쓰되 그 방식의
   한계를 기록하라.
2. Recall@1·Recall@5·MRR 을 재고, **변경 전후를 비교할 수 있게** 결과를 파일로 남긴다.
   (`data/eval/` 아래. `data/` 는 커밋하지 않는다.)

   어느 값이 잡음을 걷으면서 정상 검색을 지키는지 **수치로** 보고하라.

검증 기준: 같은 명령을 두 번 돌리면 같은 수치가 나올 것. 수치는 전부 기계 산출물에서
오고, 확인하지 못한 것은 미확인으로 적을 것. 운영 서버는 재처리가 끝난 뒤에만 쓰고,
배포·재시작은 하지 말 것.

막히거나 범위를 바꾸고 싶으면 `codex.md` 에 요청 ID 와 함께 남겨 달라.

## K-20260921-33 — 재반입에서 드러난 결함 두 가지

문서함을 비우고 원본에서 다시 올리니 손질로 가려져 있던 것이 드러났다.

1. **파일 이름 충돌**: 교내 내려받기 파일은 이름이 URL 이라 앞부분이 모두 같다
   (`www.ync.ac.kr_kor_ajx_json_UploadMgr_downloadRun.do_qcode_…`). 문서함에 넣을 때 60자로
   잘랐더니 서로 다른 문서가 같은 파일로 덮였다 — 113건이 몇 건으로 뭉갰다. 경로 해시를 붙여 고쳤다.
2. **이름 변환이 한 갈래에만**: 본문 제목으로 바꾸는 절차가 기준 문서 갈래에만 붙어 있어

## K-20260921-38 — 판독 경로의 결함 둘 (스캔 문서가 읽히지 않던 이유)

재반입에서 스캔 PDF 가 계속 제한 시간에 걸렸다. 재 보니 두 가지가 겹쳐 있었다.

1. **쪽수 많으면 판독을 통째로 건너뜀**: `_pdf_to_images(max_pages=4)` 가 4쪽을 넘으면 빈 목록을
   돌려줬다. 53쪽 스캔본은 어느 경로로도 읽히지 않은 채 구조 추출 240초 + CPU OCR 만 소진했다.
   → 앞쪽부터 상한(`ZZAIMY_VISION_MAX_PAGES`)까지 읽고, 일부만 읽었으면 처리 기록에 남긴다.
2. **CPU OCR 이 판독보다 먼저**: 글자층이 없는 PDF 도 docling(CPU OCR)을 먼저 거쳤다. 큰 스캔본은
   그 단계만 십수 분이라 판독까지 가지 못했다. → 글자층이 없고 판독 모델이 있으면 바로 비전으로 읽는다.

판독 모델 자체는 정상이었다(한 쪽 45초·13,273자). 경로가 그리로 가지 않았을 뿐이다.
검증: 140쪽 디지털 PDF 는 글자층 직독으로 0.1초·41,757자(이전에는 10분 초과 실패).

남은 실패 2건(20MB 스캔본, 0.3MB PDF)은 그대로 두고 반입을 마친 뒤 따로 본다.

## K-20260921-39 — 문서 이름을 표 줄로 잡던 결함 (증거)

목록에 없는 종류를 버려서, 표 칸에만 남겼다.

이름 규칙을 고치면 이미 들어온 문서도 다시 매겨야 한다. `overwrite` 는 저장된 이름을 무시하고
