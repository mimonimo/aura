## 아스트라에게 — Writer SFT 비교 (2026-10-24, 요청 — 1순위 막힘 있음)

오픈 모델(zzaimy-writer, Qwen3.8-27B NVFP4)과 Writer SFT 를 모델만 바꿔 같은 시험으로 비교했다(ADR-0069, 논문 원재료 4.7d).
결과는 운영 VM `data/eval/model_compare/sft-compare-20261024/`(관리자 화면), 원자료는 VM `~/ops/sft_eval/`(저장소 밖 — 시험 문항 원문이 들어 있음).
아래 문항 번호는 test.jsonl 의 줄 순서(test-000 = 첫 줄)다. 원문은 여기 옮기지 않는다.

0. 막힘 1순위 — 병합본에서 플랫폼 문서 작업 에이전트가 동작하지 않는다(확인). 운영 토르 02 를 병합본(writer-sft-v1-merged-nvfp4)으로 바꾼 상태에서
   문서 작성 시나리오(scripts/202, 양식 없이 시작 11턴, 2회)를 돌렸더니 두 회차 모두 작업본을 못 만들었다(오픈 모델 2/2, 쓴 절 6.5 → 0).
   묻기만 하고 끝난 턴 82%(오픈 14%), 단계 출력을 못 읽어 멈춘 턴(stop=format) 18%(오픈 0%). 작업 메모(chat_memory) 갱신 출력이
   「근거 설명: … 검색 계획: {…} 답변: …」 로 학습셋 틀 그대로였다(1회차 11/11턴). 평범한 업무 질문 15개(scripts/213)에도 틀(줄머리 「답변:」)이
   나왔다 — 지시 없음 11/15, 플랫폼 답변 지시(src/zzaimy/app/responder.py _SYSTEM) 15/15, 학습셋 지시 13/15(오픈 모델은 모두 0/15).
   원인은 학습쌍이 한 가지 꼴(한 줄 시스템 지시 + 질문 → 「근거 설명·답변」 틀)뿐이라는 것. 요청: 다음 학습셋에 플랫폼이 실제로 보내는 꼴을 넣는다 —
   (가) 문서 작업 에이전트 단계 JSON(도구 고르기·인자), (나) 작업 메모 갱신(지금 목표·확정된 것·진행·남은 일), (다) 채팅 답(responder 지시, 600자 안팎),
   (라) 절 쓰기·고쳐 쓰기 지시(작성방법·근거 조각이 든 서빙 프롬프트, scripts/152 real_pairs 꼴). 아니면 적어도 플랫폼이 쓰는 시스템 지시로 학습하고,
   「근거 설명/답변」 틀은 그 틀을 요청하는 지시가 있을 때만 나오게 한다. 넘기기 전 점검: `scripts/213`(틀 0/45 이어야 함)과 202 한 회차(작업본 만듦).
   참고로 학습 꼴 안에서는 좋아졌다 — 시험 문항 220 chrF 27.9 → 36.6, ROUGE-L 16.8 → 27.3, 길이 1.81배 → 0.96배, 질문에 없는 숫자 4.1% → 0%, 잘림 2.7% → 0%,
   정답 로그확률 -1.845 → -1.153. 채점 모델의 나은 답 고르기는 0.309(오픈 쪽, 대조군 잡음 폭 0.475~0.559 밖) — 병합본이 진 문항은 답이 짧았다(오픈의 0.63배).
1. 어댑터가 서빙에서 얹히지 않았다(확인). 토르 02 의 writer-sft 는 정답 토큰당 평균 로그확률(앞 40문항 -1.845)·첫 토큰 상위 5개 확률이
   오픈 모델과 소수 다섯째 자리까지 같다. 학습 손실은 1.43 → 0.92 로 내려갔으니 학습 문제가 아니라 이름 문제로 본다. 어댑터 키가
   `base_model.model.model.layers.N.*` 인데 vLLM 이 올린 모델(Qwen3_5ForConditionalGeneration)은 `model.language_model.layers.N.*` 이라 어디에도 붙지 않는다
   (기동 기록에는 어댑터를 읽었다고 나오고 visual.* 만 무시했다고 나옴). 요청: LoRA 로 서빙할 거면 키 접두를 language_model 로 바꿔 저장하거나,
   병합본으로 서빙한다. 어느 쪽이든 넘기기 전에 정답 로그확률이 오픈 모델보다 내려가는지(학습 손실 근처) 먼저 확인한다 — `scripts/210 --phase goldlp`, 몇 분이면 끝난다.
2. 병합본(NVFP4 재양자화)은 운영 토르 02 를 바꾼 뒤 쟀다(옆에 :8002 로 띄우면 메모리가 부족했음). 결과는 위 0번과 ADR-0069 요약 표. 속도는 첫 글자 0.56 → 0.65초,
   초당 토큰 24.3 → 21.5(문항당 시간은 답이 짧아져 29.6 → 16.8초). 맥락 이해 30문항은 둘 다 30/30.
3. 다음 학습 데이터 제안(오픈 모델 결과와 시험 문항 정답을 견줘 본 것, 확인):
   - 학습 꼴과 서빙 꼴을 맞춘다. 시험 문항의 시스템 지시는 한 줄(「문서 근거와 앞 대화를 확인해 답합니다…」)이고 정답은 「근거 설명: … 답변: …」 틀인데,
     플랫폼은 이 틀을 요청하지 않는다. 첫 질문에서는 오픈 모델이 이 틀을 한 번도 쓰지 않았다(0/61). 이어지는 질문에서는 앞 대화에 예시가 있어 75~90% 를 따랐다.

## 반입 품질 (2026-09-19 ~ 09-22)

- 문서 이름은 본문 제목으로 바꾸고 올라온 파일 이름은 `identity.original_filename` 에 남긴다. 표에서는 문서 종류로 끝나는 칸만 이름으로 본다.

- 판본·갈래(ADR-0027): `doc_family.py`(같은 내용 거절, 판본 잇기, 붙임 잇기), `doc_routing.guess_kind`(갈래 10종).

  일부만 읽었음을 기록한다. 디지털 PDF 는 비전으로 보내지 않는다(원문 보존).

- 괘선 표 칸: 넉넉한 글자 상자로 줄을 묶고 글자 높이 15% 를 넘는 틈에 공백을 넣어 날짜·금액이 원문 그대로 나온다.

## 운영 규칙

- 실행 중일 수 있는 셸 스크립트는 파일을 덮어쓰지 않는다. 배포는 임시 파일 뒤 이름을 바꾸는 `99_deploy.sh` 로만 한다.
- 커밋은 파일을 이름으로 `git add` 하고, 커밋 전 `git diff --cached` 로 다른 작업 중인 변경이 섞였는지 본다.
- 서비스 컨테이너 이름에는 포트를 붙인다(같은 이름이면 다른 포트로 올릴 때 운영 서비스가 지워진다).
- 오래 걸리는 원격 작업은 접속에 붙여 두지 않고 떼어 돌린다(`docker run -d`, 로그 파일).
- 무거운 작업(그래프 전체, 색인 전체)은 하나씩 돌린다.
- 운영 데이터를 고치기 전에 백업하고, 지운 번호 목록을 남긴다.
