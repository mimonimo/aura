# I. 구조화 추출 (실적 카드 DB 구축의 핵심 도구)

> 조사일: 2026-08-15
> 요구: 스키마 강제(constrained decoding) 품질. 결과보고서 → 실적 카드(사업명·연도·예산·인원·성과·부서·장비·**출처문서·출처페이지**) JSON 추출 배치.

---

## 결론 요약

| 구분 | 선정 | 근거 |
|---|---|---|
| **강제 계층 1안** | **vLLM Structured Outputs (xgrammar 백엔드)** | 서빙 엔진(J 영역 1안) 내장 — JSON 스키마를 **디코딩 수준에서 100% 강제**. 별도 의존성 없음. 배치 처리량 손실 최소화(xgrammar/XGrammar-2 세대) |
| **응용 계층 1안** | **LangExtract** (Google, 38.4k★, Apache 2.0) | **소스 그라운딩 내장** — 모든 추출값을 원문 정확한 위치(오프셋)에 매핑. 브리프 5.3(수치 출처 추적)의 요구를 라이브러리 수준에서 충족. 청킹·병렬·다중 패스로 장문서 추출 최적화. 로컬 vLLM/Ollama 연동 지원 |
| **대안** | Instructor (Pydantic 재시도 방식) | OpenAI 호환 엔드포인트(vLLM) 위에서 Pydantic 검증+재시도. 단순·성숙하나 디코딩 강제가 아니라 실패 재시도라 배치 비용 예측 어려움 |
| **탈락** | Outlines 단독, BAML | 하단 참조 |

**권장 구조 (Phase 1 설계 반영)**:
```
결과보고서 파싱 산출물(페이지 단위 텍스트+표)
  → LangExtract 스타일 추출(값+원문 오프셋) — ZZAIMY-Extract 모델을 vLLM로 서빙
  → vLLM xgrammar로 JSON 스키마 강제
  → 후검증: 추출 수치가 원문 스팬에 실제 존재하는지 문자열 대조 (기계 검증)
  → 실적 카드 DB 적재 (출처문서·페이지·오프셋 포함)
```
"스키마 강제(형식 보장)"와 "소스 그라운딩(내용 보장)"은 서로 다른 문제이고, 위 구조는 둘을 분리해 각각 전담 계층에 맡긴다. 마지막 문자열 대조 단계가 수치 환각의 기계적 차단선.

## 판단 상세

- **vLLM 내장 강제를 쓰는 이유**: 어차피 J 영역에서 vLLM을 서빙 표준으로 삼는다. 추출 배치는 수만 문서 × 문서당 수 회 호출 — 재시도 방식(Instructor)은 실패율만큼 배치 시간이 늘고, 외부 constrained decoding 라이브러리(Outlines)는 서빙 엔진과의 통합 지점이 늘어난다. 엔진 내장 xgrammar가 처리량·운영 모두 최단 경로.
- **LangExtract의 가치는 그라운딩**: 추출값→원문 오프셋 매핑과 검수용 시각화(하이라이트 HTML)를 기본 제공 — 7.4의 "사람 검수 수백 건" 작업의 효율을 직접 올린다. 위험: Gemini 중심으로 설계된 프로젝트라 로컬 vLLM 경로의 성숙도는 스모크 테스트 필요. 통합이 번거로우면 "값+오프셋 동시 출력" 스키마를 자체 프롬프트로 재현하는 것도 어렵지 않음(설계 차용).
- **Outlines 탈락(단독 채택 기준)**: 훌륭한 라이브러리지만 vLLM이 동일 기능을 내장한 이상 별도 채택 이유가 없음. transformers 직접 추론 경로(비서빙 배치)를 쓰게 되면 재등판 가능.
- **BAML 탈락**: 전용 DSL 학습 비용 + 팀 생태계(TypeScript 중심 도구체인)가 본 프로젝트 스택과 이질적. 스키마 정렬 파싱(비강제) 아이디어는 참고 가치.

## 위험
1. 표 안 수치 추출은 텍스트 추출보다 오류율 높음 — A 영역 표 구조 보존 품질에 종속. bake-off와 연동 평가 필요.
2. xgrammar의 한국어 토큰 경계 이슈(한글 부분 토큰) — JSON 문자열 값 내부는 자유 생성이라 영향 제한적이나, 스모크 테스트 확인 항목.
3. ZZAIMY-Extract 학습 전(Phase 2~4)에는 대형 모델(Qwen3.5-35B-A3B 등)로 추출 배치를 돌리므로 처리 시간 계획에 반영.
