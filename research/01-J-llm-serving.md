## vLLM 채택 논거 상세

1. **Spark 공식 지원**: vLLM 블로그(2026-06-01)가 DGX Spark 아키텍처·통합 메모리 동작·Docker 배포·모니터링까지 다룸. aarch64 nightly/릴리스 이미지 존재. 초기(2026-04)에는 sm_121 인식 이슈가 있었으나(vllm #36821 등) nightly 이미지로 해소된 이력 확인 — **버전 고정 시 Spark 검증 버전 사용 원칙**.
2. **LoRA 동적 로딩**: `--enable-lora` + 런타임 어댑터 등록/해제 API — ZZAIMY-Writer LoRA를 베이스 모델 재기동 없이 교체(v0.1→v0.2 반복 개선 사이클과 정합). NVIDIA Dynamo도 vLLM 백엔드 LoRA 서빙을 공식 지원 — 확장 경로 존재.
3. **생태계 허브 효과**: A 영역(MinerU VLM·PaddleOCR-VL·DeepSeek-OCR), I 영역(xgrammar), D 영역(임베딩 pooling 서빙)이 전부 vLLM 위에서 만난다. 서빙 스택을 하나로 수렴 → 운영 표면적 최소화.
4. **배치 병렬(브리프 4장 3항)**: Spark N대에 vLLM 인스턴스를 독립 기동하고 문서 큐를 분배하는 구조 — 분산 추론 클러스터링 불필요. (듀얼 Spark TP=2는 122B급 이상 단일 모델을 올릴 때만 선택적으로.)

## SGLang을 대안으로 두는 이유

- RadixAttention: 섹션별 생성 루프는 "공고 요구사항+지시문" 공통 프리픽스가 섹션마다 반복 — 프리픽스 캐시 이득이 구조적으로 큼. Phase 4에서 생성 파이프라인 처리량이 문제되면 A/B.
- 탈락 사유(1안 기준): LoRA 동적 로딩 성숙도·Spark 공식 문서화에서 vLLM 열세. 기능 자체는 대등해지는 추세라 관찰 유지.

## Ollama / llama.cpp의 위치

- 장점: 설치 즉시 실행, GGUF 생태계, Spark 데모에 최적.
- 프로덕션 탈락 사유: 연속 배칭 처리량·LoRA 동적 교체·구조화 강제·다중 동시 요청 처리에서 서빙 엔진 대비 미달. **개발자 로컬 실험·모델 정성 평가용으로만** 공식 채택.

## 위험
1. Spark용 vLLM은 nightly/전용 이미지 의존 이력 — 재현성 위해 **검증된 이미지 태그를 문서화하고 고정**(모델 카드·평가 재현 절차와 연동).
2. MoE(Qwen3.5-35B-A3B) + LoRA 동시 서빙 조합의 성숙도 — Phase 2 스모크 테스트 항목(F 영역과 공동).
3. 통합 메모리 특성상 KV 캐시·모델·파싱 워커가 메모리를 공유 — 동일 장비에 파서+서빙을 같이 올릴 때 메모리 예산 설계 필요(Phase 1).
