## Presidio 현황

- **저장소**: data-privacy-stack/presidio (microsoft/presidio에서 이관) · 10,494★ · push 2026-08-11 · **MIT**
- 한국어 관련 확인 사항: `ko` 언어 코드 지원, **한국 주민등록번호(RRN) recognizer 내장(2020-10 이전 발급분 체크섬 검증)**, 한국어 recognizer는 기본 비활성 — 명시적 활성화 필요.
- 구조: Analyzer(탐지) + Anonymizer(마스킹/치환) 분리. NER 백엔드로 spaCy/transformers 모델 장착 가능.

## 한국 특화 패턴 커버리지 산정 (커스텀 개발 범위)

| 패턴 | 내장 여부 | 커스텀 개발 난이도 | 비고 |
|---|---|---|---|
| 주민등록번호 | ⭕ 내장(체크섬) | — | 2020-10 이후 발급분(체크섬 폐지)은 형식 검증만 — 오탐 관리 필요 |
| 휴대전화(01X-XXXX-XXXX) | 내장 전화 인식기 있으나 한국 형식 검증 필요 | 하 | 정규식 |
| 사업자등록번호 | ❌ | 하 | 10자리 + 검증식(가중치 체크섬) 존재 — 정밀 탐지 가능 |
| 법인등록번호 | ❌ | 하 | 13자리 + 체크섬 |
| 계좌번호 | ❌ | **중** | 은행별 형식이 상이하고 체크섬 부재 — 숫자열 오탐 위험 큼. "계좌", "입금" 등 문맥 단어 결합 규칙 필요 |
| 학번 | ❌ | 하(형식 확인 후) | 본교 학번 체계 확인 필요(99번 질문) |
| 인명 | NER 필요 | **중~상** | 한국어 NER 모델(transformers 백엔드) 장착 + 임계값 튜닝. 행정 문서 특성상 직함+성명 패턴("홍길동 팀장") 규칙 결합 시 정밀도 상승 |
| 이메일/주소 | 이메일 내장 / 주소 부분적 | 하~중 | 한국 주소는 NER 또는 정규식(도로명) 보강 |

**개발 범위 추정**: 정규식·체크섬 계열(6종)은 recognizer당 소규모(테스트 포함 각 1~2일). 인명 NER은 모델 선정·평가 포함 1~2주 규모. 전체적으로 **Phase 2 내 소화 가능한 범위** — 브리프가 요구한 "미지원 시 커스텀 룰 개발 범위 산정"의 답.

## 설계 반영 사항 (Phase 1 risks.md의 입력)

1. **파이프라인 위치**: 파싱 직후·청킹 이전 단계에 PII 스크리닝 삽입. 원문 보존본(비식별화 전)은 접근 통제된 원본 저장소에만 두고, 인덱스·실적 카드 DB에는 마스킹본만 적재.
2. **마스킹 정책은 역할 구분 필요**: 계획서에는 "담당 부서·직책"이 필요하지만 개인 성명·연락처는 불필요한 경우가 대부분 — 치환 규칙(성명→직책, 연락처→제거)을 사용자와 합의(99번 질문).
3. **평가**: 표본 문서에 대한 PII 탐지 recall을 사람 검수로 측정 — recall 미달 패턴은 규칙 보강. 스캔 문서는 OCR 오류로 패턴이 깨질 수 있음(주민번호 하이픈 소실 등) — OCR 후 텍스트 기준 탐지의 한계를 위험으로 기록.

## 위험
1. **OCR 오류로 인한 탐지 누락** — 스캔본에서 숫자 오인식 시 정규식이 놓침. 완화: 느슨한 패턴 + 체크섬 2단 검증, 표본 검수.
2. 계좌번호 오탐/미탐 트레이드오프 — 문맥 규칙으로도 완전하지 않음. 정책적으로 "숫자 10~14자리 + 금융 문맥어"는 보수적으로 마스킹.
3. 한국어 NER 모델 선정은 미완(후보: KoELECTRA·KLUE-RoBERTa 계열 NER 등) — Phase 2에서 표본 기반 비교 후 확정. **미확인** 상태로 남김.
