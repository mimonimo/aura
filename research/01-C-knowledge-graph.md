# C. 지식 그래프

> 조사일: 2026-08-15
> 브리프 6장 전제: 풀스케일 GraphRAG는 기본 채택하지 않는다. 필요 관계는 `사업 ↔ 프로그램 ↔ 성과지표 ↔ 예산항목 ↔ 장비`로 좁다.

---

## 결론: **도입하지 않는다 (Phase 6 조건부 재검토)**

**정형 DB + 좁은 그래프로 충분하다고 판단한다.** 근거:

1. **필요한 관계가 이미 정형 스키마 안에 있다.** 실적 카드 DB(사업명·연도·예산·성과·부서·장비·출처)가 완성되면 브리프가 명시한 5개 엔티티 관계는 **SQL 외래키/조인으로 표현 가능**하다. "2023년 A사업에서 B장비를 활용한 프로그램의 정량 성과"는 그래프 탐색이 아니라 WHERE 절이다.
2. **GraphRAG 계열의 비용 구조가 본 프로젝트와 역방향이다.** LightRAG/GraphRAG는 **비정형 텍스트에서 LLM으로 엔티티·관계를 추출**해 그래프를 만든다. 우리는 이미 구조화 추출(ZZAIMY-Extract)로 정형 데이터를 뽑는 파이프라인을 구축한다 — 같은 작업을 두 번 하면서 LLM 추출 특유의 관계 환각 위험만 추가된다.
3. **수치 신뢰성 원칙(5.3)과 충돌 위험.** 그래프 요약(커뮤니티 서머리) 경유로 수치가 재서술되면 출처 추적이 끊어진다. 정량 수치는 실적 카드 DB에서 직접 인출하는 단일 경로를 유지해야 한다.
4. **다중 홉 질의 수요가 확인되지 않았다.** 계획서 생성 시 근거 인출은 "유사 사업 실적 검색 + 조건 필터"가 지배적. 다중 홉 추론("이 장비를 쓴 프로그램들이 속한 사업들의 예산 추이")이 실제로 필요한지는 파일럿에서 관찰 후 판단할 사안.

**재검토 트리거(Phase 6)**: ①실적 카드 DB+하이브리드 검색으로 답할 수 없는 질의 유형이 파일럿에서 반복 관찰되고 ②그 질의가 계획서 품질에 실질 기여할 때만, A/B 측정을 전제로 도입한다(브리프 10장 Phase 6과 일치).

## Phase 1 설계 반영 사항

- 실적 카드 DB 스키마에 **관계 표현력을 확보**해 둔다: 사업↔프로그램 외래키, 장비·성과지표는 정규화 테이블(또는 JSON 배열 컬럼 + 인덱스). 이렇게 하면 "좁은 그래프"는 DB 위 뷰(view)로 구현되고, 별도 그래프 스토어가 불필요.
- 검색 계층에서 그래프가 필요해 보이는 질의가 오면 로그로 수집(재검토 트리거 판단 근거).
