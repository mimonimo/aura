# H. 벡터 DB

> 조사일: 2026-08-15
> 평가 축: **메타데이터 필터링 성능**(연도·사업명·문서종류·열람등급), 온프렘 운영 난이도, aarch64 지원.
> 규모 전망: 수만 장 PDF → 청크 수십만~수백만 건 — 어떤 후보든 용량 한계와는 거리가 멂. **분산 확장성보다 필터·운영 단순성이 결정 기준.**

## 결론 요약

| 구분 | 선정 | 근거 |
|---|---|---|
| **추천 1안** | **Qdrant** | dense+sparse 하이브리드 네이티브(RRF), **필터 인식(filterable) HNSW** — 필터 강한 질의에서 성능 저하가 구조적으로 작음. Rust 단일 바이너리·공식 멀티아치(arm64) Docker 이미지로 운영 단순. Apache 2.0, 34k★ 활발 |
| **대안 1안** | **pgvector** (PostgreSQL) | 실적 카드 DB가 어차피 RDB — **벡터·정형·권한·백업을 PostgreSQL 하나로 일원화**하는 강력한 운영 논리. 필터는 SQL 그 자체. 하이브리드는 bm25s 별도 운영 필요. PostgreSQL 라이선스(허용적), arm64 자명 |
| **일체형 대안** | OpenSearch | BM25(Nori 한국어 분석기)+kNN+필터 일체형. 단 JVM 클러스터 운영 부담이 본 프로젝트 팀 규모에 과함 |

**판단 기준 제시**: Phase 1 아키텍처에서 실적 카드 DB를 PostgreSQL로 확정할 것이므로, 실질 선택지는 ①"PostgreSQL(정형) + Qdrant(벡터)" 2-스토어 vs ②"PostgreSQL + pgvector" 1-스토어. **하이브리드 검색 요구(BM25 비중 높음)와 필터 성능을 중시해 ①을 1안으로 추천**하되, 파일럿 규모(수십만 청크)에서는 ②도 충분히 동작하므로 운영 인력이 최소인 경우 ②로 단순화 가능 — Phase 1에서 최종 결정.

## 후보별 판단

### Qdrant — 추천 1안
- **필터 인식 HNSW**: 필터 조건을 그래프 탐색에 통합 — "2022년 이후 + 프로그램 결과보고서 + 열람등급 일반" 같은 강한 필터에서 재현율 붕괴가 없음. 본 프로젝트 질의의 대부분이 강필터 질의라는 점에서 핵심 강점.
- 하이브리드: sparse 벡터 네이티브 + Query API 융합(RRF) — G 영역 1안(Kiwi 토큰 주입)과 결합.
- 운영: 단일 바이너리/단일 컨테이너, 스냅샷 백업. 페이로드(JSON) 인덱스로 문서 메타데이터 관리.
- 위험: 정형 실적 카드 DB와 별도 시스템 — 출처 추적 시 두 스토어 간 ID 정합성 관리 필요(설계로 해소).

### pgvector — 대안 1안
- 실적 카드 DB(PostgreSQL)와 단일 시스템: 조인·트랜잭션·권한(row-level security)·백업 일원화. "실적 카드 → 원문 청크 → 출처 페이지"의 참조 무결성을 DB가 보장 — **수치 출처 추적(5.3) 요구와 궁합이 특히 좋음.**
- HNSW 지원, 수십만~수백만 청크에서 충분한 성능(2026 기준 0.8.x에서 필터 질의 iterative scan 개선).
- 약점: BM25가 없어 하이브리드는 bm25s 별도 + 앱 레벨 융합. 강필터+벡터 동시 질의 성능은 Qdrant 대비 튜닝 부담.

### 탈락 후보

| 후보 | 탈락 이유 |
|---|---|
| **Milvus** | 분산 아키텍처(etcd·MinIO·Pulsar 의존) — 수백만 청크 규모에 과잉. Standalone 모드도 구성요소 다수. 운영 단순성 기준 미달 |
| **Weaviate** | 기능은 충분하나 하이브리드가 자체 BM25(한국어 형태소 미지원, 커스텀 토큰 주입 불가 구조) — 한국어 BM25 요구와 불일치. 모듈 생태계가 클라우드 지향 |
| **OpenSearch** | Nori(한국어) 내장 일체형이라는 고유 강점 있으나, JVM 힙 튜닝·클러스터 관리 등 운영 부담이 커 소수 인력 교내 운영에 부적. 벡터 검색은 전용 DB 대비 후발. 단, 팀에 OpenSearch/Elasticsearch 운영 경험자가 있다면 재평가 여지(99번 질문) |
| **LanceDB** | 임베디드(서버리스)로 개발 편의는 최고이나 다중 서비스(파이프라인 워커 + 웹 UI)가 동시 접근하는 운영 형태에 서버 모드 성숙도 미흡. 프로토타입 단계 실험용으로는 유용 |

## 위험
1. Qdrant 채택 시 2-스토어 정합성 — 청크 ID·문서 ID 단일 발급 체계로 설계(Phase 1).
2. 열람 등급 필터를 "반드시 검색 단계에서" 강제(브리프 9장 risks) — Qdrant 페이로드 필터/pgvector RLS 어느 쪽이든 인덱싱 시점에 등급 메타데이터가 존재해야 함 → 문서 등급 분류 체계를 사용자에게 확인 필요(99번).
