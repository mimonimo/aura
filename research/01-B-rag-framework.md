# B. RAG 프레임워크 / 플랫폼

> 조사일: 2026-08-15
> 판단 포인트: 통합 플랫폼 vs 라이브러리 조립. 본 프로젝트는 커스텀 생성 로직(섹션 루프·배점 검증기·예산 계산기)과 자체 학습 모델 4종 투입이 무겁다.

## 결론 요약

| 구분 | 선정 | 근거 |
|---|---|---|
| **추천 1안** | **Haystack 2.x** (라이브러리 조립) + 도메인 로직은 순수 Python | 명시적 파이프라인·타입 검증 — 공공 영역 시스템의 재현성·감사가능성 요구와 정합. 커스텀 컴포넌트(자체 임베딩·리랭커·검증기)를 1급 시민으로 취급. Apache 2.0 |
| **대안 1안** | **LlamaIndex** | 인제스천→인덱스 경로 최단, 커넥터 생태계 최대(51.6k★, MIT). 파이프라인이 암묵적이라 개입 지점이 상대적으로 불투명 |
| **기각 방향** | 통합 플랫폼(RAGFlow·Dify) 전면 채택 | 하단 탈락 사유 |

**본질 판단**: 이 시스템의 차별화 요소(공고 스키마 추출, 섹션별 생성 루프, 수치 인출 검증, 배점 대조, 예산 계산)는 **어떤 프레임워크도 제공하지 않는 순수 커스텀 로직**이다. 프레임워크의 역할은 인제스천·검색 배관뿐이므로 "가볍게 조립하고 얇게 의존"이 원칙. 프레임워크 없이 직접 조립(벡터DB 클라이언트 + BM25 + 자체 코드)하는 선택지도 Phase 1 설계에서 열어둔다 — 의존 표면적이 줄어 장기 유지보수에 유리할 수 있다.

## 후보별 판단

### Haystack 2.x — 추천 1안
- 파이프라인이 **명시적 DAG**: 모든 컴포넌트(리트리버·리랭커·생성기)가 교체 가능한 노드이고 연결 시 타입 검증. "무엇이 어떤 순서로 실행되는가"가 코드에 그대로 드러남 — 수치 인출 추적·검증 단계 삽입 같은 본 프로젝트의 개입 요구와 정확히 맞음.
- 커스텀 컴포넌트 작성이 공식 1급 패턴 → ZZAIMY-Embed/Rerank/Writer/Extract를 각각 컴포넌트로 감싸 투입.
- 2026년 평가에서도 "금융·법률·정부 등 오답의 대가가 큰 영역"에 권장되는 흐름.
- 위험: LlamaIndex 대비 커넥터 수 열세(본 프로젝트에는 커넥터 수요가 적어 영향 미미).

### LlamaIndex — 대안 1안
- 문서→인덱스 최단 경로, 최다 통합. 초기 속도가 필요하면 유리.
- 위험: 파이프라인이 프레임워크 내부에 암묵적으로 관리 — 커스텀 검증 단계 삽입·감사 시 추상화를 걷어내는 비용. 릴리스 속도가 빨라 버전 추적 부담.

### 탈락 후보와 탈락 이유

| 후보 | 탈락 이유 |
|---|---|
| **Dify** (152k★) | LLMOps 통합 플랫폼 — 노코드 UI·앱 배포가 중심. 섹션 루프·배점 검증기 같은 복잡한 커스텀 파이프라인을 플랫폼 내부에 구겨 넣는 구조가 됨. 라이선스도 표준 Apache가 아닌 커스텀(멀티테넌트 제한 등, 교내 사용에는 무관하나 비표준). 자체 학습 모델 4종의 교체·평가 루프에 개입 지점 부족 |
| **RAGFlow** (88k★) | 문서 이해 특화 통합 엔진으로 완성도는 높으나, 파싱→청킹→검색→생성이 플랫폼 내부에 결합. 우리는 파서(A)·임베딩(D)·서빙(J)을 각각 자체 선정·학습 모델로 통제해야 하므로 플랫폼의 결합이 족쇄가 됨. "부분 채택"(파싱 엔진만 등)도 결합도 때문에 이득 낮음 |
| **txtai** (12.9k★) | 경량·훌륭하나 단독 개발자 중심 프로젝트 — 4개 모델 투입·대규모 파이프라인의 기반으로는 생태계·인력 리스크. 임베딩 DB 겸용 기능은 H 영역에서 전용 벡터DB에 열세 |
| **R2R** (8k★) | **2025-11 이후 커밋 정체** — 활성도 1차 필터 탈락 |

## 위험

1. 프레임워크 얇은 의존 원칙을 지키지 않으면(프레임워크 추상화에 도메인 로직 침투) 향후 교체 비용 급증 — Phase 1 설계에서 경계 명시 필요.
2. Haystack의 한국어 형태소/BM25 통합(Kiwi 등)은 커스텀 컴포넌트로 직접 작성 필요(G 영역과 연동) — 공식 지원 아님.
